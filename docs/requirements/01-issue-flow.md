# Issue の流れと運用（棚卸し・並列・間隔・状態の遷移・運用の規則）

## 棚卸し（進行役）

- FLOW-1 Project 7 の Issue を読み、次の条件をすべて満たすものだけを候補にする
  - 人が付けたラベル `agent-ready` がある
  - マイルストーンがある。複数あれば、版の小さいマイルストーンを先にする
  - Project の Status が Todo
  - Issue 依存（blocked by）の相手がすべて閉じている
  - `needs-human` ラベルが無い（人が外すまで再着手しない）。Project の Agent 欄が `human`（人が引き取った）でない
  - 受け入れの下書きコメント（進行役の投稿、`intake` の印。「[印と固定の見出しの一覧][f04]」）があり、人が `agent-ready` を付けている（TEXT-12）。本文を渡すか下書きだけを渡すかは、印の値ではなく、渡す直前に Issue の著者の権限（TEXT-10）から決める（印の値は編集で書き換えられるため）
  - `agent-ready` を付けた人が push 以上の権限を持つ（Issue の timeline で確かめる。TEXT-10）
- FLOW-2 候補を着手前の予測で待たせない。待たせるのは人が入れた依存だけ。触る範囲の重なりは着手後に実際の変更ファイルで見て、警告のコメントに留める（FLOW-8）
- FLOW-3 1 回の実行で着手する件数に上限を持つ（最初は 1 件）。進行中の Issue（`In Progress` 以降で `Done` でない）の数にも上限を持つ（WIP の上限。段階 8 までは 1）。上限に達していれば新しい Issue に着手しない
- FLOW-4 **1 回の実行で進める範囲**。進行役は Issue ごとに 1 回の実行で 1 段だけ進める。段は、受け入れ、計画、実装と PR の作成、レビュー（批評を含む）、修正、マージの判定、マージ後の片付け。
  進行中の Issue は、毎回の実行で GitHub の状態（Status、PR の有無と draft、最新の印の種類と `head`、必須チェックの結果）から「次の段」を決定的に決めて再開する。手元の記録は使わない（「運用の規則」）。
  CI は実行の中で待たず、次回の実行で結果を読む（IMPL-27）。1 回の実行の所要時間の上限を設定に持ち、超えたら残りの Issue は次回に回す（lock を長く持たない）。
  1 日 1 回の間隔では 1 Issue に 1 週間ほどかかる。間隔を狭める判断は FLOW-12
- FLOW-5 実行の記録（選んだ Issue、待たせた Issue と理由、使った時間）を追跡しないフォルダに残す。
  AI のセッション 1 回ごとの記録は欄を固定し、後から集計できる形にする：実行 ID、Issue 番号、ラウンド、役（受け入れ・計画・作業・レビュー・批評）、指定したモデルと effort、実際に使われたモデル（`--output-format json` の `modelUsage` から取る。安全側のフォールバックで別のモデルに回ったことを検知する）、費用、ターン数、実行の成否、作業の成否。
  IMPL-14 の `usage` と FLOW-13 の指標はこの欄から取る（Langfuse のような観測の道具が持つ「セッションごとのトレースに費用と成否を結びつける」形を、道具は入れずに欄として写す）

## 並列と競合

- FLOW-6 Issue ごとに worktree を分け、同時に複数の Issue を進められる
- FLOW-7 競合の正は人が入れる Issue 依存（blocked by）。進行役はそれに従う
- FLOW-8 競合の予測は AI にさせない。作業 AI の commit が出た時点で、進行役がその PR の変更ファイルを他の進行中の dev-autopilot の PR の変更ファイルと機械で比べ、重なりがあれば「待つ」ではなく Issue に「警告のコメント」を 1 回書く（FLOW-2）
- FLOW-9 先行の PR がマージされたら、依存していた PR を `develop` に載せ直してから続ける
- FLOW-10 依存で待つ Issue は Status・Agent 欄・ラベルを変えない（`Blocked` にしない。`Blocked` は人が引き取るまで触らない意味で使う）。GitHub の Issue 依存（blocked by）の表示が印になる。
  進行役は待たせた理由を記録に残し、Issue には 1 回だけコメントする（同じ理由で毎回コメントしない）。先行が閉じたら次回の実行で自動で続ける。
  作業中（`In Progress` 以降）に人が依存を足したときも同じで、その Issue のレビューと対応ループを止めて待ち、worktree と PR は残す。先行がマージされたら FLOW-9 のとおり載せ直してから続ける

## 間隔の運用

- FLOW-11 間隔と件数の上限は設定ファイル 1 つで変える（cron の設定と、進行役の上限の両方）
- FLOW-12 狭める条件：連続 7 回の実行で `needs-human` が 0 件、利用枠の消費が上限内。1 段ずつ狭める（1 日 1 回 → 12 時間 → 6 時間）
- FLOW-13 測る指標を記録に残す：マージ率（着手した Issue のうちマージに届いた割合）、往復の回数、人が却下した指摘の割合（誤検知率）、**マージ後の revert 率**（Codex 6.1%・Devin 14.5%・人 11.5% という調査がある）、1 Issue あたりの利用枠。
  revert 率は「マージした後に壊れていた」を測る唯一の値なので、進行役のマージの判定を信頼してよいか（段階 8 の出口と、将来マージの実行を進行役に移すか）の判断に使う
- FLOW-14 **指標の記録は GitHub に置く**。却下：人が PR に「## 却下 R<n>」の見出しでコメントし、却下する指摘の見出しを列挙する。進行役は、push 以上の権限を持つ人が書き、進行役の印を持たないこの見出しのコメントだけを数える（AI の出力に同じ見出しがあっても数えない。IMPL-20。検疫（TEXT-11）を通し、AI には渡さない）。
  一致：MERGE-3 の数え方。手元の記録は集計の写しであって正ではない

## Issue の状態の遷移

Issue の状態は 3 つの欄で表し、正は GitHub に置く（「運用の規則」）。進行役は毎回の実行でこの 3 つから状態を組み立て直す。

- Project の Status：`Todo` → `In Progress` → `In Review` → `Ready to Merge` → `Done`。止まったときは `Blocked`（SETUP-5）
- Project の Agent 欄：空 / `worker` / `reviewer` / `human` / `paused`。「いま動いている役、または次に動く役」を表す（SETUP-6、IMPL-7）
- ラベル：`agent-ready`（人が処理対象にした）、`needs-human`（人が引き取るまで進行役は触らない）、`from-review`（🟢 を起票した Issue）（SETUP-8）、`plan:fable` / `plan:opus`（人が計画役のモデルを上書きする。無ければ受け入れの印に従う。IMPL-10）

表の読み方：Status・Agent 欄・ラベルの列は遷移の後の値。「変えない」はその遷移で触らない欄。番号は正常な順が FLOW-15〜FLOW-27、止まる遷移が FLOW-28〜FLOW-34。

止まった状態から戻す手順（人だけが行う）：

- `needs-human`：原因を直してからラベルを外し、Status を戻す。PR が無ければ `Todo`（棚卸しで選び直す）、PR があれば `In Review`（進行役が次回の実行で PR の状態から再開する）。Agent 欄が `human` なら `worker` に戻す
- `human`：返すときは Agent 欄を `worker` に戻す。Status は触った内容に合わせて人が直す
- `paused`：再開するときは Agent 欄を空か `worker` に戻す
- 依存の待ち（FLOW-33・FLOW-34）：人の操作は要らない。先行の Issue が閉じれば、次回の実行で進行役が続ける。待ちを解きたければ人が依存（blocked by）を外す

決まり：

- `needs-human` を付けるときは、どの契機でも Status を `Blocked` にする（`Todo` のままだと翌日また選ばれるため）
- 進行役は Agent 欄を `human` と `paused` にしない。この 2 つは人の意思表示で、進行役は読むだけ。`human` の Issue と PR には進行役は触らない
- 進行役が起票する 🟢 の Issue（`from-review`）は、Project に入れて Status を `Todo` にし、マイルストーンと `agent-ready` は付けない。人がマイルストーンを付けたら受け入れ（TEXT-12）が下書きを用意し、人が `agent-ready` を付けるかを決める（IMPL-26）
- 段階による違い：段階 5 では FLOW-21 の Agent 欄が `human`（人がレビュー）、段階 7 では FLOW-24 の印を書かない（shadow）。段階ごとの振る舞いは設定の `stage` で切り替える（STRUCT-2）
- Status と Agent 欄の更新はすべて進行役が GraphQL で行い、AI のセッションは触らない（IMPL-5、「[Issue と PR の本文の扱い][f04]」）。更新は冪等で、すでにその値なら何もしない

## 運用の規則

- 状態の正は GitHub に置く（PR の有無と draft、印、Status、Agent 欄、ラベル）。進行役は毎回そこから状態を組み立て、手元の記録は補助にする。各手順は「すでに済んでいれば何もしない」（PR があれば作らない、コメントがあれば足さない）
- 多重起動を lockfile で防ぐ。launchd の自動実行と人の `/dev-autopilot` の手動実行も同じ lock を取る。lock には PID・ホスト名・起動時刻を書き、PID が生きていなければ古い lock として奪う（電源断の後に全実行が「多重起動」で止まり続けないため）。
  lock で見送った実行と、Mac のスリープで launchd が起動しなかった日は記録に残し、`check` が warn に出す（段階 4 の「7 回の実行」はこれらを除いて数える）
- 止める合図：設定ファイルの `enabled: false`（全体）、Project の Agent 欄 `paused`（その Issue）。進行役は毎回の最初に読む
- 書かずに試す合図：設定ファイルの `dryRun: true`。進行役は GitHub への書き込み（コメント・ラベル・Project の欄・PR）をすべて手元の記録に「書くつもりだった内容」として残し、実際には書かない。読むことと AI のセッションは行う（段階 4 の最初と、新しい段階に入るときに使う）
- 進行役が途中で死んだら、次回の実行が GitHub の状態から復旧する（FLOW-4 の「次の段」の決め方）。復旧できない組み合わせ（GitHub の状態から次の段を決められないもの）はその Issue を `needs-human`。作業場所はセッションごとに作り直すので、作業場所の有無は復旧の判定に使わない（[ADR-20261013-001][adr-workspace]）。Issue に紐づかない作業場所の残骸は `check` の fail（SETUP-2、UNDECIDED-27）
