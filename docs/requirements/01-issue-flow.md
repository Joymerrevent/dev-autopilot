# Issue の流れと運用（棚卸し・並列・間隔・状態の遷移・運用の規則）

## 棚卸し（進行 Bot）

- FLOW-1 **着手の条件**。決定済みの作業の単位（有効な `agent-ready` と `decision` の印がある。FLOW-36、FLOW-41）のうち、次をすべて満たすものだけを、計画の輪（T7。FLOW-37）に進める。外れたら決定済みのまま待つ（[ADR-20261024-001][adr-model-states] の決定 10）
  - マイルストーンがある。複数あれば、版の小さいマイルストーンを先にする（着手の条件を満たした作業を計画に進める順は、基本設計で決める）
  - 進行中の作業の単位の数が上限の内（FLOW-3）
  - 基線（base ブランチの必須チェック）が緑（IMPL-9）
  - 重ねる軸（止め方・先の依頼・安全）がどれも（なし）で、全体の停止の Issue が無い（FLOW-38、SAFE-19）
  - 渡す文は、人が決めたマスターの下書き。Issue の本文は、著者を問わず渡さない（TEXT-1、[ADR-20261016-002][adr-draft]）
- FLOW-2 候補を着手前の予測で待たせない。待たせるのは人が入れた依存だけ。触る範囲の重なりは着手後に実際の変更ファイルで見て、警告のコメントに留める（FLOW-8）
- FLOW-3 1 回の実行で着手する件数に上限を持つ（最初は 1 件）。進行中の Issue（計画済みから、マージ済み・閉鎖済みの前までの作業の単位。重ねる軸に値がある作業も数える。[ADR-20261024-001][adr-model-states] の決定 10。数え方は基本設計の「[状態遷移と判定][design-flow]」）の数にも上限を持つ（WIP の上限。並列化（段階 9）に入るまでは 1）。上限に達していれば新しい Issue に着手しない
- FLOW-4 **1 回の実行で進める範囲**。進行 Bot は、AI のセッションを起動する工程（重い工程：下書きと書き直し、計画の輪、変更の作成、レビュー（批評を含む）、直し（検査の失敗・指摘・衝突）、先の依頼が中止されたときの計画の見直し）を、作業の単位ごとに 1 回の実行で 1 つだけ進める。
  AI のセッションを起動しない工程（軽い工程：検疫、マスターの下書きの投稿、決定の印、マージの判定、載せ直し、催促、片付け）は、重い工程の前後に同じ実行で続けてよい。CI の結果が要る工程（レビュー、マージの判定）は CI の結果が出ている実行でだけ進め、push した実行では push した作業の単位を次の実行まで進めない（[ADR-20261015-006][adr-flow]、[ADR-20261024-003][adr-check-first]）。
  進行中の作業の単位は、毎回の実行で GitHub の状態（人の操作、印、PR、必須チェックの結果）から状態を決め（FLOW-41）、状態から次の工程を決定的に決めて再開する。手元の記録は判定に使わない（上限の数え上げにだけ使う。「運用の規則」）。
  CI は実行の中で待たず、次回の実行で結果を読む（IMPL-27）。1 回の実行の所要時間の上限を設定に持ち、超えたら残りの作業は次回に回す（lock を長く持たない）。
  1 日 1 回の間隔では 1 Issue に 1 週間ほどかかる。間隔を狭める判断は FLOW-12
- FLOW-5 実行の記録（選んだ Issue、待たせた Issue と理由、使った時間）を追跡しないフォルダに残す。
  AI のセッション 1 回ごとの記録は欄を固定し、後から集計できる形にする：実行 ID、Issue 番号、ラウンド、役（受け入れ・計画・作業・レビュー・批評）、指定したモデルと effort、実際に使われたモデル（出力（IMPL-14 の `stream-json`）の `modelUsage` から取る。安全側のフォールバックで別のモデルに回ったことを検知する）、費用、ターン数、実行の成否、作業の成否。
  IMPL-14 の `usage` と FLOW-13 の指標はこの欄から取る（Langfuse のような観測の道具が持つ「セッションごとのトレースに費用と成否を結びつける」形を、道具は入れずに欄として写す）

## 並列と競合

- FLOW-6 Issue ごとに作業ブランチを分け、作業場所は AI のセッションごとに作る（[ADR-20261013-001][adr-workspace]）ので、同時に複数の Issue を進められる
- FLOW-7 競合の正は人が入れる Issue 依存（blocked by）。進行 Bot はそれに従う
- FLOW-8 競合の予測は AI にさせない。作業 AI の commit が出た時点で、進行 Bot がその PR の変更ファイルを他の進行中の dev-autopilot の PR の変更ファイルと機械で比べ、重なりがあれば「待つ」ではなく Issue に「警告のコメント」を 1 回書く（FLOW-2。1 回かどうかは `overlap` の印で判定する）
- FLOW-9 base が進んだら（先の PR がマージされたときを含む）、レビュー合格の PR だけを `develop` に載せ直す（FLOW-44）。ほかの状態の PR は、レビュー合格になってから載せ直す。基線が緑でない間は載せ直しを待ち、作った PR のレビューと直しは続ける（IMPL-9、[ADR-20261015-006][adr-flow] の決定 2、[ADR-20261024-006][adr-cleanup]）
- FLOW-10 先の依頼で待つ作業の単位は、先の依頼の軸の値（未完了（D1）・中止あり（D3）。FLOW-38、FLOW-43）で表し、Project の「先の依頼」の欄に出す。止め方は停止中にしない（停止中は人が対処する意味で使う）。GitHub の Issue 依存（blocked by）の表示が印になる。
  進行 Bot は待たせた理由を記録に残し、Issue には 1 回だけコメントする（同じ理由で毎回コメントしない。1 回かどうかは `wait` の印で判定する）。先の作業がマージされたら、次回の実行で自動で続ける（FLOW-43）。
  PR ができた後に人が依存を足したときも同じで、その作業の単位のレビューと直しを止めて待ち、作業ブランチと PR は残す

## 間隔の運用

- FLOW-11 間隔と件数の上限はリポの設定 1 つで変える（定期の実行の間隔と、進行 Bot の上限の両方。STRUCT-2）。間隔は OS ごとの定期の実行の登録にも書くので、間隔を変える PR の後は、動かすマシンで `setup` を実行し直して登録し直す（登録し直すまで、`check` がずれを fail にして止まる。基本設計の「[導入と点検][design-setup]」）
- FLOW-12 狭める条件：連続 7 回の実行で、停止中か攻撃の疑いになった作業の単位が 0 件、利用枠の消費が上限内。1 段ずつ狭める（1 日 1 回 → 12 時間 → 6 時間）
- FLOW-13 測る指標を記録に残す：マージ率（着手した Issue のうちマージに届いた割合）、往復の回数、人が却下した指摘の割合（誤検知率）、**マージ後の revert 率**（Codex 6.1%・Devin 14.5%・人 11.5% という調査がある）、1 Issue あたりの利用枠。
  revert 率は「マージした後に壊れていた」を測る唯一の値なので、進行 Bot のマージの判定を信頼してよいか（将来マージの実行を進行 Bot に移すか（MERGE-9）と、ほかのリポに広げる時期（UNDECIDED-82））の判断に使う
- FLOW-14 **指標の記録は GitHub に置く**。却下：人が PR に「`## 却下 R<n>`」の見出しでコメントし、却下する指摘の見出しを列挙する。進行 Bot は、push 以上の権限を持つ人が書き、進行 Bot の印を持たないこの見出しのコメントだけを数える（AI の出力に同じ見出しがあっても数えない。IMPL-20。検疫（TEXT-11）を通し、AI には渡さない）。
  一致：MERGE-3 の数え方。手元の記録は集計の写しであって正ではない

## Issue の状態の遷移

作業の単位（Issue 1 件と、結びつく PR）の状態は、主な流れの状態と、主な流れに重ねる 3 本の軸（止め方・先の依頼・安全）で表す（[ADR-20261024-001][adr-model-states]）。
状態の正本は GitHub だけで、進行 Bot は毎回の実行で、人の操作（ラベルと見出しのコメント）・進行 Bot の署名付きの印・PR・必須チェックの結果から状態を組み立てる。Project の欄は進行 Bot が書く表示で、判定には読まない。
主な流れの状態と線、重ねる軸の図は、[Issue の流れ][issue-flow-diagram]（図は本節の写し）。線の番号（主な流れは T、止め方は S、先の依頼は D、安全は Q）は図と同じで、ほかの要件は番号で線を指す。状態ごとに GitHub の何を読んで決めるかは、基本設計の「[状態遷移と判定][design-flow]」。

2026-10-24 に、Project の Status・Agent 欄・`needs-human` で状態を表す形（FLOW-15〜34）をやめ、本節の形に組み直した。組み直す前の遷移は、節の最後の「組み直す前の遷移（欠番）」に取り消し線で残してある。

- FLOW-35 **作業の単位と、主な流れの状態と線**。作業の単位は、Issue が起票されて Project に入ったときに生まれる（Project の自動追加。SETUP-1）。人が決める前の Issue も追う。

- FLOW-36 **依頼の流れ**（[ADR-20261024-004][adr-master]）。依頼の今の文は「マスターの下書き」1 つにまとめる。下書き済みに入るたびに（T2・T3・T30）、進行 Bot がマスターを新しいコメントで投稿し（`draft` の印。印と見出しの形は「[印と固定の見出しの一覧][f04]」）、前の版を「古い（outdated）」として畳む（FACT-72。[10-verified-facts.md][f10]）。AI に渡す文は、いつも人が決めたマスター（TEXT-1）
  - 入口の検疫：Project に入った Issue のうち、入口の検疫の印（`quarantine`）が無いものを、進行 Bot が検疫する（TEXT-9、TEXT-11）。通れば検疫済みになり（T29）、受付 AI が Issue の文を読んで下書きを書く（T2。TEXT-12）。見つかったときは FLOW-38 の安全の軸（Q1）
  - 人の直し：push 以上の人が、マスターを写して直した全文を `## 作業指示` に書く（投稿か編集）。最新の作業指示がマスターより新しければ直し済み（T4）で、進行 Bot が検疫してから全文を新しいマスターに写す（T30）。作業指示が 2 つ以上あっても止めず、最新の 1 つを読む
  - 差し戻し：push 以上の人が、直してほしい点を `## 差し戻し` に書く（T5）。受付 AI が、マスターと頼みと Issue の文を読んで書き直す（T3）
  - 決める：`agent-ready` は、push 以上の人が最新のマスターより後に付けたときだけ有効（下書きの前、直し済みの間、書き直しの前に付けたラベルは無効）。無効なラベルは進行 Bot が外し、理由を書く（`approval-reset` の印）。有効なラベルを見つけたら（T6）、進行 Bot は決めたマスターのハッシュを `decision` の印に書き、マスターに書いた依存とマイルストーンの候補（人が Issue に先に付けていれば人の値）を Issue に付ける
  - 決めた後：決定済みより後は、`## 作業指示` も Issue の本文も読まない。決めた後の作業指示は、読まなかったことを 1 回だけ知らせる（`ignored-instruction` の印）。依頼を変えるときは、止めてから `## 再開 下書きから` で戻す（FLOW-40）
- FLOW-37 **作業の流れ**（[ADR-20261024-002][adr-no-stages]、[ADR-20261024-003][adr-check-first]）。どの作業も、最初から決まった担い手が行う（段階で担い手を変えない）
  - 計画の輪：決定済みで着手の条件（FLOW-1）を満たしたら、計画 AI が計画を書き、計画を書いた AI とは別の AI が確かめ、直す点があれば同じ回の実行で計画し直す（IMPL-10）。確かめを通った計画だけを投稿する（T7）。上限まで計画し直しても直す点が残れば、計画を投稿せずに停止中（`plan-limit`）にし、止めた理由のコメントに最後の指摘を書く。確かめの結果は計画コメントに書かない。人が計画を読むことは決まりにしない
  - 変えてはいけないパス：計画の輪の後に、計画が変える見込みのパスを照らし、当たれば計画済みのまま停止中（`protected-path`。S5）にする（IMPL-10、IMPL-15）
  - 変更の作成：計画済みから、作業 AI が計画に沿って変更を作り、進行 Bot が漏えいの検査と変えてはいけないパスの検査（IMPL-15）を通してから push し、PR にする（T8。IMPL-1〜IMPL-7）
  - 検査の後にレビュー：レビュー（変更の確かめ）は、head の必須チェックがすべて通ってから行う（T9 の後）。直す点が無ければレビュー合格（T11）、あればレビュー不合格（T12。IMPL-16、IMPL-18）。必須チェックが落ちたら（T10）、レビューせずに作業 AI が先に直す（T13。IMPL-27）。レビュー合格の後に必須チェックが落ちても、検査不合格として直す
  - 直し：レビュー不合格なら作業 AI が指摘を直す（T14。IMPL-23）。検査の失敗の直し（T13）と衝突の直し（T20）を含め、AI の直しは往復に数える（IMPL-24）
  - 人の push：人が PR に push したら、変更の枠のどの状態からも変更済みに入り（T16）、検査からやり直す。人の push の後の再レビューは往復に数えない（IMPL-24）
  - レビュー合格の間に、進行 Bot がマージの判定の印（`merge`）を書く（MERGE-2、MERGE-3）。レビュー合格に入るとき（T11）に、見送った 🟢 を新しい Issue にする（`follow-up` の印。IMPL-26）。レビュー合格のまま決めた日数を過ぎたら、1 回だけ催促する（`remind` の印）。マージは人（T15。レビュー合格の前に人がマージしたときは T22）

- FLOW-39 **Project の表示**（[ADR-20261024-001][adr-model-states] の決定 5）。進行 Bot は、毎回の実行で、主な流れと軸ごとに 1 つの欄を Project に書く。どれも表示だけで、判定には読まない。次に動く担い手（「次の番」）の欄は持たない

  | 欄 | 中身 |
  | --- | --- |
  | 主な流れの枠 | 依頼・計画・変更・終了（もともとある Status 欄の名前を変えて使う。変えられなければ、同じ働きの欄を新しく作る） |

- FLOW-40 **止めて人に渡すことと、再開**（[ADR-20261024-001][adr-model-states] の決定 7）。進行 Bot が止めるときは（S5）、止め方を停止中にし、`stop` の印に止めた理由の記号を書き、止めた理由のコメントに人がすることを書く。止まっている間も主な流れの状態は変わらない
  - 止める場面と記号は次の表で、どれも止め方の S5。実装の都合で止める理由の記号は、詳細設計で足す。AI の作業の失敗は、続くまでは同じ状態からやり直す

    | 記号 | 止まる場面 | 止める要件 |
    | --- | --- | --- |
    | `retry-limit` | AI の作業の失敗が続いた | IMPL-14 |
    | `round-limit` | 直す往復が上限に達した | IMPL-24、MERGE-6 |
    | `repeated-finding` | 直したはずの指摘がまた出た | IMPL-24 |
    | `plan-limit` | 計画の輪が上限まで回っても終わらない | FLOW-37、IMPL-10 |
    | `cost-limit` | 費用の上限に達した | IMPL-14 |
    | `pr-closed` | PR だけが閉じられた | IMPL-6 |
    | `cleanup-failed` | 片付けが失敗し続けた | FLOW-42 |
    | `plan-change` | 先の依頼が中止になり、AI が計画を変える必要があると判断した（D5） | FLOW-43 |
    | `unauthorized-close` | push 未満の人が Issue を閉じた | FLOW-42 |
    | `protected-path` | 変えてはいけないパスに当たった（計画の後か、push の前） | FLOW-37、IMPL-10、IMPL-15 |
    | `manual-push` | push で効くものの差分を人に渡した | IMPL-15 |
    | `marker-invalid` | 進行 Bot の印が書き換えられた | IMPL-20、TEXT-4 |
    | `ci-action-required` | CI を動かすのに人の承認が要る | IMPL-27 |
    | `ci-stale` | 取り消しなどの結果のまま、決めた時間を過ぎた | IMPL-27 |

  - 検疫で見つかったときは、止め方でなく安全の軸に値を入れる（FLOW-38）
  - 再開（S6）：push 以上の人が書いた最新の `## 再開 <戻す先>` を R とする

    | 戻す先 | 数えないもの | 続ける状態 |
    | --- | --- | --- |
    | 続きから | 無い | 同じ状態。PR が閉じているときは選べない |
    | 計画から | R より前の `plan`・`review`・`fix`・`merge`・`conflict` の印と、R より前の PR。開いている前の PR は、進行 Bot が閉じる | 決定済み（AI が計画し直す） |
    | 下書きから | 計画からの数えないものに加えて、R より前に付けた `agent-ready` と、R より前の `decision` の印 | 依頼の中の状態（ふつうは下書き済み。マスターより新しい `## 作業指示` があれば直し済み）。人は依頼を読み直して決め直す |

  - 一時停止中（S1）と引き取り中（S3）は、ラベルを外せば（S2・S4）続きから。ほかの戻す先にしたいときは、ラベルを外す前に `## 再開 <戻す先>` を書く
  - 印の書き換え：進行 Bot の印の署名が合わないか、印が編集されたら、誰が書き換えても停止中（`marker-invalid`）にし、`stop` の印と止めた理由のコメントに書き換えられた印を挙げる。人が確かめて再開した後は、挙げた印を無いものとして読み、読んだ結果の状態から続ける。再開の後に新しく書き換えられた印では、また止める（IMPL-20）
- FLOW-41 **状態の決め方**（[ADR-20261024-001][adr-model-states] の決定 6）。進行 Bot は、戻した後の読み方（FLOW-40）で数えない印と PR を外してから、主な流れの状態を決め、軸の値を決める。主な流れは、事実が重なったときは進んだほうを先に見る（終了 → 変更 → 計画 → 決定 → 依頼）。変更の枠の中だけは、検査不合格をレビュー合格より先に見る（レビュー合格の後に必須チェックが赤に変わったら、検査不合格と読み、マージの前に赤を見逃さない）。決定済みより後の状態では `agent-ready` を読まない。状態ごとの条件は、基本設計の「[状態遷移と判定][design-flow]」
- FLOW-42 **片付けと、Issue を閉じた人**（[ADR-20261024-006][adr-cleanup]）
  - マージ済みでは、進行 Bot が Issue を閉じ、作業ブランチと作業場所を消して、完了にする（T27）。閉鎖済みでは、進行 Bot が開いた結びつく PR を閉じ、作業ブランチと作業場所を消して、中止にする（T28）。どちらも `cleanup` の印を書く（MERGE-7）
  - 片付けは AI を使わない進行 Bot の工程で、軸の値と全体の停止を問わず行い、軸の値（ラベル、見出し）は書き換えない。片付けが失敗し続けたら、片付けの前の状態のまま停止中（`cleanup-failed`。S5）にし、人が再開するまで片付けもやり直さない
  - 作業場所を消す前の確かめ（[ADR-20261013-001][adr-workspace]）に外れたら、消さずに止める（記号は詳細設計で足す）
  - 閉鎖済みに入るのは、push 以上の人が Issue を閉じたときだけ（T21。閉じた人は Issue の timeline で確かめる）。push 未満の人（Issue を書いた外の人、Triage の役の人など。FACT-73）が閉じたときは、閉じる前の状態のまま停止中（`unauthorized-close`。S5）にし、片付けない。結びつく PR がマージされていれば、誰が閉じてもマージ済みとして読む（T15・T22）
- FLOW-43 **先の依頼**（[ADR-20261024-006][adr-cleanup]）。先の依頼（blocked by）は、決定済みと、決定済みより後の状態で効く（D1）。PR ができた後に足された先の依頼も待つ（確かめと直しも止める）。起票済みから下書き済みまで（直し済み・差し戻し済みを含む）は待たない
  - 先の作業の結びつく PR がマージされたら（マージ済みか完了）、片付けを待たずに同じ状態から続ける（D2）
  - 先の作業を push 以上の人が閉じ、PR がマージされていなければ（閉鎖済みか中止）、中止ありにする（D3）。計画を確かめる AI が、先の依頼が中止されたことを踏まえて今の計画を見直し、`dependency-review` の印に結果を書く。計画を変えずに進めてよければ（なし）に戻して続け（D4）、変える必要があれば（なし）に戻したうえで停止中（`plan-change`。S5）にし、AI の判断と理由を書いて、人に戻す先を選ばせる（D5）。後の作業が決定済み（計画の前）なら、見直さずに（なし）に戻す（D4）。先の依頼が 2 つ以上あれば 1 つずつ見直し、どれかが変える必要ありなら止める
  - 待っていることは、Project の「先の依頼」の欄に出し、Issue に 1 回だけコメントする（`wait` の印。FLOW-10）
- FLOW-44 **載せ直し**（[ADR-20261024-006][adr-cleanup]）。base が進んだら（ほかの PR か先の作業がマージされた）、レビュー合格の PR だけを載せ直す。ほかの状態の PR は、レビュー合格になってから載せ直す。差分（MERGE-6 の比べ方）が同じならレビュー合格のまま（T17）、変わったら変更済み（T18）、衝突したら衝突あり（T19。`conflict` の印）で、作業 AI が衝突を解く（T20。往復に数える）。基線が緑でない間は、載せ直しを待つ（IMPL-9）
- FLOW-45 **状態遷移に入れない出来事**（[ADR-20261024-001][adr-model-states] の決定 8）

  | 出来事 | 扱い |
  | --- | --- |
  | 決めた後に依頼が変わる（`## 作業指示` が書かれた、Issue の本文が変わった） | 読まない（FLOW-36） |
  | レビュー合格の後に検査が落ちる | 検査不合格と読む（FLOW-41） |
  | 触ってはいけない所を変える | 停止中（`protected-path`）。人が `## 仕組みの変更の承認` で認めれば変えられる（IMPL-15） |
  | 記録が書き換えられる | 停止中（`marker-invalid`。FLOW-40） |
  | 人が順番を飛ばす（下書きの前に決める） | ラベルを数えず、進行 Bot が外す（FLOW-36） |

止まった状態から戻す手順（人だけが行う）：

- 停止中：止めた理由のコメント（`stop` の印）を読み、原因を直してから、push 以上の人が `## 再開 <戻す先>` を書く（S6。FLOW-40）。止めた理由ごとに人がすることは、次の表。実装の都合で止めたときは、止めた理由のコメントに書いた手順に従う

  | 記号 | 人がすること |
  | --- | --- |
  | `retry-limit` | 実行の記録で失敗の原因を確かめ、直してから `続きから`。1 セッションに収まらない大きさの作業は、Issue を分ける（UNDECIDED-26） |
  | `round-limit` | 往復の回数は PR の初めから数え、再開しても数え直さない（IMPL-24）。人が直して push してから `続きから`（人の push の後の再レビューは往復に数えないが、直す点が出ればまた止まる）。作業 AI に続けさせるなら、リポの設定の `limits.roundTrips` を上げる PR をマージしてから `続きから`。作り直すなら `計画から`（前の PR は進行 Bot が閉じ、往復は新しい PR で数える） |
  | `repeated-finding` | 人が直して push してから `続きから`（人の push の後のラウンドでは、同じ指摘の再発を判定しない）。往復の上限を上げても止まり方は変わらない。作り直すなら `計画から` |
  | `plan-limit` | 止めた理由のコメントの最後の指摘を読む。依頼を直すなら `下書きから`、計画し直させるなら `計画から` |
  | `cost-limit` | 1 Issue の累計は数え直さない（IMPL-14）。続けるなら、リポの設定の `limits.issueCostUsd` を上げる PR をマージしてから `続きから`。上げないなら、Issue を閉じるか、小さい Issue に分けて元の Issue を閉じる |
  | `pr-closed` | やめるなら、push 以上の人が Issue を閉じる（FLOW-42）。続けるなら、PR を開き直してから `続きから`。作り直すなら `計画から` か `下書きから` |
  | `cleanup-failed` | 止めた理由のコメントに挙がった、消せなかったものを確かめ、原因を直してから `続きから`（片付けをやり直す） |
  | `plan-change` | AI の判断と理由を読み、計画を変えるなら `計画から`、依頼から直すなら `下書きから`、変えなくてよければ `続きから` |
  | `unauthorized-close` | やめるなら、push 以上の人が Issue を開き直してから閉じ直す。続けるなら、Issue を開き直してから `続きから` |
  | `protected-path` | 計画か変更が触れたパスを確かめる。変えてよければ、maintain 以上の人が `## 仕組みの変更の承認` に認めるパスを書いてから `続きから`。変えさせないなら `下書きから` で依頼を直す |
  | `manual-push` | Issue に載った差分を確かめ、人が自分で作業ブランチに push する（push の後の PR の作り方は基本設計）。push しないなら `計画から` か `下書きから` |
  | `marker-invalid` | 止めた理由のコメントに挙がった印のコメントを確かめる（誰がいつ編集したか、印の署名の鍵を替えたか）。印のコメントは、直さず、消さない。続けてよければ `続きから`（挙がった印は無いものとして読む）。鍵が漏れたときの手順は [ADR-20261021-004][adr-marker-keys] の決定 3 |
  | `ci-action-required` | GitHub で CI の実行を認めてから `続きから` |
  | `ci-stale` | CI を動かし直すか、原因を確かめてから `続きから` |

- 一時停止中・引き取り中：ラベル（`agent-paused`・`agent-manual`）を外す（S2・S4）。続きから以外にしたいときは、外す前に `## 再開 <戻す先>` を書く
- 攻撃の疑い：maintain 以上の人が、見つかった種類と場所（`security` の印のコメント）を見て文を直してから、`## 安全の確認` を書く（Q3・Q4）。見つかった文が残っていれば、次の検疫でまた止まる。全体の停止は、全体の停止の Issue に `## 安全の確認` を書いて閉じる（SAFE-19）
- 先の依頼の待ち：人の操作は要らない（先の作業がマージされたら D2、閉じられたら D3）。待ちを解きたければ、人が依存（blocked by）を外す
- 決めた後に依頼を変えたいとき：`agent-paused` を付け（S1）、`## 再開 下書きから` を書き、`agent-paused` を外す（S2。停止中なら `## 再開 下書きから` を書くだけ）。進行 Bot が残った PR を閉じ、下書き済みに戻る。人はマスターを直してから決め直す（`agent-ready` を外して付け直す）
- 着手した作業をやめるとき：push 以上の人が Issue を閉じる（T21）。進行 Bot が、開いた PR を閉じ、作業ブランチと作業場所を消す（T28。FLOW-42）

決まり：

- 進行 Bot は、人の操作の手段（ラベル `agent-ready`・`agent-paused`・`agent-manual` と、人の見出し）を書かない。例外は、無効な `agent-ready` を外すこと（FLOW-36。見た目を合わせるためだけで、外し損ねても無効と読む）
- 進行 Bot が起票する 🟢 の Issue（`from-review`。T11 で起票する）は、Project に入れ（新しい作業の単位として T1 から始まる）、マイルストーンと `agent-ready` は付けない。人がマイルストーンを付けたら入口の検疫と下書きに進み、人が決めるかを決める（IMPL-26）
- Project の表示の欄の更新は進行 Bot が GraphQL で行い、AI のセッションは触らない（IMPL-5）。更新は冪等で、すでにその値なら何もしない。進行 Bot は表示の欄を判定に読まない
- 人は進行 Bot のコメント（マスターの下書きを含む）を編集しない（印が無効になり、停止中になる。IMPL-20）。誤りは新しいコメントで補い、依頼を直すときは `## 作業指示` に全文を書く

## 運用の規則

- 状態の正は GitHub に置く（Issue と結びつく PR、進行 Bot の署名付きの印、人のラベルと見出しのコメント、必須チェックの結果）。進行 Bot は毎回そこから状態を組み立てる（FLOW-41）。Project の欄は表示だけで、判定に読まない（FLOW-39）。各手順は「すでに済んでいれば何もしない」（PR があれば作らない、コメントがあれば足さない）
- 手元の記録は判定に使わず、実行をまたぐ上限の数え上げにだけ使う：同じ作業の単位で続いた実行の失敗の回数、受付 AI が拒否した Issue の次のモデル、作業の単位ごとの累計の利用枠、1 日の利用枠（[ADR-20261015-006][adr-flow]）。書かずに試す間の受け入れと、比べるためのレビューを起こすかの 2 つの例外は、どちらも持たなくなったので無い（[ADR-20261024-002][adr-no-stages] の決定 5）
- 記録を失ったときは、上限が黙って効かなくなる側に倒さない。`setup` は記録のフォルダに、作った日時を書いた記録の目印のファイルを置く。目印のファイルが無ければ `check` は fail にする（人が `setup` をやり直して、失ったことを認める）。
  着手した作業の単位（計画済みより後の状態。[ADR-20261015-006][adr-flow] の決定 4 の「進行中の Issue」）に記録が無ければ、実行の失敗は 1 回目で停止中、累計の利用枠は次のセッションを起こさずに停止中（止めた理由の記号は、実装の都合の記号として詳細設計で足す。今の `records-missing`）。拒否の記録が無ければ受付 AI は `haiku`（完全な ID。IMPL-29）で起動する。当日の利用枠の記録が無ければ、当日の残りの AI のセッションを起こさない
- 多重起動を lockfile で防ぐ。人の `/dev-autopilot` の手動実行は、定期の実行と同じジョブを起こし（macOS は `launchctl kickstart`（`-k` なし。`-k` は動いている進行 Bot を殺す）。Linux は登録した仕組みで同じジョブを起こす操作。[ADR-20261015-001][adr-read]、[ADR-20261017-003][adr-plugin]）、同じ lock を取る。
  `setup` が進行 Bot のプログラムの写しを作り直すときも、同じ lock を取る（STRUCT-3）。lock には、lock を取ったプロセスの PID と起動の時刻（OS が返す時刻を、時刻帯に依らない値にしたもの。書く側と比べる側で同じ取り方にする）を書く。PID が生きていないか、PID のプロセスの起動の時刻が lock の起動の時刻と違えば、古い lock として奪う（電源断の後の再起動で PID が使い回されたときに、全実行が「多重起動」で止まり続けないため）。PID が生きていて起動の時刻が同じなら、持ち主が動いているので奪わない。lock にはホスト名も書くが、人が読むためだけに使い、奪うかの判定に使わない（macOS では、つないだネットワークでホスト名が変わりうるため。動かすマシンを替えるときは lock を写さない。基本設計の「[導入と点検][design-setup]」の「動かすマシンを替えるとき」）。古い lock を奪うときは、2 つのプロセスが同時に古い lock と読んでも片方だけが lock を取れる手順で取る（取り方は基本設計の「[状態遷移と判定][design-flow]」の「1 回の実行の流れ」の順 2）。
  lock を取るのは、進行 Bot の実行と `setup`（写しを作り直すときと、引数 `uninstall` のとき）だけにする。人が `/verify-issue` などから呼ぶ受け入れの Skill（`intake`）の下書きは、lock を取らず、`claude` を起こさず、記録の置き場に受け入れの依頼のファイルを置いて、定期の実行と同じジョブを起こす（`check` と `/dev-autopilot` と同じ形）。受付 AI のセッションは、依頼で起こされた進行 Bot の実行が、ほかの AI のセッションと同じ確かめと止め方で起こし、GitHub には書かない。人の Skill が待つのをやめた後に残った依頼のファイルで、定期の実行が作業を飛ばさない（扱いは基本設計の「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」。[ADR-20261022-004][adr-intake-req] の決定 1・2・5）。
  lock で見送った実行と、マシンのスリープや停止で定期の実行が起動しなかった日は記録に残し、`check` が warn に出す（FLOW-12 の「連続 7 回の実行」は、これらと、受け入れの依頼で起こされた実行を除いて数える）
- 止める合図：全体を止めるのは、当てる先のリポの変数（Actions の変数。名前は構造仕様で決める。例：`DEV_AUTOPILOT_RUN`）。値が `run` のときだけ動き、ほかの値・変数が無い・読めないときは止まる。
  `setup` の GitHub の準備が値を `stop` にして作り、人が `check` の後に `run` にする。人は GitHub の画面（スマートフォンを含む）か人の `gh` で変え、PR は要らない（変えられるのは push 以上の人。org のリポでは、変えた人が org の監査ログに残る）。
  進行 Bot の PAT は変数を読むだけで、変えられない（GitHub App に切り替えた後も同じ。[ADR-20261017-007][adr-stop]、[ADR-20261020-002][adr-app]）。1 つの作業の単位だけを止めるのは、人が付ける `agent-paused` のラベル（FLOW-38）。進行 Bot が AI の書いた文で攻撃の疑いを見つけたときは、進行 Bot が全体の停止の Issue を開いて全体を止める（SAFE-19）。進行 Bot は、合図が `run` で、全体の停止の Issue が無いときだけ、AI のセッションを起こす。
  進行 Bot は、全体の合図を、実行の最初・AI のセッションを起動する前・GitHub に書き込む前に読み、`run` を読めなければ起動も書き込みもしない。AI のセッションが動いている間も一定の間隔で読み（間隔は、基本設計の「[設定][design-settings]」の `run.stopSignalPollSeconds`）、
  `run` 以外の値を読んだら、AI のセッションを時間の上限と同じやり方（`SIGTERM`、猶予、`SIGKILL`、残ったコマンドも止める。IMPL-14）で止める。間の読み取りの失敗では止めない（書き込む前にもう一度読むため）。
  合図で止めた実行は、手元の記録に残し、lock を外して終わる。その回は実行の失敗に数えない（IMPL-14）。次の実行は、合図が `run` に戻った後、GitHub の状態から続ける
- 書かずに試すこと（`dryRun`）は持たない（[ADR-20261024-002][adr-no-stages] の決定 2）。進行 Bot は最初の実行から当てる先のリポに書くので、導入と点検を確かめ終わるまで、全体の止める合図を `stop` にしておく。GitHub App には、当てる先のリポに初めて書く前に切り替える（[ADR-20261020-002][adr-app]）
- 進行 Bot は、毎回の実行の最初に、進行 Bot の clone（`<置き場>/controller/`）で fetch した base ブランチの先端から、リポの設定を読む。1 回の実行は 1 つの版の設定で動き、途中で読み直さない（全体の止める合図は除く）。
  人の作業コピー、AI の worktree、Plugin の写しの中のリポの設定は読まない（SAFE-2）。設定の変更は、base ブランチにマージされた後の次の実行から効く。読めない・形が違うときは作業に入らず止まる（SAFE-4。[ADR-20261017-007][adr-stop]）
- 進行 Bot が途中で死んだら、次回の実行が GitHub の状態から復旧する（FLOW-4 の「次の工程」の決め方）。復旧できない組み合わせ（GitHub の状態から次の工程を決められないもの）は、その作業の単位を停止中にする（止めた理由の記号は、実装の都合の記号として詳細設計で足す）。作業場所はセッションごとに作り直すので、作業場所の有無は復旧の判定に使わない（[ADR-20261013-001][adr-workspace]）。Issue に紐づかない作業場所の残骸は `check` の fail（SETUP-2。見分け方は基本設計の「[状態遷移と判定][design-flow]」の「作業場所の残骸」）
