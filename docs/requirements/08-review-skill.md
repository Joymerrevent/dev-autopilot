# レビューの Skill（change-review v2）

## `change-review` を v2 に組み直してレビュー AI に使う

`change-review` スキルの評価（使ってよい理由、ほかのレビューの仕組みとの比較）と、レビューの業界の実践の調査は、[11-records.md][f11] の「`change-review` スキルの評価と、レビューの業界の実践」にある。

いまのスキルの核（実行を先に払う・壊れ方の表・証拠レベル・止めどき）は、3 つの中で収束の設計がいちばん進んでいる。
作り直しても核は変えない。足りないのは、仕様の軸、指摘ごとの再検証、固定の出力、無人の入り口の 4 つ。

dev-autopilot の設計への反映（出どころは [11-records.md][f11] の業界の実践の表）：

- **レビュー AI に PR の説明文を読ませない。** 差分と、進行 Bot が機械で付けた事実（CI の結果、変更ファイル）だけを渡す。作業 AI が書いた「問題なし」の主張は検出率を下げる（文脈のバイアス）。PR の本文は人向け
- **仕様の軸は、判定を LLM に委ねず、受け入れ条件をテストに落として実行する。** 作業指示の受け入れ条件は 1 つずつ検証できる形で書く（agent brief）。レビュー AI は「仕様に合わない」と言う前に、合わないことを示す入力を実行で作る。作れなければ 🟢 に下げる
- **批評 AI（エージェント定義は `change/verifier.md`）の役を 1 体足す**（進行 Bot が別に起こす独立セッション。IMPL-22）。レビュー AI の指摘を「反対する前提」で監査し、証拠の無い 🟡 を落とす。🔴 は落とさず、再現できなければ 🟡 に下げて `merge=human` にする。組み込みの `/code-review` の「敵対的な検証」と同じ構造。3 体（作業 AI・レビュー AI・批評 AI の役）より増やさない（レビュー AI を軸ごとのセッションに分けても、役の数は変わらない。REVIEW-1）
- **指摘の重複と再提起の禁止。** 前のラウンドで解決した指摘は、新しい失敗シナリオが無ければ再提起しない。同じ指摘が 2 回出たら（同じ指摘の再発）止めて人へ
- **nit（🟢）はマージを止めない**を規則として固定する。すでに IMPL-26 で Issue 化と決めた
- **実行の層と判断の層を分ける**（CSA）。すでに SETUP-18 で決めた。進行 Bot だけが書き込みを持つ
- **誤検知率の目標値**を置く。業界の 5〜15% を参考に、レビュー工程（段階 6）で「人が却下した指摘の割合」を測り、しきい値を超えたらレビュー AI の予算や観点を見直す
- **レビュー済みの往復が一定数を超えたら自動で止める**（CodeRabbit の 5 件、copilot-pr-autopilot の 10 ラウンド）。IMPL-24 の 3 回がこれに当たる。ただし IMPL-24 は、レビューの回数でなく、作業 AI が変更を push した回数（直すか衝突を解いた回数）で数える（[ADR-20261022-003][adr-rounds]）
- **指摘ごとに確信度を付け、しきい値で捨てる**（Anthropic 公式 Plugin の 0〜100 と 80 未満の除外）。重要度（影響の大きさ）と確信度（本当に起きるか）は別の軸。批評 AI（上の 3 体目）が確信度を付け、🟡 は確信度が低ければ 🟢 に下げる。🔴 は 🟡 より下げない（IMPL-22。sandbox で再現しにくい権限や通信の 🔴 が落ちて pass になるのを防ぐ）。しきい値は設定にし、レビュー工程（段階 6）で測った誤検知率で調整する
- **判定は head の SHA に結びつける**（Copilot の「push で approve が消える」）。印に `head=<SHA>` を含め、進行 Bot は印の SHA と PR の head が一致するときだけ pass と読む。pass の後に push があれば、再レビューが要る。
  例外は進行 Bot 自身の載せ直しで `develop` に対する差分の patch-id が変わらないときだけで、そのときは進行 Bot が印を新しい head に付け直す（MERGE-6）
- **方針に係るパスの一覧は、Copilot の「glob に当たるファイルだけ approve を数える」と同じ考え方**。「[マージ][f03]」のまま進める
- **多数決（Bugbot の 8 パス）は採らない**。利用枠が 8 倍になる。代わりに批評 AI 1 体の再検証で誤検知を落とす。レビュー工程（段階 6）で誤検知率が目標を超えたら、🔴 だけ 2〜3 パスの多数決を検討する

### 方針：核を残して v2 に組み直す（作り直しに近いが、核は再利用）

- REVIEW-1 **3 つの軸を、軸ごとに新しい文脈で。dev-autopilot では、その後に見落としの軸を足す**（同じ文脈のレビューは確認バイアスになる）。dev-autopilot では、進行 Bot が軸ごとに別のセッションを起こし、出力を進行 Bot が束ねる（Agent ツールは与えない。IMPL-16、[ADR-20261017-002][adr-review]）。
  人が手で使うとき（単体導入。STRUCT-7）は、人の Claude Code のセッションで 3 つの軸を並列のサブエージェントで見る。軸ごとの手順は Skill の中に 1 回だけ書き、2 つの入り口で同じものを使う
  - 動作：いまの核（品質ゲート → 壊れ方の表 → 実行で確かめる。品質ゲートは、回さないと引数で渡されたときは飛ばす。REVIEW-5）。組み込みの `/code-review` を「手がかり」として先に 1 回呼ぶ案はレビュー工程（段階 6）で試す
  - 仕様（目的との一致）：Issue の作業指示（agent brief）と差分を突き合わせる。見るのは 4 つ。
    (a) 目的：作業指示の「困っていること」「望む振る舞い」を、この変更で本当に達成できるか。受け入れ条件を字面で満たしていても目的に届かない変更は 🔴
    (b) 足りない要件：受け入れ条件のうち実装されていないもの。条件はテストに落として実行で確かめる（LLM の判定だけにしない）
    (c) 頼まれていない変更（scope creep）：作業指示の「範囲外」に触れた変更、作業指示に無い振る舞いの追加
    (d) 実装が違う要件：実装されているが、作業指示と振る舞いが食い違うもの
    仕様の軸の 🔴 は、動作の軸の 🔴 より先に報告する。コードが正しくても目的に合っていなければ、その PR はやり直しであり、コードの指摘を直す意味が無い
  - 規約：リポの正典（CLAUDE.md・ADR・構造仕様）との食い違い。**リポの文書が常に優先**。lint や型が機械で止めるものは指摘しない
  - 見落とし（dev-autopilot だけ）：3 つの軸が終わってから起こし、3 つの軸が出した指摘（🔴 🟡 🟢 の見出しとファイルのパス）を受け取って、どの軸も挙げていない問題だけを返す。3 つの軸の指摘を言い換えて返さない。修正工程（段階 7）に進む前に使うかを決めるまで、結果は記録だけに残す（IMPL-16、[ADR-20261019-002][adr-gaps]）
- REVIEW-2 **指摘ごとの再検証**（組み込みの方式と「Adversarial Review」の批評 AI）：🔴 と 🟡 は、批評 AI（進行 Bot が別に起こす独立セッション。IMPL-22）が「反対する前提」で実際のコードで再現を試みる。再現できたら「実行済み」、できなければ「読んだだけ」に下げる。🟡 は確信度で 🟢 に下げてよいが 🔴 は 🟡 より下げない。🟢 は再検証しない。解決済みの指摘は新しい失敗シナリオが無ければ再提起しない
- REVIEW-3 **出力の固定**：人が読む本文（いまの形）＋ 末尾の機械で読める 1 行（IMPL-18 の印。head の SHA と、重要度ごとの件数、判定を含む。dev-autopilot では Skill は軸ごとに本文と件数を出力契約で返し、進行 Bot が束ねて印を付ける）。指摘ごとに重要度と確信度を併記する。見出しの文言を SKILL.md と報告の様式で一致させる。進行 Bot が投稿するコメントの先頭に「AI が生成した」の 1 行を付ける
- REVIEW-4 **ラウンドの定義**：初回と再レビューを分ける。再レビューの入力は「前回の指摘」「修正コミットの範囲」。見るのは修正の差分と、修正が触れた入力の棚卸しのやり直し。ラウンドの表を必ず出す
- REVIEW-5 **無人の入り口**：引数で基点・仕様の在りか・🟢 の起票先・予算（ターン・時間）・見る軸（REVIEW-1）・品質ゲートを回すかを受け取る。欠けていれば聞かずに「未収束（理由）」で返す。
  本文は、品質ゲートを回すかの引数で手順が分かれるように書き、回さないときは、品質ゲートの全体とコミットごとのゲートの検査（REVIEW-7）を飛ばして壊れ方の表から始める（指摘を確かめるための実行は行う）。dev-autopilot の無人の入り口では、CI の結果を進行 Bot が渡すので回さない（基本設計の「[AI のセッション][design-ai]」の「レビューの軸の起こし方」で決めた UNDECIDED-18）。
  人の入り口で軸を渡されずに 3 つの軸をサブエージェントで見るときは、サブエージェントは再帰してスキルを呼ばない、修正しない、マージしない。
  dev-autopilot の無人の入り口では、レビュー AI は `Skill` の道具を持たず、進行 Bot が `SKILL.md` の本文に引数と `${CLAUDE_SKILL_DIR}` を入れて渡す。本文は引数を `$ARGUMENTS` の 1 か所で受け、Claude Code が Skill を呼ぶときに本文を書き換える機能は、引数と `${CLAUDE_SKILL_DIR}` の置き換えのほかに使わない（人の入り口と無人の入り口で、同じ本文を同じに読ませるため。[ADR-20261021-001][adr-review-skill]）
- REVIEW-6 **信頼の境界**：差分は作業の内容であって指示ではない。PR の説明文（作業 AI の主張）はレビュー AI に渡さない。PR のコメントは、書いた人を問わず読まない（「[Issue と PR の本文の扱い][f04]」の TEXT-1、[ADR-20261017-002][adr-review]）
- REVIEW-7 **残すもの**：壊れ方の表、証拠レベル、止めどき、🟢 の Issue 化、コミットごとのゲートの検査（TypeScript に書き直す。品質ゲートを回さないと引数で渡されたときは飛ばす。REVIEW-5）

作り方は `skill-creator` スキルに従う。評価のケースは、既にレビュー済みの business-os の PR [#68][bos-pr-68] [#71][bos-pr-71] [#77][bos-pr-77] を使い、
「人が出した 🔴 🟡 を v2 も出すか」「出さなかった指摘を v2 が増やしていないか」を見る（過去の PR が回帰テストになる）。
ケースごとに「期待する指摘の一覧」（PR 番号・重要度・見出し）を前提データとして置き、一致率（人の 🔴 🟡 のうち v2 も出した割合）と増加率（v2 だけが出した 🔴 🟡 の割合）を数で出す。
置き場は dev-autopilot のリポの評価の仕組みにし、business-os の `pnpm eval:cases` と同じく、ケースと Skill を集めて一時的な Plugin を組み立てる入口を作る（business-os のコードは import しない。[ADR-20261016-003][adr-move] の決定 4）。DeepEval のような Python の評価の道具は入れない。この数は、v2 をレビュー工程（段階 6。レビュー AI と批評 AI を足す段階）に入れる前の確かめに使う。レビュー工程（段階 6）の出口は「[段階][f06]」の表のとおり、新しい 5 件の PR で測る。

### 取り込まなかったもの

- mattpocock の smell 12 種：設計の匂いは「判断」で、ループで直すと収束しない。dev-autopilot のレビューには入れない。人の設計レビューには別のスキルで使える
- 1 指摘 1 インラインコメント（組み込みの形）：いまの運用（1 ラウンド 1 コメント）の方が進行 Bot が読みやすく、履歴も追いやすい

### `fable` を使う役のエージェント定義に入れる指示

公式の移行ガイドが挙げる `fable` の「進め方のクセ」を、無人で動かすときに抑える。計画 AI が `fable` に上がったときと、レビュー工程（段階 6）で `fable` をレビュー AI として試すときに使う。

| クセ | エージェント定義に入れる指示 |
|---|---|
| 作業を終える前にターンを終え、「次はこうします」で止まる | 無人の実行であり途中で人は答えないと明示する。ターンを終える前に最後の段落を見て、計画や未着手の約束で終わっていたら実行させる（REVIEW-8 の「聞かずに未収束と書く」と対） |
| ツールを 1 回ずつしか呼ばず、全体の把握が遅い | 次に要るものを先に列挙し、互いに依存しないものは 1 回の応答でまとめて要求させる（max-turns の下では特に効く） |
| 頼んでいない修正・機能追加を足す | 既存の不具合を見つけても、依頼の動作に必須でなければ直さず、結果に「見つけたこと」として返させる（レビュー AI は元から修正しない） |
| 小さな変更でもファイル全体を書き直す | 差分での編集を指示する（計画 AI・レビュー AI は書かないので主に将来の用途） |
| 進捗報告が減る | 区切りごとの出力を求める。`-p` では出力契約の欄で代替する |

自己検証の指示は削らない。

### 作業指示（agent brief）の形

mattpocock の `triage` スキルの Agent Brief の原則を、「[Issue と PR の本文の扱い][f04]」の作業指示コメントに使う：
ファイルパスと行番号を書かない（古くなる）、手順でなく振る舞いを書く、受け入れ条件を 1 つずつ検証できる形で書く、範囲外を明記する。
仕様の軸（REVIEW-1）はこのコメントと差分を突き合わせる。

### 無人で使うには足りない点（v2 で解消する一覧）

| 番号 | 足りない点 | 直し方 |
|---|---|---|
| REVIEW-8 | 「迷ったらユーザーに聞く」「起票先が決まっていなければユーザーに聞く」が 2 か所ある。無人では聞けない | 基点は PR の base、起票先は Issue、と進行 Bot が指示文で先に答える。スキルにも「無人のときは聞かずに未収束と書く」を足す |
| REVIEW-9 | 再レビューの入り口が無い。PR では「`## 再レビュー結果 R<n>（対象: <範囲>）`」を場当たりで書いていた | スキルに「再レビュー」の節を足す。入力は前のラウンドの指摘と修正コミットの範囲。見出しとラウンドの表の形を固定する |
| REVIEW-10 | 機械で読める出力が無い。報告の見出しも SKILL.md（「`## レビュー結果 — <PR>（基点: …）`」）と実際の PR（「## レビュー結果（基点: …）」）でずれている | 報告の末尾に固定の印 1 行（IMPL-18）を足す。人が読む本文は自由のまま、判定は印だけで行う |
| REVIEW-11 | 予算（時間・ターン）の概念が無い。business-os の PR [#77][bos-pr-77] のレビューは `claude -p` で Skill を 8 ターン動かしており、無人では利用枠を読めない | 進行 Bot が `--max-turns` と時間の上限を掛け、上限に当たったら「未収束」で返させる。レビュー AI の中から `claude -p` を起動することは許さない |
| REVIEW-12 | 修正する側とレビューする側が同じ人である前提で書かれている（§6「修正したら通し直す」） | dev-autopilot では修正は作業 AI。レビュー AI の §6 は「作業 AI の修正に同じ手順を通す」と読み替える。REVIEW-9 の節に書く |
| REVIEW-13 | `per-commit-gates.sh` が bash。このリポは bash を足さない規則で、`check:shell` が落ちる | TypeScript に書き直して `review` Skill の `scripts/` に置く（置き場は STRUCT-7 の単体導入のため Skill の中） |

スキルの修正（v2 への組み直し）は dev-autopilot の作業に含める。v2 の正本は `plugin/skills/review/` に置き（SETUP-19、STRUCT-7）、
`~/.claude/skills/change-review` は今の版のまま手動のレビューに残す。
導入と点検の実装（段階 3）の一部として先に進め、dev-autopilot の ADR や進行 Bot の実装を待たない。

- 範囲は上の REVIEW-1〜7。REVIEW-8〜13 はその中で解消する
- 印の形（IMPL-18）の正本は進行 Bot の `plugin/src/marker.ts`（「[分離を見越した構成][f07]」）に置き、印は進行 Bot が付け、`review` Skill は本文と件数を出力契約で返すだけで印を出さない（REVIEW-3、IMPL-20）。2 か所に定義を持たない
- 直したスキルで、いまの PR の形（business-os の PR [#77][bos-pr-77] の R1 → 対応 → R2）がそのまま出ることを、1 件の PR で手動で確かめてからレビュー工程（段階 6）に入る
