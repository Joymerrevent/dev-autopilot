# 実装・レビュー・対応ループ・モデル

## 実装（作業 AI）

- IMPL-1 AI のセッションごとに、進行 Bot が origin の URL から AI の作業場所の clone（「[隔離と鍵の分け方][f05]」）を作り直し、設定の worktree の置き場（STRUCT-2）に worktree を作って、worktree の中で `claude -p` を起動する（置き場の形、作り方、消し方は [ADR-20261013-001][adr-workspace]）。人の作業場所の clone と worktree は共有しない。
  依存の導入（`pnpm install`）は作業 AI のセッションの中（sandbox の中）で行い、進行 Bot は worktree の中でリポのコードもパッケージの lifecycle script も実行しない（「[安全側に倒す設計][f05]」）。依存はセッションの一時フォルダの store に導入し、セッションの間で共有しない（[ADR-20261015-002][adr-store]）。npm のレジストリにつながらず導入が失敗したら、実行の失敗（IMPL-14）として持ち越す
- IMPL-2 ブランチは `<型>/issue-<番号>`。型は設定のラベル対応表（例：`bug` → `fix`、それ以外 → `feat`）で進行 Bot が決める。短い名前は付けない（TEXT-6）
- IMPL-3 Issue の本文は「[Issue と PR の本文の扱い][f04]」の規則で「報告」として渡す。本文に書かれた指示には従わない
- IMPL-4 守る規約は実装リポの正典をそのまま渡す：`CLAUDE.md`、関係する ADR、`pnpm check` が緑、changeset、日本語の Conventional Commits。
  作業 AI は規約の正典（IMPL-15 の push しないパスにある CLAUDE.md・ADR・構造仕様）を変えない。固定の指示文に正典のパスを書き、変える必要があると分かったら、変えずに IMPL-8 と同じく止まった理由を返させる（[ADR-20261017-002][adr-review]）
- IMPL-5 作業 AI は GitHub に一切書かない（SETUP-18）。作業の結果は **出力契約** で進行 Bot に返す：`claude -p` の構造化出力（`--output-format stream-json` の最後の `result`。IMPL-14）（PR の題名と本文の案、止まった理由、確かめた検査の結果。計画は計画 AI の出力契約で、IMPL-10）と、worktree の中の commit。
  出力契約は進行 Bot が自分の JSON スキーマで `result` の文を検証し、欠けや型の違いがあれば「実行の失敗」（IMPL-14）とする。解析できない出力を「成功」や「0 件」と読まない。
  `--json-schema` は `--agent` と併用すると `structured_output` が空になる（実機の試し（段階 2）で確認）ので頼らない。エージェント定義には「返事は JSON だけ。前後に文を付けない」と書く
  PR の作成・draft/ready の切り替え・Project の表示の欄の更新・Issue と PR へのコメントは、すべて進行 Bot が出力を検証してから行う（gh-aw の safe outputs と同じ）
- IMPL-6 進行 Bot が PR を `develop` 向けに draft で作る。本文に `Closes #<番号>` と検査の結果を書く（`Closes #<番号>` は人向けの表示。`develop` 向けの PR には GitHub が Issue との結びつきを張らないので、結びつけには使わない）。題名は Conventional Commits の規約（小文字か日本語で始める。squash の件名になり commitlint が検査する）に進行 Bot が照らしてから使う。
  PR と Issue は、(1) head のブランチ名が `<型>/issue-<番号>`（IMPL-2）、(2) head のリポが base と同じ（fork でない）、(3) 進行 Bot の署名付きの結びつきの印がある、の 3 つで結びつける。PR を作った直後に、Issue に `link` の印（`pr` に PR の番号）、PR に `link` の印（`issue` に Issue の番号）の付いたコメントを投稿する。作者のアカウントは条件にしない（SETUP-13）。
  同じリポに、ブランチ名が一致するのに結びつきの印が無い PR があれば、停止中にする（止めた理由の記号は、実装の都合の記号として詳細設計で足す。今の `unlinked-pr`）。fork からの PR は、本文が Issue を参照していても扱わない。Issue 1 件に結びつく PR は 1 件で、マージされずに閉じられていれば停止中（`pr-closed`）にし、人が戻す先を選ぶ（[ADR-20261016-001][adr-pr]、FLOW-40）。
  `## 再開 下書きから` か `## 再開 計画から` で戻したときは、最新の再開の見出しより前の PR を数えず、開いている前の PR は進行 Bot が閉じる。戻した後に作った新しい PR が、結びつく PR になる（[ADR-20261024-001][adr-model-states] の決定 7。[ADR-20261022-005][adr-unlink] の、人が戻した時刻で閉じた PR を外す形は置き換えた）
- IMPL-7 PR を作ったら、進行 Bot が Project の表示の欄を変更済みにする（FLOW-39）。担当者（Assignee）はメンテナのまま。AI の担当を表す Agent 欄は使わない（[ADR-20261024-001][adr-model-states]）
- IMPL-8 ADR の起票が要ると分かったら、作業 AI は実装せずに「止まった理由」を出力契約で返し、進行 Bot が Issue へコメントして停止中にする（ADR が先、実装は承認後。止めた理由の記号は、実装の都合の記号として詳細設計で足す）。規約の正典（IMPL-4）を変える必要があると分かったときも同じ。ただし、maintain 以上の人が `## 仕組みの変更の承認` で認めた正典のパスは、変えてよく、止まる理由にしない（IMPL-15、[ADR-20261024-004][adr-master] の決定 9）
- IMPL-9 着手の前に、基線が緑であることを確かめる。緑でない（赤、無い、保留）なら、新しい着手（計画を含む）・最初の実装・載せ直しをせず、停止中にはしない。作った PR のレビュー・直し・マージの判定・片付けと、入口の検疫・下書き・決定の印は続け、基線が緑に戻った実行から自動で再開する（壊れた基線の上に積まない。Anthropic の harness の「まず動くことを確かめる」。[ADR-20261015-006][adr-flow]）。
  実行の記録に、緑でない必須チェックの名前を残し、`check` の warn と `/dev-autopilot` の状態の表示に出す。
  確かめ方は `origin/develop` の最新 commit に対する必須チェック（IMPL-27 と同じ一覧）がすべて `success` であること。進行 Bot は worktree の中で `pnpm check` を実行しない（進行 Bot がリポのコードを実行しないため。「[安全側に倒す設計][f05]」）
- IMPL-10 実装の前に、計画 AI（作業 AI とは別のセッション）が計画を出力契約で返し、進行 Bot が Issue にコメントする。計画を投稿した実行では実装に入らず、次回の実行で実装に入る（計画と実装は別の実行で進める。重い工程は 1 回の実行で 1 つ。FLOW-4。[ADR-20261015-006][adr-flow]）。計画は記録として残す（Jules の計画の承認）
  - 計画に必ず含める項目：対象のファイル・モジュール・型定義とその依存関係、作業の手順と順序、手順ごとの完了条件、検証方法（どのテスト・コマンドで確かめるか）、範囲外とするもの、想定する commit の分割。
    作業指示（agent brief）はパスを書かないが、計画は「どう作るか」なのでパスを書いてよい
  - 作業 AI は計画を、進行 Bot が組み立てる固定の指示文の中で「作業の内容」として受け取る（TEXT-3）。前のセッションの思考や文脈の引き継ぎには頼らない（モデルが違えば思考ブロックは読めない）
  - **計画コメントの印と検疫**：進行 Bot が投稿する計画コメントには `plan` の印（`head`、計画のハッシュ、`sig`。「[印と固定の見出しの一覧][f04]」）を付ける。次回の実行で計画を読み戻すときは IMPL-20 の 3 条件（投稿者・未編集・署名）を満たす印のあるコメントだけを使い、
    作業 AI に渡す直前に TEXT-11 の検疫を通す。計画は作業指示とリポを読んだ AI の文であり、作業指示に紛れた指示を運びうるため、作業指示と同じ扱いにする。人が計画を読むことは決まりにしない（FLOW-37）。人が計画を止めるときは `agent-paused` を付ける
  - 計画 AI のモデルは、作業ごとに使うモデルの決め方を決めるまで（UNDECIDED-90）、いつも既定の `opus`（xhigh）で始める。受付 AI の難しさの判定と、人のラベル `plan:fable`・`plan:opus` は使わない（[ADR-20261024-004][adr-master] の決定 8）。
    計画 AI の `opus` が「設計判断・アーキテクチャの選択・原因不明の障害解析を含む」と出力契約で自己申告したら、進行 Bot は 1 回だけ `fable`（high）で計画し直す（2 回目の自己申告は無視し、記録に残す）。
    計画し直すのは、次回の実行に回さず、同じ回の実行で続けて行う。計画の工程で起動する計画 AI のセッションは、自己申告による計画し直しで最大 2 つ、下の計画のレビューによる計画し直しを含めると最大 3 つ（計画し直す回数の上限が初期値のとき）になるが、工程は 1 つのまま（FLOW-4）。`opus` の計画は投稿せず、投稿するのは `fable` の計画だけ（`plan` の印の `model` は `fable`）。
    進行 Bot は計画コメントに、計画し直したことと自己申告の項目（出力契約の決まった値）を固定の文で書き添え、AI が自由に書いた文は書き添えない。モデルを上げたことは、`plan` の印の `model` が `fable` であることで分かる。
    `fable` のセッションを起動する前にも、全体の止める合図と 1 日の利用枠を確かめ、起動できなければ計画を投稿せずに終わる。`opus` と `fable` のセッションの間で実行が終わったら、次回の実行で計画を `opus` からやり直す（[ADR-20261018-002][adr-redo]）。
    モデルの判定を誤ったときの害は利用枠の増減と計画の質だけ。計画の内容が作業 AI に届く経路は、上の印と検疫で守る
  - **変えてはいけないパスとの照らし**：計画 AI は、計画で変える見込みのファイルのパスも出力契約で返す。進行 Bot は、計画の輪が終わった後（確かめを通った計画を投稿した後）に、そのパスを変えてはいけないパスの一覧（IMPL-15）と照らす。認めていないパスに 1 つでも当たれば、計画済みのまま停止中（`protected-path`）にし、当たったパスと、maintain 以上の人が `## 仕組みの変更の承認` で認めれば変えられることを、止めた理由のコメントに書く（[ADR-20261019-004][adr-policy]、[ADR-20261024-004][adr-master] の決定 9）。
    照らすのは決まった処理で、AI の判断を使わない。計画 AI がパスを書き漏らしても、push の前の検査（IMPL-15）が止める
  - **計画のレビュー**：計画 AI が計画を返した後、投稿する前に、レビュー AI が計画をレビューする（モデルの流れの表の IMPL-37。[ADR-20261018-004][adr-planrev]）。計画し直したとき（上）は、やり直した計画をレビューする。
    計画用の指示と出力契約を使い、計画 AI と同じく読むだけの道具で、計画・渡す文・リポの中身を照らし合わせる（渡す文に沿っているか、範囲外を含まないか、上の必ず含める項目がそろっているか、手順と検証方法がリポの中身と食い違わないか）。結果は `ok` か `fix` と指摘の一覧で返す。
    **計画し直す**：レビューが `fix` を返したら、進行 Bot は同じ回の実行で続けて計画 AI のセッションを起動し、渡す文と直す前の計画とレビューの指摘の一覧を渡して計画し直させ、やり直した計画をもう一度レビューする（[ADR-20261019-003][adr-replan]）。
    モデルと effort は直す前の計画と同じで、計画し直したセッションの自己申告は無視して記録に残す。レビューの指摘は手元から渡すだけで、GitHub に書かない（やり直した計画は、上の印と検疫を通って作業 AI に届く）。
    計画し直す回数は、計画の工程ごとに上限を持つ（設定。初期値 1 回）。上限まで計画し直しても `fix` なら、計画を投稿せずに停止中（`plan-limit`）にし、止めた理由のコメントに最後の指摘を書く（指摘は AI の文なので、検疫と漏えいの検査を通す）。セッションを起動する前には全体の止める合図と 1 日の利用枠を確かめ、起動できなければ計画を投稿せずに終わり、次回の実行で計画の工程を最初の計画からやり直す。
    レビューの結果と、レビューの指摘で計画し直したことは、計画コメントに書かない（確かめを通った計画だけを投稿する）。直す前の計画、レビューの結果と指摘、やり直した計画を、手元の記録（FLOW-5）に残す。人が計画を読むことは決まりにしない（[ADR-20261024-002][adr-no-stages] の決定 3）
- IMPL-11 PR は進行 Bot が draft で作り、レビュー合格になったときに進行 Bot が ready にする（Copilot coding agent と OpenHands の形。途中の PR を人が誤ってマージしない）
- IMPL-12 テストを消す・skip する・期待値を緩める・lint を抑止する変更は、作業指示が明示していない限り禁止する。レビュー AI はこれを 🔴 として探す（Anthropic の harness：「テストを消したり編集したりするのは許されない」）
- IMPL-13 1 回のセッションの上限を設定に持つ。初期値は 45 分・200 ターン（Copilot は 59 分、GitHub Agentic Workflows は 20 分・500 ターンが既定）。
  時間の上限は `claude` に無いので、進行 Bot が止める（止め方は IMPL-14。止めた後に AI のコマンドを残さない）。ターンは `--max-turns`。上限に当たったら途中の状態を commit せず、作業場所は作り直すか片付けるまで残す。途中の状態は次のセッションに引き継がない（[ADR-20261013-001][adr-workspace]。引き継ぐかは UNDECIDED-26）。扱いは IMPL-14 の表
- IMPL-14 **実行の失敗と作業の失敗**。「実行の失敗」は作業の中身と無関係に起きる失敗で、その作業の単位は止めずに次回へ持ち越す。同じ作業の単位で 3 回続いたら停止中（`retry-limit`。FLOW-40）。「作業の失敗」は AI の作業の結果が条件を満たさないことで、「対応ループ」の往復で扱う

  | 契機 | 扱い | 根拠 |
  |---|---|---|
  | 利用枠切れ（HTTP 429） | 実行の失敗。持ち越し | 本項 |
  | 時間の上限（45 分）に進行 Bot が止めた | 実行の失敗。持ち越し | IMPL-13 |
  | 止めた後に、AI のコマンドの残りが止まったと確かめられない | 停止中（作業場所を消さず、次の AI のセッションを起動しない。止めた理由の記号は、実装の都合の記号として詳細設計で足す） | 本項、[ADR-20261018-001][adr-usage] |
  | 全体の止める合図（リポの変数）で進行 Bot が止めた | 実行の失敗に数えない。持ち越し（合図が `run` に戻った後に続ける） | 「[運用の規則][f01]」、[ADR-20261017-007][adr-stop] |
  | ターンの上限（`--max-turns`）に当たった | 実行の失敗。持ち越し | IMPL-13 |
  | `claude` の異常終了、出力契約が解析できない・欠けている | 実行の失敗。持ち越し | IMPL-5 |
  | 依存の導入でレジストリにつながらない | 実行の失敗。持ち越し | IMPL-1 |
  | 受付 AI の拒否（`stop_reason: refusal`） | 実行の失敗。次回は `sonnet` で試す | TEXT-12 |
  | 人が `/verify-issue` などから呼んだ受け入れの Skill（`intake`）の依頼で、進行 Bot が起こした受付 AI のセッションの失敗（時間・ターン・費用の上限、利用枠切れ、`claude` の異常終了、出力契約が解析できない、拒否） | 実行の失敗に数えない（続いた回数に足さず、成功しても 0 に戻さない。失敗の後に間を空ける決まりも掛けない）。依頼の結果のファイルに書いて人に示し、人が呼び直す。拒否の記録はほかの受付 AI と同じに残す | STRUCT-3、[ADR-20261022-004][adr-intake-req] |
  | 作業 AI が「止まった理由」を返した（ADR が要る等） | 作業の失敗。停止中 | IMPL-8 |
  | レビューの fix | 作業の失敗。往復（上限 3 回） | IMPL-24 |
  | CI の赤（`failure`、`timed_out`） | 作業の失敗。往復（上限 3 回） | IMPL-27 |

  記録には `is_error` `num_turns` `usage` `modelUsage` を残し、1 Issue あたりの利用枠はここから取る（[ADR-20261018-001][adr-usage]）。出力は `--output-format stream-json` と `--include-partial-messages` で受け、メッセージごとの `message_delta` の `usage`（最後のトークン数）を記録に残す。
  `assistant` のイベントの `usage` は同じメッセージで重複し、`output_tokens` は最後の値でないので、足し上げに使わない（FACT-29）。
  正常に終わった回（`result` があり、`terminal_reason` が中断（`aborted_` で始まる値）でない）は、`result` の `total_cost_usd` を費用とし、`modelUsage` をモデルごとのトークンとして記録する。
  途中で止めた回（`result` が無いか、`terminal_reason` が中断）は、費用をその回の 1 セッションの費用の上限（`--max-budget-usd`）とみなす（`stream-json` のイベントは費用を持たない）。トークンは、書き終えたメッセージの `message_delta` と、書いている途中のメッセージの `message_start` から数え、出力が分からないメッセージがあったことを記録に残す。
  上限とみなすと、ほとんどの場合は多めに数える。ただし、書いている途中で止めたメッセージ 1 つ分は少なく数えうる（`--max-budget-usd` もメッセージの間で確かめるので、上限をメッセージ 1 つ分超えうる。FACT-39）。
  子プロセスは `setpgrp` で別のプロセスグループに起こす。途中で止めるとき（時間の上限、全体の止める合図。[ADR-20261017-007][adr-stop]）は、`claude` のプロセスグループに `SIGTERM` を送り、猶予（設定に持つ。STRUCT-2）の間に終わらなければ `SIGKILL` を送る。
  `claude` が終わった後、そのセッションの Bash のコマンドのプロセスグループが残っていないかを確かめ、残っていれば `SIGKILL` で止める（コマンドは `claude` と別のプロセスグループで動き、`SIGTERM` を無視したコマンドと `SIGKILL` の後のコマンドは残る。FACT-38）。
  残りの見つけ方は、基本設計の「[AI のセッション][design-ai]」の「止める手順」で決めた。残りが止まったと確かめられなければ停止中（上の表）。`SIGINT` は使わない（書いている途中で止めると、`result` がその回の費用を 0 と数える。FACT-38）。費用の上限は `--max-budget-usd` でも掛ける。
  設定に持つ上限は、1 セッションの時間とターンと費用（IMPL-13、`--max-budget-usd`）に加え、1 Issue の累計の利用枠（往復を含む）、実行の失敗の再試行の回数（3）と間隔、1 回の実行と 1 日の利用枠（SETUP-12）。1 Issue の累計の利用枠と 1 日の利用枠は、費用（Claude Code が出す USD 換算の値）で数え、トークンはモデルごとに記録に残す（[ADR-20261018-001][adr-usage]）。累計が上限に当たったら停止中（`cost-limit`）。数え上げは手元の記録で行い、記録を失ったときの扱いは「[運用の規則][f01]」
- IMPL-15 **漏えいの検査と push**。進行 Bot は、GitHub に書くすべての文（diff、commit メッセージと author、PR の題名と本文、計画・レビュー・対応・受け入れのコメント、🟢 から起票する Issue）に、漏えいの検査（鍵の形式、メールアドレス、機械上のパス、進行 Bot の設定と記録の内容）を掛ける。引っかかれば書かずに、止め方でなく、作業の単位の安全の軸に攻撃の疑い（AI の文）を入れる（全体は止めない。SAFE-19、[ADR-20261027-002][adr-leak]）。
  検査の実装は dev-autopilot 自身の `plugin/src/` に持ち、worktree の中の `check:leak`（AI が書き換えられる）は使わない。マージの判定（MERGE-2）のときは最終の head の diff 全体に掛け直す（過去の記録に頼らない）。
  push の前に、diff が変えてはいけないパス（`.claude/**` `CLAUDE.md` `**/CLAUDE.local.md` `.mcp.json` `.github/**` `dev-autopilot/**` と、規約の正典のパス（business-os なら `docs/adr/**` `docs/design/**`））のうち、maintain 以上の人が `## 仕組みの変更の承認` で認めていないパスに触れていれば、push せずに停止中（`protected-path`）にする（MERGE-4 の判定より前）。変えてはいけないパスは、効く時期で 2 つの組に分ける（[ADR-20261024-004][adr-master] の決定 9）
  - push で効くもの：CI の定義（`.github/**`）、CI が信じて動かすスクリプト（リポの設定で足す）、AI のセッションが作業場所から読み込む設定（`**/CLAUDE.local.md`、`.claude/settings.local.json`）。CI が AI の書いたワークフローを、秘密や書き込みのトークンを持って実行しないため（FACT-75、FACT-78。秘密を Environment に置いても緩めない。SAFE-20、[ADR-20261028-001][adr-ci-secrets]）、認めていても AI の変更を push せず、進行 Bot が差分を Issue に載せて（`manual-push` の印）停止中（`manual-push`）にし、人が中身を確かめて自分で push する
  - マージまで効かないもの：ほかの `.claude/**`（進行 Bot のリポの設定 `.claude/dev-autopilot.json` を含む。進行 Bot は base ブランチの先端から読む）、`CLAUDE.md`、`.mcp.json`、`dev-autopilot/**`、規約の正典。認めたパスのうち、`CLAUDE.md`・`dev-autopilot/**`・規約の正典は、AI が変えて push してよい（`CLAUDE.md` は、認めたときだけ作業 AI の安全設定の Write と Edit の禁止を外す）。`.claude/**` と `.mcp.json` は、Claude Code 自身が作業 AI に書かせない（FACT-77）ので、認めても人が変える。計画が認めた `.claude/**` か `.mcp.json` を変える見込みなら、作業 AI を起こす前に停止中にして人に渡し、作業 AI の差分に入っていれば、認めていても push しない（[ADR-20261027-003][adr-claude-dir]）。マージの判定はいつも「人が判断する」（`merge` の印の `result` が `human`）にする。レビュー AI と直しの AI は、規約の正典を base ブランチから読む（IMPL-16）ので、AI が書き換えた正典を、人がマージする前に規則として使わない

  `**/CLAUDE.local.md` は、どのフォルダに置いても次のセッションが指示として読む（下のフォルダのものは、そのフォルダのファイルを読んだときに読まれる。FACT-60）ので、すべてのフォルダで止める。`dev-autopilot/**` は、dev-autopilot を別のリポに移して business-os から消した後も残す（外すのは安全の境界を緩める変更で、残せば同じ名前のフォルダが business-os に戻ったときにも止まる。[ADR-20261016-003][adr-move] の決定 5）。
  名指しした 6 つのパス（`.claude/**` から `dev-autopilot/**` まで。以下「名指しのパス」）は、進行 Bot のプログラムに固定し、リポの設定の値に関わらず push しないパスに必ず入れる。リポの設定には、当てる先のリポごとに違う足す分（規約の正典のパスなど）だけを持つ（STRUCT-2 の `denyRead` と同じ形）。push の前の検査と、計画が変える見込みのパスとの照らし（IMPL-10）で使う変えてはいけないパスの一覧は、名指しのパスと足す分を合わせたもの。足す分も 2 つの組に分けて持つ（項目の名前は基本設計で決める）。
  名指しのパスを外すのは、設定の値の変更でなく、IMPL-15 と進行 Bot のプログラムの変更で、安全の境界を緩めるので ADR で決める（[ADR-20261021-005][adr-blocked]）。
  push は進行 Bot の clone から `git push origin <検証した SHA>:refs/heads/<型>/issue-<番号>` の形で行い、ブランチ名でなく SHA を送る。API の head（初回は、作業場所を作ったときに進行 Bot の clone で控えた base の SHA。SAFE-13）が送る SHA の祖先であること（fast-forward で届くこと）を確かめる。
  deploy key の push 先は、`setup` が作る ruleset で作業ブランチ（`<型>/issue-*`）に限り、タグの作成を禁じる（SETUP-1）。ruleset の bypass に入れてよいのは、組織の管理者とチームだけにする（リポの役（admin・maintain・write）を bypass に入れると、書き込みのある deploy key もその ruleset を素通りし、base ブランチの更新もタグの作成も通る。FACT-65）。ただし、deploy key の push 先を限る 2 つの ruleset には、人がリポの設定の一覧で許したアプリ（例：Dependabot）も入れてよい。一覧にアプリを足すのは、ADR でなく、リポの設定の PR で行う（bypass のアプリは deploy key の push 先の制限を変えず、base ブランチの ruleset には入れないので、base ブランチは PR 必須のまま。アプリが取り戻すのは、ruleset を作る前にできていたこと（作業ブランチのほかのブランチを作ることなど）だけ）。進行 Bot のアプリは、一覧にあっても入れない。bypass にリポの役・deploy key・一覧の外のアプリ・進行 Bot のアプリが入っていれば、点検（SETUP-2）が fail にする。ブランチの ruleset は、bypass の外の人とアプリによるブランチの作成と base ブランチの更新も止めるので、PR をマージする人は bypass（組織の管理者かチーム）に入れる（FACT-67）

## レビュー（レビュー AI）

- IMPL-16 PR の差分を、作業 AI とは別の作業場所で読む。レビューは、PR の head の必須チェックがすべて通ってから起こす（IMPL-27、[ADR-20261024-003][adr-check-first]）。レビューの 3 つの軸（動作・仕様・規約。REVIEW-1）ごとに、進行 Bot が別のセッションを起こす（[ADR-20261017-002][adr-review]）。
  3 つの軸が終わったら、4 つ目の軸「見落とし」のセッションを起こし、3 つの軸が出した指摘（見出しとファイルのパス）を渡して、どの軸も挙げていない問題だけを返させる。見落としの軸が終わってから、批評 AI のセッションを起こす（[ADR-20261019-002][adr-gaps]）。4 つの軸の 🔴 🟡 が合わせて 0 件のラウンドは、批評 AI のセッションを起こさない（IMPL-18、[ADR-20261022-002][adr-critic-skip]）。
  見落としの軸の指摘も、ほかの 3 つの軸と同じく批評 AI に渡し、統合した結果を `review` の印とコメントに入れる。見落としの軸のセッションが失敗したときは、ほかの軸と同じく実行の失敗として持ち越す（[ADR-20261024-002][adr-no-stages] の決定 4）。
  作業場所は、軸のセッションごとに進行 Bot が origin の URL から clone し、PR の head（API の SHA）で切る専用の worktree（作業 AI の worktree と同じ書き込みの規則。[ADR-20261013-001][adr-workspace]）。3 つのセッションを並列で起こすか順に起こすかは、基本設計の「[AI のセッション][design-ai]」の「レビューの軸の起こし方」で決めた。作業場所の名前の付け方は、同じ文書の「セッションの名前」で決めた。
  軸のセッションは同じレビュー用のエージェント定義で起こす。レビュー AI には `Skill` の道具を持たせず、進行 Bot が、写しの `review` Skill の本文に引数（見る軸を含む。REVIEW-5）と `${CLAUDE_SKILL_DIR}` を入れて、固定の指示文に続けて渡す（[ADR-20261021-001][adr-review-skill]）。規約の正典は、作業場所（PR の head）からでなく、base ブランチのものを渡す（AI が書き換えた正典を、人がマージする前に規則として使わない。IMPL-15、[ADR-20261024-004][adr-master] の決定 9）。
  手順は `review` Skill（`change-review` を v2 に組み直したもの。「[レビューの Skill][f08]」）を使う。核は変えない（実行して確かめる、fail-open を探す、収束するまで回す）
- IMPL-17 結果は、いまの PR と同じ形で PR のコメントに書く（行に付けるレビューコメントにしない）。
  1 回目は「## レビュー結果（基点: `develop`）」、2 回目以降は「`## 再レビュー結果 R<n>（対象: <範囲>）`」。
  冒頭の判定は「**通してよい。ブロッカーなし。**」か「**🟡 `<n>` 件を直してから通したい**」。末尾にラウンドの表（| ラウンド | 指摘 | 最も重い種類 |）を置く。
  参考：business-os の PR [#77][bos-pr-77] [#71][bos-pr-71] [#68][bos-pr-68] のコメント（2026-10-06〜07、R1 → 対応 → R2 で 0 件 → マージ）
- IMPL-18 進行 Bot が機械で読むために、人が読む本文に加えて固定の印を 1 行足す（`review` の印。欄は「[印と固定の見出しの一覧][f04]」の表が正本。`sig` は IMPL-20）。
  `result` を `pass` にするのは、次の 5 つをすべて満たすときだけ（「🔴 🟡 が 0 件」だけでは、無いものを pass と読む）：
  (1) レビュー AI と批評 AI の出力契約が完全に解析できた、(2) レビューが収束した（「未収束」でない）、(3) `is_error` が偽、(4) 重要度ごとの件数がすべて数値で返った、(5) 実際に使われたモデル（`modelUsage`）が、起こすときに指定したモデルと一致した（レビュー AI は、ラウンド 2 以降も最初のラウンドの `review` の印の `model=` のモデルを指定する。IMPL-33）。
  5 つの条件は、ラウンドで起こした 4 つの軸のレビュー AI のセッションと批評 AI のセッションのすべてに掛ける（[ADR-20261017-002][adr-review]、[ADR-20261022-002][adr-critic-skip]、[ADR-20261024-002][adr-no-stages] の決定 4）。4 つの軸の 🔴 🟡 が合わせて 0 件のラウンドは、批評 AI に渡す指摘が無いので批評 AI のセッションを起こさず、5 つの条件は 4 つの軸のセッションだけに掛ける。0 件と読むのは、4 つの軸のセッションがすべて 5 つの条件を満たしたときだけ。1 つでも満たさなければ、件数が分からないので 0 件と読まず、印を書かずに実行の失敗（IMPL-14）として持ち越す。進行 Bot は軸ごとの指摘を、仕様 → 動作 → 規約の順に並べて 1 つのコメントにする（REVIEW-1）。軸をまたいで同じ問題を指摘していても束ねない。
  5 つを満たしたうえで 🔴 High と 🟡 Medium が 0 件なら pass、1 件でもあれば fix（`change-review` の止めどきの規則：🟢 Low だけのラウンドになったら直さずに記録して終わる）。
  (1)〜(5) のどれかを満たさなければ印を書かず、「実行の失敗」（IMPL-14）として持ち越す。
  判定は印だけで行い、本文の言い回しは解析しない（言い回しは変わりうる）。印は GitHub のレビュー状態を使わないので、同じアカウントでも動く（SETUP-13）。
  `review` の印の `round` は 1 から欠けずに続くことを判定の条件にし、欠けていたら停止中（印のコメントの削除は API から検出できないため。止めた理由の記号は、実装の都合の記号として詳細設計で足す）。`droppedHigh` は PR ごとの累計を書く（[ADR-20261015-004][adr-markers]）
- IMPL-19 レビュー AI のモデルは設定で変えられるようにする。作業 AI と同じモデルでもよい（effort は別。「モデルの流れ」）。同じ PR を別のモデルでもレビューして比べること（比べるためのレビュー）は持たない（[ADR-20261024-002][adr-no-stages] の決定 5。[ADR-20261021-007][adr-compare] は置き換えた）
- IMPL-20 **印の真正性**：正は GitHub に置き、手元の記録に依存しない。進行 Bot は、次の 3 つをすべて満たすコメントの印だけを読む。
  (a) 投稿者が、設定に並べた進行 Bot のアカウントのどれか（[ADR-20261020-001][adr-bots]）、(b) コメントが未編集（GraphQL の `lastEditedAt` が null、または `userContentEdits.totalCount` が 0。`updated_at` は非表示（minimize）でも変わるので使わない。リアクションでは変わらない。実機の試し（段階 2）で確認）。マスターの下書きを含め、進行 Bot のコメントはどれも人が編集しない（FLOW-36））、
  (c) 印に進行 Bot の署名（`sig` の欄。HMAC）があり、印の署名の鍵の一覧のどれかの鍵で検証できる。署名の対象は印の `sig` 以外のすべての欄（「[印と固定の見出しの一覧][f04]」）で、進行 Bot は一覧の先頭の鍵で署名する。一覧の鍵は進行 Bot だけが持ち、GitHub App の秘密鍵と同じ秘密の置き場（SAFE-15）のファイルに置き、AI のセッションには渡さない。HMAC は確かめる鍵でも印を作れるので、確かめにだけ使う鍵も、書く鍵と同じに秘密として扱う。鍵は、進行中の Issue があっても替えられる（替える手順は、基本設計の「[状態遷移と判定][design-flow]」の「印の署名」。[ADR-20261021-004][adr-marker-keys]）。
  手元の記録にはコメント ID も残すが、判定には使わない（手元の記録は、上限の数え上げにだけ使う。進行 Bot が途中で死んで記録を失っても、GitHub の状態から判定できる。「[運用の規則][f01]」）。
  AI の出力を投稿する前に、`<!-- dev-autopilot` で始まる文字列を進行 Bot が取り除く（AI の出力に印を混ぜても、署名が無いので判定に使われない）。取り除く規則は、印を読む処理（`plugin/src/marker.ts`）と同じ規則（空白の揺れを含む）にする。AI のセッションに前回の印を渡すときは、進行 Bot が読み取った値（ラウンド・件数・判定）だけを渡す。
  印は HTML のコメントの中に JSON を 1 行で書き、種類を `type` の欄に持つ（「[印と固定の見出しの一覧][f04]」）。署名は、`sig` を除いた欄に、印の置き場（リポと Issue か PR の番号）を加え、決まった並べ方にそろえた JSON に掛ける（並べ方は詳細設計。別の Issue や PR に写した印の署名は通らない）。同じ Issue か PR の中で、進行 Bot のアカウント（設定に並べたどれか）が投稿した印のうち (b) か (c) を満たさないものが 1 つでもあれば、停止中（`marker-invalid`）にし、`stop` の印の `comments` に無効だった印のコメントの ID を書き、人向けの本文にも、どのコメントかを書く（[ADR-20261015-004][adr-markers]、[ADR-20261024-001][adr-model-states] の決定 7）。
  ただし、次の 3 つをすべて満たす無効な印は、止める契機に数えない：印の置き場の Issue で（置き場が PR なら、結びつく Issue で）push 以上の人が `## 再開` を書いた（書いた人は TEXT-10 のとおり確かめる）、最後の `## 再開` より前に書いた有効な `marker-invalid` の `stop` の印のどれかの `comments` に、無効な印のコメントの ID が挙がっている、無効な印のコメントが最後の `## 再開` より後に編集されていない。
  数えない印は無いものとして読み、中身（判定・件数・ハッシュなど）を判定に使わない。無いものとして読んだ結果、ほかの判定（`review` の印の `round` の欠けなど）に当たれば、当たった判定に従う。止めた理由の印に挙がっていない無効な印が 1 つでもあれば、止める（[ADR-20261021-004][adr-marker-keys]）
  **進行 Bot が投稿した文は、投稿者がコラボレータであっても常に AI の出力として扱う**（TEXT-1 の「コラボレータの文」には数えない。見分けは投稿者でなく署名付きの印の有無で行う）
- IMPL-21 再レビューの入力は「前回の印から読み取った値（ラウンド・件数・判定。IMPL-20）と指摘」「修正コミットの範囲（SHA）」「差分」だけ。作業 AI の対応コメント（「確認済み」の主張）は渡さない（「[レビューの Skill][f08]」の文脈のバイアス）。修正コミットの範囲は、前のラウンドの `review` の印の `head` から今の head までで、検査の失敗の直しの commit も含める（[ADR-20261024-003][adr-check-first] の決定 4）
- IMPL-22 **批評 AI**。4 つの軸のレビュー AI が出力契約で返した 🔴 と 🟡 をまとめて、進行 Bot が別のセッション（`dev-autopilot:change:verifier`、新しい文脈、レビュー AI と別に作った作業場所。[ADR-20261013-001][adr-workspace]）に差分とともに渡し、指摘ごとに「反対する前提」で実際のコードで再現を試みさせる。渡す 🔴 🟡 が 0 件のラウンドは、批評 AI のセッションを起こさない（IMPL-18、[ADR-20261022-002][adr-critic-skip]）。
  批評 AI は指摘ごとに、再現できたか（実行済み / 読んだだけ）、確信度（0〜100）、推奨する重要度を返す。進行 Bot は次の規則で統合し、1 つの `review` の印とコメントにする：
  🔴 は 🟡 より下げない（再現できなくても 🟡 のまま残す）。🟡 は確信度がしきい値（設定）未満なら 🟢 に下げる。🟢 は批評 AI に渡さない。
  批評 AI が 🔴 を「再現できない」と返した PR は、その後 `pass` になっても、`merge` の印の `result` を `human` にする（人が落とした理由を見てマージする。MERGE-2）。批評 AI の出力契約が解析できなければ IMPL-18 の (1) を満たさず、実行の失敗

## 対応ループ

- IMPL-23 判定が fix なら、作業 AI を PR の head から作った新しい作業場所で起動し（[ADR-20261013-001][adr-workspace]）、最新のラウンドの 🔴 と 🟡 だけに対応させる。push は進行 Bot が漏えいの検査（IMPL-15）を通してから行う。🟢 はこの PR では直さない（直すと再レビューが新しい指摘を生み、ループが終わらない）。
  対応の結果は「`## R<n> の指摘への対応（<コミット>）`」のコメントに、指摘ごとの対応と確認を書く（いまの PR と同じ形）。
  印は `fix`（`round`、`head`、`cause` が `review`、`sig`。「[印と固定の見出しの一覧][f04]」）
- IMPL-24 往復の回数に上限を持つ（最初は 3 回）。超えたら停止中（`round-limit`）にし、経緯を止めた理由のコメントに書く。人が再開するまで進めない（FLOW-40）。前のどれかのラウンドに出た 🔴 🟡 の指摘が、後のラウンドで再び出たとき（同じ指摘の再発。間が空いていても数える）も停止中（`repeated-finding`）にする。同じ指摘かは、`review` の印の `findings` の ID で見分ける（[ADR-20261019-001][adr-repeat]）。
  往復の回数は、作業 AI が直すか衝突を解いて push した回数（PR の `fix` の印の数）。レビューの `fix` の修正（IMPL-23）、CI の赤の修正（IMPL-27）、載せ直しの衝突の解消（MERGE-6）を、どれも 1 回に数え、push が GitHub に届かなかった回も数える。
  進行 Bot だけで行う載せ直しで差分が変わった再レビュー（MERGE-6）と、人の push の後の再レビューは、新しいラウンドにするが、往復に数えない。往復の回数は PR の初めから数え、人が `## 再開 続きから` で戻しても数え直さない（`## 再開 計画から` か `## 再開 下書きから` で戻したときは、前の PR の `fix` の印を数えない。「[止まった状態から戻す手順][f01]」）。
  同じ指摘の再発は、AI の変更の後のラウンド（作業 AI が直すか衝突を解いた後のラウンド）でだけ判定する。PR の最初のラウンド、進行 Bot だけの載せ直しで差分が変わった後のラウンド、人の push の後のラウンドでは判定しない。比べる相手は、判定しないラウンドを含む、前のどのラウンドの `findings` でもよい。AI の変更の後のラウンドかは、1 つ前のラウンドの最新の有効な `fix` の印で見る（1 つのラウンドに、指摘の直しと検査の失敗の直しの印が 2 つ以上つきうる。[ADR-20261024-003][adr-check-first] の決定 4）（[ADR-20261022-003][adr-rounds]。数え方と見分け方は、基本設計の「[状態遷移と判定][design-flow]」の「ラウンドと往復の数え方」と「同じ指摘の再発の判定」）
- IMPL-25 **詰まったときの上げ方**。作業 AI が `sonnet` のとき、作業 AI の 2 ラウンド目（最初の修正のセッション）から `opus`（high）に 1 段上げる。作業 AI のラウンドは、実装を 1、修正を 2 以降と数える（「モデルの流れ」の表と同じ。`review` と `fix` の印の `round` とは数え方が違う）。`fable` には上げない。
  3 回で止める規則（IMPL-24）は変えず、再計画は人が指示する（自動では計画 AI に戻さない。fail-closed）。上げたことは記録と Issue のコメントに残す（印の名前は、作業ごとに使うモデルの決め方と一緒に決める。UNDECIDED-90、[ADR-20261024-001][adr-model-states] の決定 9）。
  最初の実装で使うモデルを種類ごとに変える決め方は、段階の材料で決める形を持たなくなったので、別に決める。決めるまでは、設定の初期値（`models.work`。`opus`）を使い、変えるときはリポの設定の PR で変える（[ADR-20261024-002][adr-no-stages] の決定 7。[ADR-20261018-003][adr-model] は置き換えた）
- IMPL-26 🟢 は進行 Bot が Issue にする（`change-review` の「見送りは記録とセット」の規則）。1 件 1 Issue、題名は指摘の見出し、本文に PR 番号・ラウンド・失敗シナリオ・推奨を写し、ラベル `from-review` を付ける。本文は AI の出力として扱い、作業 AI には渡さない（Issue の本文は著者を問わず渡さない。TEXT-1、IMPL-20）。
  マイルストーンは付けない。人がマイルストーンを付けるまで入口の検疫と下書き（TEXT-12）も走らせない（🟢 の Issue が毎日増えて人の読む量を超えないため）。有効な `follow-up` の印を持ち、題名が指摘の見出しと同じ open な Issue があれば、作らずにコメントで PR 番号を足し、そのコメントにも `follow-up` の印を書く（重複を防ぐ。[ADR-20261031-001][adr-follow-up-dup]）。
  `follow-up` の印を持たない Issue（人が起票した Issue、全体の停止の Issue、進行 Bot が開いた後に印を書く前に実行が切れた Issue）は、題名が同じでも足す先にしない（進行 Bot が起票した Issue は、`follow-up` の印があるときだけ作業の単位にするため）。
  Issue を作るか足して（`follow-up` の印）から、PR を ready にする（先にマージすると、Issue 化に失敗したとき指摘が消える）。ready の前に、PR のどのラウンドの 🟢 にも、`pr` がその PR で `finding` がその指摘の ID の、有効な `follow-up` の印があることを確かめる
- IMPL-27 レビュー合格の条件：CI が緑、かつ最新のラウンドの `review` の印の `result` が `pass`（🔴 🟡 が 0 件。🟢 は残ってよい）。レビューは、CI が緑になってから起こす（[ADR-20261024-003][adr-check-first]）。
  「CI が緑」の定義：設定に列挙した必須チェック（例：`check (ubuntu-latest)` `check (windows-latest)` `commitlint`）のすべてが、PR の head SHA に対して `success`。必須チェックのうち 1 つでも、head に対するチェックがまだ作られていないか、結果が `success` 以外なら、緑ではない（検査が走らなかった変更を通さない）。
  緑でないときの扱いは、必須チェックごとに結果を読み、1 つでも当てはまれば次の表の上の行から順に決める。同じ head に同じ名前のチェックが複数あるとき（再実行）は、最新の 1 件を採る（[ADR-20261016-001][adr-pr]）

  | CI の結果 | 扱い |
  | --- | --- |
  | `action_required` | 停止中（`ci-action-required`。ワークフローの実行に人の承認が要る） |
  | `failure`、`timed_out` | 検査不合格。レビューせずに、作業 AI が先に直す。失敗したチェックの名前と結果だけを渡し、レビューの指摘とは混ぜない。往復（IMPL-24）に数える。CI のログは渡さない（作業 AI は自分の作業場所で `pnpm check` を実行して確かめる）。`fix` の印の `cause` は `check`、`round` は最新の `review` の印の `round`（最初のレビューの前は 0）。レビュー合格の後に落ちても同じ（[ADR-20261024-003][adr-check-first]） |
  | チェックがまだ作られていない（push の直後）、`queued`、`in_progress`、`pending`、`waiting`、`requested` | 待つ。次の実行で読み直す |
  | `cancelled`、`skipped`、`neutral`、`stale` | 待つ。同じ head で、完了から設定の時間が経っても変わらなければ停止中（`ci-stale`。人が再実行するか、原因を確かめる） |
  | すべて `success` | 緑。レビューを起こす（まだなら） |

  照合はチェック名だけでなく、チェックを出した app（GitHub Actions）と、base 側に存在するワークフローのパスでも行う（AI が同じ名前の job を足して緑にする経路を塞ぐ）。進行 Bot は、GitHub App の Checks の読み取りで、非公開のリポでもチェックの実行を読む（fine-grained PAT には Checks の権限が無く、非公開のリポでは読めない。FACT-52、FACT-54。[ADR-20261020-002][adr-app]）。必須チェックの一覧が空なら点検（SETUP-2）を fail にする（空を「すべて success」と読まない）。
  進行 Bot は実行の中で CI を待たず、次回の実行で結果を読む（FLOW-4）。🟢 だけ残った場合もレビュー合格とする。
  1 回目から `pass` なら 1 回でレビュー合格とする
- IMPL-28 レビュー合格の PR は、進行 Bot が「[マージ][f03]」の条件でマージの可否を判定し、結果を印として PR に書く。マージの実行は人（「[マージ][f03]」）

## モデルの流れ

工程ごとに、どの役がどのモデルと effort で動き、どこで切り替わるかの一覧。値はすべて設定ファイルの初期値（STRUCT-2）で、本節が役ごとのモデルの正本。
「[決まっていること][f00]」の表はここを参照する。実機で使われたモデルは記録の `modelUsage` の欄（FLOW-5）と突き合わせる。モデルは別名で書く（版番号を書かない。「[決まっていること][f00]」）。
表の「順」は工程の並び。「番号」は要件の番号で、ほかの文書は番号で工程を指す（振り直さない。[README][readme] の「要件を変えるとき」）。

| 順 | 番号 | 工程 | 役 | モデル / effort | 切り替わる条件 | 根拠 |
|---|---|---|---|---|---|---|
| 1 | IMPL-29 | 受け入れ（検疫は TypeScript で AI を使わない。下書きの作成） | 受付 AI | `claude-haiku-5-5` / medium（別名 `haiku` は Haiku 4.5 に解けるので、haiku だけは完全な ID で書く。実機の試し（段階 2）で確認） | 拒否（`stop_reason: refusal`）で止まったら実行の失敗として扱い、次回の実行は `sonnet` で試す | TEXT-11、TEXT-12、IMPL-14 |
| 2 | IMPL-30 | 計画の難しさの判定 | 受付 AI | 同上（同じセッション） | 作業ごとに使うモデルの決め方を決めるまで使わない（[ADR-20261024-004][adr-master] の決定 8）。~~印に `plan=opus` か `plan=fable` を書く。人はラベル `plan:fable` / `plan:opus` で上書きし、ラベルが優先~~ | TEXT-12、IMPL-10 |
| 3 | IMPL-31 | 計画 | 計画 AI | 既定 `opus` / xhigh（受け入れの判定とラベルは、IMPL-30 のとおり使わない） | `opus` が「設計判断・アーキテクチャの選択・原因不明の障害解析を含む」と自己申告したら、同じ回の実行で続けて、1 回だけ `fable` / high で計画し直す（投稿するのはやり直した計画だけ）。2 回目の自己申告は無視して記録に残す。計画のレビューの指摘で計画し直すときは、直す前の計画と同じモデル | IMPL-10、[ADR-20261018-002][adr-redo]、[ADR-20261019-003][adr-replan] |
| 4 | IMPL-32 | 実装（1 ラウンド目） | 作業 AI | `opus` / high（設定の初期値。種類ごとに変える決め方は別に決める。IMPL-25） | 上限は `opus`。`fable` には上げない | 「[決まっていること][f00]」、[ADR-20261024-002][adr-no-stages] |
| 5 | IMPL-33 | レビュー（3 つの軸と見落としの軸を、軸ごとに別のセッションで） | レビュー AI | `opus` / xhigh。4 つの軸とも同じ値で始め、軸ごとに分けるかは基本設計の設定の値で決める | 設定で変える。往復の途中では変えない（ラウンド 2 以降は、最初のラウンドの `review` の印の `model=` のモデルで起こす） | IMPL-16、IMPL-19 |
| 6 | IMPL-34 | 批評（🔴 🟡 の再検証。進行 Bot が別に起こす独立セッション） | 批評 AI | `opus` / high | 変えない | IMPL-22、REVIEW-2 |
| 7 | IMPL-35 | 修正（2 ラウンド目以降） | 作業 AI | 1 ラウンド目が `sonnet` なら `opus` / high に 1 段上げる。`opus` で始めていればそのまま | 上げたことを記録と Issue のコメントに残す。往復 3 回で停止中（`round-limit`）。再計画は人が指示する（自動では計画 AI に戻さない） | IMPL-24、IMPL-25 |
| 8 | IMPL-36 | 再レビューと再批評 | レビュー AI、批評 AI | IMPL-33・IMPL-34 と同じ | 載せ直しで差分が変わらなければレビューを回さず印を付け直す | IMPL-21、MERGE-6 |
| 9 | IMPL-37 | 計画のレビュー（3 の計画の後、投稿する前。ほかの行の順を変えないよう、最後に足した） | レビュー AI | 基本設計の「[設定][design-settings]」の `models.planReview` | `fix` なら、同じ回の実行で計画 AI に計画し直させ、もう一度レビューする（上限は設定）。結果は計画コメントに書かない。上限まで計画し直しても `fix` なら、計画を投稿せずに停止中（`plan-limit`） | IMPL-10、[ADR-20261018-004][adr-planrev]、[ADR-20261019-003][adr-replan]、[ADR-20261024-002][adr-no-stages] |

決まり：

- 役の間でモデルを「上げる」のは IMPL-31（計画 AI の自己申告）と IMPL-35（作業 AI の 2 ラウンド目）の 2 か所だけで、どちらも 1 段・1 回まで。ほかの切り替えは設定ファイルの変更で行う（人のラベル `plan:*` は、モデルの決め方を決めるまで使わない）。
  例外は IMPL-29 の受付 AI の拒否による `haiku` → `sonnet`。これは実行の失敗からの回復で、上げる扱いには数えない
- effort は `--effort` で役ごとに渡す。`opus` の既定は medium なので、表の値を明示する。`haiku` の既定は medium、`sonnet` と `fable` の既定は high
- モデルは `--model` で渡す（エージェント定義の `model` より優先される。実機の試し（段階 2）で確認）。別名は `fable` `opus` `sonnet` を使い、`haiku` だけは別名が旧版に解けるので完全な ID `claude-haiku-5-5` を書く（「[決まっていること][f00]」の「版番号を書かない」の例外。Claude Code の別名が 5.5 を指すようになったら戻す）
- どの役にも `fable` を既定にしない（無人の `-p` で max-turns の下で動かすときの `fable` のクセ（途中で止まる、ツールを 1 回ずつ）が未収束の原因になりうるため）。`fable` が走るのは、計画 AI の自己申告で選ばれた計画だけ
- 利用枠の見方：1 Issue で走るセッションは、下書き 1 回（差し戻すたびに 1 回増える）、計画 1〜3 回と計画のレビュー 1〜2 回（計画し直す回数の上限が初期値のとき）、実装 1 回、レビュー（3 つの軸と見落としの軸）と批評が往復ごとに 1 組（5 セッション。4 つの軸の 🔴 🟡 が 0 件のラウンドは、批評 AI を起こさないので 4 セッション。IMPL-16、IMPL-18）、修正（衝突の解消を含む）が往復ごとに 1 回。進行 Bot だけの載せ直しで差分が変わった再レビューは往復に数えないので、base ブランチが進んで差分が変わるたびに、レビューと批評が 1 組増える（IMPL-24、[ADR-20261022-003][adr-rounds]）。IMPL-14 の累計の上限はこの合計に掛かる。先の依頼が中止されたときは、計画の見直しが 1 回走る（FLOW-43）。人が `/verify-issue` などから受け入れの Skill（`intake`）で頼んだ受付 AI のセッションは、頼むたびに 1 回走り、1 回の実行と 1 日の利用枠と 1 Issue の累計に入る（[ADR-20261022-004][adr-intake-req]）
