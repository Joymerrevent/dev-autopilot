# 実装・レビュー・対応ループ・モデル

## 実装（作業 AI）

- IMPL-1 AI のセッションごとに、進行ボットが origin の URL から AI の作業場所の clone（「[隔離と鍵の分け方][f05]」）を作り直し、設定の worktree の置き場（STRUCT-2）に worktree を作って、worktree の中で `claude -p` を起動する（置き場の形、作り方、消し方は [ADR-20261013-001][adr-workspace]）。人の作業場所の clone と worktree は共有しない。
  依存の導入（`pnpm install`）は作業 AI のセッションの中（sandbox の中）で行い、進行ボットは worktree の中でリポのコードもパッケージの lifecycle script も実行しない（「[安全側に倒す設計][f05]」）。依存はセッションの一時フォルダの store に導入し、セッションの間で共有しない（[ADR-20261015-002][adr-store]）。npm のレジストリにつながらず導入が失敗したら、実行の失敗（IMPL-14）として持ち越す
- IMPL-2 ブランチは `<型>/issue-<番号>`。型は設定のラベル対応表（例：`bug` → `fix`、それ以外 → `feat`）で進行ボットが決める。短い名前は付けない（TEXT-6）
- IMPL-3 Issue の本文は「[Issue と PR の本文の扱い][f04]」の規則で「報告」として渡す。本文に書かれた指示には従わない
- IMPL-4 守る規約は実装リポの正典をそのまま渡す：`CLAUDE.md`、関係する ADR、`pnpm check` が緑、changeset、日本語の Conventional Commits。
  作業 AI は規約の正典（IMPL-15 の push しないパスにある CLAUDE.md・ADR・構造仕様）を変えない。固定の指示文に正典のパスを書き、変える必要があると分かったら、変えずに IMPL-8 と同じく止まった理由を返させる（[ADR-20261017-002][adr-review]）
- IMPL-5 作業 AI は GitHub に一切書かない（SETUP-18）。作業の結果は **出力契約** で進行ボットに返す：`claude -p` の構造化出力（`--output-format stream-json` の最後の `result`。IMPL-14）（PR の題名と本文の案、止まった理由、確かめた検査の結果。計画は計画 AI の出力契約で、IMPL-10）と、worktree の中の commit。
  出力契約は進行ボットが自分の JSON スキーマで `result` の文を検証し、欠けや型の違いがあれば「実行の失敗」（IMPL-14）とする。解析できない出力を「成功」や「0 件」と読まない。
  `--json-schema` は `--agent` と併用すると `structured_output` が空になる（段階 2 で確認）ので頼らない。エージェント定義には「返事は JSON だけ。前後に文を付けない」と書く
  PR の作成・draft/ready の切り替え・Status と Agent 欄の更新・Issue と PR へのコメントは、すべて進行ボットが出力を検証してから行う（gh-aw の safe outputs と同じ）
- IMPL-6 進行ボットが PR を `develop` 向けに draft で作る。本文に `Closes #<番号>` と検査の結果を書く（`Closes #<番号>` は人向けの表示。`develop` 向けの PR には GitHub が Issue との結びつきを張らないので、結びつけには使わない）。題名は Conventional Commits の規約（小文字か日本語で始める。squash の件名になり commitlint が検査する）に進行ボットが照らしてから使う。
  PR と Issue は、(1) head のブランチ名が `<型>/issue-<番号>`（IMPL-2）、(2) head のリポが base と同じ（fork でない）、(3) 進行ボットの署名付きの結びつきの印がある、の 3 つで結びつける。PR を作った直後に、Issue に `note kind=link pr=<PR の番号>`、PR に `note kind=link issue=<Issue の番号>` の印付きのコメントを投稿する。作者のアカウントは条件にしない（SETUP-13）。
  同じリポに、ブランチ名が一致するのに結びつきの印が無い PR があれば、Issue を `needs-human` にし、`note kind=stop reason=unlinked-pr` を投稿する。fork からの PR は、本文が Issue を参照していても扱わない。Issue 1 件に結びつく PR は 1 件で、マージされずに閉じられていれば `needs-human`（[ADR-20261016-001][adr-pr]）
- IMPL-7 PR を作ったら進行ボットが Status を In Review にし、担当者（Assignee）はメンテナのまま。AI の担当は Project の単一選択欄「Agent」で表す（値：`worker` `reviewer` `human` `paused`）
- IMPL-8 ADR の起票が要ると分かったら、作業 AI は実装せずに「止まった理由」を出力契約で返し、進行ボットが Issue へコメントして `needs-human` を付ける（ADR が先、実装は承認後）。規約の正典（IMPL-4）を変える必要があると分かったときも同じ
- IMPL-9 着手の前に、基線が緑であることを確かめる。緑でない（赤、無い、保留）なら、新しい着手（計画を含む）・最初の実装・載せ直しをせず、Issue に `needs-human` は付けない。作った PR のレビュー・修正・収束・マージの判定・片付けと、受け入れ・承認の確定は続け、基線が緑に戻った実行から自動で再開する（壊れた基線の上に積まない。Anthropic の harness の「まず動くことを確かめる」。[ADR-20261015-006][adr-flow]）。
  実行の記録に、緑でない必須チェックの名前を残し、`check` の warn と `/dev-autopilot` の状態の表示に出す。
  確かめ方は `origin/develop` の最新 commit に対する必須チェック（IMPL-27 と同じ一覧）がすべて `success` であること。進行ボットは worktree の中で `pnpm check` を実行しない（進行ボットがリポのコードを実行しないため。「[安全側に倒す設計][f05]」）
- IMPL-10 実装の前に、計画 AI（作業 AI とは別のセッション）が計画を出力契約で返し、進行ボットが Issue にコメントする。段階 5〜7 では計画を投稿した実行では実装に入らず、次回の実行で実装に入る（人がこの計画を見て止められる）。段階 8 以降も、計画と実装は別の実行で進める（重い工程は 1 回の実行で 1 つ。FLOW-4。[ADR-20261015-006][adr-flow]）。計画は記録として残す（Jules の計画の承認）
  - 計画に必ず含める項目：対象のファイル・モジュール・型定義とその依存関係、作業の手順と順序、手順ごとの完了条件、検証方法（どのテスト・コマンドで確かめるか）、範囲外とするもの、想定する commit の分割。
    作業指示（agent brief）はパスを書かないが、計画は「どう作るか」なのでパスを書いてよい
  - 作業 AI は計画を、進行ボットが組み立てる固定の指示文の中で「作業の内容」として受け取る（TEXT-3）。前のセッションの思考や文脈の引き継ぎには頼らない（モデルが違えば思考ブロックは読めない）
  - **計画コメントの印と検疫**：進行ボットが投稿する計画コメントには `plan` の印（`head`、計画のハッシュ、`sig`。「[印と固定の見出しの一覧][f04]」）を付ける。次回の実行で計画を読み戻すときは IMPL-20 の 3 条件（投稿者・未編集・署名）を満たす印のあるコメントだけを使い、
    作業 AI に渡す直前に TEXT-11 の検疫を通す。計画は作業指示とリポを読んだ AI の文であり、作業指示に紛れた指示を運びうるため、作業指示と同じ扱いにする。人が計画を止めるときは Agent 欄を `paused` にするか `needs-human` を付ける
  - 計画 AI のモデルは受け入れの印 `plan=opus|fable`（TEXT-12）と人のラベル（`plan:fable` / `plan:opus`。ラベルが優先）で決まる。既定は `opus`（xhigh）。
    計画 AI の `opus` が「設計判断・アーキテクチャの選択・原因不明の障害解析を含む」と出力契約で自己申告したら、進行ボットは 1 回だけ `fable`（high）で計画し直す（2 回目の自己申告は無視し、記録に残す）。
    モデルの判定を誤ったときの害は利用枠の増減と計画の質だけ。計画の内容が作業 AI に届く経路は、上の印と検疫で守る
- IMPL-11 PR は進行ボットが draft で作り、収束して Ready to Merge になったときに進行ボットが ready にする（Copilot coding agent と OpenHands の形。途中の PR を人が誤ってマージしない）
- IMPL-12 テストを消す・skip する・期待値を緩める・lint を抑止する変更は、作業指示が明示していない限り禁止する。レビュー AI はこれを 🔴 として探す（Anthropic の harness：「テストを消したり編集したりするのは許されない」）
- IMPL-13 1 回のセッションの上限を設定に持つ。初期値は 45 分・200 ターン（Copilot は 59 分、GitHub Agentic Workflows は 20 分・500 ターンが既定）。
  時間の上限は `claude` に無いので、進行ボットが止める（止め方は IMPL-14。止めた後に AI のコマンドを残さない）。ターンは `--max-turns`。上限に当たったら途中の状態を commit せず、作業場所は作り直すか片付けるまで残す。途中の状態は次のセッションに引き継がない（[ADR-20261013-001][adr-workspace]。引き継ぐかは UNDECIDED-26）。扱いは IMPL-14 の表
- IMPL-14 **実行の失敗と作業の失敗**。「実行の失敗」は作業の中身と無関係に起きる失敗で、その Issue は `needs-human` を付けずに次回へ持ち越す。同じ Issue で 3 回続いたら `needs-human`（FLOW-29）。「作業の失敗」は AI の作業の結果が条件を満たさないことで、「対応ループ」の往復で扱う

  | 契機 | 扱い | 根拠 |
  |---|---|---|
  | 利用枠切れ（HTTP 429） | 実行の失敗。持ち越し | 本項 |
  | 時間の上限（45 分）に進行ボットが止めた | 実行の失敗。持ち越し | IMPL-13 |
  | 止めた後に、AI のコマンドの残りが止まったと確かめられない | `needs-human`（作業場所を消さず、次の AI のセッションを起動しない） | 本項、[ADR-20261018-001][adr-usage] |
  | 全体の止める合図（リポの変数）で進行ボットが止めた | 実行の失敗に数えない。持ち越し（合図が `run` に戻った後に続ける） | 「[運用の規則][f01]」、[ADR-20261017-007][adr-stop] |
  | ターンの上限（`--max-turns`）に当たった | 実行の失敗。持ち越し | IMPL-13 |
  | `claude` の異常終了、出力契約が解析できない・欠けている | 実行の失敗。持ち越し | IMPL-5 |
  | 依存の導入でレジストリにつながらない | 実行の失敗。持ち越し | IMPL-1 |
  | 受付 AI の拒否（`stop_reason: refusal`） | 実行の失敗。次回は `sonnet` で試す | TEXT-12 |
  | 作業 AI が「止まった理由」を返した（ADR が要る等） | 作業の失敗。`needs-human` | IMPL-8 |
  | レビューの fix | 作業の失敗。往復（上限 3 回） | IMPL-24 |
  | CI の赤（`failure`、`timed_out`） | 作業の失敗。往復（上限 3 回） | IMPL-27 |

  記録には `is_error` `num_turns` `usage` `modelUsage` を残し、1 Issue あたりの利用枠はここから取る（[ADR-20261018-001][adr-usage]）。出力は `--output-format stream-json` と `--include-partial-messages` で受け、メッセージごとの `message_delta` の `usage`（最後のトークン数）を記録に残す。
  `assistant` のイベントの `usage` は同じメッセージで重複し、`output_tokens` は最後の値でないので、足し上げに使わない（FACT-29）。
  正常に終わった回（`result` があり、`terminal_reason` が中断（`aborted_` で始まる値）でない）は、`result` の `total_cost_usd` を費用とし、`modelUsage` をモデルごとのトークンとして記録する。
  途中で止めた回（`result` が無いか、`terminal_reason` が中断）は、費用をその回の 1 セッションの費用の上限（`--max-budget-usd`）とみなす（`stream-json` のイベントは費用を持たない）。トークンは、書き終えたメッセージの `message_delta` と、書いている途中のメッセージの `message_start` から数え、出力が分からないメッセージがあったことを記録に残す。
  上限とみなすと、ほとんどの場合は多めに数える。ただし、書いている途中で止めたメッセージ 1 つ分は少なく数えうる（`--max-budget-usd` もメッセージの間で確かめるので、上限をメッセージ 1 つ分超えうる。FACT-39）。
  子プロセスは `setpgrp` で別のプロセスグループに起こす。途中で止めるとき（時間の上限、全体の止める合図。[ADR-20261017-007][adr-stop]）は、`claude` のプロセスグループに `SIGTERM` を送り、猶予（設定に持つ。STRUCT-2）の間に終わらなければ `SIGKILL` を送る。
  `claude` が終わった後、そのセッションの Bash のコマンドのプロセスグループが残っていないかを確かめ、残っていれば `SIGKILL` で止める（コマンドは `claude` と別のプロセスグループで動き、`SIGTERM` を無視したコマンドと `SIGKILL` の後のコマンドは残る。FACT-38）。
  残りの見つけ方は基本設計で決める。残りが止まったと確かめられなければ `needs-human`（上の表）。`SIGINT` は使わない（書いている途中で止めると、`result` がその回の費用を 0 と数える。FACT-38）。費用の上限は `--max-budget-usd` でも掛ける。
  設定に持つ上限は、1 セッションの時間とターンと費用（IMPL-13、`--max-budget-usd`）に加え、1 Issue の累計の利用枠（往復を含む）、実行の失敗の再試行の回数（3）と間隔、1 回の実行と 1 日の利用枠（SETUP-12）。1 Issue の累計の利用枠と 1 日の利用枠は、費用（Claude Code が出す USD 換算の値）で数え、トークンはモデルごとに記録に残す（[ADR-20261018-001][adr-usage]）。累計が上限に当たったら `needs-human`。数え上げは手元の記録で行い、記録を失ったときの扱いは「[運用の規則][f01]」
- IMPL-15 **漏えいの検査と push**。進行ボットは、GitHub に書くすべての文（diff、commit メッセージと author、PR の題名と本文、計画・レビュー・対応・受け入れのコメント、🟢 から起票する Issue）に、漏えいの検査（鍵の形式、メールアドレス、機械上のパス、進行ボットの設定と記録の内容）を掛ける。引っかかれば書かずに `needs-human`。
  検査の実装は dev-autopilot 自身の `plugin/src/` に持ち、worktree の中の `check:leak`（AI が書き換えられる）は使わない。マージの判定（MERGE-2）のときは最終の head の diff 全体に掛け直す（過去の記録に頼らない）。
  push の前に、diff が「進行ボット・次のセッション・CI が実行するか、規則として読むパス」（`.claude/**` `CLAUDE.md` `.mcp.json` `.github/**` `dev-autopilot/**` と、規約の正典のパス（business-os なら `docs/adr/**` `docs/design/**`）。設定に持つ）に触れていれば push せず `needs-human`
  （MERGE-4 の判定より前。CI が AI の書いたワークフローを secrets 付きで実行しないため。レビュー AI と修正のセッションが、作業 AI の書き換えた正典を規則として読まないため。[ADR-20261017-002][adr-review]）。`dev-autopilot/**` は、dev-autopilot を別のリポに移して business-os から消した後も残す（外すのは安全の境界を緩める変更で、残せば同じ名前のフォルダが business-os に戻ったときにも止まる。[ADR-20261016-003][adr-move] の決定 5）。
  push は進行ボットの clone から `git push origin <検証した SHA>:refs/heads/<型>/issue-<番号>` の形で行い、ブランチ名でなく SHA を送る。API の head（初回は base）が送る SHA の祖先であること（fast-forward で届くこと）を確かめる

## レビュー（レビュー AI）

- IMPL-16 PR の差分を、作業 AI とは別の作業場所で読む。レビューの 3 つの軸（動作・仕様・規約。REVIEW-1）ごとに、進行ボットが別のセッションを起こす（[ADR-20261017-002][adr-review]）。
  作業場所は、軸のセッションごとに進行ボットが origin の URL から clone し、PR の head（API の SHA）で切る専用の worktree（作業 AI の worktree と同じ書き込みの規則。[ADR-20261013-001][adr-workspace]）。3 つのセッションを並列で起こすか順に起こすかと、作業場所の名前の付け方は、基本設計で決める。
  軸のセッションは同じレビュー用のエージェント定義で起こし、どの軸を見るかを固定の指示文と `review` Skill の引数で渡す（REVIEW-5）。規約の正典は作業場所（PR の head）のものを読む（作業 AI は正典に触れる diff を push できない。IMPL-15）。
  手順は `review` Skill（`change-review` を v2 に組み直したもの。「[レビューの Skill][f08]」）を使う。核は変えない（実行して確かめる、fail-open を探す、収束するまで回す）
- IMPL-17 結果は、いまの PR と同じ形で PR のコメントに書く（行に付けるレビューコメントにしない）。
  1 回目は「## レビュー結果（基点: `develop`）」、2 回目以降は「`## 再レビュー結果 R<n>（対象: <範囲>）`」。
  冒頭の判定は「**通してよい。ブロッカーなし。**」か「**🟡 `<n>` 件を直してから通したい**」。末尾にラウンドの表（| ラウンド | 指摘 | 最も重い種類 |）を置く。
  参考：business-os の PR [#77][bos-pr-77] [#71][bos-pr-71] [#68][bos-pr-68] のコメント（2026-10-06〜07、R1 → 対応 → R2 で 0 件 → マージ）
- IMPL-18 進行ボットが機械で読むために、人が読む本文に加えて固定の印を 1 行足す（`review` の印。欄は「[印と固定の見出しの一覧][f04]」の表が正本。`sig` は IMPL-20）。
  `verdict` を pass にするのは、次の 5 つをすべて満たすときだけ（「🔴 🟡 が 0 件」だけでは、無いものを pass と読む）：
  (1) レビュー AI と批評 AI の出力契約が完全に解析できた、(2) レビューが収束した（「未収束」でない）、(3) `is_error` が偽、(4) 重要度ごとの件数がすべて数値で返った、(5) 実際に使われたモデル（`modelUsage`）が設定と一致した。
  5 つの条件は、3 つの軸のレビュー AI のセッションと、批評 AI のセッションのすべてに掛ける（[ADR-20261017-002][adr-review]）。進行ボットは軸ごとの指摘を、仕様 → 動作 → 規約の順に並べて 1 つのコメントにする（REVIEW-1）。軸をまたいで同じ問題を指摘していても束ねない。
  5 つを満たしたうえで 🔴 High と 🟡 Medium が 0 件なら pass、1 件でもあれば fix（`change-review` の止めどきの規則：🟢 Low だけのラウンドになったら直さずに記録して終わる）。
  (1)〜(5) のどれかを満たさなければ印を書かず、「実行の失敗」（IMPL-14）として持ち越す。
  判定は印だけで行い、本文の言い回しは解析しない（言い回しは変わりうる）。印は GitHub のレビュー状態を使わないので、同じアカウントでも動く（SETUP-13）。
  `review` の印の `round` は 1 から欠けずに続くことを判定の条件にし、欠けていたら `needs-human`（印のコメントの削除は API から検出できないため）。`dropped_high` は PR ごとの累計を書く（[ADR-20261015-004][adr-markers]）
- IMPL-19 レビュー AI のモデルは設定で変えられるようにする。作業 AI と同じモデルでもよい（effort は別。「モデルの流れ」）。段階 6 の比較のためだけに `fable` で回したレビューは印を書かない（shadow。判定に混ぜない）
- IMPL-20 **印の真正性**：正は GitHub に置き、手元の記録に依存しない。進行ボットは、次の 3 つをすべて満たすコメントの印だけを読む。
  (a) 投稿者が進行ボットのアカウント（設定に持つ）、(b) コメントが未編集（GraphQL の `lastEditedAt` が null、または `userContentEdits.totalCount` が 0。`updated_at` は非表示（minimize）でも変わるので使わない。リアクションでは変わらない。段階 2 で確認）。受け入れの下書き（TEXT-12）は人が編集する前提なのでこの条件を掛けず、`agent-ready` 後に進行ボットが確定の印を新しいコメントで投稿する）、
  (c) 印に進行ボットの署名 `sig=<HMAC>` があり検証できる。署名の対象は印の `sig` 以外のすべての欄（「[印と固定の見出しの一覧][f04]」）で、進行ボットだけが持つ鍵で計算する。鍵は PAT と同じ秘密の置き場（SAFE-15）のファイルに置き、AI のセッションには渡さない。
  手元の記録にはコメント ID も残すが、判定には使わない（手元の記録は上限の数え上げにだけ使う。進行ボットが途中で死んで記録を失っても、GitHub の状態から判定できる。「[運用の規則][f01]」）。
  AI の出力を投稿する前に、`<!-- dev-autopilot:` で始まる文字列を進行ボットが取り除く（AI の出力に印を混ぜても、署名が無いので判定に使われない）。取り除く規則は、印を読む処理（`plugin/src/marker.ts`）と同じ規則（空白の揺れを含む）にする。AI のセッションに前回の印を渡すときは、進行ボットが読み取った値（ラウンド・件数・判定）だけを渡す。
  署名の対象には、`sig` 以外の欄に加えて、印の種類・リポ・置き場の Issue か PR の番号を含める（別の Issue や PR に写した印の署名は通らない）。同じ Issue か PR の中で、進行ボットのアカウントが投稿した印のうち (b) か (c) を満たさないものが 1 つでもあれば、印の置き場の Issue か PR を `needs-human` にし、`note kind=stop reason=marker-invalid` を投稿する（受け入れの下書きには (b) を掛けない。[ADR-20261015-004][adr-markers]）
  **進行ボットが投稿した文は、投稿者がコラボレータであっても常に AI の出力として扱う**（TEXT-1 の「コラボレータの文」には数えない。見分けは投稿者でなく署名付きの印の有無で行う）
- IMPL-21 再レビューの入力は「前回の印から読み取った値（ラウンド・件数・判定。IMPL-20）と指摘」「修正コミットの範囲（SHA）」「差分」だけ。作業 AI の対応コメント（「確認済み」の主張）は渡さない（「[レビューの Skill][f08]」の文脈のバイアス）
- IMPL-22 **批評 AI**。3 つの軸のレビュー AI が出力契約で返した 🔴 と 🟡 をまとめて、進行ボットが別のセッション（`critic` エージェント、新しい文脈、レビュー AI と別に作った作業場所。[ADR-20261013-001][adr-workspace]）に差分とともに渡し、指摘ごとに「反対する前提」で実際のコードで再現を試みさせる。
  批評 AI は指摘ごとに、再現できたか（実行済み / 読んだだけ）、確信度（0〜100）、推奨する重要度を返す。進行ボットは次の規則で統合し、1 つの `review` の印とコメントにする：
  🔴 は 🟡 より下げない（再現できなくても 🟡 のまま残す）。🟡 は確信度がしきい値（設定）未満なら 🟢 に下げる。🟢 は批評 AI に渡さない。
  批評 AI が 🔴 を「再現できない」と返した PR は、その後 pass になっても `merge=human` にする（人が落とした理由を見てマージする。MERGE-2）。批評 AI の出力契約が解析できなければ IMPL-18 の (1) を満たさず、実行の失敗

## 対応ループ

- IMPL-23 判定が fix なら、作業 AI を PR の head から作った新しい作業場所で起動し（[ADR-20261013-001][adr-workspace]）、最新のラウンドの 🔴 と 🟡 だけに対応させる。push は進行ボットが漏えいの検査（IMPL-15）を通してから行う。🟢 はこの PR では直さない（直すと再レビューが新しい指摘を生み、ループが終わらない）。
  対応の結果は「`## R<n> の指摘への対応（<コミット>）`」のコメントに、指摘ごとの対応と確認を書く（いまの PR と同じ形）。
  印は `fix`（`round` `head` `sig`。「[印と固定の見出しの一覧][f04]」）
- IMPL-24 往復の回数に上限を持つ（最初は 3 回）。超えたら Status を Blocked にし、`needs-human` ラベルを付け、経緯を Issue にコメントする。人が外すまで再着手しない（FLOW-1）。同じ指摘が 2 ラウンド続けて出たら振動として同じ扱い
- IMPL-25 **詰まったときの上げ方**。作業 AI が `sonnet` のとき、作業 AI の 2 ラウンド目（最初の修正のセッション）から `opus`（high）に 1 段上げる。作業 AI のラウンドは、実装を 1、修正を 2 以降と数える（「モデルの流れ」の表と同じ。`review` と `fix` の印の `round` とは数え方が違う）。`fable` には上げない。
  3 回で `needs-human` にする規則（IMPL-24）は変えず、再計画は人が指示する（自動では計画 AI に戻さない。fail-closed）。上げたことは記録と Issue のコメントに残し、段階 5 で「`sonnet` で始めて `opus` で通った件数」を数えて開始モデルを種類ごとに決める
- IMPL-26 🟢 は進行ボットが Issue にする（`change-review` の「見送りは記録とセット」の規則）。1 件 1 Issue、題名は指摘の見出し、本文に PR 番号・ラウンド・失敗シナリオ・推奨を写し、ラベル `from-review` を付ける。本文は AI の出力として扱い、作業 AI には渡さない（Issue の本文は著者を問わず渡さない。TEXT-1、IMPL-20）。
  マイルストーンは付けない。人がマイルストーンを付けるまで受け入れ（TEXT-12）も走らせない（🟢 の Issue が毎日増えて人の読む量を超えないため）。同じ見出しの open な Issue があれば作らずにコメントで PR 番号を足す（重複を防ぐ）。
  Issue を作ってから PR を Ready to Merge にする（先にマージすると、Issue 化に失敗したとき指摘が消える）
- IMPL-27 終了条件：CI が緑、かつ最新のラウンドの印が `verdict=pass`（🔴 🟡 が 0 件。🟢 は残ってよい）。
  「CI が緑」の定義：設定に列挙した必須チェック（例：`check (ubuntu-latest)` `check (windows-latest)` `commitlint`）のすべてが、PR の head SHA に対して `success`。必須チェックのうち 1 つでも、head に対するチェックがまだ作られていないか、結果が `success` 以外なら、緑ではない（検査が走らなかった変更を通さない）。
  緑でないときの扱いは、必須チェックごとに結果を読み、1 つでも当てはまれば次の表の上の行から順に決める。同じ head に同じ名前のチェックが複数あるとき（再実行）は、最新の 1 件を採る（[ADR-20261016-001][adr-pr]）

  | CI の結果 | 扱い |
  | --- | --- |
  | `action_required` | `needs-human`（ワークフローの実行に人の承認が要る） |
  | `failure`、`timed_out` | 修正に回す。失敗したチェックの名前と結果だけを、最新のラウンドの 🔴 として作業 AI に渡し、往復（IMPL-24）に数える。CI のログは渡さない（作業 AI は自分の作業場所で `pnpm check` を実行して確かめる）。`fix` の印の `round` は、最新の `review` の印の `round` と同じ |
  | チェックがまだ作られていない（push の直後）、`queued`、`in_progress`、`pending`、`waiting`、`requested` | 待つ。次の実行で読み直す |
  | `cancelled`、`skipped`、`neutral`、`stale` | 待つ。同じ head で、完了から設定の時間が経っても変わらなければ `needs-human`（人が再実行するか、原因を確かめる） |
  | すべて `success` | 緑 |

  照合はチェック名だけでなく、チェックを出した app（GitHub Actions）と、base 側に存在するワークフローのパスでも行う（AI が同じ名前の job を足して緑にする経路を塞ぐ）。必須チェックの一覧が空なら点検（SETUP-2）を fail にする（空を「すべて success」と読まない）。
  進行ボットは実行の中で CI を待たず、次回の実行で結果を読む（FLOW-4）。いまの運用（2 回目のレビューで指摘 0 件ならマージ）を含み、🟢 だけ残った場合も収束とする。
  1 回目から pass なら 1 回で収束とする。満たしたら Status を Ready to Merge にする
- IMPL-28 Ready to Merge になった PR は、進行ボットが「[マージ][f03]」の条件でマージの可否を判定し、結果を印として PR に書く。マージの実行は人（「[マージ][f03]」）

## モデルの流れ

工程ごとに、どの役がどのモデルと effort で動き、どこで切り替わるかの一覧。値はすべて設定ファイルの初期値（STRUCT-2）で、本節が役ごとのモデルの正本。
「[決まっていること][f00]」の表はここを参照する。実機で使われたモデルは記録の `modelUsage` の欄（FLOW-5）と突き合わせる。モデルは別名で書く（版番号を書かない。「[決まっていること][f00]」）。
表の「順」は工程の並び。「番号」は要件の番号で、ほかの文書は番号で工程を指す（振り直さない。[README][readme] の「要件を変えるとき」）。

| 順 | 番号 | 工程 | 役 | モデル / effort | 切り替わる条件 | 根拠 |
|---|---|---|---|---|---|---|
| 1 | IMPL-29 | 受け入れ（検疫は TypeScript で AI を使わない。下書きの作成） | 受付 AI | `claude-haiku-5-5` / medium（別名 `haiku` は Haiku 4.5 に解けるので、haiku だけは完全な ID で書く。段階 2 で確認） | 拒否（`stop_reason: refusal`）で止まったら実行の失敗として扱い、次回の実行は `sonnet` で試す | TEXT-11、TEXT-12、IMPL-14 |
| 2 | IMPL-30 | 計画の難しさの判定 | 受付 AI | 同上（同じセッション） | 印に `plan=opus` か `plan=fable` を書く。人はラベル `plan:fable` / `plan:opus` で上書きし、ラベルが優先 | TEXT-12、IMPL-10 |
| 3 | IMPL-31 | 計画 | 計画 AI | 既定 `opus` / xhigh。印かラベルが `fable` なら `fable` / high | `opus` が「設計判断・アーキテクチャの選択・原因不明の障害解析を含む」と自己申告したら、1 回だけ `fable` / high で計画し直す。2 回目の自己申告は無視して記録に残す | IMPL-10 |
| 4 | IMPL-32 | 実装（1 ラウンド目） | 作業 AI | `opus` / high から始める。段階 5 で問題なく回る種類から `sonnet` / high へ下げる | 上限は `opus`。`fable` には上げない | 「[決まっていること][f00]」、[段階 5][f06] |
| 5 | IMPL-33 | レビュー（3 つの軸を、軸ごとに別のセッションで） | レビュー AI | `opus` / xhigh（段階 6 で `fable` / high と比べて決め直す）。3 つの軸とも同じ値で始め、軸ごとに分けるかは段階 6 で決める | 設定で変える。往復の途中では変えない | IMPL-16、IMPL-19、[段階 6][f06] |
| 6 | IMPL-34 | 批評（🔴 🟡 の再検証。進行ボットが別に起こす独立セッション） | 批評 AI | `opus` / high | 変えない | IMPL-22、REVIEW-2 |
| 7 | IMPL-35 | 修正（2 ラウンド目以降） | 作業 AI | 1 ラウンド目が `sonnet` なら `opus` / high に 1 段上げる。`opus` で始めていればそのまま | 上げたことを記録と Issue のコメントに残す。往復 3 回で `needs-human`。再計画は人が指示する（自動では計画 AI に戻さない） | IMPL-24、IMPL-25 |
| 8 | IMPL-36 | 再レビューと再批評 | レビュー AI、批評 AI | IMPL-33・IMPL-34 と同じ | 載せ直しで差分が変わらなければレビューを回さず印を付け直す | IMPL-21、MERGE-6 |

決まり：

- 役の間でモデルを「上げる」のは IMPL-31（計画 AI の自己申告）と IMPL-35（作業 AI の 2 ラウンド目）の 2 か所だけで、どちらも 1 段・1 回まで。ほかの切り替えは設定ファイルの変更か人のラベルで行う。
  例外は IMPL-29 の受付 AI の拒否による `haiku` → `sonnet`。これは実行の失敗からの回復で、上げる扱いには数えない
- effort は `--effort` で役ごとに渡す。`opus` の既定は medium なので、表の値を明示する。`haiku` の既定は medium、`sonnet` と `fable` の既定は high
- モデルは `--model` で渡す（エージェント定義の `model` より優先される。段階 2 で確認）。別名は `fable` `opus` `sonnet` を使い、`haiku` だけは別名が旧版に解けるので完全な ID `claude-haiku-5-5` を書く（「[決まっていること][f00]」の「版番号を書かない」の例外。Claude Code の別名が 5.5 を指すようになったら戻す）
- どの役にも `fable` を既定にしない（無人の `-p` で max-turns の下で動かすときの `fable` のクセ（途中で止まる、ツールを 1 回ずつ）が未収束の原因になりうるため）。`fable` が走るのは、受け入れの判定か人のラベルか計画 AI の自己申告で選ばれた計画と、段階 6 の比較のレビューだけ
- 利用枠の見方：1 Issue で走るセッションは、受け入れ 1 回、計画 1〜2 回、実装 1 回、レビュー（3 つの軸）と批評が往復ごとに 1 組（4 セッション。IMPL-16）、修正が往復ごとに 1 回。IMPL-14 の累計の上限はこの合計に掛かる
