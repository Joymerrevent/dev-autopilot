問いは 4 つある：1 回の実行で進める段の数え方、基線が赤のときの扱い、段階 5（計画と実装を動かし、レビューは人が行う段階。段階は dev-autopilot を少しずつ動かす導入の順番で、正本は「[段階][setup]」の表）の Agent 欄、手元の記録を使うかどうか。

## 背景と課題（Context and Problem Statement）

問い 1（UNDECIDED-5）：段の数え方

- FLOW-4 は、段を 7 つ（受け入れ、計画、実装と PR の作成、レビュー（批評を含む）、修正、マージの判定、マージ後の片付け）と定め、「Issue ごとに 1 回の実行で 1 段だけ進める」とする
- 「[Issue の状態の遷移][flow]」の承認の確定（FLOW-18）、収束（FLOW-23）、載せ直し（FLOW-25）と、催促（MERGE-3）が、7 つのどれに当たるかが無い。すべてを 1 段と数えると、承認の確定だけで 1 回の実行を使う
- IMPL-10 と FLOW-20 は「段階 5〜7 では計画を投稿した実行では実装に入らない」とし、IMPL-10 は「段階 8 以降は同じ実行で続け」とする（段階 5〜7 は、計画と実装を動かし、レビュー AI と対応ループを順に足す段階。段階 8 は、進行役が PR にマージの判定の印を書き始める段階）。段階 8 以降は計画と実装の 2 段を 1 回で進むことになり、「1 段だけ」と食い違う

問い 2（UNDECIDED-6）：基線が赤のとき

- IMPL-9 は、着手の前に基線（`origin/develop` の最新の commit の必須チェック）が緑であることを確かめ、赤なら着手せず `needs-human` を付けるとする
- 基線の赤は `develop` の事情で、Issue の事情ではない。Issue に `needs-human` を付けると、`develop` が直っても人がラベルを外すまで進まない
- [ADR-20261013-001][adr-workspace] で、計画と最初の実装の作業場所は、進行役の clone で fetch した `origin/develop` から作ると決めた。基線が赤のまま計画や実装に入ると、赤の `develop` の上に積むことになる

問い 3（UNDECIDED-7）：段階 5（レビューは人が行う段階）の Agent 欄

- FLOW-21 と「段階による違い」は、段階 5（計画と実装を動かし、レビューは人が行う段階）の draft PR では Agent 欄を `human` にする（人がレビューする）とする
- 同じ節の決まりは「進行役は Agent 欄を `human` と `paused` にしない」「`human` の Issue と PR には進行役は触らない」とする（`human` と `paused` は人の意思表示）
- 進行役が `human` を書くと、決まりにより進行役は以後 Issue に触らず、人がマージした後の片付け（FLOW-27、MERGE-7。Issue を閉じ、作業場所を消す）も行われない。`develop` 向けの PR は、マージしても Issue を自動では閉じない

問い 4（UNDECIDED-8）：手元の記録

- FLOW-4 は「手元の記録は使わない」とし、「[運用の規則][flow]」は「手元の記録は補助にする」とする
- 実行をまたいで数える値がある：同じ Issue で続いた実行の失敗の回数（3 回で `needs-human`。IMPL-14、FLOW-29）、Issue ごとの累計の利用枠（IMPL-14）、1 日の利用枠（SETUP-12）、受け入れ AI が拒否した Issue の次のモデル（`sonnet`。IMPL-29）。GitHub の状態からは数えられない
- 記録を失うと（記録のフォルダの掃除、マシンの移行、壊れたファイル）、数が 0 に戻り、上限の `needs-human` が黙って効かなくなる
- 「1 回だけ書くコメント」は、[ADR-20261015-004][adr-markers] で `note` の印から判定すると決めたので、手元の記録は要らない

課題：1 回の実行で、どの段をいくつ進めるか。基線が赤のとき、何を止めるか。段階 5（レビューは人が行う段階）の Agent 欄に何を書くか。手元の記録を何に使い、失ったときどうするか。

## 判断の決め手（Decision Drivers）

- 1 回の実行の長さと利用枠が、上から押さえられること（lock を長く持たない。FLOW-4）
- 人の待ちと実行の回数を、必要以上に増やさないこと
- `develop` の事情で Issue の状態を汚さず、直ったら自動で再開すること
- Agent 欄の値の意味を 1 つに保ち、人の意思表示と進行役の値を混ぜないこと
- 判定の正を GitHub に保ち、記録を失っても止める側に倒れること（SAFE-4）

## 検討した選択肢（Considered Options）

問い 1：段の数え方

- 案 1-A：重い段（AI のセッションを起動する段）だけを、Issue ごとに 1 回の実行で 1 つにする。軽い段は続けてよい。段階 8（進行役が PR にマージの判定の印を書き始める段階）以降も、計画と実装は別の実行にする
- 案 1-B：案 1-A に加え、段階 8（進行役が PR にマージの判定の印を書き始める段階）以降は計画と実装を同じ実行で続ける
- 案 1-C：どの段も、Issue ごとに 1 回の実行で 1 つにする

問い 2：基線が赤のとき

- 案 2-A：新しい着手・最初の実装・載せ直しだけを止め、Issue にラベルを付けない。基線が緑に戻ったら自動で再開する
- 案 2-B：今のまま、着手しようとした Issue に `needs-human` を付ける
- 案 2-C：実行全体を止める

問い 3：段階 5（レビューは人が行う段階）の Agent 欄

- 案 3-A：進行役は Agent 欄に `worker` `reviewer` と空だけを書く。段階 5（レビューは人が行う段階）の draft PR では空にする。片付けは、`human`・`paused`・`needs-human` の除外より先に判定する
- 案 3-B：段階 5（レビューは人が行う段階）だけは、進行役が `human` を書いてよい例外にする
- 案 3-C：Agent 欄に、人がレビューする番を表す値（例：`human-review`）を足す

問い 4：手元の記録

- 案 4-A：判定には使わず、上限の数え上げだけに使う。記録を失ったら止める側に倒す
- 案 4-B：数え上げも GitHub に書く（`note` の印など）
- 案 4-C：手元の記録を使わず、実行をまたぐ上限を持たない

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-A」「案 4-A」。
理由: ~~1 回の実行で起動する AI のセッションは Issue ごとに 1 つまでになり~~ **訂正（2026-10-16）**：1 回の実行で進める重い段は Issue ごとに 1 つまでになり（重い段のうちレビューは、レビュー AI と批評者の 2 つのセッションを起動する。決定は変わらない）、実行の長さと利用枠を上から押さえられる。基線の赤で Issue の状態が汚れず、直れば自動で再開する。Agent 欄の値の意味が 1 つに保たれ、片付けも止まらない。判定は GitHub に残したまま、記録を失っても上限が黙って効かなくなることは無い。

### 決定 1：1 回の実行では、重い段を Issue ごとに 1 つだけ進める

- 重い段は、AI のセッションを起動する段：受け入れ、計画、実装と PR の作成、レビュー（批評を含む）、修正。Issue ごとに、1 回の実行で 1 つまで
- 軽い段は、AI のセッションを起動しない段：承認の確定（FLOW-18）、収束（FLOW-23）、マージの判定（FLOW-24）、載せ直し（FLOW-25）、催促（MERGE-3）、片付け（FLOW-27）。重い段の前後に、同じ実行で続けてよい
- CI の結果が要る段（収束、マージの判定）は、CI の結果が出ている実行でだけ進める。進行役は CI を待たない（IMPL-27）。push した実行（実装、修正、載せ直し）では、push した Issue を次の実行まで進めない
- 段階 8（進行役が PR にマージの判定の印を書き始める段階）以降も、計画と実装は別の実行で進める。IMPL-10 と FLOW-20 の「段階 8 以降は同じ実行で続け」を改める。段階 5〜7（計画と実装を動かし、レビュー AI と対応ループを順に足す段階）の「計画を投稿した実行では実装に入らない」は、決定 1 に含まれる
- 正常な流れの目安（1 日 1 回、往復なし）：(1) 受け入れ、(2) 人が `agent-ready` を付けた後に承認の確定と計画、(3) 実装と PR、(4) レビューと収束とマージの判定、(5) 人がマージした後に片付け。実行は 5 回、往復が 1 回増えるごとに 2 回増える。間隔を狭めるのは段階 9（WIP の上限を上げ、実行の間隔を狭める段階。FLOW-12）

### 決定 2：基線が緑でなければ、新しい着手・最初の実装・載せ直しだけを止める

- 基線（`origin/develop` の最新の commit の必須チェック。IMPL-9）が緑でない（赤、無い、保留）とき、止めるのは次の 3 つだけ
  - 新しい着手（FLOW-19。計画を含む）
  - 最初の実装（計画を投稿した Issue の、PR を作る前の実装）
  - 載せ直し（FLOW-25、MERGE-6。`origin/develop` を取り込む操作）
- 続けるもの：受け入れ、承認の確定、作った PR のレビュー・修正・収束・マージの判定（PR の head の上での作業で、赤の `develop` を取り込まない）、片付け
- Issue に `needs-human` を付けない。IMPL-9 と FLOW-29 の契機から「基線が赤」を外す。基線が緑に戻った実行から、止めた 3 つを自動で再開する
- 実行の記録に、基線が緑でないことと、緑でない必須チェックの名前を残す。`check` は warn に出し、`/dev-autopilot` の状態の表示にも出す

### 決定 3：進行役は Agent 欄に人の値を書かず、片付けは除外より先に判定する

- 進行役が Agent 欄に書く値は、`worker` `reviewer` と空だけ。`human` と `paused` は人だけが書く（決まりのまま）
- 段階 5（レビューは人が行う段階）の draft PR（FLOW-21）では、Agent 欄を空にする。人がレビューする番であることは、Status `In Review` と段階の設定（`stage`）で表し、`/dev-autopilot` の状態の表示で「人の番」と出す
- 片付け（FLOW-27、MERGE-7）は、`needs-human`・`human`・`paused` の除外より先に判定する。PR がマージされていれば、Issue を閉じて作業場所を消す。Agent 欄とラベルは書き換えない（人の意思表示を上書きしない）。マージは人の最後の操作なので、片付けは人の意思表示に反しない

### 決定 4：手元の記録は、上限の数え上げにだけ使う

- 判定（次の段、収束、マージの判定、「1 回だけ書く」）には、手元の記録を使わない。GitHub の状態と印から決める（FLOW-4 のまま）
- 手元の記録で数えるのは、実行をまたぐ上限の数え上げだけ
  - (a) 同じ Issue で続いた実行の失敗の回数（IMPL-14）
  - (b) 受け入れ AI が拒否した Issue（次の実行のモデル。IMPL-29）
  - (c) Issue ごとの累計の利用枠（IMPL-14）
  - (d) 1 日の利用枠（SETUP-12）
- 記録を失ったときの扱い（上限が黙って効かなくなる側に倒さない）
  - `setup` は、記録のフォルダに、作った日時を書いた印のファイルを置く。印のファイルが無ければ、`check` は fail にする（記録を失ったのか初めてなのかを、黙って「初めて」と読まない）。人が `setup` をやり直して、失ったことを認める
  - 進行中の Issue（Status が `In Progress` 以降、または計画の印がある）に記録が無いときは、Issue の (a) は 1 回目の失敗で `needs-human`、(c) は次のセッションを起こさずに `needs-human`（`note kind=stop reason=records-missing`）
  - (b) の記録が無ければ、受け入れ AI は `haiku` で起動する（拒否されれば実行の失敗として記録に残り、次の実行で `sonnet` に上がる）
  - (d) の当日の記録が無ければ、当日の残りの AI のセッションを起こさない（翌日から 0 で数える）
- 「[運用の規則][flow]」の「手元の記録は補助にする」を、決定 4 の文に改める
- 記録の置き場は、マシンの設定に置く（[ADR-20261015-005][adr-settings]）。マシンを移すときは、記録のフォルダも移す

### 影響（Consequences）

- 良い点: ~~1 回の実行で起動する AI のセッションは、Issue ごとに 1 つまで。~~ **訂正（2026-10-16）**：1 回の実行で進める重い段は、Issue ごとに 1 つまで（レビューの段では、レビュー AI と批評者の 2 つのセッションを起動する）。実行の長さと利用枠を上から押さえられる
- 良い点: 承認の確定や収束のような軽い段で、実行の回数を無駄にしない
- 良い点: 基線の赤で Issue の状態が汚れず、`develop` が直った実行から自動で再開する
- 良い点: Agent 欄の値の意味が 1 つに保たれ、どの段階でも、マージの後の片付けが止まらない
- 良い点: 記録を失っても、上限が黙って効かなくなることは無い
- 悪い点: 段階 8（進行役が PR にマージの判定の印を書き始める段階）以降も計画と実装が別の実行になり、1 Issue あたりの実行が 1 回多い（間隔を狭める段階 9 で目立たなくなる）
- 悪い点: 基線が赤いまま放置されると、新しい着手が止まり続ける。warn と状態の表示で知らせるが、自動では人を呼ばない
- 悪い点: 段階 5（レビューは人が行う段階）の間は、Agent 欄だけでは人の番と分からない（Status と状態の表示で補う）
- 悪い点: 記録を失うと、進行中の Issue が 1 回の失敗で `needs-human` になる

### 確認方法（Confirmation）

- 結合テスト（偽の `gh` と偽の `claude`）で、次を検査する
  - ~~1 回の実行で、1 つの Issue に対して起動する AI のセッションが 1 つまでであること。~~ **訂正（2026-10-16）**：1 回の実行で、1 つの Issue に対して進める重い段が 1 つまでであること（レビューの段では、レビュー AI と批評者の 2 つのセッションを起動する）。承認の確定と計画、レビューと収束とマージの判定が、同じ実行で進むこと
  - 基線が緑でないとき、新しい着手・最初の実装・載せ直しをせず、`needs-human` を付けず、緑に戻った実行で再開すること
  - 段階 5（レビューは人が行う段階）の draft PR で Agent 欄が空になること。`human` の Issue でも、PR がマージされていれば片付けが走り、Agent 欄を書き換えないこと
  - 記録の印のファイルが無いと `check` が fail になること。進行中の Issue の記録が無いと、1 回目の失敗で `needs-human` になること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：重い段だけ 1 つ（段階 8（マージの判定の印を書き始める段階）以降も計画と実装は別の実行）

- 良い点: 1 回の実行の AI のセッションが Issue ごとに 1 つまでになり、規則が段階で変わらない
- 良い点: 段階 8（進行役が PR にマージの判定の印を書き始める段階）以降も、人は計画を読んでから実装の前に止められる
- 悪い点: 段階 8（進行役が PR にマージの判定の印を書き始める段階）以降、1 Issue あたりの実行が 1 回多い

### 案 1-B：段階 8（マージの判定の印を書き始める段階）以降は計画と実装を同じ実行で続ける

- 良い点: 段階 8（進行役が PR にマージの判定の印を書き始める段階）以降、1 Issue あたりの実行が 1 回少ない
- 悪い点: 1 回の実行で起動する AI のセッションが、段階によって 1 つか 2 つになる。実行の長さの見積もりが段階で変わる

### 案 1-C：どの段も 1 つ

- 良い点: 規則が最も単純
- 悪い点: 承認の確定・収束・マージの判定のような軽い段だけで実行を使い、1 Issue あたりの実行が倍近くになる

### 案 2-A：新しい着手・最初の実装・載せ直しだけ止める

- 良い点: Issue の状態が汚れず、自動で再開する。進行中の PR は止まらない
- 悪い点: 赤いまま放置されると気づきにくい

### 案 2-B：着手しようとした Issue に `needs-human` を付ける

- 良い点: Issue の上で人が気づける
- 悪い点: `develop` の事情で Issue の状態が汚れ、直っても人がラベルを外すまで進まない

### 案 2-C：実行全体を止める

- 良い点: 赤の `develop` の上で何も進まない
- 悪い点: 赤の `develop` と関係の無い、進行中の PR のレビューや修正まで止まる

### 案 3-A：Agent 欄は `worker` `reviewer` と空だけ

- 良い点: Agent 欄の値の意味が 1 つに保たれる
- 悪い点: 段階 5（レビューは人が行う段階）の間は、Agent 欄だけでは人の番と分からない

### 案 3-B：段階 5（レビューは人が行う段階）だけ進行役が `human` を書く

- 良い点: Project の画面で人の番と分かる
- 悪い点: 「`human` は人の意思表示」の決まりに例外ができ、`human` の Issue には触らない決まりで、マージの後の片付けが止まる

### 案 3-C：`human-review` の値を足す

- 良い点: 人の番と、人が引き取った状態を分けて表せる
- 悪い点: Project の欄の選択肢と状態の数が増える（SETUP-6、`setup`）

### 案 4-A：上限の数え上げだけ手元の記録、失ったら止める側

- 良い点: GitHub への書き込みを増やさずに上限が効き、記録を失っても止める側に倒れる
- 悪い点: 記録を失うと、進行中の Issue が止まりやすくなる

### 案 4-B：数え上げも GitHub に書く

- 良い点: 記録を失う心配が無い
- 悪い点: 実行の失敗や利用枠のたびに Issue へ書き込み、人の読む量が増える。1 日の利用枠は Issue に属さないので、書く場所が無い

### 案 4-C：実行をまたぐ上限を持たない

- 悪い点: 失敗の繰り返しや利用枠の使い過ぎを止められない
- 却下
