# 受け入れの依頼で受付 AI の下書きが漏えいの検査だけに当たったときは、全体を止めない記録を別の置き場に残し、作業の単位を進める次の実行が Issue に security の印を書く

要件の UNDECIDED-104（人が `/verify-issue` などから呼ぶ受け入れの Skill（`intake`）の依頼で起こされた実行で、受付 AI が返した下書きが漏えいの検査だけで見つかったときに、Issue の安全の軸に値を入れるか。[決めていないこと][undecided]の「ADR で決めること」の「安全と設定」）を決める。

本 ADR では、[ADR-20261111-001][adr-keep-halt] の全体を止める記録を「見つかりの記録」、本 ADR で足す全体を止めない記録を「漏えいの見つかりの記録」と呼んで分ける。「作業の単位を進める実行」は、1 回の実行の流れの順 6〜9（基線を読み、状態を組み立て、作業の単位を進める）に進む実行（定期と手動。待つ時間を過ぎた点検の依頼で、定期の実行として続ける実行を含む）を指す。

## 背景と課題（Context and Problem Statement）

- [ADR-20261027-002][adr-leak] は、GitHub に書く文の漏えいの検査（鍵の形式、メールアドレス、機械上のパス、進行 Bot の設定と記録の内容。要件の IMPL-15）で見つかったら、止め方を停止中にせず、見つかった作業の単位で、安全の軸に攻撃の疑い（AI の文）を入れる（`security` の印の `where` が `leak`）とした。AI が秘密や機械の情報を書いたのは操られた疑いもあるので、maintain 以上の人が確かめてから外す。漏えいの検査は正当な文にも当たりやすいので、全体は止めない（決定 2）
- [ADR-20261112-003][adr-intake-finding] は、人が `/verify-issue` などから呼ぶ受け入れの Skill（`intake`）の依頼で起こされた進行 Bot の実行（以下「受け入れの依頼の実行」）で、受付 AI が返した文の欄（下書きの 4 つの欄と `policyReason`）が検疫に当たったら、GitHub に書かずに見つかりの記録（[ADR-20261111-001][adr-keep-halt]）を書き、次の実行から全体を止めるとした。漏えいの検査だけで見つかったとき（`where` が `leak`）は、全体を止めないので、見つかりの記録を書かない（決定 1）。漏えいの検査だけで見つかったときに安全の軸をどうするかは、同じ ADR の「本 ADR で決めないこと」に残した
- 受け入れの依頼の実行は GitHub に何も書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。今の設計では、漏えいの検査だけで見つかったときは、見つかった種類と場所を結果のファイル（`intake-result-<依頼の ID>.json`）に書くだけで、Issue の安全の軸に値が入らない（基本設計の「[AI のセッション][design-ai]」の「役ごとの出力契約」の「共通の決まり」の表の、受け入れの依頼の結果の行。詳細設計の「[設定と記録][d-records]」の「見つかりの記録」の「書かないとき」）
- 受付 AI は、定期の実行で下書きを書くときも、受け入れの依頼の実行でも、同じエージェント（`dev-autopilot:brief:triager`）を、同じ起動の形・安全設定と、同じ組み立てで作った Issue の文で起こす（[ADR-20261112-003][adr-intake-finding] の背景）。定期の実行の下書きが漏えいの検査に当たれば、Issue の安全の軸に値が入る。受付 AI の出力は回ごとに変わるので、次の定期の実行で、漏えいの検査が見つけ直すとは限らない
- 受け入れの依頼の実行が、ほかの確かめ（Issue の累計の費用の上限など）に外れたときは、結果のファイルに理由を書くだけで、停止中にするか安全の軸に値を入れるのは、作業の単位を進める実行が同じ確かめで行う（基本設計の「[AI のセッション][design-ai]」の「起動の前の確かめ」の表の下）。漏えいの検査は AI の出力に掛けるので、作業の単位を進める実行の同じ確かめで見つけ直すとは限らない
- 見つかりの記録（基本設計の `security-pending/`）は、1 件でもあるか、読めないファイルが 1 つでもあれば全体を止める（[ADR-20261111-001][adr-keep-halt] の決定 1・3）。記録を読む処理は、`where` が `text` のほかの記録を形が違う（読めない）として、全体を止める（詳細設計の「[設定と記録][d-records]」のテストの表の `logic/run/records.ts`）。全体を止めない記録を同じ置き場に置けば、今の読み方では全体が止まる
- 手元の記録は判定に使わず、上限の数え上げに使う。例外は、全体を止める側にだけ使う見つかりの記録の 1 つだけ（[ADR-20261015-006][adr-flow] の決定 4、[ADR-20261111-001][adr-keep-halt] の決定 3、要件の「[運用の規則][flow]」）。[ADR-20261024-002][adr-no-stages] は、手元の記録を判定に使う例外を増やさないことを判断の決め手にした
- 人の Skill は、結果のファイルを待つ時間（`run.intakeWaitMinutes`。60 分）まで待つ。待つのをやめた後に書かれた結果のファイルは人に示されず、7 日を過ぎたら進行 Bot が消す（基本設計の「[状態遷移と判定][design-flow]」の「記録の置き場のほかのファイル」）

課題：受け入れの依頼の実行で、受付 AI の文の欄が漏えいの検査だけで見つかったときに、Issue の安全の軸に値を入れるか。入れるなら、GitHub に書かない決まりのまま、誰がいつ書くか。全体を止めない手元の記録を足すなら、全体を止める見つかりの記録と取り違えたときに、止める側に倒れる形にできるか。

## 判断の決め手（Decision Drivers）

- 安全：AI が書いた文の漏えいの検査で見つかったら、起こされ方を問わず、見つけた作業の単位で、maintain 以上の人が確かめるまで AI を進めない（[ADR-20261027-002][adr-leak] の決定 1）
- 動き続けること：誤って反応しやすい漏えいの検査で、ほかの作業の単位を止めない（[ADR-20261027-002][adr-leak] の決定 2）
- 正本と人の戻し方：安全の軸の値と外し方は GitHub を正本にし、人が GitHub の画面で確かめて外せる
- 確かめやすさ：全体を止める記録と全体を止めない記録を取り違えても、全体を止める側に倒れる。手元の記録が、判定を「進めてよい」に変える経路を持たない
- 費用：足す処理と、改める承認済みの決定が少ない。手元の記録を判定に使う例外を少なくする（[ADR-20261024-002][adr-no-stages] の判断の決め手）
- 制約：受け入れの依頼の実行は GitHub に何も書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。GitHub の外への通知は、印を GitHub に書いた後にだけ送る（[ADR-20261101-002][adr-notify]）

## 検討した選択肢（Considered Options）

- 案 A：今のまま、結果のファイルにだけ書き、安全の軸に値を入れない（UNDECIDED-104 の候補 (A)）
- 案 B：全体を止めない種類の手元の記録を書き、作業の単位を進める次の実行が Issue に `security` の印（`where` が `leak`）を書き、書けたら記録を消す（UNDECIDED-104 の候補 (B)）
- 案 C：検疫に当たったときと同じく見つかりの記録を書き、次の実行から全体を止める（UNDECIDED-104 の候補 (C)）

## 決定（Decision Outcome）

採用した選択肢:「案 B」。

理由: 受付 AI は起こされ方を問わず同じ仕事をするので、受け入れの依頼の経路だけ安全の軸に値が入らないと、[ADR-20261112-003][adr-intake-finding] が検疫について塞いだのと同じ形の隙間が、漏えいの検査に残る。案 B は、[ADR-20261112-003][adr-intake-finding] と同じく、受け入れの依頼の実行が GitHub に何も書かない決まりを変えずに、作業の単位を進める次の実行が Issue に `security` の印を書く。ほかの実行で漏えいの検査に当たったときと同じく、maintain 以上の人が確かめるまで、見つけた作業の単位で AI が進まず、全体は止めない（[ADR-20261027-002][adr-leak] のまま）。
案 A は、安全の軸に値を入れるかを結果を読んだ人に任せ、人が結果を読まないときは誰も値を入れない。案 C は、新しい種類の記録を足さずに済むが、ほかの実行より厳しく全体を止め、誤った反応のたびに全体が止まる。
案 B は、手元の記録を判定に使う例外を 1 つ増やす。例外は、`security` の印を書くことと、書けなかった作業の単位を同じ実行で進めないことだけに使い、どちらも作業の単位を止める側に当たる。記録は全体を止める見つかりの記録と別の置き場に置き、取り違えても全体を止める側に倒れる形にする（決定 2）。

### 決定 1：受け入れの依頼の実行で、受付 AI の文の欄が漏えいの検査だけに当たったら、漏えいの見つかりの記録を書き、GitHub には書かない

- 進行 Bot は、受け入れの依頼の実行で、受付 AI が返した文の欄（下書きの 4 つの欄と `policyReason`）が漏えいの検査だけに当たったら（結果のファイルの見つかりの `where` が `leak` だけで、`text` が無い）、結果のファイルを書く前に、漏えいの見つかりの記録を 1 件書く。中身は、受け入れの依頼の Issue の番号、`where`（`leak`）、`finding` の種類と場所（結果のファイルに書くものと同じ。文の欄の名前と行）、見つけた時刻、受け入れの依頼の実行の実行 ID。PR の番号は持たない。見つかった文と AI が書いた文は書かない（`security` の印のコメントと同じ）
- 検疫と漏えいの検査の両方で見つけたときは、今のとおり、`where` を `text` にした見つかりの記録を 1 件だけ書き、漏えいの見つかりの記録は書かない（[ADR-20261112-003][adr-intake-finding] の決定 1。全体の停止が漏えいの扱いに隠れないため）
- 受け入れの依頼の実行は、今のとおり GitHub に何も書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。`security` の印を書かず、GitHub の外への通知も送らない
- 全体は止めない。漏えいの見つかりの記録を書いた後も、受け入れの依頼の実行は、実行の終わり（1 回の実行の流れの順 10。記録と状態の表示を書き、lock を外す）まで、ほかのときと同じに行う（実行の終わりに点検の依頼を見つけて点検を行うときの試しのセッションも、ほかの止める条件に当たらなければ起こす）
- 漏えいの見つかりの記録を書けなかったとき（記録の置き場に書けない）は、GitHub に書かず、手当てが要る終わり方（マシンの中のフォルダの異常）で終える

### 決定 2：漏えいの見つかりの記録は見つかりの記録と別の置き場に書き、読めないファイルは全体を止める側に倒す

- 漏えいの見つかりの記録は、記録の置き場の中で、見つかりの記録を置くフォルダ（基本設計の `security-pending/`）と別のフォルダ（以下「漏えい用の置き場」）に書く。漏えい用の置き場の名前、ファイルの名前と形、書き方（排他の作成と一時のファイル）は、基本設計と詳細設計で決める
- `security-pending/` と、`security-pending/` を読む処理（全体を止めるかを決める処理）は変えない。`security-pending/` にあるファイルは、今のとおり、`where` が `text` の見つかりの記録の形に合わなければ読めないとして、全体を止める。漏えいの見つかりの記録が `security-pending/` にあっても、全体を止める側に倒れる
- 漏えい用の置き場を読む処理は、名前と中身が漏えいの見つかりの記録の形に合い、`where` が `leak` のファイルだけを読めたとする。ほかのファイル（一時のファイル、中身が壊れたもの、`where` が `text` のもの、名前が形と違うもの）と、漏えい用の置き場を読めないときは、読めない見つかりの記録と同じに扱い、[ADR-20261111-001][adr-keep-halt] の決定 3 のとおり、見つかりの記録があるものとして全体を止める。読めないファイルは、全体を止める記録か止めない記録かを中身で確かめられず、人が戻す途中で見つかりの記録を取り違えて置くこともあるため
- 漏えい用の置き場は、`security-pending/` と同じ時（lock を取った直後。1 回の実行の流れの順 2）に読む。読めないファイルがあれば、全体の停止の Issue があるものとして扱い、名前から Issue の番号を読めたファイルの作業の単位は、同じ実行では進めない（読めない見つかりの記録と同じ）。進行 Bot は、読めないファイルから印を書かず、ファイルも消さない
- 全体を止めるべき見つかりを全体を止めない記録として扱いうる所は、受け入れの依頼の実行が見つけた時に、文の欄が検疫に当たったかで書く記録の種類を決める所だけになる。今の、見つかりの記録を書くかを決める所と同じ所で、記録を読む処理には、全体を止める記録を全体を止めない記録と読む経路を足さない

### 決定 3：作業の単位を進める次の実行が Issue に `security` の印を書き、書けたら漏えいの見つかりの記録を消す

- 作業の単位を進める次の実行が、見つかりの記録から印を書き直すのと同じ時と場所（状態を組み立てた後、作業の単位を進める前）で、読めた漏えいの見つかりの記録ごとに、受け入れの依頼の Issue に、記録した `where`（`leak`）と `finding` と場所で `security` の印を新しく書く。全体の停止の Issue と `halt` の印は書かない（[ADR-20261027-002][adr-leak] の決定 2）
- Issue に `security` の印を書けたら（書き込みの応答で書けたと分かったとき。読み戻さない）、漏えいの見つかりの記録を消す。書けた印は、[ADR-20261101-002][adr-notify] のとおり GitHub の外へ通知する
- 受け入れの依頼の Issue が Project に無い（作業の単位でない）ときも、当てる先のリポにあれば `security` の印を書く。人が後で Issue を Project に入れたときに、安全の軸に値がある状態で始まり、maintain 以上の人が `## 安全の確認` を書くまで AI に渡さないため（[ADR-20261112-003][adr-intake-finding] の決定 2 と同じ形）。書いた `security` の印を組み立てた状態に足すのは、Issue が作業の単位のときだけ
- Issue が当てる先のリポに無くなった（消された、別のリポに移された。見分け方は見つかりの記録の書き直しと同じ）ときは、止める作業の単位が無いので、印を書かずに記録を消す。Issue を読めない（`404` など。見えないだけのこともある）ときは、無くなったと読まず、記録を残す
- `security` の印を書けなければ（断られた、届いたか分からない、書く直前に読んだ全体の止める合図が `run` でなかった）、記録を残す。Issue が作業の単位なら、書けなかった実行では進めない（見つかりの記録から `security` の印を書き直せなかった作業の単位と同じ）。次の作業の単位を進める実行が、もう一度書く。届いたか分からなかった印が実際には届いていても、もう一度書く（最新の `security` の印より後の `## 安全の確認` で値が外れるので、重ねて書くと値は外れない側に倒れる）
- 作業の単位を進めない実行（点検の依頼で起こされ、待つ時間を過ぎていない実行と、受け入れの依頼の実行）は、読める漏えいの見つかりの記録があっても、印を書かず、記録を消さず、AI のセッションを起こすかの判定にも使わない
- 漏えいの見つかりの記録で決めるのは、`security` の印を書くことと、書けなかった作業の単位を同じ実行で進めないことだけ。安全の軸の値と外し方は、今のとおり GitHub の印だけで決める。漏えいの見つかりの記録が無いことを、作業の単位を進める理由にも、安全の軸の値を外す理由にもしない

### 決定 4：結果のファイルに漏えいの見つかりの記録を書けたかを書き、点検と状態の表示に、見つかりの記録と分けて出す

- 結果のファイルには、今のとおり、文の欄を書かずに見つかった種類と場所を書く（[ADR-20261022-004][adr-intake-req] の決定 3）。加えて、見つかりの `where` が `leak` だけのときは、漏えいの見つかりの記録を書けたか（書けた・書けなかった）を書く。[ADR-20261112-003][adr-intake-finding] の決定 3 で足した、見つかりの記録を書けたかの欄を、`where` が `leak` だけのときにも使う形を第一にする。1 つの結果に 2 つの種類の記録を書くことは無いので、どちらの記録かは見つかりの `where` で決まる
- 人の Skill（`intake`）は、書けたときは、決まった文で次を示す。全体は止めないこと。作業の単位を進める次の実行（定期の実行か、`/dev-autopilot` の手動の 1 回実行）が Issue に `security` の印を書き、Issue の安全の軸に値が入ること。人がすること（印が付いた後に、maintain 以上の人が見つかった場所と種類を確かめ、誤った反応でなければ秘密を入れ替えるなどの手当てをしてから、`## 安全の確認` を書く。印より前に書いた `## 安全の確認` では値は外れない）
- 書けなかったときは、決まった文で、記録の置き場が異常なので Issue で安全の軸に値が入るとは限らないことと、見つかった場所と種類を人が確かめて、Issue に `agent-paused` を付けて作業の単位を止めるか、全体の止める合図を `stop` にするかを人が決めることを示す
- 点検は、漏えいの見つかりの記録がある間、warn に出す。見つかりの記録とは分けて示し、Issue の番号と見つけた時刻と、全体は止めていないことと、次の作業の単位を進める実行が `security` の印を書くことを示す。書けずに残した記録は、書けなかった回数と理由の種類も示す。読めないファイルは、読めない見つかりの記録と同じく warn に出し、全体を止めていることと人の戻し方を示す。どれも点検の fail にはしない
- 状態の表示（`status.json`、`/dev-autopilot`）も、見つかりの記録と分けて、Issue の番号と見つけた時刻と、次の作業の単位を進める実行が印を書くことを出す。読める漏えいの見つかりの記録は、全体を止める間に入れない。読めないファイルは、全体を止める間に入れる
- 欄の名前、決まった文、点検の項目と理由の記号、状態の表示の欄は、詳細設計で決める

### 影響（Consequences）

- 良い点（安全が上がる）: 受付 AI が漏えいの検査に当たる文を書けば、起こされ方を問わず、見つけた Issue の安全の軸に値が入り、maintain 以上の人が確かめるまで、見つけた作業の単位で AI が進まない。人が結果を読むか（待つのをやめた後に書かれた結果を含む）に依らない。[ADR-20261027-002][adr-leak] の決定 1 に、受け入れの依頼の実行を除く例外が残らない
- 良い点（正本と人の戻し方が上がる）: 見つけた事実が GitHub の `security` の印と GitHub の外への通知に載る。人は、ほかの実行で見つけたときと同じく、Issue で確かめて `## 安全の確認` を書けばよい
- 良い点（動き続けることを保つ）: 読める漏えいの見つかりの記録では全体を止めないので、誤った反応でほかの作業の単位が止まらない
- 悪い点（確かめやすさが下がり、費用が上がる）: 新しい種類の手元の記録と置き場、読む処理、書いて消す処理、結果のファイルの値、人の Skill の決まった文、点検の項目、状態の表示を足す。手元の記録を判定に使う例外が 2 つになり、[ADR-20261015-006][adr-flow] の決定 4 を改め、[ADR-20261024-001][adr-model-states] の決定 4 と [ADR-20261024-002][adr-no-stages] の決定 5 を読み替える。[ADR-20261024-002][adr-no-stages] の判断の決め手（手元の記録を判定に使う例外を増やさない）に反する
- 悪い点（運用のしやすさが下がる）: 漏えいの見つかりの記録が読めなくなる（一時のファイルが残る、中身が壊れる）と、全体が止まり、人がマシンの上で確かめて消すまで続く。誤った反応（テストの見本のメールアドレスなど）でも、maintain 以上の人が Issue に `## 安全の確認` を書くまで、見つけた作業の単位が止まる（ほかの実行で漏えいの検査に当たったときと同じ）
- 悪い点（人が気づく早さが下がる）: `security` の印と GitHub の外への通知は、作業の単位を進める次の実行まで出ない。定期の実行の間隔（`run.intervalHours`。初期値 24 時間）だけ遅れうる。人が `/dev-autopilot` で手動の 1 回実行を起こせば早まる。結果を見た人が印より前に `## 安全の確認` を書いても値は外れず、印が付いた後にもう一度書くことになる
- 悪い点（安全の残り）: 漏えいの見つかりの記録を書けなかったとき、書く前に実行が切れたとき、人かほかのプロセスが記録のファイルだけを消したときは、安全の軸に値が入らない（[ADR-20261111-001][adr-keep-halt] の見つかりの記録と同じ隙間）
- 中立: Project に無い Issue にも `security` の印が残る。人が Project に入れない Issue は作業の単位にならないので、Issue に `## 安全の確認` を書かなくても作業は止まらない

### 確認方法（Confirmation）

- 単体テストで、受け入れの依頼の実行が受付 AI の文の欄を検査した後に書く記録を確かめる。漏えいの検査だけなら漏えいの見つかりの記録を書き、見つかりの記録を書かないこと。検疫だけか両方なら、`where` を `text` にした見つかりの記録だけを書くこと。結果のファイルに、書いた記録を書けたかを書くこと
- 単体テストで、記録を読む処理の取り違えを確かめる。`security-pending/` に漏えいの見つかりの記録を置くと、読めないとして全体を止めること。漏えい用の置き場に、`where` が `text` の記録、一時のファイル、中身の壊れたファイルを置くと、読めないとして全体を止めること。読める漏えいの見つかりの記録だけなら、全体を止めないこと
- 単体テストで、漏えいの見つかりの記録を消す条件を確かめる。Issue に `security` の印を書けたときと、Issue が当てる先のリポに無くなったときに消し、書けなかったときと Issue を読めないときは残すこと
- 結合テスト（偽の GitHub と偽の `claude`）で、次を確かめる
  - 受付 AI に漏えいの検査に当たる下書きを返させると、受け入れの依頼の実行は GitHub に何も書かずに漏えいの見つかりの記録を書き、結果のファイルに種類と場所と、記録を書けたことを書く
  - 次の定期の実行は、全体の停止の Issue を開かず、作業の単位を進める前に Issue に `security` の印（`where` が `leak`）を書いて通知し、記録を消す。見つけた作業の単位は安全の軸に値がある状態になって進まず、ほかの作業の単位は進む。Project に無い Issue でも同じに書き、組み立てた状態に足さない
  - `security` の印の書き込みを断らせると、記録が残り、見つけた作業の単位だけが進まず、ほかの作業の単位は進む
  - 点検の依頼で起こされ、待つ時間を過ぎていない実行と、受け入れの依頼の実行は、記録があっても印を書かず、記録を消さない
  - 漏えいの見つかりの記録の中身を壊すと、次の実行はどの作業の単位でも AI のセッションを起こさず、点検の warn に出す
- 基本設計と詳細設計のレビューで、漏えいの見つかりの記録を書く所、読む所、印を書いて記録を消す所、点検と状態の表示が、本 ADR の決定と同じことを書いていることを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：今のまま、結果のファイルにだけ書き、安全の軸に値を入れない

- 良い点（費用が最も下がる）: 進行 Bot に足す処理も、改める承認済みの決定も無く、手元の記録を判定に使う例外も増えない。得るものは、費用の少なさと例外を増やさないことだけ
- 中立: 見つかった種類と場所は、結果のファイルで人に示す（案 B・C も同じ）
- 悪い点（安全が下がる）: Issue の安全の軸に値が入らないので、Issue が作業の単位なら（今か、後で Project に入れたとき）、maintain 以上の人の確かめを経ずに、定期の実行の AI が下書きや計画を進める。受付 AI の出力は回ごとに変わるので、定期の実行の漏えいの検査が見つけ直すとは限らない
- 悪い点（安全が下がる）: 止めるかは結果を読んだ人に任され、人の Skill が待つのをやめた後に書かれた結果は誰にも示されない。結果を読んだ人が使えるのも、Issue に `agent-paused` を付けることと全体の止める合図だけで、安全の軸の値（進行 Bot の署名付きの `security` の印）は人には入れられない
- 悪い点（正本と人の戻し方が下がる）: 見つけた事実が GitHub に残らず、GitHub の外への通知も出ない
- 悪い点（確かめやすさが下がる）: 漏えいの検査で見つかったときの扱いが、起こされ方で分かれる。[ADR-20261027-002][adr-leak] の決定 1（起こされ方で分けていない）に、受け入れの依頼の実行を除く例外を書き足す

### 案 B：全体を止めない種類の手元の記録を書き、作業の単位を進める次の実行が Issue に `security` の印を書く

- 良い点（安全が上がる）: 人が結果を読むかに依らず、Issue に `security` の印が載り、見つけた作業の単位で AI が進まない。案 A では値が入らない（案 C も入る）
- 良い点（正本と人の戻し方が上がる）: 見つけた事実と外し方の正本が GitHub の `security` の印に載り、人は GitHub の画面で確かめて `## 安全の確認` を書けばよい。案 A では GitHub に何も載らない（案 C も載る）
- 良い点（動き続けることを保つ）: 案 C と違い、読める記録では全体を止めず、誤った反応でほかの作業の単位を止めない。ほかの実行で漏えいの検査に当たったときと同じ扱いになる
- 中立: 印と通知が GitHub に出るのは、作業の単位を進める次の実行から（案 C も同じ。案 A では出ない）
- 悪い点（確かめやすさが下がり、費用が上がる）: 新しい種類の手元の記録と、置き場、読む処理、書いて消す処理、点検の項目、状態の表示を足す。手元の記録を判定に使う例外が 1 つ増え、[ADR-20261015-006][adr-flow] の決定 4 を改める（案 C は見つかりの記録の例外の中に収まる）
- 悪い点（運用のしやすさが下がる）: 漏えいの見つかりの記録が読めなくなると、全体が止まる。誤った反応でも、maintain 以上の人が `## 安全の確認` を書くまで、見つけた作業の単位が止まる（ほかの実行と同じ）
- 悪い点（安全の残り）: 記録を書けなかったときは、GitHub にも書かないので値が入らない（案 C も同じ）

### 案 C：検疫に当たったときと同じく見つかりの記録を書き、次の実行から全体を止める

- 良い点（費用が下がる）: 案 B と違い、新しい種類の記録と置き場を足さず、見つかりの記録の書き方・書き直し・点検・状態の表示を使う。手元の記録を判定に使う新しい例外も足さない（全体を止める側の例外の中に収まる）
- 良い点（安全が上がる）: 案 A・B と違い、AI が本当に秘密を読めていたときに、ほかの作業の単位でも、次の実行から AI のセッションが止まる
- 悪い点（動き続けることが下がる）: 機械上のパスやメールアドレスの誤った反応のたびに全体が止まり、maintain 以上の人が全体の停止の Issue と見つけた Issue の 2 か所で確かめる。受付 AI は Issue の文から下書きを書くので、Issue の文にメールアドレスや機械上のパスがあれば、下書きにも写りうる
- 悪い点（確かめやすさが下がる）: 漏えいの検査で見つかったときの扱いが、起こされ方で分かれる（受け入れの依頼の実行だけ全体を止める）。[ADR-20261027-002][adr-leak] の決定 2（全体は止めない）と [ADR-20261112-003][adr-intake-finding] の決定 1（漏えいの検査だけなら見つかりの記録を書かない）を改め、見つかりの記録の形（今は `where` が `text` だけ）に `leak` を足す。受け入れの依頼の実行の下書きは GitHub に投稿しないので、ほかの実行より厳しく扱う根拠は強くない

## 補足情報（More Information）

- 起票の経緯：[ADR-20261112-003][adr-intake-finding] の要件と設計への反映（2026-11-13）で、受け入れの依頼の実行で漏えいの検査だけに当たったときの安全の軸を決めていないと気づき、要件の UNDECIDED-104 に足した。2026-11-15 にメンテナの依頼で起票した。案 A〜C は UNDECIDED-104 の候補 (A)〜(C) と同じ。受け入れの依頼の実行が自分で GitHub に `security` の印を書く形は、[ADR-20261112-003][adr-intake-finding] が案 C として比べて採らなかった（GitHub に何も書かない決まりを改め、記録を消す経路を足す）ので、本 ADR では比べない
- 決定 2 の置き場の比べ：漏えいの見つかりの記録を、見つかりの記録と同じ `security-pending/` に置き、名前と中身で種類を分ける形も比べた。読めないファイルを全体を止める側に倒すことは同じだが、全体を止めるかを決める処理に「読めるが全体を止めない記録」の分かれ道が入る。分け方の誤り（名前だけ、`where` だけを見るなど）があれば、見つかりの記録を全体を止めない記録と読む経路ができ、[ADR-20261111-001][adr-keep-halt] の決定 1（見つかりの記録が 1 件でもあれば全体を止める）も改めることになる。別の置き場なら、見つかりの記録は、全体を止めない記録と読む処理を通らない
- 本 ADR で決めないこと
  - 漏えい用の置き場の名前、ファイルの名前と形、書き方。同じ Issue の記録が 2 件以上あるときに、`security` の印を 1 つにまとめるか（基本設計と詳細設計）
  - 結果のファイルの欄の名前、人の Skill が示す決まった文、点検の項目と理由の記号、状態の表示の欄（詳細設計）
  - 読めない漏えいの見つかりの記録を人が戻す手順。見つかりの記録の人の戻し方（基本設計の「[状態遷移と判定][design-flow]」の「記録の置き場のほかのファイル」の表の下）に、確かめる印を `where` が `leak` の `security` の印にした手順を足す形を第一にする（基本設計）
  - 書けないまま残り続ける読める漏えいの見つかりの記録を、人が消してよいか。全体を止めないので、残っても続くのは点検の warn と、見つけた作業の単位を進めないことだけ。要件の UNDECIDED-99（書き直せないまま残り続ける読める見つかりの記録を、人が消してよいか）と一緒に決める
  - 漏えいの見つかりの記録がある Issue か、安全の軸に値がある Issue に、人が受け入れの依頼をもう一度置いたときに、受付 AI を起こすか。今の設計では、受け入れの依頼の実行が受付 AI を起こす前の確かめで、Issue の安全の軸を読まない。要れば決めていないことに足す
- 外の利用者：結果のファイルを読むのは dev-autopilot の intake の Skill だけで、business-os の `/verify-issue` は intake の Skill を呼ぶ形で使う。2026-11-15 に business-os の `main` と `develop` の `.claude/skills/verify-issue/SKILL.md` を見て、まだ dev-autopilot を呼んでいないことを確かめた（呼ぶ形への拡張は、導入と点検の実装（段階 3）の business-os の PR で行う）
