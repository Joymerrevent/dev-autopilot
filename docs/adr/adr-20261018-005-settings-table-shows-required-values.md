# 設定の表には、要件が決めた初期値も値で書いて要件へリンクし、要件の値を変えるときは同じ PR で表も直す

[ADR-20261015-005][adr-settings] の決定 1 のうち、「要件が初期値を決めている項目は、表に値を写さず、要件の番号を指す」を改める。決定 1 のほかの項目（要件が決めていない値は「暫定」と書いて段階の出口で見直す、今の値の正本は設定ファイル、安全の境界を緩める変更は ADR で決める）と、決定 2 は据え置く。

## 背景と課題（Context and Problem Statement）

- [ADR-20261015-005][adr-settings] の決定 1 は、構造仕様に設定の項目の表を置き、要件が初期値を決めている項目は、表に値を写さず要件の番号を指すとした。値を要件と表の 2 か所に書くと、片方だけ直ってずれるため
- 基本設計の設定の表（`docs/design/basic/01-settings.md`。dev-autopilot#31）を決定 1 のとおりに書くと、項目の 57 行のうち 25 行で、初期値の欄が「SETUP-8」「FLOW-3」「IMPL-29」のような要件の番号か見出しの名前だけになった
- メンテナがレビューで、番号だけでは初期値が分からないと指摘した。番号から値を知るには、要件のファイルを開いて項目を探す必要がある。要件の項目は見出しではないので、リンクもファイルまでしか届かない
- 表は、`setup` が設定ファイルを作るときの元で、設定を変える人が今の初期値を確かめる場所でもある
- 要件には、要件を写したものを同じ PR で直す決まりがすでにある。図は要件の写しで、要件を変えたら同じ PR で図も直す（[要件を変えるとき][req-change]）

課題：要件が決めた初期値を、設定の表でどう示すか。

## 判断の決め手（Decision Drivers）

- 表を読めば、どの項目も初期値が分かること
- 要件と表の値が食い違ったときに、どちらが正しいかが決まっていること。食い違いが残りにくいこと
- 要件と表を直す手間が増えすぎないこと

## 検討した選択肢（Considered Options）

- 案 A：表に値を書き、出典の要件へリンクを添える。正本は要件のまま。要件の値を変える PR で、表も直す（図と同じ扱い）
- 案 B：今のまま、値を写さず要件の番号を書く
- 案 C：値を表だけに書き、要件からは表を指す（表を正本にする）
- 案 D：表に値を書き、要件と表の値の食い違いを機械で探す検査を足す

## 決定（Decision Outcome）

採用した選択肢:「案 A」。
理由: 表を読めば初期値が分かり、正本は要件のまま変わらない。食い違いは、図と同じく「要件を変える PR で一緒に直す」決まりと、レビューで防ぐ。

### 決定 1：設定の表には、要件が決めた初期値も値で書き、出典の要件へリンクする

- 要件が初期値を決めている項目も、表の初期値の欄に値を書く。値の後ろに、出典の要件の番号を添えてリンクにする（例：`agent-ready` `needs-human` `from-review` `plan:fable` `plan:opus`（SETUP-8 へのリンク））
- 値の正本は要件のまま。表の値は要件の写しで、食い違っていたら要件が正しい
- 要件が当てる先のリポごとの値として決めている項目（MERGE-4 の business-os の許可一覧など）は、当てる先のリポの名前を添えて値を書く

### 決定 2：要件の初期値を変えるときは、同じ PR で設定の表も直す

- 要件の初期値を変える PR では、設定の表の同じ項目も直す。要件の README の「要件を変えるとき」に、図と並べて書く
- 表を直すのを忘れても、要件が正本なので、表を要件に合わせて直せばよい

### 影響（Consequences）

- 良い点: 表を読めば、どの項目も初期値が分かる。`setup` を作る人と設定を変える人が、要件のファイルを探さずに済む
- 良い点: 正本は要件のままで、要件と ADR は「何をするか」の正本であり続ける
- 悪い点: 値が要件と表の 2 か所に書かれ、要件を変える PR で表も直す手間が増える
- 悪い点: 表を直し忘れると、食い違いが残る。見つけるのはレビューと、表を読む人になる

### 確認方法（Confirmation）

- 基本設計の設定の表を直すときに、要件が初期値を決めている行すべてに、値と出典の要件へのリンクがあることをレビューで確かめる
- 要件の初期値を変える PR のレビューで、設定の表の同じ項目も直したかを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：表に値を書き、要件へリンクする。要件を変える PR で表も直す

- 良い点: 表を読めば初期値が分かる。正本は要件のまま。図と同じ決まりなので、覚えることが増えない
- 悪い点: 2 か所に書く。直し忘れはレビュー頼み

### 案 B：今のまま、要件の番号を書く

- 良い点: 値は要件の 1 か所だけで、ずれない
- 悪い点: 表を読んでも初期値が分からない。番号から要件の項目を探す手間がかかる

### 案 C：表を正本にする

- 良い点: 値は表の 1 か所だけで、表を読めば分かる
- 悪い点: 要件から値が抜け、要件だけを読んでも動きの決まり（往復は 3 回まで、など）が分からなくなる。要件は「何をするか」、基本設計は「どう作るか」という分け方（基本設計の README）と合わない。要件の多くの項目を直す

### 案 D：食い違いを機械で探す検査を足す

- 良い点: 直し忘れを機械で見つけられる
- 悪い点: 要件の値は文の中に書かれていて、機械で取り出しにくい。値を取り出すために、要件の書き方を揃え直す必要がある。今の手間に見合わない。食い違いが実際に起きてから考えればよい
