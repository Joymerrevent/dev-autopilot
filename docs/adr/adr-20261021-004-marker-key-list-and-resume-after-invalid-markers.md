# 印の署名を確かめる鍵を一覧にしていつでも替えられるようにし、無効な印で止めた Issue は、人が needs-human を外せば知らせた印を数えずに続ける

> **Amended by [ADR-20261024-001][adr-20261024-001]（2026-10-24）**: 決定 4 の「人が `needs-human` を外す前に知らせた無効な印は、外した後は数えない」を、「push 以上の人が `## 再開` を書く前に、`stop` の印の `comments` に挙げた印は、再開の後は数えない」に改め、決定 5 の戻し方（Status を戻す、PR を閉じる、`agent-ready` を外す、`needs-human` を最後に外す）を、戻す先の選び方に改めた（決定 7）。鍵の一覧と替え方（決定 1〜3）と、挙げていない無効な印と再開の後に新しく書き換えられた印で止めることは据え置く。

要件の UNDECIDED-63（無効な印で止めた Issue をどう戻すか。印の署名の鍵をどう替えるか）を決める。

改める決定と、据え置く決定は次のとおり。

- [ADR-20261015-004][adr-markers]（署名付きの印と、人の操作の権限の確かめ）：決定 1 の「印が無効になっていたら止める」に、人が `needs-human` を外す前に進行 Bot が知らせた無効な印は、外した後は止める契機に数えない例外（本 ADR の決定 4）を足す。
  「署名が検証できる」は、本 ADR の決定 1 の鍵の一覧のどれかで検証できることと読む。署名の対象、未編集の条件、`review` の印の `round` の欠けで止めること、決定 2 は据え置く
- [ADR-20261020-001][adr-bots]（印を書いたと認めるアカウントの一覧）：決定 3 の「署名の鍵は 1 つのまま」を、書く鍵が 1 つのままであることと読む。確かめる鍵は、鍵を替える間だけ一覧に 2 つ以上並ぶ。アカウントを替えても鍵を替えないことと、ほかの決定は据え置く
- [ADR-20261015-001][adr-read]（AI の読み取りの範囲と秘密の置き場）：決定 2 の、印の署名の鍵を秘密の置き場のファイルに置き、進行 Bot だけが読むことは据え置く。確かめにだけ使う前の鍵も、同じ置き場に置く

## 背景と課題（Context and Problem Statement）

- IMPL-20（印の真正性）は、進行 Bot のアカウントが投稿した印のうち、未編集の条件 (b) か署名の条件 (c) を満たさないものが、同じ Issue か PR の中に 1 つでもあれば、印の置き場を `needs-human` にし、`note kind=stop reason=marker-invalid` を書く（[ADR-20261015-004][adr-markers] の決定 1。基本設計の「[状態遷移と判定][design-flow]」の次の工程の表の順 5）
- 人が編集した進行 Bot のコメントは、編集の記録（`lastEditedAt`）が残る。人が `needs-human` を外しても、次の実行の順 5 でまた止まる（UNDECIDED-63）。
  抜け道はコメントを消すことだけで、`review` の印を消すと、`round` の欠けで止まる（IMPL-18。`review` の印）。「[止まった状態から戻す手順][flow]」にも、`marker-invalid` からの戻し方が無い
- 印の署名は HMAC-SHA256 で作り、鍵は秘密の置き場の `marker-signing-key` の 1 つ（基本設計の「[状態遷移と判定][design-flow]」の「印の署名」）。HMAC は、書く鍵と確かめる鍵が同じで、鍵を持てば印を作れる
- 鍵を替えると、前の鍵で署名した印が、すべて署名の条件を満たさなくなる。基本設計の「印の署名」は、鍵を替えるのを、進行中の Issue が無いときにするとしている。
  一方、`intake` と `intake-final` の印は、着手の前の Issue（下書きを人が読む番の Issue、承認の確定の後に着手を待つ Issue）にも付く。鍵を替えると、着手の前の Issue もすべて止まり、戻せない
- 鍵が漏れたときは、替えるしかない。基本設計の再レビュー（2026-10-21）では、動かすマシンを替えるときに、新しいマシンで鍵を作り直しても、同じことが起きると分かった
- 鍵を替えた時刻は、マシンの中のことで、GitHub には残らない
- 印を書いたと認めるアカウントは、一覧（`safety.botAccounts`）に持ち、替えた後に前のアカウントの印が残る Issue と PR がすべて閉じたら、前のアカウントを外す（[ADR-20261020-001][adr-bots] の決定 4）

課題：鍵を替えても、開いた Issue と PR の印を読み続けるには、どうするか。鍵を替えてよい条件と、替える手順は何か。`marker-invalid` で止めた Issue を、人がどう戻すか。

## 判断の決め手（Decision Drivers）

- 鍵を替えても、着手の前の Issue を含め、開いた Issue と PR が止まらないこと
- 鍵が漏れたときに、漏れた鍵で確かめる印を読まない側に倒れること（フェイルセーフ）
- `marker-invalid` で止めた Issue を、人が確かめたうえで戻せること。人に知らせていない無効な印では、今のとおり止まること
- 印のコメントの削除を見つける守り（IMPL-18 の `round` の欠け）を弱めないこと
- GitHub から読めることだけで判定すること（鍵を替えた時刻は GitHub に無い）
- 印の投稿の時刻で決める規則（承認の確定の時刻の規則、戻した Issue のやり直し）を崩さないこと

## 検討した選択肢（Considered Options）

問い 1：鍵の替え方

- 案 1-A：署名を確かめる鍵を一覧にし、先頭の鍵で書き、前の鍵は確かめにだけ使う。前の鍵の印が残る開いた Issue と PR が無くなったら、一覧から外す
- 案 1-B：鍵は 1 つのまま。替える前に、印のある開いた Issue と PR を閉じる手順を基本設計に書く
- 案 1-C：鍵は 1 つのまま。替えるときに、前の鍵で確かめた印を、新しい鍵で署名し直したコメントで投稿し直す

問い 2：無効な印で止めた Issue の戻し方

- 案 2-A：人が `needs-human` を外す前に、進行 Bot が止めた理由の印で挙げた無効な印を、外した後は数えない
- 案 2-B：印のコメントが最後に変わった時刻（投稿か最後の編集）が、人が `needs-human` を外した時刻より前なら、数えない
- 案 2-C：戻し方を決めない。人が印のコメントを消すか、Issue を閉じて作り直す

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」。
理由: 鍵を替えても前の鍵の印を読み続けるので、開いた Issue と PR が止まらない。印のコメントは投稿し直さないので、時刻で決める規則も崩れない。
戻し方は、人が `needs-human` を外す前に知らせた印だけを数えないので、人が確かめていない無効な印では止まる。鍵を替えた時刻を GitHub から読めなくても、知らせた印は止めた理由の印から読める。

### 決定 1：印の署名を確かめる鍵を一覧にし、先頭の鍵で書く

- 進行 Bot は、印の署名の鍵を一覧で持つ。印を書くときは、一覧の先頭の鍵で署名する。印を確かめるときは、一覧の鍵を順に試し、どれかで検証できれば、IMPL-20 の (c) を満たすとする
- 一覧は、今のとおり秘密の置き場（[ADR-20261015-001][adr-read] の決定 2）に置き、進行 Bot だけが読む。AI のセッションには渡さない。
  HMAC は確かめる鍵でも印を作れるので、確かめにだけ使う鍵も、書く鍵と同じに秘密として扱う
- 一覧が空のときは、今のとおり点検を fail にする（空のファイルを「無い」と読む）
- 印に、どの鍵で書いたかを示す欄は足さない。署名の対象（[ADR-20261015-004][adr-markers] の決定 1）も変えない
- 一覧のファイルの名前と書き方（1 行に 1 つの鍵を並べるか、鍵の値をどう解くかなど）は、基本設計で決める

### 決定 2：鍵は、進行中の Issue があっても替えられる。替える手順を決める

- 鍵は、進行中の Issue の有無を問わず、いつでも替えてよい。基本設計の「印の署名」の「替えるときは、進行中の Issue が無いときを選ぶ」は外す
- 鍵が漏れていないときは、次の順に替える
  1. 人が新しい鍵を作り、一覧の先頭に足す。前の鍵は、一覧の 2 つ目より後に残す
  2. 進行 Bot は、次の実行から、新しい鍵で書き、一覧のどれかで確かめる（進行 Bot は、起動したときに秘密を読む。[ADR-20261015-001][adr-read] の決定 2）
  3. 前の鍵でだけ確かめられる印が残る開いた Issue と PR が無くなったら、人が前の鍵を一覧から外す
- 進行 Bot は、一覧に 2 つ以上の鍵があるとき、先頭でない鍵でだけ確かめられた印が残る開いた Issue と PR の番号を、点検の warn に出す。残りが無くなったら、前の鍵を外してよいことを warn に出す（外し忘れて、印を作れる鍵が多いまま残らないため）。出し方は基本設計で決める
- 動かすマシンを替えて、新しいマシンで鍵を作り直すときも、鍵を替えたものとして同じ順に従う（前の鍵を一覧に残す）

### 決定 3：鍵が漏れたときは、漏れた鍵を確かめにも使わない

- 鍵が漏れたとき（漏れたかもしれないときを含む）は、人が次の順に行う
  1. 全体の止める合図（[ADR-20261017-007][adr-stop]）を `stop` にする。鍵の一覧はマシンの中にあり、替え終わるまでに時間がかかりうるので、替え終わるまでの間に、漏れた鍵で作られた印を読まないため
  2. 新しい鍵を作って一覧の先頭に足し、漏れた鍵を一覧から外す。漏れた鍵は確かめにも残さない（漏れた鍵を持つ人は、確かめの通る印を作れるため）
  3. 全体の止める合図を `run` に戻す。漏れた鍵で署名した印が残る開いた Issue と PR は、次の実行で `marker-invalid` で止まる（次の工程の表の順 5）
  4. 止まった Issue ごとに、印のあるコメントと GitHub の状態（PR の差分、作業ブランチ）を確かめ、決定 5 の「鍵が漏れたとき」の手順で戻す
- 秘密の置き場のほかの秘密（PAT かアプリの秘密鍵、deploy key）を替えるかは、漏れた経路を見て人が決める（本 ADR の範囲外）

### 決定 4：人が needs-human を外す前に知らせた無効な印は、外した後は数えない

- 進行 Bot は、`marker-invalid` で止めるとき、止めた理由の印（`note kind=stop reason=marker-invalid`）に、無効だった印のコメントの ID を欄として書く。欄は署名の対象に入る。
  人向けの本文にも、どのコメントかを書く。欄の名前と ID の種類は、要件の「[印と固定の見出しの一覧][text]」で決める
- 次をすべて満たす無効な印は、次の工程の表の順 5 で止める契機に数えない
  - 印の置き場の Issue で（置き場が PR なら、結びつく Issue で）、push 以上の人が `needs-human` を外した。外した人の権限は、TEXT-10（コラボレータの判定）のとおり、`UnlabeledEvent` の `actor` で確かめる。push 未満の人が外したときは、今のとおり `needs-human` を付け直す（`unauthorized-resume`）
  - 最後に外した時刻より前に書いた、有効な `marker-invalid` の止めた理由の印のどれかに、印のコメントの ID が挙がっている
  - 印のコメントの最後の編集が、最後に外した時刻より前（外した後に編集されたら、新しく無効になったものとして数える）
- 数えない印は、今のとおり無いものとして読み、中身（判定・件数・ハッシュなど）を判定に使わない。無いものとして読んだ結果、ほかの判定（`review` の印の `round` の欠け、受け入れの下書きの前の `agent-ready`、承認の確定など）に当たれば、当たった判定に従う
- 止めた理由の印に挙がっていない無効な印は、今のとおり 1 つでもあれば止める。外した後に新しく無効になった印と、鍵を一覧から外して確かめられなくなった印も、まず止めて知らせ、人が `needs-human` を外した後に、数えない対象になる
- `review` の印の `round` の欠けは、今のとおり止める。欠けは印のコメントが無いことなので、数えない対象にしない

### 決定 5：止まった状態から戻す手順に、無効な印からの戻し方を足す

「[止まった状態から戻す手順][flow]」に、次を足す。`needs-human` は、どの場合も最後に外す（外すまで、進行 Bot は Issue に触らない）。

- `marker-invalid`（印が無効）：止めた理由のコメントに挙がった印のコメントを確かめる（誰がいつ編集したか、鍵を替えたか）。印のコメントは、直さず、消さない。
  続けてよければ、Status を戻し（PR が無ければ `Todo`、あれば `In Review`）、`needs-human` を外す。進行 Bot は、挙がった印を数えず、無いものとして読む
- 途中のラウンドの `review` の印が無効なときと、`review` の印が消されて `round` が欠けるときは、PR を続けると `round` の欠けでまた止まる。PR を閉じ、作業ブランチを消し、Status を `Todo` に戻してから、`needs-human` を外す。
  進行 Bot は、閉じた PR を結びつきから外し、計画からやり直す（基本設計の「[状態遷移と判定][design-flow]」の「戻した Issue のやり直し」）

  > **［2026-10-23 追記］** 閉じた PR を結びつきから外すのは、[ADR-20261022-005][adr-unlink] の決定 1 の例外による。人が戻す手順の中で閉じた PR は、最後に `needs-human` を外すより前に閉じたので、人が戻した時刻より前に閉じた PR に当たる。人が戻した時刻より後に閉じた PR では、今のとおり `pr-closed` で止める。どの場合も `needs-human` を最後に外すことは変わらない。

- 鍵が漏れたとき（決定 3）：漏れた鍵の印は、誰が作ったかが分からないので、続けない。PR があれば閉じて作業ブランチを消し、`agent-ready` を外し、Status を `Todo` に戻してから、`needs-human` を外す。
  進行 Bot は、受け入れからやり直し、新しい下書きを書く。人は、新しい下書きを読んでから `agent-ready` を付ける
- 人は進行 Bot のコメントを編集しないこと（「止まった状態から戻す手順」の決まり）は据え置く

### 影響（Consequences）

- 良い点: 鍵を、進行中の Issue と着手の前の Issue があっても替えられ、開いた Issue と PR が止まらない
- 良い点: `marker-invalid` で止めた Issue を、人が確かめて `needs-human` を外すだけで戻せる。印のコメントを消す抜け道が要らない
- 良い点: 鍵が漏れたとき、漏れた鍵の印を読まずに止まる。人に知らせていない無効な印でも、今のとおり止まる
- 悪い点: 鍵を替える間、印を作れる鍵が 2 つ以上になる。前の鍵を外し忘れると、広いまま残る（点検の warn で知らせる）
- 悪い点: 承認を待つ Issue が長く開いていると、前の鍵を外せるまでが長くなる。急ぐときは前の鍵を外し、止まった Issue を決定 5 の手順で戻す。数えない印を無いものとして読むので、受け入れか計画からやり直すことがある
- 悪い点: 止めた理由の印の欄が増え、要件の「印と固定の見出しの一覧」と、署名と読み取りの処理を直す
- 悪い点: 途中のラウンドの `review` の印が無効なときは、PR を閉じて計画からやり直すので、利用枠を使い直す
- 悪い点: 鍵が漏れたときは、印のある開いた Issue をすべて人が確かめ、受け入れからやり直す
- 中立: 閉じた Issue を人が開き直すと、一覧から外した鍵の印で `marker-invalid` で止まる。戻し方は決定 5 と同じ

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 一覧の先頭の鍵で書き、一覧のどれかの鍵で確かめること。一覧に無い鍵の印は、署名の条件を満たさないこと。一覧が空なら点検が fail になること
  - 先頭でない鍵でだけ確かめられた印が残る Issue と PR を warn に出し、残りが無くなったら前の鍵を外してよいことを warn に出すこと
  - `marker-invalid` の止めた理由の印に、無効だった印のコメントの ID が入り、署名の対象に入ること
  - 数えない条件の組（push 以上の人が外したか、外す前の止めた理由の印に挙がっているか、外した後に編集されていないか）ごとに、止めるか数えないかが決まること
  - 数えない印を無いものとして読み、`review` の印の `round` の欠けでは今のとおり止めること
- 結合テスト（偽の `gh`）で、次を確かめる
  - 鍵を替えた後の最初の実行で、前の鍵の印のある着手の前の Issue と作業中の PR が止まらず、新しい印を新しい鍵で書くこと
  - 前の鍵を一覧から外すと、前の鍵の印が残る Issue が `marker-invalid` で止まり、push 以上の人が `needs-human` を外すと続くこと
  - 進行 Bot のコメントを編集した Issue が止まり、push 以上の人が外すと続き、外した後にもう一度編集すると、また止まること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：確かめる鍵を一覧にし、先頭の鍵で書く

- 良い点: 進行中の Issue と着手の前の Issue があっても替えられ、止まらない
- 良い点: 印のコメントの投稿の時刻と順が変わらないので、時刻で決める規則を変えずに使える
- 良い点: 印を書いたと認めるアカウントの一覧（[ADR-20261020-001][adr-bots]）と同じ形で、替える手順をそろえられる
- 悪い点: 鍵を替える間、印を作れる鍵が 2 つ以上になる。前の鍵を外し忘れると、広いまま残る
- 悪い点: 承認を待つ Issue が長く開いていると、前の鍵を外せるまでが長い

### 案 1-B：替える前に、印のある開いた Issue と PR を閉じる

- 良い点: ADR が要らず、鍵は 1 つのまま
- 悪い点: 替えるたびに、着手の前の Issue を含め、印のある開いた Issue をすべて閉じる。受け入れから作り直し、経緯が 2 つの Issue に分かれる
- 悪い点: 編集で止まった Issue は戻らない（問い 2 が残る）

### 案 1-C：新しい鍵で署名し直した印を投稿し直す

- 良い点: 替えた後は、鍵が 1 つに戻る
- 悪い点: 署名し直すには、前の鍵で確かめる間が要り、案 1-A の一覧と同じ仕組みが要る
- 悪い点: 投稿し直した印は投稿の時刻が変わるので、時刻で決める規則（`agent-ready` と `intake-final` の前後、`needs-human` を外した時刻と計画の印の前後）が変わる。`review` の印の並びも変わる
- 悪い点: 開いた Issue と PR のコメントが、替えるたびに増える

### 案 2-A：外す前に止めた理由の印で挙げた印を、外した後は数えない

- 良い点: 人が読んだ止めた理由に挙がった印だけを数えないので、人に知らせていない無効な印では止まる
- 良い点: 挙げた印のコメントの ID は署名の対象に入るので、止めた理由の印を別の Issue に写したり直したりしても、数えない印を増やせない
- 悪い点: 止めた理由の印の欄が増え、要件の「印と固定の見出しの一覧」と署名の処理を直す

### 案 2-B：印のコメントが外した時刻より前に変わったなら数えない

- 良い点: 止めた理由の印に欄を足さずに済む
- 悪い点: 鍵を一覧から外した時刻は GitHub に無いので、鍵を外した後に確かめられなくなった印も、投稿が `needs-human` を外す前なら、知らせずに数えない。止める側の印が、黙って無いものになる（fail-open）

### 案 2-C：戻し方を決めない

- 良い点: 仕組みが増えない
- 悪い点: 編集で止まった Issue は、印のコメントを消すか作り直すしかない。`review` の印を消すと、`round` の欠けでまた止まる
- 悪い点: 人が進行 Bot のコメントを消す運用になり、消したのか書いていないのかを GitHub から見分けられない（IMPL-18 で `round` の欠けを止める理由と同じ）
