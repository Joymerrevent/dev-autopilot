# 人が呼ぶ intake の Skill は、check と同じく依頼のファイルで進行 Bot のジョブに受付 AI を起こさせ、人が呼ぶ Skill は依頼のファイルを sandbox の外で書く許可を人に求める

## 背景と課題（Context and Problem Statement）

- STRUCT-6 は、business-os の `/verify-issue`（人が手で深く確かめたいときに呼ぶ Skill）が、最初に検疫のモジュール（TEXT-11）を呼び、最後に `dev-autopilot:brief:triager`（受付 AI）で下書きを作るとし、呼び方を基本設計に任せた
- 基本設計の「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」は、引数「下書き」で呼ばれた intake の Skill が、人の Claude Code の Bash の道具から写しの `src/` の受け入れのモジュールを Node で動かし、実行の lock を取って、進行 Bot の受け入れと同じ起動の形・置き場・止める手順で受付 AI のセッションを 1 つ起こすとする。
  記録は `sessions.jsonl` に起こした元の欄（`source`）を `intake-skill` にして書き、費用は 1 日の累計に数え、Issue の累計と 1 回の実行の累計には数えない
- 基本設計の 4 回目の再レビュー（2026-10-22）は、intake の Skill の形に次の 7 件の指摘を挙げた
  - M-13：起動の前の確かめ（順 1〜9）のどれを掛けるかが決まっていない。順 1 と、動いている間の全体の止める合図の読み取りには進行 Bot の GitHub の認証が要り、秘密を読まない人のセッション（[ADR-20261015-001][adr-read] の決定 2）では、書いてあるとおりに掛けられない。返す下書きを検疫と漏えいの検査に通さない。止められなかったときの扱いが無い
  - M-14：受付 AI の出力契約と `stream-json` を `outputs/` と `streams/` に残すかと、受け入れ工程（段階 4）の数え上げに人の確かめの判定が混ざるかが決まっていない
  - M-16：受付 AI の費用を 1 Issue の累計から外す例外が、IMPL-14 と [ADR-20261015-006][adr-flow] の決定 4 の (c) に無いまま、設計だけで決まっている
  - M-10：前の実行が残したセッションの費用を入れる日と実行が、指示語のために決まらない。今の実行と読めば、intake の Skill のセッションが 1 回の実行の累計に入り、記録の節の「1 日の累計にだけ入れる」と食い違う
  - M-2：進行 Bot の実行でないもの（intake の Skill と `setup`）が lock を持つ間に人が `check` を呼ぶと、点検の依頼のファイルが残り、次の定期の実行が点検だけで終わって 1 回分の作業をしない
  - M-15：人の Claude Code の sandbox の中から sandbox を掛けた `claude -p` を起こせるか、記録の置き場に書けるか、Bash の道具の時間の上限と受付 AI の 45 分が合うかを確かめていない
  - M-18：人が呼ぶ Skill の一覧（基本設計の「導入と点検」と「テスト」）に intake の Skill が無く、intake の Skill の振る舞いを確かめるテストが無い
- [ADR-20261015-001][adr-read] の決定 3 は、人の Claude Code のセッションは秘密を扱わず、進行役の親にもならず、進行役は定期の実行と同じ環境で動くとする。[ADR-20261017-004][adr-human] の決定 2 は、`check` と `/dev-autopilot` に進行 Bot のジョブを起こさせる。
  今の intake の Skill の形は、人のセッションが、AI のセッションを起こす進行役を受け持つ
- 2026-10-22 に、sandbox を有効にした Claude Code の Bash の道具から、作業フォルダの外（ホームの下と、`/private/tmp/` の下の作業フォルダの外）にファイルを書けるかを試した。どちらも `Operation not permitted` で書けなかった（[FACT-71][facts]）。
  今の intake の Skill が書く lock・`sessions.jsonl`・セッションのフォルダ・短い一時フォルダの根・安全設定は、どれも作業フォルダ（当てる先のリポの作業コピー）の外にある。`check` と `/dev-autopilot` が記録の置き場に置く依頼のファイルも同じ
- sandbox の中の Bash の道具から `launchctl kickstart` でユーザーのジョブを起こせるかは、まだ確かめていない（UNDECIDED-75。試験用のジョブの登録が要るので、人が試す）

課題：人が呼ぶ intake の Skill の「下書き」で、受付 AI のセッションをどのプロセスが起こすか。起動の前の確かめ・止める合図・止める手順・返す下書きの検査・記録・費用の累計・lock を、どう扱うか。人が呼ぶ Skill が記録の置き場に依頼のファイルを書けないとき、どうするか。

## 判断の決め手（Decision Drivers）

- 承認済みの ADR の決定（秘密は進行役だけが読む、人のセッションは進行役の親にならない、全体の止める合図を起動の前と動いている間に読む、費用を Issue の累計に数える）を、例外を作らずに満たすこと
- 起動の前の確かめ・止める合図・止める手順・記録・費用を、進行 Bot の受け入れと 1 組で使い、intake の Skill のためだけの「掛ける・掛けない」の表を作らないこと
- 外の人の文から AI が作った文を、検疫と漏えいの検査を通さずに、人の Claude Code の文脈に入れないこと（SAFE-6、TEXT-12 の「下書きも検疫に通す」）
- lock の持ち主を少なくし、人が待つのをやめた依頼で、定期の実行が作業を飛ばさないこと（M-2）
- 実機で確かめた事実（FACT-71）の上に置き、確かめていない前提（sandbox の入れ子、Bash の道具の時間の上限）に頼らないこと
- 人が深く確かめる場面で、次の定期の実行を待たずに下書きを受け取れること（STRUCT-6）

## 検討した選択肢（Considered Options）

- 案 B1：`check` と同じく、依頼のファイルで進行 Bot のジョブに受付 AI を起こさせる
- 案 B2：今の形（人のセッションの intake の Skill が受付 AI を起こす）を保ち、掛ける確かめを表で決める
- 案 B3：案 B2 と同じ形で、全体の止める合図を人の `gh` のログインで読む
- 案 B4：`/verify-issue` では下書きを作らず、進行 Bot の受け入れが Issue に書いた下書きを読む

## 決定（Decision Outcome）

採用した選択肢:「案 B1」。
理由: [ADR-20261015-001][adr-read] の決定 2・3、[ADR-20261017-004][adr-human] の決定 2、[ADR-20261017-007][adr-stop] の決定 2、[ADR-20261015-006][adr-flow] の決定 4 の (c) を、例外を作らずに満たす。
起動の前の確かめ・止める合図・止める手順・記録・費用を進行 Bot の受け入れと 1 組のまま使え、lock の持ち主も進行 Bot の実行と `setup` に戻る。人のセッションが作業フォルダの外に書くのは依頼のファイルだけになり、sandbox の入れ子と Bash の道具の時間の上限に頼らない。
案 B2 と案 B3 は、止める合図か費用で要件か ADR の例外を作り、FACT-71 で前提が崩れる。案 B4 は STRUCT-6 を改め、下書きが次の実行まで出ない。

### 決定 1：intake の Skill の「下書き」は、依頼のファイルを置いて定期の実行と同じジョブを起こし、受付 AI のセッションを自分で起こさない

- `/verify-issue` が引数「下書き」で呼んだ intake の Skill は、記録の置き場に受け入れの依頼のファイル（Issue の番号、依頼の ID、置いた時刻。ファイルの名前と形は反映で決める。例：`intake-request.json`）を置き、定期の実行と同じジョブを起こす（macOS は `launchctl kickstart`（`-k` なし）。Linux は登録した仕組みで同じジョブを起こす操作）。
  `check` の点検の依頼と、`/dev-autopilot` の手動の 1 回実行と同じ形にする（[ADR-20261017-004][adr-human] の決定 2）
- intake の Skill は、実行の lock を取らず、`claude` を起こさず、秘密を読まず、手元の記録（`sessions.jsonl` など）に書かない。受付 AI のセッションは、進行 Bot が起こす（決定 2）
- 依頼を置く前に lock を見て、進行 Bot の実行か `setup` の最中なら、依頼を置かずに、最中であることを示して止まる（`/dev-autopilot` の手動の 1 回実行と同じ）。
  置ける受け入れの依頼は 1 つにする。待つ時間（下の箇条）の内の受け入れの依頼のファイルがすでにあれば、置かずに、ほかの依頼を待っていることを示して止まる
- 依頼のファイルを置けなかったときは、ジョブを起こさずに、理由を示して止まる。依頼の無いまま起こしたジョブは、定期の実行として作業に入るため
- intake の Skill は、結果のファイル（名前は反映で決める。例：`intake-result-<依頼の ID>.json`）を、受け入れの依頼を待つ時間まで、Bash の道具の 1 回の時間の上限に収まる長さに分けて繰り返し見る。
  待つ時間は設定の項目にし、名前と初期値は反映で決める。受付 AI のセッションの時間の上限（`limits.session.minutes`）に、実行の最初の点検にかかる時間を足した長さより長くする。
  待つ時間を過ぎたら、`check` と同じく、実行中か（lock を見る）、ジョブが起きなかったか（定期の実行の登録と `launchd.err.log`）を示して終わる
- 結果を受け取ったら、下書き（決定 3 の検査を通った文の欄）と受付 AI のセッションの費用か、受付 AI を起こさなかった理由を示す。
  結果のファイルの消し方は、点検の結果のファイル（`check-result-<依頼の ID>.json`）と同じにする（人の Skill が示した後に消し、残ったものは 7 日を過ぎたら進行 Bot が消す）
- 引数「検疫」の処理（写しの `src/` の検疫のモジュールを Node で動かす。AI のセッションも秘密も使わない）と、マシンの設定が無ければ何もせずに止まること（STRUCT-3）は据え置く

### 決定 2：進行 Bot は、受け入れの依頼で起こされた実行で、受付 AI のセッションをほかのセッションと同じ確かめと止め方で 1 つ起こし、GitHub に書かず、Issue の工程に進まない

- 進行 Bot は、lock を取った後に受け入れの依頼のファイルを読み、起こされ方を「受け入れの依頼」とする（今の定期・手動・点検の依頼に足す）。
  ほかの依頼のファイル（点検の依頼、手動の 1 回実行の依頼）と重なったら、受け入れの依頼は、受付 AI を起こさずに消し、見送った理由を結果のファイルに書く（点検の依頼と重なった手動の依頼を見送る今の形と同じ）
- 受け入れの依頼の実行は、1 回の実行の流れの順 1〜5（マシンの設定、lock と前の実行が残したセッション、全体の止める合図、base ブランチの先端のリポの設定、点検）を、ほかの実行と同じに行う。
  合図が `run` でない、リポの設定を読めない、点検に fail がある、のどれかなら、受付 AI を起こさず、理由を結果のファイルに書く
- 進行 Bot は、Issue の題名・本文・コメントを自分の GitHub の認証で読み、進行 Bot の受け入れ（次の工程の順 9）と同じく検疫（TEXT-11）に通す。見つかれば、受付 AI を起こさず、見つかった種類と場所（見つかった文の中身は写さない）を結果のファイルに書く
- 受付 AI のセッションは、進行 Bot の受け入れと同じ起動の形・環境変数・セッションごとの安全設定・短い一時フォルダで起こす。モデルは、進行 Bot の受け入れと同じく `models.intake`（拒否の記録があれば `models.intakeAfterRefusal`。IMPL-29）にする。
  セッションの名前は `verify-intake-issue-<Issue の番号>` のままにし、セッションが終わったら（途中で止めたときも、残ったコマンドが止まったと確かめた後に）セッションのフォルダを消す
- 起動の前の確かめ（順 1〜9）と、記録の目印のファイルを作った日（`setup` をした日）は起こさない決まりを、ほかのセッションと同じに掛ける。
  セッションが動いている間も全体の止める合図を `run.stopSignalPollSeconds` ごとに読み、`run` でなくなれば、時間の上限と同じ止める手順で止める（[ADR-20261017-007][adr-stop] の決定 2）
- 受け入れの依頼の実行は、GitHub に何も書かない（印、コメント、ラベル、Status、Agent 欄）。`run.dryRun` の値に関わらない
- ほかのセッションなら Issue に `needs-human` を付ける確かめに外れたとき（起動の前の確かめの順 4 の Issue の累計の上限（`usage-limit`）、記録を失った（`records-missing`）、安全設定のファイルの書き換え（`settings-tampered`）など）は、受付 AI を起こさず（起こした後なら下書きを返さず）、理由を結果のファイルと実行の記録に書く。
  Issue に `needs-human` を付けるのは、進行 Bot の実行が Issue の工程を進めるときに、同じ確かめで行う
- 止めた後に残ったコマンドが止まったと確かめられないとき（`session-not-stopped`）は、Issue に書かず、点検のマシンの組を fail にし、残ったプロセスの PID とフォルダを結果のファイルと実行の記録に書く。
  止められなかったセッションは終わりの行を書かず、次の実行が前の実行が残したセッションとして探し直す。人が残りを止めるまで、ほかの Issue の作業も止まる（止める側に倒す）
- 受付 AI の後は、1 回の実行の流れの順 10（記録と `status.json` を書き、lock を外す）を行い、Issue の工程（順 6〜9）には進まない

### 決定 3：返す下書きは、投稿の前と同じく検疫と漏えいの検査に通す

- 受付 AI が返した文の欄（下書きの 4 つの欄、`planReason`、`policyReason`）は、進行 Bot の受け入れが投稿の前に掛ける検疫と漏えいの検査（TEXT-12 の「下書きも検疫に通す」、[ADR-20261016-002][adr-draft] の決定 1）に同じく通してから、結果のファイルに書く
- 見つかれば、文の欄を結果のファイルに書かず、見つかった種類と場所だけを書く
- 人の Claude Code の文脈に入る AI の文は、投稿と同じ検査を通った下書きだけにする。`/verify-issue` は、検疫を通った後に、人のセッションが外の Issue を深く確かめる Skill（STRUCT-6）なので、投稿と同じ検査を通った下書きを返す。
  `/dev-autopilot` が下書きの文を出さない決まり（書かずに試す間の `dry-run-drafts.md`。SAFE-6）は据え置く

### 決定 4：記録と費用はほかの AI のセッションと同じに扱い、実行の失敗の続いた回数と段階の出口の数え上げからは除く

- `sessions.jsonl` の行、`outputs/` の出力契約、`streams/` の `stream-json` を、ほかのセッションと同じに残す。`runs.jsonl` には、起こされ方を「受け入れの依頼」とした実行の行を書く（M-14）
- 人の Skill は手元の記録に書かないので、`sessions.jsonl` の起こした元の欄（`source`）で人の Skill の行を分ける形（`intake-skill`）は取り下げる
- 費用は、1 回の実行・1 日・1 Issue の累計のすべてに数え、起動の前の確かめの順 2〜4 も、ほかのセッションと同じに掛ける。IMPL-14 と [ADR-20261015-006][adr-flow] の決定 4 の (c) に、例外を作らない（M-16）。
  基本設計が先に決めた、Issue の累計と 1 回の実行の累計から外す形は取り下げ、前の実行が残したセッションの費用の文の「人の受け入れのセッションは入らない」も消す（M-10）
- 受付 AI の拒否の記録（[ADR-20261015-006][adr-flow] の決定 4 の (b)）は、ほかの受付 AI のセッションと同じに残し、次の受付 AI のモデルに使う
- 同じ Issue で続いた実行の失敗の回数（[ADR-20261015-006][adr-flow] の決定 4 の (a)）には数えない。受け入れの依頼の実行のセッションが失敗しても回数に足さず、成功しても 0 に戻さない。失敗の後に間を空ける決まり（`limits.retry.intervalRuns`）も、受け入れの依頼の実行には掛けない。
  受け入れの依頼の実行は Issue の工程を進めず、次回へ持ち越す作業が無い。失敗は結果のファイルに書いて人に示し、人が呼び直す。
  数えると、`limits.retry.count` 回目の失敗で付ける `needs-human`（`retry-limit`）を、GitHub に書かない実行で付けることになり、成功で 0 に戻すと、人の確かめの成功が、進行 Bot の工程の失敗の数を消すため
- 段階の出口の数え上げ（基本設計の「[状態遷移と判定][design-flow]」の「段階の出口の数え方」）は、受け入れの依頼の実行と、受け入れの依頼の実行のセッションを除く。
  除くのは、`outputs/` の受付 AI を数える行（受け入れ工程（段階 4）の方針に係る要望の判定と `agent-ready` の比べ、計画・実装工程（段階 5）の `plan=` の判定への異議など）と、`runs.jsonl` を数える行。人の確かめの助けとして起こしたセッションで、Issue に書いた下書きと結びつかないため

### 決定 5：lock を持つのは進行 Bot の実行と setup だけにし、人が待つのをやめた後に残った依頼のファイルで作業を飛ばさない

- 実行の lock を取るのは、進行 Bot の実行と `setup`（プログラムの写しを作り直すときと、引数 `uninstall` のとき）だけにする。intake の Skill は lock を取らない（決定 1）。lock の中身で持ち主の種類を見分けなくて済む
- 進行 Bot は、lock を取った後に見つけた依頼のファイルのうち、置いた時刻から人の Skill が待つ時間を過ぎたもの（人の Skill が待つのをやめた後に残ったもの）を、次のとおりに扱う。実行の起こされ方は定期とし、受け入れ工程（段階 4）の出口の実行の回数に数える
  - 受け入れの依頼（待つ時間は決定 1 の項目）：受付 AI を起こさずに消し、消したことを実行の記録に残す。人は待つのをやめていて、結果を読まないため
  - 点検の依頼（待つ時間は `run.checkWaitMinutes`）：点検の結果を書き、依頼のファイルを消してから、定期の実行として作業を続ける。今の「点検の依頼があれば点検だけを行い、作業に入らない」は、待つ時間の内の依頼に限る（M-2）
- `setup` が lock を持つ間に人が `check` を呼んだときも、残った点検の依頼は上の扱いになり、次の定期の実行は 1 回分の作業を失わない

### 決定 6：人が呼ぶ Skill は、記録の置き場に書くコマンドを sandbox の外で動かす許可を人に求める

- 人が呼ぶ Skill のうち、記録の置き場に依頼のファイルを置くもの（`check`、`/dev-autopilot` の手動の 1 回実行、intake の Skill の「下書き」）は、依頼のファイルを置くコマンドと、示した後に結果のファイルを消すコマンド（結果のファイルを読む `check` と intake の Skill）を、sandbox の外で動かす許可を人に求めてから動かす。
  sandbox を有効にした Claude Code の Bash の道具からは、作業フォルダの外に書けず（[FACT-71][facts]）、記録の置き場は作業フォルダの外にあるため
- 人の設定が sandbox の外のコマンドを許していない（Claude Code の sandbox の設定 `allowUnsandboxedCommands` が `false`）か、人が許可しなかったときは、書かずに、記録の置き場に書けないので依頼を出せないことを理由として示して止まる。ジョブも起こさない（決定 1）
- sandbox の外で動かすのは、記録の置き場に書くコマンド（と、下の箇条で sandbox の中から使えないと分かったコマンド）だけにする。検疫のモジュールを動かすこと、結果を待つことは、sandbox の中で行う。
  許可を求めるコマンドは、書く先のパスと書く中身が、人の読むコマンドの文に見える形にする。人が、記録の置き場に書くだけのコマンドかを読んで許せるようにするため
- sandbox の中から、ジョブを起こすコマンド（`launchctl kickstart`）を使えるかと、lock と結果のファイルを読めるかは、確かめていない（ジョブを起こすほうは UNDECIDED-75）。使えないと分かったコマンドにも、同じ扱い（sandbox の外で動かす許可を人に求め、許されなければ理由を示して止まる）を掛ける

### 影響（Consequences）

- 良い点: [ADR-20261015-001][adr-read] の決定 2・3、[ADR-20261017-004][adr-human] の決定 2、[ADR-20261017-007][adr-stop] の決定 2、[ADR-20261015-006][adr-flow] の決定 4 の (c) を、例外なく満たす。要件の「運用の規則」の合図の読み方にも、例外が要らない
- 良い点: 起動の前の確かめ・止める合図・止める手順・記録・費用を、進行 Bot の受け入れと 1 組で使い、intake の Skill のための「掛ける・掛けない」の表が要らない。
  人のセッションの sandbox の中から sandbox を掛け直す形（M-15 の (1)）と、Bash の道具の時間の上限で、lock と `claude` を残したまま Node が止められる形（M-15 の (3)）が無くなる
- 良い点: `models.intake` と `safety.*` を、進行 Bot が実行の最初に fetch した base ブランチの先端のリポの設定から読む。人のセッションが fetch しない理由（deploy key を読まない）と、進行 Bot の clone が無いときの扱いが要らなくなる
- 良い点: lock の持ち主が進行 Bot の実行と `setup` に戻り、人が待つのをやめた点検の依頼で、定期の実行が作業を飛ばさない（M-2）
- 良い点: 人の Claude Code の文脈に返す下書きが、進行 Bot が GitHub に投稿するときと同じ検査を通った文になる
- 良い点: 人のセッションが作業フォルダの外に書くのは、依頼のファイルを置くことと結果のファイルを消すことだけになる。FACT-71 の制約に当たるコマンドが少なく、人が許可を求められたときに中身を読みやすい
- 悪い点: 下書きが出るまで、ジョブが起き、点検を回し、受付 AI が終わるまで待つ。進行 Bot の実行と `setup` の最中は呼べない
- 悪い点: 受付 AI の費用が Issue の累計に入る。人が同じ Issue を何度も確かめると、Issue を処理対象にした後に使える残り（`limits.issueCostUsd`）が減る。1 日の累計にも入るので、人の確かめが多い日は、進行 Bot の実行が使える分が減る（今の設計と同じ）
- 悪い点: sandbox を有効にした人の Claude Code では、1 回の呼び出しで、sandbox の外のコマンドの許可を最大 2 回求める（依頼のファイルを置く、結果のファイルを消す）。許したコマンドは、人の Claude Code の sandbox の守りの外で動く。
  人の設定が sandbox の外を許していなければ、`check`・`/dev-autopilot`・intake の Skill は依頼を出せない
- 悪い点: sandbox の外で動かす許可を求めて依頼のファイルを書けることと、`launchctl kickstart` を sandbox の中から使えるか（UNDECIDED-75）は、実機で確かめていない。`check` と `/dev-autopilot` と同じ前提になる
- 悪い点: 止めた後に残ったコマンドが止まったと確かめられないときは、Issue に書けないので、点検のマシンの組を fail にする。人が残りを止めるまで、ほかの Issue の作業も止まる
- 悪い点: [ADR-20261015-006][adr-flow] の決定 4 の (a) に、比べるためのレビューに続いて 2 つ目の除外が増える
- 悪い点: 承認の後に、要件・基本設計の 01〜05・図の反映の PR が要る
- 中立: 返す下書きは、外の人の文から AI が作った文で、人の Claude Code の文脈に入る。今の設計と同じで、検疫と漏えいの検査を足した
- 中立: 受付 AI の拒否の記録は、人が呼んだ回の分も、進行 Bot の受け入れのモデル（次の回は `models.intakeAfterRefusal`）に効く
- 中立: 依頼のファイルの扱いが 3 つになる。受け入れの依頼は、ほかの依頼と重なったら見送る
- 中立: 専用マシンに移したときの形（UNDECIDED-71）は変わらない。依頼のファイルを置けるのは、進行 Bot を動かすマシンだけ

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 起こされ方の決め方：依頼のファイルの組み合わせ（受け入れの依頼だけ、点検の依頼と重なる、手動の依頼と重なる）と、置いた時刻と待つ時間の比べ（待つ時間の内か、過ぎたか）
  - 受け入れの依頼の実行のセッションの費用を、1 回の実行・1 日・1 Issue の累計に数え、続いた実行の失敗の回数に足さず、0 にも戻さないこと
  - 段階の出口の数え上げで、受け入れの依頼の実行と、受け入れの依頼の実行のセッションを除くこと
- 結合テスト（偽の `gh`・`claude`・`launchctl`）で、次を確かめる
  - intake の Skill の「下書き」が、依頼のファイルを置いてジョブを `-k` なしで起こし、lock を取らず、`claude` を起こさず、手元の記録に書かず、秘密の置き場を読まないこと（`node --permission` で起こし、`ERR_ACCESS_DENIED` が出ないこと）
  - 受け入れの依頼の実行が、受付 AI のセッションを 1 つ、進行 Bot の受け入れと同じ引数と安全設定で起こし、GitHub に何も書かず、Issue の工程に進まないこと
  - 全体の止める合図が `stop`、点検に fail がある、Issue の文が検疫に当たる、Issue の累計の上限を超える、のどの場合も、受付 AI を起こさず、理由を結果のファイルに書き、`needs-human` を付けないこと
  - 下書きの文の欄が漏えいの検査に当たると、文を結果のファイルに書かず、種類と場所だけを書くこと
  - lock があるときと、待つ時間の内の受け入れの依頼があるときに、intake の Skill が依頼を置かないこと
  - 待つ時間を過ぎた受け入れの依頼を、次の実行が受付 AI を起こさずに消し、定期の実行として作業に入ること。待つ時間を過ぎた点検の依頼で、点検の結果を書いた後に作業を続けること
  - 止めた後に残ったコマンドが止まったと確かめられないとき、Issue に書かず、点検のマシンの組を fail にすること
- 導入と点検の実装（段階 3）で、sandbox を有効にした人の Claude Code から、次を実機で試す
  - `check`・`/dev-autopilot`・intake の Skill が、sandbox の外で動かす許可を求めて依頼のファイルを置き、結果のファイルを消せること。`allowUnsandboxedCommands` が `false` の設定では、理由を示して止まり、ジョブを起こさないこと
  - sandbox の中から `launchctl kickstart` でジョブを起こせるか（UNDECIDED-75）と、lock と結果のファイルを読めるか。使えなければ、決定 6 の最後の箇条のとおりに直す
- 基本設計のレビューで、「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」、「[状態遷移と判定][design-flow]」の「1 回の実行の流れ」と「手元の記録」と「段階の出口の数え方」、「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」と「点検だけで動かす仕組み」、図 `03-human-intake` が、本 ADR の決定と同じことを書いていることを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 B1：依頼のファイルで進行 Bot のジョブに受付 AI を起こさせる

- 良い点: 承認済みの ADR の決定（秘密、進行役の親、止める合図、費用の (c)）を、例外を作らずに満たす
- 良い点: 起動の前の確かめ・止める合図・止める手順・記録・費用を、進行 Bot の受け入れと 1 組のまま使う。sandbox の入れ子と Bash の道具の時間の上限に頼らない
- 良い点: lock の持ち主が進行 Bot の実行と `setup` に戻る
- 良い点: 返す下書きが、投稿と同じ検査を通った文になる
- 中立: FACT-71 で、人のセッションは依頼のファイルを sandbox の中から書けない。`check` と `/dev-autopilot` と同じ制約で、sandbox の外で書く許可を人に求める（決定 6）
- 悪い点: 下書きが出るまでジョブと受付 AI を待つ。進行 Bot の実行と `setup` の最中は呼べない
- 悪い点: 受付 AI の費用が Issue の累計に入り、Issue を処理対象にした後の残りが減る
- 悪い点: [ADR-20261015-006][adr-flow] の決定 4 の (a) から、受け入れの依頼の実行のセッションを除く

### 案 B2：今の形を保ち、掛ける確かめを表で決める

基本設計の 4 回目の再レビュー（2026-10-22）の直しの計画の案。掛ける確かめは順 2・5・6・9、`setup` をした日の決まり、返す下書きの検疫と漏えいの検査。掛けないのは順 1（止める合図）・順 3・順 4・順 8。費用は 1 日の累計だけに数える。lock に持ち主の種類を書き、人の `check` は持ち主が進行 Bot の実行でなければ依頼を置かない。

- 良い点: ジョブを待たずに、人のセッションから受付 AI を起こせる
- 良い点: 受付 AI の費用が Issue の累計に入らず、Issue を処理対象にした後の残りが減らない
- 悪い点: 止める合図を読まずに AI のセッションを起こすので、要件の「運用の規則」と [ADR-20261017-007][adr-stop] の決定 2 に例外が要る。全体を `stop` にした後も、人の確かめで受付 AI が起きうる
- 悪い点: 費用を Issue の累計に数えないので、[ADR-20261015-006][adr-flow] の決定 4 の (c) を改める
- 悪い点: 人のセッションが、AI のセッションを起こす進行役を受け持ち、[ADR-20261015-001][adr-read] の決定 3（人のセッションは進行役の親にならない）と食い違う
- 悪い点: intake の Skill のための「掛ける・掛けない」の表と、lock の持ち主の種類の見分けが要る
- 悪い点: FACT-71 で前提が崩れる。受け入れのモジュールが書く lock・`sessions.jsonl`・セッションのフォルダ・短い一時フォルダの根・安全設定は作業フォルダの外にあり、sandbox を有効にした人の Claude Code の Bash の道具からは書けない。
  書くには、受付 AI を起こすモジュールの全体を sandbox の外で動かす許可を人に求めることになる。sandbox の中から sandbox を掛けた `claude -p` を起こせるか（M-15 の (1)）と、Bash の道具の時間の上限（M-15 の (3)）も確かめていない

### 案 B3：案 B2 と同じ形で、止める合図を人の `gh` のログインで読む

- 良い点: 人のセッションから受付 AI を起こしても、全体の止める合図を起動の前と動いている間に読める。「運用の規則」の合図の読み方に例外が要らない
- 悪い点: 人の `gh` の使い道を `setup` の GitHub の準備から広げるので、[ADR-20261017-004][adr-human] の決定 2 を改める。人の `gh` のログインが無いマシンでは動かない
- 悪い点: 案 B2 と同じく、[ADR-20261015-006][adr-flow] の決定 4 の (c) を改め、[ADR-20261015-001][adr-read] の決定 3 と食い違い、FACT-71 で前提が崩れる

### 案 B4：`/verify-issue` では下書きを作らず、進行 Bot の受け入れが Issue に書いた下書きを読む

- 良い点: 人の呼び出しで AI のセッションを起こさず、依頼のファイルも要らない。FACT-71 の制約に当たらず、費用も増えない
- 良い点: 人が読む下書きが、進行 Bot が Issue に書いた下書きと同じになる
- 悪い点: STRUCT-6 の「最後に `dev-autopilot:brief:triager` で下書きを作る」を改める
- 悪い点: 下書きは、次の定期の実行か手動の 1 回実行まで出ない。人が深く確かめる場面で、呼んだときに下書きを受け取れない
- 悪い点: 進行 Bot の受け入れの条件（Status が `Todo`、`needs-human` が無い、`limits.intakePerRun` の件数の内など）に当たらない Issue と、受け入れ工程（段階 4）より前（`/verify-issue` を拡張する導入と点検の実装（段階 3）を含む）は、下書きが出ない。
  書かずに試す間は、下書きが GitHub に無く、手元の記録の `dry-run-drafts.md` にだけある

- UNDECIDED-73・UNDECIDED-75 と FACT-71 は、同じ再レビューの直しの PR で、[決めていないこと][undecided]と[実機で確かめた事実][facts]に足す。
  M-18 の一覧のずれ（人が呼ぶ Skill の一覧に intake の Skill を足す）と、M-10 の日と実行の文（前の実行が残したセッションの費用を、終わりの行を書く日と今の実行の累計に入れる）は、同じ直しの PR で先に直す

- `setup` が作業フォルダの外に書くこと（プログラムの写し、置き場、マシンの設定、定期の実行の登録）も、FACT-71 の制約に当たりうる。本 ADR では決めない（`setup` は、作るものの一覧を出して人の承認を得てから作る。[ADR-20261017-004][adr-human] の決定 2）

- 要件と設計への反映（承認の後に、別の PR で行う）
  - 01-issue-flow.md：「運用の規則」の多重起動の項に、lock を取るのは進行 Bot の実行と `setup` だけで、intake の Skill は依頼のファイルを置いて同じジョブを起こすことを書く（決定 1、決定 5）
  - 02-implement-review-fix.md：IMPL-14 の表に、受け入れの依頼の実行のセッションの失敗は実行の失敗に数えず、結果のファイルに書いて人が呼び直すことを足す（決定 4）。費用の文は変えない
  - 07-structure.md：STRUCT-3 の intake の説明に、lock を取らず、依頼のファイルを置いて定期の実行と同じジョブを起こすことと、人が呼ぶ Skill は依頼のファイルを sandbox の外で書く許可を人に求めること（FACT-71）を書く。構成の `intake/SKILL.md` の行もそろえる
  - 09-undecided.md：UNDECIDED-73 を欠番にする（元の文を取り消し線で残す）。UNDECIDED-71 に、依頼のファイルを置けるのは進行 Bot を動かすマシンだけであることを書き添える
  - 基本設計の「[設定][design-settings]」：受け入れの依頼を待つ時間の項目を足す（決定 1）
  - 基本設計の「[AI のセッション][design-ai]」：「人の Skill から受け入れを呼ぶ形」の表と箇条を、決定 1〜4 と決定 6 で書き直す。セッションの名前の表の人の受け入れの行と、受け入れのセッションのフォルダを消す箇条をそろえる。
    前の実行が残したセッションの順 4 の「人の受け入れのセッションは入らない」を消す。起動の前の確かめの表の下に、受け入れの依頼の実行で `needs-human` に当たる確かめに外れたときの扱いを足し、実行の失敗の続いた回数の箇条に、受け入れの依頼の実行を除くことを足す
  - 基本設計の「[状態遷移と判定][design-flow]」：1 回の実行の流れの順 2（起こされ方に受け入れの依頼を足す）と、受け入れの依頼の実行が Issue の工程に進まないこと。
    手元の記録の `runs.jsonl` の起こされ方、`sessions.jsonl` の起こした元の欄（`source`）の取り下げ、記録の置き場のほかのファイル（受け入れの依頼と結果のファイルを足し、`run.lock` を書くものから intake の Skill を外す）、intake の Skill の実行 ID の箇条を消す。段階の出口の数え方で、受け入れの依頼の実行を除く
  - 基本設計の「[導入と点検][design-setup]」：見送った実行と、起動しなかった定期の実行（依頼のファイルが 3 つになること、重なったときの扱い、待つ時間を過ぎた依頼）、点検だけで動かす仕組み（待つ時間を過ぎた点検の依頼で作業を続けること、依頼のファイルを sandbox の外で書く許可）、状態の表示の手動の 1 回実行（同じ許可）、動かすマシンを替えるときに写さないファイルに受け入れの依頼と結果のファイルを足す
  - 基本設計の「[テスト][design-tests]」：確認方法の単体テストと結合テストを足す。結合テストの入口と `node --permission` で起こす処理に、intake の Skill の「下書き」を足す
