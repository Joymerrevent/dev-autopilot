# 検疫で見つかったら止め方でなく安全の軸に値を入れて maintain 以上の人の安全の確認だけで外し、AI が書いた文で見つかったら全体の停止の Issue で全体を止める

> **Amended by [ADR-20261027-002][adr-leak]（2026-10-27）**: 決定 1 の表に、漏えいの検査で見つかったときの行（`security` の印の `where` が `leak`、攻撃の疑い（AI の文）、全体は止めない）を足した。決定 3 の全体の停止は、AI が書いた文の検疫で見つかったとき（`where` が `text`）に限ると読む。ほかの決定は据え置く。

要件の UNDECIDED-80（検疫で攻撃の疑いが見つかったときの止め方と、全体の止め方。[決めていないこと][undecided]の「ADR で決めること」の「作業の単位の状態遷移」）を決める。
本 ADR は、[ADR-20261024-001][adr-model-states]（作業の単位の状態を主な流れと重ねる 3 本の軸で表す）と [ADR-20261024-004][adr-master]（検疫は AI に渡す前と GitHub に書く前に毎回行う）を前提にする。
[ADR-20261024-001][adr-model-states] で「中身を決める所」を UNDECIDED-80 とした安全の軸の値と線（Q1〜Q4）、印（`security`・`halt`）、`## 安全の確認` の使い方、表示のラベル（`security-suspected`）と、[ADR-20261024-004][adr-master] で回した検疫で見つかったときの扱いを、本 ADR で決める。

## 背景と課題（Context and Problem Statement）

- 今の形では、検疫（TEXT-9、TEXT-11）で見つかったら、ほかの止まり方と同じく `needs-human`（`quarantine`）にする。受け入れの検疫で見つかったら、検疫の結果と人への案内だけを投稿し、人が `## 作業指示` を一から書く（[ADR-20261015-003][adr-intake] の決定 2）
- `needs-human` は、人が外せば戻る。攻撃の疑いで止めたのか、ほかの理由で止めたのかが、表示で分かれない
- 全体を止めるのは、人が当てる先のリポの変数を `run` のほかの値にしたときだけ（[ADR-20261017-007][adr-stop]）。進行 Bot が攻撃の疑いを見つけても、見つけた作業のほかは動き続ける
- 2026-10-23〜24 の組み直し（[ADR-20261024-001][adr-model-states]）で、止め方・先の依頼と別に、3 本目の軸「安全」を主な流れに重ねた。検疫を AI に渡す前と書く前に毎回行い、範囲に Issue の文・人の見出し・PR の差分・AI が書いた文を入れた（[ADR-20261024-004][adr-master] の決定 7）

課題：検疫で見つかったときに、どう止め、誰が何をすれば外れるか。同じ手口がほかの作業に届いているかもしれないときに、全体をどう止めるか。攻撃されたことを、どう知らせるか。

## 判断の決め手（Decision Drivers）

- 攻撃されたことが、表示で分かる
- 人が確かめずに戻せない。外せる人を、ほかの操作より狭める
- 同じ手口がほかの作業に届いているかもしれないときは、全体を止める（壊れたときに安全側へ倒す）
- 誤って反応しやすい見つかり方で全体を止め続けない。止まり続けると、人が確かめずに外す癖がつく
- 進行 Bot に、リポの変数を書く権限を渡さない（[ADR-20261017-007][adr-stop] の決定 1）

## 検討した選択肢（Considered Options）

- 案 1-A：検疫で見つかったら、止め方（停止中）でなく、安全の軸に値を入れる
- 案 1-B：今のまま、停止中（`needs-human`）にする
- 案 2-A：AI が書いた文で見つかったら、進行 Bot が全体の停止の Issue を開いて全体を止める。AI が書いたコードの差分で見つかったら、見つかった作業だけ止める
- 案 2-B：どこで見つかっても、見つかった作業だけ止める
- 案 2-C：AI が書いた文で見つかったら、進行 Bot がリポの変数を `stop` にして全体を止める
- 案 3-A：安全の確認の後は、確かめた見つかりものを同じ作業の単位の中では通す
- 案 3-B：安全の確認は値を外すだけにし、同じ文が残っていれば次の検疫でまた止まる

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-B」。

理由: 攻撃の疑いが止め方と別の欄に出て、再開の見出しでは外れないので、人は確かめずに戻せない。AI が書いた文で見つかったときは、AI が操られた疑いがあり、同じ手口がほかの作業に届いているかもしれないので、全体を止める。
AI が書いたコードの差分は、コードの中の文字列やテストのデータで誤って反応しやすいので、見つかった作業だけ止め、誤った停止で全体が止まり続けないようにする。全体の停止を Issue で表すので、正本が GitHub に残り、進行 Bot にリポの変数を書く権限が要らない。
安全の確認は値を外すだけにし、見つかった文が残っていれば次の検疫でまた止まるので、見つかった文は人が直すまで AI に届かない。案 3-B は、起票のときにメンテナに尋ねて決めた（CC の推奨は案 3-A だった）。

### 決定 1：検疫で見つかったら、安全の軸に値を入れる

- 検疫で見つかったら、止め方を停止中にせず、安全の軸に値を入れる。主な流れは、検疫の前の状態のまま（入口なら起票済み、人の直しなら直し済み）。値がある間、AI は主な流れを進めない（[ADR-20261024-001][adr-model-states] の決定 3）

| 見つかった所 | `security` の印の `where` | 安全の軸の値 | 全体 |
| --- | --- | --- | --- |
| AI に渡す前の文（Issue の文、人の見出しのコメント） | `entry` | 攻撃の疑い（入口）（Q1） | 止めない |
| AI が書いた文（下書き、計画、PR の題名と本文、指摘、直しの返事など。GitHub に書く前） | `text` | 攻撃の疑い（AI の文）（Q2） | 止める（決定 3） |
| PR の差分（コード。人の push を含む。AI に渡す前） | `code` | 攻撃の疑い（AI の文）（Q2） | 止めない（見つかった作業だけ） |

- 見つかった文は AI に渡さず、AI が書いた文は GitHub に書かない
- 止め方の値とは別に持つので、引き取り中や再開の後も値は残る。安全の軸の値と止め方の値は同時に持ちうる（例：AI の作業の失敗が続いて停止中で、攻撃の疑いもある）
- 1 つの作業の単位に、攻撃の疑い（入口）と攻撃の疑い（AI の文）の両方があれば、表示は攻撃の疑い（AI の文）にする（[ADR-20261024-001][adr-model-states] の決定 6）
- 検疫が探すもの（見えない文字、指示の形の語、欄の区切りを模した文字列、当てる先のリポの GitHub の URL のほかの URL）は、今のまま（TEXT-9・TEXT-11、[ADR-20261022-001][adr-url]）。[ADR-20261022-001][adr-url] の「止めて `needs-human`」は、表の値を入れると読む

### 決定 2：値は、maintain 以上の人の `## 安全の確認` だけで外れ、見つかった文が残っていればまた止まる

- 安全の軸の値は、maintain 以上の人が `## 安全の確認` の見出しのコメントを書いたときだけ外れる。最新の `security` の印より後に、maintain 以上の人の `## 安全の確認` があれば、値は（なし）（Q3・Q4）。push 以上でも maintain 未満の人の `## 安全の確認` は、無いものとして読む
- `## 再開 <戻す先>` と、ラベルを外す操作では外れない。外すまでは、止め方を再開しても AI は進めない
- 人は、見つかった種類と場所（決定 4 のコメント）を見て文を確かめ、見つかった文を直してから `## 安全の確認` を書く。直し方は、Issue の文（題名・本文・コメント）を直すか消す、人の見出しのコメントを直す、コードを直して push する、戻す先を選んで作り直す（AI が書いた文で見つかったとき）のどれか
- `## 安全の確認` は値を外すだけで、見つかったものを確かめ済みにはしない。外した後も、AI に渡す前と書く前の検疫は毎回行い（[ADR-20261024-004][adr-master] の決定 7）、見つかった文が残っていれば、また見つかって値が入る。見つかった文は、人が直すまで AI に届かない
- `security` の印には、今のとおり見つかった種類と場所を書き（`where`、`finding`）、見つかった文そのものは写さない
- 入口の検疫で見つかった Issue は、人が Issue の文を直して確かめた後の検疫を通れば検疫済みに進み、受付 AI は直した Issue の文を読んで下書きを書く。今の「受付 AI を起動せず、人が `## 作業指示` を一から書く」形（[ADR-20261015-003][adr-intake] の決定 2）は無くなる

### 決定 3：AI が書いた文で見つかったら、全体の停止の Issue で全体を止める

- AI が書いた文（`where` が `text`）で見つかったら、見つかった作業の単位に攻撃の疑い（AI の文）を入れたうえで、進行 Bot が全体の停止の Issue を開き、`halt` の印（`issue` に見つけた作業の Issue の番号）を書く。開いている全体の停止の Issue がすでにあれば、新しく開かずに、開いている Issue に `halt` の印を足す
- 全体の停止の Issue が 1 つでもある間は、どの作業の単位でも AI のセッションを起こさない。進行 Bot は、実行の最初と、AI のセッションを起こす前に、全体の停止の Issue があるかを読む。全体の停止の Issue を開いた実行では、動いている AI のセッションを、全体の止める合図と同じ手順（プロセスグループごと）で止める
- AI を使わない進行 Bot の工程（検疫、表示の欄、片付けなど）は続ける。片付けは軸の値を問わず行う（UNDECIDED-81（片付けと先の依頼）の ADR で決める）
- 全体の停止は、maintain 以上の人が、全体の停止の Issue に、最新の `halt` の印より後に `## 安全の確認` を書き、Issue を閉じたときに解ける。確かめずに閉じたとき（`## 安全の確認` が無い）と、確かめても閉じていないときは、止めたままにする（止める側に倒す）
- 全体の停止を解いても、見つけた作業の単位の攻撃の疑い（AI の文）は残る。作業の単位の値は、決定 2 のとおり、作業の単位の Issue の `## 安全の確認` で外す
- AI が書いたコードの差分（`where` が `code`）で見つかったときは、全体を止めず、見つかった作業の単位だけを止める
- 人が全体を止めるリポの変数（[ADR-20261017-007][adr-stop] の決定 1・2）は据え置く。進行 Bot は、リポの変数が `run` で、全体の停止の Issue が無いときだけ、AI のセッションを起こす。進行 Bot にリポの変数を書く権限は与えない

### 決定 4：攻撃の疑いは、ラベル・コメント・表示の欄・GitHub の外への通知で知らせる

- 表示のラベル：進行 Bot が、安全の軸に値がある作業の単位の Issue に `security-suspected` を付け、値が外れたら外す。表示だけで、判定には読まない（印を正本にする）。`agent-` を付けないのは、人が付けるラベル（`agent-ready` など）と取り違えないため
- コメント：`security` の印を付けたコメントを、Issue に書く（PR が契機なら PR にも）。見つかった場所（題名・本文・何番目のコメントか、PR の差分ならファイルと行）と種類を書き、見つかった文そのものは写さない（見えない文字や指示の形の文を、進行 Bot の投稿として広めないため）。人がすること（文を確かめて直し、`## 安全の確認` を書く）も書く
- 表示の欄：Project の「安全」の欄に値を出す（[ADR-20261024-001][adr-model-states] の決定 5）
- GitHub の外への通知：攻撃の疑いと全体の停止を、GitHub の外にも知らせる。送る仕組みと鍵は、後で決める
- 全体の停止の Issue には、見つけた作業の Issue の番号と、人がすること（ほかの作業も確かめ、`## 安全の確認` を書いて閉じる）を書く

### 影響（Consequences）

- 良い点: 攻撃の疑いが、止め方と別の欄とラベルで分かる。再開の見出しでは外れないので、人は確かめずに戻せない
- 良い点: AI が操られた疑いがあるときは、ほかの作業にも AI を動かさない。全体の停止の正本が GitHub に残り、進行 Bot にリポの変数を書く権限が要らない
- 良い点: 見つかった文は、人が直すまで AI に届かない。人が確かめを誤っても、見つかった文が残っていればまた止まる
- 良い点: 入口の検疫で見つかった Issue も、人が文を直した後は受付 AI が下書きを書くので、人が作業指示を一から書かずに済む
- 悪い点: 外せる人が maintain 以上だけなので、maintain の人が少ないと、作業が止まっている時間が延びる
- 悪い点: AI が書いた文に誤って外の URL を書くと、全体が止まる（[ADR-20261022-001][adr-url] の決定 3 の指示で減らす）。誤った停止のたびに、maintain 以上の人が全体の停止の Issue と作業の Issue の 2 か所で確かめる
- 悪い点: 外の URL を含む正当な変更や、誤って反応した文でも、人が文を直すまで止まり続ける。コードの差分で見つかったときは、人がコードを直して push するか、引き取って人が進めるまで、AI のレビューに進めない

### 確認方法（Confirmation）

- 単体テストで、安全の軸の値の決め方（`security` の印と `## 安全の確認` の時刻、maintain 未満の人の確認を読まないこと、安全の確認の後も見つかった文が残っていれば次の検疫でまた値が入ること）を確かめる
- 単体テストで、全体の停止の決め方（`halt` の印、`## 安全の確認`、Issue が閉じたか）の 4 つの組み合わせを確かめる
- 結合テスト（偽の `gh` と偽の `claude`）で、AI が書いた文で見つかると、文を書かずに作業の単位に値が入り、全体の停止の Issue が開き、次の実行でどの作業の単位でも AI のセッションを起こさないことを確かめる。コードの差分で見つかったときは、ほかの作業の単位は進むことを確かめる
- 結合テストで、`security-suspected` のラベルが値に合わせて付け外しされ、コメントに見つかった文が写されていないことを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：検疫で見つかったら、安全の軸に値を入れる

- 良い点: 攻撃の疑いが表示で分かり、外し方を止め方と分けられる
- 悪い点: 軸が 1 つ増え、外す操作が止め方と別になる

### 案 1-B：今のまま、停止中にする

- 良い点: 外す操作が 1 つで済む
- 悪い点: ほかの理由の停止と見分けにくく、人が確かめずに再開できる

### 案 2-A：AI が書いた文で見つかったら全体の停止の Issue で全体を止め、コードの差分なら見つかった作業だけ止める

- 良い点: AI が操られた疑いがあるときに、ほかの作業を止められる
- 良い点: 誤って反応しやすいコードの差分では、全体を止めない
- 悪い点: AI が書いた文の誤った反応でも、全体が止まる

### 案 2-B：どこで見つかっても、見つかった作業だけ止める

- 良い点: 誤った反応で全体が止まらない
- 悪い点: 同じ手口がほかの作業に届いていても、ほかの作業の AI が動き続ける

### 案 2-C：進行 Bot がリポの変数を stop にして全体を止める

- 良い点: 人が止めるときと同じ手段で止まる
- 悪い点: 進行 Bot にリポの変数を書く権限を渡すことになる。権限が漏れると、止める合図を `run` に戻せる

### 案 3-A：確かめた見つかりものを、同じ作業の単位の中では通す

- 良い点: 誤った反応や正当な外の URL で止まり続けず、人の確かめが 1 回で済む
- 悪い点: 印にハッシュの欄が要る。確かめを誤ると、確かめた文が AI に届く

### 案 3-B：安全の確認は値を外すだけにする

- 良い点: 見つかった文は、直すまで AI に届かない
- 悪い点: 外の URL を含む正当な変更は、AI のレビューまで進めない。人が文を直さない限り止まり続ける

## 補足情報（More Information）

- 2026-10-23〜24 にメンテナと状態遷移を組み直したときに、安全の軸、外し方、AI が書いた文での全体の停止、コードの差分は見つかった作業だけ止めること、全体の停止の Issue、知らせ方を決めた。安全の確認の後の扱いは、起票のときにメンテナに尋ね、CC の推奨の案 3-A（確かめた見つかりものを通す）でなく、案 3-B（値を外すだけで、見つかった文が残っていればまた止まる）に決めた
- 全体の停止を、確かめて閉じたときだけ解くこと（確かめずに閉じても、確かめて閉じなくても止めたまま）と、全体の停止の Issue を開いた実行で動いている AI のセッションを止めることは、起票のときに、止める側に倒す形として足した
- 本 ADR で決めないこと
