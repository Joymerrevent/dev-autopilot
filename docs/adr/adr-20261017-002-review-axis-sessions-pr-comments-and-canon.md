# レビューの 3 つの軸は進行ボットが軸ごとに別のセッションで動かしてどの役にも Agent ツールを与えず、PR のコメントは AI に渡さず、規約の正典に触れる diff は push しない

> **Amended by [ADR-20261019-002][adr-gaps]（2026-10-19）**: 決定 1 のうち、「1 ラウンドのレビューは、軸ごとの 3 つのセッション（動作・仕様・規約）と、その後の批評 AI のセッションで行う」を改め、3 つの軸の後に 4 つ目の軸「見落とし」のセッションを足した。見落としの軸の結果は、修正工程（段階 7）に進む前に使うかを決めるまで記録だけに残す。決定 1 のほかの項目と、決定 2〜4 は据え置く。

> **Amended by [ADR-20261022-002][adr-critic-skip]（2026-10-22）**: 決定 1 のうち、批評 AI のセッションをどのラウンドでも起こすこと、どのラウンドでも批評 AI の統合の結果で印を書くこと、5 つの条件（IMPL-18）をどのラウンドでも批評 AI のセッションに掛けることの 3 つと、確認方法の 1 つ目の項目のうち、レビューの流れと 5 つの条件を掛ける範囲を改めた。3 つの軸がすべて 5 つの条件を満たし、🔴 🟡 が合わせて 0 件のラウンドは、批評 AI のセッションを起こさず、統合せずに 3 つの軸の指摘で 1 つの `review` の印とコメントを書く。5 つの条件は、ラウンドで起こしたセッション（見落としの軸を除く）のすべてに掛ける。決定 1 のほかの項目（軸ごとに別の作業場所で起こす、同じエージェント定義で起こす、進行 Bot が仕様 → 動作 → 規約の順に並べる、軸をまたいで束ねない、5 つの条件を 1 つでも満たさなければ印を書かずに実行の失敗にする、人が手でレビューするときの形）と、確認方法のほかの項目、決定 2〜5 は据え置く。

要件の UNDECIDED-32、UNDECIDED-33、UNDECIDED-34（[決めていないこと][undecided]の「レビューとマージ」）を決める。
どれもレビュー AI が何を読み、どの道具で動くかの論点で、問いは 3 つある：3 つの軸をどう動かし Agent ツールを許すか、コラボレータの PR のコメントを AI に渡すか、規約の正典をどこから読ませるか。

[ADR-20261015-005][adr-settings] の決定 1 のうち、設定の項目「Agent ツールを許すか」（初期値は「許さない」）を、決定 3 で改める。安全の境界を緩める変更を ADR で決めるという決定と、ADR-20261015-005 のほかの決定は据え置く。

## 背景と課題（Context and Problem Statement）

問い 1（UNDECIDED-32）：レビューの 3 つの軸をどう動かし、Agent ツールを許すか

- REVIEW-1 は、レビューを 3 つの軸（動作・仕様・規約）に分け、軸ごとに並列のサブエージェントで見るとする。軸ごとに新しい文脈で見るのは、同じ文脈のレビューが確認バイアスになるため
- 一方、「[登場するもの][overview]」のレビュー AI の道具は Bash・Read・Write（worktree の中だけ）で、サブエージェントを起こす Agent ツールが無い。作業 AI の道具は、Agent を明示して外している
- [ADR-20261015-005][adr-settings] は、Agent ツールを許すことを、安全の境界を緩める変更として ADR で決めるとし、設定の項目「Agent ツールを許すか」の初期値を「許さない」とした。設定が役ごとか、すべての役で 1 つかは決まっていない（IMPL-14、STRUCT-2）
- 批評 AI は、2026-10-11 のレビューで、サブエージェントでなく、進行ボットが別に起こす独立したセッションにした（隔離を優先した。「[2026-10-11 のレビューで決めたことと、採らなかった案][records]」の 7）
- 2026-10-17 に Claude Code の公式文書を読んだ（補足情報）。サブエージェントの Bash は親のセッションと同じ sandbox の設定で動き、`permissions.deny` の Bash の規則もサブエージェントに効く。
  一方、サブエージェントは既定で 3 段まで入れ子にでき、入れ子の既定は版ごとに変わってきた（5 段、1 段、3 段）。
  実機で確かめると、サブエージェントの消費は最後の `result` の `modelUsage` には入るが、途中のイベントからは数え切れなかった（補足情報）

問い 2（UNDECIDED-33）：コラボレータの PR のコメントを AI に渡すか

- TEXT-1 は、コメントは著者がコラボレータのものだけを渡し、「PR のコメントも同じ」とする。REVIEW-6 も「読むコメントはコラボレータのものだけ」とする
- 一方、TEXT-1 は、渡す文の範囲を `agent-ready` の時点で確定し（作業指示コメントか承認された下書き）、後から足されたコメントは渡さないとする。PR は `agent-ready` の後に作られるので、PR のコメントはすべて範囲の外になる
- 再レビューの入力（IMPL-21）と修正の入力（IMPL-23）にも、コラボレータのコメントは無い。人が PR に書く固定の見出しの `## 却下 R<n>` は、進行ボットが数えるだけで AI に渡さない（FLOW-14）
- 渡すのか、渡すならどの役のどの入力かが決まらない

問い 3（UNDECIDED-34）：規約の正典をどこから読ませるか

- 「[AI が読む文と出どころ][markers]」の表は、リポジトリのファイルについて「規約の正典は base ブランチから渡す」とする。規約の軸（REVIEW-1）が照らす正典は CLAUDE.md・ADR・構造仕様で、「リポの文書が常に優先」とする
- 一方、レビュー AI の作業場所は PR の head で作る（IMPL-16）。作業 AI は head の `docs/adr/**` や構造仕様を書き換えて push できる。
  IMPL-15 の push しないパス（`.claude/**` `CLAUDE.md` `.mcp.json` `.github/**` `dev-autopilot/**`）に入っておらず、マージの判定で `merge=human` になるだけ（MERGE-4）
- 作業 AI が、自分の変更を通す ADR を足したり、承認済みの ADR を書き換えたりすると、レビュー AI の規約の軸は書き換えた正典を規則として読む。修正のセッション（IMPL-23）も PR の head から作るので、作業 AI 自身も書き換えた正典を読む
- 作業 AI が ADR を書く場面は、要件の上では無い。ADR の起票が要ると分かったら、作業 AI は実装せずに止まった理由を返す（IMPL-8）

課題：3 つの軸を、サブエージェントで動かすか、別のセッションで動かすか、1 つのセッションで動かすか。コラボレータの PR のコメントを AI に渡すか。規約の正典を、作業 AI が書き換えられない形でどう読ませるか。

## 判断の決め手（Decision Drivers）

- 安全の境界（AI の道具・読み書きの範囲）を、確かめていない Claude Code の振る舞いや、版で変わる既定に頼って緩めないこと
- 集約・数え上げ・pass の条件の判定を、AI でなく進行ボットの決定的な処理で行うこと（「[登場するもの][overview]」の、進行ボットを AI にしない理由）
- 利用枠の数え上げ（IMPL-14）とモデルの確かめ（IMPL-18 の (5)）を、AI のセッションごとに行えること（`stream-json` からの数え方そのものは、UNDECIDED-47 で別に決める）
- AI に渡す文の範囲を、`agent-ready` の時点で確定したまま保つこと（TEXT-1、TEXT-4）
- 作業 AI の出力を、次のセッション（レビュー AI と修正のセッション）が規則として信頼しないこと（SAFE-2）
- `review` Skill が、人が手で使うとき（STRUCT-7 の単体導入）にも同じ手順で動くこと

## 検討した選択肢（Considered Options）

問い 1：3 つの軸をどう動かし、Agent ツールを許すか

- 案 1-A：レビュー AI だけに Agent ツールを許し、起こせるサブエージェントを Plugin の軸ごとのエージェント定義に絞る（`tools` に `Agent(<軸のエージェント>)` と書く）。設定は役ごとに持つ
- 案 1-B：進行ボットが軸ごとに別のセッションを起こし（批評 AI と同じ形）、出力を進行ボットが束ねる。Agent ツールはどの役にも与えず、設定の項目「Agent ツールを許すか」を無くす
- 案 1-C：1 つのレビュー AI のセッションが 3 つの軸を順に見る。サブエージェントを使わない

問い 2：コラボレータの PR のコメントを AI に渡すか

- 案 2-A：PR のコメントは、書いた人を問わず、どの役にも渡さない。PR について AI に渡すのは、進行ボットが印から組み立てた入力（前回の指摘など）だけにする
- 案 2-B：固定の見出し（例：`## 追加の指摘`）を持つコラボレータの PR のコメントを、次の修正のセッションに、最新のラウンドの指摘と並べて渡す
- 案 2-C：コラボレータの PR のコメントをすべて、レビュー AI と作業 AI に渡す

問い 3：規約の正典をどこから読ませるか

- 案 3-A：規約の正典のパスを、IMPL-15 の push しないパスの一覧に足す。作業 AI は正典を変えられないので、レビュー AI と修正のセッションは、作業場所（PR の head）の正典をそのまま読む
- 案 3-B：進行ボットが base の SHA を渡し、レビュー AI は正典を `git show <base の SHA>:<パス>` で読む（固定の指示文で指示する）。head の正典の変更は差分として読む
- 案 3-C：進行ボットが base の正典を、作業場所の外（セッションのフォルダ）に写すか、固定の指示文に入れて渡す

## 決定（Decision Outcome）

採用した選択肢:「案 1-B」「案 2-A」「案 3-A」。
理由: 軸ごとの新しい文脈を保ったまま、Agent ツールという新しい境界を開けず、集約と数え上げを進行ボットの決定的な処理に残せる。AI に渡す文の範囲は `agent-ready` の時点のまま変わらない。
作業 AI が正典を変える経路を push の前の機械の検査で止めるので、レビュー AI が指示を守るかに頼らずに、次のセッションが書き換えた正典を読まなくなる。

### 決定 1：レビューの 3 つの軸は、進行ボットが軸ごとに別のセッションで動かす

- 1 ラウンドのレビューは、軸ごとの 3 つのセッション（動作・仕様・規約）と、3 つのセッションの後に起こす批評 AI のセッション（IMPL-22）で行う。
  軸のセッションは、それぞれ別の作業場所（[ADR-20261013-001][adr-workspace] の形。AI のセッションごとに origin から clone し、PR の head で worktree を切る）で起こす
- 軸のセッションは、同じレビュー用のエージェント定義（`plugin/agents/reviewer.md`）で起こし、どの軸を見るかを、進行ボットが固定の指示文と `review` Skill の引数で渡す（REVIEW-5 の無人の入り口の引数に「軸」を足す）。
  モデルと effort は、どの軸も IMPL-33 の値で始める。軸ごとに分けるかは、設定の値として段階 6（レビュー AI と批評 AI を足す段階。「[段階][stages]」）で決める
- 3 つのセッションを並列で起こすか順に起こすかと、作業場所の名前の付け方は、基本設計で決める
- 進行ボットは、軸ごとの出力契約を検証し、仕様 → 動作 → 規約の順に並べて 1 つにする（REVIEW-1 の「仕様の軸の 🔴 を先に報告する」）。
  批評 AI には、3 つの軸の 🔴 と 🟡 をまとめて渡す。統合した結果を、1 つの `review` の印とコメントにする（IMPL-18、IMPL-22）
- 軸をまたいで同じ問題を指摘していても、進行ボットは束ねない（2 つの文が同じ問題を指すかを、機械で判定できないため）。重複があっても、判定が pass か fix かは変わらない
- `verdict` を pass にする 5 つの条件（IMPL-18）は、3 つの軸のセッションと批評 AI のセッションのすべてに掛ける。1 つでも満たさなければ印を書かず、実行の失敗（IMPL-14）として持ち越す
- 人が手でレビューするとき（`review` Skill を単体で使うとき。STRUCT-7）は、引数で軸を渡されなければ、人の Claude Code のセッションで 3 つの軸をサブエージェントで見る（REVIEW-1 のまま）。
  軸ごとの手順は Skill の中に 1 回だけ書き、無人の入り口と人の入り口で同じものを使う

### 決定 2：Agent ツールは、AI の 5 役のどれにも与えない

- 計画 AI・作業 AI・レビュー AI・批評 AI・受付 AI のエージェント定義の `tools` に、Agent を書かない
- 重ねる守りとして、進行ボットが渡す安全設定の `permissions.deny` に `Agent` を入れる（公式文書では、道具の名前だけを書いた deny は、道具をモデルの文脈から取り除く）
- AI の 5 役に Agent ツールを与えるのは、エージェント定義（dev-autopilot のリポの `plugin/agents/`）を変えることで、新しい ADR で決める

### 決定 3：設定の項目「Agent ツールを許すか」を無くす

- IMPL-14 と STRUCT-2 の「Agent ツールを許すか」を、設定の項目から外す。[ADR-20261015-005][adr-settings] の決定 1 の「Agent ツールの初期値は『許さない』」は、項目を無くすことで改める
- 理由：AI の道具は、dev-autopilot のリポのエージェント定義の `tools` で決まる。当てる先のリポの設定に同じことを決める項目を置くと、正本が 2 つになる。
  設定の値を「許す」に変えても、エージェント定義に Agent が無ければ使えないので、項目が働かない

### 決定 4：コラボレータの PR のコメントは、どの役にも渡さない

- PR のコメントは、書いた人（コラボレータ、外の人、進行ボットのアカウント）を問わず、書かれたままの形では AI に渡さない。
  TEXT-1 の「PR のコメントも同じ」を外し、渡す文の範囲は、`agent-ready` の時点の作業指示コメントか承認された下書きのまま（TEXT-1、TEXT-4）にする
- PR について AI に渡すのは、進行ボットが署名付きの印のあるコメント（IMPL-20 の 3 条件を満たすもの）から組み立てた入力（前回の印から読み取った値と指摘。IMPL-21）と、進行ボットが機械で付けた事実（差分、CI の結果、変更ファイル）だけにする。
  前回の指摘は、今のとおり検疫（TEXT-11）を通す
- REVIEW-6 の「読むコメントはコラボレータのものだけ」を、「PR のコメントは読まない」に改める
- 人が PR の進み方を変えたいときは、今ある手段を使う：Agent 欄を `paused` にする、`needs-human` を付ける、`## 却下 R<n>` を書く（進行ボットが数えるだけで AI に渡さない。FLOW-14）、新しい Issue を立てる、人が直す
- 人の指摘を対応ループに足す仕組み（案 2-B）が要るかは、段階 8（進行ボットが PR にマージの判定の印を書き始める段階）までの記録（`## 判定と違う判断` の件数と中身など）を見て、要るなら新しい ADR で決める

### 決定 5：規約の正典に触れる diff は push しない

- 規約の正典のパス（REVIEW-1 の規約の軸が照らす CLAUDE.md・ADR・構造仕様）を、IMPL-15 の push しないパスの一覧に足す。
  一覧はリポの設定に持ち（STRUCT-2）、初期値は構造仕様の設定の表で決める（[ADR-20261015-005][adr-settings]。business-os なら `CLAUDE.md` と `docs/adr/**` と `docs/design/**`）
- 一覧の説明を「進行ボット・次のセッション・CI が実行するパス」から「進行ボット・次のセッション・CI が実行するか、規則として読むパス」に改める。diff が一覧のパスに触れていれば、今のとおり push せずに `needs-human` にする
- 作業 AI の固定の指示文に規約の正典のパスを書き、正典を変える必要があると分かったら、変えずに止まった理由を出力契約で返させる（IMPL-8 の ADR と同じ扱い）
- 作業 AI が正典を変えられないので、PR の head の正典は、head に取り込んだ `develop` の正典（人がマージしたもの）と同じになる。
  レビュー AI と修正のセッションは、作業場所（PR の head）の正典をそのまま読む。「[AI が読む文と出どころ][markers]」の表の「規約の正典は base ブランチから渡す」を、作業場所の head の正典を読む形に改める
- 一覧からパスを外すのは、安全の境界を緩める変更として ADR で決める（[ADR-20261015-005][adr-settings] の決定 1 のまま）

### 影響（Consequences）

- 良い点: Agent ツールを開けないので、安全の境界は今のまま。サブエージェントの入れ子の深さや道具の受け継ぎのような、版で変わる振る舞いに頼らない
- 良い点: 軸ごとの出力を進行ボットが機械で束ねる。差分に紛れた指示が 1 つの軸のセッションを惑わせても、ほかの軸の指摘は消えない
- 良い点: 軸のセッションごとに、今の仕組み（`modelUsage` の確かめ、時間とターンと費用の上限）がそのまま効き、消費もセッションごとの記録で数えられる。
  途中で止めた回の消費の数え方は、案に関わらず UNDECIDED-47 で決める
- 良い点: AI に渡す文の範囲が `agent-ready` の時点で確定したまま変わらず、対応ループの入力を印から再現できる
- 良い点: 作業 AI が正典を書き換えて自分の変更を通す経路が、レビュー AI の指示の守り方でなく、push の前の機械の検査で止まる
- 悪い点: 1 ラウンドのセッションが 2 つ（レビューと批評）から 4 つ（3 つの軸と批評）になり、作業場所の clone と依存の導入が軸の数だけ増える（clone は約 3 秒、sandbox の中の `pnpm install` は空の store で約 9 秒。FACT-21、FACT-22）。
  進行ボットの起動の処理と、一部の軸だけが失敗したときの処理が増える
- 悪い点: 軸をまたいだ重複が、そのまま人の読むコメントに出る。重複が人の読む量をどれだけ増やすかは、段階 6 で測る
- 悪い点: 人が PR のコメントで AI に指示できない。人の指摘を反映するには、止めて人が直すか、新しい Issue を立てる
- 悪い点: 作業指示が構造仕様の更新を求める Issue でも、作業 AI は正典を変えられず `needs-human` になる。正典の更新は人が行う
- 悪い点: ブランチを作った後に `develop` で正典が変わると、レビュー AI は載せ直し（MERGE-5）まで古い正典を読む。
  載せ直しで差分の patch-id が変わらなければ再レビューしない（MERGE-6）ので、新しく承認された ADR に照らさないまま判定に進むことがある。マージの実行は人が行う（MERGE-1）

### 確認方法（Confirmation）

- 構造仕様を書くときに、次をレビューで確かめる
  - レビューの段の流れが、軸ごとの 3 つのセッションと批評 AI のセッションで書かれ、IMPL-18 の 5 つの条件をすべてのセッションに掛けていること
  - 設定の表に「Agent ツールを許すか」が無く、push しないパスの一覧の初期値に規約の正典のパスがあること
- 段階 3（`setup` と `check` を作る段階）の `check`（SETUP-2）で、AI のセッションの道具の一覧（`stream-json` の初期化の記録）に Agent が無いことを確かめる（初期化の記録では `Task` という名前で出るので、`Agent` と `Task` の両方を探す）
- 結合テスト（偽の `gh`）で、次を検査する
  - 軸のセッションのどれか 1 つの出力契約が解析できなければ、`review` の印を書かずに実行の失敗になること
  - コラボレータの PR のコメントが、どの AI のセッションの入力にも入らないこと
  - 規約の正典のパスに触れる diff を push せず、`needs-human` になること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：レビュー AI だけに Agent ツールを許し、起こせるサブエージェントを絞る

- 良い点: REVIEW-1 の形（並列のサブエージェント）のまま動く。Claude Code 組み込みの `/code-review` も、観点ごとの並列のサブエージェントで動く（「[`change-review` スキルの評価と、レビューの業界の実践][records]」の比べたもの）。作業場所は 1 ラウンドに 1 つで済む
- 良い点: 公式文書では、サブエージェントの Bash は親のセッションと同じ sandbox の設定で動き、`permissions.deny` の Bash の規則もサブエージェントに効く。読み書きの範囲そのものは広がらない
- 中立: 公式文書では、`claude --agent` で動くエージェントの `tools` に `Agent(<種類>)` と書くと、起こせるサブエージェントの種類を許可一覧で絞れる。組み込みの Explore などは起こせなくなる
- 悪い点: 3 つの軸の結果を束ねるのがレビュー AI（AI）になる。差分に紛れた指示がレビュー AI を惑わせると、サブエージェントが出した指摘を落とせる
- 悪い点: サブエージェントの消費は、最後の `result` の `modelUsage` と `total_cost_usd` には入るが、途中のイベントからは数え切れない（2026-10-17 に実機で確かめた。補足情報）。
  時間の上限で止めた回（最後の `result` が出ない回）は、サブエージェントの消費を記録に残せない。サブエージェントのモデルは `modelUsage` に別の項目として出るので、IMPL-18 の (5) の確かめ方も変える必要がある
- 悪い点: サブエージェントをバックグラウンドで動かすかを、モデルが呼び出しごとに決める（同じ指示で 3 回中 2 回がバックグラウンド）。
  バックグラウンドのときは、1 回の実行で `result` が 2 つ出て、1 つ目はサブエージェントの答えが揃う前の返事だった
- 悪い点: 入れ子の深さの既定は版ごとに変わってきた（v2.1.172〜v2.1.216 は 5 段、v2.1.217〜v2.1.218 は 1 段、v2.1.219 以降は 3 段）。軸のエージェント定義から Agent を外せば入れ子は止まるが、守りが Claude Code の版ごとの振る舞いに依る
- 悪い点: サブエージェントの数を制限するフラグが無い（IMPL-14）。消費は `--max-budget-usd`（公式文書では、サブエージェントの消費も上限に数える）と時間の上限でしか止まらない
- 悪い点: ADR-20261015-005 の「安全の境界を緩める変更」に当たる

### 案 1-B：進行ボットが軸ごとに別のセッションを起こし、出力を進行ボットが束ねる

- 良い点: Agent ツールを開けない。批評 AI を独立したセッションにした判断（2026-10-11）と同じ形
- 良い点: 集約と数え上げが進行ボットの決定的な処理になる。軸ごとのセッションに、今の上限と確かめがそのまま効く
- 良い点: 軸ごとにモデルや予算を、設定で分けられる
- 悪い点: セッションと作業場所が軸の数だけ増え、進行ボットの処理が増える
- 悪い点: 軸をまたいだ重複を束ねない

### 案 1-C：1 つのセッションが 3 つの軸を順に見る

- 良い点: 仕組みがいちばん小さい。Agent ツールを開けず、作業場所も 1 つ
- 悪い点: 軸ごとの新しい文脈が無くなり、前の軸の見立てが後の軸を引きずる（REVIEW-1 が避けた確認バイアス）。1 つの文脈が長くなる

### 案 2-A：PR のコメントはどの役にも渡さない

- 良い点: AI に渡す文の範囲が `agent-ready` の時点で確定したまま。検疫と権限確認の対象が増えない
- 良い点: 新しく決める規則（見出し、時刻の範囲、ラウンドとの対応）が無い
- 悪い点: 人が PR のコメントで対応ループに指摘を足せない

### 案 2-B：固定の見出しのコラボレータのコメントを修正のセッションに渡す

- 良い点: 人の指摘を対応ループで直させられる
- 悪い点: 見出し、渡す範囲（どの印からどの起動までに書かれたコメントか）、権限確認（TEXT-10）、往復への数え方、レビュー AI が人の指摘を確かめるかを、新しく決める必要がある。TEXT-1 の「`agent-ready` の時点で確定」を変える
- 悪い点: コラボレータが PR のコメントに貼った外の文が、作業 AI に届く経路が増える（検疫は網であって壁ではない。TEXT-11）

### 案 2-C：コラボレータの PR のコメントをすべて渡す

- 良い点: 人が自由に書いたことが、すべて AI に届く
- 悪い点: 雑談や確かめの問いも、作業の内容として AI に届く。レビュー AI に作業 AI の主張を読ませない理由（文脈のバイアス。REVIEW-6）と同じ問題が、人のコメントにも起きうる
- 悪い点: 渡す文の範囲が確定しなくなり、TEXT-4 のハッシュの照合が働かない

### 案 3-A：規約の正典に触れる diff は push しない

- 良い点: 機械の検査で止まり、レビュー AI と修正のセッションの両方が、書き換えた正典を読まない
- 良い点: 作業 AI は ADR を書かない（IMPL-8）という今の規則と揃う。正典に触れる PR は、もともと `merge=human`（MERGE-4）
- 悪い点: 構造仕様の更新を含む作業も `needs-human` になる
- 悪い点: ブランチを作った後の `develop` の正典の変更は、載せ直しまで届かない

### 案 3-B：レビュー AI が正典を `git show <base の SHA>:<パス>` で読む

- 良い点: 作業 AI が正典を変える PR も作れる。レビュー AI は最新の base の正典を読める
- 良い点: レビュー AI の作業場所は origin から作り直した clone なので、base の commit は作業 AI に触られていない（ADR-20261013-001）
- 悪い点: レビュー AI が指示どおりに base から読むかに頼る。head のファイルを読んでも、止める仕組みが無い
- 悪い点: 修正のセッション（作業 AI）は、head の正典を読み続ける

### 案 3-C：base の正典を作業場所の外に写すか、指示文に入れて渡す

- 良い点: head の正典と別の場所に置くので、取り違えにくい
- 悪い点: Read ツールは作業場所の外を読めない（FACT-22）ので、写した正典は Bash でしか読めない。
  指示文に入れると、business-os の ADR（`docs/adr/` の 35 件。2026-10-17 に確かめた）を毎回渡すことになるか、関係する ADR を選ぶ判断が要る
- 悪い点: レビュー AI が head の正典を読んでも止める仕組みが無いのは、案 3-B と同じ

## 補足情報（More Information）

- 関連する要件：REVIEW-1、REVIEW-5、REVIEW-6（[08-review-skill.md][review]）、IMPL-4、IMPL-8、IMPL-14、IMPL-15、IMPL-16、IMPL-18、IMPL-21、IMPL-22、IMPL-23、「モデルの流れ」（[02-implement-review-fix.md][impl]）、MERGE-4、MERGE-6（[03-merge.md][merge]）、
  TEXT-1、TEXT-4、TEXT-11、「AI が読む文と出どころ」（[04-external-text-and-markers.md][markers]）、SAFE-2、SAFE-10（[05-safety.md][safety]）、STRUCT-2、STRUCT-7（[07-structure.md][struct]）、FLOW-14（[01-issue-flow.md][flow]）、
  [ADR-20261013-001][adr-workspace]、[ADR-20261015-005][adr-settings]
- 2026-10-17 に、Claude Code の公式文書（[サブエージェント][doc-subagents]、[sandbox][doc-sandboxing]、[CLI の一覧][doc-cli]、[権限][doc-permissions]、[`-p` での実行][doc-headless]）を読んだ。手元の Claude Code は 2.1.285。読んだこと：
  - サブエージェントは親のセッションと同じプロセスで動き、同じ sandbox の設定を使う。親のセッションで sandbox が有効なら、サブエージェントの Bash も sandbox の中で動く
  - 組み込みのサブエージェントは、親の会話の権限の規則を受け継ぐ。`permissions.deny` の Bash の規則は、親の会話とサブエージェントの両方に効く
  - `claude --agent` で動くエージェントは、`tools` に `Agent(<種類>, ...)` と書くと、起こせるサブエージェントの種類を許可一覧で絞れる。`tools` に Agent が無ければ、サブエージェントを起こせない
  - サブエージェントは、親の会話で使える組み込みのツールと MCP のツールを受け継ぎ、決まった絞り込みを受ける。macOS では、親に無い Glob と Grep を受け取ることがある
  - サブエージェントは既定で 3 段まで入れ子にできる（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` で変えられる）。既定は v2.1.172〜v2.1.216 が 5 段、v2.1.217〜v2.1.218 が 1 段、v2.1.219 以降が 3 段
  - `--max-budget-usd` は、サブエージェントの消費も上限に数える（上限での停止は v2.1.217 以降）
  - `stream-json` にサブエージェントの文を出すには、`--forward-subagent-text` が要る。サブエージェントの消費が `usage` と最後の `modelUsage` にどう出るかは、読んだ範囲に書いていない（下の実機の確かめで調べた）
  - `permissions.deny` に道具の名前だけを書くと、道具がモデルの文脈から取り除かれる。`Agent(<種類>)` の形で、特定の種類のサブエージェントだけを止めることもできる
  - 組み込みの Explore のモデルは、親の会話のモデル。親が `fable` のときは、サブスクリプションで接続していれば `opus` の別名が解けるモデルになる
- 2026-10-17 に、サブエージェントの消費が `stream-json` の記録にどう出るかを実機で確かめた（macOS、Claude Code 2.1.285）。
  試験用の Plugin（親のエージェントは `tools: Agent, Read`、サブエージェントは `tools: Read` でファイルを 1 つ読む）を、`claude -p --setting-sources local --plugin-dir <Plugin> --agent <親> --model claude-haiku-5-5 --output-format stream-json --verbose` で 3 回起動した。
  2 回目は `--forward-subagent-text`、3 回目は `--include-partial-messages` を足し、3 回目だけサブエージェントの `model` を `sonnet` にした。sandbox は掛けていない
  - 最後の `result` の `modelUsage` と `total_cost_usd` は、サブエージェントの消費を含む。サブエージェントのモデルが親と違えば、別の項目に出る（3 回目：親の `claude-haiku-5-5` とサブエージェントの `claude-sonnet-5-5`）。
    サブエージェントの `model` を親と同じ系統の別名（`haiku`）にすると、親のモデル（`claude-haiku-5-5`）で動き、同じ項目に足された（公式文書の、モデルの決まり方のとおり）
  - `assistant` のイベントは、1 つのメッセージが中身の区切り（thinking・text）ごとに別のイベントに分かれ、同じ `usage` を繰り返して持つ。`usage.output_tokens` はストリームの始めの値（`stop_reason` が null）で、最後の値ではない。
    3 回目の親のメッセージでは、イベントの `output_tokens` の和が 25、`modelUsage` が 485 だった。サブエージェントの有無に関わらず、親のセッションでも起きる
  - `--include-partial-messages` を付けると、親のメッセージの `message_delta` の `output_tokens` が最後の値を持つ（3 回目の親の和は 485 で、`modelUsage` と一致した）。サブエージェントのメッセージは、`stream_event` として出なかった
  - サブエージェントの `assistant` のイベントは、動き方で出方が変わる。バックグラウンドのとき（1 回目と 2 回目）はすべてのメッセージが `parent_tool_use_id` 付きで出た。
    前で動いたとき（3 回目。`--forward-subagent-text` なし）は、2 つのメッセージのうち道具を呼んだ 1 つだけが出た。途中の記録（`task_progress` と `task_notification`）は、`total_tokens`・`tool_uses`・`duration_ms` だけを持ち、モデルと入力・出力の内訳を持たない
  - サブエージェントをバックグラウンドで動かすかは、同じ指示でも回ごとに違った（1 回目と 2 回目はバックグラウンド、3 回目は前）。バックグラウンドの回は、親がサブエージェントの答えを待たずにターンを終え、`result` が 2 つ出た（1 つ目は「サブエージェントはまだ動いている」という返事）。プロセスは 2 つ目の `result` の後に終わった
  - 初期化の記録の道具の一覧では、Agent ツールは `Task` という名前で出た
- 本 ADR の決定と関わらない発見：実機の確かめの途中で、`assistant` のイベントの `usage` が同じメッセージで重複し、`output_tokens` が最後の値でないこと（FACT-29）と、`--setting-sources local` のセッションにも claude.ai のコネクタが入る回があること（FACT-30）が分かった。
  どちらも [実機で確かめた事実][facts] に足し、決め方を [決めていないこと][undecided] の UNDECIDED-47・UNDECIDED-48 に回した（[dev-autopilot の PR #5][da-pr-5]）
- 2026-10-17 に、business-os の `develop` の `CLAUDE.md` と `docs/` を GitHub の API で読んだ：正典は `docs/adr/`（35 件）、構造仕様は `docs/design/architecture.md`
- 要件への反映（承認の後に、別の PR で行う）
  - 「[登場するもの][overview]」：レビュー AI の行を、軸ごとの 3 つのセッションに改める。5 役に共通の説明に、Agent ツールをどの役にも与えないことを書く
  - REVIEW-1：dev-autopilot では進行ボットが軸ごとに別のセッションを起こし、人が手で使うときはサブエージェントで見る、に改める。REVIEW-5：無人の入り口の引数に「軸」を足す。REVIEW-6：PR のコメントを読まない、に改める
  - IMPL-14、STRUCT-2：設定の項目「Agent ツールを許すか」を外す
  - IMPL-16、IMPL-18、IMPL-22：軸ごとのセッションと作業場所、5 つの条件をすべてのセッションに掛けること、批評 AI に 3 つの軸の指摘を渡すことを書く
  - 「モデルの流れ」：IMPL-33 と IMPL-36 と「利用枠の見方」を、軸ごとの 3 つのセッションに合わせる
  - TEXT-1、TEXT-11、「AI が読む文と出どころ」の表：PR のコメントを渡さないこと、規約の正典を作業場所（PR の head）から読むことを書く
  - IMPL-15、SAFE-2 の (c)：push しないパスの一覧に規約の正典のパスを足し、一覧の説明を改める。IMPL-4、IMPL-8：正典を変える必要があれば止まった理由を返すことを書く
  - SAFE-2 の (e)：安全設定の `permissions.deny` に `Agent` を入れることを書く
  - 07-structure.md の構成の図の `reviewer.md` の説明：軸ごとに起こすことを書く
  - 図：「[図][diagrams]」の概要の図と Issue の流れの図のレビュー AI の箱を、軸ごとのセッションに合わせて直すかを確かめる
  - ADR-20261015-005：タイトルの下に、決定 1 の Agent ツールの項目を本 ADR で改めた旨の注記を足す
  - 09-undecided.md：UNDECIDED-32、UNDECIDED-33、UNDECIDED-34 を欠番にする（元の文を取り消し線で残す）
