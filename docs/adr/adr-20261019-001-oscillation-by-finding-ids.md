# 振動は、review の印に足す 🔴 🟡 の指摘の ID で見分け、間を空けて再び出た指摘も振動に数える

要件の UNDECIDED-41（[決めていないこと][undecided]の「振動の数え方」）を決める。あわせて、振動を見分けるのに要る材料（どの指摘を出したか）を、判定に使える形で GitHub に残す方法を決める。

## 背景と課題（Context and Problem Statement）

- IMPL-24 は「同じ指摘が 2 ラウンド続けて出たら振動」とし、往復の上限（3 回）と同じく `needs-human` にする（FLOW-28）。「[レビューの Skill][review]」の方針は「同じ指摘が 2 回出たら振動として止めて人へ」とする。間を空けて再び出た指摘を振動に数えるかが決まっていない（UNDECIDED-41）
- 振動を見分けるには、前のラウンドでどの指摘を出したかが要る。ところが、判定に使える材料に、指摘を見分けるものが無い
  - `review` の印の欄は `round` `head` `high` `medium` `low` `verdict` `dropped_high` で、件数しか持たない（[印と固定の見出しの一覧][markers]）
  - 判定は印だけで行い、本文の言い回しは解析しない（IMPL-18）
  - 判定に手元の記録を使わない（[ADR-20261015-006][adr-flow] の決定 4）
- 進行 Bot は、指摘を 1 件ずつ扱っている。批評 AI は指摘ごとに確信度と推奨する重要度を返し（IMPL-22）、🟢 は 1 件ずつ見出し・失敗シナリオ・推奨を写した Issue にする（IMPL-26）。指摘ごとに重要度と確信度を併記する（REVIEW-3）。指摘ごとのファイルのパスは、要件に書いていない。同じ見出しで見分ける決まりは、🟢 の Issue の重複（IMPL-26。同じ見出しの open な Issue）と、人の却下（FLOW-14。却下する指摘の見出しを列挙）にすでにある
- 往復の回数の上限は 3 回（IMPL-24）なので、1 つの PR のレビューは多くても 4 ラウンド

課題：同じ指摘をどう見分け、その材料をどこに残すか。間を空けて再び出た指摘を振動に数えるか。

## 判断の決め手（Decision Drivers）

- 振動の判定を、GitHub にある署名付きの印だけで決定的に行えること（印の真正性。IMPL-20）
- AI の言い換えで見逃しても、安全側に倒れること（見逃しても往復の上限で止まる）
- 印と出力契約を大きく変えないこと

## 検討した選択肢（Considered Options）

- 案 A：`review` の印に、🔴 🟡 の指摘ごとの短い ID の一覧の欄を足す。ID は、軸・正規化した見出し・ファイルのパスから進行 Bot が計算する。前のラウンドの印の ID と比べて振動を見分ける
- 案 B：進行 Bot が投稿したレビューのコメントの本文（未編集を確かめたもの）から、前のラウンドの指摘の見出しを読む
- 案 C：再レビューのレビュー AI に前のラウンドの指摘を渡し、同じ指摘かを出力契約で返させる。進行 Bot は、同じと返った件数を印に足す
- 案 D：振動の検出をやめ、往復の上限（3 回）だけで止める（IMPL-24 を変える）

間を空けて再び出た指摘については、次の 2 つを比べた。

- 案 1：直前のラウンドにも出ていたときだけ振動に数える（IMPL-24 の文のとおり）
- 案 2：前のどのラウンドに出ていても振動に数える（「[レビューの Skill][review]」の方針のとおり）

## 決定（Decision Outcome）

採用した選択肢:「案 A」と「案 2」。
理由: 振動の判定が、署名付きの印だけで決定的にできる。ID の計算は進行 Bot が行い、AI の判断を足さない。見出しの言い換えで見逃しても、往復の上限で止まる。間を空けて再び出た指摘も、前のラウンドで直したはずの指摘が戻ったことに変わりがないので、振動に数えて早く人に渡す。

### 決定 1：`review` の印に、🔴 🟡 の指摘の ID の一覧を足す

- `review` の印に `findings=<ID>,<ID>,...` の欄を足す。批評 AI の統合（IMPL-22）の後に残った 🔴 と 🟡 の指摘だけを入れる（🟢 は入れない）。指摘が無ければ空にする
- ID は、指摘ごとに「軸」「正規化した見出し」「ファイルのパス」を改行でつないだ文字列の SHA-256 の、先頭 8 文字（16 進）とする。ファイルのパスが無い指摘は、パスを空にする
- 見出しの正規化：Unicode の NFKC にそろえ、先頭の重要度の記号（🔴 🟡 🟢）と空白を除き、英字を小文字にする
- ID を計算するのは進行 Bot。レビュー AI の出力契約は、指摘ごとに見出しとファイルのパス（無ければ空）を返す形にする。出力契約の中身は、基本設計の AI のセッションの文書で決める
- 載せ直しで差分が同じとき（MERGE-6）に印を新しい head に付け直すときは、`findings` も同じ値で付け直す

### 決定 2：前のどのラウンドに出た指摘でも、再び出たら振動に数える

- 新しいラウンドの `review` の印の `findings` の ID が、前のどれかのラウンドの `review` の印の `findings` にもあれば、振動とする（直前のラウンドでなくても数える。UNDECIDED-41）
- 振動なら、往復の上限と同じく、修正せずに Status を `Blocked` にして `needs-human` を付け、経緯を Issue にコメントする（IMPL-24、FLOW-28）。コメントには、振動とした指摘の見出しと、出たラウンドを書く
- 同じラウンドの中で同じ ID が 2 つ出たとき（軸をまたいで同じ見出しとパスの指摘）は、振動に数えない

### 影響（Consequences）

- 良い点: 振動の判定が、署名付きの印だけで決まる。手元の記録も本文の解析も要らない
- 良い点: ID の計算は進行 Bot が行い、単体テストで確かめられる。AI に新しい判断をさせない
- 悪い点: レビュー AI が見出しを言い換えると ID が変わり、振動を見逃す。見逃しても、往復の上限（3 回）で止まる
- 悪い点: 見出しとファイルのパスが同じで中身が違う指摘を、同じ指摘と読みうる。そのときは人に渡る（安全側）
- 悪い点: `review` の印の欄が 1 つ増え、要件の印の表を直す。出力契約に、指摘ごとのファイルのパスが要る

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、ID の計算（正規化を含む）、`findings` の書き方、前のラウンドとの比べ方（直前のラウンドと、間を空けたラウンドの両方）、載せ直しで付け直すときに同じ値を書くことを検査する
- 修正工程（段階 7）の記録で、振動で止めた件数と、そのときの指摘の見出しを見て、見逃しや誤りがないかを人が確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：印に指摘の ID の一覧を足す

- 良い点: 署名付きの印だけで決まる。AI の判断を足さない
- 悪い点: 見出しの言い換えで見逃す（往復の上限で止まる）

### 案 B：コメントの本文から見出しを読む

- 良い点: 印を変えない
- 悪い点: 本文の言い回しを解析しない決まり（IMPL-18）と食い違う。本文の様式を変えると判定が壊れる

### 案 C：AI に同じ指摘かを返させる

- 良い点: 見出しの言い換えにも強い
- 悪い点: 判定が AI の判断に頼る。出力契約を変え、印に件数を足す必要もある。再提起しない方針（「[レビューの Skill][review]」）を守らない AI が、同じ指摘だと返さないおそれがある

### 案 D：振動の検出をやめる

- 良い点: 仕組みが増えない
- 悪い点: 同じ指摘の繰り返しにも往復を使い切ってから止まり、利用枠を使う。要件の方針（同じ指摘が 2 回出たら人へ）を外す

### 案 1：直前のラウンドだけ数える

- 良い点: IMPL-24 の文のまま
- 悪い点: 直した指摘が 1 ラウンド空けて戻った場合を見逃し、往復を使い切るまで止まらない

### 案 2：前のどのラウンドでも数える

- 良い点: 直した指摘が戻ったら、間が空いていても止まる。レビューの Skill の方針と合う
- 悪い点: 別の理由で同じ箇所に同じ見出しの指摘が出たときも止まる（人に渡るので安全側）
