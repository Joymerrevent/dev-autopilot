# AI の文の検疫で見つけたことを GitHub に書けなかったときは、手元の記録で次の実行からも全体を止め、印を書き直せたら記録を消す

要件の UNDECIDED-97（AI が書いた文の検疫で見つけた後に `security` の印を GitHub に書けなかったとき、次の実行からも全体を止めるか。[決めていないこと][undecided]の「ADR で決めること」の「安全と設定」）を決める。

## 背景と課題（Context and Problem Statement）

- SAFE-19 と [ADR-20261024-005][adr-security] の決定 3 は、AI が書いた文（GitHub に書く前）の検疫で見つかったら、進行 Bot が、見つけた作業の単位に `security` の印（`where` が `text`）を書き、続けて全体の停止の Issue を開いて `halt` の印を書くとする。全体の停止の Issue がある間は、どの作業の単位でも AI のセッションを起こさない。同じ手口がほかの作業に届いているかもしれないため
- 止めるかは、GitHub の状態と印から決め、手元の記録を判定に使わない（[ADR-20261015-006][adr-flow] の決定 4、[ADR-20261024-002][adr-no-stages] の決定 5、要件の「[運用の規則][flow]」）。手元の記録は、実行をまたぐ上限の数え上げ（実行の失敗、拒否、累計の利用枠、1 日の利用枠）にだけ使う。1 日の利用枠の記録が無ければ当日の残りの AI のセッションを起こさないので、手元の記録で AI のセッションを起こさない側に倒す形は、すでにある
- 詳細設計の 2 回目の再レビュー（2026-11-11）の直しで、設計は次の形になった（基本設計の「[状態遷移と判定][design-flow]」の「全体の停止の Issue」、詳細設計の「[1 回の実行の流れ][d-flow]」の「全体の停止と通知」）
  - 見つけた実行の残りでは、印を書けたかを問わず、AI のセッションを起こさない（実行の中の値で決める）
  - `security` の印を書けた後に、全体の停止の Issue か `halt` の印を書けなかったときは、次の実行が、作業の単位の Issue の `security` の印より後に `halt` の印が無いことを GitHub から読み、全体の停止の Issue を開き直す。開き直すまでの間は全体を止める
- `security` の印を書けなかったときは、見つけた事実が GitHub に残らない。書けない場面は 4 つある
  - GitHub が断った（HTTP の状態）
  - 届いたか分からない（時間の上限で取り消した、つながらない）
  - 書く直前に読み直した全体の止める合図が `run` でなかった（[ADR-20261017-007][adr-stop] の決定 2 で書かない。人が合図を `stop` にした間に見つけた場合）
  - 書く前に実行が切れた（電源断、プロセスの強制終了）
- 見つけた AI の文は投稿しないので GitHub に無い。次の実行では、同じ工程の AI のセッションが文を書き直すので、検疫で見つけ直すとは限らない。次の実行は、全体を止めずに、ほかの作業の単位・点検の試し・受付 AI で AI のセッションを起こしうる。GitHub の外への通知も印を書いた後にだけ送る（[ADR-20261101-002][adr-notify]）ので、人も気づかない
- PR が契機（レビューの指摘、PR の題名と本文）のときは、`security` の印を Issue と PR の 2 か所に書く（[ADR-20261024-005][adr-security] の決定 4）。PR にだけ書けたときは、作業の単位の安全の軸には値が入る（安全の軸は、置き場を問わず最新の `security` の印で決める）が、開き直しは Issue の印を見るので、次の実行から全体が止まらない
- 2 回目の再レビューは、高の指摘（R1-07）と中の指摘 2 件（R3-7、R4-3）として挙げた。基本設計の「次の実行は、AI の文が変わらなければ検疫でまた見つける」の文は、上の隙間が無いように読める

課題：`security` の印を GitHub に書けなかった後に、次の実行からの全体の停止を何で保つか。印を Issue と PR の片方だけに書けたときに、書けたと読むか。

## 判断の決め手（Decision Drivers）

- 安全：見つけた後に、書き込みの失敗・合図による見送り・実行の中断のどれがあっても、次の実行で AI のセッションを起こさない（SAFE-19）
- 正本と人の戻し方：止めた事実と、人の確かめと解き方の正本を GitHub に置く。人がマシンの前にいなくても、GitHub の画面で確かめて解ける
- 動き続けること：AI を使わない工程（検疫、表示の欄、マージの判定、片付け）を止めない。GitHub の不調か合図が戻れば、人の手を借りずに印が GitHub に載る
- 確かめやすさ：止めるかの決め方を単体テストで確かめられる。手元の記録が、止めるかの判定を「進めてよい」に変える経路を持たない
- 費用：進行 Bot に足す処理と、改める承認済みの決定が少ない
- 制約：進行 Bot にリポの変数を書く権限を渡さない（[ADR-20261017-007][adr-stop]）。受け入れの依頼の実行は GitHub に書かない（[ADR-20261022-004][adr-intake-req] の決定 2）

## 検討した選択肢（Considered Options）

- 案 A：全体の停止の Issue と `halt` の印を先に書き、`security` の印を後に書く（[ADR-20261024-005][adr-security] の決定 3 の順を改める）
- 案 B：見つけたら GitHub に書く前に手元の記録に残し、記録がある間は全体の停止の Issue があるものとして扱い、次の実行が印を書き直せたら記録を消す（[ADR-20261015-006][adr-flow] の決定 4 に、止める側にだけ使う例外を足す）
- 案 C：書けなかった実行は、人が戻すまで次の実行を止める（lock を外さずに終えるなど）
- 案 D：隙間を残すと決め、点検の warn と GitHub の外への通知で人に知らせる
- 案 E：同じ実行の中で、時間の上限の内に書き直しを重ねる

## 決定（Decision Outcome）

採用した選択肢:「案 B」。

理由: 書けなかった理由（断られた、届いたか分からない、合図、実行が切れた）を問わず、次の実行が AI のセッションを起こす前に止まる。印は次の実行が GitHub に書き直すので、止めた後の正本と、人の確かめと解き方は、今と同じく GitHub に残る。
手元の記録は止める側にだけ効き、記録が無ければ今と同じく GitHub の印だけで決まる。記録が、止めるかの判定を「進めてよい」に変えることは無い。
案 A は、GitHub に書けない間（合図が `run` でない間を含む）と、書く前に実行が切れたときに隙間が残る。案 C は、AI を使わない工程まで止め、印が人の手当てまで GitHub に載らない。案 D と案 E は、隙間を狭めるか知らせるだけで、全体を止めない。

### 決定 1：AI の文の検疫で見つけたら、GitHub に書く前に手元に記録を残し、記録がある間は全体の停止の Issue があるものとして扱う

- 進行 Bot は、AI が書いた文の検疫で見つけたら（`security` の印の `where` が `text`）、`security` の印を書く前に、記録の置き場に、書けなかった見つかりの記録（以下「見つかりの記録」）を 1 件足す。書くのは、見つけた作業の単位の Issue の番号、PR が契機なら PR の番号、`security` の印に書く `where` と `finding` と見つかった場所、見つけた時刻と実行 ID。見つかった文と AI が書いた文は書かない（`security` の印のコメントと同じ）
- 進行 Bot は、実行の最初（lock を取った後、AI のセッションを起こす処理より前）に見つかりの記録を読む。1 件でもあれば、全体の停止の Issue があるときと同じに扱う。どの作業の単位でも AI のセッションを起こさず、点検の試しのセッションと受付 AI も起こさない（点検は未確認の warn、受け入れの依頼の実行は受付 AI を起こさない理由を結果のファイルに書く）。AI を使わない工程は続ける
- 全体の停止の Issue と見つかりの記録のどちらかがある間は、AI のセッションを起こさない。[ADR-20261024-005][adr-security] の決定 3 の「リポの変数が `run` で、全体の停止の Issue が無いときだけ、AI のセッションを起こす」は、「リポの変数が `run` で、全体の停止の Issue と見つかりの記録が無いときだけ」と読む
- 見つかりの記録を書けなかったとき（記録の置き場に書けない）は、今の形のまま、見つけた実行の残りでは AI のセッションを起こさずに GitHub に印を書き、手当てが要る終わり方で終える
- GitHub に書く順は、[ADR-20261024-005][adr-security] の決定 3 のまま（見つけた作業の単位の Issue に `security` の印、PR が契機なら PR にも。続けて全体の停止の Issue と `halt` の印）

### 決定 2：見つかりの記録は、作業の単位の Issue の `security` の印と `halt` の印の両方を書けたときに消し、書けなければ次の実行が書き直す

- 見つかりの記録を消すのは、見つけた作業の単位の Issue の `security` の印と、`issue` が作業の単位の番号の `halt` の印（全体の停止の Issue に書いたもの）の両方を書けたときだけ。PR の `security` の印は、書けなくても記録を消す妨げにしない（安全の軸の値と全体の停止は、Issue の印と全体の停止の Issue で決まるため）
- 見つけた実行で両方を書けなかったときは、見つかりの記録を残したまま終える。次の実行のうち、1 回の実行の流れの順 6〜9 に進む実行（定期と手動。待つ時間を過ぎた点検の依頼で、定期の実行として続ける実行を含む）が、状態を組み立てた後、作業の単位を進める前に、見つかりの記録から `security` の印と全体の停止の Issue（`halt` の印）を書き直す。書き直す時と場所は、開き直し（`security` の印を書けた後に全体の停止の Issue を開けなかったとき）と同じにする
- 書き直しでは、記録した `where` と `finding` と場所で `security` の印を新しく書く。前の実行で届いたか分からなかった印が実際には届いていても、もう一度書く。最新の `security` の印より後の `## 安全の確認` で値を外す決まり（[ADR-20261024-005][adr-security] の決定 2）なので、重ねて書くと値は外れない側に倒れる
- 見つけた作業の単位の Issue が当てる先のリポに無くなった（消えた、別のリポに移された）ときは、`halt` の印を書けたら見つかりの記録を消す。全体の停止は全体の停止の Issue で人が確かめて解き、当てる先のリポに無い Issue は作業の単位にならないため
- 順 6〜9 に進まない点検の依頼の実行と、受け入れの依頼の実行は、見つかりの記録を読んで AI のセッションを起こさないが、書き直さず、記録も消さない（開き直しを書かないのと同じ。受け入れの依頼の実行は GitHub に何も書かない。[ADR-20261022-004][adr-intake-req] の決定 2）
- 書き直した印も、[ADR-20261101-002][adr-notify] のとおり、書けた印ごとに GitHub の外へ通知する

### 決定 3：見つかりの記録は止める側にだけ使い、読めなければあるものとし、ある間は人に示す

- 見つかりの記録で決めるのは、AI のセッションを起こさないことと、印を書き直すことだけ。作業の単位の状態、安全の軸の値、全体の停止の解き方は、今のとおり GitHub の印だけで決める。見つかりの記録が無いことを、全体の停止を解く理由にしない
- 見つかりの記録を読めない（中身が壊れている）ときは、あるものとして AI のセッションを起こさない。書き直す中身が分からないので、~~点検の fail に出し~~、記録のファイルの場所と戻し方（人が、実行の記録と GitHub で見つけた作業の単位を確かめてから記録を消す。確かめ方は基本設計で決める）を示す。中身を読めない lock を人が確かめて消す形（基本設計の「[状態遷移と判定][design-flow]」の「lock の取り方」）と同じにする
  **訂正（2026-11-11）**: 「点検の fail に出し」は、下の「影響」の「AI を使わない工程は止めず」「AI のセッションが止まり続ける」と食い違っていた。点検に fail が 1 つでもあれば作業に入らない（要件の SETUP-2）ので、fail に出すと AI を使わない工程まで止まる。メンテナの決定で、読めない記録は点検の warn に出し、AI のセッションだけを起こさない形と読む。読めなければあるものとして AI のセッションを起こさないことと、人が確かめてから消すことは変わらない
- 見つかりの記録がある間は、点検の warn と状態の表示（`status.json`、`/dev-autopilot`）に、見つけた作業の単位の Issue の番号と、次の定期の実行が GitHub に印を書き直すことを出す
- 記録の置き場を失ったときは、[ADR-20261015-006][adr-flow] の決定 4 の記録の目印のファイルで見つける（点検が fail にし、人が `setup` をやり直す）。見つかりの記録のファイルの名前・形・書き方（排他と一時のファイル）は、基本設計と詳細設計で決める

### 影響（Consequences）

- 良い点（安全が上がる）: 見つけた後に `security` の印を書けなかった理由を問わず、次の実行が AI のセッションを起こす前に止まる。PR にだけ印を書けたときも、Issue の印と `halt` の印を書けるまで止まり続ける。書く前に実行が切れたときも、記録を書く前に切れた場合を除いて止まる
- 良い点（正本と人の戻し方を保つ）: 印は次の実行が GitHub に書き直すので、人は今と同じく、全体の停止の Issue と作業の単位の Issue で確かめて `## 安全の確認` を書けばよい。マシンの上の操作は、記録が壊れたときだけに要る
- 良い点（動き続ける）: AI を使わない工程は止めず、GitHub の不調か合図が戻った後の定期の実行が、人の手を借りずに印を書き直す
- 悪い点（確かめやすさが下がる）: 止めるかの判定の入力に、GitHub の印のほかに手元のファイルが 1 つ加わる。単体テストと結合テストの組み合わせが増える
- 悪い点（運用のしやすさが下がる）: 見つかりの記録が壊れると、人がマシンの上でファイルを確かめて消すまで、AI のセッションが止まり続ける
- 悪い点（安全の残り）: 見つかりの記録を書く前に実行が切れたときと、人かほかのプロセスが記録のファイルだけを消したときは、今と同じ隙間が残る
- 悪い点: 届いたか分からなかった印が実際には届いていたとき、次の実行が `security` の印を重ねて書く。見つけた実行と次の実行の間に人が `## 安全の確認` を書いていれば、人はもう一度書くことになる

### 確認方法（Confirmation）

- 単体テストで、全体を止めるかの決め方を確かめる。見つかりの記録がある・無い・読めないの 3 つと、全体の停止の Issue の有無を組み合わせ、記録が無ければ GitHub の印だけで決まること
- 単体テストで、見つかりの記録を消す条件（Issue の `security` の印と `halt` の印の両方。PR の印は問わない。Issue が当てる先のリポに無ければ `halt` の印だけ）を確かめる
- 結合テスト（偽の GitHub と偽の `claude`）で、次を確かめる
  - `security` の印の書き込みを断らせると、次の実行は点検の試しとどの作業の単位の AI のセッションも起こさず、組 1 の前に `security` の印と全体の停止の Issue を書き、見つかりの記録を消す
  - 合図を `stop` にして書き込みを見送らせ、`run` に戻した後の実行でも、同じく止まって書き直す
  - PR の `security` の印だけを書かせたときも、次の実行が Issue の印と `halt` の印を書くまで止まる
  - 点検の依頼の実行と受け入れの依頼の実行は、見つかりの記録があれば試しのセッションと受付 AI を起こさず、GitHub に書かず、記録を消さない

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：全体の停止の Issue と `halt` の印を先に書き、`security` の印を後に書く

- 良い点（安全が上がる）: 全体の停止の Issue を書けて `security` の印だけを書けなかったときは、次の実行も止まる（案 D・E では止まらない）
- 中立: 手元の記録を判定に使わず、止める事実はいつも GitHub にある（案 D・E も同じ）
- 悪い点（安全の隙間が残る）: GitHub に書けない間（両方とも断られる、届かない）、合図が `run` でない間、書く前に実行が切れたときは、どちらの印も無く、次の実行で AI のセッションを起こしうる
- 悪い点（安全が下がる）: `security` の印を書けないまま人が全体の停止を解くと、見つけた作業の単位に値が無く、作業の単位の `## 安全の確認` を経ずに AI が進む。防ぐには、安全の軸を `halt` の印からも決める形と、開き直しの条件を逆向きにする形が要り、[ADR-20261024-005][adr-security] の決定 2 と設計の読み方も変わる

### 案 B：見つけたら手元に記録を残し、記録がある間は全体を止め、次の実行が印を書き直せたら記録を消す

- 良い点（安全が上がる）: 書けなかった理由を問わず、次の実行が AI のセッションを起こす前に止まる。案 A・D・E では、合図が `run` でない間と、書く前に実行が切れたとき（記録を書いた後）に止まらない（案 C も止まる）
- 良い点（動き続けることと、正本と人の戻し方を保つ）: 案 C と違い、AI を使わない工程を止めず、印は次の実行が書き直すので、GitHub の不調か合図が戻れば、人の手当てなしで正本が GitHub に載る。人は GitHub の画面で確かめて解ける
- 中立: 手元の記録で AI のセッションを起こさない側に倒す形は、1 日の利用枠（[ADR-20261015-006][adr-flow] の決定 4 の (d)）にすでにある
- 悪い点（確かめやすさが下がり、費用が上がる）: 判定の入力に手元のファイルが加わり、[ADR-20261015-006][adr-flow] の決定 4 と [ADR-20261024-005][adr-security] の決定 3 を改める。記録から印を書き直す処理も足す
- 悪い点（運用のしやすさが下がる）: 記録が壊れると、人がマシンの上で確かめて消すまで止まり続ける

### 案 C：書けなかった実行は、人が戻すまで次の実行を止める

- 良い点（費用が下がる）: 記録から GitHub に印を書き直す処理を持たない
- 悪い点（動き続けることが下がる）: AI を使わない工程（検疫、表示の欄、マージの判定、片付け）まで止まり、SAFE-19 の「AI を使わない工程は続ける」と合わない
- 悪い点（正本と人の戻し方が下がる）: 印は人が戻すまで GitHub に載らず、人は見つけたことをマシンの記録と状態の表示で知り、マシンの上で戻す。スマートフォンの GitHub の画面からは戻せない
- 悪い点: lock は持ち主の PID が生きていなければ古い lock として奪われるので、lock を外さないだけでは止まらない。奪われない別のファイルが要り、手元の記録を判定に使う点は案 B と同じになる

### 案 D：隙間を残すと決め、点検の warn と GitHub の外への通知で知らせる

- 良い点（費用が最も下がる）: 足すのは、書けなかったことを点検と通知で示す処理だけで、止める決まりを足さない。得るものは費用の少なさだけ
- 悪い点（安全の隙間が残る）: 人が気づいて合図を `stop` にするまで、次の実行がほかの作業の単位で AI のセッションを起こす。SAFE-19 の全体の停止が、書き込みの失敗の後は効かない
- 悪い点: 印を書けなかったときの通知は、GitHub に正本の無い知らせになり、[ADR-20261101-002][adr-notify] の「印を書いた後にだけ送る」を改める。GitHub がつながらないときは、通知の送り先にも届かないことがある。次の実行の点検の warn に出すにも、書けなかったことを手元に残す必要がある（判定には使わない）

### 案 E：同じ実行の中で、時間の上限の内に書き直しを重ねる

- 良い点（安全が少し上がる）: 一時的に断られたときは、見つけた実行の中で印が GitHub に載り、GitHub の外への通知も次の実行を待たずに届く
- 中立: 承認済みの ADR を改めない（案 D も同じ）
- 悪い点（安全の隙間が残る）: 合図が `run` でない間、書く前に実行が切れたとき、GitHub の不調が続くときは塞がらない
- 悪い点（動き続けることが下がる）: GitHub が不調な間に、実行が書き直しの待ちで長くなる。案 B と組めば次の実行が書き直すので、同じ実行で重ねる要は無い
