# 書かずに試すのは受け入れ工程（段階 4）だけにし、試した下書きは同じ文の間は作り直さず、試した回の費用を Issue の累計に数えない

要件の UNDECIDED-60（書かずに試す間（`dryRun`）に、何を確かめ、どう数えるか）を決める。

改める決定と、据え置く決定は次のとおり。

- [ADR-20261015-006][adr-flow]：決定 4 の「判定には、手元の記録を使わない」に、書かずに試す間だけの例外（本 ADR の決定 2 と決定 3）を足す。書き始めた後（`run.dryRun` が `false`）の判定は、今のとおり GitHub の状態と印だけから決める。決定 4 の数え上げの (a)〜(d) と、記録を失ったときの扱いは据え置く。本 ADR の決定 4 で、(a) と (c) から書かずに試した回を除く
- [ADR-20261017-007][adr-stop]：書かずに試す合図をリポの設定に置き、`false` にする（書き始める）のを PR に残すことは据え置く
- [ADR-20261020-002][adr-app]：書き始める前に GitHub App に切り替えることは据え置く

## 背景と課題（Context and Problem Statement）

- 「運用の規則」は、書かずに試す合図（`run.dryRun`）が `true` の間、GitHub への書き込みをすべて手元の記録に「書くつもりだった内容」として残し、読むことと AI のセッションは行うとする。使う場面は、受け入れ工程（段階 4）の最初と、新しい段階に入るとき
- 段階の表は、受け入れ工程（段階 4）の最初に、下書きと選定の結果を手元の記録にだけ書いて人が読むとする。異議は、記録の置き場のファイルに `## 異議` の見出しで書き足し、段階 4 の出口で数える
- 判定には手元の記録を使わない（[ADR-20261015-006][adr-flow] の決定 4）。書かずに試す間は印を書かないので、基本設計の再レビュー（2026-10-20）で、次のことが起きると分かった
  - 受け入れの印も `intake-final` の印も書かないので、選定（候補の条件を満たすか。FLOW-1）まで進まず、選定の結果が出ない
  - 毎回の実行で、Issue の番号の小さい `limits.intakePerRun` 件を受け入れ直し、ほかの Issue には下書きが出ない
  - 受け入れ直した回の費用が Issue の累計に入る。受け入れ工程（段階 4）の 1 Issue の累計の上限（`limits.issueCostUsd`）は 2 USD で、起動の前に 1 セッションの上限（1 USD）を足して比べるので、書き始めた後に、一度も投稿していない Issue が `usage-limit` で止まりうる
  - 人が手元の記録の下書きを読んで `agent-ready` を付けると、GitHub に受け入れの印が無いので、書き始めた最初の実行で `approved-before-intake` で止まる
  - 計画・実装工程（段階 5）より後の段階で書かずに試すと、計画の印を書かないので、毎回同じ Issue の計画をやり直し、実装に届かない
- 計画・実装工程（段階 5）より後の段階には、段階ごとに記録だけに残す仕組みがある（計画のレビューの結果、修正工程（段階 7）の shadow 判定、レビュー工程（段階 6）の見落としの軸）。着手は 1 回の実行で 1 件、進行中の Issue は 1 件までで（FLOW-3）、人が計画をすべて読む（段階の表）

課題：書かずに試す間に、何を確かめられるようにするか。書かずに試した回を、書き始めた後の判定と上限にどう持ち込まないか。

## 判断の決め手（Decision Drivers）

- 書かずに試す間に、人が、受け入れる Issue すべての下書きと選定の結果を読めること（段階の表の受け入れ工程（段階 4））
- 書かずに試した回が、書き始めた後の判定と上限を狂わせないこと（一度も投稿していない Issue が累計の上限で止まらない、`approved-before-intake` で止まらない）
- 書き始めた後の判定は、GitHub の状態と印から決める決まり（FLOW-4、[ADR-20261015-006][adr-flow] の決定 4）を崩さないこと
- 記録を失ったときに、受け入れを黙って飛ばす側に倒れないこと（フェイルセーフ）
- 実行を重ねるたびに、同じ Issue に利用枠を使わないこと

## 検討した選択肢（Considered Options）

- 案 A：書かずに試すのは受け入れ工程（段階 4）だけにする。書かずに試す間だけ、書くつもりだった受け入れの下書きを、同じ文の間は書いたものとして扱い、受け入れの相手を選ぶときと選定の結果を作るときに使う。試した回の費用は Issue の累計に数えない
- 案 B：今の基本設計のまま、毎回受け入れ直す。利用枠は `limits.intakePerRun` と費用の上限で抑える
- 案 C：書かずに試す間も、印だけは GitHub に書く
- 案 D：書くつもりだった内容をすべて GitHub の状態に重ねて読み、どの段階でも書かずに試せるようにする
- 案 E：書かずに試さず、受け入れ工程（段階 4）の最初から GitHub に書く

## 決定（Decision Outcome）

> **［2026-10-24 追記・supersede］** 本 ADR の決定 1〜4 は、[ADR-20261024-002][adr-20261024-002] で置き換えた。書かずに試すこと（`run.dryRun`）は持たず、進行 Bot は最初の実行から当てる先のリポに書く。GitHub App には、当てる先のリポに初めて書く前に切り替える（[ADR-20261024-002][adr-20261024-002] の決定 2）。以下の記述は当時の決定の記録として残す。

採用した選択肢:「案 A」。
理由: 手元の記録を判定に使う範囲を、書かずに試す間の受け入れだけに絞れる。実行を重ねると、すべての Issue に下書きと選定の結果が出る。書き始めた後の判定と上限は、書かずに試した回に左右されない。段階 5 より後の段階は、段階ごとの記録だけの仕組みと 1 件ずつの着手で、書く前に確かめる役を果たせる。

### 決定 1：書かずに試すのは、受け入れ工程（段階 4）だけにする

- `run.dryRun` を `true` にしてよいのは、`run.stage` が受け入れ工程（段階 4）のときだけにする。計画・実装工程（段階 5）より後の段階に入るときは、書かずに試さない
- 新しい段階は、段階の表のとおり、段階ごとに記録だけに残す仕組みと、1 件ずつの着手（FLOW-3）と、人が計画と PR を読むことで始める
- 毎回の点検は、`run.dryRun` が `true` で `run.stage` が受け入れ工程（段階 4）でなければ fail にして、作業に入らない。印を書かないまま計画をやり直し続けて、利用枠を使わないため

### 決定 2：書かずに試す間は、同じ文の Issue を受け入れ直さない

- `run.dryRun` が `true` の間だけ、進行 Bot は、手元の記録にある「書くつもりだった受け入れの下書き」を、同じ Issue で、受け入れに使う文（題名・本文・コメント）のハッシュが同じ間は、書いたものとして扱う。扱うのは、受け入れの相手を選ぶとき（次の工程の表の受け入れ）と、選定の結果を作るとき（決定 3）だけ
  - 書くつもりだった `needs-human`（検疫で見つかった、実行の失敗が `limits.retry.count` 回続いた）も、同じハッシュの間は書いたものとして扱い、受け入れ直さない
  - 受付 AI が拒否した Issue は、今のとおり実行の失敗として扱い、次の実行で `sonnet` で受け入れ直す（IMPL-29）
  - 文が変われば（ハッシュが違えば）、受け入れ直す。人が Issue を直したときの下書きも読める
- 受け入れの相手の順は今のとおり Issue の番号の小さい順で、1 回の実行の件数の上限（`limits.intakePerRun`）まで。書いたものとして扱う Issue を除くので、実行を重ねると、番号の大きい Issue にも下書きが出る
- 手元の記録が無いとき（失ったとき）は、書いたものとして扱う下書きが無いので、受け入れ直す。利用枠は、`limits.intakePerRun` と、1 回の実行と 1 日の費用の上限で抑える
- `run.dryRun` が `false` の実行は、書くつもりだった内容を読まない。書き始めた最初の実行からは、GitHub に受け入れの印が無い Issue を、改めて受け入れる。書かずに試した下書きは投稿しない（投稿する下書きは、投稿する実行の検疫と受付 AI で作る）

### 決定 3：書かずに試す間の選定の結果は、人の承認の条件を除いて作る

- 書いたものとして扱う下書きがある Issue について、候補の条件（FLOW-1）から、人の承認にかかわる条件（`agent-ready` があること、`agent-ready` を付けた人の権限、受け入れの下書きがあり人が `agent-ready` を付けていること）を除いたものを確かめる。
  満たすか、どの条件で外れたか、満たす Issue を着手する順を、手元の記録にだけ残す。人は、下書きと合わせて選定の結果を読む
- 書かずに試す間は、人は `agent-ready` を付けない。付けた Issue は、今のとおり `approved-before-intake` で `needs-human` にする（書くつもりだった内容として記録に残り、書き始めた最初の実行で GitHub に書く）。人は、書き始めた後に GitHub に出た下書きを読んでから `agent-ready` を付ける

### 決定 4：書かずに試した回の費用と失敗は、書き始めた後の上限に数えない

- 書かずに試す間の AI のセッションの費用は、1 回の実行の上限（`limits.runCostUsd`）と 1 日の上限（`limits.dailyCostUsd`）に数える。利用枠は実際に使うため
- 1 Issue の累計（`limits.issueCostUsd`）には数えない。書かずに試した下書きは投稿せず、書き始めた後に受け入れ直すので、数えると、一度も投稿していない Issue が累計の上限で止まりうるため
- 同じ Issue で続いた実行の失敗の回数（IMPL-14）は、書かずに試す間の `needs-human` の扱い（決定 2）にだけ使い、書き始めた後の回数には数えない
- 受付 AI の拒否の記録（IMPL-29）は、書き始めた後も使う。同じ文で拒否された `haiku` を、書き始めた後にもう一度使わないため
- 手元の記録には、AI のセッションごとと実行ごとに `run.dryRun` の値を残し、数えるときに書かずに試した回を見分ける

### 影響（Consequences）

- 良い点: 実行を重ねると、番号の大きい Issue にも下書きが出る。人は、受け入れる Issue すべての下書きと選定の結果を読める
- 良い点: 書き始めた後の判定は、今のとおり GitHub の状態と印だけで決まる。書かずに試した回の費用と失敗で、Issue が止まらない
- 良い点: 記録を失っても、受け入れ直す側に倒れ、受け入れを黙って飛ばさない
- 悪い点: 書かずに試す間だけ、手元の記録を判定に使う例外ができる（受け入れの相手と選定の結果に限る）
- 悪い点: 書き始めた後に、すべての Issue を受け入れ直すので、受け入れの利用枠を 2 回使う
- 悪い点: 計画・実装工程（段階 5）より後の段階に入るとき、GitHub に書く前に試す手段が無くなる。段階ごとの記録だけの仕組みと、1 件ずつの着手と、人が読むことで代える
- 中立: 書かずに試す間の 1 回の実行と 1 日の費用は、今のとおり上限に数える

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 書くつもりだった下書きを、同じ文のハッシュの間だけ書いたものとして扱い、ハッシュが変われば受け入れ直すこと
  - 記録が無ければ受け入れ直すこと
  - `run.dryRun` が `false` なら、書くつもりだった内容を読まないこと
  - 選定の結果から、人の承認の条件を除くこと
  - 1 Issue の累計と実行の失敗の回数から、書かずに試した回を除くこと
- 結合テストで、書かずに試す実行を 2 回通し、2 回目が 1 回目と別の Issue を受け入れること、`run.dryRun` を `false` にした最初の実行が、受け入れの印が無い Issue を受け入れ直すことを確かめる
- 点検の単体テストで、`run.dryRun` が `true` で段階 4 でなければ fail にすることを検査する

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：段階 4 だけ、書くつもりだった下書きを同じ文の間は書いたものとして扱う

- 良い点: すべての Issue に下書きと選定の結果が出る
- 良い点: 手元の記録を判定に使う範囲が、書かずに試す間の受け入れだけに絞られる
- 悪い点: 段階 5 より後の段階で、書く前に試せない

### 案 B：毎回受け入れ直す

- 良い点: 手元の記録を判定に使わない決まりに、例外が要らない
- 悪い点: 番号の大きい Issue に下書きが出ない。選定の結果が出ない
- 悪い点: 受け入れ直した回の費用が Issue の累計に入り、書き始めた後に `usage-limit` で止まりうる

### 案 C：印だけは GitHub に書く

- 良い点: 判定は GitHub の印から決まり、手元の記録の例外が要らない
- 悪い点: 印は下書きのコメントに載せる形で、下書きを書かずに印だけを書く形が無い。印を書くと、人が読む前の下書きの代わりのコメントが Issue に出る
- 悪い点: GitHub App に切り替える前に書くことになり、PAT のアカウントの印が残る（[ADR-20261020-002][adr-app] の、書き始める前に切り替える前提が崩れる）

### 案 D：書くつもりだった内容をすべて重ねて読む

- 良い点: どの段階でも書かずに試せる
- 悪い点: GitHub の状態と書くつもりだった内容の 2 つを重ねて判定する仕組みを、すべての工程に持つ。判定が 2 通りになる
- 悪い点: 段階 5 より後は、PR と push を書かないと、レビューと修正に進めない

### 案 E：書かずに試さない

- 良い点: 仕組みが増えない
- 悪い点: 下書きの質と検疫の漏れを、人が読む前に Issue に出す。公開のリポでは、誰でも読める
