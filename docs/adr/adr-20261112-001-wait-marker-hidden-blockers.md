# App から見えない依存の相手で待つときは、wait の印に見えない相手の数を書き、番号の並びと数の組で同じ相手かを比べる

要件の UNDECIDED-101（依存の相手が App から見えないだけで先の依頼の軸を未完了にしたときに、`wait` の印をどう書くか。[決めていないこと][undecided]の「ADR で決めること」の「作業の単位の状態遷移」）を決める。

改める決定と、据え置く決定は次のとおり。

## 背景と課題（Context and Problem Statement）

- FLOW-10 と FLOW-43 は、先の依頼（blocked by）で待つ作業の単位を、先の依頼の軸を未完了にして表し、Issue に 1 回だけコメントするとする。1 回かどうかは `wait` の印で判定する。止め方は停止中にしない（[01-issue-flow.md][f01]）
- `wait` の印の欄は `blockedBy`（先の Issue の番号の並び）だけで、「1 回だけ書く」印は、同じ種類で同じ相手の有効な印があれば書かない。`wait` の相手は `blockedBy` で比べる（要件の「[印と固定の見出しの一覧][f04]」、[ADR-20261024-001][adr-model-states] の決定 9）。詳細設計は、`blockedBy` を 1 つ以上の番号の並びとする（「[印][d-markers]」の「欄の値の形」）
- 進行 Bot の App は、当てる先のリポだけに入る（[ADR-20261020-002][adr-app] の決定 2）。App のトークンで読むと、App から見えないリポにある依存の相手は、エラーにならずに依存の一覧から消え、番号が分からない。相手の数だけが GraphQL の `issueDependenciesSummary` の `totalBlockedBy` に残る（[FACT-143][facts]）。閉じた相手も一覧と `totalBlockedBy` に残り、App のトークンでも `totalBlockedBy` は見えない相手を数える（[FACT-150][facts]）
- 詳細設計（「[1 回の実行の流れ][d-flow]」で、「GitHub の事実の読み方」にある依存の相手の行）は、一覧の件数（`totalCount`）が `totalBlockedBy` より少なければ見えない相手があるとして、先の依頼の軸を未完了にする（止める側）。見えない相手は閉じても数え続けるので、人が依存を外すか、相手を当てる先のリポに移すまで未完了のまま。見えない相手の数は、`runs.jsonl` に、作業の単位の結果（待たせた理由）としてだけ書く
- 見えない相手だけで未完了になると、`wait` の印の `blockedBy` に書く番号が無い
  - 印を書かなければ、FLOW-10 の 1 回のコメントが無くなる。人は Project の「先の依頼」の欄で未完了を見ても、待つ理由を GitHub で読めない
  - 空の並びで書けば、形に外れた印になる。次の実行が無効な印（`shape`）と読み、作業の単位を停止中（`marker-invalid`）にする（基本設計の「[状態遷移と判定][design-flow]」にある「先に見る」の順 5（無効な印で止める）、IMPL-20）
  - 見える相手と見えない相手が混じるときも、見えない相手の分を印に表す欄が無い。見えない相手の数が変わっても、`blockedBy` が同じなら新しいコメントを書かない
- 導入と点検の実装（段階 3）の一度だけの試しを設計に反映した後、確かめ直したとき（2026-11-12）の指摘 M-4（元の指摘 R1-1）で見つけた

課題：App から見えない依存の相手があるときに、`wait` の印にどの欄を持たせ、同じ相手かをどう比べるか。

## 判断の決め手（Decision Drivers）

- 人の戻し方（運用のしやすさ）：見えない相手での待ちは、進行 Bot が相手の終わりを読めないので、人が依存を外すか相手を当てる先のリポに移すまで終わらない。人がマシンの前にいなくても、GitHub の画面で、待つ理由とすることを知れる
- 動き続けること：人の操作が少なく、人が依存を外せば次の実行で続く
- 確かめやすさ：同じ相手かを印の欄だけで決められる。書く側の誤りを、印の形の確かめで見つけられる
- 費用：改める要件と承認済みの ADR と、足す処理が少ない
- 制約：App は当てる先のリポだけに入れる（[ADR-20261020-002][adr-app] の決定 2）。進行 Bot の印は、形か署名が合わなければ無効で、作業の単位を止める（IMPL-20）。FLOW-10 は、先の依頼で待つ作業の単位を停止中にしない

## 検討した選択肢（Considered Options）

- 案 A：`wait` の印に、App から見えない相手を数える欄（`hidden`）を足し、同じ相手かを `blockedBy` の番号の集合と `hidden` の組で比べる
- 案 B：見えない相手だけで待つときは、`wait` でなく停止中にし、人が依存を確かめて戻す
- 案 C：見えない相手があるときは、`wait` の印もコメントも書かず、`runs.jsonl` だけに残す（FLOW-10 の例外）
- 案 D：欄を足さず、見えない相手があるときだけ `blockedBy` の空を許し、同じ相手かは今のとおり `blockedBy` で比べる

## 決定（Decision Outcome）

採用した選択肢:「案 A」。

理由: 見えない相手だけのときも FLOW-10 の 1 回のコメントを保ち、待つ理由（見えない相手の数）と人がすることを GitHub に残せる。見えない相手の数が変わったときも、新しいコメントで人に知らせる。待つ理由の全体が印に残るので、同じ相手かを印の欄だけで比べ、理由の無い空の `blockedBy` を印の形の確かめで止められる。
案 B は、人の操作が依存を外すことと `## 再開` の 2 つになり、FLOW-10 の「止め方は停止中にしない」を改める。案 C は、待つ理由が GitHub に残らない。案 D は、見えない相手の数が変わっても新しいコメントを書かず、待つ理由の数が印に残らない。

### 決定 1：`wait` の印に、App から見えない依存の相手を数える欄 `hidden` を足す

- `wait` の印の欄は、`blockedBy`（終わっていない先の Issue のうち、依存の一覧で番号が分かるものの番号の並び）と、`hidden`（App から見えない依存の相手の数。0 以上の整数）の 2 つにする
- `hidden` は、依存の数（`issueDependenciesSummary` の `totalBlockedBy`）から依存の一覧の件数（`totalCount`）を引いた数とする。見えない相手は終わったかを読めないので、閉じた相手も数える（[FACT-150][facts]）。読み方は、詳細設計の「[1 回の実行の流れ][d-flow]」で依存の相手の行に書いたとおり
- `blockedBy` は、`hidden` が 1 以上のときだけ空を許す。`hidden` が 0 なら、今のとおり 1 つ以上の番号を持つ。`blockedBy` と `hidden` の組み合わせは、印の形として確かめる（`blockedBy` が空で `hidden` が 0 の印は、形が合わない）
- `hidden` は、進行 Bot の最初の版から必ずある欄として足す。`wait` の印を書く版をまだ出していないので、`hidden` が無い、前の版が書いた印を読む決まり（詳細設計の「[印][d-markers]」にある「前の版の印では無くてよい」欄）は要らない
- 先の依頼の軸が取る値と線は変えない。見えない相手があれば、今のとおり未完了（D1）にする

### 決定 2：同じ相手かは、`blockedBy` の番号の集合と `hidden` の組で比べる

- 「1 回だけ書く」印の判定では、`wait` の同じ相手を、`blockedBy` の番号の集合と `hidden` の数の両方が同じことと読む。両方が同じ有効な `wait` の印が作業の単位の Issue にあれば書かず、無ければ書く
- 見えない相手の数が変わったとき（人が見えない相手の依存を足した、外したなど）は、`blockedBy` が同じでも、新しい `wait` の印とコメントを書く
- ほかの「1 回だけ書く」印（`overlap`・`remind`・`ignored-instruction`）の比べ方は変えない

### 決定 3：`hidden` が 1 以上なら、`wait` の印を付けるコメントに、見えない相手の数と人がすることを書く

- `hidden` が 1 以上のときは、`wait` の印を付けるコメントの決まった文に、App から見えないリポにある先の依頼の数と、人がすること（依存を外すか、相手を当てる先のリポに移す）を書く。進行 Bot は見えない相手が終わったかを読めず、人が依存を外すか相手を移すまで待ち続けるため
- 見えない相手のリポと番号は、App から読めないので書かない。文の言い回しは、詳細設計の決まった文（`logic/text/comments.ts`）で決める

### 影響（Consequences）

- 良い点（人の戻し方が上がる）: 見えない相手だけで待つ作業の単位にも、待つ理由と人がすることを書いたコメントが 1 回つく。人は GitHub の画面だけで、依存を外すか、相手を移すかを決められる
- 良い点（確かめやすさが上がる）: 同じ相手かを、印の 2 つの欄だけで決められる。理由の無い空の `blockedBy`（`hidden` が 0）を、印の形の確かめで見つけられる
- 悪い点（費用が上がる）: 要件の「印と固定の見出しの一覧」の `wait` の行と「1 回だけ書く」印の決まり、[ADR-20261024-001][adr-model-states] の決定 9 の表、基本設計と詳細設計の数か所を直す。印の形を確かめるテストと、比べ方のテストが増える
- 悪い点（人の戻し方に隙間が残る）: 見えない相手で待つ作業の単位は、人が依存を外すか相手を移すまで未完了のままで、止め方の停止中のビューには出ない（今の設計と同じ）。人は、コメントか、Project の「先の依頼」のビュー（FLOW-39）で気づく
- 悪い点: 見えない相手の数は、どの相手かを表さない。2 回の実行の間に、見えない相手の依存が 1 つ外れ、別の見えない相手の依存が 1 つ足されると、数が同じなので新しいコメントを書かない

### 確認方法（Confirmation）

- 単体テスト（`marker.ts`）で、`wait` の印の形を確かめる。`blockedBy` が空で `hidden` が 1 以上の印（見えない相手だけ）と、`blockedBy` と `hidden` の両方が 1 以上の印（混じり）を、形が合うとすること。`blockedBy` が空で `hidden` が 0 の印、`hidden` の無い印、`hidden` が負の数か整数でない印を、形が合わないとすること
- 単体テスト（`logic/state/next.ts`）で、`wait` の印を書くかを確かめる。`blockedBy` の集合と `hidden` の組が同じ有効な印があれば書かず、見えない相手だけのとき、混じりのとき、見えない相手の数が変わったときに書くこと
- 単体テスト（`logic/text/comments.ts`）で、`hidden` が 1 以上のときだけ、決まった文に見えない相手の数と人がすることが入ること
- 結合テスト（偽の GitHub）で、App から見えない相手だけを持つ依存の答え（一覧に出さず、`totalBlockedBy` にだけ数える）を 2 回の実行で読ませ、`wait` の印とコメントが 1 回だけ書かれ、作業の単位が `marker-invalid` で止まらないこと。依存を外した答えに変えると、次の実行で先の依頼の軸が（なし）に戻ること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：`wait` の印に見えない相手を数える欄 `hidden` を足し、番号の集合と数の組で比べる

- 良い点（人の戻し方が上がる）: 見えない相手の数が変わったときも、新しいコメントで知らせる（案 D は、`blockedBy` が同じなら知らせない。案 C は、コメントを書かない）
- 良い点（確かめやすさが上がる）: 待つ理由の全体（番号と数）が印に残り、同じ相手かを印だけで比べられる。`blockedBy` の空を `hidden` が 1 以上のときに限る形を、印の形の確かめで守れる（案 D は、空の `blockedBy` が見えない相手によるものかを形で確かめられない）
- 中立: 先の依頼の軸で待ち続けるので、人が依存を外せば `## 再開` なしに次の実行で続く（案 C・D も同じ。案 B は `## 再開` も要る）
- 悪い点（費用が上がる）: 印に欄を 1 つ足すので、要件の印の表と「1 回だけ書く」印の決まり、[ADR-20261024-001][adr-model-states] の決定 9 の表を改める（案 D は改めない）
- 悪い点（人の戻し方が下がる）: 人が依存を外すまで終わらない待ちが、止め方の停止中のビューに出ない（案 B は出る）

### 案 B：見えない相手だけで待つときは停止中にし、人が依存を確かめて戻す

- 良い点（人の戻し方が上がる）: 見えない相手での待ちは、人が依存を外すか相手を移すまで終わらない（[FACT-150][facts]）ので、人が対処する意味の停止中（FLOW-10）に合う。人は、止め方のビューと止めた理由のコメントで、人の番として見つけられる
- 悪い点（動き続けることが下がる）: 人の操作が、依存を外すことと `## 再開` の 2 つになる。依存を外さずに `## 再開` を書くと、次の実行がまた止め、`stop` の印とコメントが増える
- 悪い点（費用が上がる）: FLOW-10 の「止め方は停止中にしない」と FLOW-43 を改め、止めた理由の記号を足す（FLOW-40、[ADR-20261024-001][adr-model-states] の決定 7）。[ADR-20261024-006][adr-cleanup] の決定 3 で、表の「ほか → 未完了のまま」にも、見えない相手だけのときの例外を足す
- 悪い点（人の戻し方が下がる）: 見える相手と見えない相手が混じるときは、今のとおり `wait` の印で待つので、見えない相手の分を印に表す欄が無いまま残り、見えない相手の数が変わっても知らせない
- 悪い点（確かめやすさが下がる）: 見える相手が終わると、待ちから停止中に変わる。見えない相手だけか、混じりかで、作業の単位の読み方と書く印が分かれ、テストの組み合わせが増える

### 案 C：見えない相手があるときは、`wait` の印もコメントも書かず、`runs.jsonl` だけに残す

- 良い点（費用が下がる）: 印の欄と形を変えず、承認済みの ADR の印の表を改めない（要件は、FLOW-10 の 1 回のコメントに例外を足す）。足す処理は、見えない相手があるときに `wait` の印を書かない分かれ道だけ。得るものは費用の少なさだけ
- 悪い点（人の戻し方が下がる）: 待つ理由が GitHub に残らず、マシンの `runs.jsonl` にしか無い。人が見えない相手を閉じても先の依頼の軸は未完了のまま（[FACT-150][facts]）で、理由が GitHub に無いので、人が依存を外す必要に気づきにくい
- 悪い点: 見える相手と見えない相手が混じるときも `wait` の印を書かないので、見える相手の番号も印に残らない。`wait` の印に書いた `blockedBy` の番号を、依存の相手が消されたかを引く手がかりに使う形（同じ日に起票した ADR-20261112-002 の推奨）が、混じるときに使えない

### 案 D：欄を足さず、見えない相手があるときだけ `blockedBy` の空を許す

- 良い点（費用が下がる）: 印の欄を変えない。要件の印の表（`blockedBy` に空を許すかを書いていない）と「1 回だけ書く」印の決まり、[ADR-20261024-001][adr-model-states] の決定 9 の表を改めずに済み、直すのは詳細設計の値の形（1 つ以上）と決まった文が主になる
- 中立: 見えない相手だけのときも、コメントを 1 回書き、決まった文に数を書ける（案 A と同じ）
- 悪い点（人の戻し方が下がる）: 見えない相手の数が変わっても、`blockedBy` が同じなら新しいコメントを書かない。見える相手と混じるときに、見えない相手の依存が足されても、外されても知らせない
- 悪い点（確かめやすさが下がる）: 待つ理由の数が印に残らず、空の `blockedBy` が見えない相手によるものかを印だけで確かめられない。書く側の誤りで空の `blockedBy` を書いても、印の形の確かめで見つけられない
