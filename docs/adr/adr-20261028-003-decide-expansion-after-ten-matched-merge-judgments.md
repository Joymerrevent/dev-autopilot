# ほかのリポへの適用と専用マシンへの移行は、マージの判定が直近 10 件で人の判断と一致し、revert が無くなってから決める

要件の UNDECIDED-82（ほかのリポへの適用と配布、1 台のマシンで複数のリポに当てる形、専用マシンへの移行を、いつ決めるか。[決めていないこと][undecided]の「ADR で決めること」の「流れと工程」）を決める。
UNDECIDED-82 の 3 つと同じ時期を目安にしていた UNDECIDED-21（クラウドの仕組み）と UNDECIDED-58（Docker のコンテナ）の決める時期も、本 ADR で決める。

| --- | --- | --- | --- |
| [ADR-20261016-003][adr-move]（基本設計の前に別のリポへ移す） | 一部を改める | 決定 2 の「段階 8 の出口を越え」と「段階 8 の後に決めるまで」を、本 ADR の決定 1 の条件に改める | 決定 2 のうち、設定ファイルの項目だけで別のリポに当てられると確かめてから決めること、決めるまで当てる先を business-os だけにすること、dev-autopilot 自身のリポに当てないこと。ほかの決定 |

## 背景と課題（Context and Problem Statement）

- [ADR-20261016-003][adr-move] の決定 2、[ADR-20261017-003][adr-plugin]、[ADR-20261021-005][adr-blocked]、要件の「[分離の時期の目安][structure]」とリポの CLAUDE.md は、ほかのリポへの適用と配布（marketplace への登録、skills CLI での `review` の単体導入。STRUCT-7）と、1 台のマシンで複数のリポに当てる形を、マージ判定工程（段階 8。進行 Bot が PR にマージの判定の印を書き始める段階）の出口を越えてから決めるとしていた。
  段階 8 の出口は、10 件で人のマージの判断と進行 Bot の判定が全件一致し、revert が 0 件になることだった
- [ADR-20261024-002][adr-no-stages] で段階 4〜8 を持たなくなり、段階の出口の数え上げも持たなくなった（決定 6）ので、決める時期が無くなった。決め直すまでは、当てる先は business-os だけのまま（2026-10-24 に 3 つの ADR に足した追記）
- UNDECIDED-21（クラウドの仕組みを、利用者のマシンの定期の実行の代わりか補助に使うか）と UNDECIDED-58（進行 Bot と AI のセッションを Docker のコンテナの中で動かすか）も、同じ時期を目安にしていた。UNDECIDED-71（専用マシンで進行 Bot を動かすときに、人の手元のマシンから受け入れの Skill を使う形）は、専用マシンに移すときに決める
- 段階が無くなった後も、進行 Bot は PR にマージの判定の印（`merge`）を書き、人のマージの判断との一致を運用の記録で数える（[MERGE-3][merge]、基本設計の「[運用の記録の数え方][design-flow]」の「マージの判定と人の判断の一致」）。
  マージの実行を進行 Bot に移すかの目安（[MERGE-9][merge]）は、段階 8 の出口と同じ数（10 件で全件一致し、revert が 0 件）を使っている
- revert は、マージから 14 日以内に、base ブランチにその squash の commit を revert する commit か、本文でその PR の番号を「戻す」と言及する fix の PR がマージされたもの（基本設計の「運用の記録の数え方」の「revert 率」）。
  要件の FLOW-13 は、revert 率を、進行 Bot のマージの判定を信頼してよいかと、ほかのリポに広げる時期の判断に使うとしている（[01-issue-flow.md][flow]）

課題：ほかのリポへの適用と配布、1 台のマシンで複数のリポに当てる形、専用マシンへの移行（と、同じ時期を目安にしていた UNDECIDED-21・58）を、どの条件を満たしたら決めるか。

## 判断の決め手（Decision Drivers）

- 当てる先を広げる前に、進行 Bot のマージの判定を信頼してよいかを、数で確かめる
- 決めた根拠が、運用の記録に残る
- 件数が少ないまま時期が来ることを避ける
- 新しい数を作らず、今まで合意していた数と、今ある数え方を使う

## 検討した選択肢（Considered Options）

- 案 A：マージの判定と人の判断の一致が、直近 10 件で全件一致し、その 10 件に revert が無くなったら決める（段階 8 の出口と、MERGE-9 と同じ数）
- 案 B：運用を始めてからの期間で区切る
- 案 C：条件を置かず、メンテナが決めたいときに決める

## 決定（Decision Outcome）

採用した選択肢:「案 A」。

理由: 進行 Bot のマージの判定を信頼してよいかを測る、今まで合意していた数をそのまま使える。数え方は基本設計の「運用の記録の数え方」にあり、新しい欄が要らない。案 B は件数が少ないまま期間が過ぎうる。案 C は判断の根拠が残らない。

### 決定 1：マージの判定と人の判断が直近 10 件で全件一致し、revert が無くなったら決める

- 基本設計の「運用の記録の数え方」の「マージの判定と人の判断の一致」で数えた PR のうち、直近の 10 件がすべて一致し、10 件のうちマージした PR が、どれもマージから 14 日を過ぎて revert が無いことを、決める時期の条件にする。不一致か revert があれば、その後の 10 件で数え直す
- 条件を満たしたら、メンテナが、ほかのリポへの適用と配布、1 台のマシンで複数のリポに当てる形、専用マシンへの移行を、それぞれ ADR で決める。条件を満たしても、自動では広げない（MERGE-9 と同じ）
- ほかのリポへの適用を決めるときは、今のとおり、設定ファイルの項目だけで別のリポに当てられると確かめてから決める（[ADR-20261016-003][adr-move] の決定 2）
- 決めるまでは、当てる先は business-os だけのまま。dev-autopilot 自身のリポに当てないことは変えない

### 決定 2：UNDECIDED-21 と UNDECIDED-58 も、決定 1 の条件を満たした後に決める

- クラウドの仕組み（UNDECIDED-21）と Docker のコンテナ（UNDECIDED-58）は、決定 1 の条件を満たした後、ほかのリポへの適用か専用マシンへの移行を決めるときに、一緒に決める。UNDECIDED-58 の目安（Linux か Windows のマシンに広げるとき、ほかの人に配るとき）は据え置く
- UNDECIDED-71 は、今のとおり、専用マシンに移すと決めたときに決める

### 影響（Consequences）

- 良い点: 決める根拠が、運用の記録の数で残る
- 良い点: 新しい数え方や欄を作らない（基本設計の「運用の記録の数え方」の 2 行で数える）
- 悪い点: 当てる先の PR が少ないと、条件を満たすまで長くかかる。不一致か revert が 1 件あれば、数え直す
- 悪い点: 条件を満たしたことに人が気づく仕組みは、まだ無い。気づかせ方（`/dev-autopilot` の状態の表示に件数を出す、など）は基本設計で決める
- 中立: 条件を満たしても、自動では広げない。広げ方は、そのときに ADR で決める

### 確認方法（Confirmation）

- 要件と設計への反映の後に、時期を「段階 8 の後」「段階 8 の出口」で書いた文が、要件・基本設計・図・リポの CLAUDE.md に残っていないことを grep で確かめる（承認済みの ADR の本文は、注記で示す）
- 条件を満たしたかは、基本設計の「運用の記録の数え方」の「マージの判定と人の判断の一致」と「revert 率」の数え方で数える

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：直近 10 件で全件一致し、revert が無くなったら決める

- 良い点: 進行 Bot のマージの判定を信頼してよいかを、今まで合意していた数で測れる。数え方は基本設計にある
- 悪い点: 当てる先の PR が少ないと、長くかかる

### 案 B：運用を始めてからの期間で区切る

- 良い点: いつ決めるかの見通しが立つ
- 悪い点: 件数が少ないまま期間が過ぎうる。期間の長さに根拠が無い

### 案 C：メンテナが決めたいときに決める

- 良い点: 決まりが増えず、事情に合わせて早くも遅くも決められる
- 悪い点: 判断の根拠が記録に残らない
