# 片付けの中で作業場所の確かめに外れたら workspace-tampered で止め、片付けをやり直さない条件をマージ済みか閉鎖済みに入った後の stop の印で決める

要件の UNDECIDED-87（片付けの中で作業場所の確かめに外れたときの止めた理由の記号と、片付けをやり直さない条件。[決めていないこと][undecided]の「ADR で決めること」の「作業の単位の状態遷移」）を決める。
本 ADR は、[ADR-20261024-006][adr-cleanup]（マージと中止の後は片付けの前の状態を挟んで進行 Bot が片付ける）を前提にする。

改める決定と、据え置く決定は次のとおり。

| ADR | 扱い | 改める決定 | 据え置く決定 |
| --- | --- | --- | --- |
| [ADR-20261024-006][adr-cleanup]（マージと中止の後の片付け、先の依頼、載せ直し） | 一部を改める | 決定 1 の「作業場所を消す前の確かめに外れたら、消さずに止める（止めた理由の記号は、実装の都合の記号として詳細設計で足す）」を決定 1 に、「片付けをやり直さないのは停止中（`cleanup-failed`）だけ（軸の値を問わず行う決まりの、ただ 1 つの例外）」を決定 2 に改める | 決定 1 のほかの項目（T27・T28 で片付ける、片付けは軸の値と全体の停止を問わず行う、軸の値を書き換えない、片付けが失敗し続けたら `cleanup-failed` で止める、片付けの後に人が Issue を開き直したときの読み方）。決定 2〜4 |
| [ADR-20261013-001][adr-workspace]（AI のセッションごとに新しい clone を作る） | 据え置く | — | 作業場所を消す前に、作ったときと同じかを確かめ、違えば消さないこと |

## 背景と課題（Context and Problem Statement）

- 片付け（T27・T28）は、軸の値（止め方・先の依頼・安全）と全体の停止を問わず行う。例外は、片付けが失敗し続けて止めた停止中（`cleanup-failed`）だけで、人が `## 再開` を書くまで片付けもやり直さない（[ADR-20261024-006][adr-cleanup] の決定 1）
- 片付けは、作業場所（セッションのフォルダ）を消す前に、`commondir` と `gitdir` が作ったときの値と同じかを確かめ、違えば消さずに止める（[ADR-20261013-001][adr-workspace]）。止めた理由の記号は、実装の都合の記号として詳細設計で足すとした
- 基本設計の「[状態遷移と判定][design-flow]」は、作業場所が作ったときと違うときを、どこで見つけても停止中（`workspace-tampered`。実装の都合の記号）にする。見つける場所は 3 つある：push の前の取り込み（objects の検査の失敗も含む）、戻した後に前の PR のフォルダを消すとき（先に見るの順 9）、片付け
- 片付けの中で `workspace-tampered` で止めると、片付けをやり直さない例外（`cleanup-failed` だけ）に当たらない。次の実行でも片付けをやり直し、同じ確かめに外れて止め直すので、`stop` の印が実行のたびに増える（2026-10-25 に、基本設計への反映の途中で見つけた）

課題：片付けの中で作業場所の確かめに外れたときに、どの記号で止めるか。片付けをやり直さない条件を、どう決めるか。

## 判断の決め手（Decision Drivers）

- 同じ出来事（作業場所が作ったときと違う）には、見つけた場所を問わず同じ記号を付ける。人の対応と、記号で数えることがまとまる
- 作業場所の作り替えは、AI のセッションが作業場所の外へ手を伸ばそうとした疑いで、運用の失敗とは人のすることが違う。攻撃の疑いを、運用の失敗に紛れさせない
- 片付けで止めたものは、人が確かめるまで、片付けで止め直さない（`stop` の印を増やさない）
- 人が、止まっている作業の単位の PR をマージしたか、Issue を閉じたときは、今までどおり片付ける（止め方を問わず片付ける決まりを崩さない）
- 片付けで止める理由が後で増えても、やり直さない条件を直さずに済む

## 検討した選択肢（Considered Options）

- 案 A：`workspace-tampered` で止め、片付けをやり直さない条件を、止めた理由の記号でなく、主な流れがマージ済みか閉鎖済みに入った後に書かれた `stop` の印で決める
- 案 B：片付けの失敗として、続いた回数を待たずに `cleanup-failed` で止め、やり直さない例外は今のまま（`cleanup-failed` だけ）にする
- 案 C：止め方でなく、安全の軸（攻撃の疑い）に値を入れる

## 決定（Decision Outcome）

採用した選択肢:「案 A」。

理由: 作業場所が作ったときと違うことに、見つけた場所を問わず同じ記号が付き、人は作り替えられた疑いとして調べられる。やり直さない条件を記号でなく「マージ済みか閉鎖済みに入った後の `stop` の印か」で決めるので、片付けで止めたものは記号を問わず止め直さず、人が止まっている PR をマージしたときは今までどおり片付ける。片付けで止める理由が増えても、条件を直さずに済む。

### 決定 1：片付けの中で作業場所の確かめに外れたら、workspace-tampered で止める

- 片付けの中で、作業場所の `commondir` か `gitdir` が作ったときの値と違えば、消さずに、片付けの前の状態（マージ済みか閉鎖済み）のまま停止中（`workspace-tampered`）にする。止めた理由の記号は、基本設計の今の実装の都合の記号を使う
- 止めた理由のコメントに、作業場所が作ったときと違うこと（作り替えられた疑い）と、消すフォルダの組と消す順を書く。人は、中身を確かめ、同じ時期のほかの作業も疑ったうえで、フォルダを消してから `## 再開 続きから` を書く。片付けは、残りから続ける
- 片付けの失敗の続いた回数には数えない。止めた時点で、片付けをやり直さない（決定 2）

### 決定 2：片付けをやり直さない条件を、マージ済みか閉鎖済みに入った後の stop の印で決める

- 主な流れがマージ済みか閉鎖済みで、止め方が停止中で、最新の `stop` の印が、主な流れがマージ済みか閉鎖済みに入った後（結びつく PR がマージされた時刻か、push 以上の人が Issue を閉じた時刻より後）に書かれていれば、`## 再開` が書かれるまで片付けもしない
- マージ済みか閉鎖済みに入った後に `stop` の印を書くのは、片付け（`cleanup-failed`・`workspace-tampered`、後で足すもの）と、前の実行が残したセッションを止められなかったとき（`session-not-stopped`）。どれも人が確かめるまで作業場所を消さない方がよいので、記号を問わず当たる
- 停止中の作業の単位の PR を人がマージしたか、人が Issue を閉じたとき（最新の `stop` の印は、マージか閉じた時刻より前）は、当たらないので、今までどおり軸の値を問わず片付ける
- 片付けの前の状態に入った後の `stop` の印かは、GitHub の事実（`stop` の印の時刻と、PR のマージの時刻か、Issue の timeline の最新の `ClosedEvent` の時刻）だけで決める。手元の記録を使わない

### 影響（Consequences）

- 良い点: 片付けの中で作業場所の確かめに外れても、`stop` の印は 1 つだけ書かれ、人が確かめるまで止め直さない
- 良い点: 作業場所の作り替えに、どこで見つけても同じ記号が付く。攻撃の疑いが、片付けの失敗に紛れない
- 良い点: 片付けで止める理由が後で増えても、やり直さない条件を直さずに済む
- 良い点: マージか閉じた後に、前の実行が残したセッションを止められなかったとき（`session-not-stopped`）も、人が確かめるまで作業場所を消さない（今の決まりでは、軸の値を問わず片付けて消す）
- 悪い点: やり直さない条件に、`stop` の印とマージか閉じた時刻の比べが要る（記号を見るだけより手間がかかる）
- 悪い点: 片付けの中で外れたときと、ほかの場所で外れたときで、人が戻した後の続き方（片付けの残り、変更の作成など）は違う。止めた理由のコメントで、どこで見つけたかを書き分ける

### 確認方法（Confirmation）

- 単体テストで、片付けをやり直さない条件を確かめる：最新の `stop` の印が、マージか閉じた時刻より後なら（`cleanup-failed` でも `workspace-tampered` でも `session-not-stopped` でも）片付けをしない。前なら（人が止まっている PR をマージしたとき）片付ける。`## 再開` の後は片付ける
- 結合テスト（偽の `gh`）で、片付けの中で作業場所の `gitdir` を書き換えた筋書きで、`workspace-tampered` の `stop` の印が 1 つだけ書かれ、次の実行で片付けをやり直さず、人がフォルダを消して `## 再開 続きから` を書いた後の実行で片付けが終わる（`cleanup` の印）ことを確かめる
- 結合テストで、停止中（`round-limit` など）の作業の単位の PR を人がマージすると、片付けが進むことを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：workspace-tampered で止め、やり直さない条件をマージ済みか閉鎖済みに入った後の stop の印で決める

- 良い点: 同じ出来事に同じ記号が付き、人は作り替えの疑いとして調べられる
- 良い点: やり直さない条件が記号に縛られず、片付けで止める理由が増えても直さずに済む
- 中立: 改める決定は、[ADR-20261024-006][adr-cleanup] の決定 1 の 2 か所だけ
- 悪い点: やり直さない条件に、時刻の比べが要る

### 案 B：片付けの失敗として cleanup-failed で止める

- 良い点: 例外を `cleanup-failed` の 1 つだけのままにでき、ADR の改訂が要らない
- 悪い点: 同じ出来事に、見つけた場所で違う記号が付く
- 悪い点: 攻撃の疑いが、運用の失敗に紛れる。人が「消せなかった原因を直して続きから」で済ませるおそれがある

### 案 C：安全の軸（攻撃の疑い）に値を入れる

- 良い点: 作り替えの疑いを、maintain 以上の人の `## 安全の確認` でだけ外せる
- 悪い点: 安全の軸は、検疫で見つけた文とコードに入れるもの（[ADR-20261024-005][adr-security]）で、範囲を広げる大きな変更になる
- 悪い点: 片付けは軸の値を問わず行うので、やり直さない条件は別に要る
