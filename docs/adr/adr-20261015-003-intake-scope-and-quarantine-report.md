# 受け入れはマイルストーンを待たずに走らせ、検疫で見つかったら作業指示を書かずに検疫の結果と印だけを投稿する

要件の UNDECIDED-14 と UNDECIDED-15（[決めていないこと][undecided]の「受け入れと印」）を決める。
どちらも受け入れ（TEXT-12）の論点で、問いは 2 つある：受け入れをどの Issue に走らせるか、検疫で見つかったときに Issue に何を残すか。

## 背景と課題（Context and Problem Statement）

受け入れ（TEXT-12）は、Issue に検疫を通し、作業指示の下書き・依存とマイルストーンの候補・計画の難しさの判定を「受け入れの下書き」コメントに書く。人は下書きを読み、`agent-ready` を付けて処理対象にする。
要件の中に、受け入れについて答えが食い違う箇所が 2 つある。

問い 1（UNDECIDED-15）：受け入れの対象

- TEXT-12 は受け入れの対象を「マイルストーンが付いている Issue」に限る。一方で、同じ TEXT-12 が「マイルストーンの候補」を出し、FLOW-18 が `agent-ready` の後に候補でマイルストーンを確定する。マイルストーンが付いた Issue だけが対象なら、候補を出す場面が無い
- 「[決まっていること][overview]」の「人の関所」、TEXT-12 の冒頭、SETUP-16 は「人の操作は `agent-ready` を付ける 1 つだけ」とし、FLOW-15〜FLOW-16 は「起票されて Project に入ったら受け入れる」流れで、マイルストーンを条件にしていない。
  マイルストーンを受け入れの条件にすると、人の操作はマイルストーンを付けることと `agent-ready` の 2 つになる
- 進行役が起票する 🟢 の Issue（`from-review`）だけは、人がマイルストーンを付けるまで受け入れを走らせないと決まっている（IMPL-26。🟢 の Issue が毎日増えて人の読む量を超えないため）
- 着手の選定（FLOW-1）は、マイルストーンがあることを条件にしている。受け入れの対象とは別の条件である

問い 2（UNDECIDED-14）：検疫で見つかったとき

- TEXT-9 は、検疫で見つかったら「下書きを作らずに `needs-human` にし、人が作業指示を一から書く」とした直後に、「下書きコメントに『混入の検査：無し / 有り（種類）』の行を必ず書く」としている。TEXT-12 も「有りなら下書きを作らず `needs-human`」とする
- 「[印と固定の見出しの一覧][markers]」の `intake` の印は `quarantine=none|found` の欄を持つ。下書きのコメントを作らないなら、`quarantine=found` を載せる場所が無い
- TEXT-12 の受け入れの対象は「受け入れの印が無い Issue」なので、印を残さないと、次の実行でも同じ Issue に受け入れが走り続ける

課題：受け入れの対象にマイルストーンを条件にするか。検疫で見つかったとき、Issue に何を残すか。

## 判断の決め手（Decision Drivers）

- 人の操作を、要件の多くの箇所が書いている「`agent-ready` を付ける 1 つ」に保つこと
- 人の読む量と利用枠が、Issue の数に押し流されないこと（1 回の実行で受け入れる件数の上限。TEXT-12）
- 検疫で見つかった文を、AI の下書きにも、人が `agent-ready` で承認する文にも入れないこと
- 受け入れ済みかを、手元の記録でなく GitHub の印で決められること（FLOW-4）

## 検討した選択肢（Considered Options）

問い 1：受け入れの対象

- 案 1-A：マイルストーンを待たずに受け入れる（Project に入った Issue。`from-review` だけはマイルストーンを待つ）
- 案 1-B：マイルストーンが付いた Issue だけを受け入れ、マイルストーンの候補は出さない

問い 2：検疫で見つかったとき

- 案 2-A：作業指示を書かずに、検疫の結果と `intake` の印（`quarantine=found`）だけを載せたコメントを投稿し、`needs-human` を付ける
- 案 2-B：コメントを投稿せず、`needs-human` だけを付ける
- 案 2-C：見つかった部分を除いて、受け入れ AI に下書きを書かせる

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」。
理由: 人の操作が `agent-ready` の 1 つのまま保たれ、マイルストーンの候補にも出番がある。検疫で見つかった Issue にも印が残るので、受け入れが繰り返し走らず、人は見つかった種類と場所を Issue の上で読める。

### 決定 1：受け入れはマイルストーンを待たずに走らせる

- 受け入れの対象は、Project に入った Issue のうち、`agent-ready` が無く、受け入れの印（`intake`）も無いもの。マイルストーンの有無は問わない
- `from-review` の Issue だけは、今のまま人がマイルストーンを付けるまで対象にしない（IMPL-26）
- マイルストーンの候補は今のまま出し（open な 0.x のうち版が最小のもの。人が先に付けていれば人が付けたもの）、`agent-ready` の後に確定する（FLOW-18）。人は下書きのコメントで候補を直せる
- 着手の選定（FLOW-1）は今のまま、マイルストーンがあることを条件にする。`agent-ready` の後に確定したマイルストーンで条件を満たす
- 外の人が Issue を大量に立てたときは、1 回の実行で受け入れる件数の上限（TEXT-12）で利用枠を止める。受け入れる順は基本設計で決める

### 決定 2：検疫で見つかったら、作業指示を書かずに検疫の結果と印だけを投稿する

- 検疫（TEXT-11）で 1 つでも見つかったら、受け入れ AI を起動しない。作業指示の下書きも、計画の難しさの判定も作らない
- 進行役は「受け入れの下書き」コメントを投稿する。中身は次の 3 つだけ
  - 検疫の結果：見つかった種類と場所（題名・本文・何番目のコメントか、何行目か）。見つかった文の中身は写さない（見えない文字や指示の形の文を、進行役の投稿として広めないため）
  - 人への案内：作業指示の下書きは無いので、処理対象にするなら `## 作業指示` の見出しのコメントを一から書くこと
  - `intake` の印：`quarantine=found` と `sig`。`body=` `brief=` `plan=` は持たない
- `needs-human` を付ける。受け入れの印があるので、次の実行で受け入れは走らない
- 人が `## 作業指示` を書いて `agent-ready` を付けたら、進行役は作業指示コメントだけを渡す文にする（`intake-final` の `source=instruction`）。`quarantine=found` の Issue では、本文（`source=body`）と下書き（`source=draft`）を渡す文にしない。作業指示コメントも、渡す直前に検疫を通す（TEXT-11）
- 計画役のモデルは、`plan=` が無いので既定の `opus` になる。人はラベル `plan:fable` で上書きできる（IMPL-10）

### 影響（Consequences）

- 良い点: 人の操作は `agent-ready` の 1 つのまま。マイルストーンを付ける手間は、候補を直すときだけになる
- 良い点: 検疫で見つかった Issue にも印と理由が残り、人は何がどこで見つかったかを Issue の上で読める。受け入れが繰り返し走らない
- 良い点: 検疫で見つかった文は、受け入れ AI にも、人が承認する文にも入らない
- 悪い点: マイルストーンを付けるつもりの無い Issue にも受け入れが走り、下書きのコメントが付き、受け入れ AI の利用枠を使う（`haiku`。1 回の実行の件数の上限で止まる）
- 悪い点: 外の人が Issue を大量に立てると、上限の分だけ毎回の受け入れが埋まり、ほかの Issue の受け入れが遅れる

### 確認方法（Confirmation）

- 結合テスト（偽の `gh`）で、次を検査する
  - マイルストーンの無い Issue に受け入れが走り、マイルストーンの候補が下書きのコメントに出ること。`from-review` の Issue には、マイルストーンが付くまで走らないこと
  - 検疫で見つかった Issue では、受け入れ AI を起動せず、検疫の結果と `quarantine=found` の印だけのコメントを投稿して `needs-human` を付けること。コメントに見つかった文の中身が無いこと
  - 次の実行で、印のある Issue に受け入れが走らないこと
  - `quarantine=found` の Issue で `agent-ready` が付いたとき、`## 作業指示` のコメントが無ければ `intake-final` を投稿せずに `needs-human` のままにし、あれば `source=instruction` だけを渡す文にすること
- 段階 4（棚卸しと受け入れを動かす段階）の出口の記録で、受け入れた件数とマイルストーンの候補を人が直した件数を数える

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：マイルストーンを待たずに受け入れる

- 良い点: 人の操作が `agent-ready` の 1 つで済む
- 良い点: 人は下書きを読んでから、処理対象にするかを決められる
- 悪い点: 処理対象にしない Issue にも下書きが付き、利用枠を使う

### 案 1-B：マイルストーンが付いた Issue だけを受け入れる

- 良い点: 人がマイルストーンを付けた Issue にだけ利用枠を使う。外の人の Issue が大量に立っても、受け入れは走らない
- 悪い点: 人の操作がマイルストーンを付けることと `agent-ready` の 2 つになる。「人の関所」・TEXT-12・SETUP-16 の「1 操作」を書き直すことになる
- 悪い点: 人は下書きを読む前に、マイルストーンを付けるか（処理するか）を決めることになる

### 案 2-A：検疫の結果と印だけを投稿する

- 良い点: 受け入れ済みの印が残り、受け入れが繰り返し走らない
- 良い点: 人が見つかった種類と場所を読める
- 悪い点: `intake` の印が、`body=` `brief=` `plan=` を持たない形を許すことになる

### 案 2-B：`needs-human` だけを付ける

- 良い点: 投稿が増えない
- 悪い点: 人に理由が伝わらない
- 悪い点: 印が無いので、受け入れの対象から外す条件を別に足さないと、次の実行でも受け入れが走る

### 案 2-C：見つかった部分を除いて下書きを書かせる

- 悪い点: 検疫は機械で探せる形しか見つけない（TEXT-11）。見つかった Issue には、見つからなかった指示も混じっている見込みが高く、受け入れ AI に読ませると下書きに混ざりうる
- 却下
