# 承認は agent-ready の付け直しでやり直し、push 未満の人の作業指示は読まず、作業指示が 2 つ以上なら止める

要件の UNDECIDED-61（承認した後に渡す文を直したいとき、承認をやり直す手順をどうするか。外の人の `## 作業指示` のコメントをどう扱うか）を決める。

改める決定と、据え置く決定は次のとおり。

- [ADR-20261015-004][adr-markers]：決定 2 の時刻の規則の「`agent-ready` を付けた時刻」を、承認をやり直したときは、最新の `agent-ready` を付けた時刻と読む。権限を確かめる相手と、push 未満の人の操作の扱いは据え置く
- [ADR-20261015-003][adr-intake]：検疫で見つかった Issue（`quarantine=found`）では、渡す文を人の作業指示コメントだけにすることは据え置く。読む作業指示コメントは、本 ADR の決定 3 と決定 4 で選ぶ
- [ADR-20261016-002][adr-draft]：渡す文は作業指示コメントか承認された下書きで、Issue の本文は著者を問わず渡さないことは据え置く

## 背景と課題（Context and Problem Statement）

- TEXT-4 は、承認した時点の渡す文のハッシュを `intake-final` の印に書き、着手時と対応ループの各回で照らし、変わっていたら `needs-human` にする（`brief-changed`）
- 承認の確定は、受け入れの印があり、人が `agent-ready` を付け、`intake-final` の印が無いときに行う（基本設計の次の工程の表の順 10）。
  人が文を直して `needs-human` を外しても、`intake-final` の印は残るので、同じハッシュの照らしで止まり続ける。「止まった状態から戻す手順」にも、承認をやり直す手順が無い
- 基本設計の「戻した Issue のやり直し」は、人が `needs-human` を外して Status を `Todo` に戻すと、最後に `needs-human` を外した時刻より前の計画の印を無いものとして、計画し直す。
  計画コメントが、渡す直前の検疫（TEXT-11）で見つかったとき、人は計画コメントを直せない（未編集の条件。IMPL-20）が、戻す手順で計画し直せる
- TEXT-10 は、作業指示コメントを書いた人が push 未満なら `needs-human` にする。一方、「印と固定の見出しの一覧」は、固定の見出しは push 以上の人が書いたものだけを読むとする（FLOW-14）。
  公開のリポでは、外の人が `## 作業指示` のコメントを書くだけで、どの Issue の承認も止められる
- 作業指示コメントが 2 つ以上あるときに、どれを渡すかが決まっていない。基本設計は、決まるまでの間、push 以上の人の作業指示コメントが 2 つ以上なら、承認を確定せずに `needs-human` にする（`draft-format`）
- 渡す文の範囲は `agent-ready` の時点で確定し、後から足されたコメントは渡さない（TEXT-1）

課題：承認した後に渡す文を直したいとき、承認をどうやり直すか。push 未満の人の作業指示コメントと、2 つ以上ある作業指示コメントをどう扱うか。

## 判断の決め手（Decision Drivers）

- 人が渡す文を直して、承認をやり直せること（直しても止まり続けない）
- 承認は、人が読んだ文で、push 以上の人の 1 操作で確定すること（[ADR-20261015-004][adr-markers] の人の関所のまま）
- 外の人の投稿で、Issue を止められないこと（公開のリポ）
- 渡す文が 1 つに決まらないときに、進行 Bot が推測で選ばないこと（フェイルセーフ）
- 人の操作とラベルを増やさないこと

## 検討した選択肢（Considered Options）

問い 1：承認のやり直し

- 案 1-A：最新の `intake-final` の印より後に、push 以上の人が付け直した `agent-ready` を、承認のやり直しとして扱う
- 案 1-B：人が `intake-final` の印のコメントを消すと、承認を確定し直す
- 案 1-C：承認をやり直す専用のラベルを足す
- 案 1-D：やり直さない。人が Issue を閉じて作り直す

問い 2：push 未満の人の作業指示コメント

- 案 2-A：読まない（無いものとして扱い、止めない）
- 案 2-B：今のとおり `needs-human` にする
- 案 2-C：読まずに、読まなかったことを Issue にコメントする

問い 3：push 以上の人の作業指示コメントが 2 つ以上あるとき

- 案 3-A：承認を確定せずに `needs-human` にし、人に 1 つにしてもらう
- 案 3-B：いちばん新しいものを渡す
- 案 3-C：すべてを投稿の順につなげて渡す

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-A」。
理由: 承認のやり直しは、承認と同じ `agent-ready` の操作で済み、ラベルも手順も増えない。外の人の作業指示は、固定の見出しの読み方（FLOW-14）にそろえて読まないので、外の人が Issue を止められない。作業指示が 2 つ以上なら、進行 Bot が選ばずに人に返す。

### 決定 1：承認は、agent-ready の付け直しでやり直す

- 次をすべて満たす Issue を、承認のやり直しとして扱う
  - `intake-final` の印がある
  - push 以上の人が `agent-ready` を付けた最新の時刻（timeline の `LabeledEvent`）が、最新の `intake-final` の印の投稿より後
  - Status が `Todo` で、`needs-human` が無く、開いている結びつく PR が無い
- 承認のやり直しでは、承認の確定（次の工程の表の順 10）と同じことを確かめ、満たせば新しい `intake-final` の印を新しいコメントで書く。満たさなければ、今のとおり `intake-final` を書かずに `needs-human` を付ける。
  時刻の規則（[ADR-20261015-004][adr-markers] の決定 2）は、最新の `agent-ready` を付けた時刻で見る
- 進行 Bot は、最新の `intake-final` の印だけを読む。ハッシュの照らし（TEXT-4）も、最新の印で行う
- 計画の印が最新の `intake-final` の印より前なら、計画の印が無いものとして、着手の後に計画し直す（基本設計の「戻した Issue のやり直し」と同じ扱い）
- 着手した後（Status が `Todo` でない）に付け直した `agent-ready` は、やり直しとして扱わない。渡す文が変わっていれば、今のとおりハッシュの照らしで止まる（`brief-changed`）。人は、戻す手順で `Todo` に戻してから付け直す

### 決定 2：止まった状態から戻す手順に、承認のやり直しを足す

- 渡す文を直したいとき：作業指示コメントか下書きを直す → `needs-human` があれば外し、Status を `Todo` に戻す → `agent-ready` を外して付け直す。文を直すのは、付け直す前にする（時刻の規則）
- PR がある Issue の渡す文を直すときは、PR を閉じ、作業ブランチを消して `Todo` に戻してから付け直す（基本設計の「戻した Issue のやり直し」）
- 計画コメントが渡す直前の検疫で見つかったときは、戻す手順で `Todo` に戻せば計画し直す。原因が渡す文にあれば、文を直して承認をやり直す

### 決定 3：push 未満の人の作業指示コメントは読まない

- 進行 Bot は、`## 作業指示` のコメントのうち、push 以上の人が書いたものだけを読む（固定の見出しの読み方（FLOW-14）にそろえる）。push 未満の人の作業指示コメントは、無いものとして扱い、止めない。AI にも渡さない
- 書いた人の権限は、今のとおり渡す直前に 1 人ずつ引く（TEXT-10）。push 未満の人が付けた `agent-ready` と、push 未満の人がした渡す文の編集は、今のとおり無効として `needs-human` にする
- 検疫で見つかった Issue で、push 以上の人の作業指示コメントが無いまま `agent-ready` が付いたら、今のとおり `needs-human` にする（[ADR-20261015-003][adr-intake]）

### 決定 4：push 以上の人の作業指示コメントが 2 つ以上あれば止める

- 承認の確定（やり直しを含む）で、push 以上の人の作業指示コメントが 2 つ以上あれば、`intake-final` を書かずに `needs-human` を付ける。人は、1 つを残してほかのコメントを消すか見出しを外してから、`agent-ready` を付け直す
- 着手と対応ループの各回も、承認の確定と同じ規則で渡す文を選ぶ。承認の後に作業指示コメントが足されたら、渡す文が変わるか 2 つ以上になるので止まる。人は承認をやり直す
- 止めた理由の記号は、基本設計で決める（決まるまでの `draft-format` を置き換える）

### 影響（Consequences）

- 良い点: 人は、渡す文を直して承認をやり直せる。操作は、承認と同じ `agent-ready` の付け直しだけ
- 良い点: 外の人の投稿で、Issue の承認が止まらない
- 良い点: 作業指示が 2 つ以上あるとき、進行 Bot が推測で選ばない
- 悪い点: 承認をやり直すと計画からやり直すので、計画のセッションの利用枠を使い直す
- 悪い点: 外の人が作業指示を書いても、進行 Bot は知らせない。取り込みたいときは、push 以上の人が自分の作業指示コメントに書き写す
- 悪い点: 作業指示が 2 つ以上あると、人が 1 つにまとめる手間がかかる
- 中立: Issue に `intake-final` の印が 2 つ以上並ぶことがある。進行 Bot は最新だけを読む

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 承認のやり直しの条件（最新の `agent-ready` と最新の `intake-final` の前後、Status、`needs-human`、開いている PR）
  - 最新の `intake-final` の印だけを読むこと。計画の印が最新の `intake-final` より前なら計画し直すこと
  - push 未満の人の作業指示コメントを読まず、止めないこと
  - push 以上の人の作業指示コメントが 2 つ以上なら、承認の確定・着手・対応ループのどこでも止めること
- 結合テストで、`brief-changed` で止まった Issue を、文を直して `Todo` に戻し、`agent-ready` を付け直すと、新しい `intake-final` の印を書いて計画し直すことを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：agent-ready の付け直しでやり直す

- 良い点: 承認と同じ操作で、ラベルも手順も増えない
- 良い点: 時刻の規則と権限の確かめを、承認と同じものでやり直せる
- 悪い点: `agent-ready` を外した時点で着手していれば、`issue-changed` で止まるので、人は戻す手順を先に行う

### 案 1-B：intake-final の印のコメントを消す

- 良い点: 進行 Bot の判定を変えずに済む（印が無ければ承認を確定する）
- 悪い点: コメントの削除は API から見分けられず、消したのか書いていないのかが分からない（IMPL-18 の `round` と同じ理由）。人が進行 Bot のコメントを消す運用になる

### 案 1-C：専用のラベルを足す

- 良い点: やり直しの意思がはっきりする
- 悪い点: ラベルが 1 つ増え、`setup` と点検と権限の確かめに足す。承認と同じ確かめを 2 つの入口で持つ

### 案 1-D：やり直さない

- 良い点: 仕組みが増えない
- 悪い点: Issue を閉じて作り直すたびに、受け入れからやり直し、経緯が 2 つの Issue に分かれる

### 案 2-A：読まない

- 良い点: 固定の見出しの読み方（FLOW-14）とそろう。外の人が Issue を止められない
- 悪い点: 外の人の作業指示は、人が書き写さないと使われない

### 案 2-B：needs-human にする

- 良い点: 人が必ず気づく
- 悪い点: 公開のリポでは、外の人が 1 つのコメントで、どの Issue の承認も止められる

### 案 2-C：読まずにコメントで知らせる

- 良い点: 人が気づける
- 悪い点: 外の人の投稿のたびに進行 Bot が書くので、外の人が進行 Bot に書かせる経路になる

### 案 3-A：止めて人に 1 つにしてもらう

- 良い点: 渡す文を進行 Bot が推測で選ばない
- 悪い点: 人の手間がかかる

### 案 3-B：いちばん新しいものを渡す

- 良い点: 人が新しい作業指示を書くだけで済む
- 悪い点: 古い作業指示を残したまま、どれが渡されたかが Issue から読みにくい。新しいコメントが足し書きのつもりだと、古い作業指示が黙って落ちる

### 案 3-C：すべてをつなげて渡す

- 良い点: 書いた内容が落ちない
- 悪い点: 食い違う作業指示が、人がまとめないまま AI に渡る
