# 自動化用の GitHub アカウントはいまは分けず、印を書いたと認めるアカウントを設定の一覧に持つ

> **Amended by [ADR-20261020-002][adr-app]（2026-10-20）**: 決定 1（いまは分けない）を、GitHub に書き始める前に GitHub App に切り替えて分ける形に改めた。決定 2 の「投稿に使うアカウントは PAT の持ち主」と点検の「PAT の持ち主が一覧にある」は、切り替えの後はアプリの投稿者の名前と読む。一覧の形、決定 3、決定 4 は据え置く。

要件の UNDECIDED-20（[決めていないこと][undecided]の「自動化用の GitHub アカウントを分けるか」）を決める。あわせて、ADR「署名付きの印と、人の操作の権限の確かめ」（[ADR-20261015-004][adr-markers]）の決定 1 のうち、印を読む条件の「進行 Bot のアカウント」を、1 つのアカウントから設定に並べたアカウントの一覧に改める。[ADR-20261015-004][adr-markers] のほかの決定（決定 1 の署名と印の読み方、決定 2 の人の操作の確かめ）は据え置く。

## 背景と課題（Context and Problem Statement）

- 進行 Bot は、印を読むとき、投稿者・未編集・署名の 3 つを確かめる（IMPL-20 の (a)〜(c)、[ADR-20261015-004][adr-markers]）。投稿者は、リポの設定の `safety.botAccount` に持つ 1 つのアカウントと比べる（基本設計の「[設定][design-settings]」）
- 進行 Bot は、当面メンテナと同じアカウントで投稿する（SETUP-13）。人と進行 Bot の投稿は印の有無で見分け、印は進行 Bot だけが持つ鍵の署名で確かめるので、1 つのアカウントでも判定は動く（[ADR-20261015-004][adr-markers]）
- SETUP-13 は、監査のために分けたくなったら、自動化用のアカウントをコラボレータに足すとする。UNDECIDED-20 は、分けるか、分けるなら machine user と GitHub App のどちらかを、レビュー工程（段階 6）で確かめてから決めるとしていた
- アカウントを替えると、替える前のアカウントが書いた印は、投稿者の条件を満たさなくなって読まれない。作業中の Issue は、受け入れや計画の印が無いものとして扱われ、止まるか、受け入れからやり直すことになる
- 設定の形（1 つの文字列）を、進行 Bot のコードを書いた後に一覧に変えると、書いたリポの設定を移す処理が要る。進行 Bot のコードはまだ無い

課題：自動化用のアカウントを、いつ分けるか。分けたときに、作業中の Issue の印をどう読み続けるか。

## 判断の決め手（Decision Drivers）

- アカウントの管理と人の手間を、要るまで増やさないこと
- アカウントを替えても、作業中の Issue が止まったり、受け入れからやり直したりしないこと
- 印を読む条件を広げても、署名の守り（進行 Bot だけが持つ鍵）を弱めないこと（フェイルセーフ）
- 設定の形を、進行 Bot のコードを書く前に決めておくこと

## 検討した選択肢（Considered Options）

- 案 A：いまは分けない。設定を一覧（`safety.botAccounts`）にし、印を読む条件の投稿者を「一覧のどれか」にする。分けるときは、一覧に新しいアカウントを足して切り替える
- 案 B：いまは分けない。設定は 1 つのアカウントのまま。分けるときは、進行中の Issue が無いときを選んで替える
- 案 C：いまは分けない。設定は 1 つのアカウントのまま。分けると決めたときに、切り替え方を別の ADR で決める（UNDECIDED-20 を残す）
- 案 D：最初から自動化用のアカウント（machine user か GitHub App）に分ける

## 決定（Decision Outcome）

採用した選択肢:「案 A」。
理由: いまの手間は増やさず、分けると決めたときに、作業中の Issue を止めずに切り替えられる。設定の形を進行 Bot のコードを書く前に決めるので、後で設定を移す処理も要らない。印を読む条件を一覧に広げても、署名の鍵は 1 つのままなので、守りの本体は変わらない。

### 決定 1：いまは自動化用のアカウントを分けない

- 進行 Bot は、SETUP-13 のとおり、メンテナのアカウントで投稿する
- 分ける要望が出たら、分けると決めたときに、machine user と GitHub App のどちらにするかと、新しいアカウントの権限と PAT の出し方を、別の ADR で決める
- UNDECIDED-20 は、本 ADR で決めたとする。レビュー工程（段階 6）で、1 つのアカウントで印の判定が動くかは、段階の出口の確かめの中で見る

### 決定 2：設定 `safety.botAccount` を、一覧の `safety.botAccounts` にする

- 中身は、印を書いたと認める GitHub のアカウント名の一覧。リポの設定に持つ（今の `safety.botAccount` と同じ置き場）
- 最初は `setup` が、人の `gh` のログイン名を 1 つ書く
- 投稿に使うアカウントは、進行 Bot の PAT の持ち主で決まり、一覧では決めない。点検は、PAT の持ち主（`GET /user` の `login`）が一覧にあることを確かめ、無ければ fail にする。一覧が空のときも fail にする
- AI のセッションに渡す commit の作者（`GIT_AUTHOR_NAME` など）は、PAT の持ち主の名前にする

### 決定 3：印を読む条件の投稿者を、一覧のどれかにする

- IMPL-20 の (a) を「投稿者が `safety.botAccounts` のどれか」にする。(b) 未編集と (c) 署名は変えない
- 署名の鍵は 1 つのまま、アカウントを替えても替えない。前のアカウントが書いた印も、署名で確かめて読める
- [ADR-20261015-004][adr-markers] の決定 1 の「進行役のアカウントが投稿した印」と「印の無い進行役のアカウントの投稿は、人の投稿として読む」の「進行役のアカウント」も、一覧のどれかと読む

### 決定 4：一覧を変えるときの決まり

- 足すのは、アカウントを分けると決めた ADR の後だけにする。認める投稿者を増やす向き（安全の境界を緩める変更）なので、リポの設定の PR に残し、決めた ADR を書き添える
- 替えた後、前のアカウントで書いた印が残る Issue と PR がすべて閉じたら、前のアカウントを一覧から外す。外すのは認める投稿者を減らす向きなので、PR に残せば足りる

### 影響（Consequences）

- 良い点: アカウントを替えても、作業中の Issue の印を読み続けられ、止まらない。受け入れの下書きもやり直さない
- 良い点: 設定の形を進行 Bot のコードの前に決めるので、後で設定を移す処理が要らない
- 良い点: いまの人の手間は増えない（一覧の要素は 1 つ）
- 悪い点: 印を読む条件の投稿者が、1 つのアカウントから一覧に広がる。前のアカウントを外し忘れると、認める投稿者が多いまま残る
- 悪い点: 設定の項目の名前と形が変わり、要件（IMPL-20、STRUCT-2、SETUP-13）と基本設計（設定、AI のセッションの環境変数、導入と点検）を直す
- 中立: 人のアカウントが一覧にある間、人が同じ Issue に進行 Bot の印を写して投稿すると、署名が通る。1 つのアカウントで始める今と同じで、[ADR-20261015-004][adr-markers] が受け入れた形のまま。署名の鍵が守りの本体であることも変わらない

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 投稿者が一覧のどれかなら印を読み、どれでもなければ読まないこと
  - 一覧の 2 つ目のアカウントが書いた印も、署名で確かめて読むこと
  - PAT の持ち主が一覧に無いとき、一覧が空のときに、点検が fail になること
- 基本設計のレビューで、設定の表、AI のセッションの環境変数の表、点検の組が、一覧の形と PAT の持ち主の確かめになっているかを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：設定を一覧にし、投稿者を一覧のどれかにする

- 良い点: 作業中の Issue を止めずにアカウントを替えられる
- 良い点: 設定の形を、コードを書く前に決められる
- 悪い点: 印を読む条件が一覧に広がり、要件と設計の直しがいま要る

### 案 B：1 つのアカウントのまま、進行中の Issue が無いときに替える

- 良い点: 印を読む条件が 1 つのアカウントのまま
- 悪い点: 進行中の Issue が無くなるまで、替えられない。待つ間、新しい着手を止めることになる
- 悪い点: 承認を待つ受け入れの下書きの印も読まれなくなり、受け入れからやり直す（下書きが重なって投稿される）

### 案 C：分けると決めたときに、切り替え方を決める

- 良い点: いま決めることが最も少ない
- 悪い点: 分けるときに、切り替え方を決める ADR がもう 1 つ要る。案 A の形にするなら、切り替えるときに設定の形を変え、書いたリポの設定を移す処理が要る

### 案 D：最初から自動化用のアカウントに分ける

- 良い点: 人と進行 Bot の投稿を、投稿者でも見分けられる（監査しやすい）
- 悪い点: アカウントか GitHub App の作成と管理、権限と PAT の出し直しが今から要る
- 悪い点: SETUP-13 の「最初は 1 つのアカウントで始める」と合わない。印の判定は 1 つのアカウントでも動く（[ADR-20261015-004][adr-markers]）ので、分けても判定の仕組みは良くならない
