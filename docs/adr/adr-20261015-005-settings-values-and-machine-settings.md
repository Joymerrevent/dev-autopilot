# 要件が決めていない設定の値は構造仕様に初期値として書いて設定ファイルで変え、マシンごとの値はリポの外の設定に置く

要件の UNDECIDED-17（[決めていないこと][undecided]の「まだ値が決まっていない設定」）を決める。
問いは 2 つある：要件が値を決めていない設定の値をどこで決めるか、マシンごとに違う値（置き場のパスなど）をどこに置くか。

## 背景と課題（Context and Problem Statement）

STRUCT-2 は、リポ固有の値をすべて設定ファイル 1 つ（例：business-os の `.claude/dev-autopilot.json`）に出すと決めている。SETUP-3 は「設定ファイルの正本は 1 つ」とする。
一方、設定の項目の値の決まり方は揃っていない。

- 要件に初期値まで書いてあるもの：1 セッションの時間とターン（IMPL-13。45 分・200 ターン）、実行の失敗の再試行の回数（IMPL-14。3）、役ごとのモデルと effort（「[モデルの流れ][impl]」の表）、マージ判定の許可一覧（MERGE-4）、ラベルの名前（SETUP-8）
- 「設定に持つ」とだけ書いてあり、値が無いもの：1 回の実行の所要時間（FLOW-4）、1 回の実行で受け入れる件数（TEXT-12）、費用の上限（1 セッション、1 Issue の累計、1 日。IMPL-13、IMPL-14、SETUP-12）、再試行の間隔（IMPL-14）、Agent ツールを許すか（IMPL-14）、批評者の確信度のしきい値（IMPL-22）、置き場のパス
- 既に決めた ADR も、値を UNDECIDED-17 に回している：秘密の置き場の既定のパス（[ADR-20261015-001][adr-read]）

値は運用で変わる。変えるたびに要件の PR や ADR を作ると、要件と ADR が値の変更で埋まる。一方で、値の中には安全の境界を動かすもの（Agent ツールを許す、上限を外す）があり、黙って変えてよいものではない。

置き場の値には、もう 1 つ問題がある。STRUCT-2 は、`devAutopilotPath`（絶対パス）、worktree の置き場、記録と lock の置き場を設定ファイルに持つとしている。

- 設定ファイルを business-os に commit すると、手元のマシンの絶対パス（ユーザー名を含む）が公開のリポに入る。business-os の漏えいの検査（`check:leak`）が見るのはメールアドレス・電話番号・法人格・金額・許可リストに無いドメインで、機械上のパスは見ない
- 手元の Mac と将来の専用マシンではパスが違う。commit した 1 つのファイルでは、両方の値を持てない
- 秘密の置き場のパス（ADR-20261015-001）も、マシンごとに違う

課題：要件が値を決めていない設定の値をどこで決め、どう変えるか。マシンごとに違う値をどこに置くか。

## 判断の決め手（Decision Drivers）

- 値の変更が、要件や ADR の変更なしに、記録の残る形（PR）で済むこと
- 安全の境界を緩める変更は、黙って行われないこと
- 公開のリポに、マシンのパスや秘密の置き場を書かないこと
- 項目ごとに正本が 1 つで、`check` が確かめられること（SETUP-2、SETUP-3）
- 文書に値を複製しないこと（値の正本を 1 か所にし、ほかは正本を指す）

## 検討した選択肢（Considered Options）

問い 1：要件が値を決めていない設定の値をどこで決めるか

- 案 1-A：構造仕様（`dev-autopilot/docs/design/`）の設定の表に初期値と根拠を書き、`setup` が表の初期値で設定ファイルを作る。値を変えるのは設定ファイルの PR。安全の境界を緩める変更だけ ADR にする
- 案 1-B：要件に初期値を書く（IMPL-13 の形を広げる）。値を変えるたびに要件を直す
- 案 1-C：値も ADR で決める

問い 2：マシンごとに違う値をどこに置くか

- 案 2-A：設定を 2 つに分ける。リポの設定（business-os に commit）と、マシンの設定（commit しない。リポの外の同期されないフォルダ）
- 案 2-B：1 つのファイルにすべて入れて commit する（今の STRUCT-2 の文のまま）
- 案 2-C：1 つのファイルにすべて入れ、commit しない

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」。
理由: 値の変更は設定ファイルの PR で記録に残り、要件と ADR は形の判断に絞られる。安全の境界を緩める変更だけは ADR を通る。マシンのパスは公開のリポに入らず、手元の Mac と専用マシンで同じリポの設定を使える。

### 決定 1：要件が値を決めていない設定の値は、構造仕様に初期値として書き、設定ファイルで変える

- 構造仕様（`dev-autopilot/docs/design/`。STRUCT-5）に、設定の項目の表を置く。表は項目ごとに、置き場（決定 2 のリポの設定かマシンの設定か）、初期値、根拠、根拠の要件の番号を持つ。STRUCT-2 の「基本設計では要件番号から項目への対応表にする」を、構造仕様の設定の表で満たす
  - 要件が初期値を決めている項目（IMPL-13 の 45 分・200 ターンなど）は、表に値を写さず、要件の番号を指す
  - 要件が値を決めていない項目（背景の一覧）は、表に初期値と根拠を書く。初期値は「暫定」と明記し、段階の出口の記録（FLOW-5、FLOW-13）で見直す
- `setup` は、表の初期値で設定ファイルを作る。今の値の正本は設定ファイルで、表は初期値と根拠の正本
- 値を変えるのは、設定ファイルを変える PR で行う。ADR も要件の変更も要らない。リポの設定は `.claude/**` にあり、AI のセッションは変えられない（IMPL-15）
- 安全の境界を緩める変更は、値の変更であっても ADR で決める。次のものを指す
  - AI の道具・読み書きの範囲・通信先を広げる（Agent ツールを許す、`allowRead`・`allowWrite`・通信の許可先を足す）
  - マージ判定の許可一覧（MERGE-4）にパスを足す。進行役が実行するパスの一覧（IMPL-15）からパスを外す
  - 上限（時間・ターン・費用・件数・往復の回数）を外す。上限の値を変えるのは設定でよい
- Agent ツールの初期値は「許さない」（「[登場するもの][overview]」の作業 AI の道具の表のとおり）
- 迷ったら、安全の境界を緩める変更として ADR にする

### 決定 2：設定を、リポの設定とマシンの設定に分ける

- リポの設定（business-os の `.claude/dev-autopilot.json`。commit する）：リポと Project の ID、ラベルの名前、固定の見出し、段階（`stage`）、上限、モデル、検査と判定の一覧、規約、進行役のアカウント名、外への通信の許可先、子プロセスに渡す環境変数の名前。マシンに依らない値だけを持つ。PR で変える
- マシンの設定（commit しない）：`devAutopilotPath`、置き場（`<置き場>/`）、記録と lock の置き場、秘密の置き場（`paths.secrets`。ADR-20261015-001）、sandbox の安全設定の置き場、ホームの中にある道具のフォルダ（`allowRead` に足すもの）。マシンごとに `setup` が作る
  - 置き場所は、リポの外の、同期されないフォルダ（秘密の置き場と同じ条件。ADR-20261015-001）。秘密の置き場と並べてよい
  - 進行役は、起動の定義（launchd の plist。`setup` が書く）から渡されるパスでマシンの設定を読む
  - AI のセッションの `denyRead` に入れる（置き場と秘密の置き場と同じ扱い）
  - 既定のパスの値は、構造仕様の設定の表で決める（決定 1）
- 項目ごとに、置き場はリポの設定かマシンの設定のどちらか一方だけにする。SETUP-3 の「正本は 1 つ」は「項目ごとに正本は 1 つ」に改める
- `check` は、すべての項目がどちらか一方にだけあること、リポの設定に絶対パス（`/Users/` `/home/` などで始まる値）が無いこと、マシンの設定の実体のパスが同期フォルダの下に無いことを確かめる

### 影響（Consequences）

- 良い点: 値の変更が設定ファイルの PR で済み、記録が git の履歴に残る。要件と ADR は形の判断に絞られる
- 良い点: Agent ツールや許可一覧のような安全の境界は、値の形をしていても ADR を通る
- 良い点: 公開のリポにマシンのパスが入らない。手元の Mac と専用マシンで、同じリポの設定を使える
- 悪い点: 設定ファイルが 2 つになり、項目がどちらにあるかを覚える必要がある（構造仕様の表と `check` で補う）
- 悪い点: マシンの設定は commit しないので、専用マシンへ移るときは `setup` で作り直す
- 悪い点: 「安全の境界を緩める変更」かの線引きに迷う変更が出る（迷ったら ADR）

### 確認方法（Confirmation）

- 構造仕様を書くときに、設定の表が STRUCT-2 の項目をすべて持ち、項目ごとに置き場・初期値か要件の番号・根拠があることをレビューで確かめる
- 段階 3 の `check`（SETUP-2）で、決定 2 の 3 つ（項目の重複が無い、リポの設定に絶対パスが無い、マシンの設定が同期フォルダの下に無い）を確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：構造仕様に初期値、設定ファイルで変える、安全の境界は ADR

- 良い点: 値の変更が速く、記録も残る
- 良い点: 安全の境界を緩める変更を取りこぼさない
- 悪い点: 線引きに迷う変更が出る

### 案 1-B：要件に初期値を書く

- 良い点: 要件を読めば初期値が分かる
- 悪い点: 運用で値を変えるたびに要件を直す。今の値（設定ファイル）と要件の値がずれやすい

### 案 1-C：値も ADR で決める

- 良い点: すべての値の経緯が ADR に残る
- 悪い点: ADR が値の変更で埋まり、形の判断を探しにくくなる。段階ごとの調整（確信度のしきい値など）が遅くなる

### 案 2-A：リポの設定とマシンの設定に分ける

- 良い点: 公開のリポにマシンのパスが入らない。マシンを替えても、リポの設定は変えずに使える
- 悪い点: ファイルが 2 つになる

### 案 2-B：1 つのファイルにすべて入れて commit する

- 良い点: ファイルが 1 つで分かりやすい
- 悪い点: 手元のマシンの絶対パスが公開のリポに入り、`check:leak` も止めない。手元の Mac と専用マシンでパスが違い、両方を持てない
- 却下

### 案 2-C：1 つのファイルにすべて入れ、commit しない

- 良い点: パスが公開のリポに入らない
- 悪い点: リポ固有の値（Project の ID、許可一覧、上限）の変更が PR を通らず、記録が残らない。マシンを替えると値が失われる
