# CI が赤なら修正に回し、結果が出ていなければ待ち、merge=ready は 1 回の実行で 1 件にして残りは次の実行に回し、PR と Issue はブランチ名と署名付きの印で結びつける

要件の UNDECIDED-9、UNDECIDED-10、UNDECIDED-12（[決めていないこと][undecided]の「レビューとマージ」と「受け入れと印」）を決める。
どれも進行役が PR をどう扱うかの論点で、問いは 3 つある：レビューが pass なのに CI が緑でないとき、2 件目以降の `merge=ready`、PR と Issue の結びつけ。

## 背景と課題（Context and Problem Statement）

問い 1（UNDECIDED-9）：pass なのに CI が緑でないとき

- IMPL-27 は、収束の条件を「CI が緑、かつ最新のラウンドの印が `verdict=pass`」とし、必須チェックのうち 1 つでも、head に対するチェックがまだ作られていないか、`pending`・`skipped`・`failure` のどれかなら、緑ではないとする。緑でないときに何をするかは書いていない
- 何もしなければ、レビューが pass で CI が赤の PR は、収束しないまま残る。CI の結果には、作業の結果による赤（`failure`）のほかに、チェックがまだ作られていない状態（push の直後）、保留（`pending` など）、取り消し（`cancelled`）、人の承認待ち（`action_required`）があり、どれを修正に回すかで利用枠と往復の回数が変わる

問い 2（UNDECIDED-10）：2 件目以降の `merge=ready`

- MERGE-5 は「1 回の実行で `merge=ready` にするのは 1 件まで（人が 1 件マージするごとに、残りは載せ直しと CI を経て判定し直す）」とする。2 件目以降の PR に何を書くかは決めていない
- 2 件目に `merge=human` を書くと、人が 2 件目の PR をマージしたときに「不一致」に数えられ、判定と人の判断の一致の記録（MERGE-3 の数え方。段階 8（進行役が PR にマージの判定の印を書き始める段階）の出口の条件と、マージの実行を進行役に移すかの判断（MERGE-9）に使う）を汚す
- 進行中の Issue の数（WIP）の上限は、段階 8（進行役が PR にマージの判定の印を書き始める段階）までは 1（FLOW-3）。段階は dev-autopilot を少しずつ動かす導入の順番で、正本は「[段階][setup]」の表。
  2 件目は、段階 9（WIP の上限を 1 から上げる段階）から起きる。段階 8 の間は起きないので段階 8 の出口の条件そのものには影響しないが、一致の記録は段階 8 の後も数え続ける

問い 3（UNDECIDED-12）：PR と Issue の結びつけ

- IMPL-6 は、PR の本文に `Closes #<番号>` を書くとする。進行役が PR から Issue を、Issue から PR を引く方法は書いていない。`Closes #n` の結びつき（GraphQL の `closingIssuesReferences`）で引くと、次の問題がある
- business-os の既定のブランチは `main` で、dev-autopilot の PR は `develop` 向けに作る。2026-10-16 に確かめると、`develop` 向けの PR の本文に「Closes #44」「Closes #86」と書いてあっても、`closingIssuesReferences` は 0 件だった（PR #45、#88）。
  `Closes #n` で引くと、進行役は PR を見つけられず、実装の段を繰り返す
- 公開のリポでは、外の人が fork から PR を出せる。本文に `Closes #n` と書けば、外の人の PR を Issue に結びつけられる（「[AI が読む文と出どころ][markers]」は、外の人の PR を dev-autopilot が扱わないとしている）
- 進行役は当面メンテナと同じアカウントで PR を作る（SETUP-13）ので、PR の作者では、進行役が作った PR と人が作った PR を見分けられない（[ADR-20261015-004][adr-markers]）

課題：CI の結果ごとに、修正に回すか、待つか、人に渡すか。1 回の実行で `merge=ready` にできない 2 件目以降の PR に何を書くか。PR と Issue を何で結びつけるか。

## 判断の決め手（Decision Drivers）

- 修正のセッション（利用枠と往復）を、作業の結果に原因があるときだけ起こすこと
- 時間が解決するもので止めず、時間が解決しないもので止まり続けないこと
- 判定と人の判断の一致の記録（MERGE-3 の数え方。段階 8（進行役が PR にマージの判定の印を書き始める段階）の出口の条件と、マージの実行を進行役に移すかの判断（MERGE-9）に使う）を、判定の中身と関係の無い理由で汚さないこと
- 既定のブランチの設定や本文の書き方に頼らず、外の人の PR や人が手で作った PR を、進行役の判定に入れないこと（SETUP-13 の 1 つのアカウントでも成り立つこと）

## 検討した選択肢（Considered Options）

問い 1：pass なのに CI が緑でないとき

- 案 1-A：赤（作業の結果による失敗）だけを修正に回し、結果が出ていないもの（チェックがまだ作られていない、保留）は待つ。取り消しなどは時間が経っても変わらなければ人に渡す
- 案 1-B：緑でなければ、すべて修正に回す
- 案 1-C：緑でなければ、すべて `needs-human` にする

問い 2：2 件目以降の `merge=ready`

- 案 2-A：判定を次の実行に回し、`merge` の印を書かない
- 案 2-B：`merge=human` を書く
- 案 2-C：1 件の上限を外す

問い 3：PR と Issue の結びつけ

- 案 3-A：head のブランチ名、同じリポ（fork でない）、進行役の署名付きの結びつきの印の 3 つで結びつける
- 案 3-B：`Closes #n` の結びつき（`closingIssuesReferences`）で結びつける
- 案 3-C：head のブランチ名だけで結びつける

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-A」。
理由: 修正のセッションは作業の結果が赤のときだけ起き、時間が解決するものは待ち、解決しないものは人に渡る。2 件目以降は判定を遅らせるだけで中身を変えないので、一致の記録が汚れない。PR と Issue の結びつきは、既定のブランチや本文に頼らず、進行役だけが作れる形になる。

### 決定 1：CI の結果ごとの扱い

必須チェック（IMPL-27 の一覧）ごとに結果を読み、1 つでも当てはまれば、表の上の行から順に扱いを決める。同じ head に同じ名前のチェックが複数あるとき（再実行）は、最新の 1 件を採る。

| CI の結果 | 扱い |
| --- | --- |
| `action_required` | `needs-human`（ワークフローの実行に人の承認が要る） |
| `failure`、`timed_out` | 修正に回す。失敗したチェックの名前と結果だけを、最新のラウンドの 🔴 として作業 AI に渡し、往復（IMPL-24）に数える。CI のログは渡さない（作業 AI は自分の作業場所で `pnpm check` を実行して確かめる） |
| チェックがまだ作られていない（push の直後）、`queued`、`in_progress`、`pending`、`waiting`、`requested` | 待つ。次の実行で読み直す |
| `cancelled`、`skipped`、`neutral`、`stale` | 待つ。同じ head で、完了から設定の時間が経っても変わらなければ `needs-human`（人が再実行するか、原因を確かめる） |
| すべて `success` | 緑 |

- 修正に回すときの `fix` の印の `round` は、最新の `review` の印の `round` と同じにする。修正の後は、今の流れのまま再レビューする（IMPL-23）
- マージの判定（MERGE-2）の時点で CI が緑でなければ、判定を次の実行に回し、`merge` の印を書かない（`merge=human` にしない）
- 「設定の時間」の初期値は、構造仕様の設定の表で決める（[ADR-20261015-005][adr-settings]）

### 決定 2：2 件目以降の `merge=ready` は、判定を次の実行に回す

- 1 回の実行で `merge=ready` にするのは 1 件まで（MERGE-5 のまま）。判定する順は PR の番号の小さい順
- 2 件目以降の、`merge=ready` になるはずの PR は、判定を次の実行に回し、`merge` の印を書かない（`merge=human` にしない）。Status は `Ready to Merge` のまま
- 次の実行では、人が 1 件目をマージしていれば、残りの PR は載せ直し（FLOW-25）と CI を経てから判定し直す。マージしていなければ、1 件目の印は変えず、2 件目以降は待つ
- `merge=human` の判定（満たさない条件がある PR）は、1 件の上限に数えない

### 決定 3：PR と Issue は、ブランチ名・同じリポ・署名付きの結びつきの印で結びつける

- 進行役は、次の 3 つをすべて満たす PR だけを、Issue に結びつける
  - (1) head のブランチ名が `<型>/issue-<番号>`（IMPL-2）
  - (2) head のリポが base と同じ（fork でない）
  - (3) 進行役の署名付きの結びつきの印がある
- 結びつきの印：PR を作った直後に、進行役は Issue に `note kind=link pr=<PR の番号>`、PR に `note kind=link issue=<Issue の番号>` の印付きのコメントを投稿する（ADR-20261015-004 の `note` に、`link` の種類と `pr` `issue` の欄を足す）。署名は印の種類・リポ・置き場の番号を含むので、別の Issue や PR に写しても通らない
- PR の作者のアカウントは条件にしない（SETUP-13 の 1 つのアカウントでは、作者で人と進行役を見分けられない）
- `Closes #<番号>` は、人向けの表示として PR の本文に書くが、結びつけには使わない（IMPL-6 の本文の規則は残す）
- 同じリポに、ブランチ名が一致するのに結びつきの印が無い PR があれば、Issue を `needs-human` にし、`note kind=stop reason=unlinked-pr` を投稿する。PR の作成と印の投稿の間で進行役が止まったときもこれに当たる（まれなので、人が確かめる）
- fork からの PR は、本文が Issue を参照していても扱わない
- Issue 1 件に結びつく PR は 1 件。結びついた PR がマージされていれば片付け（MERGE-7）へ進み、マージされずに閉じられていれば `needs-human`（人が閉じた意図を確かめる）

### 影響（Consequences）

- 良い点: 修正のセッションは、作業の結果が赤のときだけ起きる。push の直後でチェックがまだ作られていないときや保留で、往復を使わない
- 良い点: `merge=human` は「満たさない条件がある」ときだけになり、判定と人の判断の一致の記録（MERGE-3 の数え方。段階 8（進行役が PR にマージの判定の印を書き始める段階）の出口の条件と、マージの実行を進行役に移すかの判断（MERGE-9）に使う）が汚れない
- 良い点: 既定のブランチの設定に頼らずに PR と Issue を結びつけられ、外の人の PR と人が手で作った PR を判定に入れない
- 悪い点: CI の赤も往復に数えるので、往復の上限（3 回）を CI の失敗だけで使い切ることがある。壊れた変更を回し続けないので、`needs-human` でよい
- 悪い点: 段階 9（WIP の上限を 1 から上げる段階）に入ると、2 件目以降の判定が実行 1 回ずつ遅れる
- 悪い点: PR の作成と結びつきの印の投稿の間で進行役が止まると、人の確認が要る
- 悪い点: 印の種類 `note` に `link` と欄が増える

### 確認方法（Confirmation）

- `src/marker.ts` の単体テストで、`note kind=link` の印を別の Issue や PR に写すと署名が通らないことを検査する
- 結合テスト（偽の `gh`）で、次を検査する
  - CI の結果ごとに、表のとおり修正・待つ・`needs-human` に分かれること。マージの判定の時点で CI が緑でなければ、`merge` の印を書かないこと
  - 1 回の実行で `merge=ready` が 1 件だけになり、2 件目以降に `merge` の印を書かないこと
  - `Closes #n` を書いた fork の PR と、結びつきの印の無い同じリポの PR を、Issue に結びつけないこと。後者では `needs-human` になること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：赤だけ修正に回し、結果が出ていなければ待ち、取り消しなどは時間が経てば人に渡す

- 良い点: 修正のセッションを、作業の結果に原因があるときだけ起こす
- 悪い点: CI の結果の種類ごとの表を持つ必要がある

### 案 1-B：緑でなければ、すべて修正に回す

- 良い点: 規則が単純
- 悪い点: push の直後でチェックがまだ作られていないときや保留でも修正のセッションを起こし、利用枠と往復を無駄に使う

### 案 1-C：緑でなければ、すべて `needs-human`

- 良い点: 人がすべての CI の失敗を見る
- 悪い点: 作業 AI が直せる赤まで人に渡り、待てば済む保留でも止まる

### 案 2-A：判定を次の実行に回し、印を書かない

- 良い点: 判定の中身を変えず、一致の記録が汚れない
- 悪い点: 2 件目以降が実行 1 回ずつ遅れる

### 案 2-B：`merge=human` を書く

- 良い点: 人がすぐに印を見られる
- 悪い点: 人がマージすると「不一致」に数えられ、判定と人の判断の一致の記録（MERGE-3 の数え方。段階 8（進行役が PR にマージの判定の印を書き始める段階）の出口の条件と、マージの実行を進行役に移すかの判断（MERGE-9）に使う）が汚れる

### 案 2-C：1 件の上限を外す

- 良い点: 遅れない
- 悪い点: 1 件をマージすると残りは base が古くなり、ruleset の「base と最新であること」でマージできない。印が無駄になり、人が古い印でマージしようとして止まる

### 案 3-A：ブランチ名・同じリポ・署名付きの結びつきの印

- 良い点: 既定のブランチの設定に頼らない。進行役だけが作れる
- 悪い点: PR の作成と印の投稿の間で止まると、人の確認が要る

### 案 3-B：`Closes #n` の結びつき

- 良い点: GitHub の画面で結びつきが見える
- 悪い点: `develop` 向けの PR では結びつきが張られない（2026-10-16 に確かめた）。外の人の PR も本文に書けば結びつく
- 却下

### 案 3-C：ブランチ名だけ

- 良い点: 仕組みが小さい
- 悪い点: push の権限を持つ人が同じ名前のブランチで PR を作ると、進行役の PR と見分けられない
