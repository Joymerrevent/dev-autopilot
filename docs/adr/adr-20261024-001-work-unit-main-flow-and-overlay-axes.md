## 背景と課題（Context and Problem Statement）

- 今の形は、Issue の状態を Project の Status・Agent 欄・ラベルの 3 つで表し、Status と Agent 欄は人も進行 Bot も書く（「[Issue の状態の遷移][flow]」、SETUP-5・SETUP-6）。
  止まる・待つ・人が引き取る・攻撃の疑いは、どれも `needs-human` と Status の `Blocked`、または Agent 欄の値で表す
- Status を最後に変えた人は API で取れない（FACT-27・FACT-28）。進行 Bot は、印と PR の状態から決まる Status と Project の Status を比べ、人が戻す手順に当たるときだけ従い、ほかの違いは想定外の Status として止める（SAFE-4、[ADR-20261015-004][adr-markers] の決定 2）。
  基本設計の「[状態遷移と判定][design-flow]」には、食い違いを見分けるための「印と PR から許す Status」の表がある
- 人が止まった作業を戻す手順は、止めた理由ごとに順がある（Status を戻し、PR を閉じ、`agent-ready` を付け直し、最後に `needs-human` を外す）。
  基本設計の再レビュー（2026-10-20〜22）で、手順の順と閉じた PR の扱いの食い違いが続けて見つかり、[ADR-20261021-003][adr-reapprove]・[ADR-20261021-004][adr-marker-keys]・[ADR-20261022-005][adr-unlink] で 1 つずつ決めた
- メンテナの見立てでは、今の設計で決まっていることを生かそうとして状態の整理が込み入った。込み入った元は、Status と Agent 欄を人と進行 Bot が兼ねて書くこと、止まる・待つ・攻撃の疑いの軸を 1 列に並べたこと、段階による違い
- 2026-10-23〜24 に、メンテナと CC で、今の要件・ADR・基本設計を前提にせずに、目的（人が決めた依頼を AI が作業し、人がマージする）から状態遷移を組み直した。
  出来事を洗い出し、出来事と出来事の間で作業が何を待っているかを状態にし、同時に重なる条件を別の軸に分け、最後に GitHub での表し方を決めた。今の形との違いは、話題ごとに UNDECIDED-76〜81 に分けた

課題：作業の単位の状態を、どの模型で表すか。人の操作と、進行 Bot が書く表示を、どう分けるか。印をどう書くか。

## 判断の決め手（Decision Drivers）

- 人に見せる表示と、進行 Bot が次の工程を決める判定が、食い違わない
- 人の操作を、操作した人と時刻で確かめられる（Project の欄は、値を変えた人を API で取れない）
- 止まる・待つ・攻撃の疑いが重なっても、主な流れの状態と、戻り方が 1 通りに決まる
- 状態の正本を GitHub に置く（今の形と同じ）。進行 Bot が途中で止まっても、GitHub から続きが決まる
- 人は Project のカード 1 枚で作業の状態を読め、自分の番を探せる
- 印を、読み取りを自分で作らずに、決まった形で確かに読める（印は署名を確かめる元になる）

## 検討した選択肢（Considered Options）

- 案 1-A：主な流れの状態と、主な流れに重ねる 3 本の軸で表し、人の操作はラベルと見出しのコメントで受ける
- 案 1-B：今の形（Status・Agent 欄・ラベル）のまま、込み入った所を 1 つずつ直す
- 案 2-A：Project の表示は、主な流れと軸ごとに 1 つの欄にする
- 案 2-B：Project の表示は「状態」と「次の番」の 2 つの欄にする
- 案 3-A：印は、HTML のコメントの中に JSON を 1 行で書き、種類を `type` の欄に 1 つ持つ
- 案 3-B：印は今の書き方（スペースと `=` の欄、`note` と `kind` の 2 段）のままにする

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-A」。

理由: 表示と判定が 1 つの模型から出るので、2 つが食い違わない。人の操作は人だけが書く手段で受け、書いた人と時刻を GitHub で確かめられるので、想定外の Status のような食い違いの扱いが要らなくなる。
止まっている間も主な流れの状態は変わらないので、止まる前の状態ごとに戻る線を引かずに済み、戻す操作は `## 再開 <戻す先>` の 1 つで済む。表示の欄を軸ごとに分けると、軸どうしを 1 列に並べ直す順が要らない。印を JSON で書くと、欄の数と並びが決まった形で読める。

### 決定 1：作業の単位と、状態の区切り方

- 作業の単位は、Issue 1 件と、結びつく PR（[ADR-20261016-001][adr-pr] の決定 3 の条件で結びつく PR）をまとめた 1 つにする。人は Project のカード 1 枚で見る
- 作業の単位は、Issue が起票されて Project に入ったときに生まれる（Project の自動追加。SETUP-1）。人が決める前の Issue も追い、人が決める番も表示と判定に入れる
- 状態は、出来事と出来事の間で、作業が待っている場所にする。待つ場所は、次に動く担い手（人・AI・進行 Bot・CI）が替わる所と、AI の作業が 1 つ終わった所（確かめを通った計画ができた、変更ができた）で区切る。途中で切れても、区切りから続けられる
- 計画の輪（計画を書く → 計画を書いた AI とは別の AI が確かめる → 直す点があれば計画し直す）は、1 つの作業の中に置き、状態に分けない（輪の中身は UNDECIDED-77（段階と試し）の ADR で決める）
- 次に動く担い手と次の出来事が同じでも、直前の出来事が違い、次の作業に渡すものも違えば、状態を分ける。渡すものが同じなら 1 つにする。
  変更済み（最初の変更の後と、直した後）は、どちらも次に渡すものが PR の head なので 1 つにする。下書き済み（AI の下書きの後と、人の直しの後）も、どちらも次に渡すものが下書きなので 1 つにする
- 止まる・待つ・攻撃の疑いは、主な流れの状態にせず、主な流れに重ねる軸にする（決定 3）。止まっている間も主な流れの状態は変わらず、軸の値が外れたら同じ状態から続ける
- 状態の名前は、済ませた事実で付ける（例：下書き済み、レビュー不合格）。次に動く担い手は名前に入れない

| T22 | 変更の枠のレビュー合格のほかの状態 → マージ済み | 人がマージした（レビュー合格の前でも、引き取り中でも同じ） | 本 ADR |
| T27 | マージ済み → 完了 | 進行 Bot が片付けた | UNDECIDED-81 |
| T28 | 閉鎖済み → 中止 | 進行 Bot が片付けた | UNDECIDED-81 |

- 線の番号は、組み立てた順に付けた。T23〜T26 と T31 は、組み立ての途中で取り消した線で、使わない
- 人が PR に push したら、変更の枠のどの状態からでも変更済みに入る（新しい head ができ、次に渡すものが head で同じ）
- 人のマージは、PR のあるどの状態からでもマージ済みに入る（マージは人の最後の操作）
- 次に動く担い手は、Project の表示の欄には出さない（決定 5）。進行 Bot が次に何をするかの決め方と、図の箱の色に使う

### 決定 3：主な流れに重ねる 3 本の軸

止める・待つ・攻撃の疑いは、主な流れに重ねる 3 本の軸で表す。3 本は同時に値を持てる。

| 軸 | 値 | 中身を決める所 |
| --- | --- | --- |
| 止め方 | （なし）・一時停止中・引き取り中・停止中 | 本 ADR |
| 先の依頼 | （なし）・未完了・中止あり | 未完了は本 ADR、中止ありは UNDECIDED-81 |
| 安全 | （なし）・攻撃の疑い（入口）・攻撃の疑い（AI の文） | UNDECIDED-80 |

止め方の線：

| 線 | 元 → 先 | 出来事 |
| --- | --- | --- |
| S1 | （なし）→ 一時停止中 | 人が `agent-paused` を付けた |
| S2 | 一時停止中 →（なし） | 人が `agent-paused` を外した（戻す先は決定 7） |
| S3 | （なし）→ 引き取り中 | 人が `agent-manual` を付けた（AI の作業を人の手で進める） |
| S4 | 引き取り中 →（なし） | 人が `agent-manual` を外した（戻す先は決定 7） |
| S5 | （なし）→ 停止中 | 進行 Bot が止めて人に渡した（止めた理由は決定 7） |
| S6 | 停止中 →（なし） | push 以上の人が `## 再開 <戻す先>` を書いた |

先の依頼の線：

| 線 | 元 → 先 | 出来事 | 中身を決める所 |
| --- | --- | --- | --- |
| D1 | （なし）→ 未完了 | 先の依頼（GitHub の依存の blocked by）が足された。主な流れが決定済みか、決定済みより後のときだけ。決定済みに入ったときに終わっていない先の依頼があっても入る | 本 ADR |
| D2 | 未完了 →（なし） | 先の作業が終わった | 本 ADR（終わりの決め方は UNDECIDED-81） |
| D3 | 未完了 → 中止あり | 先の作業が閉鎖済みになった | UNDECIDED-81 |
| D4 | 中止あり →（なし） | AI が計画を見直し、計画を変えずに進めてよいと判断した | UNDECIDED-81 |
| D5 | 中止あり →（なし） | AI が計画を変える必要があると判断し、止め方を停止中にした | UNDECIDED-81 |

安全の線（すべて UNDECIDED-80 で中身を決める）：

| 線 | 元 → 先 | 出来事 |
| --- | --- | --- |
| Q1 | （なし）→ 攻撃の疑い（入口） | AI に渡す前の検疫で見つかった |
| Q2 | （なし）→ 攻撃の疑い（AI の文） | AI が書いた文の検疫で見つかった |
| Q3 | 攻撃の疑い（入口）→（なし） | 人が文を確かめて直し、`## 安全の確認` を書いた |
| Q4 | 攻撃の疑い（AI の文）→（なし） | 人が確かめ、`## 安全の確認` を書いた |

- どれかの軸に値がある間、AI は主な流れを進めない。人の push（T16）、人のマージ（T15・T22）、人が Issue を閉じること（T21）は、軸の値を問わず起きる。片付け（T27・T28）を軸の値を問わず行うかは、UNDECIDED-81 の ADR で決める
- 先の依頼は、決定済みと、決定済みより後の状態で効く。PR ができた後に足された先の依頼も待つ（変更の確かめと直しも止める）。起票済みから下書き済みまで（直し済み・差し戻し済みを含む）は、先の依頼を待たずに進める（下書きと人が決めることは、先の依頼と関わりなく進められる）
- 止め方と先の依頼を別の軸にするのは、先の依頼が人の操作と関わりなく終わるため。安全を止め方と別の軸にするのは、外し方が違い（決定 4 の `## 安全の確認`）、止め方と同時に値を持ちうるため

### 決定 4：状態の正本と、人の操作の手段と権限

- 状態の正本は GitHub だけにする。進行 Bot は、毎回の実行で、Issue・PR・ラベル・進行 Bot の署名付きの印・必須チェックの結果から状態を組み立てる。手元の記録は、費用や失敗の回数の数え上げにだけ使う（[ADR-20261015-006][adr-flow] の決定 4 のまま）
- 人が書くものと進行 Bot が書くものを分ける。人の操作は人だけが書く手段で受け、進行 Bot が書く欄（Project の欄）は表示だけにして、判定に読まない
- 続く様子を表す操作（決める・一時止める・引き取る）はラベル、文を伴う操作は固定の見出しのコメントで受ける。どちらも、操作した人と時刻を GitHub の timeline で確かめられる

| 操作 | 手段 | 名前 | 要る権限 | 読むときの確かめ |
| --- | --- | --- | --- | --- |
| 決める | ラベル | `agent-ready` | push 以上 | 付けた人と時刻（timeline の付けた記録） |
| 一時止める | ラベル | `agent-paused` | push 以上 | 同じ |
| 引き取る | ラベル | `agent-manual` | push 以上 | 同じ |
| 下書きを直す | 見出しのコメント | `## 作業指示` | push 以上 | 書いた人、最後に編集した人と時刻 |
| 差し戻す | 見出しのコメント | `## 差し戻し` | push 以上 | 書いた人と時刻 |
| 再開する | 見出しのコメント | `## 再開 続きから`・`## 再開 下書きから`・`## 再開 計画から` | push 以上 | 書いた人と時刻 |
| 安全を確かめた | 見出しのコメント | `## 安全の確認` | maintain 以上 | 書いた人と時刻 |
| 仕組みの変更を認める | 見出しのコメント | `## 仕組みの変更の承認` | UNDECIDED-79 で決める | 書いた人と時刻 |
| 先の依頼を足す | GitHub の依存（blocked by） | — | — | — |
| マージ・Issue を閉じる・push | GitHub の操作 | — | — | Issue を閉じた人は timeline で確かめる（UNDECIDED-81） |

- ラベルの名前は、`agent-` を頭に付けて「AI の作業の様子」として続けて読めるようにする。引き取るを `agent-takeover` にしないのは、「AI に引き継ぐ」とも読めるため
- 見出しの名前は、今の見出し（`## 作業指示`・`## 却下 R<n>`・`## 異議`）と同じく名詞にそろえる
- 権限の無い人が書いたものは、無いものとして読む。権限は、今のとおり読む直前に 1 人ずつ引く（TEXT-10）
- `## 作業指示`・`## 差し戻し`・`## 仕組みの変更の承認` の中身と使い方は UNDECIDED-79、`## 安全の確認` は UNDECIDED-80 の ADR で決める。本 ADR は、手段と名前と、`## 仕組みの変更の承認` のほかの権限を決める
- 今の Agent 欄（`worker`・`reviewer`・`human`・`paused`）は使わない。Status の値も判定に読まない

### 決定 5：Project の表示

- 進行 Bot は、主な流れと軸ごとに 1 つの欄を、毎回の実行で Project に書く。どれも表示だけで、判定に読まない

| 欄 | 中身 | 例 |
| --- | --- | --- |
| 主な流れの枠 | 依頼・計画・変更・終了 | 依頼 |
| 状態 | 主な流れの 17 の状態の名前 | 下書き済み |
| 止め方 | （なし）・一時停止中・引き取り中・停止中 | 停止中 |
| 先の依頼 | （なし）・未完了・中止あり | 未完了 |
| 安全 | （なし）・攻撃の疑い（入口）・攻撃の疑い（AI の文） | 攻撃の疑い（入口） |

- 主な流れの枠には、Project にもともとある Status 欄を使い、名前を「主な流れの枠」に変える（ボードの列が 4 つで済む）。Status 欄の名前を変えられなければ、同じ働きの欄を新しく作る（変えられるかは、確かめてから[実機で確かめた事実][facts]に載せる）
- 「次の番」（次に動く担い手）の欄は持たない。人が自分の番を探すときは、軸ごとにビューを分けて見る

| ビューの例 | 絞り込み |
| --- | --- |
| 人が決める・マージする番 | 状態が、下書き済みかレビュー合格 |
| 止まっている作業 | 止め方が、停止中・一時停止中・引き取り中のどれか |
| 攻撃の疑い | 安全が、（なし）でない |
| 待っている作業 | 先の依頼が、（なし）でない |

- 攻撃の疑いを知らせる表示のラベル（`security-suspected`）は、UNDECIDED-80 の ADR で決める。表示のラベルも判定には読まない

### 決定 6：状態の決め方

進行 Bot は、毎回の実行で、次の順に読んで状態を組み立てる。

1. 戻した後の読み方（決定 7）で、数えない印と PR を外す
2. 主な流れの状態を、下の表で決める。表を上から見て、最初に当てはまった行の状態にする
3. 主な流れが依頼の中の状態なら、依頼の中の表で決める
4. 3 本の軸の値を決める

主な流れは、事実が重なったときに、進んだほうを先に見る（終了 → 変更 → 計画 → 決定 → 依頼）。変更の枠の中だけは、検査不合格をレビュー合格より先に見る。レビュー合格の後に必須チェックが赤に変わったら、検査不合格と読み、AI に直させる（マージの前に赤を見逃さない）。決定済みより後の状態では、`agent-ready` を読まない。

| 順 | 状態 | 条件 |
| --- | --- | --- |
| 1 | 完了 | 結びつく PR がマージされ、`cleanup` の印がある |
| 2 | マージ済み | 結びつく PR がマージされ、`cleanup` の印が無い |
| 3 | 中止 | push 以上の人が Issue を閉じ、結びつく PR がマージされておらず、`cleanup` の印がある |
| 4 | 閉鎖済み | push 以上の人が Issue を閉じ、結びつく PR がマージされておらず、`cleanup` の印が無い |
| 5 | 衝突あり | 開いた結びつく PR があり、head に `conflict` の印がある |
| 6 | 検査不合格 | 開いた結びつく PR があり、head の必須チェックに `failure` か `timed_out` がある |
| 7 | レビュー不合格 | 開いた結びつく PR があり、head の最新の `review` の印の `result` が `fix` |
| 8 | レビュー合格 | 開いた結びつく PR があり、head の最新の `review` の印の `result` が `pass` で、必須チェックがすべて `success` |
| 9 | 検査合格 | 開いた結びつく PR があり、必須チェックがすべて `success` で、head に `review` の印が無い |
| 10 | 変更済み | 開いた結びつく PR があり、順 5〜9 に当たらない（必須チェックがまだ無いか、動いている途中など） |
| 11 | 計画済み | 開いた結びつく PR が無く、数える `plan` の印がある |
| 12 | 決定済み | 依頼の中の表で下書き済みになり、有効な `agent-ready` がある（有効なラベルの条件は UNDECIDED-79） |
| 13 | 依頼の中の状態 | 順 1〜12 に当たらない。依頼の中の表で決める |

- push 未満の人が Issue を閉じたときの読み方は、UNDECIDED-81 の ADR で決める
- 必須チェックのほかの結果（`action_required`、`cancelled` など）の読み方は、[ADR-20261016-001][adr-pr] の決定 1 の中身のまま（`needs-human` は停止中と読む。決定 11）

依頼の中の表（中身は UNDECIDED-79 の ADR で決める）。「人の操作」は push 以上の人が書いた `## 作業指示`（投稿か編集）と `## 差し戻し`、「マスター」は最新のマスターの下書き（`draft` の印）：

| 順 | 状態 | 条件 |
| --- | --- | --- |
| 1 | 起票済み | Issue が Project にあり、Issue の入口の検疫を通った印（`quarantine` の印の `target` が `issue`）が無い |
| 2 | 検疫済み | マスターがまだ無い |
| 3 | 差し戻し済み | 最新の人の操作が `## 差し戻し` で、マスターより新しい |
| 4 | 直し済み | 最新の人の操作が `## 作業指示` で、マスターより新しい |
| 5 | 下書き済み | マスターが、最新の人の操作より新しい |

軸の値の決め方：

- 1 本の軸に当てはまる値が 2 つ以上あるときは、人が外すのに手間がかかるほうを上にして、上の値を出す。止め方は 停止中 → 引き取り中 → 一時停止中、先の依頼は 未完了 → 中止あり、安全は 攻撃の疑い（AI の文）→ 攻撃の疑い（入口）。下の値は消えずに残り、上の値が外れると次の値が出る。軸どうしは別の欄（決定 5）なので、重なりは軸の中だけで起きる
- 止め方：最新の `stop` の印が、最新の `## 再開` より新しければ停止中。権限のある人が付けた `agent-manual` があれば引き取り中。権限のある人が付けた `agent-paused` があれば一時停止中
- 先の依頼：決定済みより前の状態では見ない。依存の相手のどれかが終わっていなければ未完了（終わりの決め方と、中止ありの条件は UNDECIDED-81）
- 安全：UNDECIDED-80 の ADR で決める

### 決定 7：止めて人に渡すことと、再開と戻す先

- AI の作業が失敗したら（時間切れ、異常終了など）、同じ状態からやり直す。失敗が続いたら、止めて人に渡す（停止中）
- 直す往復が終わらない、計画の輪が終わらない、費用の上限に達したときも、止めて人に渡す
- PR だけが閉じられたら、止めて人に渡し、人が戻す先を選ぶ（閉じた意図が、やめたいのか作り直したいのか分からないため）。Issue が閉じられたときは、UNDECIDED-81 の ADR で決める
- 検疫で見つかったときは、止め方でなく安全の軸に値を入れる（UNDECIDED-80）
- 止めるときは、進行 Bot が `stop` の印を書き、`reason` に止めた理由の記号を書く。記号は、組み直した形で止まる場面から並べ直した 14 個にし、今の 24 個は引き継がない

| 記号 | 止まる場面 | 中身を決める所 |
| --- | --- | --- |
| `retry-limit` | AI の作業の失敗が続いた | 本 ADR |
| `round-limit` | 直す往復が上限に達した | 本 ADR |
| `repeated-finding` | 直したはずの指摘が、また出た | 本 ADR |
| `plan-limit` | 計画の輪が、上限まで回っても終わらない | UNDECIDED-77 |
| `cost-limit` | 費用の上限に達した | 本 ADR |
| `pr-closed` | PR だけが閉じられた | 本 ADR |
| `cleanup-failed` | 片付けが失敗し続けた | UNDECIDED-81 |
| `plan-change` | 先の依頼が中止になり、AI が計画を変える必要があると判断した | UNDECIDED-81 |
| `unauthorized-close` | push 未満の人が Issue を閉じた | UNDECIDED-81 |
| `protected-path` | 変えてはいけないパスに当たった（計画の後か、push の前） | UNDECIDED-79 |
| `manual-push` | push で動くものの差分を人に渡した（人が push するのを待つ） | UNDECIDED-79 |
| `marker-invalid` | 進行 Bot の印が書き換えられた | 本 ADR |
| `ci-action-required` | CI を動かすのに、人の承認が要る | 本 ADR |
| `ci-stale` | 取り消しなどの結果のまま、決めた時間を過ぎた | 本 ADR |

- 実装の都合で止める理由（作業場所の書き換え、push の先端のずれ、AI のセッションを止められない、ブランチ名が一致するのに結びつきの印が無い PR など）の記号は、詳細設計で足す。マージの判定の `reasons` の記号は、今の設計のまま使う
- 再開では、人が戻す先を選ぶ。push 以上の人が書いた最新の `## 再開 <戻す先>` を R とする

| 戻す先 | 数えないもの | 続ける状態 |
| --- | --- | --- |
| 続きから | 無い | 同じ状態。PR が閉じているときは選べない |
| 計画から | R より前の `plan`・`review`・`fix`・`merge`・`conflict` の印と、R より前の PR。開いている前の PR は、進行 Bot が閉じる | 決定済み（AI が計画し直す） |
| 下書きから | 計画からの数えないものに加えて、R より前に付けた `agent-ready` と、R より前の `decision` の印 | 依頼の中の表で決める（ふつうは下書き済み。マスターより新しい `## 作業指示` があれば直し済み）。人は依頼を読み直して決め直す |

- 人は戻す先を選ぶだけで、残った PR は進行 Bot が閉じる（人の操作が 1 回で済む）。計画が誤っていたときや、決めた後に依頼を直したいときは、止めてから計画からか下書きからに戻す
- 一時停止中と引き取り中は、ラベルを外せば続きから。ほかの戻す先にしたいときは、ラベルを外す前に `## 再開 <戻す先>` を書く（ラベルを付けた後に書いた R の戻す先で続ける）。停止中は、`## 再開 <戻す先>` で終える
- 進行 Bot の印の署名が合わないか、印が編集されたときは、誰が書き換えても停止中にする（`marker-invalid`）。`stop` の印の `comments` の欄と、人向けの本文に、書き換えられた印のコメントを挙げる。
  人が中身を確かめて再開した後は、挙げた印を無いものとして読み、読んだ結果の状態から続ける（例：マスターの下書きが書き換えられていたら、マスターが無いものとして読み、検疫済みに戻って AI が下書きを書き直す）。人は、書き換えられた印を消したり直したりしなくてよい。再開の後に新しく書き換えられた印では、また止める

### 決定 8：状態遷移に入れない出来事

次の出来事は、状態も線も足さずに、状態遷移の外で扱う。

| 出来事 | 見つけ方 | 扱い | 中身を決める所 |
| --- | --- | --- | --- |
| 決めた後に依頼が変わる | 決定済みより後に、`## 作業指示` が書かれたか、Issue の本文が変わった | 読まない（AI には決めたときのマスターだけを渡す） | UNDECIDED-79 |
| レビュー合格の後に検査が落ちる | head の必須チェックが赤になった | 検査不合格と読む（止めない。決定 6） | 本 ADR |
| 触ってはいけない所を変える | 計画が変える見込みのパスか、変更が触れたパスが、変えてはいけないパスの一覧に当たった | 停止中（`protected-path`） | UNDECIDED-79 |
| 記録が書き換えられる | 印の署名が合わないか、印が編集された | 停止中（`marker-invalid`。決定 7） | 本 ADR |
| 人が順番を飛ばす（下書きの前に決める） | マスターより前に `agent-ready` が付いた | ラベルを数えない | UNDECIDED-79 |

### 決定 9：印の書き方と名前

- 進行 Bot の印は、HTML のコメントの中に JSON を 1 行で書く。印の種類は `type` の欄に書き、今の `note` と `kind` の 2 段の分け方はやめて、印ごとに種類を 1 つ持つ

  ```text
  <!-- dev-autopilot {"type":"review","round":2,"head":"1a2b3c","result":"fix","sig":"…"} -->
  ```

- 署名は、`sig` を除いた欄に、印の置き場（リポと Issue か PR の番号）を加え、決まった並べ方にそろえた JSON に掛ける（並べ方は詳細設計で決める）。別の Issue や PR に写した印は、署名が通らない（[ADR-20261015-004][adr-markers] の決定 1 と同じ）
- 名前の付け方：種類（`type`）は名詞、欄の名前は camelCase、値は小文字の英単語（2 語以上は `-` でつなぐ）
- 判定の結果を入れる欄の名前は、どの印も `result` にそろえる。値の組は `type` で決まる（`review` は `pass` か `fix`、`merge` は `ready` か `human`、`dependency-review` は `keep` か `change`）
- `fix` の印に `cause`（`check`・`review`・`conflict`。何を直したか）を足す。往復の数え方や記録の集計で、何を直した往復かを印だけで分けられる
- 印の種類は次の 21 個。名前と欄は本 ADR で決め、書くときの条件と中身は「中身を決める所」の ADR で決める

| 種類（`type`） | 書くとき | 置き場 | 欄（`type` と `sig` のほか） | 中身を決める所 |
| --- | --- | --- | --- | --- |
| `quarantine` | 入口の検疫を通った（T29）、人の直しの検疫を通った（T30） | Issue | `target`（`issue` か `instruction`）、`comment`（`instruction` のとき、検疫した作業指示のコメントの ID）、`textHash` | UNDECIDED-79 |
| `draft` | マスターの下書きを投稿した（T2・T3・T30） | Issue | `source`（`ai` か `instruction`）、`textHash` | UNDECIDED-79 |
| `decision` | 決めるラベルを見つけた（T6） | Issue | `draft`（決めたマスターのコメントの ID）、`textHash` | UNDECIDED-79 |
| `plan` | 計画を投稿した（T7） | Issue | `baseHead`、`planHash`、`model` | 本 ADR |
| `link` | PR を作った（T8） | Issue と PR | Issue には `pr`、PR には `issue`（相手の番号） | 本 ADR |
| `review` | 変更を確かめた（T11・T12） | PR | `round`、`head`、`result`、`high`・`medium`・`low`（件数）、`droppedHigh`、`findings`（指摘の ID の並び）、`model` | 本 ADR |
| `fix` | AI が直した（T13・T14・T20） | PR | `round`、`head`、`cause` | 本 ADR |
| `conflict` | 載せ直しが衝突した（T19） | PR | `head` | UNDECIDED-81 |
| `merge` | マージの判定をした（決定 10） | PR | `head`、`result`、`reasons`（満たさない条件の記号の並び） | 本 ADR |
| `remind` | 催促した（決定 10） | PR | `head` | 本 ADR |
| `stop` | 停止中にした（S5） | Issue（PR が契機なら PR にも） | `reason`（記号）、`comments`（書き換えられた印のコメントの ID の並び） | 本 ADR |
| `wait` | 先の依頼で待つ（D1） | Issue | `blockedBy`（先の Issue の番号の並び） | 本 ADR |
| `dependency-review` | 中止ありの計画を見直した（D4・D5） | Issue | `dependency`（相手の番号）、`result` | UNDECIDED-81 |
| `security` | 攻撃の疑いを見つけた（Q1・Q2） | Issue（PR が契機なら PR にも） | `where`（`entry`・`text`・`code`）、`finding`（見つかった種類。見つかった文は写さない） | UNDECIDED-80 |
| `cleanup` | 片付けた（T27・T28） | Issue | — | UNDECIDED-81 |
| `halt` | 全体を止めた | 全体の停止の Issue | `issue`（見つけた作業の番号） | UNDECIDED-80 |
| `approval-reset` | 無効な `agent-ready` を外した | Issue | `label`、`reason`（`stale`・`early`・`permission`） | UNDECIDED-79 |
| `ignored-instruction` | 決めた後の作業指示を読まなかった | Issue | `comment`（作業指示のコメントの ID） | UNDECIDED-79 |
| `manual-push` | push で動くものの差分を人に渡した | Issue | `head`、`paths`（並び） | UNDECIDED-79 |
| `follow-up` | 🟢 を新しい Issue にした（決定 10） | 新しい Issue | `pr`、`finding`（指摘の ID） | 本 ADR |
| `overlap` | AI の変更が触ったファイルが、ほかの進行中の PR と重なった（1 回だけ警告し、待たせない） | Issue | `prs`（重なった PR の番号の並び）、`paths`（重なったパスの並び） | 本 ADR |

- 今の印との対応：`plan`・`review`・`fix`・`merge` は名前を変えない（`review` の `verdict` と `merge` の `merge` は `result` に、`dropped_high` は `droppedHigh` にする）。`note` の `kind` の `wait`・`overlap`・`remind`・`stop`・`link` は、同じ名前の種類にする。
  `intake` と `intake-final` は、UNDECIDED-79 の ADR で `quarantine`・`draft`・`decision` に置き換えるかを決める
- 今の `note kind=raise`（作業 AI のモデルを上げた）は、作業ごとに使うモデルの決め方を決めるときに一緒に決める。今の `note kind=duplicate`（🟢 の重複の Issue に PR の番号を足した）と `note kind=conflict`（段階による載せ直しの衝突）の扱いは、本 ADR では決めない
- 人は進行 Bot のコメントを編集しない（今のまま）。署名が合わないか、編集された印は無効として扱う（決定 7）

### 決定 10：今の設計から模型に入れた 4 つ

今の設計にあって、組み直した模型に無かった 4 つを、状態を足さずに入れる。

- 着手の条件：決定済みから計画の輪（T7）に進む前に、マイルストーンがある・進行中の数が上限の内・base の CI が緑、を確かめる。外れたら決定済みのまま待つ（FLOW-1・FLOW-3・IMPL-9 のまま）。
  進行中の数は、計画済みから、マージ済み・閉鎖済みの前までの作業を数える。軸に値がある作業も数える（人の対処を待つ作業があるうちに、新しい作業を積み増さない）。着手の条件を満たした決定済みの作業を、どの順に計画に進めるかは、基本設計で決める
- マージの判定：レビュー合格の間に、進行 Bot がマージしてよいかを判定し、`merge` の印（`result` が `ready` か `human`）を PR に書く。マージは人のまま（MERGE-2・MERGE-3）
- 🟢 の起票：レビュー合格に入るとき（T11）に、見送った軽い指摘を新しい Issue にする（`follow-up` の印）。新しい Issue は、新しい作業の単位として起票済みから始まる（IMPL-26）
- 催促：レビュー合格のまま決めた日数を過ぎたら、1 回だけ催促を書く（`remind` の印。MERGE-3）

### 決定 11：ほかの承認済みの ADR の読み替え

`needs-human`・Status・Agent 欄・`note` の印に触れる承認済みの ADR は、本 ADR の承認の後、次のように読む。決定の中身（止める・人に渡すなど）は変えず、表し方だけを読み替える。

| 承認済みの ADR の書き方 | 本 ADR の後の読み方 |
| --- | --- |
| `needs-human` を付ける（Status を `Blocked` にする） | 止め方を停止中にし、`stop` の印を書く。検疫で見つかったときの読み方は、UNDECIDED-80 の ADR で決める |
| `note kind=stop reason=<記号>` | `stop` の印。記号は決定 7 の 14 個と、詳細設計で足す実装の都合の記号に読み替える |
| 人が `needs-human` を外す（Status を `Todo` か `In Review` に戻してから） | push 以上の人が `## 再開 <戻す先>` を書く。`Todo` に戻すのは計画から、`In Review` に戻すのは続きからと読む |
| Agent 欄を `paused` にする・戻す | `agent-paused` を付ける・外す |
| Agent 欄を `human` にする・`worker` に戻す | `agent-manual` を付ける・外す |
| 進行 Bot が Status を変える、Agent 欄を `worker`・`reviewer`・空にする | 進行 Bot が表示の欄（決定 5）を書く。判定には読まない |
| `note kind=wait`・`overlap`・`remind`・`link` の印 | `type` が同じ名前の印（決定 9） |

### 影響（Consequences）

- 良い点: 表示と判定が同じ模型から出るので、2 つが食い違わない。想定外の Status と、「印と PR から許す Status」の表が要らなくなる
- 良い点: 人の操作を、書いた人と時刻で確かめられる。人が止まった作業を戻す操作は、`## 再開 <戻す先>` の 1 つで済み、止めた理由ごとの戻す順（[ADR-20261022-005][adr-unlink] の決定 2）が要らなくなる
- 良い点: 止まっている間も主な流れの状態が残るので、止まる前の状態ごとに戻る線を引かずに済む
- 良い点: 止まっている理由・待っている理由・攻撃の疑いが別の欄に出て、人は軸ごとのビューで自分の番を探せる
- 良い点: 印を JSON で書くので、欄の数と並びが決まった形で読め、読み取りを自分で作らずに済む
- 悪い点: 要件・基本設計・図の多くを書き直す（「Issue の状態の遷移」、「止まった状態から戻す手順」、次の工程の表、印と固定の見出しの一覧、stop の理由の記号、図 `issue-flow` など）。書き直すまで、要件と基本設計が本 ADR より古いまま残る
- 悪い点: 人が覚える操作が増える（ラベル 3 つと、見出し 5 つ）
- 悪い点: Project の欄が 5 つになり、`setup` が作る欄と選択肢が増える。Status 欄の名前を変えられるかは、まだ確かめていない
- 悪い点: 次に動く担い手の欄が無いので、人の番は、軸ごとに分けたビューで探す
- 悪い点: 印の書き方を変えるので、基本設計の印の例と、テストの前提を書き直す

### 確認方法（Confirmation）

- 基本設計の「作業の単位の状態遷移」の節の表と図が、本 ADR の決定 2〜7 と一致していることを、設計のレビューで確かめる
- 単体テストで、状態の決め方（決定 6）を、GitHub の事実の組み合わせごとに確かめる（事実が重なったときの順、戻した後の読み方、軸の値の上下）
- 単体テストで、印の JSON の読み書きと署名を確かめる（置き場の番号を変えた印と、欄を変えた印の署名が通らない）
- 結合テスト（偽の `gh`）で、一時止める・引き取る・3 つの戻す先での再開・PR だけを閉じる・印の書き換えの場合ごとに、表示の欄と、進行 Bot の次の工程が決定どおりになることを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：主な流れの状態と、重ねる 3 本の軸で表し、人の操作はラベルと見出しのコメントで受ける

- 良い点: 表示と判定が同じ模型から出る
- 良い点: 人の操作を、書いた人と時刻で確かめられる。Project の欄の値を変えた人を取れない問題（FACT-27・FACT-28）に頼らない
- 良い点: 止まる・待つ・攻撃の疑いを、主な流れと別に表すので、主な流れの状態が止まる前のまま残り、戻り方が 1 通りに決まる
- 中立: 人の操作の手段と、表示の欄が変わるので、人が慣れるまで手間がかかる
- 悪い点: 要件・基本設計・図の書き直しが大きい

### 案 1-B：今の形のまま、込み入った所を 1 つずつ直す

- 良い点: 要件と基本設計の書き直しが小さい
- 悪い点: Status と Agent 欄を人と進行 Bot が兼ねて書くので、食い違いを見分ける決まり（想定外の Status、印と PR から許す Status）が残る
- 悪い点: 止まる・待つ・攻撃の疑いが `needs-human` と Status にまとまったままで、止めた理由ごとに戻す順を決め続ける。再レビューのたびに、戻す手順の食い違いが見つかっていた

### 案 2-A：Project の表示は、主な流れと軸ごとに 1 つの欄にする

- 良い点: 図と同じ形で、軸どうしが重なったときの順が要らない
- 良い点: 軸ごとのビューで、人が自分の番を探せる
- 悪い点: 欄が 5 つになる

### 案 2-B：Project の表示は「状態」と「次の番」の 2 つの欄にする

- 良い点: 欄が 2 つで済み、人は「次の番が人」のカードだけを絞り込める
- 悪い点: 「次の番」に、次に動く担い手と軸の値（停止中、攻撃の疑い、先の依頼の未完了）を入れるので、軸を 1 列に並べ直す順が要り、込み入る（組み直す前の形と同じ問題）

### 案 3-A：印は、HTML のコメントの中に JSON を 1 行で書く

- 良い点: 数と並びの形が決まっていて、読み取りを自分で作らずに済む。印は署名を確かめる元なので、読み取りの確かさを優先する
- 良い点: 種類を `type` の 1 段にするので、`note` の中を `kind` で分ける 2 段が無くなる
- 悪い点: 署名の前に、JSON の並べ方をそろえる決まりが要る（詳細設計で決める）

### 案 3-B：印は今の書き方のままにする

- 良い点: 要件と基本設計の印の例を書き直さずに済む
- 悪い点: スペースと `=` の欄の読み取りと、`note kind=link` のような 2 段の分け方が分かりにくい（メンテナの指摘）
- 悪い点: 値に空白や `=` を含めるときの決まりを、自分で作って保つことになる
