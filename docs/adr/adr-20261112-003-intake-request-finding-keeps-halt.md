# 受け入れの依頼で受付 AI の下書きが検疫に当たったときも、見つかりの記録を書いて次の実行から全体を止め、印は作業の単位を進める次の実行が GitHub に書く

要件の UNDECIDED-98（人が `/verify-issue` などから呼ぶ受け入れの Skill（`intake`）の依頼で起こされた実行で、受付 AI が返した下書きが検疫で見つかったときに、見つかりの記録を書いて次の実行から全体を止めるか。[決めていないこと][undecided]の「ADR で決めること」の「安全と設定」）を決める。

## 背景と課題（Context and Problem Statement）

- SAFE-19 と [ADR-20261024-005][adr-security] の決定 3 は、AI が書いた文（GitHub に書く前）の検疫で見つかったら、進行 Bot が全体の停止の Issue を開き、どの作業の単位でも AI のセッションを起こさないとする。AI が操られた疑いがあり、同じ手口がほかの作業に届いているかもしれないため。決定 3 は、実行の起こされ方で分けていない
- [ADR-20261111-001][adr-keep-halt] は、AI が書いた文の検疫で見つけたら、GitHub に書く前に手元に見つかりの記録を残し、記録がある間は全体の停止の Issue があるものとして扱うとした。作業の単位を進める次の実行（1 回の実行の流れの順 6〜9（基線を読み、状態を組み立て、作業の単位を進める）に進む実行）が、記録から `security` の印と全体の停止の Issue（`halt` の印）を書き直し、両方を書けたら記録を消す
- 人が `/verify-issue` などから呼ぶ受け入れの Skill（`intake`）の依頼で起こされた実行（以下「受け入れの依頼の実行」）は、GitHub に何も書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。受付 AI が返した文の欄（下書きの 4 つの欄と `policyReason`）が検疫に当たったときも、見つかった種類と場所を結果のファイルにだけ書く（同じ ADR の決定 3）。[ADR-20261022-004][adr-intake-req] は、全体の停止の Issue を決めた [ADR-20261024-005][adr-security] より前に決めたので、全体の停止を扱っていない
- [ADR-20261111-001][adr-keep-halt] は、受け入れの依頼の実行で見つけたときを「本 ADR で決めないこと」に残した。今の設計は、見つかりの記録を書かず、全体を止めない（詳細設計の「[設定と記録][d-records]」の「見つかりの記録」の「書かないとき」、「[1 回の実行の流れ][d-flow]」の「全体の停止と通知」の「攻撃の疑いにする」の行とテストの表）
- 見つけた AI の文は GitHub に無く、受付 AI の出力は回ごとに変わるので、次の実行の検疫が見つけ直すとは限らない。Issue の文で見つかったとき（`where` が `entry`）は、文が GitHub に残るので、作業の単位を進める実行が、入口の検疫で同じ文を見つけ直す。見つけ直せないのは、AI が書いた文（`where` が `text`）だけである
- 受付 AI は、定期の実行で下書きを書くときも、受け入れの依頼の実行でも、同じエージェント（`dev-autopilot:brief:triager`）を、同じ起動の形・安全設定と、同じ組み立てで作った Issue の文で起こす（基本設計の「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」の順 6、詳細設計の「[文の検査と受け入れ][d-text]」の「掛ける文」）
- 受け入れの依頼は Issue の番号だけを持つ。intake の Skill の「下書き」も、受け入れの依頼の実行も、Issue が Project にあるか（作業の単位か）を確かめない（基本設計の「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」の順 3〜7、詳細設計の「[文の検査と受け入れ][d-text]」の「人が呼ぶ intake」、「[1 回の実行の流れ][d-flow]」の `flow/run/intake.ts`）。Project に無い Issue にも、受け入れの依頼を置ける
- 進行 Bot の GitHub App は、当てる先のリポの Issues に書く権限を持つ（基本設計の「[導入と点検][design-setup]」の GitHub App の権限の表）。Project に無い Issue にもコメントを書ける。見つかりの記録からの書き直し（[ADR-20261111-001][adr-keep-halt] の決定 2）は、Issue を当てる先のリポで引いて見分けるだけで、Project にあるかを見ない
- 人の Skill は、結果のファイルを待つ時間（`run.intakeWaitMinutes`。60 分）まで待つ。待つのをやめた後に書かれた結果のファイルは人に示されず、7 日を過ぎたら進行 Bot が消す（基本設計の「[状態遷移と判定][design-flow]」の「記録の置き場のほかのファイル」）

課題：受け入れの依頼の実行で、受付 AI が返した文の欄が検疫に当たったときに、次の実行から全体を止めるか。止めるなら、GitHub に書かない決まりのまま、何で止め、`security` の印と全体の停止の Issue を誰が書くか。人の Skill に何を示すか。

## 判断の決め手（Decision Drivers）

- 安全：AI が書いた文の検疫で見つけたら、起こされ方を問わず、次の実行で AI のセッションを起こさない（SAFE-19、[ADR-20261024-005][adr-security] の決定 3）
- 正本と人の戻し方：止めた事実と、人の確かめと解き方の正本を GitHub に置き、人が GitHub の画面で確かめて解ける
- 人が気づく早さ：見つけたことを、見つけた後すぐに人が見る場所（結果のファイル、GitHub、GitHub の外への通知）に出す
- 確かめやすさと費用：改める承認済みの決定と、受け入れの依頼の実行に足す経路が少ない。受け入れの依頼の実行を「GitHub に何も書かない」と 1 つの決まりで確かめられる
- 運用のしやすさ：人が確かめるときの補助（`/verify-issue`）を呼んだ後に、人がすることが少ない
- 制約：進行 Bot にリポの変数を書く権限を渡さない（[ADR-20261017-007][adr-stop]）。GitHub の外への通知は、印を GitHub に書いた後にだけ送る（[ADR-20261101-002][adr-notify]）

## 検討した選択肢（Considered Options）

- 案 A：見つかりの記録を書き、受け入れの依頼の実行は GitHub に書かないまま、作業の単位を進める次の実行が `security` の印と全体の停止の Issue を書く（UNDECIDED-98 の候補 (A)）
- 案 B：今のまま、結果のファイルにだけ書き、全体を止めない（UNDECIDED-98 の候補 (B)）
- 案 C：受け入れの依頼の実行が、GitHub に書かない決まりの例外として、見つけたときだけ自分で `security` の印と全体の停止の Issue を書く（見つかりの記録は [ADR-20261111-001][adr-keep-halt] の決定 1 のとおり先に書く）

## 決定（Decision Outcome）

採用した選択肢:「案 A」。

理由: 受付 AI は起こされ方を問わず同じ仕事をするので、起こされ方で全体を止めるかが変わると、受け入れの依頼の経路だけが SAFE-19 の隙間になる。案 A は、[ADR-20261111-001][adr-keep-halt] の見つかりの記録と書き直しを使い、受け入れの依頼の実行が GitHub に何も書かない決まり（[ADR-20261022-004][adr-intake-req] の決定 2）を変えずに、次の実行から全体を止める。印は次の実行が GitHub に書くので、止めた後の正本と人の解き方は今と同じく GitHub に残る。
案 B は、全体を止めるかを、結果を読んだ人に任せ、人が結果を読まないときは誰も止めない。案 C は、GitHub の印と通知が早く出るが、受け入れの依頼の実行に GitHub に書く経路と記録を消す経路を足し、承認済みの決定を 2 つ改める。止まり始める時は案 A と同じ（次の実行から）。

### 決定 1：受け入れの依頼の実行で、受付 AI が返した文の欄が検疫に当たったら、見つかりの記録を書き、GitHub には書かない

- 進行 Bot は、受け入れの依頼の実行で、受付 AI が返した文の欄（下書きの 4 つの欄と `policyReason`）の検疫で見つけたら（結果のファイルの `where` が `text`）、結果のファイルを書く前に、見つかりの記録を 1 件書く。中身は [ADR-20261111-001][adr-keep-halt] の決定 1 と同じにする。Issue の番号は受け入れの依頼の Issue の番号、PR の番号は無し、`where` は `text`、`finding` と場所は結果のファイルに書くものと同じ（文の欄の名前と行）、見つけた時刻と、受け入れの依頼の実行に付けた実行 ID。見つかった文と AI が書いた文は書かない
- 検疫と漏えいの検査の両方で見つけたときは、`where` を `text` にして書く。漏えいの検査だけで見つけたとき（`where` が `leak`）は、全体を止めないので書かない（[ADR-20261027-002][adr-leak]）
- 受け入れの依頼の実行は、今のとおり GitHub に何も書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。`security` の印と全体の停止の Issue を書かず、GitHub の外への通知も送らない（印を書いた後にだけ送る。[ADR-20261101-002][adr-notify]）
- 受け入れの依頼の実行は、見つけた後の残りでも、AI のセッションを起こさない（実行の終わりに点検の依頼を見つけて点検を行うときの試しのセッションを含む）。実行の中の値で決める（[ADR-20261111-001][adr-keep-halt] の決定 1 と同じ）
- 見つかりの記録を書けなかったとき（記録の置き場に書けない）は、手当てが要る終わり方で終える。GitHub には書かない（下の「影響」の安全の残り）

### 決定 2：次の実行が書き直す形は ADR-20261111-001 の決定 2 のままにし、受け入れの依頼の Issue が作業の単位でなくても `security` の印を書く

- 見つかりの記録を読んで全体を止めること、作業の単位を進める次の実行（定期と手動。待つ時間を過ぎた点検の依頼で、定期の実行として続ける実行を含む）が、状態を組み立てた後、作業の単位を進める前に、記録から `security` の印と全体の停止の Issue（`halt` の印）を書き直すこと、記録を消す条件、Issue が当てる先のリポに無くなったときは `halt` の印を書けたら消すこと、書けた印ごとに通知することは、[ADR-20261111-001][adr-keep-halt] の決定 1〜3 のとおりにする。受け入れの依頼の実行で書いた記録と、ほかの実行で書いた記録を分けない
- 受け入れの依頼の Issue が Project に無い（作業の単位でない）ときも、当てる先のリポにあれば、`security` の印を書き直す。`halt` の印の `issue` は、受け入れの依頼の Issue の番号にする。人が後で Issue を Project に入れたときに、安全の軸に値がある状態で始まり、人が `## 安全の確認` を書くまで AI に渡さないため。書き直した `security` の印を組み立てた状態に足すのは、Issue が作業の単位のときだけ
- 受け入れの依頼の実行と、順 6〜9 に進まない点検の依頼の実行は、今のとおり、見つかりの記録を読んで AI のセッションを起こさないが、書き直さず、記録も消さない（[ADR-20261111-001][adr-keep-halt] の決定 2）

### 決定 3：結果のファイルに見つかりの記録を書いたかを足し、人の Skill が全体を止めたことを示す

- 結果のファイルには、今のとおり、文の欄を書かずに見つかった種類と場所を書く（[ADR-20261022-004][adr-intake-req] の決定 3）。加えて、`where` が `text` の見つかりがあるときは、見つかりの記録を書けたか（書けた・書けなかった）を書く
- 人の Skill（`intake`）は、書けたときは、決まった文で次を示す。次の実行から全体を止めること。作業の単位を進める次の実行（定期の実行か、`/dev-autopilot` の手動の 1 回実行）が、Issue に `security` の印を書き、全体の停止の Issue を開くこと。人がすること（全体の停止の Issue が開いたら、見つけた Issue とほかの作業を確かめ、`## 安全の確認` を書いて全体の停止の Issue を閉じる）
- 書けなかったときは、決まった文で、記録の置き場が異常なので次の実行から全体が止まるとは限らないことと、全体の止める合図を `stop` にするかを人が決めることを示す
- 欄の名前と決まった文は、詳細設計で決める

### 影響（Consequences）

- 良い点（安全が上がる）: 受付 AI が操られた疑いがあれば、起こされ方を問わず、次の実行から全体を止める。人が結果を読まなくても（待つのをやめた後に書かれた結果を含む）止まる。SAFE-19 と [ADR-20261024-005][adr-security] の決定 3 に、受け入れの依頼の実行を除く例外が残らない
- 良い点（正本と人の戻し方が上がる）: 今は見つけた事実が GitHub に残らない。次の実行が印を GitHub に書くので、人は、ほかの実行で見つけたときと同じく、全体の停止の Issue と見つけた Issue で確かめて `## 安全の確認` を書けばよい
- 悪い点（費用が少し上がる）: 受け入れの依頼の実行に、記録を書く処理と、結果のファイルの欄と、人の Skill が示す文を足す。書き直し、記録を消す条件、点検の warn、状態の表示は [ADR-20261111-001][adr-keep-halt] の仕組みを変えずに使い、GitHub に何も書かない決まりも変えない
- 悪い点（人が気づく早さが下がる）: GitHub の印と GitHub の外への通知は、作業の単位を進める次の実行まで出ない。定期の実行の間隔（`run.intervalHours`。初期値 24 時間）だけ遅れうる。人が `/dev-autopilot` で手動の 1 回実行を起こせば早まる。間に人に示すのは、結果のファイルと、点検の warn と、状態の表示（`status.json`、`/dev-autopilot`）
- 悪い点（運用のしやすさが下がる）: 人が確かめるときの補助（`/verify-issue`）を呼んだ結果で、全体が止まりうる。人が全体の停止の Issue に `## 安全の確認` を書いて閉じるまで、どの作業の単位でも AI のセッションを起こさない
- 悪い点（安全の残り）: 見つかりの記録を書けなかったときは、GitHub にも書かないので、次の実行から全体が止まるとは限らない。結果のファイルを書ければ人に示すが、記録の置き場ごと書けなければ、手当てが要る終わり方で知らせるだけになる。見つかりの記録を書く前に実行が切れたときも、[ADR-20261111-001][adr-keep-halt] の場面と同じ隙間が残る
- 中立: Project に無い Issue にも `security` の印が残る。人が Project に入れない Issue は作業の単位にならないので、Issue に `## 安全の確認` を書かなくても作業は止まらない

### 確認方法（Confirmation）

- 単体テストで、受け入れの依頼の実行が受付 AI の文の欄を検査した後の扱いを確かめる。検疫に当たれば（`where` が `text`）、結果のファイルより先に見つかりの記録を書き、GitHub に書かないこと。漏えいの検査だけなら記録を書かないこと。両方なら `where` を `text` にすること。結果のファイルに記録を書けたかを書くこと
- 結合テスト（偽の GitHub と偽の `claude`）で、次を確かめる
  - 受付 AI に検疫に当たる下書きを返させると、受け入れの依頼の実行は GitHub に何も書かずに見つかりの記録を書き、結果のファイルに種類と場所と、記録を書けたことを書く
  - 続けて受け入れの依頼をもう一度置くと、受付 AI を起こさずに理由（`halt-issue`）を結果のファイルに書く
  - 次の定期の実行は、点検の試しのセッションも、作業の単位ごとの AI のセッションも起こさず、作業の単位を進める前に、Issue に `security` の印を、全体の停止の Issue に `halt` の印を書き、記録を消す。Project に無い Issue でも同じに書き、組み立てた状態に足さない
  - 記録の置き場に書けないようにすると、受け入れの依頼の実行は GitHub に書かず、手当てが要る終わり方で終え、結果のファイルに記録を書けなかったことを書く
- 基本設計と詳細設計のレビューで、受け入れの依頼の実行が見つかりの記録を書く所と、書き直しが作業の単位でない Issue を扱う所が、本 ADR の決定と同じことを書いていることを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：見つかりの記録を書き、作業の単位を進める次の実行が印を書く

- 良い点（安全が上がる）: 次の実行から全体が止まり、人が結果を読むかに依らない。案 B では止まらない（案 C も止まる）
- 良い点（正本と人の戻し方が上がる）: 止めた事実と解き方の正本が GitHub に載る。案 B では載らない（案 C も載る）
- 良い点（費用が下がり、確かめやすさが上がる）: 案 C と違い、[ADR-20261022-004][adr-intake-req] の決定 2 と [ADR-20261111-001][adr-keep-halt] の決定 2 を改めず、受け入れの依頼の実行に GitHub に書く経路と記録を消す経路を足さない。受け入れの依頼の実行は「GitHub に何も書かない」の 1 つの決まりで確かめられる
- 悪い点（人が気づく早さが下がる）: GitHub の印と GitHub の外への通知は、作業の単位を進める次の実行まで出ない（案 C は見つけた実行で出る）
- 悪い点（運用のしやすさが下がる）: `/verify-issue` で見つけた後に、人が全体の停止を確かめて解く手間が増える（案 C も同じ。案 B では増えない）
- 悪い点（安全の残り）: 見つかりの記録を書けなかったときは、GitHub にも書かないので止まるとは限らない（案 C は GitHub に書く）

### 案 B：今のまま、結果のファイルにだけ書き、全体を止めない

- 良い点（費用と運用の手間が最も少ない）: 進行 Bot に足す処理が無く、`/verify-issue` で見つけた後に、人が全体の停止を解く手間も無い。得るものは費用と手間の少なさだけ
- 中立: 見つかった種類と場所は、結果のファイルで人に示す（案 A・C も同じ）
- 悪い点（安全の隙間が残る）: 次の実行が、ほかの作業の単位・点検の試し・受付 AI で AI のセッションを起こす。全体を止めるかは、結果を読んだ人が全体の止める合図を `stop` にするかに任される。人の Skill が待つのをやめた後に書かれた結果は人に示されないので、誰も止めないことがある
- 悪い点（安全が下がる）: Issue に `security` の印が載らないので、Issue が作業の単位なら（今か、後で Project に入れたとき）、安全の軸に値が入らないまま、定期の実行の AI が下書きや計画を進める。下書きや計画を投稿する前の検疫が見つけ直すかは、AI の出力が回ごとに変わるので決まらない
- 悪い点: SAFE-19 と [ADR-20261024-005][adr-security] の決定 3（起こされ方で分けていない）に、受け入れの依頼の実行を除く例外を書き足す

### 案 C：受け入れの依頼の実行が、見つけたときだけ自分で印を書く

- 良い点（人が気づく早さが上がる）: 見つけた実行で、Issue の `security` の印、全体の停止の Issue、GitHub の外への通知が出る。人がマシンの前にいなくても、すぐに気づける
- 良い点（安全の残りが減る）: 見つかりの記録を書けなかったときも、GitHub に印を書く（[ADR-20261111-001][adr-keep-halt] の決定 1 と同じ形）。案 A では止まらないことがある
- 中立: 次の実行から全体が止まる時は、案 A と同じ（どちらも見つかりの記録で止まる）
- 悪い点（確かめやすさが下がり、費用が上がる）: [ADR-20261022-004][adr-intake-req] の決定 2（GitHub に何も書かない）と、[ADR-20261111-001][adr-keep-halt] の決定 2（受け入れの依頼の実行は書き直さず、記録も消さない）を改める。受け入れの依頼の実行に、書く前に合図を読み直すことを含む GitHub に書く経路と、記録を消す経路を足す。「GitHub に何も書かない」で確かめていた結合テストが、見つけたときとほかのときに分かれる

## 補足情報（More Information）

- 起票の経緯：[ADR-20261111-001][adr-keep-halt] の起票（2026-11-11）で、受け入れの依頼の実行で見つけたときを決めていないと気づき、要件の UNDECIDED-98 に足した。2026-11-12 にメンテナの依頼で起票した。案 A・B は UNDECIDED-98 の候補 (A)・(B) と同じ。案 C は、比べるために足した
- 本 ADR で決めないこと
  - 結果のファイルに足す欄の名前と、人の Skill が示す決まった文（詳細設計）
  - 読めない見つかりの記録を人が戻すときの手がかりとして、受け入れの依頼の実行が `runs.jsonl` の行に見つかった種類と場所を残すか。今の手がかりは、同じ実行 ID で引く `runs.jsonl` の行（作業の単位の結果）、`sessions.jsonl` の始まりの行、`outputs/<実行 ID>/` の出力契約で、受け入れの依頼の実行の行には作業の単位の結果が無い（詳細設計）
  - 受け入れの依頼の実行で、受付 AI の下書きが漏えいの検査だけで見つかったとき（`where` が `leak`）の安全の軸。全体を止めないので見つかりの記録を書かない（本 ADR の決定 1）。ほかの実行なら、見つけた作業の単位で安全の軸に値を入れる（[ADR-20261027-002][adr-leak]）が、受け入れの依頼の実行は GitHub に書かないので値が入らず、次の実行が見つけ直すとも限らない。要れば決めていないことに足す
  - 書き直せないまま残り続ける読める記録を、人が消してよいか（UNDECIDED-99。受け入れの依頼の実行で書いた記録も同じに扱う）
- 外の利用者：結果のファイルを読むのは dev-autopilot の intake の Skill だけで、business-os の `/verify-issue` は intake の Skill を呼ぶ形で使う。2026-11-12 に business-os の `main` と `develop` の `.claude/skills/verify-issue/SKILL.md` を見て、まだ dev-autopilot を呼んでいないことを確かめた（呼ぶ形への拡張は、導入と点検の実装（段階 3）の business-os の PR で行う）
