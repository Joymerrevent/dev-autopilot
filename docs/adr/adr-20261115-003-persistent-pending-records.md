# 見つかりの記録から Issue に security の印を書き直せないときも halt の印を書き、人が GitHub で全体の停止を解いたら進行 Bot が記録を消す

要件の UNDECIDED-99（進行 Bot が書き直せないまま残り続ける、読める見つかりの記録を、人が消してよいか。[決めていないこと][undecided]の「ADR で決めること」の「安全と設定」）を決める。

本 ADR では、次の言葉を使う。

- 「見つかりの記録」：[ADR-20261111-001][adr-keep-halt] の、全体を止める手元の記録（基本設計の `security-pending/`）
- 「漏えいの見つかりの記録」：[ADR-20261115-002][adr-intake-leak] の、全体を止めない手元の記録（基本設計の `leak-pending/`）
- 「作業の単位を進める実行」：1 回の実行の流れの順 6〜9（基線を読み、状態を組み立て、作業の単位を進める）に進む実行（定期と手動。待つ時間を過ぎた点検の依頼で、定期の実行として続ける実行を含む）
- 「書き直し」：作業の単位を進める実行が、状態を組み立てた後、作業の単位を進める前に、見つかりの記録から `security` の印と `halt` の印を書き直すこと（[ADR-20261111-001][adr-keep-halt] の決定 2）
- 「全体の停止を解く」：maintain 以上の人が、全体の停止の Issue に、最新の `halt` の印より後に `## 安全の確認` を書き、Issue を閉じること（[ADR-20261024-005][adr-security] の決定 3）

## 背景と課題（Context and Problem Statement）

- [ADR-20261111-001][adr-keep-halt] は、AI が書いた文の検疫で見つけたら、GitHub に書く前に見つかりの記録を残し、記録が 1 件でもある間は全体の停止の Issue があるものとして扱うとした（決定 1）。記録を消すのは、記録の Issue に書く `security` の印と、`issue` に記録の Issue を書いた `halt` の印の両方を書けたときと、Issue が当てる先のリポに無くなった（消された、別のリポに移された）ときに `halt` の印を書けたときだけ（決定 2）。記録は止める側にだけ使い、記録が無いことを全体の停止を解く理由にしない（決定 3）。読めない記録は、人が確かめてから消す（決定 3 と訂正）
- 書き直しは、記録の Issue に `security` の印を書き、PR が契機なら PR にも書き、続けて全体の停止の Issue に `halt` の印を書く（[ADR-20261024-005][adr-security] の決定 3 の書く順）。詳細設計は、Issue を読めないときと、Issue に `security` の印を書けなかったときは、`halt` の印に進まずに記録を残すとした（「[1 回の実行の流れ][d-flow]」の「全体の停止と通知」の「見つかりの記録から印を書き直す」の行の (1)・(2)）。見つけた実行も、Issue に `security` の印を書けたときだけ `halt` の印を書く（同じ表の「攻撃の疑いにする」の行）
- 今の人の戻し方では、人は読める記録を消さない。書き直せないとき（点検の `machine.security-pending` の warn。理由の記号は `rewrite-failed`）は、人が書き直せない原因（App の権限や導入先、Issue の機能を切った、全体の止める合図、つながらない）を直し、次の作業の単位を進める実行が書き直して消す。原因を直しても書き直せないまま残り続けるときは、UNDECIDED-99 で決めるとし、今は消さない（基本設計の「[状態遷移と判定][design-flow]」の「記録の置き場のほかのファイル」の表の下、詳細設計の「[点検][d-check]」の `machine.security-pending`、「[設定と記録][d-records]」の「見つかりの記録」）
- 読めない記録は、人が次の順で戻す（同じ表の下の順 1〜6）。全体の止める合図を `stop` にし、記録の置き場の中身と、GitHub の Issue と PR と手元の記録を確かめる。Issue に記録の後の `security` の印と `halt` の印がそろっていれば消す。そろっていなければ、maintain 以上の人が、見つけた作業の単位とほかの作業の単位を確かめ、続けてよいと確かめられなければ作業の単位を止めて（Issue を閉じるか、`agent-paused` のラベルを付ける）から消す。最後に合図を `run` に戻す。どれもマシンの上の操作で、人の確かめは GitHub に残らない
- 原因を直せない場面がある
  - Discussion に変えた Issue（FACT-154）：元の番号は、閉じて鍵の掛かった Issue として残り、REST は `200`、GraphQL も Issue を返す。コメントは、App のトークンでも、組織の管理者の PAT でも `422` で断られる。ラベルの付け外しは通る。timeline には `ConvertedToDiscussionEvent`（REST では `converted_to_discussion`）が残り、閉じた出来事は無い。変える操作は API に無い。Discussion から元の Issue に戻せるかは確かめていない。今の設計では、Issue が「ある」と見分けられるので `security` の印を書こうとして断られ、`halt` の印にも進まない
  - 移した先で消された Issue（FACT-145）：元の番号は `404`。`404` は、消されたか見えないだけかを見分けられないので、無くなったと読まない（読めない）。`security` の印も `halt` の印も書かない
  - どちらでも、全体の停止の Issue が開かれないまま記録が残り、どの作業の単位でも AI のセッションを起こさないままになる。人が GitHub で解ける全体の停止の Issue が無いので、人に示すのは点検の warn と状態の表示（`status.json`、`/dev-autopilot`）だけで、warn の文は書き直せない原因を直すよう示す
- 受け入れの依頼の実行で書いた見つかりの記録（[ADR-20261112-003][adr-intake-finding]）は、作業の単位を進める次の実行まで残る（定期の実行の間隔 `run.intervalHours` は初期値 24 時間）。間に人が Issue を Discussion に変えれば、上の場面になる。記録の Issue は Project に無いこともある。書き直しと消す条件は、ほかの実行で書いた記録と同じ
- 漏えいの見つかりの記録（[ADR-20261115-002][adr-intake-leak]）も、Issue に `security` の印を書けないまま残り続けうる。読める記録では全体を止めず、残っても続くのは、点検の warn（`machine.leak-pending` の `write-failed`）と、記録の Issue が作業の単位なら着手しないこと（要件の FLOW-1（着手の条件））だけ。`halt` の印は書かない。人が消してよいかは UNDECIDED-99 と一緒に決めるとした（同じ ADR の「本 ADR で決めないこと」）
- 進行 Bot は、毎回の実行で全体の停止の Issue を読み（順 4。リポの設定を読んだ直後）、全体の停止が解けたかを、`halt` の印と、maintain 以上の人の `## 安全の確認` と、Issue の開閉から決めている（基本設計の「全体の停止の Issue」の「止める間」）

課題：書き直せないまま残り続ける読める見つかりの記録を、人が消してよいか。消してよいなら、誰が何を確かめてから消すか。見つけた事実と人の確かめを GitHub に残したまま、全体の停止から戻る道を作れるか。漏えいの見つかりの記録にも同じ扱いを当てるか。

## 判断の決め手（Decision Drivers）

- 安全：記録を消す前に、見つけた事実が GitHub に載り、maintain 以上の人が、見つけた作業の単位とほかの作業の単位を確かめる（SAFE-19、[ADR-20261024-005][adr-security] の決定 3）。手元のファイルの操作だけでは、全体の停止が解けない
- 正本と人の戻し方：止めた事実、人の確かめ、解き方の正本を GitHub に置く。人がマシンの前にいなくても、GitHub の画面で確かめて解ける
- 動き続けること：原因を直せない場面でも、決まった手順で AI のセッションを起こせる形に戻せる。決まった手順が無いと、人は記録のファイルを消す、記録の置き場を作り直すなど、手順に無い戻し方をとる
- 人が気づく早さ：書き直せないことを、人が見る場所（GitHub、GitHub の外への通知）に早く出す
- 確かめやすさ：記録を消すかの決め方を、GitHub の事実から単体テストと結合テストで確かめられる。GitHub の応答の種類（Discussion、`404`、まだ確かめていない応答）を 1 つずつ見分けることに頼らない
- 費用：足す処理と、改める承認済みの決定が少ない
- 制約：受け入れの依頼の実行は GitHub に書かない（[ADR-20261022-004][adr-intake-req] の決定 2）。GitHub の外への通知は、印を書いた後にだけ送る（[ADR-20261101-002][adr-notify]）。進行 Bot にリポの変数を書く権限を渡さない（[ADR-20261017-007][adr-stop]）。見つかりの記録が無いことを、全体の停止を解く理由にしない（[ADR-20261111-001][adr-keep-halt] の決定 3）

## 検討した選択肢（Considered Options）

- 案 A：今のまま、人は消さず、点検の warn で示し続ける（UNDECIDED-99 の候補 (A)）
- 案 B：maintain 以上の人が、見つけた作業の単位とほかの作業の単位を GitHub で確かめてから、手元で記録を消す（UNDECIDED-99 の候補 (B)。読めない記録の人の戻し方を、読める記録にも使う）
- 案 C：書き直せない回数の上限を設け、上限に当たったら、全体の停止の Issue（`halt` の印）だけを書いて記録を消す（UNDECIDED-99 の候補 (C)）
- 案 D：Discussion に変えた Issue（timeline の `ConvertedToDiscussionEvent` で見分ける）を、[ADR-20261111-001][adr-keep-halt] の決定 2 の「当てる先のリポに無くなった」に入れ、`halt` の印だけを書いて記録を消す
- 案 E：書き直しで Issue に `security` の印を書けなくても、全体の停止の Issue に `halt` の印を書き、人が GitHub で全体の停止を解いたら、進行 Bot が記録を消す

## 決定（Decision Outcome）

採用した選択肢:「案 E」。

理由: 原因を直せない場面でも、見つけた事実が全体の停止の Issue に載り、人は、今と同じ解き方（maintain 以上の人の `## 安全の確認` と、Issue を閉じること）で、GitHub の画面から全体の停止を解ける。記録を消すのは、人が GitHub で解いたことを進行 Bot が読んだ後だけなので、人の確かめと解き方の正本が GitHub に残り、手元のファイルの操作で全体の停止が解ける経路を足さない。書けない理由を見分けずに同じに扱うので、Discussion、`404`、まだ確かめていない応答のどれでも戻せる。
案 A は戻す手順が無く、人が手順に無い戻し方をとる。案 B は人の確かめが GitHub に残らず、見つけた事実が GitHub に一度も載らないまま記録が消える。案 C は上限まで GitHub に何も載らず、上限の値に根拠が無い。案 D は Discussion の場面しか戻せない。
案 E では、見つけた作業の単位で安全の軸に値が入らないまま、全体の停止が解けうる（[ADR-20261111-001][adr-keep-halt] が案 A の悪い点に挙げた隙間）。隙間は Issue に `security` の印を書けない場面に限り、`halt` の印を書くコメントで、見つけた Issue を止めるかを人に確かめさせ、記録がある間は `security` の印を書き直し続けて狭める。

### 決定 1：書き直しで Issue に `security` の印を書けなかったときも、全体の停止の Issue に `halt` の印を書く

- 作業の単位を進める実行は、書き直しで記録の Issue に `security` の印を書けなかったとき（Issue を読めない（`404` など）、書き込みを断られた（Discussion に変えた Issue の `422` など）、届いたか分からない）も、記録を残したまま、全体の停止の Issue に、`issue` に記録の Issue を書いた `halt` の印を書く。開いている全体の停止の Issue があれば足し、無ければ開く（[ADR-20261024-005][adr-security] の決定 3 の開き方）。`halt` の印も書けなければ、今のとおり記録を残し、次の作業の単位を進める実行がもう一度書く。PR の `security` の印は、今のとおり、Issue に書けたときだけ書く
- 記録を見つけた後に書いた、`issue` に記録の Issue を書いた `halt` の印が、全体の停止の Issue のどれかにすでにあれば、重ねて書かない。毎回の実行で `halt` の印と通知を重ねないため
- 書く直前に読んだ全体の止める合図が `run` でなければ、今のとおり、どちらの印も書かない
- `security` の印を書けずに `halt` の印を書くときは、コメントに、[ADR-20261024-005][adr-security] の決定 4 の中身（見つけた Issue の番号と、人がすること）に加えて、次を書く。Issue に `security` の印を書けていないこと。見つかった種類と場所（`security` の印に書くものと同じ。見つかった文は書かない）。人がすること（見つけた Issue を確かめ、続けてよいと確かめられなければ、作業の単位を止める（Issue を閉じるか、`agent-paused` のラベルを付ける）。ほかの作業の単位も確かめ、`## 安全の確認` を書いて閉じる）。Issue が当てる先のリポに無くなったときに書く `halt` の印（[ADR-20261111-001][adr-keep-halt] の決定 2）にも、見つかった種類と場所を書く
- 書けた `halt` の印は、[ADR-20261101-002][adr-notify] のとおり GitHub の外へ通知する
- 次の作業の単位を進める実行も、記録があれば、今のとおり先に Issue に `security` の印を書き直す。書けたら、今のとおり続けて `halt` の印を書き（開き直しの条件は、Issue の最新の `security` の印より後の `halt` の印を見るため）、両方を書けたら記録を消す。人が `security` の印を書けるより先に全体の停止を解いていれば、`halt` の印が全体の停止の Issue に改めて載り、人はもう一度解く
- 見つけた実行の書く順（Issue に `security` の印を書けたときだけ `halt` の印を書く）は変えない。見つけた実行で書けなければ、次の作業の単位を進める実行が、本決定のとおり書き直す

### 決定 2：人が全体の停止を GitHub で解いたら、Issue に `security` の印を書けないままでも、進行 Bot が記録を消す

- 見つかりの記録を消す条件に、次を足す。記録を見つけた後に書いた、`issue` に記録の Issue を書いた `halt` の印を持つ全体の停止の Issue で、全体の停止が解けた（maintain 以上の人が、全体の停止の Issue に、最新の `halt` の印より後に `## 安全の確認` を書き、Issue を閉じた）
- 作業の単位を進める実行は、書き直しと同じ時と場所で、先に Issue に `security` の印を書き直し、書けなかったときだけ、上の条件を GitHub の印から読んで記録を消す。全体の停止が解けたかは、順 4（リポの設定を読んだ直後）で全体の停止の Issue を読むときと同じ形（印と `## 安全の確認` と開閉）で決める
- どの `halt` の印が、記録を見つけた後に書いたものかを決められないときは、消さない（止める側）。記録と `halt` の印を結ぶ方法（GitHub の時刻と、記録に書いた見つけた時刻を比べるか、`halt` の印を書くコメントに記録のファイル名を書くか）は、詳細設計で決める
- 記録を消した実行の残りでは、順 2（lock を取った直後）で記録を読んだ値のまま、AI のセッションを起こさない。次の実行から、ほかの止める条件に当たらなければ起こす
- 全体の停止の正本は、今のとおり GitHub の印で、記録は人が GitHub で解いた後に消える。見つかりの記録が無いことを全体の停止を解く理由にしない（[ADR-20261111-001][adr-keep-halt] の決定 3）は変わらない
- Issue に `security` の印を書けないまま消すので、見つけた作業の単位では、安全の軸に値が入らない。続けてよいかは、全体の停止を解く人が、決定 1 で `halt` の印を書いたコメントを見て決める
- 人は、今のとおり、読める記録を手元で消さない。読めない記録の人の戻し方も変えない
- 受け入れの依頼の実行で書いた記録（[ADR-20261112-003][adr-intake-finding]）にも同じに当てる（記録の Issue が Project に無いときも）。受け入れの依頼の実行と、作業の単位を進めない点検の依頼の実行は、今のとおり書き直さず、記録も消さない

### 決定 3：点検の warn と状態の表示に、`halt` の印を書いたかと、人がすることを出す

- 点検の warn（`machine.security-pending` の `rewrite-failed`）と状態の表示は、書き直せずに残した記録ごとに、今の書き直せなかった回数と理由の種類に加えて、`security` の印を書けずに `halt` の印を書いたか（書いたなら、どの全体の停止の Issue に書いたか）を出す
- 書いたときは、決まった文で、全体の停止の Issue で見つけた Issue とほかの作業の単位を確かめて全体の停止を解けば、次の作業の単位を進める実行が記録を消すことを示す。書けていないときは、今のとおり、書き直せない原因を直すよう示す
- 書き直した結果（`runs.jsonl` の行）に、`security` の印を書けずに `halt` の印を書いたことと、人が全体の停止を解いたので消したことを、ほかの結果と分けて残す。書き直せなかった回数の数え方（見つけた時刻より後に「残した」と書いた行を数える）は変えない
- 欄の名前、結果の値、決まった文は、詳細設計で決める

### 決定 4：漏えいの見つかりの記録には当てず、今のとおり人は消さない

- 決定 1〜3 は、見つかりの記録（`security-pending/`）に当てる。漏えいの見つかりの記録（`leak-pending/`）には、全体の停止の Issue も `halt` の印も無く、人が GitHub で解いた事実を記録と結べないので、当てない
- Issue に `security` の印を書けないまま残り続ける読める漏えいの見つかりの記録も、今のとおり人は消さず、点検の warn（`write-failed`）で示す（[ADR-20261115-002][adr-intake-leak] の決定 3・4）。全体を止めないので、残っても続くのは warn と、記録の Issue が作業の単位なら着手しないことだけ。見つけた事実が GitHub に載っていない記録を、手元の操作で消さない
- warn の文は、原因を直せない場面（Discussion に変えた Issue、移した先で消された Issue）では warn が残り続けることを示す形に直す（承認の後に詳細設計で直す）

### 影響（Consequences）

- 良い点（動き続けることが上がる）: 原因を直せない場面でも、人が全体の停止の Issue で全体の停止を解けば、次の作業の単位を進める実行が記録を消し、記録を消した次の実行から AI のセッションを起こせる。人はマシンの上の操作をせずに、GitHub の画面から戻せる
- 良い点（正本と人の戻し方を保ち、安全を保つ）: 記録を消す前に、見つけた Issue の番号と、見つかった種類と場所が `halt` の印に載り、人の確かめ（maintain 以上の人の `## 安全の確認`）と解いた事実が GitHub に残る。本 ADR は、見つけた事実が GitHub に一度も載らないまま記録が消える経路を足さない
- 良い点（人が気づく早さが上がる）: 書き直せない間も、全体の停止の Issue と GitHub の外への通知が出る。今は、点検の warn と状態の表示にしか出ない
- 良い点（確かめやすさが上がる）: 書けない理由（Discussion、`404`、まだ確かめていない応答）を見分けずに同じに扱うので、応答ごとの見分けを足さない。記録を消すかは、全体の停止の Issue の印と `## 安全の確認` と開閉から決まる
- 悪い点（安全が下がる）: 人が、Issue に `security` の印を書けないまま全体の停止を解くと、見つけた作業の単位では、安全の軸に値が入らない。続けてよいかは、人が `halt` の印を書いたコメントを読んで、見つけた作業の単位を止めるかに頼る。`404` が見えないだけで、後で Issue がまた読めるようになったときも、値の無いまま作業の単位になりうる
- 悪い点（運用のしやすさが下がる）: 一時の失敗でも `halt` の印と通知が出る。次の実行で `security` の印を書けたら、もう一度 `halt` の印を書くので、人が先に全体の停止を解いていれば、もう一度解く
- 悪い点（費用が上がり、確かめやすさが下がる）: [ADR-20261111-001][adr-keep-halt] の決定 2 と [ADR-20261024-005][adr-security] の決定 3・4 を一部改める。書き直しの分かれ道（`security` の印を書けなかったときに `halt` の印を書く）、記録と `halt` の印を結ぶ方法、全体の停止が解けたかを記録ごとに読む処理、`halt` の印を書くコメントの文、点検の文と結果の値を足す
- 悪い点（動き続けることの残り）: 漏えいの見つかりの記録は、原因を直せない場面で、点検の warn が残り続ける（決定 4）
- 中立: 人が全体の停止を解くまで、全体は止まったまま（どの案でも、記録か全体の停止の Issue で止まる）

### 確認方法（Confirmation）

- 単体テストで、記録を消すかの決め方を確かめる。記録の Issue に `security` の印を書けた・書けなかった、記録を見つけた後の `halt` の印がある・無い・結べない、`halt` の印を持つ全体の停止の Issue が解けた・`## 安全の確認` が無いまま閉じた・maintain 未満の人の `## 安全の確認` だけ・開いている、を組み合わせ、`security` の印を書けずに全体の停止が解けたときだけ消すこと。結べない `halt` の印では消さないこと
- 単体テストで、`security` の印を書けなかったときに `halt` の印を書くかの決め方を確かめる。記録を見つけた後の `halt` の印がすでにあれば書かないこと。合図が `run` でなければ書かないこと
- 結合テスト（偽の GitHub と偽の `claude`）で、次を確かめる
  - 記録の Issue へのコメントを `422` で断らせる（Discussion に変えた Issue をまねる）と、作業の単位を進める実行は、記録を残したまま全体の停止の Issue を開いて `halt` の印を書き、通知し、点検の warn に全体の停止の Issue の番号を出す。次の実行は `halt` の印を重ねない
  - 記録の Issue を `404` にしても同じ
  - 人が全体の停止の Issue に maintain 以上の人の `## 安全の確認` を書いて閉じると、次の作業の単位を進める実行が記録を消し、記録を消した次の実行から AI のセッションを起こす
  - 閉じただけのときと、maintain 未満の人の `## 安全の確認` だけのときは、記録を消さない
  - 一時の失敗の後に `security` の印を書けると、`halt` の印をもう一度書き、両方を書けたので記録を消す
  - 受け入れの依頼の実行と、作業の単位を進めない点検の依頼の実行は、印を書かず、記録を消さない
  - 漏えいの見つかりの記録は、Issue に `security` の印を書けなくても、`halt` の印を書かず、消さない
- 基本設計と詳細設計のレビューで、書き直しの分かれ道、記録を消す条件、`halt` の印を書くコメント、点検と状態の表示が、本 ADR の決定と同じことを書いていることを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：今のまま、人は消さず、点検の warn で示し続ける

- 良い点（費用が最も下がる）: 進行 Bot にも設計にも足すものが無く、承認済みの決定も改めない。得るものは費用の少なさだけ
- 中立: 記録がある間は全体を止める（案 B〜E も、記録を消すまでは同じ）
- 悪い点（動き続けることが下がる）: 原因を直せない場面で、どの作業の単位でも AI のセッションを起こさないままになり、決まった戻し方が無い
- 悪い点（安全が下がる）: 決まった戻し方が無いので、人は、記録のファイルを消す、記録の置き場を作り直すなど、手順に無い戻し方をとりうる。手順に無い戻し方では、maintain 以上の人の確かめも、GitHub に残る跡も無い
- 悪い点（正本と人の戻し方が下がる）: 見つけた事実が GitHub に載らず、人に示すのは点検の warn と状態の表示だけ。warn の文は、直せない原因を直すよう示す

### 案 B：maintain 以上の人が GitHub で確かめてから、手元で記録を消す

- 良い点（費用が下がる）: 案 C〜E と違い、進行 Bot の処理を変えず、読めない記録の人の戻し方（基本設計の順 1〜6）を、読める記録にも使うと書くだけで済む
- 良い点（動き続けることが上がる）: 漏えいの見つかりの記録が残り続ける場面も、同じ手順で戻せる（案 E では戻せない）
- 中立: 人が確かめる中身（見つけた作業の単位とほかの作業の単位）は、全体の停止の Issue に `## 安全の確認` を書くときと同じ（案 E も同じ）
- 悪い点（正本と人の戻し方が下がる）: 人の確かめと、解いた事実が GitHub に残らない。戻すにはマシンの上で操作し、GitHub の画面からは戻せない
- 悪い点（安全が下がる）: `halt` の印を書けていない記録を消すので、見つけた事実が GitHub に一度も載らないまま記録が消える経路ができる。消す人が maintain 以上かを、進行 Bot は確かめられない（手元のファイルは、マシンに入れる人なら消せる）
- 悪い点（安全が下がる）: 人が、直せる原因（App の権限など）と直せない原因を見分けて消すことに頼る。見分けを誤ると、`security` の印も `halt` の印も GitHub に載らないまま、全体の停止が解ける

### 案 C：書き直せない回数の上限を設け、上限で `halt` の印だけを書いて記録を消す

- 良い点（費用が下がる）: 書き直せなかった回数は今も数えている（詳細設計の `logic/run/records.ts`）。記録を消す条件は、Issue が無くなったときと同じ「`halt` の印を書けたら消す」で、全体の停止が解けたかを記録と結ばずに済む（案 E では結ぶ）
- 中立: 上限の後は、人が全体の停止の Issue で解く（案 E と同じ）
- 悪い点（人が気づく早さが下がる）: 上限に当たるまで、GitHub に何も載らないまま全体が止まる（案 E は最初に書き直せなかった実行で載る）
- 悪い点（安全が下がる）: 上限で記録を消すと、`security` の印の書き直しをやめる。原因が後で直っても、見つけた作業の単位に値が入らない（案 E は、人が全体の停止を解くまで書き直し続ける）
- 悪い点（確かめやすさが下がる）: 上限の値に根拠が無い。定期の実行の間隔と、手動で起こした実行の数で、上限に当たるまでの時が変わる。一時の失敗が続いたのか、直せない原因なのかを、回数で見分けることになる

### 案 D：Discussion に変えた Issue を「当てる先のリポに無くなった」に入れる

- 良い点（動き続けることが上がる）: Discussion の場面では、漏えいの見つかりの記録も、Issue が無くなったときの決まり（[ADR-20261115-002][adr-intake-leak] の決定 3）で、印を書かずに消える（案 E では消えない）
- 中立: Discussion の場面では、見つかりの記録は `halt` の印を書けた時に消え、人が全体の停止の Issue で解くまで全体は止まる。人がすることは案 E と同じ
- 悪い点（動き続けることが下がる）: 移した先で消された Issue（`404`）と、まだ確かめていない応答では、戻せない（案 A のまま）
- 悪い点（確かめやすさが下がり、費用が上がる）: REST で `200` を返す Issue を「無くなった」と読む見分けを足し、timeline を読む（`422` で返る `message` の文は、API が約束した文でないので、見分けに使わない。基本設計の「状態の組み立て」の見分け方と同じ考え）。状態の組み立てでは同じ Issue を「ある」と読むので、書き直しと状態の組み立てで読み方が分かれる（状態の組み立ての読み方は本 ADR で決めない）。応答を確かめたのは FACT-154 の 1 回の試しだけ

### 案 E：`security` の印を書けなくても `halt` の印を書き、人が GitHub で解いたら記録を消す

- 良い点（動き続けることが上がる）: 書けない理由を問わず、人が全体の停止を解けば戻せる。案 A では戻せず、案 D では Discussion の場面だけ
- 良い点（正本と人の戻し方が上がり、安全を保つ）: 記録を消す前に、見つけた事実が `halt` の印に載り、人の確かめと解いた事実が GitHub に残る。案 B では GitHub に残らず、手元の操作で全体の停止が解ける
- 良い点（人が気づく早さが上がる）: 最初に書き直せなかった実行で、全体の停止の Issue と通知が出る。案 A・B では出ず、案 C では上限まで出ない
- 良い点（安全が上がる）: 人が全体の停止を解くまで `security` の印を書き直し続けるので、一時の失敗なら、人が解く前に値が入る（案 C は上限で書き直しをやめる）
- 悪い点（安全が下がる）: 人が、Issue に `security` の印を書けないまま全体の停止を解くと、見つけた作業の単位では値が入らない。人が `halt` の印を書いたコメントを読んで止めるかに頼る（案 C・D も同じ）
- 悪い点（費用が上がり、確かめやすさが下がる）: [ADR-20261111-001][adr-keep-halt] の決定 2 と [ADR-20261024-005][adr-security] の決定 3・4 を改める。書き直しの分かれ道、記録と `halt` の印を結ぶ方法、全体の停止が解けたかを記録ごとに読む処理を足す
- 悪い点（運用のしやすさが下がる）: 一時の失敗でも `halt` の印と通知が出て、次の実行で `security` の印を書けたら、もう一度 `halt` の印が出る
- 悪い点（動き続けることが下がる）: 案 B・D と違い、漏えいの見つかりの記録が残り続ける場面は戻せない（案 A・C も戻せない）

## 補足情報（More Information）

- 起票の経緯：詳細設計の 7 回目の再レビュー（2026-11-11）で見つけ、要件の UNDECIDED-99 に足した。2026-11-15 に、Discussion に変えた Issue の応答を FACT-154 で確かめた後、メンテナの依頼で起票した。案 A〜C は UNDECIDED-99 の候補 (A)〜(C) と同じ。案 D・E は、比べるために足した
- 読めない記録の人の戻し方を、読める記録にも使えるか：使える（案 B）。基本設計の順 5 の「印がそろっていなければ、maintain 以上の人が確かめ、続けてよいと確かめられなければ作業の単位を止めてから消す」は、読める記録にも当てはまる。採らなかったのは、案 B の悪い点（人の確かめが GitHub に残らない、見つけた事実が GitHub に載らないまま消える）のため。読めない記録は書き直す中身が分からないので、進行 Bot が印を書けず、手元の操作が要る。読める記録は進行 Bot が `halt` の印を書けるので、人の確かめを GitHub に置ける
- 決定 1 を書き直しに限った理由：見つけた実行で書けないのは、多くが一時の失敗で、次の作業の単位を進める実行がまず書き直す。見つけた実行でも `security` の印を書けずに `halt` の印を書く形は、通知が 1 回の実行だけ早いが、一時の失敗のたびに `halt` の印が重なり、見つけた実行の書く順（[ADR-20261024-005][adr-security] の決定 3）も改める
- 決定 4 の扱い：決定 4 は、案 E を当てる範囲を書いたもので、漏えいの見つかりの記録の扱いは変えない（warn の文を、残り続ける事実に合わせるだけ）。漏えいの見つかりの記録を消す決まりを足すなら、案 E と独立した変更になるので、本 ADR には入れない
- 案を組む形の比べ：案 D と案 E を組む形（Discussion の場面は案 D、ほかは案 E）も比べた。案 E だけで Discussion の場面も戻せ、案 D が足すのは、見つかりの記録が人の解く前に消えることと、漏えいの見つかりの記録が消えることだけ。案 D は、Discussion に変えた Issue を「無くなった」と読む見分けで、状態の組み立ての読み方と同じ論点に当たるので、本 ADR に入れず、下の「本 ADR で決めないこと」に残した（1 件の ADR に決定を 1 つ）
- 本 ADR で決めないこと
  - Discussion に変えた Issue を、状態の組み立てでどう読むか（`ClosedEvent` が無いので、閉じた人を読めない）。案 D（Discussion に変えた Issue を「無くなった」に入れる）も、同じ論点で扱う。無くなったと読むと決めれば、Discussion の場面では、見つかりの記録は `halt` の印を書けた時に消え、漏えいの見つかりの記録も [ADR-20261115-002][adr-intake-leak] の決定 3 で印を書かずに消える
  - 記録と `halt` の印を結ぶ方法、書き直した結果の値、点検の文、状態の表示の欄、`halt` の印を書くコメントの文（詳細設計）。`halt` の印に欄を足すか（要件の印の一覧）も、コメントの文で足りるかを詳細設計で確かめてから決める
  - 人が全体の停止の Issue を Discussion に変えたとき。FACT-154 でコメントが `422` で断られたことから見込むと、`## 安全の確認` を書けないまま閉じた全体の停止の Issue になり、全体の停止を解けなくなりうる（全体の停止の Issue では確かめていない）。要れば決めていないことに足す
  - Discussion に変えたものでない、鍵の掛かった Issue に、App がコメントを書けるか（確かめていない）。書けなければ、本 ADR の決定 1・2 の場面に入る
