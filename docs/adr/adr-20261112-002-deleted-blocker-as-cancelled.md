# 依存の相手の Issue が消されたら、wait の印に書いた番号を当てる先のリポで引いて見つけ、中止ありと読んで計画を見直す

要件の UNDECIDED-100（依存の相手の Issue が消されたときに、先の依頼の軸をどう読むか。[決めていないこと][undecided]の「ADR で決めること」の「作業の単位の状態遷移」）を決める。

改める決定と、据え置く決定は次のとおり。

| ADR | 扱い | 改める決定 | 据え置く決定 |
| --- | --- | --- | --- |
| [ADR-20261024-006][adr-cleanup]（片付けの前の状態と、先の依頼の待ち方） | 一部を改める | 決定 3 の表（先の作業がどうなったら、後の作業で先の依頼の軸をどう読むか）に、「先の作業の Issue が当てる先のリポで消された → 中止あり（D3）」の行を足す（本 ADR の決定 1・2）。消された相手を、表の「ほか → 未完了のまま」に入れない | 決定 3 の表にあるほかの行（結びつく PR がマージされた → D2、push 以上の人が閉じた → D3、ほか → 未完了のまま）と、中止ありの見直しの決まり（計画を確かめる AI、`dependency-review` の印、`keep` と `change`、後の作業が決定済みなら見直さずに（なし）、相手ごとに 1 つずつ見直す）。決定 1・2・4 |
| [ADR-20261024-001][adr-model-states]（作業の単位の状態を、主な流れと重ねる 3 本の軸で表す） | 読み替える | 決定 3 にある先の依頼の線 D3 で、出来事「先の作業が閉鎖済みになった」を、本 ADR で消されたと読んだ相手を含めて読む | 決定 6 にある軸の値の決め方（未完了を中止ありより上に出し、下の値は消えずに残る）。決定 9 の `wait` と `dependency-review` の印の欄（本 ADR は欄を変えない）。ほかの決定 |
| [ADR-20261015-006][adr-flow]（手元の記録は上限の数え上げにだけ使う） | 据え置く | — | 決定 4。本 ADR の見分けは、GitHub にある `wait` の印・依存の一覧・REST の応答だけで決め、手元の記録（`runs.jsonl` に書く依存の相手のリポと番号を含む）を使わない。[ADR-20261111-001][adr-halt-pending] が足した、全体を止める側の例外 1 つのほかに、例外を足さない |
| [ADR-20261020-002][adr-app]（GitHub App に切り替える） | 据え置く | — | 決定 2（App を当てる先のリポだけに入れる）。消された相手を見分けるために、App の導入先を広げない |

## 背景と課題（Context and Problem Statement）

- FLOW-43 と [ADR-20261024-006][adr-cleanup] の決定 3 は、先の依頼（blocked by）の相手の結びつく PR がマージされるまで待ち（未完了）、push 以上の人が相手の Issue を閉じて PR がマージされていなければ中止ありにするとした。中止ありの作業の単位は、計画を確かめる AI が計画を見直し、結果を `dependency-review` の印に書く（基本設計の「[状態遷移と判定][design-flow]」の「先に見る」の順 14（計画の見直し））。先の変更が入らないのに、先の変更があるつもりで立てた計画のまま進まないため
- FLOW-10 は、待つ作業の単位の Issue に 1 回だけコメントし、1 回かどうかを `wait` の印で判定するとした。`wait` の印は、`blockedBy` に終わっていない先の Issue の番号を並べ、同じ `blockedBy` の有効な印があれば書かない（要件の「[印と固定の見出しの一覧][f04]」）。どの相手で待ったかを、進行 Bot が GitHub に残すのは `wait` の印だけで、`blockedBy` は相手のリポを持たない
- 相手の Issue を消すと、依存の一覧からも、依存の数（GraphQL の `issueDependenciesSummary` の `totalBlockedBy`）からも相手が消える（FACT-144）。すべてのリポを読める App のトークンでも、当てる先のリポだけに絞った App のトークンでも同じで、依存を足した出来事（timeline の `BlockedByAddedEvent`）も消え、跡が残らない（FACT-152）。閉じた相手は、一覧と数に残る（FACT-150）
- 人が依存を外したときも、相手は一覧と数から消える。timeline には、外した人と相手が分かる出来事（`BlockedByRemovedEvent`）が残る（FACT-152）。人が依存を外すことは、人が先の依頼の待ちを解く操作として要件にある（[01-issue-flow.md][flow] の「止まった状態から戻す手順」にある先の依頼の待ち）
- 依存の一覧と数だけを読むと、相手が消されたことと、人が依存を外したことを見分けられない。今の設計は、決めるまで一覧に無い相手を読まない（詳細設計の「[1 回の実行の流れ][d-flow]」の「GitHub の事実の読み方」。候補 (A) と同じ）。ほかに終わっていない相手が無ければ、先の依頼の軸が黙って（なし）に戻り、待っていた作業の単位は、計画を見直さずに次の工程へ進む。[ADR-20261024-006][adr-cleanup] の決定 3 の表は、消された相手がどの行に当たるかを決めていない
- 消された Issue を REST で引くと `410` を返す（FACT-134・FACT-148）。Issue の機能を切ったリポも `410` を返すので、リポの `has_issues` で見分ける（FACT-147）。別のリポに移した Issue の元の番号は `301` を返し、移した先で消した後は `404` を返す（FACT-66・FACT-145）。基本設計の「[状態遷移と判定][design-flow]」にある「状態の組み立て」は、作業の単位の Issue が無くなったかを、REST をリダイレクトをたどらずに引いて見分ける（詳細設計の `classifyMissingIssue`）。消された・移された・あるのどれでもない応答は「読めない」とし、順 7（状態の組み立て）で実行を止める
- 進行 Bot の App は当てる先のリポだけに入り（[ADR-20261020-002][adr-app] の決定 2）、点検は App がほかのリポに入っていれば fail にし、毎回の実行で使うトークンも当てる先のリポだけに絞る（基本設計の「[導入と点検][design-setup]」の「GitHub App の権限」）。App から見えないリポにある相手は、依存の一覧に出ない（FACT-143。試した相手のリポは非公開）。一方、詳細設計は、ほかのリポにある相手が一覧に出たときを未完了として扱い、相手の番号も `blockedBy` に書く。公開のリポにある相手が、絞ったトークンの一覧に出るかは確かめていない
- 導入と点検の実装（段階 3）の一度だけの試し（2026-11-12）で FACT-144 を確かめたときに見つけた

課題：依存の相手の Issue が消されたことを、GitHub の何から見つけ、先の依頼の軸をどう読むか。

## 判断の決め手（Decision Drivers）

- 安全：先の依頼で待っていた相手が無くなったのに、計画を確かめずに後の作業を進めない。相手が閉じられたとき（中止あり）と同じ側に倒す
- 人の戻し方：人が依存を外せば、今のとおり待ちが解け、計画の見直しも起きない
- 動き続けること：1 つの作業の単位で相手を読めないことで、人が手当てする道の無いまま、ほかの作業の単位まで止め続けない
- 確かめやすさ：確かめた応答（FACT）と、すでにある見分け方で決める。見つける条件と読み方を、単体テストで組み合わせて確かめられる
- 費用：足す処理と GitHub の呼び出しと、改める承認済みの決定が少ない
- 制約：判定に手元の記録を使わない（[ADR-20261015-006][adr-flow] の決定 4。例外は [ADR-20261111-001][adr-halt-pending] の 1 つだけ）。App は当てる先のリポだけに入れる（[ADR-20261020-002][adr-app] の決定 2）。`wait` の印の欄は本 ADR で変えない（App から見えない相手で待つときの欄は、同じ日に起票する ADR-20261112-001 が決める）

## 検討した選択肢（Considered Options）

- 案 A：今のまま、一覧に無い相手は読まない（相手を消したことを、消した人の判断として受ける）
- 案 B：`wait` の印に書いた番号が依存の一覧から無くなったら、番号を当てる先のリポで引いて見分け、消されていれば中止ありと読んで計画を見直す。見分け方の形を 2 つ比べた
  - 形 B-1：REST の応答を、状態の組み立ての見分け方（`classifyMissingIssue`）で見分け、「消された」を応答で見つける
  - 形 B-2：timeline の `BlockedByRemovedEvent` で「人が外した」を見つけ、外した出来事の無い番号を、消されたと読む
- 案 C：案 B と同じ形で見つけたら、作業の単位を停止中にし、人が依存を確かめて戻す

## 決定（Decision Outcome）

採用した選択肢:「案 B」の形 B-1。

理由: 相手が消されたことを、GitHub に残る進行 Bot の `wait` の印と、消された Issue の `410` から見つけ、相手が閉じられたとき（中止あり）と同じく、計画を確かめてから進む。人が依存を外したときは相手の Issue が残る（2xx）ので何もせず、人の待ちの解き方を変えない。判定の入力は GitHub だけで、見分けは状態の組み立てと同じ関数で行う。
案 A は、消された相手で待っていた作業の単位が、計画を確かめずに進む。案 C は、計画を変えなくてよい場合も、人が確かめて `## 再開` を書くまで止まる。形 B-2 は、消されたことを出来事が無いことから推し量り、確かめていない振る舞いに頼る点が多い。

### 決定 1：有効な `wait` の印に書いた番号のうち、依存の一覧に今は無い番号を、当てる先のリポで引く

- 引くのは、作業の単位の主な流れが計画済みか、計画済みより後で、終了の枠（マージ済み・完了・閉鎖済み・中止）の前のときだけ。決定済み（計画の前）は、相手が閉じられたときと同じく見直さずに（なし）と読む（[ADR-20261024-006][adr-cleanup] の決定 3）ので、引かない。決定済みの間に消された相手は、閉じられた相手と同じく、計画済みに入った後の実行で引いて見直す（基本設計にある中止ありの条件のまま）。終了の枠では「先に見る」の順 1・2（何もしない・片付け）が先に当たり、先の依頼の軸で工程が変わらないので、引かない
- 引く番号は、作業の単位の Issue にある有効な `wait` の印（最新に限らない）の `blockedBy` に書いた番号のうち、次の 2 つに当たるもの
  - 今の依存の一覧に、当てる先のリポにある同じ番号の相手が無い
  - 番号を `dependency` に持つ有効な `dependency-review` の印が無い（見直し済みの相手は引き直さない。[ADR-20261024-006][adr-cleanup] の決定 3 の「見直し済みとして数え直さない」と同じ）
- 最新の `wait` の印に限らないのは、消された相手を手がかりから外さないため。ほかに終わっていない相手があれば、先の依頼の軸は未完了を中止ありより上に出し（[ADR-20261024-001][adr-model-states] の決定 6）、「先に見る」の順 13（待つ）が、消された相手を除いた番号で新しい `wait` の印を書く。最新の印だけを見ると、次の実行で消された相手の番号が手がかりから外れ、中止ありが黙って消える。同じ決定 6 の「下の値は消えずに残り、上の値が外れると次の値が出る」に合わせる
- 番号は、当てる先のリポの番号として引く。`wait` の印に相手のリポを足さない。ほかのリポにある相手（一覧に出たときだけ番号を書く）が消されたことは、本 ADR で見つけない（下の「影響」）
- 引き方は、状態の組み立ての見分け方と同じにする。順 7（状態の組み立て）の中で、REST の `GET /repos/{owner}/{repo}/issues/{issue_number}` を、リダイレクトをたどらずに 1 回引き、`410` のときだけ当てる先のリポの `has_issues` を読む。当てる先のリポの名前を変えたときの `301`（`/repositories/<同じ ID>/` の形）は、同じ見分け方のとおり 1 回だけ引き直す（基本設計の「[状態遷移と判定][design-flow]」の「状態の組み立て」）

### 決定 2：消されたと読めたら中止ありとし、人が外したか移されたと読めたら何もしない

| 見分けの結果 | 先の依頼の軸 | 理由 |
| --- | --- | --- |
| 消された（Issue の機能が有効なリポの `410`。FACT-134・FACT-148） | 中止あり（D3）。「先に見る」の順 14 で計画を見直し、`dependency-review` の印（`dependency` に番号）を書く | 相手が閉じられたときと同じく、先の変更が入らないことを踏まえて、計画を確かめてから進む |
| `404` | 中止あり（消されたときと同じ） | 同じ実行で、作業の単位の Issue と依存の一覧を、当てる先のリポから読めている。当てる先のリポの相手なら、`404` は、移した先で消された（FACT-145）と読める。読み違えても、起きるのは計画の見直しが 1 回で、見直した後は `dependency-review` の印があるので引き直さない。順 7 で止めると、人が手当てする道の無いまま、毎回の実行が止まる |
| ある（2xx で当てる先のリポの Issue が返った） | 変えない（何もしない） | 相手の Issue は残り、依存だけが無い。人が依存を外したと読む（人が待ちを解く操作） |
| 移された（`/repos/` の形でほかのリポを指す `301` か、`Location` の値が空の `301`。FACT-66・FACT-145） | 変えない（何もしない） | 相手は別のリポにある。App から見えないリポへ移った相手は、依存の数に残るので、詳細設計の数の比べ（一覧の件数が `totalBlockedBy` より少ない）で未完了のまま。移した後に人が外したときは、待ちが解ける |
| ほかの読めない応答（Issue の機能を切ったリポの `410`、当てる先のリポを読めない、`Location` の形が決まった形でない `301`、`302`・`307`、`403`、`5xx`、つながらない、時間の上限で取り消した） | 順 7（状態の組み立て）で読めないときと同じに止める（`github-unreadable`） | 一時の失敗か、確かめていない応答。消されたと読まず、読めなかった作業の単位と相手の番号を、実行の記録と状態の表示に出す |

- 中止ありにした後は、今の決まり（[ADR-20261024-006][adr-cleanup] の決定 3）のまま。`keep` なら（なし）に戻して続け（D4）、`change` なら（なし）に戻したうえで停止中（`plan-change`）にする（D5）。相手が 2 つ以上なら 1 つずつ見直す
- 計画を確かめる AI には、相手が閉じられたのでなく消されたこと（番号）を渡す。消された Issue の中身は読めない
- 消した人は読めない（消すと出来事も残らない。FACT-152）。中止ありは計画の見直しを起こすだけで、後の作業を閉じたり捨てたりしないので、消した人の権限を問わない
- 番号ごとの見分けの結果を、`runs.jsonl` に作業の単位の結果として書く。人が読むためで、判定には使わない

### 影響（Consequences）

- 良い点（安全が上がる）: 消された相手で待っていた作業の単位は、計画を確かめてから進む。相手を閉じたときと消したときで、計画の見直しの有無が変わらない
- 良い点（人の戻し方を保つ）: 人が依存を外せば、今のとおり待ちが解け、計画の見直しも起きない
- 良い点（確かめやすさを保つ）: 判定の入力は GitHub の印・一覧・応答だけで、見分けは状態の組み立てと同じ関数と、確かめた応答（FACT-134・FACT-145・FACT-147・FACT-148）で決まる
- 悪い点（安全の残り）: `wait` の印に番号の無いまま消された相手は、今と同じく見つけられない。依存を足してから次の実行までに相手を消したとき、`wait` の印を書けなかったとき（書き込みの失敗、全体の止める合図が `run` でない間）が当たる
- 悪い点（安全の残り）: App から見えない相手（番号が分からず、依存の数にだけ残る）が消されたときは、依存の数が減るだけで見つけられない。ADR-20261112-001 の見えない相手の数が減っても、人が外したか消されたかを見分けられないので、本 ADR は数に依らない
- 悪い点（安全の残り）: ほかのリポにある相手（一覧に出たときだけ番号を書く）は、番号を当てる先のリポで引く。消されても見つけられない（引いた番号の Issue があるか、移されていれば、案 A と同じく何もしない）。引いた番号の Issue が当てる先のリポで消されていたか無いとき（`410`・`404`）は、要らない計画の見直しが 1 回起きる
- 悪い点（費用が上がる）: 人が外した相手の番号は、作業の単位が終了の枠に入るまで、毎回の実行で REST を 1 回ずつ引く。人が依存を外した後に相手が消されると、要らない計画の見直しが 1 回起きる
- 悪い点（動き続けることの残り）: 確かめていない応答（例：Discussion に変えた Issue。基本設計の一度だけの試しに残る）が、`wait` の印に書いた番号で続けて返ると、毎回の実行が順 7 で止まる。今の人の戻し方は、作業の単位の Issue を閉じることだけ。試しで応答を確かめたら、見分け方に足す
- 悪い点（確かめやすさが下がる）: 状態の組み立ての見分け方で `404` は読めないとしているが、本 ADR で相手の番号を引くときは中止ありと読む。同じ関数の結果を、使う場所で読み分ける

### 確認方法（Confirmation）

- 単体テストで、先の依頼の軸を決める処理を確かめる。有効な `wait` の印の番号、今の依存の一覧、見分けの結果（消された・`404`・ある・移された・ほかの読めない）、`dependency-review` の印の有無、主な流れ（決定済み・計画済みより後・終了の枠）を組み合わせ、次を確かめる
  - 消されたと `404` のときだけ中止ありになり、ある・移されたでは軸が変わらず、ほかの読めない応答では順 7 の止まり方になること
  - 決定済みと終了の枠、見直し済みの番号、当てる先のリポにある同じ番号の相手が一覧に残る番号では、引かないこと
  - 消された相手のほかに終わっていない相手があるとき、未完了を出し、消された相手を除いた新しい `wait` の印を書いた後の実行でも、中止ありが下の値として残ること（最新でない `wait` の印の番号でも見つけること）
- 結合テスト（偽の GitHub と偽の `claude`）で、`wait` の印を書いた後に、偽の GitHub が相手を一覧と数から除き、相手の番号の REST を `410`（`has_issues` は `true`）にすると、次の実行が計画を見直すセッションを起こして `dependency-review` の印を書き、さらに次の実行では引き直さないことを確かめる。REST を `200` にすると、見直しを起こさずに続くことも確かめる
- 実機の振る舞い（相手を消したときの一覧・数・timeline と、消した Issue の `410`）は確かめた（FACT-134・FACT-144・FACT-148・FACT-152）。`setup` が作る進行 Bot の App で同じ応答になるかは、段階 3 の一度だけの試し（基本設計の「[導入と点検][design-setup]」の「GitHub App の権限」）の残りで確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：今のまま、一覧に無い相手は読まない

- 良い点（費用が最も下がる）: 足す処理も GitHub の呼び出しも無い。得るものは費用の少なさだけ
- 中立: 人が依存を外したときに待ちが解ける（案 B・案 C も同じ）
- 悪い点（安全が下がる）: 消された相手で待っていた作業の単位は、ほかに終わっていない相手が無ければ、計画を確かめずに次の工程へ進む。相手を閉じれば計画を見直し、消せば見直さないので、人は消し方で結果が変わることを覚えておく必要がある
- 悪い点（確かめやすさが下がる）: [ADR-20261024-006][adr-cleanup] の決定 3 の表で、消された相手は「ほか → 未完了のまま」に当たりうるのに、実際は（なし）に戻る。表と振る舞いが食い違ったまま残り、表から振る舞いを確かめられない

### 案 B の形 B-1：REST の応答で消されたことを見つける（採用）

- 良い点（安全が上がる）: 消された相手で、計画を確かめてから進む（案 A では確かめない）。消されたことを、消された Issue の `410` という応答で見つける（形 B-2 は出来事が無いことから推し量る）
- 良い点（動き続けることが上がる）: 案 C と違い、計画を変えなくてよいときは人を待たずに続く
- 良い点（確かめやすさが上がる）: 形 B-2 と違い、見分けは状態の組み立てと同じ関数で、応答ごとの見本とテストがすでにある。足すのは、引く番号の選び方と、結果の読み方だけ
- 悪い点（費用が上がる）: 一覧から無くなった番号ごとに REST を引く。人が外した番号は、作業の単位が終了の枠に入るまで毎回引く。人が外した後に相手が消されると、要らない計画の見直しが 1 回起きる

### 案 B の形 B-2：timeline の外した出来事で人が外したことを見つける

- 良い点（費用が下がる）: 人が外したことを、残り続ける出来事で読むので、人が外した番号を毎回 REST で引かない。外した後に相手が消されても外した出来事が残るなら、要らない見直しを起こさない（残るかは確かめていない）
- 悪い点（費用が上がる）: 消されたことを、出来事が無いことから推し量る。App から見えないリポへ移した相手の出来事は、絞ったトークンでは返らない（FACT-152）ので、移した後に人が外した相手も消されたと読み、要らない見直しが起きる（形 B-1 は `301` で移されたと読み、何もしない）
- 悪い点（確かめやすさが下がる）: 確かめていない振る舞いに頼る（外した後に相手を消すと外した出来事も消えるか、公開のリポにある相手の出来事が絞ったトークンで返るか）。出来事と `wait` の印を時刻で比べる処理と、相手のリポと番号の突き合わせを、新しく作ってテストする
- 中立: 形 B-1 と同じく、`wait` の印に番号の無い相手は見つけられない

### 案 C：見つけたら作業の単位を停止中にし、人が依存を確かめて戻す

- 良い点（安全が少し上がる）: 消された相手を、AI でなく人が必ず確かめる
- 悪い点（動き続けることが下がり、人の手間が増える）: 計画を変えなくてよい場合も、人が依存を確かめて `## 再開` を書くまで止まる。[ADR-20261024-006][adr-cleanup] が案 3-C（先の作業が閉鎖済みなら後の作業も止める）を退けた理由と同じ悪い点で、閉じられた相手（AI が見直す）と消された相手で扱いが分かれる
- 悪い点（費用が上がる）: 止めた理由の記号を足し、止めた理由の表を改める
- 中立: 見つけ方と見つけられない相手は、案 B と同じ

## 補足情報（More Information）

- 起票の経緯：段階 3 の一度だけの試し（2026-11-12）で FACT-144 を確かめ、要件の UNDECIDED-100 に足した。案 A〜C は UNDECIDED-100 の候補 (A)〜(C) と同じ。形 B-1 と形 B-2 は、人が外したときの timeline（FACT-152）を確かめた後に、案 B の見分け方の形として足した
- 推奨が成り立つかを確かめたこと
  - `blockedBy` の番号は、当てる先のリポの番号だけとは言えない。App は当てる先のリポだけに入り、点検がほかのリポへの導入を fail にし、トークンも絞る（[ADR-20261020-002][adr-app] の決定 2、基本設計の「[導入と点検][design-setup]」の「GitHub App の権限」）。非公開のほかのリポにある相手は一覧に出ない（FACT-143）。一方、公開のリポにある相手が絞ったトークンの一覧に出るかは確かめておらず、詳細設計は、ほかのリポにある相手が一覧に出れば、相手の番号も `blockedBy` に書く。本 ADR は番号を当てる先のリポで引き、ほかのリポの相手で起こりうる読み違いを、何もしない（案 A と同じ）か、要らない見直し 1 回にとどめる（決定 2 の表と「影響」）
  - 判定に手元の記録を使わない決まり（[ADR-20261015-006][adr-flow] の決定 4、[ADR-20261111-001][adr-halt-pending] の例外）に反しない。使うのは、署名付きの `wait` と `dependency-review` の印、依存の一覧、REST の応答だけ
- 決定の細かい形で比べたこと
  - 引く番号を、最新の `wait` の印に限る形も考えた。消された相手のほかに終わっていない相手があると、順 13（待つ）が消された相手を除いた番号で新しい `wait` の印を書き、次の実行で中止ありが黙って消えるので、有効な `wait` の印のすべてにした（決定 1）
  - `404` を、状態の組み立てと同じく読めないとし、順 7 で止める形も考えた。一覧から無くなった番号は、見直し済みになるか、作業の単位が終了の枠に入るまで毎回引くので、相手が移した先で消されると、毎回の実行が止まり続け、人が手当てする道は作業の単位の Issue を閉じることしか無い。同じ実行で当てる先のリポを読めているので、`404` は当てる先のリポに番号の Issue が無いことを示し、計画の見直しに倒しても後の作業を閉じたり捨てたりしないので、中止ありにした（決定 2）
- 本 ADR で決めないこと
  - 計画を確かめる AI に、相手が消されたことを伝える文（基本設計の「[AI のセッション][design-ai]」）
  - `wait` の印に相手のリポを持たせて、ほかのリポにある相手が消されたことも見つけること（印の表を改めるので、要るなら別の ADR で決める）
  - Discussion に変えた相手の応答の読み方（一度だけの試しで応答を確かめてから、見分け方に足す）
  - timeline の外した出来事で、人が外した番号の REST の引き直しを省くこと（費用が問題になったら、形 B-2 の確かめていない振る舞いを試してから決める）
