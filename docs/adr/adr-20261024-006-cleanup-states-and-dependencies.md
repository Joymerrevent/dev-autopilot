# マージと中止の後は片付けの前の状態を挟んで進行 Bot が片付け、先の依頼は先の作業がマージ済みで続け閉鎖済みなら AI が計画を見直し、載せ直しはレビュー合格の PR だけにする

> **Amended by [ADR-20261025-001][adr-tampered]（2026-10-26）**: 決定 1 のうち、作業場所を消す前の確かめに外れたときの止め方と、片付けをやり直さない例外を改めた。片付けの中で外れたら `workspace-tampered`（実装の都合の記号）で止め、片付けをやり直さないかは、止めた理由の記号（`cleanup-failed`）でなく、マージ済みか閉鎖済みに入った後に書いた `stop` の印かで決める。片付けを軸の値と全体の停止を問わず行うこと、片付けが失敗し続けたら `cleanup-failed` で止めることと、決定 2〜4 は据え置く。
>
> **Amended by [ADR-20261027-001][adr-leftover]（2026-10-27）**: 決定 1 の「作業場所を消す前の確かめ」に、残りのプロセスの確かめを足した。片付けで作業場所を消す前に、作業フォルダかファイルを開いているプロセスを探し、見つかるか探し切れなければ、消さずに停止中（`session-not-stopped`）にする。片付けを軸の値と全体の停止を問わず行うことと、ほかの決定は据え置く。

## 背景と課題（Context and Problem Statement）

- 今の形では、マージを見つけたら、同じ実行で Issue を閉じ、作業場所を消す（FLOW-27、MERGE-7）。片付けは状態にしないので、片付けに失敗したときの居場所が無い。片付けは `needs-human`・`human`・`paused` の除外より先に判定する（[ADR-20261015-006][adr-flow] の決定 3）
- 着手した Issue をやめるときは、人が開いた PR を閉じ、作業ブランチを消し、Issue を閉じる。作業場所のフォルダが残っていれば、進行 Bot は消さずに `needs-human`（`workspace-residue`）にする（「止まった状態から戻す手順」の「着手した Issue をやめるとき」）。着手の後に Issue が閉じられたら `needs-human` にする
- 先の Issue（blocked by）が閉じたら続け（FLOW-33・FLOW-34）、先の PR がマージされたら、後の PR を状態を問わず載せ直す（FLOW-9。作業 AI が直す番は直した後に載せ直す。[ADR-20261022-003][adr-rounds] の決定 5）。先の依頼が中止されたときの決まりは無い
- GitHub では、Read の役でも自分が開いた Issue を閉じられ、Triage の役はどの Issue も閉じられる（公式文書の組織のリポの役の表。2026-10-24 に確かめた）。push 未満の人も、Issue を閉じて作業をやめる形にできる
- 2026-10-23〜24 の組み直し（[ADR-20261024-001][adr-model-states]）で、終了の枠に、マージ済み・完了・閉鎖済み・中止を置き、先の依頼を主な流れに重ねる軸にした

課題：マージと中止の後の片付けを、どう状態に置き、誰が行うか。誰が Issue を閉じたら中止にするか。先の依頼が終わった・中止されたときに、後の作業をどう続けるか。base が進んだときに、どの PR を載せ直すか。

## 判断の決め手（Decision Drivers）

- 片付けを待つ間と、片付けに失敗したときの居場所が、状態で分かる
- 外の人に、進行 Bot の片付けで作業を捨てさせない
- 後の作業に要るのは、先の変更が base に入ったこと。先の依頼が中止されたら、計画のまま進めてよいかを確かめる
- PR を閉じる判断を AI だけに任せず、人が push した変更を捨てない
- 載せ直しで、まだ直している途中の変更を確かめ直す手間を使わない

## 検討した選択肢（Considered Options）

- 案 1-A：マージ済みと閉鎖済みを片付けの前の状態にし、どちらも進行 Bot が片付ける
- 案 1-B：今のまま、マージを見つけた実行で片付け、着手の後に閉じた Issue は人が片付ける
- 案 2-A：push 以上の人が Issue を閉じたときだけ閉鎖済みにし、push 未満の人が閉じたら止めて人に渡す
- 案 2-B：誰が閉じても閉鎖済みにする
- 案 3-A：先の作業がマージ済みで続け、閉鎖済みなら AI が計画を見直す
- 案 3-B：今のまま、先の Issue が閉じたら（マージでも中止でも）続ける
- 案 3-C：先の作業が閉鎖済みなら、後の作業も止めて人に渡す
- 案 4-A：base が進んだら、レビュー合格の PR だけを載せ直す
- 案 4-B：今のまま、先の PR がマージされたら、後の PR を状態を問わず載せ直す

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」「案 3-A」「案 4-A」。

理由: マージや中止から片付けまでの間と、片付けに失敗したときの居場所が状態で分かり、中止の後の片付けも人の手を要らない。外の人が Issue を閉じても、進行 Bot が作業を捨てない。
先の依頼は、後の作業に要るもの（先の変更が base に入ったこと）で続け、中止されたときは計画のまま進めてよいかを AI が確かめ、変える必要があれば人に戻す先を選ばせる。載せ直しは、人に渡す直前のレビュー合格の PR だけに行うので、直している途中の変更を確かめ直さない。

### 決定 1：マージと中止の後は、片付けの前の状態を挟み、進行 Bot が片付ける

| 線 | 元 → 先 | 出来事 | 進行 Bot がすること |
| --- | --- | --- | --- |
| T15・T22 | 変更の枠の状態 → マージ済み | 人がマージした | — |
| T27 | マージ済み → 完了 | 進行 Bot が片付けた | Issue を閉じ、作業ブランチと作業場所（セッションのフォルダ）を消し、`cleanup` の印を書く |
| T21 | 依頼・計画・変更の枠の状態 → 閉鎖済み | push 以上の人が Issue を閉じた（決定 2） | — |
| T28 | 閉鎖済み → 中止 | 進行 Bot が片付けた | 開いた結びつく PR を閉じ、作業ブランチと作業場所を消し、`cleanup` の印を書く |

- 片付けは AI を使わない進行 Bot の工程で、重ねる軸の値（一時停止中・引き取り中・停止中・先の依頼・攻撃の疑い）と全体の停止を問わず行う。軸の値（ラベル、見出し）は書き換えない（マージと Issue を閉じることは人の最後の操作で、人の止め方に反しない）
- 作業ブランチを消しても、閉じた PR の commit は GitHub の PR に残る
- 作業場所を消す前の確かめ（[ADR-20261013-001][adr-workspace] の、作業場所が作ったときと同じかの確かめ）は今のまま行い、外れたら消さずに止める（止めた理由の記号は、実装の都合の記号として詳細設計で足す）
- 片付けが失敗し続けたら（回数は今の実行の失敗の上限と同じ考え方で、基本設計で決める）、片付けの前の状態（マージ済みか閉鎖済み）のまま停止中（`cleanup-failed`）にする。人が確かめて `## 再開 続きから` を書くまで、片付けもやり直さない（軸の値を問わず行う決まりの、ただ 1 つの例外。消せないものを毎回消そうとし続けない）
- 片付けの後（完了・中止）に人が Issue を開き直したときは、[ADR-20261024-001][adr-model-states] の状態の決め方のまま読む。結びつく PR がマージされずに閉じていれば、PR だけが閉じられた形として停止中（`pr-closed`）になり、人が戻す先を選ぶ

### 決定 2：閉鎖済みに入るのは、push 以上の人が Issue を閉じたときだけ

- 進行 Bot は、Issue を閉じた人を、Issue の timeline の閉じた記録で確かめる。push 以上の人が閉じたら閉鎖済み（T21）
- push 未満の人（Issue を書いた外の人、Triage の役の人など）が閉じたときは、閉鎖済みにせず、主な流れは閉じる前の状態のまま停止中（`unauthorized-close`）にする。進行 Bot は片付けない
- 人は、やめるなら、push 以上の人が Issue を開き直してから閉じ直す（閉鎖済みに入り、進行 Bot が片付ける）。続けるなら、Issue を開き直してから `## 再開 <戻す先>` を書く
- 結びつく PR がマージされていれば、誰が Issue を閉じてもマージ済み（片付けの前）として読む（マージは人の最後の操作）

### 決定 3：先の依頼は、先の作業がマージ済みで続け、閉鎖済みなら AI が計画を見直す

- 先の依頼の軸は、主な流れが決定済みか、決定済みより後のときだけ見る（[ADR-20261024-001][adr-model-states] の決定 3）
- 先の作業は、次のときに終わったとみなす

| 先の作業 | 後の作業の先の依頼の軸 | 線 |
| --- | --- | --- |
| 結びつく PR がマージされた（マージ済みか完了） | （なし）に戻り、同じ状態から続ける | D2 |
| push 以上の人が Issue を閉じ、結びつく PR がマージされていない（閉鎖済みか中止） | 中止あり | D3 |
| ほか（push 未満の人が閉じて止まっている場合を含む） | 未完了のまま | — |

- 先の作業がマージ済みになったら、片付けを待たずに続ける（後の作業に要るのは、先の変更が base に入ったこと）
- 中止ありの作業は、AI（計画を確かめる AI。計画を書いた AI とは別）が、先の依頼が中止されたことを踏まえて、今の計画を見直す。進行 Bot は、見直しの結果を `dependency-review` の印（`dependency` に先の Issue の番号、`result` が `keep` か `change`）に書く
  - `keep`（計画を変えずに進めてよい）：（なし）に戻り、同じ状態から続ける（D4）
  - `change`（計画を変える必要がある）：（なし）に戻し、あわせて止め方を停止中（`plan-change`）にする。止めた理由のコメントに、AI の判断と理由を書く（AI の文なので検疫を通す）。人が戻す先を選ぶ（D5）。PR を閉じる判断を AI だけに任せず、人が push した変更を捨てないため
- 後の作業が決定済み（計画の前）なら、見直さずに（なし）に戻す。計画は、先の作業が中止された後の base で立てるため
- 先の依頼が 2 つ以上あるときは、1 つずつ見直し、どれかが `change` なら止める。`dependency-review` の印のある先の作業は、見直し済みとして数え直さない

### 決定 4：base が進んだら、レビュー合格の PR だけを載せ直す

- 進行 Bot は、base が進んだとき（ほかの PR がマージされた、先の作業がマージされた）に、レビュー合格の PR だけを載せ直す。ほかの状態の PR は、レビュー合格になってから載せ直す
- 載せ直しの結果（MERGE-6 の差分（patch-id）の比べ方のまま）

| 結果 | 線 | 次 |
| --- | --- | --- |
| 差分が同じ | T17（レビュー合格のまま） | `review` の印（`findings` を含む）と `merge` の印を新しい head に付け直す（今のまま） |
| 差分が変わった | T18（変更済み） | 必須チェックを待ってからレビューする（[ADR-20261024-003][adr-check-first]）。往復に数えない（[ADR-20261022-003][adr-rounds] の決定 1） |
| 衝突した | T19（衝突あり） | `conflict` の印（`head`）を書く。作業 AI が衝突を解く（T20）。衝突の解消は、今のとおり対応コメントと `fix` の印（`cause` が `conflict`）を書き、往復に数え、作業 AI を起こす前に往復の上限を確かめる（[ADR-20261022-003][adr-rounds] の決定 2） |

- 基線が緑でない間は、今のとおり載せ直しを待つ（[ADR-20261015-006][adr-flow] の決定 2）
- 作業 AI が直している途中の PR は載せ直さないので、修正と載せ直しの順の決まり（[ADR-20261022-003][adr-rounds] の決定 5）は要らなくなる

### 影響（Consequences）

- 良い点: マージや中止から片付けまでの間と、片付けに失敗したときの居場所が状態で分かる。中止の後の PR・作業ブランチ・作業場所を、人が片付けなくてよい
- 良い点: 外の人や Triage の役の人が Issue を閉じても、進行 Bot が作業を捨てない
- 良い点: 先の依頼が中止されたときに、計画のまま進めてよいかを確かめられる。変える必要があれば人が戻す先を選ぶので、人が push した変更を AI の判断だけで捨てない
- 良い点: 載せ直しをレビュー合格の PR だけにするので、直している途中の変更を確かめ直す手間と、修正と載せ直しの順の決まりが要らない
- 悪い点: 中止の片付けで作業ブランチを消すので、中止の後に作業を続けたいときは、閉じた PR から取り出す
- 悪い点: push 未満の人が Issue を閉じると止まり、push 以上の人が開き直して閉じ直すか、開き直して再開する手間がかかる
- 悪い点: 先の依頼が中止されると、計画の見直しのセッションを 1 つ使う
- 悪い点: レビュー合格になるまで base を取り込まないので、base が大きく進むと、レビュー合格の後の載せ直しで差分が変わり、もう一度レビューすることが増える

### 確認方法（Confirmation）

- 単体テストで、終了の枠の状態の決め方（PR のマージ、Issue を閉じた人の権限、`cleanup` の印）と、push 未満の人が閉じたときに停止中になることを確かめる
- 単体テストで、先の依頼の軸の決め方（先の作業がマージ済み・閉鎖済み・push 未満の人が閉じた、`dependency-review` の印、後の作業が決定済みのとき）を確かめる
- 結合テスト（偽の `gh` と偽の `claude`）で、マージの後に Issue が閉じられて作業場所が消え、中止の後に PR が閉じられて作業ブランチと作業場所が消え、片付けが失敗し続けると停止中になることを確かめる
- 結合テストで、base が進んだときに、レビュー合格の PR だけが載せ直され、ほかの状態の PR は載せ直されないことを確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：片付けの前の状態を持ち、どちらも進行 Bot が片付ける

- 良い点: 片付けを待つ間と、失敗したときの居場所がある。中止の後も人の手が要らない
- 悪い点: 状態が 2 つ増える

### 案 1-B：今のまま

- 良い点: 状態が少ない
- 悪い点: 片付けの失敗の居場所が無い。中止の後は、人が PR と作業ブランチを片付け、残った作業場所で止まる

### 案 2-A：push 以上の人が閉じたときだけ閉鎖済みにする

- 良い点: 外の人に、進行 Bot の片付けで作業を捨てさせない
- 悪い点: push 未満の人が閉じると止まり、人の手が要る

### 案 2-B：誰が閉じても閉鎖済みにする

- 良い点: 閉じれば必ず片付く
- 悪い点: Issue を書いた外の人が閉じるだけで、進行 Bot が PR と作業ブランチを消す

### 案 3-A：先の作業がマージ済みで続け、閉鎖済みなら AI が計画を見直す

- 良い点: 先の変更が base に入った時点で続けられる。中止されたときに、計画のまま進めてよいかを確かめられる
- 悪い点: 見直しのセッションを使う

### 案 3-B：今のまま、先の Issue が閉じたら続ける

- 良い点: 見直しのセッションが要らない
- 悪い点: 先の依頼が中止されても、先の変更があるつもりの計画のまま進む

### 案 3-C：先の作業が閉鎖済みなら、後の作業も止めて人に渡す

- 良い点: 人が必ず確かめる
- 悪い点: 計画を変えなくてよい場合も、人の手が要る

### 案 4-A：レビュー合格の PR だけを載せ直す

- 良い点: 直している途中の変更を確かめ直さない。修正と載せ直しの順の決まりが要らない
- 悪い点: base が大きく進むと、レビュー合格の後にもう一度レビューすることが増える

### 案 4-B：今のまま、どの状態でもすぐ載せ直す

- 良い点: PR がいつも新しい base の上にある
- 悪い点: 直している途中の変更を、載せ直しのたびに確かめ直す。修正と載せ直しの順の決まりが要る

## 補足情報（More Information）

- 2026-10-23〜24 にメンテナと状態遷移を組み直したときに、片付けの前の状態、片付けを軸の値を問わず行うことと失敗したときの例外、push 以上の人が閉じたときだけ中止にすること、先の依頼の終わり方と中止ありの見直し、レビュー合格の PR だけの載せ直しを決めた
- 中止ありの見直しに計画を確かめる AI を使うことは、組み直しのときの案を、起票のときに決定にした。片付けの後に Issue を開き直したときの読み方と、作業場所を消す前の確かめに外れたときの扱いは、起票のときに今の形に合わせて足した
- push 未満の人も Issue を閉じられることは、GitHub の公式文書（組織のリポの役の表の「Close issues they opened themselves」と「Close, reopen, and assign all issues and pull requests」）で、2026-10-24 に確かめた
- 本 ADR で決めないこと
  - 片付けが失敗し続けたとみなす回数（基本設計）
  - 中止ありの見直しで AI に渡すもの（基本設計）
- 関連する要件：FLOW-9、FLOW-10、FLOW-27、FLOW-33、FLOW-34、「止まった状態から戻す手順」の「着手した Issue をやめるとき」（[01-issue-flow.md][flow]）、MERGE-6、MERGE-7（[03-merge.md][merge]）、UNDECIDED-81（[09-undecided.md][undecided]）
- 関連する ADR：[ADR-20261024-001][adr-model-states]、[ADR-20261024-003][adr-check-first] と、冒頭の表の ADR
