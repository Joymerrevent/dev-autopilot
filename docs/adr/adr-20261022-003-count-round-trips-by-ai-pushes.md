# 往復の回数は、作業 AI が直すか衝突を解いて push した回数（fix の印の数）で数え、同じ指摘の再発は、AI の変更の後のラウンドでだけ判定する

要件の UNDECIDED-72（[決めていないこと][undecided]の「ADR で決めること」の「レビューとマージ」。往復の数え方と、同じ指摘の再発を判定するラウンド）を決める。

改める決定と、据え置く決定は次のとおり。改める文と、改めた後の読み方は、決定 7 に並べる。

- [ADR-20261019-001][adr-repeat]：決定 2 の「新しいラウンド」（同じ指摘の再発を判定するラウンド）を、AI の変更の後のラウンドに限る（本 ADR の決定 3）。確認方法の 1 つ目の項目の単体テストに、判定するラウンドとしないラウンドの組を足す。
  2026-10-22 の追記（往復に数えるラウンドでだけ判定する）は、本 ADR で決め直す。
  決定 1（`findings` の ID）、決定 2 のうち比べる相手（前のどのラウンドの `findings` でもよい）と同じラウンドの中の重なりを数えないこと、確認方法のほかの項目は据え置く
- [ADR-20261018-003][adr-model]：決定 1 の、修正工程（段階 7）の材料「AI のレビューの後に AI が直した回数（往復の回数）」は据え置く。本 ADR の往復の回数（`fix` の印の数）は、文を変えずに「AI が直した回数」と同じ数になる
- [ADR-20261016-001][adr-pr]：決定 1 の、CI の `failure` と `timed_out` を修正に回して往復（IMPL-24）に数えることは据え置く。CI の赤の修正も `fix` の印を書くので、本 ADR の数え方で 1 回に数える
- [ADR-20261015-005][adr-settings]：決定 1 の、往復の回数の上限を外すのは安全の境界を緩める変更として ADR で決めることは据え置く。本 ADR は上限を外さず、往復に数える出来事を決める。
  進行 Bot だけの載せ直しで差分が変わった再レビューを往復から外すのは、数える出来事を減らす向きなので、本 ADR で決める
- MERGE-6 の「（patch-id が変わったときの再レビューを）往復に数える」は、ADR で決めた文でなく要件だけの文だが、往復の数え方を変えるので本 ADR で決める

## 背景と課題（Context and Problem Statement）

- 往復の上限と同じ指摘の再発（IMPL-24、FLOW-28）は、AI の修正が収束しない PR を人に渡すための決まり。往復の上限の初期値は 3 回（`limits.roundTrips`）で、[ADR-20261015-005][adr-settings] の決定 1 は、上限を外すのを安全の境界を緩める変更とする
- 要件の中に、往復の定義が 2 つある
  - IMPL-24 は、1 つの文の中で、往復を「AI の修正の往復（作業 AI が直し、レビュー AI が見直す往復）」と「AI が直した回数」とし、続けて「載せ直しで差分が変わった再レビュー（MERGE-6）も往復に数える」とする
  - MERGE-6 は、載せ直しで差分（patch-id）が変わった（周辺が変わった、衝突した）ときの再レビューを往復に数える。衝突の解消は、作業 AI の修正セッション（IMPL-23 と同じ形）で行う
  - 段階の表の修正工程（段階 7）、IMPL-25、[ADR-20261018-003][adr-model] の決定 1 は、段階 7 の材料を「AI が直した回数（往復の回数）」と書く
- 基本設計の「[状態遷移と判定][design-flow]」の「ラウンドと往復の数え方」は、往復の回数を、PR の有効な `fix` の印の数と、載せ直しで差分が変わった再レビューのラウンドの数の和で数える。
  載せ直しのラウンドは、ラウンドの head が、1 つ前のラウンドの最後の head を 1 つ目の親に、base ブランチの commit を 2 つ目の親に持つ merge の commit かで見分ける。`fix` の印は修正を push した後に書き、衝突の解消には書かない
- 同じ指摘の再発は、[ADR-20261019-001][adr-repeat] の決定 2 が「新しいラウンド」で判定するとし、用語を「修正の後のラウンドで、前のラウンドと同じ指摘がもう一度出ること」と決めた。
  基本設計の 3 回目の再レビュー（2026-10-22）の直し（PR #100）は、判定を「往復に数えるラウンド（AI の修正の後か、載せ直しで差分が変わった後のラウンド）」に限る文を、IMPL-24 と基本設計に書き、[ADR-20261019-001][adr-repeat] に 2026-10-22 の追記として足した
- 基本設計の 4 回目の再レビュー（2026-10-22）は、往復の数え方と判定の範囲に、次の穴と食い違いを見つけた
  - 数え漏れ（続ける側に倒れる）
    - H-1：衝突の解消で作業 AI が merge の commit の後に commit を足すと（品質ゲートで壊れた型やテストを直すなど）、head が merge の commit の形にならず、載せ直しのラウンドにも `fix` の印にも当たらない。衝突のたびに、往復の上限が 1 回分ずつ効かなくなる
    - M-4：修正の push と、`fix` の印付きの対応コメントの書き込みの間で実行が落ちるか、全体の止める合図が `stop` になると、修正を往復に数えず、次のラウンドで同じ指摘の再発も判定せず、対応コメントも PR に出ない
  - 数えすぎ（止まる側に倒れる）
    - M-5：修正の後に依存の載せ直しが入ると、1 回の再レビューを、`fix` の印と載せ直しのラウンドの 2 回に数える。人が GitHub の画面で base ブランチを取り込んだ merge の commit も、載せ直しとして数える
    - H-2：レビュー工程（段階 6）の載せ直しのラウンドを修正工程（段階 7）に持ち越し、作業 AI が 1 回も直す前に `round-limit` になる
  - 判定の誤り
    - H-2：`fix` が出て作業 AI がまだ直していない間に、依存の載せ直しで差分が変わると、載せ直しのラウンドで同じ指摘の再発を判定する。直していない指摘を再発と読んで `repeated-finding` で止め、人が `needs-human` を外しても同じラウンドでまた止まる
  - 言葉と正典の食い違い
    - M-21：IMPL-24 の中の往復の定義と、段階 7 の「AI が直した回数（往復の回数）」が、基本設計の数え方と別の数を指す
    - M-22：[ADR-20261019-001][adr-repeat] の 2026-10-22 の追記は、決定 2 の判定の範囲を、人のラウンドを外す向きに狭め、用語の「修正の後のラウンド」より載せ直しのラウンドの分だけ広げた。
      [ADR の README][adr-readme] の基準（直した後の注記を読んで、決定が変わったと思う人がいるか）では、追記でなく新しい ADR に当たる
  - 人の戻し方の欠け
    - M-3：`round-limit` と `repeated-finding` で止めた PR は、人が `needs-human` を外しても往復を数え直さないので、人が直さずに戻すと次の実行でまた止まる。止めた理由のコメントにも、要件の「止まった状態から戻す手順」にも、人がすることが書いていない

課題：往復の回数で 1 回と数える出来事は何か。同じ指摘の再発を、どのラウンドで判定するか。衝突の解消を往復に数えるか、数えるなら何で見分けるか。
修正の push と `fix` の印の間で切れたとき、作業 AI が直す番に依存の相手がマージされたとき、人が `needs-human` を外したときを、どう扱うか。段階 7 の記録で「AI が直した回数」と「往復の回数」を分けるか。

## 判断の決め手（Decision Drivers）

- 往復の上限が止めたいもの（AI の変更が収束しない PR）を、AI の変更の回数で直接数えること
- 数え漏れを無くし、迷う場面は止まる側に倒すこと（フェイルセーフ。往復の上限は安全の境界の 1 つ）
- 作業 AI が 1 回も直していない PR を、往復の上限でも同じ指摘の再発でも止めないこと（基本設計の 3 回目の再レビュー（2026-10-22）の H-8 の直しで、メンテナが選んだ形）
- 判定を、GitHub にある署名付きの印と commit だけで決め（[ADR-20261015-006][adr-flow] の決定 4）、commit の親の形のような壊れやすい読み方に、往復の上限を頼らないこと
- 往復の定義を要件の中で 1 つにし、承認済みの ADR の文とそろえること

## 検討した選択肢（Considered Options）

- 案 A1：往復を、作業 AI が変更を push した回数（`fix` の印の数）で数え、同じ指摘の再発は AI の変更の後のラウンドでだけ判定する
- 案 A2：今の数え方（`fix` の印の数と、載せ直しで差分が変わったラウンドの数の和）を保ち、穴を塞ぐ
- 案 A3：今の設計の文のまま、レビュー工程（段階 6）の載せ直しのラウンドも数え、単体テストの期待を狭め、段階 6 から 7 に替えるときに往復の回数を示す

## 決定（Decision Outcome）

採用した選択肢:「案 A1」。
理由: 往復の上限が止めたいもの（AI の変更が収束しない形）を、作業 AI が変更を push した回数で直接数える。数える元が `fix` の印だけになり、H-1 と M-5 の穴の元になった commit の形の見分けが、往復の回数に要らなくなる。
AI の変更は、修正・衝突の解消・push が届かなかった回のどれも数える側に倒れる。進行 Bot だけの載せ直しの再レビューは AI の変更を含まず、費用は 1 Issue の累計の上限（`limits.issueCostUsd`）で止まる。
改める承認済みの決定は [ADR-20261019-001][adr-repeat] の決定 2 の判定の範囲だけ（M-22 の直しで、どの案でも要る）で、[ADR-20261018-003][adr-model] と [ADR-20261016-001][adr-pr] の文は変えずに合う。

### 決定 1：往復の回数は、作業 AI が変更を push した回数（PR の有効な `fix` の印の数）で数える

- 往復の回数は、PR の有効な `fix` の印の数。`fix` の印は、作業 AI の変更を push するたびに 1 つ書く
  - レビューの `fix` を直したとき（IMPL-23）
  - CI の赤を直したとき（[ADR-20261016-001][adr-pr] の決定 1）
  - 載せ直しの衝突を解いたとき（決定 2）
  - push が GitHub に届かなかった回も数える（決定 4）
- 次の再レビューは、新しいラウンドにするが、往復に数えない
  - 進行 Bot だけで行う載せ直し（AI のセッションを起こさない）で、差分（patch-id）が変わった再レビュー
  - 人の push の後の再レビュー。人が GitHub の画面で base ブランチを取り込んだ後の再レビューを含む
- レビュー工程（段階 6）では作業 AI が直さないので、`fix` の印が無い。段階 6 から修正工程（段階 7）に持ち越した PR は、往復を 0 回から数える
- 数える元は `fix` の印だけで、commit の親の形で往復を数えない。1 つのラウンドを、`fix` の印と載せ直しのラウンドの 2 回に数える形は無い
- 往復の回数がすでに上限（`limits.roundTrips`）に達していれば、作業 AI を起こさずに `needs-human`（`round-limit`）にする（今のとおり。衝突の解消にも掛ける。決定 2）
- 段階 7 の記録の「AI が直した回数（往復の回数）」（[ADR-20261018-003][adr-model] の決定 1、IMPL-25、段階の表）は、本決定の往復の回数と同じ数にし、2 つの数に分けない。
  衝突の解消の回数を分けて見たいときは、手元の記録のセッションの名前（衝突の解消は `rebase-pr-<PR の番号>`。基本設計の「[AI のセッション][design-ai]」の「セッションの名前」）で分けられる

### 決定 2：衝突の解消も、修正と同じく対応コメントと `fix` の印を書き、作業 AI を起こす前に往復の上限を確かめる

- 修正工程（段階 7）以降の載せ直しの衝突は、今のとおり作業 AI の衝突の解消のセッション（MERGE-6。IMPL-23 と同じ形）で解く
- 衝突の解消の push でも、修正と同じく、対応コメントと `fix` の印を書く
  - 見出しは IMPL-23 の見出し（`## R<n> の指摘への対応（<コミット>）`）のまま。本文は、進行 Bot が持つ「base ブランチを取り込んで衝突を解いた」の固定の文と、作業 AI が返した検査の結果（出力契約の `checks`）
  - 対応コメントには、修正の対応コメントと同じく、push の手順の漏えいの検査と検疫を掛ける
  - `fix` の印の `round` は、修正と同じく、最新の `review` の印の `round`
- 作業 AI が merge の commit の後に commit を足しても、merge の commit を作らずに衝突を解いても、`fix` の印 1 つで 1 回に数える。push の手順に、head が merge の commit 1 つだけかを確かめる決まりは足さない
- 衝突の解消の作業 AI を起こす前に、往復の回数を確かめる。すでに上限に達していれば、衝突を解かずに `needs-human`（`round-limit`）にする
- レビュー工程（段階 6）の衝突は、今のとおり人の番にし（`note kind=conflict`）、`fix` の印を書かない

### 決定 3：同じ指摘の再発は、AI の変更の後のラウンドでだけ判定する

- AI の変更の後のラウンドは、1 つ前のラウンドに有効な `fix` の印があり、ラウンドの `review` の印の `head` が、次のどちらかに当たるラウンド
  - 1 つ前のラウンドの `fix` の印の `head` と同じ
  - 1 つ前のラウンドの `fix` の印の `head` を 1 つ目の親に、base ブランチの commit を 2 つ目の親に持つ merge の commit
- 2 つ目の形は、修正の後に進行 Bot が依存の載せ直しを行ったラウンドに当たる。merge の commit の作者は問わない。人が base ブランチを取り込んだ merge の commit も、形が同じなら判定する。base ブランチを取り込んだだけの merge の commit では、レビューする変更が作業 AI の変更のままのため
- 次のラウンドでは判定しない
  - PR の最初のラウンド
  - 進行 Bot だけの載せ直しで差分が変わったラウンド（1 つ前のラウンドに `fix` の印が無い）
  - 人の push の後のラウンド（head が上の 2 つの形に当たらない）
  - レビュー工程（段階 6）のラウンドと、段階 6 から持ち越した PR の、作業 AI が直す前のラウンド
- 比べる相手は、今のとおり前のどのラウンドの `findings` でもよい。往復に数えないラウンドと、判定しないラウンドの `findings` も比べる相手に入れる。同じラウンドの中の重なりは数えない（[ADR-20261019-001][adr-repeat] の決定 2 のまま）
- 判定しないラウンドの `review` の印にも、今のとおり `findings` を書く。後のラウンドの比べる相手になるため
- head の形の見分けは、同じ指摘の再発を判定するかにだけ使い、往復の回数（決定 1）には使わない

### 決定 4：修正と衝突の解消の `fix` の印は push の前に書き、ラウンドの `fix` の印があるかは、PR に届いた印で見る

- 修正と衝突の解消の push では、対応コメントと `fix` の印（`head` は送る SHA）を、push の前に書く。push の手順の、全体の止める合図を読み直す順番（GitHub に書き込む前に合図を読む運用の規則）は変えず、合図を読み直した後、push の前に書く。push の後に、作業ブランチの先端が送った SHA になったことを読み戻す（今のとおり）
- push の後に実行が切れても、対応コメントと `fix` の印は書いてあるので、修正を往復に数え、次のラウンドで同じ指摘の再発を判定する。対応コメントも PR に出る（M-4 の窓が無くなる）
- push が断られたか、`fix` の印を書いた後、push の前に実行が切れたときは、`fix` の印の `head` が PR に届かない
  - 次の工程の表の順 15 で、最新のラウンドの `fix` の印がまだ無いかは、`head` が PR の head か、PR の head の祖先の `fix` の印（PR に届いた `fix` の印）で見る。届いた `fix` の印が無ければ、修正をやり直す
  - 衝突の解消の push が届かなかったときは、base ブランチが PR の head より先に進んだままなので、次の工程の表の順 18 で載せ直しからやり直す（往復の上限の確かめを含む。決定 2）
  - 往復の回数には、届かなかった `fix` の印も数える。届かなかった回の数えすぎは、止まる側に倒れる

### 決定 5：作業 AI が直す番は、依存の載せ直しを修正の後に回す

- 作業 AI が直す番は、修正工程（段階 7）以降で、最新の `review` の印が `fix` か CI が赤で、最新のラウンドに PR に届いた `fix` の印がまだ無い間
- 作業 AI が直す番の PR は、依存の相手の Issue に結びつく PR がマージされても、作業中の表の前の確かめで載せ直さず、修正（次の工程の表の順 15）を先に行う。載せ直しは、修正の push の後の実行で、再レビューの前に行う。再レビューは、載せ直した head で行う
- 修正の前に載せ直さない理由は 2 つある
  - 修正の前の載せ直しが衝突すると、衝突の解消の `fix` の印が、まだ直していないラウンドに付く。順 15 は直したラウンドと読んで修正に進まず、次のラウンドは AI の変更の後のラウンドとして判定され、直していない指摘を同じ指摘の再発と読む（H-2）
  - 修正の前の載せ直しで差分が変われば、まだ直していない変更をもう一度レビューする分の利用枠を使う
- 作業 AI が直す番でない PR（レビュー工程（段階 6）で人が直す番の PR を含む）の依存の載せ直しは、今のとおり作業中の表の前に行う

### 決定 6：人が `needs-human` を外しても往復を数え直さず、止めた理由のコメントと戻す手順に、人がすることを書く

- 往復の回数は PR の初めから数え、人が `needs-human` を外しても数え直さない（1 Issue の累計の費用と同じ）
- `round-limit` の止めた理由のコメントと、要件の「止まった状態から戻す手順」に、次を書く
  - 外しても往復を数え直さないので、何もせずに外すと、次の実行でまた止まること
  - 人が直して push してから戻すこと。人の push の後の再レビューは往復に数えないが、再レビューが `fix` を返すと、往復の回数は上限のままなので、また止まること
  - 作業 AI に続けさせるなら、リポの設定の `limits.roundTrips` を上げる PR をマージしてから戻すこと
- `repeated-finding` の止めた理由のコメントと、要件の「止まった状態から戻す手順」に、次を書く
  - 外しても、同じラウンドの同じ判定で、次の実行でまた止まること
  - 人が直して push してから戻すこと。人の push の後のラウンドでは、同じ指摘の再発を判定しない
  - `limits.roundTrips` を上げても、同じ指摘の再発の止まり方は変わらないこと
- 止まる遷移（FLOW-28）と、止めた理由の記号（`round-limit`、`repeated-finding`）は変えない

### 決定 7：要件の 2 つの文と、ADR-20261019-001 の決定 2 を、次のとおりに読む

- IMPL-24 の往復の定義を 1 つにする。往復の回数は、作業 AI が直すか衝突を解いて push した回数（PR の `fix` の印の数）。
  進行 Bot だけの載せ直しで差分が変わった再レビューと、人の push の後の再レビューは、往復に数えない。同じ指摘の再発は、AI の変更の後のラウンドでだけ判定する（決定 1、決定 3）
- MERGE-6 の「patch-id が変わった（周辺が変わった、衝突した）ときだけ再レビューを行い、往復に数える」は、「patch-id が変わったときだけ再レビューを行う。往復（IMPL-24）に数えるのは、衝突を作業 AI が解いたときだけで、進行 Bot だけの載せ直しで差分が変わった再レビューは往復に数えない」と読む。
  衝突の解消でも、対応コメントと `fix` の印を書く（決定 2）
- 段階の表の修正工程（段階 7）、IMPL-25、[ADR-20261018-003][adr-model] の決定 1 の「AI が直した回数（往復の回数）」は、文を変えずに本 ADR の往復の回数と同じ数を指す
- [ADR-20261019-001][adr-repeat] の決定 2 の「新しいラウンドの `review` の印の `findings` の ID が、前のどれかのラウンドの `review` の印の `findings` にもあれば、同じ指摘の再発とする」は、「新しいラウンド」を AI の変更の後のラウンド（決定 3）と読む。
  同じ ADR の冒頭の用語の「修正の後のラウンド」は、衝突の解消の後を含む、AI の変更の後のラウンドと読む
- [ADR-20261019-001][adr-repeat] の確認方法の 1 つ目の項目の「前のラウンドとの比べ方」は、判定するラウンドとしないラウンドの組（決定 3）を含めて読む
- [ADR-20261019-001][adr-repeat] の本文は書き換えない。承認の後に、タイトルの下に改めた旨の注記を足し、2026-10-22 の追記に取り消し線を引いて、本 ADR で決め直したことを添える（ADR の README の「決定の一部だけを改める」）

### 影響（Consequences）

- 良い点: 往復の回数に commit の形の見分けが要らず、衝突の解消で作業 AI が commit を足しても 1 回に数える（H-1）。head の形の見分けを誤っても、往復の上限は効く
- 良い点: 1 つのラウンドを 2 回に数える形と、人の base ブランチの取り込みを往復に数える形が無くなる（M-5）
- 良い点: 作業 AI が 1 回も直していない PR は、往復の上限でも同じ指摘の再発でも止まらない。段階 6 から持ち越した PR と、修正を待つ間の依存の載せ直しで、AI が直す前に止まる形が無くなる（H-2）
- 良い点: 修正の push と `fix` の印の間の窓が無くなり、push が届かなかった回は止まる側に数える（M-4）
- 良い点: 要件の往復の定義が 1 つになり、段階 7 の材料（[ADR-20261018-003][adr-model]）と CI の赤の扱い（[ADR-20261016-001][adr-pr]）の文を変えずに合う（M-21）。同じ指摘の再発の判定の範囲を、ADR で決め直す（M-22）
- 良い点: 人が止まった PR を戻すときにすることが、止めた理由のコメントと戻す手順で分かる（M-3）
- 悪い点: 進行 Bot だけの載せ直しで差分が変わった再レビューは、往復の上限では止まらない。base ブランチが進んで差分が変わるたびに 1 ラウンドのレビューを起こし、1 Issue の累計の費用の上限（`limits.issueCostUsd`）で止まる
- 悪い点: 「[レビューの Skill][review]」の業界の例（レビュー済みの往復が一定数を超えたら止める。CodeRabbit の 5 件など）とは数え方が違う。IMPL-24 は、レビューの回数でなく、作業 AI の変更の回数で数える
- 悪い点: push が断られた回の対応コメントが、PR に届かなかった変更の説明として PR に残る。届かなかった回は、修正のセッションをやり直す分の利用枠を使い、往復にも数えるので、push の失敗が続くと、AI が直した回数より早く上限に当たる（止まる側）
- 悪い点: 衝突の解消も往復に数えるので、base ブランチが進んで衝突するたびに上限に近づく（止まる側）。段階 7 のモデルの比べの往復の回数にも、衝突の回数が入る
- 悪い点: 作業 AI が直す番に依存の載せ直しを後に回す分かれ道が増え、進行 Bot の単体テストの場合が増える
- 悪い点: 承認の後に、要件（IMPL-24、MERGE-6、戻す手順、印の一覧）、基本設計の 3 つの文書、図 4〜5 枚、[ADR-20261019-001][adr-repeat] の注記を直す反映の PR が要る
- 中立: 修正のセッションは、依存の相手の変更を取り込む前の head で動く。再レビューは、修正の後に載せ直した head で行う
- 中立: 人が base ブランチを取り込んだ merge の commit の後のラウンドは、往復に数えないが、修正の後で形が同じなら、同じ指摘の再発を判定する（決定 3）。形が違えば人の push の後のラウンドとして判定しないが、往復の上限は `fix` の印で効く

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 往復の回数が、有効な `fix` の印の数になること。修正、CI の赤の修正、衝突の解消、push が届かなかった回を、どれも 1 回ずつ数えること
  - 次のラウンドを往復に数えないこと：進行 Bot だけの載せ直しで差分が変わったラウンド、人の push の後のラウンド、人が base ブランチを取り込んだ merge の commit の後のラウンド。修正の後の依存の載せ直しのラウンドを、`fix` の印の分の 1 回だけに数えること
  - レビュー工程（段階 6）で載せ直しと人の修正のラウンドがある PR を修正工程（段階 7）に持ち越すと、往復が 0 回から始まり、作業 AI が直す前に `round-limit` にも `repeated-finding` にもならないこと
  - 衝突の解消で作業 AI が merge の commit の後に commit を足した例で、往復を 1 回に数え、次のラウンドで同じ指摘の再発を判定すること
  - 同じ指摘の再発を判定するラウンドとしないラウンドの組（決定 3）。比べる相手に、判定しないラウンドの `findings` も入ること
  - push が断られた修正の次の実行で、順 15 が修正をやり直すこと。push の後に切れた修正の次の実行で、順 14 の再レビューに進むこと
  - 作業 AI が直す番に依存の相手の PR がマージされても、修正の前に載せ直さないこと。修正の push の後の実行で、再レビューの前に載せ直すこと
  - 往復が上限に達した PR で載せ直しが衝突したら、作業 AI を起こさずに `round-limit` にすること
  - 人が `needs-human` を外しても往復を数え直さないこと。`round-limit` と `repeated-finding` の止めた理由のコメントに、人がすることと数え直さないことが入ること
- 基本設計のレビューで、IMPL-24、MERGE-6、要件の「止まった状態から戻す手順」、基本設計の「[状態遷移と判定][design-flow]」の「ラウンドと往復の数え方」「同じ指摘の再発の判定」「push の手順」と作業中の次の工程の表、図が、本 ADR の決定と同じことを書いていることを確かめる
- 修正工程（段階 7）の記録で、`round-limit` と `repeated-finding` で止めた件数と、止めたときの往復の回数とラウンドを見て、作業 AI が直す前に止まった PR が無いかを人が確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A1：往復を、作業 AI が変更を push した回数で数える

- 良い点: 数える元が `fix` の印だけで、往復の回数に commit の形の見分けが要らない
- 良い点: AI の変更は、修正・衝突の解消・push が届かなかった回のどれも数える側に倒れる
- 良い点: 作業 AI が 1 回も直していない PR を止めない（3 回目の再レビュー（2026-10-22）の H-8 の直しの形を保つ）
- 良い点: 改める承認済みの決定は [ADR-20261019-001][adr-repeat] の決定 2 の判定の範囲だけ。要件で直すのは IMPL-24 と MERGE-6 の 2 つの文
- 悪い点: 進行 Bot だけの載せ直しの再レビューを往復の上限で止めず、1 Issue の累計の費用の上限で止める
- 悪い点: 業界の例（レビュー済みのラウンドで数える）と数え方が違う
- 悪い点: push が断られた回の対応コメントが PR に残る。作業 AI が直す番に依存の載せ直しを後に回す分かれ道が増える

### 案 A2：今の数え方を保ち、穴を塞ぐ

1 つのラウンドは 1 回だけ数える（1 つ前のラウンドに `fix` の印があれば `fix` の印で数え、載せ直しとしては数えない）。PR の最初の有効な `fix` の印より前のラウンドは、数えも判定もしない。
衝突の解消の push は、push の手順で「1 つ目の親が PR の head、2 つ目の親が渡した base の SHA の merge の commit 1 つだけ」かを確かめ、違えば push せずに `needs-human` にする。
人が GitHub の画面で取り込んだ merge の commit は、作者で見分けて数えないか、数えすぎを認めて IMPL-24 に書く。修正の push と `fix` の印の間で切れたときは、案 A1 と同じ。段階 7 の記録は「AI が直した回数（`fix` の印の数）」と「往復の回数」を分け、[ADR-20261018-003][adr-model] に訂正の注記を足す。

- 良い点: 進行 Bot だけの載せ直しの再レビューも往復の上限で止まり、止まる側に多く倒れる
- 良い点: MERGE-6 の「往復に数える」の文と、業界の例（レビュー済みのラウンドで数える）に近い
- 悪い点: commit の形の見分けを保つ。衝突の解消で作業 AI が commit を足すと push せずに止まるので、品質ゲートで壊れた型やテストを直した衝突の解消も人に渡る
- 悪い点: 人の取り込みを作者で見分けるか、数えすぎを認めるかを、別に決める
- 悪い点: 段階 7 の記録に 2 つの数が要り、往復の回数に base ブランチの進み具合が混ざる。[ADR-20261018-003][adr-model] の言い換え（AI が直した回数（往復の回数））に訂正の注記が要る

### 案 A3：今の設計の文のまま、段階 6 の載せ直しのラウンドも数える

レビュー工程（段階 6）の載せ直しのラウンドも往復に数えると決め、基本設計の「テスト」の単体テストの期待を「人が直した後と人の push の後のラウンドだけでは止まらない」に狭め、段階 6 から 7 に替えるときに、開いた PR の往復の回数を `check` で示す。

- 良い点: 基本設計の数え方の文を直す量が少ない
- 中立: 段階 6 から 7 に替えるときに、開いた PR の往復の回数が `check` で分かる
- 悪い点: 作業 AI が 1 回も直していない PR が、段階 6 の載せ直しの分で `round-limit` になる。3 回目の再レビュー（2026-10-22）の H-8 の直しでメンテナが選んだ「AI が 1 回も直していないのに止まる形を無くす」を戻す
- 悪い点: H-1・M-4・M-5 の穴と、修正を待つ間の依存の載せ直しで直していない指摘を再発と読む形（H-2）が残り、別の直しが要る
- 悪い点: 判定の範囲を変えた 2026-10-22 の追記（M-22）は、案 A3 でも ADR で決め直す
