# レビュー工程（段階 6）の比べるためのレビューは、本番のラウンドの後の実行に別の重い工程として起こし、済んだかを手元の記録で見分け、失敗を実行の失敗に、費用を Issue の累計に数えない

要件の UNDECIDED-67（比べるためのレビューを、どの実行で起こし、済んだかを何で見分けるか）を決める。
比べるためのレビューは、レビュー工程（段階 6）で、レビュー AI を `opus` で回した同じ PR を `fable` でも回して比べるレビューで、印を書かない（IMPL-19）。

改める決定と、据え置く決定は次のとおり。

- [ADR-20261015-006][adr-flow]：決定 4 の「判定には、手元の記録を使わない」に、比べるためのレビューを起こすかを決めるときだけの例外（本 ADR の決定 2）を足す。例外は、書かずに試す間の受け入れ（[ADR-20261021-002][adr-dry]）に続く 2 つ目になる。
  決定 4 の数え上げの (a)（同じ Issue で続いた実行の失敗の回数）と (c)（Issue ごとの累計の利用枠）から、比べのセッションを除く（本 ADR の決定 3）。(b) と (d)、記録を失ったときの扱い、決定 1〜3 は据え置く。比べるためのレビューは、決定 1 の重い工程として数える
- [ADR-20261021-002][adr-dry]：書かずに試す間の受け入れの例外は据え置く
- [ADR-20261018-001][adr-usage]：途中で止めた回の費用の数え方（決定 2）と、利用枠を費用で数えること（決定 3）は据え置き、比べのセッションにも同じに掛ける

## 背景と課題（Context and Problem Statement）

- IMPL-19 と段階の表は、レビュー工程（段階 6）で、レビュー AI を `opus`（xhigh）で回した同じ PR を `fable`（`models.reviewComparison`）でも回して比べ、比べのためのレビューは印を書かない（shadow。判定に混ぜない）とする。
  レビュー工程（段階 6）の出口では、`opus` と `fable` の一致率・却下率・利用枠を並べ、既定のモデルを決める
- 基本設計の「[AI のセッション][design-ai]」は、比べるためのレビューを、本番のラウンドの `review` の印を書いた後の次の実行に、別の重い工程として、3 つの軸を同じ形で起こし、結果を手元の記録（`outputs/`）にだけ残すとする。
  見落としの軸と批評 AI は起こさない。費用は、ほかのセッションと同じく 1 日・1 回の実行・Issue の累計に数えるとする
- 基本設計の「[状態遷移と判定][design-flow]」の作業中の次の工程の表には、比べるためのレビューに進む行が無い。レビュー工程（段階 6）で `review` の印を書いた後の実行は、順 15（人の番にする）・順 16（CI を待つ）・順 17（収束）・順 18（載せ直し）・順 21（何もしない）のどれかに当たる。
  どの行の前後で起こすか、ラウンドごとか PR ごとに 1 回か、人の push で head が変わったらどのラウンドで回すかも決まっていない
- 比べるためのレビューは印を書かないので、済んだかは手元の記録でしか分からない。判定に手元の記録を使わない決まり（[ADR-20261015-006][adr-flow] の決定 4）の例外は、書かずに試す間の受け入れだけ（[ADR-20261021-002][adr-dry]）。
  記録から読めば決まりに反し、読まなければ、条件に当たる実行のたびに比べを起こし直す
- 比べのセッションの失敗を実行の失敗（IMPL-14）に数えると、印を書かない比べの失敗で、本番の Issue が `retry-limit` で止まる。Issue の累計（`limits.issueCostUsd`）に数えると、本番の流れが `usage-limit` で止まりうる。どちらも決まっていない
- 基本設計の「[設定][design-settings]」は、計画・実装工程（段階 5）からの 1 回の実行の費用の上限（`limits.runCostUsd`）を、1 つの重い工程が起こしうるセッションの数の最大（5。レビューの 1 ラウンドは 3 つの軸・見落としの軸・批評 AI）の分にしている

課題：比べるためのレビューを、どの実行で、どの条件で起こすか。済んだかを何で見分けるか。比べのセッションの失敗と費用を、本番の上限にどう数えるか。

## 判断の決め手（Decision Drivers）

- 比べるためのレビューの結果を、本番の判定（収束、マージの判定、止める条件）に混ぜないこと（IMPL-19）
- 比べのセッションの失敗と費用で、本番の Issue が止まらないこと
- 判定を GitHub の状態と印から決める決まり（FLOW-4、[ADR-20261015-006][adr-flow] の決定 4）の例外を、狭く保つこと
- 記録を失ったときに、本番の流れを誤らせる側に倒れないこと（フェイルセーフ）
- 同じラウンドの比べを、実行のたびに起こし直して利用枠を使わないこと
- 印の種類と、1 回の実行の上限の値（重い工程 1 つ分）を変えずに済むこと

## 検討した選択肢（Considered Options）

問い 1：比べるためのレビューの起こし方と、済んだかの見分け方

- 案 1-A：本番のラウンドの後の実行に、別の重い工程として起こし、済んだかを手元の記録で見る。比べのセッションの失敗は実行の失敗に数えず、費用は Issue の累計に数えない（UNDECIDED-67 の候補 (c)）
- 案 1-B：本番のラウンドと同じ重い工程の中で、続けて起こす（候補 (a)）
- 案 1-C：済んだことを、署名付きの `note` の印で PR に書く（候補 (b)）
- 案 1-D：済んだかを見分けず、条件に当たる実行のたびに起こす

問い 2：比べのセッションが失敗したとき

- 案 2-A：やり直さない。失敗で終わった比べも、済んだとして記録に残す
- 案 2-B：実行の失敗と同じ回数（`limits.retry.count`）まで、比べだけの失敗の回数を数えてやり直す

## 決定（Decision Outcome）

採用した選択肢:「案 1-A」「案 2-A」。
理由: 比べの結果を判定に混ぜず、印も増やさずに、済んだかを見分けられる。手元の記録を判定に使う範囲は、比べるためのレビューを起こすかの 1 つだけに絞られ、記録を失っても比べを回し直すだけで、本番の流れは変わらない。
比べのセッションの失敗と費用で、本番の Issue が `retry-limit` と `usage-limit` で止まらない。比べの工程は 3 つのセッションで、1 回の実行の上限の値（重い工程 1 つ分の 5 セッション）の内に収まる。失敗した比べをやり直さないので、比べだけの失敗の回数を数えずに、1 ラウンドの比べの利用枠が 1 回分で決まる。

### 決定 1：比べるためのレビューは、本番のラウンドの後の実行に、別の重い工程として起こす

- 比べるためのレビューは、レビュー工程（段階 6。`run.stage` が 6）だけで起こす。修正工程（段階 7）より後の段階では起こさない（IMPL-19）
- 起こすのは、本番のラウンドの `review` の印を書いた実行より後の実行。比べるためのレビューは重い工程で、本番のラウンドと同じ実行では起こさない（FLOW-4。Issue ごとに、1 回の実行で重い工程は 1 つ）
- 次の工程の作業中の表に、比べるためのレビューの行を 1 行足す。条件は、次のすべてを満たすこと
  - レビュー工程（段階 6）である
  - 最新の `review` の印の `head` が、PR の head と同じ（順 14 のレビューに当たらない）
  - 最新の `review` の印のラウンドで、比べるためのレビューが済んでいない（決定 2）
- 足す行は、順 14（レビュー）の後に置く。レビュー工程（段階 6）では、順 15 より後の行は軽い工程か待ちだけなので（AI は直さず、人の番にする）、比べに進んでも本番の重い工程を次の実行に回さない。
  順 15〜18 の軽い工程（人の番にする、収束、載せ直し）は、比べを起こす前に同じ実行で進め、進めた後の状態で比べの条件を確かめる（FLOW-4 の、重い工程の前後に軽い工程を続けてよい決まり）。表の中の並べ方は、基本設計で決める
- 基線が緑でなくても起こす。本番のレビューと同じく、PR の head の上の作業で、base ブランチを取り込まないため（[ADR-20261015-006][adr-flow] の決定 2）
- 比べるのは、最新の `review` の印のラウンドだけで、ラウンドごとに 1 回。比べる前に人の push で head が変わり、本番が新しいラウンドをレビューしたら、前のラウンドの比べは起こさない。
  載せ直しで差分が同じで、同じラウンドの印を新しい head に付け直したときは、起こし直さない
- 起こす形は、基本設計の今の形のまま。3 つの軸（動作・仕様・規約）を、本番のラウンドと同じ形で、`models.reviewComparison` のモデルで並べて起こし、見落としの軸と批評 AI は起こさない。
  比べの工程が起こすセッションは 3 つで、1 回の実行と 1 日の上限との比べは、工程を始める前に 3 つ分をまとめて行う
- 比べの結果は、手元の記録（`outputs/`）にだけ残し、GitHub に書かない。収束、マージの判定、同じ指摘の再発、ラウンドの数え方などの本番の判定には使わない（IMPL-19 のまま）。段階の出口の数え上げと、人が読むためにだけ使う

### 決定 2：比べるためのレビューが済んだかは、手元の記録で見分ける

- 進行 Bot は、決定 1 の行の条件を確かめるときだけ、手元の記録（`sessions.jsonl`）を読み、最新の `review` の印のラウンドの、3 つの軸の比べのセッション（セッションの名前は `review-pr-<PR の番号>-round-<ラウンド>-<軸>-compare`）に、終わりの行があるかを見る。
  [ADR-20261015-006][adr-flow] の決定 4 の、2 つ目の例外とする
- 3 つの軸のすべてに終わりの行があれば、済んだとする。終わりの行は、失敗で終わった回も含む（決定 3）
- 全体の止める合図で止めた軸と、起動の前の確かめ（止める合図、1 日と 1 回の実行の上限）で起動しなかった軸は、済んでいないとする。合図が `run` に戻った後か、上限の内に戻った後の実行で、済んでいない軸だけを起こす
- 記録を失ったとき（記録のフォルダを失った、行が読めない、人が古い実行の分を別の場所に移した）は、済んでいないとして、条件に当たれば比べを起こし直す。比べの結果は本番の判定に使わないので、本番の流れは変わらない
- 記録を失ったかの見分け（決定 4 の「記録が無いとき」。着手した Issue の記録が無ければ `records-missing` で止める、など）には、比べのセッションの記録を使わない。比べの記録だけが残っても、本番の記録を失ったことを見落とさないため。決定 4 の記録を失ったときの扱いは据え置く

### 決定 3：比べのセッションの失敗は実行の失敗に数えず、費用は Issue の累計に数えない

- 比べのセッションの失敗（時間・ターン・費用の上限、利用枠切れ（HTTP 429）、`claude` の異常終了、出力契約が解析できない、IMPL-18 の条件を満たさない）は、実行の失敗（IMPL-14）に数えない。
  同じ Issue で続いた実行の失敗の回数に足さず、`retry-limit` にしない。比べのセッションが成功しても、続いた回数を 0 に戻さない
- 失敗した比べは、やり直さない（決定 2 で済んだとする）。失敗したことと終わり方は記録に残し、レビュー工程（段階 6）の出口で、`fable` の失敗も比べの結果として読む
- 比べのセッションの費用は、1 回の実行の上限（`limits.runCostUsd`）と 1 日の上限（`limits.dailyCostUsd`）に数える。利用枠は実際に使うため
- 1 Issue の累計（`limits.issueCostUsd`）には数えない。起動の前の確かめでも、Issue の累計の確かめを比べのセッションに掛けず、比べのセッションでは `usage-limit` にしない
- 費用の数え方（正常に終わった回は `total_cost_usd`、途中で止めた回は 1 セッションの費用の上限とみなす）は、[ADR-20261018-001][adr-usage] のまま比べのセッションにも掛ける
- 安全のための止め方は、ほかのセッションと同じに掛ける。止めた後に残ったコマンドが止まったと確かめられない（`session-not-stopped`）、安全設定のファイルが書き換わった（`settings-tampered`）、起動の前の確かめで検疫・渡す文のハッシュ・worktree の設定ファイルに当たった（`quarantine`・`brief-changed`・`local-settings`）ときは、比べのセッションでも `needs-human` にする。
  比べの成否ではなく、作業場所と入力の安全にかかわる見つかり方なので、比べのセッションだからと見逃さない

### 影響（Consequences）

- 良い点: 比べの結果を本番の判定に混ぜず、印も増やさずに、同じラウンドの比べを 1 回だけ起こせる
- 良い点: 比べのセッションの失敗と費用で、本番の Issue が `retry-limit` と `usage-limit` で止まらない
- 良い点: 記録を失っても、比べを回し直すだけで、本番の流れは変わらない。比べの記録だけが残っても、本番の記録を失ったことを見落とさない
- 良い点: 比べの工程は 3 つのセッションで、1 回の実行の上限（重い工程 1 つ分）の値を変えずに済む
- 悪い点: 手元の記録を判定に使う例外が、2 つ（書かずに試す間の受け入れと、比べるためのレビューを起こすか）になる
- 悪い点: 比べの分だけ、レビュー工程（段階 6）の 1 回の実行と 1 日の利用枠を使う。同じ実行のほかの Issue の工程（受け入れなど）が、上限で次の実行に回りうる
- 悪い点: 失敗した比べと、比べる前に head が変わったラウンドは、比べの結果が欠ける。レビュー工程（段階 6）の出口に要る件数がそろうのが遅れうる
- 悪い点: 記録を失うと、同じラウンドの比べを 2 回起こしうる（利用枠を 2 回使う）
- 中立: 安全のための止め方は比べのセッションにも掛けるので、比べのセッションでの見つかり方で、本番の Issue が `needs-human` になることはある
- 中立: 比べの費用は Issue の累計に入らないので、Issue ごとに使った費用を見るときは、比べのセッションの費用を足して読む

### 確認方法（Confirmation）

- 進行 Bot の単体テストで、次を検査する
  - 比べの行の条件（レビュー工程（段階 6）であること、最新の `review` の印の `head` と PR の head、記録の終わりの行）と、修正工程（段階 7）以降では起こさないこと
  - 3 つの軸のすべてに終わりの行があれば済んだとし、全体の止める合図で止めた軸と起動しなかった軸は済んでいないとして、済んでいない軸だけを起こすこと
  - 記録が無ければ比べを起こし直し、本番の判定（次の工程、収束、マージの判定）が変わらないこと。比べの記録だけがあっても、記録を失ったことを見落とさないこと
  - 比べのセッションの失敗を実行の失敗の回数に足さず、成功しても回数を 0 に戻さないこと。費用を 1 回の実行と 1 日の累計に入れ、Issue の累計に入れないこと
  - 載せ直しで同じラウンドの印を付け直したときに、比べを起こし直さないこと
- 結合テスト（偽の `gh` と偽の `claude`）で、次を確かめる
  - レビュー工程（段階 6）で、本番のラウンドの後の実行が比べを起こし、次の実行は比べを起こさないこと
  - 偽の `claude` で比べのセッションを失敗させても、Issue が `retry-limit` にならず、本番の流れを続けること

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 1-A：本番のラウンドの後の実行に別の重い工程として起こし、済んだかを手元の記録で見る

- 良い点: 印を増やさず、IMPL-19 の「印を書かない」のまま
- 良い点: 1 回の実行の上限の値を変えずに済む
- 悪い点: 手元の記録を判定に使う例外が増える
- 悪い点: 本番のラウンドと別の実行になるので、比べる前に head が変わると、ラウンドの比べが欠ける

### 案 1-B：本番のラウンドと同じ重い工程の中で続けて起こす

- 良い点: 済んだかの見分けが要らず、手元の記録の例外も要らない
- 良い点: 本番のラウンドと同じ head を、同じ実行の中で必ず比べる
- 悪い点: 1 ラウンドのセッションが 5 から 8 になり、レビュー工程（段階 6）の 1 回の実行の上限と、費用の上限の値の関係（1 つの重い工程が起こしうるセッションの数の最大）を直す
- 悪い点: 1 ラウンドの所要時間の最大が、3 つの軸・見落としの軸・批評 AI の 135 分に比べの 45 分を足した 180 分になり、1 回の実行の所要時間の上限（`run.maxMinutes` の初期値 180 分）に並ぶ
- 悪い点: 比べのセッションの失敗を、本番のラウンドの失敗と分けて扱う決まりが別に要る

### 案 1-C：済んだことを note の印で PR に書く

- 良い点: 済んだかを GitHub の印から決められ、手元の記録の例外が要らない
- 悪い点: IMPL-19 の「印を書かない」に反し、要件の印の一覧と `note` の種類を直す
- 悪い点: 比べのたびに PR へ書き込み、人が読む PR のコメントが増える

### 案 1-D：済んだかを見分けない

- 良い点: 仕組みが最も少ない
- 悪い点: 条件に当たる実行のたびに、同じラウンドの比べを起こし直し、利用枠を使い続ける

### 案 2-A：失敗した比べをやり直さない

- 良い点: 比べだけの失敗の回数を数えずに済み、1 ラウンドの比べの利用枠が 1 回分で決まる
- 良い点: `fable` の失敗も、比べの結果として記録に残る
- 悪い点: 利用枠切れのような一時の失敗でも、ラウンドの比べが欠ける

### 案 2-B：比べだけの失敗の回数を数えてやり直す

- 良い点: 一時の失敗で比べが欠けにくい
- 悪い点: 比べだけの失敗の回数を、手元の記録で別に数える。判定に使う手元の記録が増える
- 悪い点: 失敗が続くと、1 ラウンドで比べの利用枠を最大 3 回分使う
