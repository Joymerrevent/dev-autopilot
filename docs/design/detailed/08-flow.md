# 1 回の実行の流れ

進行 Bot の 1 回の実行（順 1〜10）、GitHub の事実の読み方、状態の組み立て、次の工程、工程、push の手順、判定、全体の停止と通知の処理の作りと、人が呼ぶ `/dev-autopilot` の処理を決める。
順・状態・工程・判定・印・止めた理由の正本は、基本設計の「[状態遷移と判定][b02]」にある。本書は、正本の表を並べ直さず、ファイルの分け方、1 回の実行の中で持つ値、終わり方と終了コード、GitHub の事実を読む形、状態と工程の記号、作業の単位の見直しの止め方、GitHub に書くときの決まり、実行の失敗の数え方、実装の都合で止める理由の記号の扱いを決める。

- 「基本設計」の欄の節は、ことわりの無いものは「[状態遷移と判定][b02]」の節
- 工程のファイルは、状態の組み立ても次の工程の選び方も持たない。`logic/state/next.ts` が選んだ工程を行い、結果（下の「工程の結果」）を返すだけにする。工程を選ぶ規則を 1 か所に置き、単体テストで表の行ごとに確かめるため
- 判断の層のファイルは、時刻を引数で受ける。ラベルの付き外しと印の新しさを比べる判定が多く、組み合わせごとに単体テストで確かめるため
- 運用の記録の数え方（「[状態遷移と判定][b02]」の「運用の記録の数え方」）を数える処理は、今は作らない。今の入口（`main.ts`・`setup`・`check`・`/dev-autopilot`・intake）のどれも数えた値を使わないため。数えるための欄は記録に別に持たない決まりなので、数える入口を足すときに、記録と GitHub から数える処理を足す。数えた値を使うのは、[FLOW-12][flow] の連続 7 回の実行の条件を見るときと、ほかのリポに広げる時期を決めるとき（[ADR-20261028-003][adr-expand]）なので、どちらかを見るより前に、数える入口と処理を本書に足す

## 1 回の実行の中で持つ値

`flow/run/run.ts` は、実行の最初に、実行の間の値（`RunContext`）を 1 つ作り、流れの層の処理に引数で渡す。

| 値 | 中身 | 使う所 |
| --- | --- | --- |
| 実行 ID と起こされ方 | `logic/run/ids.ts`（「[設定と記録][d02]」）と `logic/run/wake.ts` で決める | 記録、`status.json` |
| 設定 | 凍らせたマシンの設定とリポの設定と、リポの設定を読んだ base ブランチの SHA（「[設定と記録][d02]」の「設定を読む順」） | すべて |
| 期限 | 実行を始めた時刻に `run.maxMinutes` を足した時刻 | 順 9 |
| 費用の帳簿 | 今日の累計・今の実行の累計・作業の単位ごとの累計と、取り置き（枠ごと）。型と入れ替える関数は `logic/session/budget.ts`（「[AI のセッション][d07]」の「費用の取り置き」） | AI のセッション |
| 合図 | 最後に読んだ全体の止める合図（`run`・ほかの値・読めない・読んでいない。順 3 の前は「読んでいない」で、`run` でないものと扱う）と、全体の停止の Issue の有無（ある・無い・読んでいない。判定に使う止める間の値で、GitHub の全体の停止の Issue のほか、見つかりの記録が「ある」か「読めない」とき、下の「全体の停止と通知」の開き直しの条件に当たる作業の単位があるとき、その実行で `where` が `text` で見つけたときも「ある」）と、GitHub で読んだ全体の停止の Issue の有無（ある・無い・読めない・読んでいない。順 4 と読み直しで GitHub から読んだ最後の値（一覧を読めなければ「読めない」）と、その実行で全体の停止の Issue に `halt` の印を書けたこと（「ある」）だけで決める。「ある」になったら、その実行の中では入れ替えない。見つかりの記録と、開き直しの条件を読むこと（作業の単位の Issue の印）は、この値を変えない）と、読んだ `halt` の印（`issue` と時刻。その実行で書けた `halt` の印も足す）と、開き直しの条件に当たった作業の単位の番号（その実行で `logic/state/halt.ts` が返したもの）と、順 2 で読んだ見つかりの記録（読んだ結果（ある・無い・読めない）、読めた記録の並び、読めないファイルの名前と、名前から読めた作業の単位の Issue の番号。記録の形は「[設定と記録][d02]」の「見つかりの記録」）。どれも読んだ時刻を添える | 書き込み、重い工程、AI のセッションの起動の前の確かめ（どの役も）、点検（順 5・10）、受け入れの依頼の受付 AI、見つかりの記録からの書き直し（`flow/run/units.ts`）、`status.json`（全体の停止の Issue の有無と、GitHub で読んだ全体の停止の Issue の有無と、開き直しの条件に当たった作業の単位の番号。見つかりの記録は、順 10 で読み直した値を書く） |

| 見つかりの記録を書き直した結果 | 記録のファイルの名前ごとの、結果（消した・残した・消せなかった）と、残したときの何をと理由、消せなかったときの失敗の種類（値の形は「[設定と記録][d02]」の `runs.jsonl` の「見つかりの記録を書き直した結果」）。足すのは `flow/safety/suspect.ts`（書き直す関数と、見つけた実行で記録を消せなかったとき。下の「全体の停止と通知」） | 順 10 の `runs.jsonl`、順 10 の点検（今の実行で書き直せなかった記録も数える）、思わない失敗の後始末の `runs.jsonl` |
| 実行を終える理由 | 実行を途中で終える理由の記号（`stop-signal`・`signal-unreadable`・`machine-unsafe`）。無ければ空 | `flow/run/units.ts`（残りの作業の単位を進めない）、終わり方 |
| 漏えいの検査に渡す値 | マシンのパスの並び（書いたままの形、実体の形、実体が `/private/` で始まるときは頭の `/private` を除いた形。実体に解くのは `io/files.ts`）と、短い一時フォルダの ID の並び（`sessions.jsonl` の一時フォルダの行の ID と、今の実行で決めた ID）。実行の最初に作り、セッションの順 2（一時フォルダの確かめ）で ID を決めるたびに足す | 漏えいの検査（「[文の検査と受け入れ][d06]」の「漏えいの検査」） |

- 値は 1 つの進行 Bot のプロセスの中にだけ持つ。実行の lock で、同じマシンで同じリポの実行は 1 つだけなので、ファイルで守る要は無い（「[AI のセッション][d07]」の「費用の取り置き」と同じ）
- 合図の値は、読み直すたびに入れ替える。全体の停止の Issue の値は、「ある」になったら、その実行の中では「無い」に戻さない（読み直して全体の停止の Issue が見つからなくても）。開けなかった全体の停止の Issue（下の「全体の停止と通知」）を、同じ実行の読み直しで解かないため。人が実行の途中で解いた全体の停止は、次の実行から効く。順 2 で見つかりの記録を読んで「ある」にしたときも同じ（[ADR-20261111-001][adr-halt-records] の決定 1）
- AI の文の検疫で見つけたとき（`where` が `text` の `security` の印を書く前。書けなかったときも）と、全体の停止の Issue を開いたときは、読み直さずに全体の停止の Issue を「ある」に入れ替え、その後の AI のセッションを起こさない（「[状態遷移と判定][b02]」の「全体の停止の Issue」）
- 時刻・待ち・乱数（`FlowSystem`。[README][readme] の「層と依存の向き」）は、外との境と並べて引数で渡し、`RunContext` には入れない

## 起こされ方と進む順

![1 回の実行の順と受け持つファイル][fig-run]

`logic/run/wake.ts` は、lock を取った後に読んだ 3 つの依頼のファイル（形が違うものは無いものとする。「[設定と記録][d02]」の「依頼と結果のファイル」）と今の時刻から、起こされ方と、依頼のファイルごとの扱い（残す・消す・見送って消す）を返す。決め方は「[導入と点検][b04]」の「見送った実行と、起動しなかった定期の実行」のとおり。起こされ方は、定期を `scheduled`、手動を `manual`、点検の依頼を `check-request`、受け入れの依頼を `intake-request` の記号で、`runs.jsonl` と `status.json` に書く。`flow/run/run.ts` は、起こされ方で、次の順に進む。

| 順 | 受け持つファイル | 定期・手動 | 点検の依頼（待つ時間の内） | 受け入れの依頼（待つ時間の内） |
| --- | --- | --- | --- | --- |
| 1 | `flow/run/settings.ts`（マシンの設定） | 行う | 行う | 行う |
| 2 | `flow/run/lock.ts`、`flow/run/records.ts`（記録の切れた行と、見つかりの記録のファイル）、`flow/safety/signal.ts`（見つかりの記録）、`logic/run/wake.ts`、`flow/run/requests.ts`（手動の 1 回実行の依頼と、待つ時間を過ぎた受け入れの依頼を消す）、`flow/session/leftovers.ts` | 行う | 行う | 行う |
| 3 | `flow/safety/signal.ts`（全体の止める合図） | 行う | 行う | 行う |
| 4 | `flow/run/clone.ts`、`flow/run/settings.ts`（リポの設定）、`flow/safety/signal.ts`（全体の停止の Issue） | 行う | 行う | 行う |
| 5 | `check.ts`（「[点検][d04]」） | 行う | 行い、結果を書いて依頼を消す（`flow/run/requests.ts`） | 行う |
| 6・7 | `flow/run/gather.ts`、`logic/state/assemble.ts` | 行う | 行わない | 行わない |
| 8・9 | `flow/run/units.ts` | 行う | 行わない | 全体の停止の Issue が無ければ、受付 AI を 1 つ起こす（`flow/run/intake.ts`）。あれば起こさず、理由（`halt-issue`）を受け入れの依頼の結果のファイルに書く |
| 10 | `flow/run/requests.ts`、`flow/run/records.ts`、`flow/run/status.ts`、`flow/run/lock.ts` | 行う | 記録・`status.json`（入れ替える欄だけ）・lock（点検の結果は順 5 で書いた） | 受け入れの結果・記録・`status.json`（入れ替える欄だけ）・lock |

- 待つ時間を過ぎた点検の依頼は、順 5 の結果を書いて依頼のファイルを消してから、定期の実行として順 6 へ進む。待つ時間を過ぎた受け入れの依頼は、受付 AI を起こさずに消し、消したことを記録に残す。その実行は、起こされ方を定期（`scheduled`）として、順 3〜10 を定期の実行と同じに行う（「[導入と点検][b04]」の「見送った実行と、起動しなかった定期の実行」）
- 順 2 で、`flow/run/requests.ts` は、`logic/run/wake.ts` が返した扱いのとおりに、手動の 1 回実行の依頼と、待つ時間を過ぎた受け入れの依頼を、起こされ方を決めた直後に消す（読んだ依頼と ID が同じときだけ）。手動の 1 回実行の依頼を読んだ直後に消すのは、実行が途中で落ちても、残った依頼を次の定期の実行が読んで「手動」と記録しないため（「[導入と点検][b04]」の「見送った実行と、起動しなかった定期の実行」の「`run-request.json` は読んだら消し」）
- 順 3 で合図が `run` でないか読めないとき、順 4 でリポの設定を読めないときは、点検の依頼（待つ時間の内も過ぎたものも）があれば、順 4（順 3 で止まったとき）と順 5 を行ってから順 10 へ進む。順 4 でリポの設定を読めないときは、読めないことを fail として順 5 の結果に書く（「[設定と記録][d02]」の「設定を読む順」）。合図が `run` でない間は、試しのセッションと書き込みの権限の試しを行わず、未確認の warn にする（「[点検][d04]」の「組の順と前提」）。点検の依頼が無ければ、止まった順から順 10 へ進む（「[状態遷移と判定][b02]」の「1 回の実行の流れ」の順 3・4）
- 順 2 で記録の切れた行に当たったとき（下の箇条）と、順 3〜5 で止まるときも、順 10 を行う。点検の依頼の結果は、待つ時間の内も過ぎたものも、順 5 で書いて依頼のファイルを消す（読んだ依頼と ID が同じときだけ。「[導入と点検][b04]」の「点検だけで動かす仕組み」の順 4）。順 10 は、点検の依頼のファイルを読み直し、順 2 で読んだ依頼と ID が違う依頼（実行の途中で人が `check` を呼んだもの）があるときだけ、合図と全体の停止の Issue を読み直して順 5 だけを行い、結果を書いて依頼を消す。ID が同じ依頼が残っていれば（順 5 で消せなかった）、点検し直さずに消し直す（「[状態遷移と判定][b02]」の「1 回の実行の流れ」の順 10）
- 順 1 の前に、`io/os.ts` が動かさない OS を返したら、マシンの設定を読まずに止める（`unsupported-os`。下の「終わり方と終了コード」）
- 順 2 で lock を取った直後に、`flow/run/records.ts` が `runs.jsonl` と `sessions.jsonl` が改行で終わっているかを読む。切れた行があれば、前の実行が残したセッションを止める手順だけを行い（終わりの行は書かない）、作業に入らずに順 10 へ進む（点検の依頼があれば、記録の項目を fail として結果を書き、受け入れの依頼があれば、受付 AI を起こさずに理由 `records-cut` を結果のファイルに書き、lock を外す）。見つかりの記録は、順 2 では読まず（AI のセッションも GitHub への書き込みも無いため）、順 10 で `status.json` を書く前に読み直す。終わり方は `records-cut`（「[設定と記録][d02]」の「手元の記録」）
- 順 4 で、`flow/run/clone.ts` は次の順に行う。(1) `<置き場>/known_hosts` が無ければ、`io/github.ts` の読み取りで `GET /meta` を呼び（インストールのトークン）、返った SSH のホストの鍵から、`io/files.ts` の「排他の作成」で書く（書いている途中で切れた `known_hosts` を、あるものとして書き直さずに使い続けないため）。あれば書き直さない。(2) `<置き場>/controller/` が無ければ、origin（マシンの設定の `repository.*` から作る SSH の URL）から、deploy key の `GIT_SSH_COMMAND` で clone する。途中で止まった clone を、できた clone と読まないため、一時の名前（`controller.new-<実行 ID>`）に clone してから rename で `controller/` にする。前の実行の一時の名前のフォルダが残っていれば、消してから作る（lock を持つ実行の中なので、ほかに使う者はいない）。(3) fetch する。(1)〜(3) のどれかが失敗したら、リポの設定を読めないとして止まる（`settings-unreadable`）。外れた所（`known-hosts`・`clone`・`fetch`・`read`（リポの設定のファイルを読めないか形が違う））と失敗の種類（HTTP の状態か、`git` の終了コード。標準エラーの中身は書かない）を `runs.jsonl` の行に書き（「[設定と記録][d02]」の「手元の記録」）、点検の依頼があれば、読めないことを書く fail の `details` にも入れる。人が、deploy key と `known_hosts` と GitHub へのつながりのどれを直すかを見分けるため
- 順 2 で lock を取った後に、`flow/safety/signal.ts` が `flow/run/records.ts` で見つかりの記録（記録の置き場の `security-pending/`）を読み、「ある」か「読めない」なら `RunContext` の全体の停止の Issue を「ある」にする（下の「全体の停止と通知」の「見つかりの記録を読む」の行）。どの起こされ方の実行も読む。順 5 の試しのセッションと受け入れの依頼の受付 AI より前に読むため
- 全体の停止の Issue は、見分けに `safety.botAccounts`（リポの設定）を使うので、順 4 でリポの設定を読んだ直後に読む。順 4 より前に、AI のセッションを起こす処理も GitHub に書く処理も無いので、[ADR-20261024-005][adr-security] の決定 3 の「実行の最初に読む」を満たす。順 4 で止まった実行は、全体の停止の Issue を読まない（作業に入らない）
- 順 5 の `check.ts` には、`RunContext` の合図（全体の止める合図の値と、全体の停止の Issue の有無）と、前の実行が残したセッションの片付けの結果を渡す。順 10 で点検だけを行い直すときは、順 2 の片付けの結果に、今の実行で `not-stopped` で返り、終わりの行の無いセッション（`RunContext` の動いているセッションにあるもの。順 5 の試しのセッション、順 8・9 の受付 AI と作業の単位のセッション）を、止められなかったセッションとして足して渡す（順 2 は 1 回の実行で 1 回だけ行う。同じ実行で残りが動いているのに、マシンの組を pass にして試しのセッションをもう 1 つ起こさないため）。順 10 では、同じ実行の順 5 の sandbox の組の結果と、`RunContext` の見つかりの記録を書き直した結果も渡す（今の実行の `runs.jsonl` の行はまだ書いていないので、試しを省く判定が最後に行った点検の結果として読み、`machine.security-pending` が今の実行で書き直せなかった記録も数える。「[点検][d04]」の「試しのセッションを省く判定」と「ファイルの一覧」の表の下）
- 順 10 で、`flow/run/status.ts` が `status.json` を書く前に、`flow/run/records.ts` の読む関数で見つかりの記録を読み直し、その値を「全体」の欄の見つかりの記録に書く（どの起こされ方の実行も）。点検の欄の `machine.security-pending` の項目も、読み直した値と `RunContext` の見つかりの記録を書き直した結果から、`flow/check/machine.ts` の項目を決める関数で決め直して入れ替える。見つけた実行で残った記録も、書き直して消した記録も、実行の終わりの表示に合わせるため。点検だけの実行と受け入れの依頼の実行は、点検の欄と「全体」の欄を、その実行の値で入れ替え（基線の欄は入れ替えない）、入れ替えた実行の ID と時刻を添える（「[設定と記録][d02]」の「status.json」）
- 受け入れの依頼の実行は、`RunContext` の全体の停止の Issue が「ある」（読めなかったときを含む）なら、受付 AI を起こさない（「[状態遷移と判定][b02]」の「1 回の実行の流れ」の表の下、[ADR-20261024-005][adr-security] の決定 3）
- 順 2〜4 の子プロセスと GitHub の呼び出し（順 4 の `known_hosts` と clone を含む）の時間の上限は、リポの設定を読むまで、プログラムに固定した 10 分と 10 秒を使う（「[設定と記録][d02]」の「プログラムに固定する値」）
- 起動しなかった定期の実行は、順 4 でリポの設定を読んだ後に、`logic/run/missed.ts` が `runs.jsonl` の行と、定期の実行の時刻（「[導入と点検][b04]」の「時刻」。間隔の `run.intervalHours` はリポの設定にある）と、今の時刻から決め、順 10 で記録に書く。順 4 より前に止まった実行は決めず、`runs.jsonl` の起動しなかった定期の実行の時刻の欄を書かない（決めて 1 つも無かったときの空の並びと分ける）。次に決める実行は、欄を書いた最後の実行の起動の時刻から今までの時刻を並べて決める。決めなかった実行の間の分を落とさないため

## 終わり方と終了コード

`runs.jsonl` の終わり方（「[状態遷移と判定][b02]」の「手元の記録」）を、次の記号で書く（`runs.jsonl` に書かないと添えた 2 つは、終了コードと標準エラーにだけ出る）。終わり方の記号と終了コードの対応は、`runs.jsonl` の行の形と一緒に `logic/run/records.ts`（「[設定と記録][d02]」の「手元の記録」）に置き、`main.ts` は、`flow/run/run.ts` が返した終わり方から、対応の終了コードで終える。

| 終わり方 | 記号 | 終了コード |
| --- | --- | --- |
| 作業した | `worked` | 0 |
| 点検だけ | `check-only` | 0 |
| 受け入れの依頼だけ | `intake-only` | 0 |
| 合図で止めた | `stop-signal` | 0 |
| lock で見送った（持ち主が動いている lock） | `lock-skipped` | 0 |
| lock を見分けられずに見送った | `lock-unknown` | 1 |
| 動かさない OS で止めた（`runs.jsonl` に書かない） | `unsupported-os` | 1 |
| マシンの設定を読めずに止めた（順 1。`runs.jsonl` に書かない） | `machine-settings-unreadable` | 1 |
| 記録の切れた行で止めた（順 2。記録の最後の行が切れている） | `records-cut` | 1 |
| 合図を読めずに止めた（順 3 か、実行の途中の読み直し） | `signal-unreadable` | 1 |
| 設定を読めずに止めた（順 4） | `settings-unreadable` | 1 |
| 点検の fail で止めた | `check-failed` | 1 |
| GitHub を読めずに止めた（順 7） | `github-unreadable` | 1 |
| マシンの中のフォルダの異常で止めた（起動の前の確かめの順 5・6、順 9 の上のフォルダ。見つかりの記録を記録の置き場に書けないときと、消せないときを含む） | `machine-unsafe` | 1 |
| 思わない失敗があった | `crashed` | 1 |

- `flow/run/run.ts` は、終わり方と一緒に、標準エラー（定期の実行の `launchd.err.log`）に書く行の並びを返す。返すのは、`unsupported-os`（OS の名前）と `machine-settings-unreadable`（読めなかったパスと理由の種類。ファイルの中身は書かない）のとき、`lock-unknown` のとき（`run.lock` のパスと見分けられなかった理由の種類。「[設定と記録][d02]」の「lock」）、`runs.jsonl` に切れた行があって足せないとき（`records-cut` と lock で見送った実行。ファイルのパスと、断片の位置と長さ。「[設定と記録][d02]」の「手元の記録」）。`main.ts` は、返った行を標準エラーに書いてから、終わり方の終了コードで終える。動かさない OS では OS ごとの部分を使えず、順 1 でマシンの設定を読めないときは記録の置き場が分からず、読めない lock と切れた行は人が戻すまで続くため
- 写しの `node_modules` が欠けて `main.ts` が起動で止まったときは、Node が標準エラー（`launchd.err.log`）に書いて、終了コード 1 で終わる。`main.ts` は依存の照らしを持たない（写しはハッシュで確かめてある。「[導入と点検][b04]」の「依存」）
- 終了コードを 0 と 1 に分けるのは、人が `launchd.err.log` と定期の実行の登録から、手当てが要る終わり方かを見分けるため。合図で止めたときと、持ち主が動いている lock で見送ったとき（`lock-skipped`）は、決まりどおりの終わり方なので 0 にする。lock を見分けられずに見送ったとき（`lock-unknown`）は、人が壊れた lock を戻すまで続くので 1 にする（「[設定と記録][d02]」の「lock」）。合図を読めないときは、秘密鍵の取り違え、App のインストールの外れ、つながらないなど、人の手当てが要るので 1 にする
- 終わり方が 2 つ以上に当たるときは、終了コード 1 のものを先にし、1 どうしは先に起きたものにする。0 どうし（`stop-signal` と、`worked`・`check-only`・`intake-only`）は `stop-signal` を先にする。下の「作業の単位の進め方」の表の下で、実行を終える理由があれば終わり方をその理由の記号にするのと同じく、合図で止めたことを記録で見分けるため。待つ時間の内の点検の依頼の実行は、点検に fail があっても `check-failed` にせず `check-only` にする（fail は結果のファイルで人に示す）
- 思わない失敗（`crashed`）は、例外で止まったときも、記録と lock を残したままにしないための終わり方（「[状態遷移と判定][b02]」の「手元の記録」の `runs.jsonl` の終わり方の「思わない失敗があった」）
  - 作業の単位を進める間（順 8 の作業の単位ごとの見直し。組 2 の後のマージの判定を含む）の思わない失敗は、`flow/run/units.ts` が作業の単位ごとに受ける。その作業の単位の動いているセッションを止める手順で止め、作業の単位の結果を `failed`（思わない失敗。例外の種類と工程の記号を添え、例外の文は書かない）として `RunContext` に書き、次の作業の単位へ進む。`logic/run/failures.ts` は、この `failed` も実行の失敗に数えるので、同じ例外が続けば `limits.retry.count` 回目で（同じ実行で）停止中（`retry-limit`）になる。実行の終わり方は、上の先後で `crashed` にする（作業の単位を進めても、人が終了コードで気づくため）
  - 上の箇条のほかの思わない失敗（順 1〜10 のすべて。受け入れの依頼の実行の受付 AI（順 8・9）、組 1 の前の停止中と開き直し、表示の欄の書き込みを含む）は、`flow/run/run.ts` が例外を受け、動いているセッションを止める手順（「[AI のセッション][d07]」の「止める相手と前の実行の残り」）で止め、次の順で後始末をする。(1) 依頼で起こされた実行（待つ時間の内の点検の依頼か受け入れの依頼）で、まだ結果を書いていなければ、結果のファイルを書いてから依頼を消す（読んだ依頼と ID が同じときだけ）。点検の結果は、まだ結果の無い項目をすべて `fail`（`unchecked`）にして書く（「[点検][d04]」の、組の処理が思わない失敗で止まったときと同じ関数）。受け入れの結果は、受付 AI の文の欄を書かず、受付 AI を起動する前なら `outcome` を `not-run`、起動した後なら、止める手順で止められれば `no-draft` にし、どちらも理由を `crashed` にする。止められなければ `not-stopped` と残ったプロセスを書く（「[文の検査と受け入れ][d06]」の「受け入れの結果のファイル」）。結果のファイルを書けなければ、依頼を消さない（次の実行が、待つ時間で扱いを決める）。(2) `runs.jsonl` の行（`RunContext` の見つかりの記録を書き直した結果を含む）と `status.json`（見つかりの記録は順 10 と同じく読み直す）を書き、lock を外す
  - 止められなかったセッションは終わりの行を書かず、次の実行が「前の実行が残したセッション」で探す。後始末の途中でも例外が出たら、そこで終了コード 1 で終える（lock は、PID のプロセスが無いので、次の実行が古い lock として奪う。「[設定と記録][d02]」の「lock」）

## GitHub の事実の読み方

`flow/run/gather.ts` は、順 6 で基線の必須チェックを、順 7 で作業の単位ごとの事実（`logic/state/facts.ts` の型）を読む。読むものと使い方は「[状態遷移と判定][b02]」の「状態の組み立て」の表のとおりで、本節は読む形を決める。

| 別のリポに移されたか、消された Issue を探す、当てる先のリポの開いている PR | GraphQL の操作 `OpenPullRequests` と、印の Issue の REST（`io/github.ts` の `readIssueWithoutRedirect` で、`GET /repos/{owner}/{repo}/issues/{issue_number}` をリダイレクトをたどらずに引いた状態）と、当てる先のリポの REST の `GET /repos/{owner}/{repo}`（`id` と `has_issues`）。見分け方は「[状態遷移と判定][b02]」の「状態の組み立て」の箇条（FACT-66・FACT-134・FACT-145〜148） |

- GraphQL の一覧（Project の項目、コメント、timeline、PR、依存の相手、編集の記録など、`first` と `endCursor` で読むものすべて）は、100 件ずつのページで読み、続きは同じ名前の操作に、前のページの終わりの位置（`endCursor`）を渡して読む。途中のページで失敗したら、読めたページだけで判断しない（「[外との境][d01]」の「GitHub の呼び方」）
- 1 つの作業の単位でも読めなければ、読めた作業の単位だけで進めず、順 7 の「API が失敗したら、作業を増やさずに記録して止まる」に当てる（終わり方は `github-unreadable`。読めなかった作業の単位の Issue と PR の番号（依存の相手の番号を読めなかったときは、相手の番号も）を、`runs.jsonl` と `status.json` の「実行」の欄に書く。「[設定と記録][d02]」の「手元の記録」と「status.json」）。読めない作業の単位を飛ばして進めると、着手の件数や進行中の作業の単位の数を少なく数えるため
- コメントの ID は、GraphQL の `fullDatabaseId`（文字列）を数にして持つ。REST の `id` と同じ値で、印の欄のコメントの ID（「[印][d03]」の「欄の値の形」）と突き合わせられる（[FACT-125][facts]）。`databaseId` は、GraphQL の Int の範囲を超える値を返すので使わない。数にした値が `Number.isSafeInteger` に収まらなければ、読めなかったものとする
- 投稿者とラベルの出来事の人の名前は、REST の `login` の形にそろえて持つ。GraphQL の `__typename` が `Bot` なら、`login` の後ろに `[bot]` を足す（GitHub App の名前は、REST では `<アプリの名前>[bot]`、GraphQL では `[bot]` が無い。コメントの投稿者と、timeline のラベルと閉じた出来事の `actor` で同じ形だった。試し用 App で確かめた。[FACT-126・139][facts]）。`safety.botAccounts` は REST の形で書くので、そろえないと、進行 Bot の印を人のコメントと読み誤る。投稿者が無い（アカウントが消された）ときは、権限の無い人として読む。`setup` が作る進行 Bot の App で同じ形になるかだけを、段階 3（導入と点検の実装）の一度だけの試しで確かめる（「[導入と点検][b04]」の「GitHub App の権限」）
- 未編集かは、GraphQL の `lastEditedAt` が無いことで読む（[FACT-16][facts]）。人の見出しの最後に編集した人は、コメントの編集の記録（`userContentEdits`）の項目のうち、`editedAt` の最も新しいものの `editor` で読み、名前を上と同じにそろえる（「[状態遷移と判定][b02]」の「状態の組み立て」。並びの順に頼らず、`editedAt` で選ぶ）。`lastEditedAt` があるのに編集の記録が空か読めないときと、`editor` が無い（アカウントが消された）ときは、最後に編集した人を権限の無い人として読む（止める側）。コメントの `editor` の欄は使わない。編集の記録の最新の項目の `editor` が最後に編集した人になることは、確かめた（2 つのアカウントで続けて編集すると、`editedAt` の最も新しい項目の `editor` が最後に編集したアカウントだった。並びは新しい順で、`last: 1` は書いた版を返すので、並びの順に頼らない。[FACT-142][facts]）
- 人の権限は、事実を読むときに 1 人ずつ引く。1 回の実行の中では同じ人を 1 回だけ引いて同じ実行の組み立てにだけ使い、実行をまたいで持たない。コラボレータの一覧は取らない（[TEXT-10][text]）。進行 Bot のアカウントの出来事（進行 Bot が外したラベル）は、権限を引かずに、行ったものとして読む
- push 以上と maintain 以上は、`user.permissions` の真偽で見分ける。`admin` か `maintain` が `true` なら maintain 以上、それに当たらず `push` が `true` なら push 以上とし、どれでもないか、欄が無いか、真偽でなければ、権限の無い人として読む（止める側）。`permission` の欄は maintain を `write` に寄せうるので、`role_name` の欄は独自の役の名前を返しうるので使わない。maintain・push・triage の人の応答の値は、段階 3（導入と点検の実装）の一度だけの試し（「[導入と点検][b04]」の「GitHub App の権限」）で確かめる（[FACT-132][facts] は admin の人だけで確かめた）
- コメントの印は、`logic/marker/read.ts` に通した結果（有効・無効・読まない（人のコメント）・読まない（印の無い進行 Bot のコメント。人の投稿として読む）。「[印][d03]」の「読み方」）を事実に入れる。印の中身の意味（数えるか、止める契機か）は、`logic/state/discount.ts` が決める
- `logic/marker/read.ts` が「読まない（人の投稿として読む）」と返したコメントは、投稿者が `safety.botAccounts` のどれかでも、人のコメントとして見出しを読み、権限はほかの人と同じに引く（[ADR-20261015-004][adr-markers] の決定 1）
- `## 仕組みの変更の承認` に挙がったパスは、`logic/settings/paths.ts` の形の確かめに通し、形に外れたパスは認めなかったものとして事実に入れる（止める側。「[設定と記録][d02]」の「パスの照らし」）
- 依存の相手のリポと番号は、`runs.jsonl` の作業の単位の結果（待たせた理由）に書く。`wait` の印の `blockedBy` は番号だけなので、別のリポの相手を人が見分けるため。依存は別のリポの Issue を指せる（[FACT-143][facts]）。相手を別のリポに移すと、移した先を読めるトークンでは、一覧は移した先を指して残る（[FACT-144][facts]）ので、移した先が当てる先のリポの外なら、上の表の依存の相手の行のとおり未完了とする。進行 Bot のトークン（当てる先のリポだけ）では、App から見えないリポへ移した相手は一覧から消え、上の表の依存の相手の行の数の比べ（一覧の件数が `totalBlockedBy` より少ない）で未完了とする（[FACT-143・150][facts]）。相手を消すと、一覧からも数（`totalBlockedBy`）からも消える（[FACT-144][facts]）ので、上の表の依存の相手の行のとおり、有効な `wait` の印に書いた番号を引いて見つける。見分けの関数の結果の種類は、作業の単位の Issue の見分け（下の箇条）と同じにし、依存の相手の番号では、`flow/run/gather.ts` が次のとおり読み分けて作業の単位の事実に入れる（「[状態遷移と判定][b02]」の「状態の組み立て」）。消されたと、読めないのうち `readIssueWithoutRedirect` の応答が `404` のもの（`/repositories/<同じ ID>/` の引き直しの応答を含む）は、消された相手（`logic/state/axes.ts` が中止ありにする）。ある・移されたは、何もしない（人が依存を外したか、相手が別のリポに移った）。ほかの読めないは、上の箇条の順 7 の止まり方（`github-unreadable`）に当て、読めなかった作業の単位の番号と一緒に、相手の番号を `runs.jsonl` と `status.json` の「実行」の欄に書く。番号ごとの見分けの結果は、`runs.jsonl` の作業の単位の結果にも書く（人が読むためで、判定には使わない）。`wait` の印に番号の無いまま消された相手と、App から見えない相手と、ほかのリポにある相手が消されたことは、見つけられない（ほかのリポにある相手の番号も当てる先のリポで引くので、当てる先のリポに同じ番号の Issue が無ければ、要らない計画の見直しが 1 回起きる）。依存の一覧の項目が読めない（`null`）ときは、読めなかったとして上の箇条（順 7 の止まり方）に当てる（止める側）
- 必須チェックは、チェックの実行にワークフローのパスが無いので、ワークフローの実行の `check_suite_id` とチェックの実行の `check_suite.id` を突き合わせてパスを付ける（[FACT-127][facts]）。GitHub Actions のほかの app のチェックは、パスを持たない（設定の `workflow` が `null` のもの。「[設定][b01]」の `checks.required`）
- 印の Issue を GraphQL で引いて `NOT_FOUND` のときは、`io/github.ts` の `readIssueWithoutRedirect`（REST をリダイレクトをたどらずに 1 回だけ引く。「[外との境][d01]」の「GitHub の呼び方」）で引き、「[状態遷移と判定][b02]」の「状態の組み立て」の見分け方（`410` は、当てる先のリポの Issue の機能が有効（`has_issues` が `true`）なときだけ消された。`301` で `Location` の先が `/repos/<owner>/<repo>/issues/<番号>` の形で別のリポを指すか、`Location` の値が空の文字列なら移された。`/repositories/<ID>/issues/<番号>` の形で ID が当てる先のリポの ID と同じなら、`Location` の先をたどらずに 1 回だけ引き直して見分ける。ほかの `301`（`Location` の見出しが無い、ID が違う、当てる先のリポ自身を指すなど）、`302`・`307` など `301` でないリダイレクト、`has_issues` が `false` の `410`、`404`・`403`・ほかは読めない。当てる先のリポの Issue が返ったら、GraphQL と食い違うので読めない）で見分ける。見分けは `flow/run/gather.ts` の関数（`classifyMissingIssue`）に置き、見つかりの記録の書き直し（`flow/safety/suspect.ts`。下の「全体の停止と通知」）と点検の作業場所の残骸の見分けも、同じ関数で見分ける。当てる先のリポの ID と Issue の機能が有効かは、`410` と `/repositories/<ID>/` の形の `301` のときだけ、REST の `GET /repos/{owner}/{repo}` の `id` と `has_issues` で読む（読めなければ、読めない。ほかの応答は、リポを読まずに見分ける）。移された Issue の先が見えるかは問わない（App は当てる先のリポだけに入っている）。移されたときも消されたとき（Issue の機能が有効なリポの `410`）も、結びつく PR を `issue-changed` の停止中にする（`flow/steps/stop.ts`。`stop` の印は PR にだけ書く）。止めた理由のコメントには、`## 再開` でなく「PR を閉じるか残すかを人が決める」を示し（作業の単位の Issue が無いので、人の `## 再開` を読めない）、移されたときは移った先の Issue（`Location` の URL から取り出した owner・repo・番号。API では引かない）を書き（`Location` の値が空なら書かない）、消されたときは「作業の単位の Issue が消された。PR を閉じるか残すかを人が決める」（`logic/text/comments.ts` の決まった文）を書く。消されたときも、PR を閉じたり作業ブランチを消したりする片付けはしない（基本設計の「先に見る」の順 8）。読めないときは、作業の単位を読めないときと同じ（`github-unreadable`。`404` は App の権限や導入先が外れただけでもなりうるので、移されたか消されたと読まない）

## 状態と軸の記号

`logic/state/states.ts` に、主な流れの 17 の状態と、重ねる 3 本の軸の値の記号を持つ。記号は `status.json` と記録に書き、Project の表示の欄には、同じ表の [FLOW-39][flow] の名前で書く。

| 枠 | 状態 | 記号 |
| --- | --- | --- |
| 依頼 | 起票済み・検疫済み・差し戻し済み・直し済み・下書き済み・決定済み | `filed`・`quarantined`・`returned`・`corrected`・`drafted`・`decided` |
| 計画 | 計画済み | `planned` |
| 変更 | 変更済み・検査合格・検査不合格・レビュー不合格・レビュー合格・衝突あり | `changed`・`checks-passed`・`checks-failed`・`review-failed`・`review-passed`・`conflicted` |
| 終了 | マージ済み・閉鎖済み・完了・中止 | `merged`・`closed`・`done`・`cancelled` |

| 軸 | 値 | 記号 |
| --- | --- | --- |
| 止め方 | 停止中・引き取り中・一時停止中 | `stopped`・`manual`・`paused` |
| 先の依頼 | 未完了・中止あり | `unfinished`・`cancelled` |
| 安全 | 攻撃の疑い（AI の文）・攻撃の疑い（入口） | `ai-text`・`entry` |

- 状態の記号は、状態の名前と同じく、済ませた事実で付ける（次に動く担い手を名前に入れない）
- 軸の値の（なし）は、記号を持たず、値が無いことで表す。Project の表示の欄も、選択肢を選ばずに空にする（「[設定][b01]」の `project.fields.*`）
- `logic/state/assemble.ts` は、状態を決められない（読んだ事実の組み合わせが、どの表のどの行にも当たらない）ときに、状態の代わりに「決められない」を返す。`logic/state/next.ts` は、「決められない」を受けたら停止中（`unrecoverable`）にする（「[状態遷移と判定][b02]」の「次の工程」）
- 「決められない」作業の単位は、`logic/state/order.ts` が進行中の作業の単位の数に数え、組 2（進行中）に入れる。数えないと、読み誤った作業の単位の分だけ新しい着手が増える側に倒れるため（「[状態遷移と判定][b02]」の「次の工程」の「作業を増やさずに」）。Project の表示の欄は、`flow/steps/display.ts` が、主な流れの枠と状態を書き換えずに前の値のまま残し、止め方の欄だけを書く

## 作業の単位の進め方

![作業の単位の見直し][fig-units]

`flow/run/units.ts` は、作業の単位を次の組の順に進める（「[状態遷移と判定][b02]」の「作業の単位を進める順」）。

| 組 | 進める工程 |
| --- | --- |
| 1（片付け） | 片付け |
| 2（進行中） | マージの判定のほかの工程 |
| 組 2 の後 | レビュー合格の PR の、マージの判定（PR の番号の小さい順。組 2 でマージの判定に当たって見直しを止めた作業の単位を、同じ見直しの輪でもう一度見直す） |
| 3（依頼） | 依頼の枠の工程 |
| 4（新しい着手） | 決定の印と計画の輪 |

作業の単位ごとに、次の見直しを繰り返す。

| 順 | すること |
| --- | --- |
| 1 | `logic/state/assemble.ts` で状態を組み立てる |
| 2 | `logic/state/next.ts` に、状態と、作業の単位ごとの値と、実行の全体の値（どちらも下の箇条）と、凍らせたリポの設定と、今の時刻を渡し、工程を決める |
| 3 | 下の「見直しを止める条件」に当たれば、作業の単位を終える |
| 4 | 工程のファイルを呼ぶ |
| 5 | 工程の結果の書いた印と GitHub の変化を、`logic/state/apply.ts` で事実に足し、順 1 に戻る |

| 見直しを止める条件 | 理由 |
| --- | --- |
| 何もしないか待つ行（止め方か安全の軸に値がある、待つ、人の番）に当たった | 「次の工程」の「先に見る」と「状態ごとの工程」 |
| 同じ実行で 2 つ目の重い工程に当たった | 重い工程は作業の単位ごとに 1 回の実行で 1 つ（[FLOW-4][flow]） |
| push した | push した作業の単位は次の実行まで進めない（[FLOW-4][flow]） |
| 工程の結果が `advanced` でない（止めた、攻撃の疑いにした、失敗した、起こさなかった） | 下の「工程の結果」 |
| 組 2 で、マージの判定に当たった | マージの判定は組 2 の後に回す（[MERGE-5][merge]） |
| 同じ実行で、同じ作業の単位に、前に工程のファイルを呼んだ（見直しの順 4 に進んだ）工程の記号を、また選んだ。順 3 のほかの条件で止めた選び（組 2 でマージの判定に当たったなど）は数えない | 書いた印の足し方の誤りで、同じ書き込みを重ねないため。工程を呼ばずに、実行の失敗（`failed`）として記録し、次の作業の単位へ進む |
| 1 つの作業の単位で、見直しが 20 回を超えた（回数は「[設定と記録][d02]」の「プログラムに固定する値」） | 足し方の誤りで工程が入れ替わりながら続き、実行が終わらない形を止めるため。実行の失敗として記録し、次の作業の単位へ進む |

- 工程の結果が `failed` のとき（思わない失敗を含む）は、作業の単位を終える前に、`logic/run/failures.ts` で続いた回数を数え直し、`limits.retry.count` 回目になっていれば、`flow/steps/stop.ts` で停止中（`retry-limit`、片付けの工程なら `cleanup-failed`）にしてから終える（「[AI のセッション][b03]」の「起動の前の確かめ」の表の下の「その回で停止中にする」）。`stop` の印を書けなければ、次の実行の `logic/state/next.ts` が停止中を返す（下の「実行の失敗の数え方」の表の下）
- `logic/state/next.ts` に渡す作業の単位ごとの値は、実行の失敗が続いた回数、片付けの失敗が続いた回数、重い工程を起こしてよいか（どれも `logic/run/failures.ts` が返す。下の「実行の失敗の数え方」）
- `logic/state/next.ts` に渡す実行の全体の値は、全体の止める合図、全体の停止の Issue の有無、基線が緑か、着手した件数、下書きと書き直しの件数、`ready` の判定を書いた PR、進行中の作業の単位の数（着手しようとする作業の単位自身を除く。`logic/state/order.ts` が、渡す時点のすべての作業の単位の状態から数える）。設定（`limits.*`・`checks.required` など）は、`RunContext` の凍らせたリポの設定をそのまま渡す。設定のほかは実行の中で変わるので、作業の単位ごとと見直しごとに渡し直す
- 足す時刻は、書いたときの GitHub の応答の時刻（コメントの `created_at` など）を使い、手元の時計を使わない。マスターと人の操作のように、時刻の前後で状態が決まるため
- 作業の単位の見直しを終えたら、`flow/steps/display.ts` で、Project の表示の欄と表示のラベル `security-suspected` を書く。`ProjectIssues` で読んだ今の値と違う欄とラベルだけを書く。毎回の実行で、変わっていない欄まで書き直さないため
- 作業の単位を 1 つ終えるたびに、期限（`RunContext`）を見る。過ぎていたら、残りの作業の単位を進めず、作業の単位の結果に「次の実行に回した」と書く（順 9）。組の境目でも同じに見る
- 工程を 1 つ終えるたびに、`RunContext` の実行を終える理由を見る。あれば、残りの作業の単位を進めず、作業の単位の結果に「次の実行に回した」と書き、順 10 へ進む。1 回の実行の終わり方は、実行を終える理由の記号（`stop-signal`・`signal-unreadable`・`machine-unsafe`）にする
- 前の実行が残したセッションを止められなかった作業の単位は、組を問わず、組 1 の前に停止中（`session-not-stopped`）にする。`flow/steps/stop.ts` が止めた先（Issue と、PR のセッションなら PR）のすべてに `stop` の印を書けたら、`flow/session/leftovers.ts` で、そのセッションの終わりの行を、始まりの行の `--max-budget-usd` の値で書き、`session-not-stopped` で人に渡したことを書く（「[AI のセッション][b03]」の「前の実行が残したセッション」の順 4）。書いた `stop` の印は、`logic/state/apply.ts` で作業の単位の事実に足してから組 1 に進む（同じ実行の組の中で、止め方の軸に値のある状態で組み立て、AI のセッションを起こさないため）。書けなかった作業の単位は、下の「GitHub に書くとき」の表の下のとおり、今の実行では組 1〜4 に入れない。控えた作業の単位が順 7 の作業の単位に無いとき（人が Project から外した、別のリポに移した、消した）は、停止中にせず、終わりの行も書かない。人が残りを止めた後の実行が、「[AI のセッション][b03]」の「前の実行が残したセッション」の順 2 で残りが無いと確かめて、順 4 で終わりの行を書く。それまでは、動いているセッションとして `--max-budget-usd` の値で起動の前の確かめに数え、点検の止めなかったプロセスの項目に `warn` で出る（「[点検][d04]」の「ファイルの一覧」の表の下）。`stop` の印を 1 つでも書けなければ、終わりの行を書かない（次の実行が同じセッションを見つけて、停止中にし直す）。片付けの「先に見る」の順 2 の扱いは、書いた `stop` の印の時刻で決まる（「[状態遷移と判定][b02]」の「1 回の実行の流れ」の順 2）
- 前の実行が全体の停止の Issue を開けなかった作業の単位（下の「全体の停止と通知」の開き直し）は、組を問わず、組 1 の前に、全体の停止の Issue を開き直す。見つかりの記録から `security` の印と `halt` の印を書き直すのも、同じ所で、開き直しより先に行う（下の「全体の停止と通知」の「見つかりの記録から印を書き直す」の行）。書き直して書けた `security` の印は `logic/state/apply.ts` で作業の単位の事実に、`halt` の印は `RunContext` の読んだ `halt` の印に、GitHub の応答の時刻で足してから、開き直しと組 1 に進む（組 1 の前に書いた `stop` の印と同じ。同じ実行の組の中で、安全の軸に値のある状態で組み立てるため）。作業の単位の Issue に `security` の印を書き直せなかった作業の単位は、今の実行では組 1〜4 に入れない。中身を読めない見つかりの記録のうち、ファイルの名前から作業の単位の Issue の番号を読めたものの作業の単位も、今の実行では組 1〜4 に入れない（AI を使わない工程も進めない。名前から番号を読めなければ、外す作業の単位は無い）。安全の軸に値がある作業の単位は「先に見る」の順 4 で何もしないので、作業の単位の見直しの外で行う

## 工程

`logic/state/next.ts` は、次の記号の工程を返す。重さと線は「[状態遷移と判定][b02]」の「状態ごとの工程」と「先に見る」の表のとおり。

| 工程の記号 | 当たる行 | ファイル |
| --- | --- | --- |
| `entry-quarantine`・`draft`・`redraft`・`instruction-quarantine`・`approval-reset`・`ignored-instruction` | 起票済み・検疫済み・差し戻し済み・直し済み・下書き済み、決めた後の `## 作業指示` | `flow/steps/brief.ts` |
| `decision-marker`・`start` | 決定済み（(1) と (2)） | `flow/steps/decide.ts`（`start` は `flow/steps/plan.ts` を呼ぶ） |
| `create-change`・`create-pr-from-branch`・`fix-checks`・`fix-review`・`fix-conflict` | 計画済み・検査不合格・レビュー不合格・衝突あり | `flow/steps/change.ts` |
| `review`・`remark-review` | 検査合格（載せ直しの後に印を付け直すときは `remark-review`） | `flow/steps/review.ts` |
| `follow-up`・`ready`・`sync-base`・`merge-judgment`・`remind` | レビュー合格の (1)〜(5) | `flow/steps/passed.ts` |
| `cleanup`・`close-old-pr` | マージ済み・閉鎖済み、「先に見る」の順 9 | `flow/steps/cleanup.ts` |
| `wait-marker`・`dependency-review` | 「先に見る」の順 13・14 | `flow/steps/dependency.ts` |
| `stop` | 停止中にする行（止めた理由の記号と、止めた先を添える） | `flow/steps/stop.ts` |
| `none` | 何もしないか待つ行 | — |

- `sync-base` は、進行 Bot の clone で base ブランチを作業ブランチに取り込む（`git merge`）載せ直し。`git rebase` と、GitHub の PR のブランチを更新する API は使わない（「[状態遷移と判定][b02]」の「push の手順」の表の下）。基本設計のセッションの名前 `rebase-pr-<PR の番号>`（衝突の解消。「[AI のセッション][b03]」の「セッションの名前」）は、工程の記号 `fix-conflict` に当たる
- 工程は、同じ行の対象をまとめて 1 回で行う（`ignored-instruction` は対象の作業指示のコメントのすべて、`follow-up` はまだ記録していない 🟢 の指摘のすべて、`close-old-pr` は前の PR のすべて、`wait-marker` は終わっていない先の Issue のうち依存の一覧で番号が分かるもののすべてと、App から見えない相手の数）。書いた印を正しく足せていれば、同じ実行で、同じ作業の単位に同じ工程が 2 回選ばれることは無い
- `flow/steps/brief.ts` の入口の検疫と書き直しの前の検疫、`flow/run/intake.ts` の受け入れの依頼の実行の検疫は、`logic/text/issue-text.ts` で組み立てた Issue の文（進行 Bot の有効な印のコメントを除いたもの。「[文の検査と受け入れ][d06]」の「掛ける文」）を使う
- 計画の輪（`flow/steps/plan.ts`）とレビューのラウンド（`flow/steps/review.ts`）は、工程の前に、起こしうるセッションの数の分（数は「[AI のセッション][b03]」の「起動の前の確かめ」の重い工程の段落）を `RunContext` の費用の帳簿でまとめて取り置き、セッションごとに 1 枠ずつ `flow/session/run.ts` に渡す。使わなかった枠は、工程の終わりに返す（「[AI のセッション][d07]」の「費用の取り置き」）

### 工程の結果

工程のファイルは、次の結果を返す。`flow/run/units.ts` は、結果で見直しを続けるかを決め、作業の単位の結果（`runs.jsonl`）に書く。

| 結果 | 中身 | 見直し |
| --- | --- | --- |
| `advanced` | 工程を終えた。書いた印と GitHub の変化を添える | 続ける（push したときと、重い工程の後に 2 つ目の重い工程に当たったときを除く） |
| `stopped` | 停止中にした（止めた理由の記号） | 止める |
| `suspected` | 攻撃の疑いにした（`security` の印の `where`） | 止める |
| `failed` | 実行の失敗（AI のセッションの終わり方の記号、push の失敗、書き込みの失敗など） | 止める |
| `deferred` | 合図・全体の停止・1 日か 1 回の実行の費用の上限で起こさなかったか、途中で止めた。マシンの中のフォルダの異常（`machine-unsafe`。起動の前の確かめの順 5・6、順 9 の上のフォルダ）で起こさずに実行を終えた。マージの判定を次の実行に回した（`ready` の 1 件の上限、判定の時点で CI が緑でない、base ブランチが PR の head より先に進んだ。「[状態遷移と判定][b02]」の「マージの判定」） | 止める。実行の失敗に数えない |

- AI のセッションの終わり方の記号（「[AI のセッション][d07]」の「セッションの順」と終わり方の記号）は、`logic/state/session-result.ts` が工程の結果に写し、工程のファイルはこの関数を呼ぶだけにする。`done` のほかは、`not-stopped` を `stopped`（`session-not-stopped`）に、`settings-tampered` を `stopped`（`settings-tampered`）に、`stop-signal` を `deferred` に、`not-started` を外れた順の扱い（`deferred`・`stopped`・`suspected`・実行を終える）に、ほか（`prepare-failed`・上限・`refusal`・`error`・`contract-invalid`）を `failed` にする
- 扱いが実行を終えるとき（起動の前の確かめの順 1 で合図が `run` でないか読めない、順 5・6、順 9 の上のフォルダ）は、工程を `deferred` にし、`RunContext` の実行を終える理由に、添えられた記号（`stop-signal`・`signal-unreadable`・`machine-unsafe`）を入れる。起動の前の確かめの順 1 で全体の停止の Issue に当たったときは `deferred` だけにし、実行を終えない（AI を使わない工程は続ける）。`stop-signal` で止まったセッションは、`RunContext` の合図が `run` でなければ、実行を終える理由を `stop-signal` にする。全体の停止の Issue を開いて止めたとき（`flow/safety/halt.ts`）は、合図が `run` のままなので、実行を終えない。全体の止める合図で止めた実行は、手元の記録に残し、lock を外して終わる（[ADR-20261017-007][adr-stop]）
- 計画の輪とレビューのラウンドのように、1 つの工程が 2 つ以上のセッションを起こすときは、セッションごとの記号を、「[AI のセッション][d07]」の終わり方の記号の先後で 1 つにしてから写し、結果は工程に 1 つにする
- 子プロセスの出力が上限を超えて失敗したときは、`runs.jsonl` の作業の単位の結果の失敗の理由に `output-limit` を書く（「[外との境][d01]」の「子プロセスの起こし方と止め方」）。止めた理由の記号には足さない

## GitHub に書くとき

`flow/run/write.ts` は、GitHub に書くすべての処理（コメントと印、ラベル、Project の欄、PR の作成と閉じること、Issue を閉じること、ブランチを消すこと）の前と後に、次を行う。push は `flow/push.ts` が、同じ決まりで行う。

| 順 | すること |
| --- | --- |
| 1 | 全体の止める合図を読み直す（`flow/safety/signal.ts`）。`run` でない値なら `stop-signal`、読めなければ `signal-unreadable` を `RunContext` の実行を終える理由に入れ、書かずに工程を `deferred` で終える |
| 2 | 印を付けるコメントは、`marker.ts` と `logic/marker/sign.ts` で印の行を作り、`logic/text/comments.ts` で決まった部分と `CheckedText` の文につなぐ（「[文の検査と受け入れ][d06]」の「コメントの組み立て」） |
| 3 | 書く |
| 4 | 結果（書いた、HTTP の状態で断られた、届いたか分からない（時間の上限で取り消した、つながらない、GraphQL の誤り））を `writes/<実行 ID>.jsonl` に 1 行足す（「[設定と記録][d02]」の「手元の記録」） |

- 書き込みが断られたときと、届いたか分からないときは、作業の単位を今の実行では進めず、工程を `failed` で終える。次の実行が GitHub から読み直して続ける（「[設定][b01]」の「子プロセスが時間の上限を過ぎたとき」）
- 書いた印は、コメントの ID と GitHub の応答の時刻と組で、工程の結果に添える（上の「作業の単位の進め方」の足す時刻）
- 「1 回だけ書く」印（「[状態遷移と判定][b02]」の「ほかの印」）を書くかは、`logic/state/next.ts` が、事実の有効な印から決める。`flow/run/write.ts` は書くかを判定しない
- 合図は、工程ごとにまとめて読まず、書き込みの呼び出しのたびに読む。工程の途中で人が合図を `stop` にした後の書き込みも止めるため（[ADR-20261017-007][adr-stop] の「GitHub に書き込む前に合図を読む」を、呼び出しの単位で行う）

## 実行の失敗の数え方

`logic/run/failures.ts` は、`runs.jsonl` の作業の単位の結果と、今の実行の作業の単位の結果（`RunContext`。順 10 まで `runs.jsonl` に書かないため）と、作業の単位の最新の `## 再開`（R）の時刻と、今の時刻から、作業の単位ごとに次を返す。数え方の決まりは「[AI のセッション][b03]」の「起動の前の確かめ」の表の下のとおり。

| 返すもの | 決め方 |
| --- | --- |
| 実行の失敗が続いた回数 | R より後の結果を新しい順に見て、結果が `failed` のものを数え、重い工程を終えた結果（`advanced` の重い工程）で数えるのをやめる。`deferred` と、作業の単位を進めなかった実行は、数えず、数えるのもやめない |
| 片付けの失敗が続いた回数 | 同じく、片付けの工程の `failed` だけを数える。片付けのほかの工程の結果では、数えるのをやめる |
| 重い工程を起こしてよいか | 最後に `failed` を書いた実行より後の、起こされ方が定期の実行の数（今の実行を含む）が、`limits.retry.intervalRuns` 以上か（初期値の 1 なら、次の定期の実行で起こしてよい） |

- 失敗が `limits.retry.count` 回目になったら、失敗した工程の後に、同じ実行で停止中にする（`retry-limit`、片付けは `cleanup-failed`。停止中にするのは `flow/run/units.ts`。上の「作業の単位の進め方」の表の下）。`stop` の印を書けなかったときに備え、`logic/state/next.ts` も、回数が上限に達していて、R より新しい `stop` の印が無ければ、工程の代わりに停止中を返す
- 受け入れの依頼の実行のセッションは、作業の単位の結果に書かないので、続いた回数に入らない（「[AI のセッション][b03]」の「起動の前の確かめ」の表の下）

## push の手順

`flow/push.ts` は、「[状態遷移と判定][b02]」の「push の手順」の順 1〜8 を行い、次のどれかを返す。工程のファイルは、返った結果を工程の結果に写す。

| push の結果 | 中身 | 工程の結果 |
| --- | --- | --- |
| `pushed` | 送り、読み戻した（初回は PR と `link` の印まで） | `advanced` |
| `stopped` | `adr-required`（順 1。作業 AI の出力契約の `stopReason` が `adr-required` か `canon-change`）・`workspace-tampered`・`no-new-commit`・`protected-path`・`manual-push`・`not-fast-forward`・`unrecoverable` のどれかで止めた | `stopped` |
| `suspected` | 漏えいの検査（`where` が `leak`）か検疫（`where` が `text`、`manual-push` の差分は `code`）で見つけた。両方で見つけたときは、検疫の `where` で 1 つにする | `suspected` |
| `deferred` | 順 6 で、合図が `run` でないか、全体の停止の Issue があった（合図が `run` でないか読めないときは、上の「GitHub に書くとき」の順 1 と同じく、`RunContext` の実行を終える理由を入れる） | `deferred` |
| `failed` | 出力契約を取り出せない、対応コメントを書けない、push が断られた、PR を作れない、時間の上限を過ぎた | `failed` |

- 範囲の commit の一覧（`git rev-list <控えた SHA> ^<base> ^<origin>`）、commit ごとの触れたパス（`git diff-tree -r --name-only -z`。merge の commit は `--cc`）、commit ごとの差分とメッセージと作者は、`io/git.ts` で読む（漏えいの検査に渡す差分は、`io/git.ts` の漏えいの検査用の読み方（`--text`。「[外との境][d01]」の「git の呼び方」、[FACT-129][facts]）で読む）。パスの照らしは `logic/push/paths.ts` が `logic/settings/paths.ts` を使って行い、push で効くものの当たりを、マージまで効かないものの当たりより先に返す
- PR の題名を規約（`conventions.*`）に照らす処理と、固定の形の題名と、本文の並べ方は、`logic/text/comments.ts` に置く（「[文の検査と受け入れ][d06]」の「コメントの組み立て」）
- 重なり（`overlap` の印）は、順 2 で取り込んだ後に、`logic/push/overlap.ts` が、PR の変更ファイルの一覧と、ほかの進行中の PR の変更ファイルの一覧（進行 Bot の clone の `git diff --name-only <base>...<ブランチ>`）を比べて決める
- 取り込みの前の後始末（git のプロセスが無いことの確かめ、`index.lock` を消す、`git merge --abort`、`git reset --hard` と `git clean -ffdx`）は、`flow/run/clone.ts` が行う。git のプロセスがあれば、取り込まずに `failed` にする
- 載せ直しと、載せ直しの後に印を付け直すときの差分の比べ方は、`git diff <base>...<head>` に `git patch-id --stable` を掛けた値にする。前の head と新しい head の両方で、同じ base の先端（進行 Bot の clone で fetch したもの）を使う

## 判定

`logic/judge/` の判定は、基本設計の「[状態遷移と判定][b02]」の「判定」のとおり。本節は、判定に渡す事実と、基本設計が決めていない細部を決める。

| ファイル | 渡す事実 | 決めた細部 |
| --- | --- | --- |
| `checks.ts` | `checks.required`、パスを付けたチェックの実行（名前、app、パス、状態、結果、始まりと終わりの時刻、ID）、今の時刻 | 「最新の 1 件」は、名前・app・パスが同じものの中で、始まりの時刻が新しいもの（同じなら ID の大きいもの）。`checks.required` が空なら緑と読まず、待つと返す（点検が fail にする。[IMPL-27][impl]） |
| `rounds.ts` | 数える `review` と `fix` の印 | `round` の欠けは、数える `review` の印の `round` の集合が 1 から最大まで欠けずにそろうかで見る。同じ `round` の印が 2 つ以上あっても欠けにしない（最新の 1 つを採る） |
| `convergence.ts` | 必須チェックの結果、PR の head、最新の `review` の印 | — |
| `repeat.ts` | ラウンドごとの `review` の印の `findings` と `head`、`fix` の印、最新のラウンドの head の形（親の SHA の並びと、2 つ目の親が base ブランチにあるか） | head の形は、工程のファイルが進行 Bot の clone で読む（`git rev-list --parents -n 1 <head>` と `git merge-base --is-ancestor <2 つ目の親> <base>`） |
| `merge.ts` | レビュー合格の判定、PR の向き先と `link` の印、`git diff --raw <base>...<head>` の一覧、最終の head の差分（漏えいの検査用の読み方で読んだもの）への漏えいの検査の結果、最新の `review` の印の `droppedHigh`、`merge.allowPaths` と `merge.policyPaths`、実行の全体の値の `ready` の判定を書いた PR、ほかの開いた PR の最新の `merge` の印 | `ready` の 1 件の上限は、今の実行で `ready` を書いた PR と、ほかの開いた PR のうち、最新の数える `merge` の印が `ready` のものを、印の `head` が PR の今の head と同じかを問わずに数える。head の進んだ PR も、閉じられるか、判定し直して最新の数える `merge` の印が `human` になるまで数える（[MERGE-5][merge]、[ADR-20261016-001][adr-merge-limit] の決定 2） |

- `reasons` の記号の一覧は `logic/judge/merge-reasons.ts` の定数にし、`logic/judge/merge.ts` と `marker.ts` が読む（「[印][d03]」の「欄の値の形」の表の下）

## 全体の停止と通知

| すること | ファイル | 決めたこと |
| --- | --- | --- |
| 全体の止める合図を読む | `flow/safety/signal.ts` | REST でリポの変数 `DEV_AUTOPILOT_RUN` を読む。値が `run` か、ほかの値か、読めないかを分けて返す。呼ぶ側は、読めないときを `run` でないものと扱う（書かず、AI のセッションを起こさない）。ただし、AI のセッションの見張りは、読めないときに止めない（「[AI のセッション][d07]」の「見張り」、[ADR-20261017-007][adr-stop] の決定 2）。順 3 で読めなければ、終わり方は `signal-unreadable` |
| 見つかりの記録を読む | `flow/safety/signal.ts`、`flow/run/records.ts`、`logic/run/records.ts` | 順 2 で lock を取った後に、`flow/safety/signal.ts` が `flow/run/records.ts` の読む関数を呼び、読んだ結果（ある・無い・読めない）と、読めた記録と、読めないファイルの名前と番号を `RunContext` に持つ（読み方と、ある・無い・読めないの決め方は「[設定と記録][d02]」の「見つかりの記録」。点検のマシンの組も同じ関数で読む）。「ある」か「読めない」なら、`RunContext` の全体の停止の Issue を「ある」にする。どの起こされ方の実行も読む。「読めない」ときも、点検の `warn`（`unreadable`）に出すだけで作業には入り、AI のセッションだけを起こさない（AI を使わない工程と、読める記録の書き直しは続ける。[SETUP-2][setup] の fail に当てない）。名前から作業の単位の Issue の番号を読めた読めない記録の作業の単位は、組 1〜4 から外す（上の「作業の単位の進め方」）。読めない記録は、書き直す中身が分からないので、書き直さず、消さない（人の戻し方は「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」の表の下）。見つかりの記録で決めるのは、AI のセッションを起こさないことと、下の書き直しだけ。作業の単位の状態、安全の軸の値、全体の停止の解き方は、今のとおり GitHub の印だけで決め、見つかりの記録が無いことを全体の停止を解く理由にしない（[ADR-20261111-001][adr-halt-records] の決定 1・3） |

## 止めた理由の記号

`logic/state/reasons.ts` に、止めた理由の記号の一覧を、14 個と実装の都合の記号の 2 つの組で定数として持つ。`logic/state/reasons.ts` は何も import しない（`marker.ts` が読むので、互いに import しあう形を作らないため）。`marker.ts` は、`stop` の印の `reason` の値の形を、一覧で確かめる（「[印][d03]」の「欄の値の形」）。

- 実装の都合の記号は、基本設計の「止めた理由の記号」の表の名前を変えずに使う（基本設計が、名前を変えるかを詳細設計に任せた）。どれも英小文字を `-` でつないだ形で、14 個の記号と書き方がそろっており、要件・基本設計・図に同じ名前で載っている。名前を変えても動きは変わらず、文書と図を直す手間だけが増えるため
- 組み直す前の記号（`usage-limit` など）は、一覧に入れない。進行 Bot はまだ GitHub に印を書いたことが無く、読む古い印も無いため。古い記号の `stop` の印は、形が合わない無効な印になる
- 止めた理由のコメントの決まった文（人がすること）は、記号ごとに `logic/text/comments.ts` の言語ごとの表に持つ。記号ごとの差し込む値（当たったパス、PR へのリンク、消すフォルダの組と順など）は、`flow/steps/stop.ts` が工程の結果から受け取る

## 作業場所の残骸

`logic/run/residue.ts` は、置き場の `sessions/` のフォルダの名前と、短い一時フォルダの根の下の ID と、セッションのフォルダの ID のファイルの中身と、名前から引いた Issue と PR の事実を受け取り、フォルダごとに、扱い（「[状態遷移と判定][b02]」の「作業場所の残骸」の表の行）と扱う所（点検か次の工程か）を返す。表の行が使う作業の単位の状態（終了の枠の前か、マージ済みか閉鎖済みか、完了か中止か）は、受け取った事実から `logic/state/assemble.ts` で組み立てる。点検（順 5）は状態の組み立て（順 7）より前なので、名前から引いた作業の単位だけを同じ関数で組み立てる。点検と次の工程で、状態の決め方を分けないため

- 点検（順 5）は、名前から引いた Issue と PR を `flow/run/gather.ts` と同じ読み方で読み、扱う所が点検の行だけを結果にする（「[点検][d04]」）
- 次の工程は、`logic/state/next.ts` が、作業の単位の事実に入れた残骸の扱いで、「先に見る」の順 8（Issue が移されたか消された）・順 9（戻した R より前の PR・作業ブランチ・セッションのフォルダが残っている）・順 12（作業場所の残骸がある）に当てる
- 名前から工程と番号を読む処理は、`logic/session/names.ts` と共有する（「[AI のセッション][d07]」の「ファイルの一覧」）
