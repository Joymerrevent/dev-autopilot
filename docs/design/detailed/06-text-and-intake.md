# 文の検査と受け入れ

AI に渡す文と GitHub に書く文を扱う処理（Issue の文の組み立て、検疫、漏えいの検査、ハッシュ、コメントの組み立て、出力契約の取り出し、見出しの比べ方）と、人が呼ぶ intake の Skill の処理を決める。
検疫を掛ける文と時は要件の [TEXT-11][text]、漏えいの検査を掛ける文は [IMPL-15][impl]、URL の照らし方・出力契約の欄・コメントの形・ハッシュの取り方・intake の流れは基本設計の「[AI のセッション][b03]」が正本。本書は、正本が種類だけを挙げた検査の中身と、処理の作りを決める。

## 検疫

### 結果の形

検疫は、見つかったものの並び（空なら通った）を返す。1 件は、種類の記号と、場所を持ち、見つかった文の中身を持たない（[TEXT-11][text]、「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」）。

| 種類の記号 | 検査 |
| --- | --- |
| `delimiter` | 欄の区切りと、印と指摘の区切りの行を模した文字列 |
| `instruction` | 指示の形の語 |
| `invisible` | 見えない文字 |
| `html-comment` | HTML のコメント |
| `hidden-text` | GitHub が画面に出さない Markdown と HTML の書き方に入れた文 |
| `encoded` | 長い base64・16 進と、符号を並べた難読化 |
| `url` | 当てる先のリポの GitHub の URL のほかの URL |
| `attachment-url` | GitHub の Issue の添付の URL（`url` と分けて数える。「[AI のセッション][b03]」の「検疫が探す URL」） |

- 場所は、文の種類（題名・本文・何番目のコメント・欄の名前）と、文の中の行の番号。PR の差分なら、ファイルのパスと新しい側の行の番号（[ADR-20261027-002][adr-leak] の決定 1 の「文なら欄と行」）。文の中の行の番号は、CR と CRLF を LF にそろえた文を LF で分けた行の、1 から数えた番号で、当たった所の始まりの行を書く。正規化した文（見えない文字を除き NFKC をした文）で見つけたときも、元の文の行で書く（見えない文字を除くことと NFKC は LF を足し引きしないので、行は変わらない）
- 種類の記号は、`security` の印の `finding` の値の一覧でもある（「[印][d03]」の「欄の値の形」が本節に任せた）。一覧は `logic/text/finding-kinds.ts` に置き、`quarantine.ts`・`leak.ts`・`marker.ts` が読む。見つかった種類が 2 つ以上あるときは、表の上の行ほど先にして 1 つを `finding` に書き、攻撃の疑いのコメントの本文には、すべての種類と場所を書く
- 漏えいの検査の種類（下の「漏えいの検査」）も、`security` の印の `where` が `leak` のときの `finding` の値にする

### 検査ごとの決まり

どの検査も、書いてあるままの文と、正規化した文（見えない文字を除き、Unicode の互換の正規化（NFKC）をした文）の両方で探す。見えない文字や全角の文字で崩した形を見逃さないため（URL の検査の崩した形の決まりと同じ考え方）。

| 種類 | 探すもの |
| --- | --- |
| `delimiter` | (1) 役ごとの入力の欄の区切りの決まった部分（`logic/session/input.ts` の定数の見つけ方。「[AI のセッション][d07]」の「入力の欄の区切り」、「[AI のセッション][b03]」の「渡し方の決まり」）。後ろの `>>>` だけでは当てない。(2) 印の形と、指摘の区切りの行の形（「[印][d03]」の「印の形の見つけ方」と同じ見つけ方。英字の大小は区別しない） |
| `instruction` | `logic/text/patterns.ts` の指示の形の語の一覧（英語と日本語。例：前の指示を無視させる言い方、役を名乗る行の始まり（`system:`、`assistant:`）、役を表すタグ（`<system>`、`[INST]`、`<\|im_start\|>`）、システムの指示を名指す語）。空白の続きを 1 つにし、英字の大小を区別せずに照らす |
| `invisible` | 制御文字（タブ・改行・復帰のほか）、Unicode の書式の文字（ゼロ幅の文字、向きを変える文字、タグの文字 U+E0000〜E007F、ソフトハイフンなど。一般の分類が Cf のもの）、行と段落の区切り（U+2028・U+2029）、ハングルの埋め字（U+115F・U+1160・U+3164・U+FFA0）、異体字の選択子（U+FE00〜FE0D と U+E0100〜E01EF） |
| `html-comment` | コードの書式の外の `<!--`。コードの書式の中は、人の目にも文字として見えるので探さない。コードの書式かは、URL の検査と同じ `logic/text/markdown-code.ts` で決める |
| `hidden-text` | コードの書式の外の、(1) 題（`"…"`・`'…'`・`(…)`）を持つ参照の定義（`[ラベル]: 先 "題"`。先が相対のパスでも当てる）、(2) 先が `#` だけの参照の定義（`[//]: #` の形。Markdown のコメントの書き方で、ラベルにも文を隠せる）、(3) HTML のタグの属性の値のうち、URL を値に取る属性（「[AI のセッション][b03]」の「検疫が探す URL」の HTML の属性の値。URL の検査で照らす）のほかのもの（`title`・`name` など）。どれも画面に文が出ない（[FACT-131][facts]）。コードの書式かは `logic/text/markdown-code.ts` で決める。PR の差分には掛けない（下の「掛ける文」） |
| `encoded` | base64 の文字（英数字と `+`・`/`・`-`・`_`。末尾の `=` を含む）が切れ目なく 100 文字以上続き、英字と数字の両方を含むもの。16 進の文字が 100 文字以上続くもの。`%XX`・`\xXX`・`\uXXXX`・`&#…;` の符号が 10 個以上続くもの |
| `url` と `attachment-url` | 「[AI のセッション][b03]」の「検疫が探す URL」のとおり |

- `invisible` は、ゼロ幅の結合子（U+200D）だけ、直前と直後の文字がどちらも絵文字（Unicode の `Extended_Pictographic`）のときは当てない。絵文字を使った人の文で毎回止めないため。肌の色の修飾子（U+1F3FB〜1F3FF）か U+FE0F をはさんで U+200D が続く並び（👩🏽‍💻、🏳️‍🌈）と、ほかの所の U+200D は当てる（止める側。外すなら、下の箇条のとおり ADR で決める）。異体字の選択子の U+FE0E・U+FE0F は、見えない文字の一覧に入れていないので当てない
- `encoded` の 100 文字は、パッケージのロックファイルの完全性のハッシュ（`sha512-` に続く base64 の 88 文字）を当てず、隠した文を入れられる長さの塊を当てる境目として決めた。100 文字に満たない base64 でも、文を隠すことはできる。検疫は網であって壁でない（[TEXT-11][text]）ので、短い塊は AI の権限の制限で受ける
- 指示の形の語の一覧は、言い換えを取りこぼす前提の網で、新しい手口を見つけたら一覧と `fixtures/quarantine/` の見本に足す（[TEXT-11][text]）。一覧に語を足すこと、検査の種類や見本を足すことは、検疫を強める向きなので ADR は要らない（PR で足す）。一覧から語を外すこと、見えない文字の例外を足すか広げること、`encoded` の長さを上げること、検査の種類を外すことは、検疫の範囲を狭める変更なので、安全の境界を緩める変更として ADR で決める（要件の [TEXT-11][text] が URL の範囲を ADR で決めるのと同じ扱い。[ADR-20261015-005][adr-settings] の決定 1 の「迷ったら ADR」、[設計を変えるとき][design-change]）

### 掛ける文

検疫を掛ける文と時は [TEXT-11][text] の表のとおり。本書は、Issue の文の組み立てと、PR の差分の範囲を決める。

- Issue の文（題名・本文・コメント）は、`logic/text/issue-text.ts` が、コメントから進行 Bot の有効な印のコメント（`logic/marker/read.ts` が有効な印と返したもの。投稿者が `safety.botAccounts` のどれかで、未編集で、印の形がちょうど 1 つで、形と署名が通る）を除き、作成の順に並べて組み立てる。進行 Bot が書いた印の行と決まった文を、入口の検疫で攻撃の疑いと読まないため。進行 Bot のコメントの AI の文は、投稿の前に検疫と漏えいの検査を通っている。印の無い進行 Bot のアカウントのコメント（人の投稿として読む。[ADR-20261015-004][adr-markers] の決定 1）と、無効な印のコメント（書き換えられた文を持ちうる）は除かない（止める側）
- 入口の検疫、受け入れの依頼の実行の検疫（「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」の順 5）、受付 AI に渡す前の検疫（起動の前の確かめの順 7）、受付 AI の欄、`quarantine` の印の `textHash` は、どれも上の組み立てで作った同じ文を使う。進行 Bot の有効な印のコメントは、受付 AI の Issue の文の欄に入れない（書き直しで要る今のマスターは、検疫を通して、Issue の文と別の欄で渡す。「[AI のセッション][b03]」の「役ごとの要素」の受付 AI の行）ので、検疫から除いても、渡す文の検疫は緩まない
- PR の差分は、足した行（diff の `+` の行）だけを検疫する。消した行と前後の行は base ブランチの中身で、base ブランチのファイルは検疫しない（[TEXT-11][text]）。場所は、ファイルのパスと新しい側の行の番号で書く
- `hidden-text` は、PR の差分に掛けない。差分は人の目に元の行のまま見え、GitHub が描き出さないので、画面に出ない文が無いため（上の `html-comment` がコードの書式の中を探さないのと同じ考え方）。ほかの検査は差分にも掛ける
- 中身を文で持たないファイル（git が binary とみなすもの）は、diff に中身が出ないので検疫しない。AI にも中身を渡さない

## 漏えいの検査

`logic/text/leak.ts` は、GitHub に書くすべての文（[IMPL-15][impl] の一覧。diff は、`io/git.ts` が `--text` で読んだ差分の足した行。git が binary とみなすファイルも、中身の行を検査する。[FACT-129][facts] は `.gitattributes` の `-diff` で確かめた。`binary` の属性と NUL を含むファイルは確かめていない）を検査し、見つかったものの並びを返す。結果の形は検疫と同じ（種類の記号と場所。見つかった文の中身は持たない）。

| 種類の記号 | 探すもの |
| --- | --- |
| `secret-format` | 鍵とトークンの決まった形（`logic/text/patterns.ts` の一覧。例：PEM と OpenSSH の秘密鍵の始まりの行、GitHub のトークン（`ghp_`・`gho_`・`ghu_`・`ghs_`・`ghr_`・`github_pat_`）、主なクラウドとサービスのキーの形）。あわせて、進行 Bot が秘密の置き場から読んだ値の、書いてあるままの文字（印の署名の鍵の各行、Webhook の URL、秘密鍵のファイルの各行のうち 32 文字以上のもの）が文の中にあるか |
| `email` | メールアドレスの形。例のために予約されたドメイン（`example.com`・`example.org`・`example.net`・`.example`・`.invalid`・`.test`）、GitHub の `users.noreply.github.com`、進行 Bot の commit の作者のアドレス、`git@<ホスト>` は当てない |
| `machine-path` | マシンのパス：ホームのフォルダ、マシンの設定の `paths.*` と `sessionTmp.root` と `devAutopilotPath`、マシンの設定のフォルダ、macOS の人の一時フォルダ（`getconf DARWIN_USER_TEMP_DIR`）。照らす値は、呼ぶ側が値ごとに、書いたままのパス（マシンの設定の値と `getconf` が返した値）、実体のパス、実体のパスが `/private/` で始まるときは頭の `/private` を除いた形の 3 つ（同じものは 1 つ）を、末尾の `/` を除いて渡す。macOS の `/tmp` と `/var` は `/private/tmp` と `/private/var` へのリンクで、人と AI の文にはどちらの書き方も現れるため。文の中のパスとは、部分の一致で照らす |
| `bot-record` | 手元の記録の識別子の形（実行 ID と依頼の ID の `YYYYMMDDTHHMMSSZ-<16 進の 4 文字>`。「[設定と記録][d02]」の「実行 ID と依頼の ID」）と、セッションの名前の形（「[AI のセッション][b03]」の「セッションの名前」）と、短い一時フォルダの ID の値（「[AI のセッション][b03]」の「短い一時フォルダ」）。ID は英小文字と数字の乱数で、形がほかの語と分けられないので、形でなく、呼ぶ側が渡す ID の並び（`sessions.jsonl` の一時フォルダの行の ID と、今の実行で作った ID）と照らす。部分の一致でも当てる |
| `binary-diff` | 差分の中の、hunk の外にある `Binary files` で始まり `differ` で終わる行と、`GIT binary patch` の行。`--text` で読めば出ない行で、出たら中身を見ずに通さないために当てる（[FACT-129][facts]） |

- 進行 Bot が読んだ秘密の値と照らすときも、値は秘密の値の型（「[外との境][d01]」の「秘密の置き場」）のまま渡し、見つかったときの結果に値を入れない。中身は `logic/text/leak.ts` が照らすときだけ `revealSecret`（`logic/secret.ts`）で取り出す
- 進行 Bot が自分で組み立てる決まった文（印、決まった見出し、固定の文）は検査しない。AI の文と、人の文を写したもの（マスターに写した作業指示など）と、diff と commit を検査する
- 渡す文（人が決めたマスター）の TEXT-7 の検査（[TEXT-7][text]）は、上の種類のうち `secret-format` と `email` だけを掛ける関数で行う。人が貼ったマシンのパスでは止めない（TEXT-7 は事業データと認証情報の形を挙げる）。見つけたときの扱い（着手せずに停止中（`brief-sensitive`）。安全の軸に入れない）は呼ぶ側が決める
- AI に渡す欄の文には、漏えいの検査を掛けない（AI に渡す前に掛けるのは検疫。「[AI のセッション][b03]」の「起動の前の確かめ」の順 7）。漏えいの検査は GitHub に書く文と、受け入れの依頼の結果のファイルの文の欄に掛ける

## 検査を通った文の型

`logic/text/checked.ts` に、検査を通った文だけが持てる型を 2 つ置く。どちらも TypeScript の名目の型（ほかの文字列から作れない形）にする。

| 型 | 通った検査 | 入れる所 |
| --- | --- | --- |
| `QuarantinedText` | 検疫 | AI に渡す欄（「[AI のセッション][b03]」の「起動の前の確かめ」の順 7、「渡し方の決まり」） |
| `CheckedText` | 検疫と漏えいの検査 | GitHub に書く文と、受け入れの依頼の結果のファイルの文の欄（「[AI のセッション][b03]」の「共通の決まり」、[IMPL-15][impl]） |

- `CheckedText` は、`QuarantinedText` としても渡せる。どちらの型も、作れるのはそれぞれ 1 つの関数だけにする
- `QuarantinedText` を作る関数は、検疫を掛け、何も見つからなければ値を返し、外れたときは検疫の結果を返す
- `CheckedText` を作る関数は、検疫と漏えいの検査の両方をいつも掛け（片方で見つけても、もう片方も掛ける）、どちらも何も見つからなければ値を返す。外れたときは、検疫の結果と漏えいの検査の結果を分けて、両方を持つ値を返す
- 呼ぶ側は、検疫の結果が 1 つでもあれば、文の出どころで `where` を決める。AI の文なら `text`（全体を止める。[ADR-20261024-005][adr-security] の決定 3）、人が push した差分（`manual-push` の差分を載せるコメント）なら `code`（作業の単位だけを止める。「[状態遷移と判定][b02]」の「push の手順」）。漏えいの検査の結果だけのときに `leak`（全体を止めない。[ADR-20261027-002][adr-leak] の決定 2）にする。`security` の印は 1 つだけ書き（`finding` は、検疫の種類の表の上の行ほど先）、攻撃の疑いのコメントの本文には、検疫と漏えいの検査の両方の種類と場所を書く。両方に当たったときに、全体の停止が漏えいの扱いに隠れないため
- コメントを組み立てる関数（`logic/text/comments.ts`）は、AI の文と人の文を `CheckedText` でだけ受け取る。AI に渡す欄を組み立てる関数（`logic/session/input.ts`）は、AI の文と人の文と PR の差分を `QuarantinedText` でだけ受け取る。検査を通していない文をコメントや欄に入れる書き方を、型の検査で止めるため（人の注意でなく仕組みで守る）
- 印の形と指摘の区切りの行の形を取り除く処理（「[印][d03]」の「AI の文から印の形を取り除く」）は、AI の文の検査の前に掛ける。取り除いた後の文を検査し、通ったものを `QuarantinedText` か `CheckedText` にする

## ハッシュ

`logic/text/hash.ts` は、「[AI のセッション][b03]」の「ハッシュの取り方」のとおりに、正規化と SHA-256 を行う。

- 正規化は、CR と CRLF を LF にし、行ごとに末尾の空白（空白・タブ）を除き、前と後ろの空の行を除く。Unicode の正規化はしない。見た目が同じでも文字が違えば、違う文として扱うため
- Issue の文のハッシュは、上の「検疫」の「掛ける文」の組み立てで作った題名・本文・コメントの本文（作成の順）を 1 つずつ正規化し、改行・NUL 文字・改行の 3 文字でつないでから取る

## コメントの組み立て

`logic/text/comments.ts` に、決まった見出しと固定の文を、言語（リポの設定の `conventions.language`）ごとの表で持つ。今の表は `ja` だけで、ほかの言語は固定の文を足すときに表に足す。表に無い言語ではコメントを組み立てられないので、点検の設定の組で fail にする（「[設定][b01]」の `conventions.language` の形を、表にある言語に限った）。

- コメントは、決まった部分（見出し、「AI が生成した」の 1 行、固定の文）と、`CheckedText` の文と、最後の印の行（`marker.ts` で組み立てたもの）をつないで作る
- 組み立てたコメントが 60,000 文字を超えたときの扱いは、「[AI のセッション][b03]」の「共通の決まり」と「レビューのコメントの形」のとおり。長さは、JavaScript の文字列の長さでなく Unicode の文字の数で数える。GitHub のコメントの上限を何で数えるか（文字の数か、UTF-16 の単位か、バイトか）は確かめていない（[実機で確かめた事実][facts] に無い）。導入と点検の実装（段階 3）で、上限を超える長さのコメントを書いて確かめ、文字の数と違えば数え方を直す
- `wait` の印を付けるコメント（「[1 回の実行の流れ][d08]」の工程 `wait-marker`）は、`hidden`（App から見えない依存の相手の数。「[印][d03]」の「欄の値の形」）が 1 以上のときだけ、決まった文「App から見えないリポにある先の依頼が <数> 件ある。進行 Bot は、見えない先の依頼が終わったかを読めないので、人が依存（blocked by）を外すか、先の依頼の Issue を当てる先のリポに移すまで待つ」を足す（<数> は `hidden` の値。[ADR-20261112-001][adr-wait-hidden] の決定 3）。見えない相手のリポと番号は、App から読めないので書かない

## 指摘の区切りの行と見出しの比べ方

`logic/text/findings.ts` は、指摘の区切りの行（`<!-- dap-finding … -->` と `<!-- dap-finding-end -->`。形は「[AI のセッション][b03]」の「レビューのコメントの形」）を組み立てて読み、指摘の ID を計算する。

- 見出しの正規化は、[ADR-20261019-001][adr-repeat] の決定 1 のとおり（NFKC、先頭の重要度の記号（🔴 🟡 🟢）と空白を除く、英字を小文字にする）。指摘の ID の計算と、🟢 を記録する Issue の題名の比べ方（「[状態遷移と判定][b02]」の「状態ごとの工程」のレビュー合格の (1)）は、同じ正規化の関数を使う。題名と見出しを比べるときは、どちらも正規化した後に、末尾の空白（空白・タブ）を除き、同じなら同じ見出しとする（[ADR-20261031-001][adr-follow-up-dup] が見出しの比べ方の前後の空白の扱いを詳細設計に任せた。前の空白は正規化で除いている。GitHub が題名の末尾の空白を残すかを確かめていないので、どちらでも同じ見出しと読む）。指摘の ID の計算は、末尾の空白を除かない（[ADR-20261019-001][adr-repeat] の決定 1 のまま）
- 区切りの行の欄は `<名前>=<値>` を空白 1 つで並べ、値の見出しとパスは `encodeURIComponent` の符号で書く（「[AI のセッション][b03]」の「レビューのコメントの形」）。読むときは、欄の名前の並びと値の形（ID は 16 進の 8 文字、確信度は 0〜100 の整数など）を確かめ、外れた行のあるコメントは読めないものとして扱う。パスの値は空（`path=`）を許す（ファイルに結びつかない指摘。「[AI のセッション][b03]」の「役ごとの出力契約」の `findings[].path`）

## 出力契約

`logic/text/contracts.ts` に、役と工程ごとの出力契約のスキーマを、表で 1 か所に持つ（「[AI のセッション][b03]」の「役ごとの出力契約」の表を写す）。

- スキーマの表は、キー、型、要るか、長さの上限（値は「[AI のセッション][b03]」の「役ごとの出力契約」の「共通の決まり」）を持つ。型は、文、文（1 行）、文の一覧、真偽、整数（範囲を添える：0 以上・0〜100）、決まった値、決まった値の一覧（重なりを許さない）、オブジェクト（欄ごとに名前と型を持つ。`counts`）、オブジェクトの一覧（要素のオブジェクトの型を持つ。`plan.steps`・`findings`・`responses`・`checks`・`results`）。要るかは、要る・あってもよい・条件つき（ほかの欄の値か、工程で要るか無いかが決まる）のどれか。条件つきの欄は、`stopReason` と `stopDetail`（`outcome` が `stopped` のときだけ要り、ほかのときは無い）、`pr.*`（実装で `done` のとき）、`responses`（修正で `done` のとき）、`checks`（`done` のとき）、`unconvergedReason`（`converged` が偽のとき）
- 出力契約の確かめの関数は、設定の確かめ（「[設定と記録][d02]」の「設定の表を 1 か所に持つ」）とは別に `contracts.ts` に持つ。設定はすべての項目が要り、条件つきの欄を持たないため。JSON スキーマのライブラリは使わない（「[導入と点検][b04]」の「依存」）
- 取り出し：`stream-json` の最後の `result` の行の `result` の文を、前後の空白を除いて読む。全体が 1 つのコードブロック（最初の行が `` ```json ``、最後の行が `` ``` ``）なら、区切りの行を外す。残りを JSON として解き、オブジェクトでなければ取り出せないとする
- 確かめ：表に無いキー、要る欄の欠け、条件つきの欄の欠けとあってはいけない欄、型の違い、整数でない数と範囲の外の数、オブジェクトの一覧の要素の型の違い、決まった値のほかの値、長さの上限を超えた欄を、問題の並びにして返す。`{"environmentError": …}` は、ほかの欄より先に見分け、ほかの欄と一緒なら取り出せないとする（「[AI のセッション][b03]」の「共通の決まり」）。問題が 1 つでもあれば、実行の失敗にする（「[AI のセッション][b03]」の「共通の決まり」）。問題には、キーの名前と問題の種類だけを書き、AI の文を写さない
- 役と工程ごとの追加の確かめ（渡した値（軸、通し番号の並び）を引数で受ける）：計画のレビューは、`verdict` が `fix` なら `findings` が 1 件以上、`ok` なら 0 件。修正は、`responses[].id` の集合が渡した通し番号の集合と同じ（欠けも余りも重なりも無い）。レビュー AI は、`axis` が渡した軸と同じで、`counts` の 3 つが `findings` の重要度ごとの件数と同じ。批評 AI は、`results[].id` の集合が渡した通し番号の集合と同じで、`counts` が `results[].severity` ごとの件数と同じ（どれも「[AI のセッション][b03]」の「役ごとの出力契約」）。外れたら、ほかの確かめと同じく問題の並びにして返す。[IMPL-18][impl] の 5 つの条件の (1) と (4)（「[AI のセッション][d07]」の `logic/session/conditions.ts`）は、出力契約の確かめの結果を読む
- オブジェクトの一覧は、件数の上限を持たない（件数の上限は文の一覧のもの）。`responses` と `results` は、渡した件数で決まる。大きすぎる出力は、`io/claude.ts` が受ける `stream-json` の 1 行の上限（「[外との境][d01]」の「claude の起こし方」）で読めなかった行になり、取り出せないとする。レビューのコメントが長すぎるときは、「[AI のセッション][b03]」の「レビューのコメントの形」の `review-too-long` で止まる
- 拒否は、`stream-json` の行のうち、`stop_reason` の欄が `refusal` の行が 1 つでもあれば拒否とする（広く取る）。見る欄は、`result` の行の `stop_reason`、`assistant` の行の `message.stop_reason`、`stream_event` の `message_delta` の `delta.stop_reason`。どの行に出るかを実機で確かめていない（[実機で確かめた事実][facts] に拒否の回の事実が無い）ので、1 つに決めない。導入と点検の実装（段階 3）で、拒否で止まった回の `stream-json` を記録して確かめる（「[AI のセッション][b03]」の「受付 AI」の拒否の箇条）。拒否と分けたら、`is_error` の真偽と、`result` の文が JSON として読めるかを問わず、出力契約を取り出さない（「[AI のセッション][b03]」の「役ごとの出力契約」の受付 AI）。拒否の見分けは本ファイルに置き、`flow/session/run.ts` が `stream-json` の行の並びを渡す
- 確かめを通った値の文の欄は、まだ AI の文なので、検査を通った文の型でない。次の AI に渡す前に検疫を通し（`QuarantinedText`）、GitHub に書く前に検疫と漏えいの検査を通す（`CheckedText`）

## 人が呼ぶ intake

![intake の 2 つの引数][fig-intake]

`flow/skill/intake.ts` は、「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」の順 1・3・8 を受け持つ。lock を取らず、`claude` を起こさず、秘密を読まず、手元の記録に書かない（[README][readme] の「入口ごとの import の範囲」）。

| `entry/intake.ts` の引数（Skill の引数） | すること |
| --- | --- |
| `quarantine`（「検疫」） | 標準入力で受けた Issue の文（題名・本文・コメントの並び。コメントは、本文と、投稿者（REST の `login` の形）と、編集されたか（GraphQL の `lastEditedAt` があるか）を持つ。JSON）から、進行 Bot のコメントを除いて `logic/text/quarantine.ts` に通し、結果（無し、または見つかった種類と場所）と、除いたコメントの数を JSON で返す。除くのは、投稿者が `status.json` の `safety.botAccounts`（進行 Bot が base ブランチの先端のリポの設定から最後に読んだ値）のどれかで、編集されておらず、本文の印の形がちょうど 1 つで「[印][d03]」の書く形と欄の値の形（「読み方」の順 3〜5）に合うコメントだけ。署名は確かめない（人の Skill は鍵を読まない）。`status.json` が無いか、欄が無いか、形に合わなければ、除かずに通す（進行 Bot のコメントの印で見つかったと返り、`/verify-issue` が止まる側に倒れる）。当てる先のリポの owner と名前は、マシンの設定から読む。GitHub を読まない（Issue の文は、呼ぶ側の `/verify-issue` が読んで渡す） |
| `draft <Issue の番号>`（「下書き」の最初） | lock と、待つ時間の内の受け入れの依頼を見る。lock があれば、依頼を置かずに、実行の最中か、前の実行が落ちて lock が残っているかのどちらかであることと、lock の起動の時刻を示す。続けて、前の実行が落ちて lock が残っているときは、`check` を呼ぶと定期の実行と同じジョブが起き、持ち主の無い lock を奪って片付けることも示す（人の Skill は lock が古いかを見分けないので、どちらのときも示す。「[1 回の実行の流れ][d08]」の「人が呼ぶ /dev-autopilot」と同じ文）。lock の中身を読めなければ、依頼を置かずに、壊れた lock であることと戻し方（「[設定と記録][d02]」の「lock」）を示す（`check` の案内は出さない）。待つ時間の内の受け入れの依頼があれば、置かずに、ほかの依頼を待っていることを示す。置けるときだけ、依頼の ID と、依頼を置くコマンドの文（`node` の 1 行で、書く先のパスと中身（Issue の番号・依頼の ID・置いた時刻・待つ時間）を引数に置く。「[点検][d04]」の「人が呼ぶ check」と同じ形）と、ジョブを起こすコマンドの文（`launchctl kickstart`、`-k` なし）を返す。待つ時間は、`status.json` のリポの設定の値の `run.intakeWaitMinutes` から読み、無いか形に合わなければ設定の表の初期値（60 分）を使う。Skill は、置くコマンドを人の許可を得て sandbox の外で、起こすコマンドを sandbox の中で動かす |
| `wait <依頼の ID>`（「下書き」の待ち） | sandbox の中で、1 回の呼び出しで最大 60 秒、5 秒ごとに `intake-result-<依頼の ID>.json` を見る（「[点検][d04]」の「人が呼ぶ check」の `wait` と同じ上限。Bash の道具の 1 回の時間の上限に収めるため）。結果があれば、形を確かめて、下書きと費用か理由と、結果のファイルを消すコマンドの文（書く先のパスが見える `node` の 1 行）を返す。結果が無く、同じ ID の依頼のファイルがあり、そこに書いた置いた時刻から待つ時間を過ぎていなければ、「まだ」を返し、Skill は `wait` をもう一度呼ぶ。待つ時間を過ぎたか、結果も依頼のファイルも無ければ（進行 Bot が待つ時間を過ぎた依頼を消した）、実行中か（lock を見る）、ジョブが起きなかったか（定期の実行の登録と `launchd.err.log`）を示して終わる（「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」の順 8） |

- マシンの設定・lock・`status.json` は、`flow/skill/context.ts` で読む（受け持ちとテストは「[設定と記録][d02]」の「ファイルの一覧」と「テスト」）。lock があるときと、lock の中身を読めないときに示す決まった文は、`logic/text/comments.ts` の 1 つの文を、`/dev-autopilot`・`check`・intake の Skill で使う
- `quarantine` は、入力の形（題名・本文・コメントの並び。コメントは本文・投稿者・編集されたか）が違えば、検疫をせずに形が違うことを返す。通ったと返さない

| `policy`・`policyReason` | 真偽・文（1 行） | `draft` のときだけ（`policyReason` も `CheckedText`） |
| `findings` | オブジェクトの一覧（`where`・`kind`・場所） | `found` のときだけ。`where` は `entry`（Issue の文。受け入れの依頼の実行の順 5（進行 Bot が Issue の文を読んで掛ける検疫。「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」）か、起動の前の確かめの順 7（受付 AI に渡す前の検疫））・`text`（返した文の欄の検疫）・`leak`（返した文の欄の漏えいの検査）。`kind` は上の検疫と漏えいの検査の種類の記号。場所は上の「結果の形」の場所。見つかった文の中身は書かない |
| `reason` | 記号 | `not-run` と `no-draft` のときだけ。`not-run` は次の閉じた一覧のどれか：実行を途中で止めた終わり方（「[1 回の実行の流れ][d08]」の「終わり方と終了コード」の記号）の `records-cut`・`stop-signal`・`signal-unreadable`・`settings-unreadable`・`check-failed`・`crashed`（`crashed` は受付 AI を起動する前の思わない失敗に限る）、`halt-issue`（全体の停止の Issue の止める間。読めなかったときと、開き直しの条件に当たる作業の単位があるときと、見つかりの記録があるとき（[ADR-20261111-001][adr-keep-halt] の決定 1。受け入れの依頼の実行は、記録を書き直さず、消さない）を含む。「[点検][d04]」の「結果の形」の `unverified` の `halt-issue` と同じ）、`overlap`（ほかの依頼と重なった。「[AI のセッション][b03]」の「人の Skill から受け入れを呼ぶ形」の表の下）、`not-started`（起動の前の確かめに外れた）、`prepare-failed`（セッションの準備に失敗した）。受付 AI のセッションが起動の前の確かめの順 1 で外れたときは、合図なら `stop-signal`・`signal-unreadable`、全体の停止の Issue なら `halt-issue` を書く（1 回の実行の流れの順 3（全体の止める合図を読む）・順 4（全体の停止の Issue を読む）で止まったときと同じ記号。人に示す文を同じにするため）。順 2〜9 で外れたときは `not-started` と `preflightStep`。`machine-unsafe` は書かない（起動の前の確かめの順 5・6・9 で起きるので、`not-started` と `preflightStep` で書く）。`no-draft` は、「[AI のセッション][d07]」の終わり方の記号のうち `done` と `not-stopped` のほかと、起動した後の思わない失敗の `crashed` |
| `preflightStep` | 2〜9 の整数（起動の前の確かめの順 1 で外れたときは `not-started` を書かない。上の `reason` の行） | `reason` が `not-started` のときだけ。外れた起動の前の確かめの順 |
| `securityPending` | 記号：`written`・`not-written` | `outcome` が `found` で、`findings` に `where` が `text` の見つかりがあるときだけ。見つかりの記録（「[設定と記録][d02]」の「見つかりの記録」）を書けたか。`not-written` は記録の置き場に書けなかった（[ADR-20261112-003][adr-intake-finding] の決定 3） |
| `costUsd` | 0 以上の数 | 受付 AI を起こしたときだけ（終わりの行と同じ数え方） |
| `leftovers` | オブジェクトの一覧（`pid`・`command`・`folder`） | `not-stopped` のときだけ。残ったプロセスの PID とコマンドの名前とフォルダ（「[AI のセッション][b03]」の「止める手順」の順 5） |

- 欄の形は、`logic/run/requests.ts`（「[設定と記録][d02]」の「依頼と結果のファイル」）が、本節の表を写して持つ（`reason` の値の一覧も写す）。`flow/skill/intake.ts` は、読むときに形を確かめ、形が違えば結果が無いものとして扱う
- 条件つきの欄は、`outcome` で要るか無いかが決まる（`securityPending` は、`outcome` と `findings` の `where` で決まる）。表に無い欄と、`outcome` に合わない欄があれば、形が違うとする
- `reason` が `halt-issue` のとき、Skill が示す文は、「[点検][d04]」の「結果の形」の表の下の `halt-issue` の決まった文と同じにする（GitHub に全体の停止の Issue が無くても止める間がありうること、どれに当たるかを `/dev-autopilot` の状態の表示で見ること、開き直しの条件に当たる作業の単位だけのときは、順 6〜9 に進む次の実行が開き直すまで待つこと）
- `securityPending` があるとき、Skill は、見つかった種類と場所に続けて、`logic/text/comments.ts` の決まった文を示す（[ADR-20261112-003][adr-intake-finding] の決定 3）。`written` なら「受付 AI の下書きが検疫に当たったので、進行 Bot は見つかりの記録を書いた。次の実行から、どの作業の単位でも AI のセッションを起こさない。作業の単位を進める次の実行（定期の実行か、`/dev-autopilot` の手動の 1 回実行）が、Issue に `security` の印を書き、全体の停止の Issue を開く。全体の停止の Issue が開いたら、見つけた Issue とほかの作業を確かめ、maintain 以上の人が `## 安全の確認` を書いて、全体の停止の Issue を閉じる」。`not-written` なら「受付 AI の下書きが検疫に当たったが、記録の置き場が異常で、見つかりの記録を書けなかった。次の実行から全体が止まるとは限らない。全体の止める合図（リポの変数）を `stop` にするかを、人が決める」
