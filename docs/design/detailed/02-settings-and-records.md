# 設定と記録

設定の読み込みと確かめ、手元の記録、lock、依頼と結果のファイル、`status.json` の作りを決める。
判断の層（`logic/settings/`・`logic/run/`）が形と判定を持ち、流れの層（`flow/run/`）が外との境（[外との境][d01]）を通して読み書きする（[README][readme] の「層と依存の向き」）。

## 設定の表を 1 か所に持つ

![設定の表を 1 か所に持つ][fig-table]

リポの設定とマシンの設定の項目を、`logic/settings/repo.ts` と `logic/settings/machine.ts` の表に 1 回だけ書く。表の 1 行は、次の欄を持つ。

| 欄 | 中身 |
| --- | --- |
| キー | ドットで区切った名前（`run.commandMinutes`、`safety.sandbox.denyRead` など） |
| 形 | 文字列、整数、数、真偽、選択肢、文字列の一覧、対応表（キーと値の形を持つ）、オブジェクト（欄ごとに名前と形を持つ。欄の形も同じ語で書く）、オブジェクトの一覧（要素のオブジェクトの形を持つ） |
| 範囲 | 最小と最大、選んでよい値、空を許すか、`null` を許すか（書かなければ許さない）、文字列の形（パターン） |
| 初期値 | 「[設定][b01]」の表の初期値。要件が決めた初期値は要件の写し（[ADR-20261018-005][adr-table]）。当てる先のリポに依る値（許可一覧と方針のパス）は持たない |
| 置き場 | リポの設定かマシンの設定か |

- 「[設定][b01]」の書き方は、次の形で表に書く：`githubApp.appId`・`githubApp.installationId` は整数（1 以上）で `null` を許す。`githubApp.setupClientId`・`program.previousVersion` は文字列で `null` を許す。`checks.required` はオブジェクトの一覧（`name` は文字列、`app` は文字列、`workflow` は文字列で `null` を許す）で、空を許さない。`labels.branchTypes` はオブジェクトの一覧（`label` は文字列、`type` は選択肢）。`project.fields.*` はオブジェクト（`id` は文字列、`options` は値が文字列の対応表）。`models.*` はオブジェクト（`model` と `effort` は文字列）
- TypeScript の型は、`null` を許す欄を `<型> | null` にする

同じ表から、次の 3 つを作る。表と別に、型やスキーマのファイルを手で書かない。

| 作るもの | 使う所 |
| --- | --- |
| 値を確かめる処理（`logic/settings/schema.ts`） | 進行 Bot の 1 回の実行の流れの順 1 と順 4、点検の設定の組（`04-check.md`） |
| TypeScript の型（表から型を写す） | 設定を読むすべての処理 |
| 初期の設定ファイル | `setup` がリポの設定の PR とマシンの設定を作るとき（`05-setup.md`） |

- 確かめる処理は、外の部品（JSON スキーマのライブラリ）を使わずに `plugin/src/` の中に書く（「[導入と点検][b04]」の「依存」）
- 確かめた結果は、問題の一覧で返す。問題は、キーと種類（無い、形が違う、範囲の外、表に無いキー、重なったキー、置き場が違う、絶対パス、関係が崩れている）と、期待した形を持つ
- すべての項目が要る（無いキーは問題）。表に無いキーも問題にする（綴りの誤りで、足したつもりの守りが黙って効かない形を止める。「[設定][b01]」の「`check` が設定について確かめること」）。オブジェクトの中の欄も同じく、表に無い欄は「表に無いキー」、無い欄は「無い」にする（`null` を許す欄は、`null` を書けば「無い」にしない）
- 同じオブジェクトの中に同じキーが 2 つ以上あれば、「重なったキー」の問題にする（`JSON.parse` は後ろのキーの値を黙って採るので、人が読む値と進行 Bot が使う値が分かれるため）。`logic/settings/schema.ts` に、`JSON.parse` で読めた文字列を先頭から走査して、オブジェクトごとにキーの重なりを探す関数を置く。キーは、エスケープを解いた後の文字列で比べる（`"denyRead"` と `"deny\u0052ead"` は同じキー）。問題のキーは、重なったキーのドットで区切った名前（`safety.sandbox.denyRead` など）で返す。マシンの設定とリポの設定の両方に掛ける
- リポの設定の値に、絶対パス（`/` で始まる値と `~` で始まる値）が無いことを確かめる。安全設定の足す分は `${home}` か `${worktree}` で始めて書く（「[AI のセッション][b03]」の「リポの設定に書く足す分」）
- 項目どうしの関係は、`logic/settings/relations.ts` が、表で確かめた後の値で確かめる
- 短い一時フォルダの長さ（`<sessionTmp.root の実体のパス>/<sessionTmp.idLength の文字数>/claude-<uid>` のバイト数が `sessionTmp.maxBytes` 以内か。「[設定][b01]」の「`check` が設定について確かめること」）は、根の実体のパス（macOS の `/tmp` は `/private/tmp`）と uid が要り、設定の値だけでは決まらないので、順 1・4 の確かめでは数えない。数えるのは、点検のマシンの組（根が無ければ権限 700 で作った後に、`io/files.ts` の「実体のパス」で根の実体のパスを取り、システムの `uid` を渡す）と、起動の前の確かめの順 6（短い一時フォルダがまだ無く長さが上限の内かの確かめ。作るフォルダの実体のパスを渡す）で、どちらも `relations.ts` の同じ関数（`<渡したパス>/claude-<uid>` の UTF-8 のバイト数を返す）を使う。`sessionTmp.maxBytes` が 44 以下であることは、表の範囲（1〜44）で順 1 に確かめる
- 問題を fail と warn に分けるのは点検（`04-check.md`）。進行 Bot の順 1・4 では、問題が 1 つでもあれば作業に入らず止まる（[SAFE-4][safety]）

## 設定を読む順

`flow/run/settings.ts` は、1 回の実行の流れの順 1 と順 4 で、次の順に読む（「[状態遷移と判定][b02]」の「1 回の実行の流れ」）。

| 順 | 読むもの | 読み方 | 読めないか、問題があるとき |
| --- | --- | --- | --- |
| 1 | マシンの設定 | 定期の実行の定義が渡したパスの `settings.json` を、`io/files.ts` で読む。読めた JSON を、表で確かめる前に重なったキーの走査に通す | 作業に入らず止まる（終わり方は `machine-settings-unreadable`。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）。記録の置き場が分からないので、`runs.jsonl` に書かず、点検の依頼があっても結果を書けない |
| 4 | リポの設定 | 進行 Bot の clone で fetch した base ブランチの先端の SHA から、`git show <SHA>:.claude/dev-autopilot.json` を `io/git.ts` の読み取りで読む。読めた JSON を、表で確かめる前に重なったキーの走査に通す | 作業に入らず止まる。点検の依頼があれば、fail として結果に書く |

- 読んだ値は、1 回の実行の間変えない。深く凍らせた値（`Object.freeze` を中までかけたもの）にして渡す（[ADR-20261017-007][adr-stop] の決定 4）。リポの設定は、読んだ base ブランチの SHA と組で持ち、`runs.jsonl` に SHA を書く
- リポの設定を読む前に要る値（子プロセスの時間の上限と猶予）は、`logic/settings/fixed.ts` から読む

| --- | --- | --- |

## パスの照らし

`logic/settings/paths.ts` は、パスの一覧（`merge.allowPaths`・`merge.policyPaths`・`protectedPaths.*`・名指しのパス・`## 仕組みの変更の承認` に書かれたパス）とパスを照らす。

- 照らしは、git の pathspec の `:(glob)` と同じ当たり方を TypeScript で書く。計画が変える見込みのパス（`plan.paths`）は、まだリポに無いファイルの名前を含み、git のコマンドでは照らせないため。push の前の差分も、変わったパスの一覧を `git diff --name-only -z` で受け取り、同じ照らしで見る（照らし方を 1 つにする）
- 当たり方：`*` は `/` を越えない。`**/` は 0 個以上のフォルダに当たる。`/**` はフォルダの中のすべてに当たる。`.` で始まる名前にも `*` が当たる（「[設定][b01]」の「検査と判定」）。ワイルドカード（`*`）を含まないパスは、書いたパスと、書いたパスをフォルダとした中のすべてに当たる（`dev-autopilot` は `dev-autopilot/x/y.ts` に当たり、`CLAUDE.md` は `CLAUDE.mdx` に当たらない。FACT-133）
- 書いてよい形：パスの一覧の値は、`*`・`**/`・`/**` と文字どおりの名前だけで書く。`?`・`[`・`]`・`\` を含む値、`:` で始まる値（git の magic）、`/` で区切った部分の中で `**` をほかの文字とつなげた値（`**.md`・`a**`）、先頭の `/`、`.` か `..` だけの部分を持つ値は、形に外れるとする。`logic/settings/paths.ts` に形の確かめの関数を置く。設定の確かめ（`merge.allowPaths`・`merge.policyPaths`・`protectedPaths.*`）は、形に外れる値を「範囲の外」の問題にする。`## 仕組みの変更の承認` に書かれたパスで形に外れるものは、認めなかったものとして扱う（止める側）。照らす関数は、形に外れる一覧の値を受け取らない。git と当たり方が分かれやすい書き方を、当たらないまま通さずに止めるため（FACT-133）
- 大文字と小文字は、呼ぶ側が選ぶ。止める側の一覧は区別せず（`:(glob,icase)` と同じ）、許す側の一覧は区別する（`:(glob)` と同じ）。選び方は「[設定][b01]」の「検査と判定」のとおりで、照らす関数は区別するかを引数で必ず受け、既定の値を持たない（書き忘れで許す側に倒れないため）
- 前提データ（`fixtures/paths/`）に、例ごとにパス・書き方・大文字と小文字を区別するか・当たるかを置く。「当たるか」は、本物の git の pathspec で確かめた結果を書く：例のパスを commit した使い捨てのリポで、`git ls-files -- ':(glob)<書き方>'`（区別しないときは `:(glob,icase)`）を動かした結果（作り方は前提データの README に書く）。単体テストは前提データと照らし、git と当たり方が違えば落ちる
- 前提データに必ず入れる例：`*` が `/` を越えないこと（`.changeset/*.md` と `.changeset/a/b.md`、`docs/*` と `docs/a/b.md`）、`**/` が 0 個以上のフォルダに当たること（`**/CLAUDE.local.md` と、根の `CLAUDE.local.md`・`a/b/CLAUDE.local.md`）、`/**` が中のすべてに当たること、`.` で始まる名前に `*` が当たること、ワイルドカードの無いパスのフォルダとしての当たり方（`dev-autopilot` と `dev-autopilot/x/y.ts`、`CLAUDE.md` と `CLAUDE.mdx`）、大文字と小文字を変えた例（止める側の一覧で当たり、許す側の一覧で当たらない）
- 基本設計の「git の pathspec で照らす」は、git の pathspec と同じ当たり方で照らす、と読む

## 手元の記録

記録の置き場のファイル（「[状態遷移と判定][b02]」の「手元の記録」）の行の形を、`logic/run/records.ts` に TypeScript の型で持つ。

| ファイル | 行の種類 |
| --- | --- |
| `runs.jsonl` | 1 回の実行の行（1 種類） |
| `sessions.jsonl` | 一時フォルダの行・始まりの行・プロセスの行・終わりの行（`kind` の欄が `tmp`・`start`・`pid`・`end`） |
| `writes/<実行 ID>.jsonl` | GitHub に書いた 1 件の行。書く先、種類、本文か値、結果（書いた、HTTP の状態で断られた、届いたか分からない（時間の上限で取り消した、つながらない、GraphQL の誤り）） |
| `streams/<実行 ID>/<セッションの名前>.jsonl` | `claude` の `stream-json` の行を、受け取ったとおりに（形を確かめない） |
| `security-pending/<作業の単位の Issue の番号>-<実行 ID>.json` | 見つかりの記録 1 件（JSON の 1 つのオブジェクト。下の「見つかりの記録」） |

- どの行にも、形の版（`v`。今は 1）を書く。行の形は、欄を足すことでだけ変え、`v` は上げない。前の版が必ず読む欄は消さず、意味も変えずに書き続ける（意味を変えたいときは、新しい名前の欄を足す）。読む側は、知らない欄を読み飛ばす。足した欄は、前の版が書いた行に無くても読めるように、無いときの読み方を足した版が決める（数え上げが少なく出ない側にする）。`setup rollback` で前の版に戻しても、前の版が新しい版の行を読め、新しい版も前の版の行を読めるようにするため（「[導入と点検][b04]」の「プログラムの写し」。`rollback` は記録に触れない）。動かすマシンを替えて記録を写したときにも読める
- 書き方：`io/files.ts` の「1 行を足す」で、1 行を改行で終えて足し、ディスクへ書き出す。「1 行を足す」は、ファイルが改行で終わっていなければ（切れた行がある）、書かずに失敗を返す（下の「切れた行の後には足さない」）。`streams/` の行の足し方は、[外との境][d01]の「claude の起こし方」
- 読み方：ファイルの中身を改行で分ける。改行で終わっていない最後の断片は「切れた行」として読まず、点検を fail にする。結果の `details` には、ファイルのパスと、最後の改行の後のバイトの位置と、断片の長さを書き、断片の中身は書かない。改行で終わる行で、JSON として読めないか、形が違う行（`v` が 1 でない、種類ごとの必ずある欄が無いか形が違う。知らない欄があることは形の違いにしない）は「読めない行」として読まず、点検を fail にする（数え上げが少なく出て、上限が効かなくなる側に倒さない。「[状態遷移と判定][b02]」の「手元の記録」）
- 切れた行の後には足さない：断片の後に足すと、断片と新しい行が 1 行につながって読めない行になり、点検が fail のまま戻れないため。`flow/run/records.ts` は、lock を取った直後（「[状態遷移と判定][b02]」の「1 回の実行の流れ」の順 2 の最初）に、`runs.jsonl` と `sessions.jsonl` が改行で終わっているかを読む。どちらかに切れた行があれば、前の実行が残したセッションを止める手順（記録に足す前にできる）だけを行い、終わりの行は書かずに（次の実行が、終わりの行の無いセッションとしてもう一度見つける）、作業に入らず止める。終わり方は `records-cut`（終了コード 1。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）。`runs.jsonl` に足せなければ、順 1 でマシンの設定を読めないときと同じく、標準エラーに 1 行（ファイルのパスと断片の位置と長さ）を書く（`flow/run/run.ts` が返し、`main.ts` が書く。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）。点検の依頼があれば、記録の項目を fail として結果のファイルに書く（結果のファイルは別のファイルなので書ける）。lock を取らない実行（lock で見送った実行）は、「1 行を足す」が失敗を返したら、標準エラーに同じ 1 行を書き（同じく `flow/run/run.ts` が返し、`main.ts` が書く）、終了コード 1 で終える
- 切れた行の戻し方：人が、進行 Bot の実行と `setup` が動いていないときに、点検が示したファイルの、最後の改行より後ろ（断片）だけを消す。前の行は消さず、書き換えない。点検の結果には、消すコマンドの文（`node` の 1 行で、`fs.truncateSync` にパスと、最後の改行の後のバイトの位置を渡す）を示す。断片は書いている途中で切れた 1 件の記録で、読めないので、消しても読める行は減らない。切れた行の後には何も足さないので、示した位置は人が消すまで変わらない
- `runs.jsonl` の行は、基本設計の欄に加えて、詳細設計で決めた次の値を持つ
  - 終わり方の記号（「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）
  - 作業の単位の結果の、思わない失敗のときの例外の種類と工程の記号（例外の文は書かない。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）
  - GitHub を読めずに止めた（`github-unreadable`）ときは、読めなかった作業の単位の Issue と PR の番号（作業の単位の Issue を見分け方で読めなかったときを含む。「[状態遷移と判定][b02]」の「状態の組み立て」）
  - `settings-tampered` で返ったセッションごとの、セッションの名前と安全設定のファイルの 2 つのハッシュ（作ったときと、起動の直前かセッションの後に読み直したとき。役を問わない。「[1 回の実行の流れ][d08]」の「1 回の実行の中で持つ値」の「安全設定を書き換えられたセッション」）
  - 点検を行った実行では、行った点検ごと（順 5（点検を回す）と順 10（実行の終わりに点検の依頼を見る））の sandbox の組の結果（`pass`・`warn`・`fail`。試しを省いたときは省いて使った前の結果）を、行った順に並べる。「[点検][d04]」の「試しのセッションを省く判定」が、後に行った点検の結果を前の結果として読む
  - 見つかりの記録を書き直した結果（「[1 回の実行の流れ][d08]」の「全体の停止と通知」の「見つかりの記録から印を書き直す」の行。見つけた実行で記録を消せなかったときも書く）。値の形は、記録のファイルの名前ごとに次の欄を持つ（本箇条を正本にし、`RunContext` と点検の `details` は指す）
    - 結果：消した・残した・消せなかった（両方の印を書けたのに記録を消せなかった）
    - 残したときは、何を（`security` の印・`halt` の印・Issue の読み取り）と、理由（HTTP の状態（断られた。状態の番号）・応答が無い（時間の上限で取り消した、つながらない。書き込みでは届いたか分からない）・合図が `run` でない）の 2 つの欄
    - 消せなかったときは、`io/files.ts` の「ファイルを消す」の失敗の種類
    - 点検が、記録ごとに書き直せなかった回数（「残した」の数）と、消せなかったことを読む（下の「見つかりの記録」）
- 出力契約（`outputs/<実行 ID>/<セッションの名前>.json`）は、`io/files.ts` の「新しく書く」で書き、書き直さない
- 記録には、秘密の値（JWT・トークン・Webhook の URL）と、渡す文と AI の文のほかの外から入る文の写しを、決まった欄のほかに書かない。`writes/` の本文は、検疫と漏えいの検査を通った後の文（GitHub に書いたもの）だけ

### 見つかりの記録

AI が書いた文の検疫で見つけたこと（`security` の印の `where` が `text`）を、GitHub に印を書けたと分かるまで手元に残す記録（[ADR-20261111-001][adr-halt-records]）。記録が「ある」か「読めない」間は、全体の停止の Issue があるものとして扱い、AI のセッションを起こさない。
ファイルの名前と中身の欄、読み方、人の戻し方の正本は「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」の表と表の下、書く時・書き直す時・消す時の正本は同じ文書の「全体の停止の Issue」の「見つかりの記録」にある。本節は、受け持つモジュールと、関数と、読んだ結果の形を決める。

- 受け持ち：`security-pending/` のファイルを `io/files.ts` で書く・読む・消すのは `flow/run/records.ts` だけ。形の確かめ、名前から作業の単位の Issue の番号を読むこと、読んだ結果（ある・無い・読めない）の決め方、書き直せなかった回数の数え方は `logic/run/records.ts`。呼ぶのは、読む（順 2）が `flow/safety/signal.ts`、書く（見つけた実行）と消す（見つけた実行と書き直し）が `flow/safety/suspect.ts`、点検が `flow/check/machine.ts`（順 2 と同じ読む関数を呼ぶ）、順 10 で `status.json` を書く前の読み直しが `flow/run/status.ts`（同じ読む関数を呼ぶ。下の「status.json」）。書く順と書き直しの順は「[1 回の実行の流れ][d08]」の「全体の停止と通知」
- 名前：`<作業の単位の Issue の番号>-<実行 ID>.json`。一時のファイルは `<作業の単位の Issue の番号>-<実行 ID>.json.new-<自分の PID>`（`io/files.ts` の「排他の作成」の形。「[外との境][d01]」の「ファイル」）
- 中身：「[状態遷移と判定][b02]」の表の欄を、1 つの JSON のオブジェクトにする。形の確かめでは、`v` が 1 で、`where` が `text` で、見つかった文を持つ欄が無いことを見る（見つかった文と AI が書いた文は書かない。`security` の印のコメントと同じ）
- 書き方：`flow/run/records.ts` の書く関数は、フォルダが無ければ `io/files.ts` の「フォルダを作る」（権限 700）で作り、`io/files.ts` の「排他の作成」（権限 600）で書く。書いている途中で落ちても、中身が半分のファイルを残さないため（[ADR-20261111-001][adr-halt-records] の決定 3 の「排他と一時のファイル」）。同じ名前のファイルがあれば（同じ実行で同じ作業の単位に 2 回目）、書いたものとして返す。書けなければ失敗を返し、呼ぶ側（`flow/safety/suspect.ts`）が実行を終える理由を `machine-unsafe` にする（「[1 回の実行の流れ][d08]」の「全体の停止と通知」の「攻撃の疑いにする」の行）
- 書かないとき：漏えいの検査で見つけたとき（`where` が `leak`）と、PR の差分で見つけたとき（`where` が `code`）は、全体を止めないので書かない（[ADR-20261027-002][adr-leak]）。受け入れの依頼の実行で、受付 AI の下書きが検疫に当たったときも、今は書かない（結果のファイルに書く。要件の UNDECIDED-98 で決めるまでの扱い。「[状態遷移と判定][b02]」の「全体の停止の Issue」の「見つかりの記録」）
- 読み方：`flow/run/records.ts` の読む関数は、フォルダを一覧にしてファイルを読み、`logic/run/records.ts` が読んだ結果を次の 3 つで決める
  - 無い：フォルダが無いか空
  - ある：どのファイルも、名前が `<作業の単位の Issue の番号>-<実行 ID>.json` の形で、中身の形が合う
  - 読めない：フォルダかファイルを読めない、中身の形が合わない、名前が形と違う（一時のファイルを含む。読み飛ばさない）ファイルが 1 つでもある（止める側）
  - 返す値は、読んだ結果と、読めた記録の並びと、読めないファイルごとの名前と、名前の頭から最初の `-` までの数字で読めた作業の単位の Issue の番号（読めなければ無し）。フォルダを読めないときは、フォルダのパス。「ある」か「読めない」なら、呼ぶ側が `RunContext` の全体の停止の Issue を「ある」にする（実行の中で「無い」に戻さない）。「読めない」ときも、点検の `machine.security-pending` は `warn`（`unreadable`）で、AI のセッションだけを起こさず、作業には入る（AI を使わない工程と、読める記録の書き直しは続ける。[SETUP-2][setup] の fail に当てない）。読めない記録は、書き直す中身が分からないので、進行 Bot は書き直さず、消さない。名前から作業の単位の Issue の番号を読めた読めない記録は、その作業の単位を、呼ぶ側がその実行の組 1〜4 から外す（AI を使わない工程も進めない。「[1 回の実行の流れ][d08]」の「作業の単位の進め方」）
- 消し方：`flow/run/records.ts` の消す関数は、`io/files.ts` の「ファイルを消す」で、渡された名前のファイルだけを消す。消せなければ失敗を返し、呼ぶ側（`flow/safety/suspect.ts`）が、書き直した結果を「消せなかった」にして、実行を終える理由を `machine-unsafe` にする（記録は残り、次の実行が書き直す。「[1 回の実行の流れ][d08]」の「全体の停止と通知」）。消す時（作業の単位の Issue の `security` の印と `halt` の印の両方を書けたとき。書き込みの応答で書けたと分かったときで、読み戻さない）と、書き直して消すのが順 6〜9 に進む実行だけであることは、「[状態遷移と判定][b02]」の「全体の停止の Issue」の「見つかりの記録」
- 書き直せなかった回数：`logic/run/records.ts` は、`runs.jsonl` の行のうち、見つけた時刻より後に、記録のファイルの名前を「残した」と書いた行（上の `runs.jsonl` の行の「見つかりの記録を書き直した結果」）を数え、記録ごとの回数と、最後の時刻と、最後の何をと理由を返す。記録ごとの最後の結果（残した・消せなかった）も返す。「消せなかった」は回数に数えない。点検は、最後の結果が「残した」の記録があれば `rewrite-failed` にし、最後の結果が「消せなかった」の記録は、回数に依らず `pending` の「消せなかった」に出す（「[点検][d04]」の「ファイルの一覧」の表の下）。順 10 の点検では、`RunContext` の今の実行の見つかりの記録を書き直した結果も合わせて数える（今の実行の行はまだ書いていないため。「[1 回の実行の流れ][d08]」の「起こされ方と進む順」）。点検が `warn`（`rewrite-failed`）に出す（「[点検][d04]」の「ファイルの一覧」の表の下）
- 見つかりの記録は止める側にだけ使う。作業の単位の状態、安全の軸の値、全体の停止の解き方は、GitHub の印だけで決め、記録が無いことを全体の停止を解く理由にしない（[ADR-20261111-001][adr-halt-records] の決定 3）
- 人に示す：点検の `machine.security-pending`（「[点検][d04]」の「ファイルの一覧」の表の下）と、`status.json` の「全体」の欄（下の「status.json」）に出す
- 人の戻し方：人が記録を消すのは、点検が `warn`（`unreadable`）にした読めない記録だけで、「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」の表の下の順で戻す。`warn`（`rewrite-failed`）のときは、人は記録を消さず、書き直せない原因を直す（原因を直しても書き直せないまま残り続けるときの人の戻し方は、要件の UNDECIDED-99 で決める。今は消さない。同じ表の下。読める記録を消すのは進行 Bot だけ。理由の種類は、点検の `details` と、後の実行の `runs.jsonl` の行の見つかりの記録を書き直した結果にある）。消せなかった記録（点検の `pending` の `details` に出る）は、人は記録を消さず、記録の置き場の `security-pending/` の権限と持ち主を直す。読めない記録の手がかりは、記録の置き場の `security-pending/` の中身（ファイルの名前と中身）と、名前に作業の単位の Issue の番号と実行 ID があれば、それで引く次のもの
  - `runs.jsonl` の同じ実行 ID の行（作業の単位の結果の、検疫で見つかった種類）。書く前に実行が切れたときは行が無い
  - `sessions.jsonl` の同じ実行 ID の始まりの行（Issue と PR の番号、役）
  - `outputs/<実行 ID>/` の出力契約（検疫に当たった AI の文がある。人が読むためだけに使う）

## 実行 ID と依頼の ID

`logic/run/ids.ts` は、実行 ID と依頼の ID を、UTC の時刻と乱数の組（`YYYYMMDDTHHMMSSZ-<16 進の 4 文字>`）で作る（「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」）。時刻と乱数は、流れの層が受けた `FlowSystem` の `now` と `randomBytes`（2 バイト）を渡す。形の確かめ（パスに入れても困らない文字だけか）も同じファイルに置く。

## lock

![lock が古いかの判定][fig-lock]

`run.lock` の中身は、PID・起動の時刻（lock を取ったプロセスの起動の時刻。エポック秒）・ホスト名（人が読むためだけ。`io/os.ts` の「ホスト名」で取る）の JSON（「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」）。

`logic/run/lock.ts` は、読んだ lock と、次の 2 つの事実から、持ち主が動いているか、古いか、見分けられないかを決める。

| 事実 | 取り方 |
| --- | --- |
| PID のプロセスがあるか | `io/processes.ts` の「プロセスがあるか」（ある・無い・分からない。[外との境][d01]、FACT-117） |
| PID のプロセスの起動の時刻 | `io/os.ts` の「プロセスの起動の時刻」（lock を書く側と同じ関数） |

| lock の中身 | PID のプロセス | 起動の時刻 | 判定 |
| --- | --- | --- | --- |
| 読めない（壊れている） | — | — | 見分けられない（奪わずに見送る） |
| 読めた | 無い（`ESRCH`） | — | 古い（奪う） |
| 読めた | ある | lock の起動の時刻と同じ | 持ち主が動いている（見送る） |
| 読めた | ある | lock の起動の時刻と違う | 古い（PID が使い回されている。奪う） |
| 読めた | ある | 取れない | 見分けられない（奪わずに見送る） |
| 読めた | 分からない | — | 見分けられない（奪わずに見送る） |

- 見分けられないときは奪わない（止める側。lock を持たないまま 2 つの実行が動く形にしない）。見分けられずに見送った実行は、持ち主が動いているときの見送り（`lock-skipped`。終了コード 0）と分けて、終わり方を `lock-unknown`（終了コード 1。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）にする。`runs.jsonl` に見送った行を書き、標準エラー（定期の実行の `launchd.err.log`）に 1 行（`run.lock` のパスと、見分けられなかった理由の種類：`unreadable`（中身を読めない）・`no-start-time`（起動の時刻を取れない）・`pid-unknown`（プロセスがあるか分からない））を書く（`flow/run/run.ts` が返し、`main.ts` が書く。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）。lock の中身は書かない。読めない lock は次の実行でも読めないので、人が気づいて戻すまで続くため
- 壊れた lock の戻し方：中身を読めない lock は、進行 Bot が奪わないので、人が戻す。人が呼ぶ Skill（`check`・`/dev-autopilot`・intake の下書き）は、`run.lock` の中身を `flow/skill/context.ts` から `logic/run/lock.ts` の「lock の中身の形」で読み、読めなければ「実行の最中」と示さず、`check` を呼べば片付くとも示さず（進行 Bot は読めない lock を奪わないため）、壊れた lock であることと、`run.lock` のパスと、次の戻し方を示す。戻し方：人が、進行 Bot の実行（写しの `main.ts` を動かす `node`）と `setup` のプロセスが無いことを `ps` で確かめてから、`run.lock` を消す。消した後の最初の実行が lock を取り、見送った実行を点検の warn に出す。`setup` も、lock を取れず中身を読めないときは、同じ文を示す（「[setup][d05]」の「マシンの準備の順」）
- 取り方・奪い方・戻し方の手順は「[状態遷移と判定][b02]」の「lock の取り方」のとおりで、`flow/run/lock.ts` が `io/files.ts` の「排他の作成」と「退ける」で行う。外すときと、退けたファイルを消すときは、`io/files.ts` の「ファイルを消す」で消す
- 外すときは、`run.lock` を読み直し、中身が自分の書いたものと同じときだけ消す。同じでなければ消さずに記録に残す（ほかのプロセスの lock を消さないため）

## 依頼と結果のファイル

`logic/run/requests.ts` に、依頼と結果のファイルの形を持つ（「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」）。

| ファイル | 欄 |
| --- | --- |
| `check-request.json` | 依頼の ID、置いた時刻、待つ時間（分） |
| `check-result-<依頼の ID>.json` | 依頼の ID、書いた時刻、点検の項目ごとの結果（形は `04-check.md`） |
| `run-request.json` | 依頼の ID、置いた時刻 |
| `intake-request.json` | Issue の番号、依頼の ID、置いた時刻、待つ時間（分） |
| `intake-result-<依頼の ID>.json` | 欄の表は「[文の検査と受け入れ][d06]」の「受け入れの結果のファイル」 |

- 待つ時間を過ぎたかは、置いた時刻と待つ時間と今の時刻から、`logic/run/requests.ts` が決める（今の時刻は引数で受ける）
- 進行 Bot は、依頼を読んだときの依頼の ID を持ち、消すときに読み直して ID が同じときだけ消す（「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」）。進行 Bot は、依頼と結果のファイルを `io/files.ts` の「ファイルを消す」で消す。人の Skill が返す消すコマンドの文（`node` の 1 行。「[点検][d04]」の「人が呼ぶ check」、「[文の検査と受け入れ][d06]」の「人が呼ぶ intake」）も、リンクをたどらず渡した名前のファイルだけを消す形（`fs.unlinkSync`）にする
- 進行 Bot が書く結果のファイルと `status.json` は、一時のファイル（`<名前>.new-<自分の PID>`）に書いて書き出してから、`rename` で名前を付ける。読む側（人の Skill）が書きかけのファイルを読まないため
- 7 日を過ぎた結果のファイルは、`flow/run/requests.ts` が実行の終わりに消す
- ファイルの中の値を読むときも、表と同じく形を確かめ、形が違えば依頼が無いものとして扱い、記録に残す（壊れた依頼で点検や受付 AI を起こさない）

| `logic/run/requests.ts`・`flow/run/requests.ts` | 待つ時間の判定。ID が違えば消さないこと。結果を一時のファイルから名前を付けて書くこと。7 日を過ぎた結果だけを消すこと。受け入れの結果のファイルの `reason` の値の一覧が、「[文の検査と受け入れ][d06]」の「受け入れの結果のファイル」の一覧と同じこと（期待値は 06 から写す）。`preflightStep` が 2〜9 の整数でないとき、`reason` が `not-started` でないのに `preflightStep` があるときは、形が違うとすること |
| `logic/run/status.ts`・`flow/run/status.ts` | 人の番の分け方。点検だけの実行と受け入れの依頼の実行で、点検の欄と、「全体」の欄と、リポの設定の値の欄と、書き直した実行の欄だけを入れ替えること。手動の依頼を見送ったときは見送った依頼の欄も入れ替えること。リポの設定を読めなかった定期の実行で、リポの設定の値の欄を前の `status.json` のまま残すこと。全体の合図（4 つの値）と、GitHub の全体の停止の Issue（4 つの値）と、止める間と、見つかりの記録（3 つの値）を書くこと。記録の切れた行で止まった実行で、合図と GitHub の全体の停止の Issue を「読んでいない」と書き、基線の欄を書かないこと。`github-unreadable` の実行で、「実行」の欄に読めなかった作業の単位の番号を書くこと。見つかりの記録があり、GitHub に全体の停止の Issue が無い定期の実行で、GitHub の全体の停止の Issue を「無い」、止める間を「ある」と書くこと。全体の停止の Issue の一覧を読めなかった実行で「読めない」と書くこと。順 3 で止まった実行で、GitHub の全体の停止の Issue を「読んでいない」と書くこと。見つかりの記録を順 10 で読み直した値で書くこと（見つけた実行で記録を書いた後は「ある」、書き直して消した後は「無い」）。読めない記録と読める記録が混じるとき、読めた記録の番号と時刻も書くこと。順 10 で点検の欄の `machine.security-pending` を決め直して入れ替えること（書き直して消した後に `pending` を残さないこと） |
| `flow/skill/context.ts` | 読めないマシンの設定・読めない lock・無い `status.json`・欄の無い `status.json` で、読めなかったことと理由の種類を決まった形で返すこと（示す文は呼ぶ Skill が決める）。待つ時間の欄が無いか型と範囲に合わなければ設定の表の初期値を返し、`safety.botAccounts` の欄が無ければ「無い」を返すこと。`flow/run/` を import しないことは構成の検査で確かめる |
