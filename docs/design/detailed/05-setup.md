# setup

人が呼ぶ `setup`（引数の `rollback`・`upgrade`・`uninstall` を含む）の作りを決める。setup の流れと、作るもの・確かめ方の正本は、基本設計の「[導入と点検][b04]」の「setup の流れ」から「動かすマシンを替えるとき」までと、「setup 用の App」「GitHub App を作る」にある。本書は、流れを人の Claude Code の上でどう動かすか（プロセスの分け方と、人とのやりとり）と、差分の一覧の作り方、準備の順を決める。

## ファイルの一覧

| --- | --- | --- | --- |

| `flow/setup/run.ts` | 流れ | setup の本体。下の「順」のとおりに進め、出来事を書き、答えを待つ | 同上 |

- 設定の表と、設定ファイルの足し引き（足りない項目を足し、表に無いキーを消す）は、`logic/settings/`（「[設定と記録][d02]」の「設定の表を 1 か所に持つ」）を使う

## プロセスの分け方

![setup と Skill のやりとり][fig-room]

setup の 1 回の実行は、人の代わりのトークンを受け取ってから終わるまで、1 つのプロセス（`entry/setup.ts run`）で動かす。トークンを `setup` の実行の間だけメモリに持ち、ファイルに書かない決まり（「[導入と点検][b04]」の「setup 用の App」）を、承認を挟んでも守るため。プロセスを分けると、分けた先へトークンを渡すにはファイルか環境変数を通すことになり、承認のコードを入れ直さない限り、決まりを守れない。

- Skill は、`run` を、Bash の道具の後ろで動かすコマンド（バックグラウンドの実行）として起こす。`run` は作業フォルダの外（マシンの中のフォルダ、秘密の置き場、定期の実行の登録）に書くので、Skill は、sandbox の外で動かす許可を人に求めてから起こす。許可が無ければ、何も作らずに理由を示して止まる（「[導入と点検][b04]」の「setup の流れ」の表の下）
- `run` と Skill は、部屋のフォルダでやりとりする。部屋は、Skill が sandbox の中で作れる一時フォルダ（Claude Code の `TMPDIR` の下の `dev-autopilot-setup-<実行 ID>/`）に、Skill が権限 700 で作り、`run` にパスを渡す。`run` は、部屋がシンボリックリンクでなく、自分の持ち物で、権限が 700 であることを確かめてから使う
- `run` は、出来事を部屋の `events.jsonl` に 1 行ずつ足す。Skill は `entry/setup.ts next`（sandbox の中で動く）で、読んだ行の番号より後の出来事を、来るまで最大 60 秒待って受け取り、人に示す
- 人に聞くことの答えは、Skill が `entry/setup.ts answer`（sandbox の中で動く）で部屋に答えのファイルを書く。`run` は、聞いた出来事の番号と同じ番号の答えだけを読み、読んだら消す
- `run` が答えを待つのは 30 分まで。過ぎたら、待つ前までにしたことを出来事に書いて、何も足さずに終わる。人の代わりのトークンは 8 時間で切れる（FACT-93）ので、待つ間に切れることは無い
- `run` が終わったら、Skill が部屋を消す。部屋の中身は、出来事（何をしたか、何を聞いたか）と答えだけで、トークンと秘密鍵と鍵の値は書かない

| 出来事（`kind`） | 中身 | Skill がすること |
| --- | --- | --- |
| `ask` | 聞くこと（base ブランチ、setup 用の App の `client_id`、規約、変えてはいけないパスの足す分、ruleset の bypass に入れるアプリ）と、選べる値 | 人に聞いて、`answer` で答えを書く |
| `device-code` | 承認のコードと、入れる URL（`https://github.com/login/device`） | 人に示す（答えは要らない。`run` が GitHub に問い合わせて待つ） |
| `open-url` | 開く URL（setup 用の App の登録フォーム、進行 Bot の App のマニフェストを送るページ）と、人が開いた画面ですること | 人に示す |
| `plan` | 差分の一覧と、一覧のハッシュ | 人に示し、承認と、GitHub の準備とマシンの準備のどちらを行うかを、`answer` で書く（ハッシュを添える） |
| `step` | 済んだ手順と、作ったもの | 人に示す |
| `todo` | 人がやること（「[導入と点検][b04]」の「setup の流れ」の順 6） | 人に示す |
| `done`・`stopped` | 終わったか、止まった理由 | 人に示し、部屋を消す |

- 段階 3（導入と点検の実装）で、sandbox を有効にした人の Claude Code で、バックグラウンドの実行が続く間に別の Bash の呼び出しから部屋を読み書きできることを確かめる。できなければ、「プロセスの分け方」を決め直す

## 順

`run` は、基本設計の「setup の流れ」の順 1〜8 を、次のとおりに進める。

| 順 | すること | 人とのやりとり |
| --- | --- | --- |
| 1 | 開いているプロジェクトの origin から owner/repo を引き、`logic/setup/self-repo.ts` で dev-autopilot 自身のリポなら止まる。Linux なら、動かさないことを示して止まる（「[導入と点検][b04]」の「Linux（systemd のユーザーのタイマー）」） | — |
| 2 | マシンの設定を読む。無ければ、base ブランチを聞く。`githubApp.setupClientId` が無ければ、setup 用の App の登録フォームを開かせ、`client_id` を聞く | `ask`・`open-url` |
| 3 | device flow で承認のコードを示し、人の代わりのトークンを待つ。人が入れなければ（承認のコードの期限（GitHub が返す `expires_in`）を過ぎた）、GitHub を読まずに、マシンの準備だけの一覧に進む | `device-code` |
| 4 | GitHub の今の状態とマシンの今の状態を読み、差分の一覧を作る（下の「差分の一覧」）。規約などの初めてのときだけ聞く値は、一覧を作る前に聞く | `ask` |
| 5 | 一覧を示し、承認を待つ。承認されなければ、何も作らずに終わる | `plan` |
| 6 | 承認の後に、今の状態をもう一度読んで一覧を作り直し、ハッシュが承認したものと同じことを確かめる。違えば何も作らずに止まり、違いを示す（人は `setup` を実行し直して、新しい一覧を承認する） | — |
| 7 | GitHub の準備（選んだとき）。進行 Bot の App が無ければ、先に作る（下の「GitHub の準備の順」） | `open-url`・`step` |
| 8 | マシンの準備（選んだとき。下の「マシンの準備の順」） | `step` |
| 9 | 人がやることを示す。マシンの準備をしたときは、定期の実行と同じジョブで点検だけを起こし、結果を示す（「[点検][d04]」の「人が呼ぶ check」と同じ依頼のファイルを置く） | `todo`・`step` |

- 順 6 で一覧を作り直すのは、人が一覧を読んでいる間に、ほかの人か前の `setup` が GitHub を変えたときに、承認していない変更をしないため
- 手順の途中で止まったら、止まる前に作ったものを `step` に書いたまま `stopped` で終わる。`setup` は冪等（「[導入と点検][b04]」の「setup の流れ」の表の下）なので、人は止まった理由を直して実行し直す

## 差分の一覧

`logic/setup/plan.ts` は、今の状態（GitHub、マシンの設定、マシンの中のフォルダ、写し、定期の実行の登録）と、設定の表と、Plugin の版から、差分の一覧を作る。

- 一覧の 1 件は、組（`github`・`machine`）、種類（作る・足す・消す・置き換える・写す・登録する）、対象（ラベルの名前、ruleset の名前、設定のキー、パスなど）、元に戻せないか（Status 欄の選択肢の置き換えのように、今の値が失われるもの）を持つ。元に戻せないものは、一覧の先頭に分けて示す
- 一覧のハッシュは、一覧を JSON にして取る SHA-256（16 進）。JSON は、印の署名と同じくキーを文字の符号の順に並べて空白を入れない（「[印][d03]」の「署名」の順 2）。一覧の並びは、組・種類・対象の順に並べ替えてから取る。同じ状態から同じハッシュになるようにするため
- 秘密の値と秘密の置き場のファイルの中身は、一覧に入れない（秘密のファイルは「空で作る」とだけ書く）

## GitHub の準備の順

`flow/setup/github.ts` は、承認された一覧の `github` の組を、次の順に行う。後の手順が前の手順の結果を使うため。

| 順 | すること |
| --- | --- |
| 1 | 進行 Bot の App が無ければ作り、インストールの ID を読む（「[導入と点検][b04]」の「GitHub App を作る」の順 3〜5）。手元で戻り先を待つのは `io/http.ts` の `listen`（`127.0.0.1` と `::1`。FACT-95）、マニフェストのコードの引き換えは `io/github.ts`（「[外との境][d01]」の「GitHub の呼び方」） |
| 2 | ラベルを作る |
| 3 | Project の欄・選択肢・ビューを作り、Status 欄の選択肢を置き換える（承認された一覧に入っているときだけ） |
| 4 | 3 つの ruleset を作るか足し、`bypass_actors` を含めて読み戻して、`logic/check/rulesets.ts` で比べる。守りが弱い向きの違いがあれば、ここで止まる |
| 5 | 全体の止める合図の変数を、無ければ `stop` で作る |
| 6 | 順 4 で違いが無ければ、ruleset の控えの変数を書く |
| 7 | リポの設定の PR を作る（下の箇条） |
| 8 | 読むだけの確かめ（組み込みのワークフロー、CI の秘密の置き方、App の導入先）を行い、違いを `step` に示す |

- リポの設定の PR は、base ブランチの先端から新しいブランチ（`dev-autopilot/setup-<実行 ID>`）を作り、`.claude/dev-autopilot.json` を書いた commit を 1 つ足して、base ブランチへの PR を作る（Git のデータの API と Pulls の API）。前の `setup` の PR（ブランチ名が `dev-autopilot/setup-` で始まる開いた PR）があれば、新しく作らずに前の PR を示す。ブランチ名は作業ブランチの形（`<型>/issue-*`）に当たらないので、deploy key の push 先と混ざらない
- リポの設定の PR を作るには、setup 用の App に Contents の書き込み（ブランチと commit を作る）と Pull requests の書き込み（PR を作る）が要る。基本設計の「setup 用の App」の権限の表に足した（[ADR-20261030-001][adr-setup-app] の「権限の表は基本設計で決める」の範囲）。人の代わりのトークンは、承認した人の権限との重なりだけを持つので、人が書けないリポには書けない
- 承認した人が組織の管理者でなく、順 4 で ruleset を作れなければ、そこで止める（「[導入と点検][b04]」の「setup 用の App」）

## マシンの準備の順

`flow/setup/machine.ts` は、承認された一覧の `machine` の組を、実行の lock を取ってから次の順に行い、最後に lock を外す。進行 Bot の実行と、マシンの中のファイルを同時に書き換えないため。lock を取れなければ、マシンの準備をせずに、後で実行し直すように示して止まる。

| 順 | すること |
| --- | --- |
| 1 | マシンの設定のフォルダと `settings.json` を作るか、足りない項目を足し、表に無いキーを消す（今の値は書き換えない） |
| 2 | 置き場、安全設定の置き場、記録の置き場、短い一時フォルダの根を、決めた権限で作る。記録の目印のファイルは、無いときだけ作る |
| 3 | 秘密の置き場を権限 700 で作り、無いファイルだけを空のまま権限 600 で作る。あるファイルは開かない |
| 4 | プログラムの写しを作る（`flow/setup/copy.ts`。「[導入と点検][b04]」の「プログラムの写し」の順 1〜6。lock はすでに持っている） |
| 5 | 定期の実行を登録し直す（`flow/setup/schedule.ts`） |

- ファイルは、一時のファイル（`<名前>.new-<自分の PID>`）に書いて書き出してから `rename` で名前を付ける（「[設定と記録][d02]」の「依頼と結果のファイル」と同じ）。途中で止まっても、半分だけ書いたファイルが残らないため
- 権限は、作った後に読み戻して確かめる。フォルダがすでにあって権限が違えば、付け直さずに止まって示す（人が意図して変えたものを黙って変えないため）。点検が同じ権限を fail にするので、人が直して実行し直す

## プログラムの写し

`logic/setup/manifest.ts` に、写しの中身の一覧の作り方を持つ。

- 一覧の 1 件は、写しの根からの相対パスと、中身の SHA-256（16 進）。パスは `/` 区切りで、符号の順に並べる。シンボリックリンクがあれば、一覧を作らずに止める（「[導入と点検][b04]」の「依存」）
- `program/<版>.manifest.json` は、形の版（`v`）、Plugin の版、一覧を持つ。毎回の点検は、写しの中身から同じ形の一覧を作って比べる（「[点検][d04]」のマシンの組）
- 依存が揃っているかは、`plugin/package-lock.json` の `packages` の各項目（`node_modules/<名前>` と `version`）と、入れた Plugin の `node_modules/<名前>/package.json` の `version` を照らす。確かめる処理は、`node:` のほかを import しないファイルに置き、依存を import するモジュールより先に動かす（「[導入と点検][b04]」の「依存」）

## 定期の実行の登録

`logic/setup/schedule.ts` は、時刻の一覧と、登録の中身を組み立てる。`flow/setup/schedule.ts` が、ファイルを書いて OS の仕組みを呼ぶ（「[外との境][d01]」の「OS ごとの部分」）。

- 時刻の一覧は、0 時から `run.intervalHours` ごとの `{Hour, Minute: 0}` の並び。`run.intervalHours` が 24 の約数でなければ、組み立てずに止める（点検も fail にする）
- plist は、キーと値の表（「[導入と点検][b04]」の「macOS（launchd）」）を、XML の文字をエスケープして書く。値に改行と制御文字があれば、組み立てずに止める。点検が登録の中身を読み戻して比べるので、書く側と読む側で同じ組み立ての関数を使う
- 登録し直すときは、`launchctl bootout` の後に `bootstrap` する。`bootout` で登録が無かった（登録していなかった）ことは失敗にしない

## 引数ごとの流れ

| 引数 | 順（上の「順」） | 違い |
| --- | --- | --- |
| （無し） | 1〜9 | — |
| `upgrade` | 1〜9 | 版を固定していても（`program.pinned` が `true`）、新しい版で写し、固定を外す |
| `rollback` | 1〜9 | `program.previousVersion` の版の写しに向け直し、版を固定する。設定を戻す先の版の表に合わせる足し引きを一覧に出す。GitHub の準備は、リポの設定の PR だけを行う（承認のコードが要る） |
| `uninstall` | 1 と、定期の実行の登録を外すことだけ | lock を取り、登録を外して読み戻し、lock を外す。写し・置き場・記録・秘密は消さない。GitHub を読まないので、承認のコードは要らない |

## テスト

| ファイル | 単体テストで確かめること |
| --- | --- |
| `flow/setup/run.ts` | 順のとおりに進み、承認されなければ何も作らないこと。順 6 でハッシュが違えば止まること。答えを 30 分待って終わること。人の代わりのトークンを、部屋のファイル・記録・ログに書かないこと（偽の GitHub が返したトークンの文字が、部屋のどのファイルにも無いことを確かめる） |

| `logic/setup/schedule.ts` | 時刻の一覧（24 の約数ごと）。plist の中身とエスケープ。改行のある値で止まること |
| `logic/setup/app-manifest.ts` | マニフェストの権限が `logic/check/app-permissions.ts` の表と同じこと。Webhook を書かないこと。登録フォームの URL の権限 |
| `flow/setup/github.ts` | 手順の順。読み戻した ruleset に守りが弱い向きの違いがあれば、控えを書かずに止まること。前の `setup` の PR があれば作らないこと |
| `flow/setup/machine.ts` | lock を取れなければ何も作らないこと。あるファイルを開かないこと。権限が違うフォルダで止まること |

- 結合テストは、承認のコードを入れない形（GitHub を読まずにマシンの準備だけ）で、`run` を部屋のやりとりとともに通す。device flow と App を作る手順は、人がブラウザで行う操作を含むので、単体テストで確かめる（「[テスト][b05]」の「偽物」）
