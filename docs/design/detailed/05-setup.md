# setup

人が呼ぶ `setup`（引数の `rollback`・`upgrade`・`uninstall` を含む）の作りを決める。setup の流れと、作るもの・確かめ方の正本は、基本設計の「[導入と点検][b04]」の「setup の流れ」から「動かすマシンを替えるとき」までと、「setup 用の App」「GitHub App を作る」にある。本書は、流れを人の Claude Code の上でどう動かすか（プロセスの分け方と、人とのやりとり）と、差分の一覧の作り方、準備の順を決める。

## プロセスの分け方

![setup と Skill のやりとり][fig-room]

setup の 1 回の実行は、人の代わりのトークンを受け取ってから終わるまで、1 つのプロセス（`entry/setup.ts run`）で動かす。トークンを `setup` の実行の間だけメモリに持ち、ファイルに書かない決まり（「[導入と点検][b04]」の「setup 用の App」）を、承認を挟んでも守るため。プロセスを分けると、分けた先へトークンを渡すにはファイルか環境変数を通すことになり、承認のコードを入れ直さない限り、決まりを守れない。

- Skill は、`run` を、Bash の道具の後ろで動かすコマンド（バックグラウンドの実行）として起こす。`run` は作業フォルダの外（マシンの中のフォルダ、秘密の置き場、定期の実行の登録）に書くので、Skill は、sandbox の外で動かす許可を人に求めてから起こす。許可が無ければ、何も作らずに理由を示して止まる（「[導入と点検][b04]」の「setup の流れ」の表の下）。Skill は `run` を、Bash の道具のバックグラウンドの実行で許される最も長い時間の上限で起こす
- `run` と Skill は、部屋のフォルダでやりとりする（本書の「部屋」は、setup の本体と Skill が出来事と答えをやりとりするためだけに `run` が作るフォルダを指す）。部屋は、sandbox の中のコマンドが書けない場所に、`run` が作る。macOS は `getconf DARWIN_USER_TEMP_DIR` の下の `dev-autopilot-setup-<実行 ID>/`（作業フォルダの外で、`/tmp/claude-<uid>/` の外）。sandbox の中のコマンドが既定で書けるのは作業フォルダとユーザーごとの一時フォルダだけ（FACT-34・36・71）なので、人のほかの Claude Code のセッションの sandbox の中のコマンドは、部屋に書けない。Linux では `setup` が順 1 で止まるので決めない
- Skill は、`entry/setup.ts begin`（sandbox の中で動く）から、実行 ID と部屋のパスを入れた `run` のコマンドの文を受け取り、そのコマンドを sandbox の外で動かす許可を人に求めて起こす。`run` は、部屋のパスが人の一時フォルダの直下の `dev-autopilot-setup-<実行 ID の形>` でなければ止まり、部屋を排他で（すでにあれば止まる）権限 700 で作り、シンボリックリンクでなく、自分の持ち物で、権限が 700 であることを読み戻してから使う
- `run` は、出来事を部屋の `events.jsonl` に 1 行ずつ足す。Skill は `entry/setup.ts next`（sandbox の中で動く）で、読んだ行の番号より後の出来事を、来るまで最大 60 秒待って受け取り、人に示す
- 人に聞くことの答えは、Skill が、部屋に答えのファイルを書くコマンド（`entry/setup.ts answer`。`node` の 1 行で、部屋のパスと聞いた出来事の番号と答えを引数に置く）を、sandbox の外で動かす許可を人に求めてから動かす（「[点検][d04]」の「人が呼ぶ check」の依頼を置くコマンドと同じ形。「[導入と点検][b04]」の「点検だけで動かす仕組み」の表の下）。人は、許可を求める画面で、答えの中身（`client_id`、bypass に入れるアプリ、承認する一覧のハッシュなど）を読んで許す。許されなければ答えを書かず、`run` は待つ上限で終わる。sandbox の中のコマンドは部屋に書けないので、答えを書けるのは人が許したコマンドだけになる。`run` は、聞いた出来事の番号と同じ番号の答えだけを読み、読んだら消す
- `run` が答えを待つのは 30 分まで。過ぎたら、待つ前までにしたことを出来事に書いて、何も足さずに終わる。人の代わりのトークンは 8 時間で切れる（FACT-93）ので、待つ間に切れることは無い
- `run` が終わったら、Skill が、部屋を消すコマンドを sandbox の外で動かす許可を人に求めて消す。許されなければ残す（次の `setup` は別の実行 ID の部屋を作る）。部屋の中身は、出来事（何をしたか、何を聞いたか）と答えだけで、トークンと秘密鍵と鍵の値と、device flow の `device_code`（GitHub にトークンを問い合わせるときに使う値。部屋を読める同じユーザーのプロセスが、人の承認の後にトークンを受け取れるため）は書かない。出来事の `device-code` に書くのは、人が入れる承認のコード（`user_code`）と入れる URL だけ

| 出来事（`kind`） | 中身 | Skill がすること |
| --- | --- | --- |
| `ask` | 聞くこと（base ブランチ、setup 用の App の `client_id`、規約、変えてはいけないパスの足す分、ruleset の bypass に入れるアプリ、進行 Bot の App を当てる先のリポに入れたか、読めなかったときのインストールの ID）と、選べる値 | 人に聞いて、`answer` で答えを書く |
| `device-code` | 承認のコードと、入れる URL（`https://github.com/login/device`） | 人に示す（答えは要らない。`run` が GitHub に問い合わせて待つ） |
| `open-url` | 開く URL（setup 用の App の登録フォーム、進行 Bot の App のマニフェストを送るページ）と、人が開いた画面ですること | 人に示す |
| `plan` | 差分の一覧と、一覧のハッシュ | 人に示し、承認と、GitHub の準備とマシンの準備をそれぞれ行うか（両方も、片方だけも選べる。「[導入と点検][b04]」の「setup の流れ」の順 3）と、選べる件のうち行うもの（必須チェックの候補は、選んだものだけを ruleset と `checks.required` に入れる）を、`answer` で書く（ハッシュを添える）。選べる件は、既定で選ばない（人が 1 つずつ選ぶ） |
| `step` | 済んだ手順と、作ったもの | 人に示す |
| `todo` | 人がやること（「[導入と点検][b04]」の「setup の流れ」の順 6） | 人に示す |
| `done`・`stopped` | 終わったか、止まった理由 | 人に示し、部屋を消す |

- 段階 3（導入と点検の実装）で、sandbox を有効にした人の Claude Code で、次を確かめる（「[導入と点検][b04]」の「点検だけで動かす仕組み」の表の下の、段階 3 で試すこと）。(1) か (3) が外れたら、「プロセスの分け方」を決め直す。(2) が外れたら（書けたら）、部屋で答えを受けない（`setup` は答えを読まずに止まる）形に直してから作る
  1. バックグラウンドの `run` が続く間に、sandbox の中の `next` が部屋を読めること
  2. sandbox の中のコマンドが部屋に書けないこと
  3. 人の許可を得て sandbox の外で動かした `answer` が部屋に書けること
  4. バックグラウンドの `run` を途中で止めて（Claude Code を閉じる）、次の `setup` が同じ結果になること。あわせて、Bash の道具のバックグラウンドの実行の時間の上限を確かめ、`run` の答えを待つ 30 分と点検の結果を待つ時間が 1 つの聞くことの間に収まるかを見る

## 順

`run` は、基本設計の「setup の流れ」の順 1〜8（順 8 のうち人がすることを除く）を、次のとおりに進める。表の右の欄は、対応する基本設計の「setup の流れ」の順。本書で「順 N」とだけ書くときは本表の順を指し、基本設計の順は「setup の流れ」の順 N と書く。

| 順 | すること | 人とのやりとり | 基本設計の順 |
| --- | --- | --- | --- |
| 1 | 開いているプロジェクトの origin から owner/repo を引き、`logic/setup/self-repo.ts` で dev-autopilot 自身のリポなら止まる。Linux なら、動かさないことを示して止まる（「[導入と点検][b04]」の「Linux（systemd のユーザーのタイマー）」） | — | 1 |
| 2 | マシンの設定を読む。無ければ、base ブランチを聞く。`githubApp.setupClientId` が無ければ、setup 用の App の登録フォームを開かせ、`client_id` を聞く | `ask`・`open-url` | 2 |
| 3 | device flow で承認のコードを示し、人の代わりのトークンを待つ。人が入れなければ（承認のコードの期限（GitHub が返す `expires_in`）を過ぎた）、GitHub を読まずに、マシンの準備だけの一覧に進む | `device-code` | 2 |
| 4 | GitHub の今の状態とマシンの今の状態を読み、差分の一覧を作る（下の「差分の一覧」）。規約などの初めてのときだけ聞く値は、一覧を作る前に聞く | `ask` | 2 |
| 5 | 一覧を示し、承認を待つ。承認されなければ、何も作らずに終わる | `plan` | 3 |
| 6 | 承認の後に、今の状態をもう一度読んで一覧を作り直し、ハッシュが承認したものと同じことを確かめる。違えば何も作らずに止まり、違いを示す（人は `setup` を実行し直して、新しい一覧を承認する）。選んだ件は、作り直した一覧にも同じ対象と中身があるものだけを行う | — | 3 |
| 7 | GitHub の準備（選んだとき）。進行 Bot の App が無ければ、先に作る（下の「GitHub の準備の順」） | `open-url`・`step` | 4 |
| 8 | マシンの準備（選んだとき。下の「マシンの準備の順」） | `step` | 5 |
| 9 | 人がやることを示す。マシンの準備をしたときは、定期の実行と同じジョブで点検だけを起こし、結果を示す（「[点検][d04]」の「人が呼ぶ check」と同じ依頼のファイルを置く。項目は ID と `logic/check/items.ts` の決まった文と `details` で出す）。結果と一緒に、試しのセッションを行う最初の実行が次の日からになること（記録の目印のファイルを作った日は AI のセッションを起動しないため。「[導入と点検][b04]」の「setup の流れ」の順 8）を示す | `todo`・`step` | 6・7・8（8 は示すことだけ） |

- 順 6 で一覧を作り直すのは、人が一覧を読んでいる間に、ほかの人か前の `setup` が GitHub を変えたときに、承認していない変更をしないため
- 手順の途中で止まったら、止まる前に作ったものを `step` に書いたまま `stopped` で終わる。`setup` は冪等（「[導入と点検][b04]」の「setup の流れ」の表の下）なので、人は止まった理由を直して実行し直す
- `run` は、Claude Code に止められても（バックグラウンドの実行の時間の上限、人が Claude Code を閉じた）、`stopped` を書けないまま終わる。止められたときの残りは、どれも次の `setup` が同じ結果にする
  - 実行の lock は、持ち主の PID が無いので、次の実行か `setup` が古い lock として奪う（「[設定と記録][d02]」の「lock」）
  - 書きかけの写しは、次の `setup` が `program/.new-*` を消す（「[導入と点検][b04]」の「プログラムの写し」の順 3（別の名前で写す順））。ファイルは一時のファイルから `rename` で置くので、半分だけ書いたファイルは残らない
  - 部屋は残るが、秘密は無い。次の `setup` は別の実行 ID の部屋を作る
  - GitHub の準備は無いものだけを作るので、作り直さない。ruleset を作って控えを書く前に止まったときは、点検が控えの無いことで fail にし、次の `setup` が読み戻して控えを書く
  - 定期の実行の登録を外した後に止まったときは、点検が登録のずれで fail にし、次の `setup` が登録する
  - 進行 Bot の App を作った後、秘密鍵を受け取る前に止まったときは、GitHub に App が残る。次の `setup` は、`githubApp.appId` が無いので作り直そうとし、名前が使われていれば作れないので、人に、残った App を App の設定の画面で消すか、名前を変えて作るように示す

## 差分の一覧

`logic/setup/plan.ts` は、今の状態（GitHub、マシンの設定、マシンの中のフォルダ、写し、定期の実行の登録）と、設定の表と、Plugin の版と、リポの設定の `run.intervalHours`（下の「定期の実行の登録」の読み方で読んだ値）から、差分の一覧を作る。設定の表は、設定の足し引きに使う版の表（引数ごとの決め方は下の「引数ごとの流れ」）。

- 一覧の 1 件は、組（`github`・`machine`）、種類（作る・足す・消す・置き換える・写す・登録する）、対象（ラベルの名前、ruleset の名前、設定のキー、パスなど）、中身、元に戻せないか（Status 欄の選択肢の置き換えのように、今の値が失われるもの）、選べるか（必須チェックの候補のように、人が選んだものだけを行う件）を持つ。元に戻せないものは、一覧の先頭に分けて示す
- 中身は、足すか変える値の並び：ruleset に足す必須チェックの名前と app、除外に足すか外す ref の形、bypass に入れるアプリの名前と ID、Status 欄の置き換える前と後の選択肢の名前、リポの設定の PR とマシンの設定で足すキーと値と消すキー、定期の実行の登録の時刻と環境変数の名前（値は入れない）、写す版。中身の無い件（ラベルを作るなど）は空にする。人は中身を読んで承認する
- 必須チェックの候補（「[導入と点検][b04]」の「GitHub の準備」の表の下）は、候補ごとに 1 件（組 `github`、種類「足す」、対象「必須チェック」、中身に候補の名前・出した app・ワークフローのパス）にし、選べる件にする
- 進行 Bot の App を作ること（組 `github`。中身は App の名前と権限）と、秘密鍵と `githubApp.appId` と `githubApp.installationId` を書くこと（組 `machine`。秘密鍵の値は入れない）も、1 件ずつ一覧に入れる
- 一覧のハッシュは、一覧を JSON（中身を含む）にして取る SHA-256（16 進）。JSON は、印の署名と同じくキーを文字の符号の順に並べて空白を入れない（「[印][d03]」の「署名」の順 2）。一覧の並びは、組・種類・対象の順に並べ替えてから取る。組・種類・対象が同じ件（必須チェックの候補など）は、中身を同じ並べ方の JSON にした文字列の、文字の符号の順に並べる。中身の中の、順に意味の無い並び（足す必須チェックの名前、除外に足すか外す ref の形、足すキーと消すキー、環境変数の名前）は、書く前に、数は小さい順、文字列は文字の符号の順に並べ、同じ値を 1 つにする（「[印][d03]」の「書く形」の並びの欄と同じ）。Status 欄の選択肢の名前の並びは、順に意味があるので並べ替えない。同じ状態から同じハッシュになるようにするため
- 秘密の値と秘密の置き場のファイルの中身は、一覧に入れない（秘密のファイルは「空で作る」とだけ書く）

## GitHub の準備の順

`flow/setup/github.ts` は、承認された一覧の `github` の組を、次の順に行う。後の手順が前の手順の結果を使うため。

| 順 | すること |
| --- | --- |
| 1 | 進行 Bot の App が無ければ作る（「[導入と点検][b04]」の「GitHub App を作る」の順 3〜5（マニフェストを送って App を作り、秘密鍵を受け取り、インストールの ID を読む））。手元で戻り先を待つのは `io/http.ts` の `listen`（`127.0.0.1` と `::1`。FACT-95）で、待てなければ理由を示して止まる。マニフェストのコードの引き換えは `io/github.ts`（「[外との境][d01]」の「GitHub の呼び方」）。引き換えたら、すぐに、秘密鍵を秘密の置き場の `github-app-key.pem`（権限 600）に、App の ID をマシンの設定の `githubApp.appId` に書く（表の下の箇条）。続けて、`ask` で人に App を当てる先のリポだけに入れたら答えるように聞き、答えの後に、メモリの秘密鍵で作った JWT（`io/github-jwt.ts`）でインストールの ID を読んで `githubApp.installationId` に書く。読めなかったとき（人が入れたと答えた後に読めなかった（入れる先を誤ったなど）、App がすでにあってインストールの ID が無い）は、秘密の置き場を読まずに、`ask` でインストールの ID を聞いて書く（書いた ID が進行 Bot の App のものかは、上の「順」の順 9（人がやることを示し、点検だけを起こす順）の点検のアプリの権限の組が確かめ、違えば fail になる）。人が答えないまま答えを待つ 30 分を過ぎたときは、何も足さずに終わり（上の「プロセスの分け方」）、次の `setup` が、App がすでにあってインストールの ID が無いときとして聞く |
| 2 | ラベルを作る |
| 3 | Project の欄・選択肢・ビューを作り、Status 欄の選択肢を置き換える（承認された一覧に入っているときだけ） |
| 4 | 3 つの ruleset を作るか足し、`bypass_actors` を含めて読み戻して、`logic/check/rulesets.ts` で比べる。守りが弱い向きの違いがあれば、ここで止まる。読み戻した ruleset に `bypass_actors` が無ければ（比べる関数が「bypass を比べていない」を付けて返したら）、守りが弱い向きの違いと同じく、ここで止まり、控えを書かない。止まった理由（bypass を読める認証で承認していない）と、組織の管理者が承認して `setup` を実行し直すことを示す |
| 5 | 全体の止める合図の変数を、無ければ `stop` で作る |
| 6 | 順 4 で、`bypass_actors` を含めて比べられ、守りが弱い向きの違いが無ければ、ruleset の控えの変数を書く（[ADR-20261028-004][adr-bypass-baseline] の決定 1）。守りが弱い向きでない違い（設定に無い型の除外など）があるときも書き、違いを `step` に示す |
| 7 | リポの設定の PR を作る（下の箇条） |
| 8 | 読むだけの確かめ（組み込みのワークフロー、CI の秘密の置き方、App の導入先）を行い、違いを `step` に示す |

- リポの設定の PR は、base ブランチの先端から新しいブランチ（`dev-autopilot/setup-<実行 ID>`）を作り、`.claude/dev-autopilot.json` を書いた commit を 1 つ足して、base ブランチへの PR を作る（Git のデータの API と Pulls の API）。前の `setup` の PR（開いた PR のうち、head のリポが当てる先のリポで（fork でない）、head のブランチ名が `dev-autopilot/setup-` で始まり、base が base ブランチで、変えたファイルが `.claude/dev-autopilot.json` だけのもの）があれば、新しく作らずに前の PR を示す。前の PR を示すときは、PR を作った人と head のリポも示す。ブランチ名が `dev-autopilot/setup-` で始まるのに条件に外れる PR があれば、前の PR として使わずに新しく作り、外れた PR の番号を `step` に示す（fork の head のブランチ名は誰でも付けられるが、当てる先のリポの中の `dev-autopilot/setup-` のブランチは、ブランチの ruleset で bypass の外の人とアプリが作れない）。ブランチ名は作業ブランチの形（`<型>/issue-*`）に当たらないので、deploy key の push 先と混ざらない
- リポの設定の PR のブランチ・commit・PR のどれかを作れなければ（ruleset で断られた、など）、作りかけのブランチがあれば示し、`stopped` で終わる。止まる前に、リポの設定に書く中身（足すキーと値と消すキー）と、人がブランチの ruleset の bypass に入る人（組織の管理者か bypass に入れたチーム）として PR を出す手順を `todo` に示す。リポの設定の PR がマージされるまで点検は fail のまま（「[導入と点検][b04]」の「GitHub の準備」の表のリポの設定の行）なので、作業には入らない。人の代わりのトークンで ruleset の外のブランチを作れるかは確かめていない（FACT-94 の `current_user_can_bypass` が `always` なのは見込みの根拠どまり）
- リポの設定の PR を作るには、setup 用の App に Contents の書き込み（ブランチと commit を作る）と Pull requests の書き込み（PR を作る）が要る。基本設計の「setup 用の App」の権限の表に足した（[ADR-20261030-001][adr-setup-app] の「権限の表は基本設計で決める」の範囲）。人の代わりのトークンは、承認した人の権限との重なりだけを持つので、人が書けないリポには書けない
- 承認した人が組織の管理者でなく、順 4 で ruleset を作れなければ、そこで止める（「[導入と点検][b04]」の「setup 用の App」）
- 順 1 の秘密鍵の書き方：初めての `setup` で書く先が無ければ、マシンの準備の順 1 と順 3（マシンの設定のフォルダと `settings.json`、秘密の置き場）をこの時に先に行う（どちらも承認した一覧の `machine` の組にある。マシンの設定が無いので進行 Bot は動いておらず、実行の lock は要らない）。`github-app-key.pem` は、一時のファイルに書いてから `rename` で置く（`io/secret-files.ts` の秘密のファイルを置く操作。「[外との境][d01]」の「秘密の置き場」）。空のファイルがあれば置き換え（空のファイルは無いものと読む。「[設定][b01]」の「秘密の置き場のファイル」）、中身のあるファイル（大きさが 0 でない。改行だけのファイルも当たる）があれば、開かずに、置かずに止まって示す。引き換えた後に止まると 1 回だけ受け取った秘密鍵を失うので、App を作る前（戻り先を待つ前）にも、`github-app-key.pem` が無いか大きさが 0 かを `io/files.ts` の `lstat` で確かめ（中身は読まない）、外れれば App を作らずに止まり、ファイルを消すか空にするよう人に示す。マニフェストのコードの引き換えは 1 回だけなので、秘密鍵を書くのをマシンの準備まで持ち越さない（持ち越すと、マシンの準備の前に止められたときに秘密鍵を失う）
- マシンの準備を選ばなかった回（手元のマシンで、専用マシンのために GitHub の準備だけを行う回）は、秘密鍵を書かずに捨てる（「[導入と点検][b04]」の「GitHub App を作る」の表の下）。App の ID とインストールの ID は、マシンの設定があれば書き、無ければ作らない。どちらのときも、2 つの ID と、人が App の設定の画面で秘密鍵を作って専用マシンの秘密の置き場に置く手順を `todo` に示す
- `flow/setup/apps.ts` は、人の代わりのトークンと、引き換えで受け取った秘密鍵を、秘密の値の型（`logic/secret.ts`。「[外との境][d01]」の「秘密の置き場」）のまま持ち、`io/github.ts`・`io/github-jwt.ts`・`io/secret-files.ts` に渡す

## マシンの準備の順

`flow/setup/machine.ts` は、承認された一覧の `machine` の組を、実行の lock を取ってから次の順に行い、最後に lock を外す。進行 Bot の実行と、マシンの中のファイルを同時に書き換えないため。記録の置き場（`run.lock` の置き場）が無いとき（初めての `setup`）は、lock を取る前に、下の順 1（マシンの設定のフォルダと `settings.json`）と、順 2 のうち記録の置き場だけを、順 1・2 と同じく権限 700 で先に行う。記録の置き場の macOS の既定はマシンの設定のフォルダの中にある（「[設定][b01]」の「マシンの中のフォルダ」）ので、親のフォルダから順に作る。記録の置き場が無い間は、進行 Bot も lock を取れずに動いていないため（上の「GitHub の準備の順」の、秘密鍵を書くときにマシンの準備の順 1 と順 3 を先に行うのと同じ形）。lock を取れなければ、マシンの準備をせずに、後で実行し直すように示して止まる。中身を読めない lock（`logic/run/lock.ts` が見分けられない理由を `unreadable` で返したもの）のときは、後で実行し直すようには示さず、壊れた lock であることと戻し方（「[設定と記録][d02]」の「lock」。示す文は `logic/text/comments.ts` の人の Skill と同じ文）を示して止まる。

| 順 | すること |
| --- | --- |
| 1 | マシンの設定のフォルダ（権限 700）と `settings.json` を作るか、足りない項目を足し、表に無いキーを消す（今の値は書き換えない） |
| 2 | 置き場、安全設定の置き場、記録の置き場、短い一時フォルダの根を、権限 700 で作る（「[設定][b01]」の「マシンの中のフォルダ」。値は `logic/settings/fixed.ts` の定数）。記録の目印のファイルは、無いときだけ作る |
| 3 | 秘密の置き場を権限 700 で作り、「[設定][b01]」の「秘密の置き場のファイル」の表の「`setup` が空で作るとき」が「いつも」のファイルのうち、無いものだけを空のまま権限 600 で作る（`github-pat` は作らず、`github-app-key.pem` は空で作らない。秘密鍵は上の「GitHub の準備の順」の順 1 で書く）。あるファイルは開かない |
| 4 | プログラムの写しを作る（`flow/setup/copy.ts`。「[導入と点検][b04]」の「プログラムの写し」の順 2〜4（版を読み、別の名前で写し、名前を変える）と、順 5 のうち `devAutopilotPath` を向け直し、版が変わるときに `program.previousVersion` を書くこと。lock はすでに持っている） |
| 5 | 定期の実行を登録し直す（`flow/setup/schedule.ts`。写しの順 5 の登録し直しは、ここで 1 回だけ行う） |
| 6 | 今使う版と `program.previousVersion` の版のほかの `program/<版>/` と manifest を消す（写しの順 6 のうち、lock を外すことを除く） |

- ファイルは、一時のファイル（`<名前>.new-<自分の PID>`）に書いて書き出してから `rename` で名前を付ける（「[設定と記録][d02]」の「依頼と結果のファイル」と同じ）。途中で止まっても、半分だけ書いたファイルが残らないため
- 権限は、作った後に読み戻して確かめる。フォルダがすでにあって権限が違えば、付け直さずに止まって示す（人が意図して変えたものを黙って変えないため）。点検が同じ権限を fail にするので、人が直して実行し直す

## プログラムの写し

`logic/setup/manifest.ts` に、写しの中身の一覧の作り方を持つ。

- 一覧の 1 件は、写しの根からの相対パスと、中身の SHA-256（16 進）。パスは `/` 区切りで、符号の順に並べる。シンボリックリンクがあれば、一覧を作らずに止める（「[導入と点検][b04]」の「依存」）
- `program/<版>.manifest.json` は、形の版（`v`）、Plugin の版、一覧を持つ。毎回の点検は、写しの中身から同じ形の一覧を作って比べる（「[点検][d04]」のマシンの組）
- 依存が揃っているかは、`plugin/package-lock.json` の `packages` の各項目（`node_modules/<名前>` と `version`）と、入れた Plugin の `node_modules/<名前>/package.json` の `version` を照らす。確かめる処理は、依存を import するモジュールより先に動かす（「[導入と点検][b04]」の「依存」）。読み取りは `entry/deps-check.ts`、照らしは `logic/setup/manifest.ts` に置く
- `entry/setup.ts` は、静的な import を `node:` で始まるモジュールと `entry/deps-check.ts` だけにし、どの引数でも最初に照らしを動かす。照らしが通ったら、本体（`flow/setup/` など）を、引数を文字列で書いた `import()` で読み込む（`entry/setup.ts` のほかで `import()` を使わない。[README][readme] の「層と依存の向き」と「構成の検査に足すこと」）。依存が足りなければ、本体を読み込まずに、足りない依存の名前と版と、Plugin を入れ直すことを標準出力に示し、決まった終了コードで終える。Skill は最初に `entry/setup.ts begin`（sandbox の中で、前で動く）を呼ぶので、照らしの結果を人に示せる
- `main.ts` は依存の照らしを持たない。写しの `node_modules` は写したときにハッシュで確かめてあり（「[導入と点検][b04]」の「プログラムの写し」の順 3（別の名前で写し、ハッシュを比べる順））、欠けたときは Node が標準エラー（`launchd.err.log`）に書いて終了コード 1 で終わる

## 定期の実行の登録

`logic/setup/schedule.ts` は、時刻の一覧と、登録の中身を組み立てる。`flow/setup/schedule.ts` が、ファイルを書いて OS の仕組みを呼ぶ（「[外との境][d01]」の「OS ごとの部分」）。

- `run.intervalHours` は、承認のコードを入れた回は、base ブランチの先端のリポの設定（`setup` 用の App の人の代わりのトークンで Contents を読む）から、入れなかった回は、`status.json` のリポの設定の値の欄（進行 Bot が base ブランチの先端から最後に読んだ値。「[設定と記録][d02]」の「status.json」）から読む。どちらも無いか、設定の表の型と範囲に合わなければ、設定の表の初期値を使う。作業コピーの `.claude/dev-autopilot.json` は読まない（別のブランチか古い版でありうるため）。どの値を使ったかを、差分の一覧の定期の実行の登録の件の中身と、`step` に示す
- 時刻の一覧は、0 時から `run.intervalHours` ごとの `{Hour, Minute: 0}` の並び。`run.intervalHours` が 24 の約数でなければ、組み立てずに止める（点検も fail にする）
- plist は、キーと値の表（「[導入と点検][b04]」の「macOS（launchd）」）を、XML の文字をエスケープして書く。値に改行と制御文字があれば、組み立てずに止める。`safety.env.values` に、GitHub への通信の行き先を変える環境変数の名前（`HTTP_PROXY`・`HTTPS_PROXY`（小文字の名前も）・`NODE_USE_ENV_PROXY`・`NODE_EXTRA_CA_CERTS`・`NODE_OPTIONS`。点検のマシンの組と同じ一覧。[ADR-20261107-001][adr-github]）があれば、組み立てずに止め、名前と、`safety.env.values` から外すことを示す（黙って抜くと、`safety.env.names` の名前が進行 Bot の環境に無く、AI のセッションを起動しないまま進むため）。点検が登録の中身を読み戻して比べるので、書く側と読む側で同じ組み立ての関数を使う
- 登録し直すときは、`launchctl bootout` の後に `bootstrap` する。`bootout` で登録が無かった（登録していなかった）ことは失敗にしない。登録が無かったことを終了コードと出力のどちらで見分けるかは確かめていないので、段階 3（導入と点検の実装）で、登録のあるときと無いときの `bootout` の終了コードと出力を実機で確かめてから決める。見分けられない失敗は、登録が無かったと読まずに止まる

## 引数ごとの流れ

| 引数 | 順（上の「順」） | 違い |
| --- | --- | --- |
| （無し） | 1〜9 | 版を固定している間（`program.pinned` が `true`）は、設定の足し引きに、入れた Plugin の版の表でなく、今の写しの版の控え（`logic/setup/settings-versions.ts`）を使う |
| `upgrade` | 1〜9 | 版を固定していても（`program.pinned` が `true`）、新しい版で写し、固定を外す |
| `rollback` | 1〜9 | `program.previousVersion` が `null` なら、何も変えずに止まる。版を固定していなければ（`program.pinned` が `false`）、`program.previousVersion` の版の写しに向け直し、版を固定する。固定していれば（すでに戻した）、写しを向け直さない（`program.previousVersion` は戻す前の新しい版なので、向け直すと新しい版に戻るため）。どちらも、設定を、戻す先の版（固定していなければ `program.previousVersion` の版、固定していれば今の写しの版）の控え（`logic/setup/settings-versions.ts`）に合わせる足し引きを一覧に出す。一覧を作る順 4・6（一覧を作る順と作り直す順）では、まだ写しを向け直していないため。控えに無い版なら、何も変えずに止まる。GitHub の準備は、リポの設定の PR だけを行う（承認のコードが要る。入らなければ、マシンの設定と写しだけを戻し、承認のコードを入れて `setup rollback` を実行し直すことを `todo` に示す） |
| `uninstall` | 1 と、定期の実行の登録を外すことだけ | lock を取り（取れないときは上の「マシンの準備の順」と同じに示す）、登録を外して読み戻し、lock を外す。写し・置き場・記録・秘密は消さない。GitHub を読まないので、承認のコードは要らない |

| `flow/setup/room.ts` | 部屋がリンクか、ほかの持ち物か、権限が 700 でなければ使わないこと。部屋のパスが人の一時フォルダの直下の決まった名前でなければ使わないこと。部屋がすでにあれば作らずに止まること。聞いた番号と違う答えを読まないこと。読んだ答えを消すこと |
| `logic/setup/plan.ts` | 状態の組み合わせごとの一覧。元に戻せないものを先頭に分けること。同じ状態から同じハッシュになること。中身が 1 つでも変わるとハッシュが変わること。必須チェックの候補が選べる件として 1 件ずつ入ること。GitHub から読む順（必須チェックの候補、除外の ref の形、ラベル）を入れ替えても、同じハッシュになること。秘密の値を一覧に入れないこと |
| `logic/setup/self-repo.ts` | owner/repo と `plugin.json` の名前の組み合わせごとの見分け |
| `logic/setup/manifest.ts` | 一覧の並べ方とハッシュ。シンボリックリンクで止まること。依存の版の照らし。依存の名前か版が欠けた組で、欠けたものを返すこと |
| `logic/setup/schedule.ts` | 時刻の一覧（24 の約数ごと）。plist の中身とエスケープ。改行のある値で止まること。`safety.env.values` に GitHub への通信の行き先を変える環境変数の名前（小文字の名前を含む）があれば止まること |
| `logic/setup/app-manifest.ts` | マニフェストの権限が `logic/check/app-permissions.ts` の表と同じこと。Webhook を書かないこと。登録フォームの URL の権限 |
| `logic/setup/settings-versions.ts` | 今の Plugin の版（`plugin.json` の `version`）の控えが、`logic/settings/repo.ts` と `logic/settings/machine.ts` の表のキーと初期値と同じこと（版を上げて表を変えたのに控えを足し忘れると落ちる） |
| `flow/setup/github.ts` | 手順の順。読み戻した ruleset に守りが弱い向きの違いがあれば、控えを書かずに止まること。`bypass_actors` の無い読み戻しで、控えを書かずに止まること。守りが弱い向きでない違いだけのときに控えを書くこと。前の `setup` の PR があれば作らないこと。fork から出た PR と、ほかのファイルも変える PR を、前の `setup` の PR と見なさないこと。ブランチの作成が断られたら、`todo` にリポの設定の中身を示して止まること |
| `flow/setup/apps.ts` | App がすでにあれば作らないこと。人の代わりのトークンと更新のトークンをファイルに書かないこと。`setup` 用の App の登録フォームを開く処理に、秘密鍵を作る手順が無いこと（[ADR-20261030-001][adr-setup-app]）。インストールの ID を読めなかったときに聞くこと。秘密の置き場を読まないこと。戻り先を待てなければ止まること |
| `flow/setup/copy.ts` | 中身の一覧のとおりに写し、写した後のハッシュを確かめること。`rollback` で前の版に戻すこと |
| `flow/setup/schedule.ts` | 組み立てた登録のファイルを書いて `launchctl` を呼ぶ順。`uninstall` で外すこと |
| `flow/setup/machine.ts` | lock を取れなければ何も作らないこと。あるファイルを開かないこと。権限が違うフォルダで止まること。定期の実行の登録し直しが 1 回だけで、lock を外すのが最後であること。中身を読めない lock では、壊れた lock の文と戻し方を示して止まること。記録の置き場が無いときに、順 1 と記録の置き場を作ってから lock を取ること（マシンの設定のフォルダが無い状態から始める見本を含む）。記録の置き場があるときは、lock を取る前に何も作らないこと |

- `entry/deps-check.ts` は、2 種類のファイル（lock のファイルと、依存ごとの `package.json`）を読んで渡すだけなので単体テストを持たず、理由を添えて `test/repo/no-unit-test.json` に書く（照らしは `logic/setup/manifest.ts` の単体テストで、読む処理は `setup` の結合テストで確かめる。[README][readme] の「テストで外との境を差し替える方法」の表の下）
- 結合テストは、承認のコードを入れない形（GitHub を読まずにマシンの準備だけ）で、`run` を部屋のやりとりとともに通す。device flow と App を作る手順は、人がブラウザで行う操作を含むので、単体テストで確かめる（「[テスト][b05]」の「偽物」）
