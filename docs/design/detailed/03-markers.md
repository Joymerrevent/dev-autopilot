# 印

進行 Bot が GitHub のコメントに書く印の、書く形・欄の値の形・署名・鍵の読み方・読み方と、AI の文から印の形を取り除く規則を決める。
印の種類と欄の正本は要件の「[印と固定の見出しの一覧][markers]」で、どのときにどの印を書くかと、無効な印をどう扱うかは基本設計の「[状態遷移と判定][b02]」にある。印を扱う処理はどれも判断の層（`marker.ts`・`logic/marker/`）に置き、外に触れない（[README][readme] の「層と依存の向き」）。

## ファイルの一覧

| ファイル | 層 | 受け持つこと | 基本設計 |
| --- | --- | --- | --- |
| `marker.ts` | 判断 | 印の形の正本。種類ごとの欄と値の形の表、印の行の組み立て、印の形の見つけ方と取り除き方、印の行の読み取り（形の確かめ） | 「[状態遷移と判定][b02]」の「印の種類」、「[AI のセッション][b03]」の「共通の決まり」 |
| `logic/marker/sign.ts` | 判断 | 署名する文字列の組み立て、署名、確かめ | 「[状態遷移と判定][b02]」の「印の署名」 |
| `logic/marker/keys.ts` | 判断 | 鍵の一覧のファイルの中身から鍵を読み、問題を返す | 同上 |
| `logic/marker/read.ts` | 判断 | コメント 1 つから、有効な印か、無効な印か、読まないか（人のコメントか、印の無い進行 Bot のコメントか）を決める（投稿者・未編集・印の有無と数・形・署名） | 同上、要件の [IMPL-20][impl] |

- 鍵のファイルを読むのは外との境の `io/secrets.ts`（「[外との境][d01]」の「秘密の置き場」）で、`logic/marker/keys.ts` は読んだ中身（秘密の値の型）を受け取る
- 無効な印を、止める契機にするか、数えない印として無いものとして読むかは、状態の組み立て（`logic/state/`）が決める（「[状態遷移と判定][b02]」の「数えない無効な印」）。`logic/marker/read.ts` は、コメントごとの結果だけを返す
- `marker.ts` と `logic/marker/` が import してよいのは、`marker.ts` と `logic/marker/` の中と、下の「欄の値の形」の記号の一覧のファイルと、秘密の値の型の `logic/secret.ts`（「[外との境][d01]」の「秘密の置き場」）だけ。どれも、印のモジュールを import し返さない

## 書く形

印は、Issue と PR の会話のコメント（REST の issue comments）にだけ書き、そこからだけ読む。PR のレビューのコメント（行のコメント）と、Issue と PR の本文には書かず、読まない。

```text
<!-- dev-autopilot {"type":"review","round":2,"head":"…","result":"fix",…,"sig":"…"} -->
```

- 進行 Bot のコメント 1 つに、印を 1 つだけ書く。コメントの最後の行に、空の行をはさんで置く
- 印の行は、左から `<!--`、`dev-autopilot`、JSON、`-->` を、間に空白を 1 つずつはさんで並べた 1 行にする
- JSON の欄は、`type`、種類ごとの欄（下の「欄の値の形」の表の順）、`sig` の順に書く。読むときは欄の順を見ない（署名は、欄を並べ替えた文字列に掛ける。下の「署名」）
- JSON の文字列の中の `<`・`>`・`&` は、JSON の Unicode のエスケープ（`\u` と小文字の 16 進の 4 文字）で `\u003c`・`\u003e`・`\u0026` と書く。`JSON.stringify` は `<`・`>`・`&` を書き換えないので、組み立てた JSON の文字列の中の `<`・`>`・`&` を置き換える（欄の名前と記号の値は `<`・`>`・`&` を含まないので、置き換わるのは文字列の値の中だけ）。パスなどの値に `-->` や `<!--` があっても、印の行の切れ目がずれないようにするため。読むときは JSON として解くので、元の文字に戻る
- 並びの欄は、JSON の配列で書く。書く側は、数は小さい順、文字列は文字の符号の順に並べ、同じ値を 1 つにする。同じ印をもう一度書くかの判定（「1 回だけ書く」印）は、並びを集合として比べる

## 欄の値の形

欄の名前と意味の正本は要件の「[印と固定の見出しの一覧][markers]」で、本節は各欄の値の形を決める。表に無い欄があるか、必ずある欄が無いか、値の形が合わなければ、読み取りは「形が合わない」とする（下の「読み方」）。

既存の種類に後から欄を足すときは、欄の表に「前の版の印では無くてよい」と書き、足した欄の無い印も形が合うとする。無いときの読み方（判定に使う値）は、欄を足す版が、止める側か、前の版と同じ判断になる値に決めて、同じ表に書く。必ずある欄として足すと、上げた後の最初の実行で、前の版が書いた同じ種類の印がすべて形の違う印になり、開いている作業の単位が一斉に `marker-invalid` で止まるため。今の表の欄は、どれも最初の版の欄で、「持つとき」を書いた欄のほかは必ずある。

| 値の形 | 中身 |
| --- | --- |
| 数 | 0 以上の整数 |
| 番号 | Issue か PR の番号。1 以上の整数 |
| コメントの ID | REST の `id`。1 以上の整数で、JavaScript で誤差なく持てる範囲（`Number.isSafeInteger`） |
| SHA | commit の SHA。小文字の 16 進の 40 文字 |
| ハッシュ | 「[AI のセッション][b03]」の「ハッシュの取り方」のハッシュ。小文字の 16 進の 64 文字 |
| 指摘の ID | 小文字の 16 進の 8 文字（[ADR-20261019-001][adr-repeat] の決定 1） |
| 記号 | 決まった値のどれか。値は表の右の欄に書くか、表のある節を指す |
| モデル | 作業 AI かレビュー AI を起こしたときに `--model` に渡した値。制御文字を含まない 1〜100 文字 |
| ラベル | ラベルの名前（リポの設定の `labels.*` の値）。制御文字を含まない 1〜50 文字 |
| パス | リポの中の相対パス。`/` で区切り、先頭の `/` と、`.`・`..` の部分を持たない |
| 並び | 上の形の値の JSON の配列。空を許すかは欄ごと |

| 種類（`type`） | 置き場 | 欄と値の形 |
| --- | --- | --- |
| `quarantine` | Issue | `target`（記号：`issue`・`instruction`）、`comment`（コメントの ID。`target` が `instruction` のときだけ持つ）、`textHash`（ハッシュ） |
| `draft` | Issue | `source`（記号：`ai`・`instruction`）、`textHash`（ハッシュ） |
| `decision` | Issue | `draft`（コメントの ID）、`textHash`（ハッシュ） |
| `plan` | Issue | `baseHead`（SHA）、`planHash`（ハッシュ）、`model`（モデル） |
| `link` | Issue と PR | Issue に書くときは `pr`（番号）、PR に書くときは `issue`（番号）。どちらか 1 つだけを持つ |
| `review` | PR | `round`（1 以上の数）、`head`（SHA）、`result`（記号：`pass`・`fix`）、`high`・`medium`・`low`・`droppedHigh`（数）、`findings`（指摘の ID の並び。空を許す）、`model`（モデル） |
| `fix` | PR | `round`（数。最初のレビューの前は 0）、`head`（SHA）、`cause`（記号：`check`・`review`・`conflict`）、`model`（モデル） |
| `conflict` | PR | `head`（SHA） |
| `merge` | PR | `head`（SHA）、`result`（記号：`ready`・`human`）、`reasons`（記号の並び。記号は「[状態遷移と判定][b02]」の「マージの判定」の表。`result` が `ready` なら空、`human` なら 1 つ以上） |
| `remind` | PR | `head`（SHA） |
| `stop` | Issue か PR | `reason`（記号。「[状態遷移と判定][b02]」の「止めた理由の記号」の表）、`comments`（コメントの ID の並び。1 つ以上。`reason` が `marker-invalid` で、挙げるコメントがあるときだけ持つ） |
| `wait` | Issue | `blockedBy`（番号の並び。1 つ以上） |
| `dependency-review` | Issue | `dependency`（番号）、`result`（記号：`keep`・`change`） |
| `security` | Issue か PR | `where`（記号：`entry`・`text`・`code`・`leak`）、`finding`（記号。見つかった種類。一覧は検疫と漏えいの検査の詳細設計（`06-text-and-intake.md`）で決め、`logic/text/finding-kinds.ts` に置く） |
| `cleanup` | Issue | 無し |
| `halt` | Issue（全体の停止の Issue） | `issue`（番号） |
| `approval-reset` | Issue | `label`（ラベル）、`reason`（記号：`stale`・`early`・`permission`） |
| `ignored-instruction` | Issue | `comment`（コメントの ID） |
| `manual-push` | Issue | `head`（SHA）、`paths`（パスの並び。1 つ以上） |
| `follow-up` | Issue | `pr`（番号）、`finding`（指摘の ID） |
| `overlap` | Issue | `prs`（番号の並び。1 つ以上）、`paths`（パスの並び。1 つ以上） |

- 置き場が合わない印（PR のコメントにある `plan` の印など）も、形が合わないとする。印を読むときは、コメントが Issue と PR のどちらにあるかを渡す
- `merge` の `result` と `reasons`、`quarantine` の `target` と `comment` のように、欄の間で決まる組み合わせも、形として確かめる。値の意味の組み合わせ（`review` の件数と `result` が合うかなど）は形として確かめず、判定の処理が決める
- 記号の一覧（止めた理由の記号、マージの判定の `reasons` の記号、見つかった種類）は、一覧だけを持ち何も import しないファイルの定数を `marker.ts` が読む：止めた理由は `logic/state/reasons.ts`、マージの判定の記号は `logic/judge/merge-reasons.ts`、見つかった種類（検疫と漏えいの検査）は `logic/text/finding-kinds.ts`。記号を 2 か所に書かないため。`marker.ts` は、印の形を見つけるために検疫のモジュールが import するので、`marker.ts` から判定や検疫のモジュールを import すると、互いに import しあい、入口ごとの import の順で起動の時に止まる（初期化の前の参照）
- 欄を足すときは、版の文字列（下の「署名」の順 3）を上げない。署名は読んだ欄から組み立て直すので、足した欄の無い前の版の印は、前の版と同じ文字列になり、署名が通る
- 進行 Bot の版を戻したとき（`setup rollback`）、新しい版で足した欄を持つ印は、前の版では形が合わず、無効な印になる。止まる側に倒れ、人が中身を確かめて `## 再開` で戻せば、数えない印になる（「[状態遷移と判定][b02]」の「数えない無効な印」）

## 署名

![署名する文字列][fig-sign]

「[状態遷移と判定][b02]」の「印の署名」が、HMAC-SHA256 で `sig` を作ることと、署名する文字列に `sig` を除いた欄と印の置き場を入れることを決めている。本節は、署名する文字列の並べ方を決める（[ADR-20261024-001][adr-model-states] の決定 9 が詳細設計に任せた）。

| 順 | すること |
| --- | --- |
| 1 | 印の欄から `sig` を除き、置き場の欄 `at` を足す。`at` の値は `<owner>/<repo>#<番号>`（`owner` と `repo` はマシンの設定の `repository.*` を小文字にしたもの、番号は印のある Issue か PR の番号）。印の欄に `at` という名前の欄は無いので、ぶつからない |
| 2 | キーを文字の符号の順（JavaScript の文字列の比べ方の順）に並べ替え、空白を入れずに JSON にする（`JSON.stringify`）。値は文字列・整数と、文字列か整数の並びだけなので、文字列の書き方と数の書き方は `JSON.stringify` のとおりに決まる。中の `<`・`>`・`&` も、印の行の書き方と違って、書き換えずに元の文字で入れる |
| 3 | 先頭に、版の文字列 `dev-autopilot-marker-v1` と改行（LF）を足し、UTF-8 のバイト列にする |
| 4 | 鍵の一覧の先頭の行の鍵で、HMAC-SHA256 を掛け、結果を小文字の 16 進の 64 文字にして `sig` に書く |

- 署名する文字列は、印の行の文字を書いたまま使うのでなく、読んだ値から組み立て直す。書き方（欄の順、`<` などの書き方）が違っても、値が同じなら同じ文字列になるため
- 置き場を入れるので、別の Issue や PR に写した印は署名が通らない（[ADR-20261015-004][adr-markers] の決定 1）。リポの名前を変えたときも、すべての印の署名が通らなくなり、止まる側に倒れる。`owner` と `repo` を小文字にするのは、GitHub が大文字と小文字を区別しないので、マシンの設定の書き方の揺れで署名が変わらないようにするため
- 版の文字列は、印の書き方や並べ方を変えるときに上げる（欄を足すだけのときは上げない。上の「欄の値の形」）。上げるときは、前の版の文字列でも確かめる期間を、別の ADR か設計で決める
- 確かめるときは、読んだ値から同じ文字列を作り、一覧の鍵を先頭の行から順に試す。`sig` と計算した結果は、16 進を解いたバイト列で、時間の揃った比べ方（`node:crypto` の `timingSafeEqual`）で比べる。どの鍵で通ったか（一覧の何行目か）を結果に添える。点検が、先頭でない鍵でだけ確かめられた印を warn に出すため（「[状態遷移と判定][b02]」の「鍵を替えるとき」）
- `node:crypto` の `createHmac` と `timingSafeEqual` は、渡した値から結果が決まり外に触れないので、判断の層で使う（`createHmac` と `timingSafeEqual` は、[README][readme] の「構成の検査に足すこと」の許す一覧にある）

## 鍵の読み方

`logic/marker/keys.ts` は、秘密の置き場の `marker-signing-keys` の中身から、鍵の並びを読む。「[状態遷移と判定][b02]」の「印の署名」の決まり（末尾の空白と改行を除く、空の行を読まない、32 バイトでない行と、鍵が 1 つも無いファイルは点検の fail）を、次の形で行う。

- ファイルの先頭に UTF-8 の BOM があれば除く。エディタが付けても鍵が変わらないため
- 改行（LF）で行に分け、各行の末尾の空白（空白・タブ・CR）を除く。除いた後に空の行は読まない
- 残った行は、標準の base64 の 44 文字（英数字と `+`・`/` の 43 文字の後に `=` が 1 つ）でなければならない。先頭の空白、URL 用の base64（`-`・`_`）、改行で折った base64 は、解ける形でも問題にする。解いて 32 バイトにし、解いた値を base64 に戻して元の行と同じになるか（余りのビットが 0 か）も確かめる
- 問題は、行の番号と種類（形が違う・長さが違う・鍵が無い）だけを返し、行の中身を返さない。点検の表示と記録に、鍵の値が出ないようにするため
- 鍵は秘密の値の型（`logic/secret.ts`）のまま持つ。中身を取り出すのは、`logic/marker/keys.ts` が行を解くときと、`logic/marker/sign.ts` が HMAC を掛けるときだけにし、解いた鍵も秘密の値の型に入れ直す（「[外との境][d01]」の「秘密の置き場」の一覧）

## 読み方

![コメントの印を読む][fig-read]

`logic/marker/read.ts` は、コメント 1 つ（投稿者、未編集か、本文、Issue か PR か、置き場の番号）と、鍵の並びと、進行 Bot のアカウントの一覧（リポの設定の `safety.botAccounts`）を受け取り、次の順に確かめて結果を返す（[IMPL-20][impl]）。

| 順 | 確かめること | 外れたときの結果 |
| --- | --- | --- |
| 1 | 投稿者が、進行 Bot のアカウントのどれか | 読まない（人のコメント。印の形があっても、印として読まない） |
| 2 | コメントが未編集（GitHub の事実。「[状態遷移と判定][b02]」の「状態の組み立て」） | 無効（`edited`） |
| 3 | 本文に印の形がある（下の「印の形の見つけ方」） | 読まない（印の無い進行 Bot のコメント。人の投稿として読む。[ADR-20261015-004][adr-markers] の決定 1） |
| 4 | 本文の印の形が 1 つだけ | 無効（`count`）。2 つ以上 |
| 5 | 印の形が、上の「書く形」の 1 行のとおりで、JSON の欄と値が「欄の値の形」のとおり（置き場を含む） | 無効（`shape`） |
| 6 | 一覧のどれかの鍵で署名が通る（上の「署名」） | 無効（`signature`） |

- どれにも外れなければ、有効な印として、欄の値と、通った鍵の行を返す
- 無効の結果には、コメントの ID と、外れた順の記号だけを添える。止めた理由のコメントと `stop` の印の `comments` に、どのコメントかを書くため（「[状態遷移と判定][b02]」の「止めた理由の記号」の `marker-invalid`）
- 結果は 4 つ：有効、無効、読まない（人のコメント）、読まない（印の無い進行 Bot のコメント。人の投稿として読む）
- 進行 Bot のアカウントの、印の形の無い未編集のコメントは、印として読まず、人の投稿として読む（[ADR-20261015-004][adr-markers] の決定 1。「進行役のアカウント」は `safety.botAccounts` のどれかと読む。[ADR-20261020-001][adr-bots] の決定 3）。見出しとして読むかは、ほかの人のコメントと同じく、書いた人の権限で決める
- 編集されたコメントは、印の形が無くても無効（`edited`）にする。進行 Bot は印の無いコメントを書かないので、編集で印が消えたものと読む（要件の [FLOW-40][flow] の「印の書き換え」と、[IMPL-20][impl] の (b)、[ADR-20261015-004][adr-markers] の決定 1 の追記（2026-11-11））。人が印を編集で消して、止める印を黙って無くす形を作らないため

### 印の形の見つけ方

印を読む処理と、AI の文から取り除く処理は、同じ見つけ方を使う（[IMPL-20][impl]、「[AI のセッション][b03]」の「共通の決まり」）。

- 見つけ方：`<!--` の後に空白（空白・タブ・改行）を 0 個以上はさみ、`dev-autopilot` が続くところから、次の `-->` まで（`-->` が無ければ文の終わりまで）を、印の形とする。`dev-autopilot` の英字の大小は区別しない
- 見つけ方は広く取り、受け入れる形（上の表の順 5（書く形と欄の値の形の確かめ））は狭く取る。進行 Bot が書かない揺れ（空白の数、大文字、改行）も印の形として数え、有効な印にはしないため。揺れた印の形が進行 Bot のコメントにあれば、印の数（順 4）か形（順 5）で無効になる

## AI の文から印の形を取り除く

AI の文の欄を GitHub に書く前に、`marker.ts` の取り除く処理に通す（「[AI のセッション][b03]」の「共通の決まり」）。

- 上の「印の形の見つけ方」で見つけた印の形を、すべて取り除く。レビューのコメントの区切りの行の形（`<!--` の後に空白を 0 個以上はさみ、`dap-finding` が続くところから、次の `-->` まで。形の正本は「[AI のセッション][b03]」の「レビューのコメントの形」）も、同じ見つけ方で取り除く
- 取り除いた後の文をもう一度探し、見つからなくなるまで繰り返す。取り除いた跡の前後がつながって、新しい印の形ができることがあるため（例：`<!-` と `- dev-autopilot …` の間にあった印の形を取り除くと、`<!-- dev-autopilot …` がつながる）
- 取り除いたかどうかは、結果に添える。手元の記録に残すため（取り除いた文の中身は残さない）

## 要件の表との突き合わせ

`marker.ts` の種類の表は、要件の「[印と固定の見出しの一覧][markers]」と一致させる（[ADR-20261024-001][adr-model-states] の決定 9）。構成の検査（`test/repo/`）で、要件の表の 1 列目の種類の名前の集合と、`marker.ts` の種類の名前の集合が同じことを確かめる。欄の名前は、要件の表の欄の列が文で書かれていて機械で取り出せないので、PR のレビューで照らす。

## テスト

| ファイル | 単体テストで確かめること |
| --- | --- |
| `marker.ts` | 種類ごとに、書いた印の行を読むと同じ値に戻ること。表に無い欄、必ずある欄が無いとき、値の形が違うとき、置き場が違うとき、欄の間の組み合わせが違うとき（`merge` の `result` と `reasons` など）に、形が合わないとすること。`<`・`>`・`&` を `\u003c`・`\u003e`・`\u0026` に書き換えて書くこと（例：`paths` が `["a-->b<&c"]` の `manual-push` の印の行が `"a--\u003eb\u003c\u0026c"` を含み、`-->` を印の行の終わりのほかに含まないこと）。読み戻すと元のパスに戻ること。「前の版の印では無くてよい」欄を持つ種類の表（テストの中で作る表）で、足した欄の無い印を形が合うとし、署名が通ること。見つけ方が、空白の揺れ・大文字・改行・`-->` の無い印の形を見つけること |
| `marker.ts`（取り除く） | 取り除いた後につながってできる印の形も取り除くこと。`dap-finding` の形も取り除くこと。印の形の無い文を変えないこと |
| `logic/marker/sign.ts` | 決めた入力（欄・置き場・鍵）に対する `sig` が、前もって計算した値と同じこと（並べ方と版の文字列を変えると落ちる）。欄の順を変えて書いた印でも同じ `sig` になること。置き場を変えると通らないこと。2 行目の鍵で書いた印が、何行目の鍵で通ったかを返すこと |
| `logic/marker/keys.ts` | BOM・CR・末尾の空白・空の行を除いて読むこと。先頭の空白、URL 用の base64、43 文字や 45 文字の行、余りのビットが 0 でない行、空のファイルを問題にすること。問題に行の中身を含めないこと |
