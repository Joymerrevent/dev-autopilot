# 点検

点検の組ごとの処理の分け方、結果の形、組の順と前提、試しのセッションを省く判定と結果の決め方、`setup` の読み戻しと共有する比べる規則、人が呼ぶ `check` の処理を決める。
点検の項目の正本は要件の [SETUP-2][setup] で、項目の組と、いつ・どう確かめるかは基本設計の「[導入と点検][b04]」の「点検」にある。本書は、項目を並べ直さず、組の処理の作りを決める。

- 試しのスクリプト `entry/check-probe.ts` は、ファイルとプロセスに触れるので入口の層に置く。セッションのフォルダに写して `node` で動かすので、`node:` で始まるモジュールのほかを import しない（写した先に `plugin/src/` も `node_modules` も無いため。[README][readme] の「入口ごとの import の範囲」）
- 試しのスクリプトは、ほかのファイルを import できないので、試しの処理を自分で持つ（入口を薄くする決まりの例外。[README][readme] の「層と依存の向き」）。外に触れる関数（読む、書く、一覧を出す、子プロセスを起こす）を引数で受ける形にし、既定の値を `node:` の関数にする。`node` で直接起こされたとき（`process.argv[1]` の実体のパスが自分のファイルのとき）だけ試しを行い、import されたときは何もしない。単体テストで偽物を渡すため
- 組の処理は、外との境を型だけで受け取り、入口が組み立てた実体を引数で受ける（[README][readme] の「層と依存の向き」）
- 短い一時フォルダの長さは、マシンの組が短い一時フォルダの根を作った後に、根の実体のパスと uid を `logic/settings/relations.ts` の長さの関数に渡して数える（「[設定と記録][d02]」の「設定の表を 1 か所に持つ」）
- 止めなかったプロセスの項目は、`check.ts` が呼ぶ側から受け取った、前の実行が残したセッションの片付けの結果から、次のとおり決める（「[導入と点検][b04]」の「組と回数」の表の下、「[AI のセッション][b03]」の「前の実行が残したセッション」の順 2（見つけたセッションごとに残りを探して止める順）・順 3（置き場の `sessions/` と短い一時フォルダの根の全体を探す順））
  - 全体の探し方（順 3）で見つけたプロセスのうち、`session-not-stopped` で人に渡したセッションのフォルダか短い一時フォルダの中のものは `warn`、フォルダの外のものは `fail`
  - 止められなかったセッションのうち、作業の単位を持たないもの（受け入れの依頼の実行のセッション（名前が `verify-intake-issue-` で始まるもの）と、点検の試しのセッション（名前が `check-` で始まるもの）。「[AI のセッション][b03]」の「前の実行が残したセッション」の順 2）は `fail`
  - 止められなかったセッションのうち、作業の単位を持つものは `warn`（作業の単位は、順 8 で停止中（`session-not-stopped`）にし、ほかの作業の単位は続ける。「[1 回の実行の流れ][d08]」の「作業の単位の進め方」、「[導入と点検][b04]」の「組と回数」の表の下）。作業の単位が順 7 の作業の単位に無く停止中にできないときも、人が残りを止め、次の実行が残りが無いと確かめるまで、毎回の実行の点検に `warn` で出る
- 見つかりの記録の項目（`machine.security-pending`）は、`flow/check/machine.ts` が、実行の順 2 と同じ `flow/run/records.ts` の読む関数で記録の置き場の `security-pending/` を読み、読んだ結果（ある・無い・読めない。決め方は「[設定と記録][d02]」の「見つかりの記録」）から次のとおり決める。どれも `warn` までで、[SETUP-2][setup] の fail に当てない（AI のセッションだけを起こさず、AI を使わない工程は続ける。[ADR-20261111-001][adr-halt-records] の決定 3 と影響）。どれも、見つかった文は出さない
  - 無い：`pass`
  - ある（どの記録も、前の実行が書き直していないだけ）：`warn`、`reason` は `pending`（`details` に、すべての記録の作業の単位の Issue の番号と見つけた時刻。次の定期の実行が GitHub に印を書き直すことを、決まった文で示す）
  - ある（書き直せずに残した記録がある）：`warn`、`reason` は `rewrite-failed`。書き直せずに残したかは、見つけた時刻より後の `runs.jsonl` の行と、順 10 では今の実行の書き直した結果で数える（数え方は `logic/run/records.ts`）。`details` に、すべての記録の番号と見つけた時刻と、書き直せなかった記録には回数と最後の時刻と最後の理由の種類（断られた（HTTP の状態）・届いたか分からない・合図が `run` でない・Issue を引けない）。決まった文で、人は記録を消さず、書き直せない原因（App の権限や導入先、全体の止める合図、つながらないなど）を直すことと、直せば次の実行が書き直して消すことを示す
  - 読めない（ほかに読める記録があっても）：`warn`、`reason` は `unreadable`（`details` に、読めないファイルごとのパスと、名前から読めた作業の単位の Issue の番号。番号を読めない名前のファイルはパスだけ、フォルダを読めないときはフォルダのパス。読める記録の番号と見つけた時刻も）。決まった文で、人の戻し方を示す
  - 2 つ以上に当たるときは、`unreadable`・`rewrite-failed`・`pending` の順で最初の 1 つを `reason` にし、`details` にはすべてを挙げる
  - 人の戻し方は「[状態遷移と判定][b02]」の「記録の置き場のほかのファイル」の表の下（人が消すのは読めない記録だけ。手がかりの読み方は「[設定と記録][d02]」の「見つかりの記録」）

## 結果の形

`logic/check/result.ts` に、項目の結果の形を持つ。点検の結果のファイル（`check-result-<依頼の ID>.json`。「[設定と記録][d02]」の「依頼と結果のファイル」）、`status.json` の点検の欄、実行の記録は、どれも同じ形で項目を書く。

| 欄 | 中身 |
| --- | --- |
| `id` | 項目の ID。`<組>.<項目>` の形（例：`github.rulesets`、`machine.os`）。組は `settings`・`machine`・`app`・`github`・`probes`・`sandbox`。項目は英小文字と数字を `-` でつないだもの |
| `level` | `pass`・`warn`・`fail` |
| `unverified` | 未確認の warn のときだけ、理由の記号（`stop-signal`：全体の止める合図が `run` でない間（`stop`、ほかの値、変数が無い、読めない）。`halt-issue`：全体の停止の Issue がある間（読めなかったときと、開き直しの条件に当たる作業の単位があるとき（「[1 回の実行の流れ][d08]」の「全体の停止と通知」）と、見つかりの記録があるとき（[ADR-20261111-001][adr-halt-records] の決定 1）を含む）。`setup-day`：記録の目印のファイルを作った日）。2 つ以上に当たるときは、`stop-signal`・`halt-issue`・`setup-day` の順で最初の 1 つを書く |
| `reason` | fail と warn の理由の記号。項目ごとに決める。確かめようとして確かめられなかった fail は `unchecked`（前の組が fail で前提が欠けた、応答が読めない、時間の上限を過ぎた）。試しのセッションを起動できなかった fail は `not-started`、試しのセッションの安全設定のファイルが書き換えられた fail は `settings-tampered`（下の「試しのセッションの判定」） |
| `details` | 人が直すための値の並び。1 つの値は種類と値の組で、種類は次だけ：数（Issue と PR の番号、鍵の行の番号、PID、HTTP の状態、起動の前の確かめの順の番号）、時刻（UTC の ISO 8601）、名前（ラベル、必須チェック、ruleset、Environment、App の名前と ID、App の権限の名前と読み取りか書き込みか、通知の種類、プロセスのコマンドの名前）、ref の形（ruleset の対象の `refs/heads/<型>/issue-*` など）、パス（リポの中のパスと、マシンの中のパス（置き場・記録の置き場・短い一時フォルダの根・マシンの設定のフォルダ・道具のフォルダなど）。秘密の置き場とその下は入れない）、版 |

- 項目の ID の一覧は `logic/check/items.ts` に持ち、ID ごとに、確かめる基本設計の項目（「組と回数」の表の項目）を書き添える。点検の項目の正本は要件と基本設計なので、本書には一覧を写さない
- 人に見せる文は、ID と `level` と `reason` ごとに `logic/check/items.ts` が持つ決まった文にする。外から読んだ文（GitHub の応答の `message`、ファイルの中身）を、書き換えずに文に入れない。人の `check` と setup は `check.ts` を import できない（[README][readme] の「入口ごとの import の範囲」）ので、文を判断の層に置いて共有する
- `details` に、秘密（鍵の値、トークン、JWT、Webhook の URL、秘密の置き場のファイルの中身）と、秘密の置き場の実体のパスを入れない。鍵は行の番号で示す（「[状態遷移と判定][b02]」の「印の署名」）。結果のファイルは記録の置き場にあり、人の Claude Code の文脈にも入るため
- 全体の結果は、fail が 1 つでもあれば `fail`、無くて warn があれば `warn`、どちらも無ければ `pass`。未確認の warn も warn に数える（[SETUP-2][setup] の「fail が 1 つでもあれば作業に入らない」は、`fail` だけを見る）
- 確かめられなかったものを pass にしない。組の処理が思わない失敗で止まったら、止まった組でまだ結果の無い項目をすべて `fail`（`unchecked`）にして、次の組へ進む。まだ結果の無い項目を `fail`（`unchecked`）で埋める処理は、`check.ts` の外（`flow/run/run.ts` の思わない失敗の後始末。「[1 回の実行の流れ][d08]」の「終わり方と終了コード」）からも呼べる関数として持つ

## 組の順と前提

![組の順と前提][fig-groups]

`check.ts` は、組を次の順に呼ぶ。前の組の結果が、後の組の前提になるため。
`check.ts` は、呼ぶ側（`flow/run/run.ts`）から、`RunContext` の合図（全体の止める合図の値と、全体の停止の Issue の有無）と、前の実行が残したセッションの片付けの結果を引数で受ける（「[1 回の実行の流れ][d08]」の「1 回の実行の中で持つ値」）。順 10（実行の終わりの点検）で行い直すときは、読み直した合図と、今の実行で止められなかったセッションを足した片付けの結果と、同じ実行の順 5 の sandbox の組の結果（下の「試しのセッションを省く判定」の (2)）と、`RunContext` の見つかりの記録を書き直した結果（上の「ファイルの一覧」の表の下の `rewrite-failed`）を受ける（「[1 回の実行の流れ][d08]」の「起こされ方と進む順」の表の下）。

| 順 | 組 | 前提（欠けたら、組の項目を `fail` の `unchecked` にする） | 毎回の実行の最初 | `setup`・人の `check` |
| --- | --- | --- | --- | --- |
| 1 | 設定 | 無し（マシンの設定を読めないときは、記録の置き場も分からず結果を書けない。「[導入と点検][b04]」の「点検だけで動かす仕組み」） | 行う | 行う |
| 2 | マシン | マシンの設定を読めた | 行う | 行う |
| 3 | アプリの権限 | マシンの設定の `githubApp.*` と秘密鍵がある | 読み取りは行う。書き込みの権限の試しは、試しの直前に読み直した合図が `run` のときだけ | 読み取りは行う。書き込みの権限の試しは、試しの直前に読み直した合図が `run` のときだけ |
| 4 | GitHub | インストールのトークンを作れた（順 3 の読み取りが通った）。リポの設定を読む項目は、リポの設定を読めた | 行う | 行う |
| 5 | 子プロセスと clone | リポの設定を読めた（AI のセッションの環境変数を組み立てるため） | 行う | 行う |
| 6 | sandbox と AI のセッション | 順 1〜5 に `fail` が無い | 省く条件（下の「試しのセッションを省く判定」）に当たらず、合図が `run` で、全体の停止の Issue が無いときだけ | 合図が `run` で、全体の停止の Issue が無いときだけ（省く条件は掛けない） |

- 順 6 は、前の組に `fail` が 1 つでもあれば、試しのセッションを起こさずに、sandbox の組の項目を `fail`（`unchecked`。表の見出しの、前提が欠けたとき）にする。壊れた環境で AI のセッションを起こさないため。基本設計の「GitHub の組の、base ブランチの先端に local の設定と指示が無いことの確かめが fail なら、試しのセッションを起こさない」を、前の組の `fail` のすべてに広げた形
- 全体の止める合図が `run` でない間（`stop`、ほかの値、変数が無い、読めない）は、書き込みの権限の試し（順 3）と試しのセッション（順 6）を行わず、`warn`（`unverified` が `stop-signal`）にする（[ADR-20261017-007][adr-stop] の決定 1・2）。書き込みの権限の試しの前には、`flow/safety/signal.ts` で合図を読み直す（GitHub に書き込む前に合図を読む決まり。「[状態遷移と判定][b02]」の「1 回の実行の流れ」の表の下）。試しのセッションは、起動の前の確かめ（「[AI のセッション][d07]」の「セッションの順」の 1）で合図と全体の停止の Issue を読み直す
- 全体の停止の Issue がある間（`RunContext` の全体の停止の Issue が「ある」の間。読めなかったときと、見つかりの記録が「ある」か「読めない」ときを含む。[ADR-20261111-001][adr-halt-records] の決定 1）は、試しのセッションが要るときも行わず、`warn`（`unverified` が `halt-issue`）にする。書き込みの権限の試し（順 3）は、AI のセッションを起こさないので行う（[ADR-20261024-005][adr-security] の決定 3。AI を使わない工程は続ける）
- 試しのセッションの起動の前の確かめ（「[AI のセッション][d07]」の「セッションの順」の 1）は、作業の単位の Issue の印も読み、開き直しの条件に当たる作業の単位があれば `not-started`（扱いは `deferred`）を返すので、下の「試しのセッションの判定」の表の全体の停止の Issue の行で、`halt-issue` の warn にする
- 記録の目印のファイルを作った日は、試しのセッションを行わず、`warn`（`unverified` が `setup-day`）にする（「[導入と点検][b04]」の「組と回数」の表の下）
- 人が呼ぶ `check` で入れた Plugin と写しの版が違うことの warn は、人の Skill だけが確かめる（定期の実行は入れた Plugin の場所を知らない）。`flow/skill/check.ts` が結果を表示するときに足す
- 1 つの組の中の項目は、互いに前提を持たない限り、すべて確かめる。最初の `fail` で組を止めない。人が 1 回の点検で直すものをまとめて知るため

## 試しのセッションを省く判定

`logic/check/trial-skip.ts` は、前の試しのセッションの記録と今の値を受け取り、省くかを返す（「[導入と点検][b04]」の「組と回数」の表の下の 5 つの条件）。前の記録は、`flow/check/trial.ts` が手元の記録の 2 つから読む。(1) `sessions.jsonl` の、試しのセッションの最新の終わりの行の、省く条件の値と試しの結果（終わりの行に試しの結果を入れる時は、下の「試しのセッションの判定」。残す欄の正本は「[状態遷移と判定][b02]」の「手元の記録」）。(2) 最後に行った点検の sandbox の組の結果。`runs.jsonl` の、sandbox の組の結果を持つ最新の行のうち、後に行った点検（順 10 があれば順 10）の結果（行には、行った点検ごとの結果が行った順に並ぶ。「[設定と記録][d02]」の「手元の記録」）。順 10 で点検し直すときは、今の実行の行をまだ書いていないので、呼ぶ側から受けた同じ実行の順 5 の結果を最新とする。(2) は、試しを起こさなかった回と起動できなかった回（終わりの行を書かない）を見分けるために読む。

- 省く条件の値は、`claude --version` の出力、条件のハッシュ、写しの版、OS の版（macOS は `sw_vers -productVersion`）の 4 つと、前の結果が `pass` であること
- 条件のハッシュは、試しのセッションに渡す安全設定と、環境変数の名前の並びと、マシンの設定の `sessionTmp.*` を、1 つの JSON にして取る SHA-256（16 進）。安全設定は、`logic/session/sandbox.ts` に、セッションごとに変わる値を決まった値にして渡して組み立てる。セッションの名前は `check-hash`、セッションのフォルダは `<置き場>/sessions/check-hash`、短い一時フォルダは `<短い一時フォルダの根の実体のパス>/<sessionTmp.idLength 文字の 0 の並び>`。ハッシュのためにフォルダは作らず、パスの文字だけを渡す。セッションごとに変わるパス（セッションのフォルダ、短い一時フォルダ）を、毎回同じにするため（「[導入と点検][b04]」の「組と回数」の表の下の、セッションごとに変わるパスを除いたハッシュ）
- JSON は、印の署名と同じく、キーを文字の符号の順に並べて空白を入れない（「[印][d03]」の「署名」の順 2）。キーの順で同じ値のハッシュが変わらないため
- 前の記録が無い、読めない、(1) の試しの結果が `pass` でない、(2) が `pass` でない（`fail`・未確認の `warn`。試しを起こさなかった回と起動できなかった回を含む）ときは、省かない（「[導入と点検][b04]」の「組と回数」の表の下の「fail・未確認・起動できなかった回の後は、毎回回し直す」）

## 試しのセッションの判定

`flow/check/trial.ts` は、「[導入と点検][b04]」の「試しのセッション」の手順で試しのセッションを起こし、判定の元を集める。`logic/check/trial-judge.ts` は、集めた元から項目の結果を決める。判定の決まりは基本設計の「試しのセッション」のとおりで、本節は判定の元の受け渡しを決める。
`flow/check/trial.ts` は、`flow/session/run.ts` に、終わりの行に足す値を決める関数を渡す。関数は、ディスクの有無を確かめ、`logic/check/trial-judge.ts` で項目の結果を決め、試しの結果（pass か fail と項目ごとの結果）と省く条件の値（上の「試しのセッションを省く判定」の 4 つ）を返す。`flow/session/run.ts` は、セッションの順 9（数える順）で終わりの行を書く前に関数を呼び、返った値を終わりの行に入れる（「[AI のセッション][d07]」の「セッションの順」、「[状態遷移と判定][b02]」の「手元の記録」）。`flow/session/run.ts` は、関数が返した値を返す値にも添えるので、`flow/check/trial.ts` はその値を、その回の sandbox の組の項目の結果にする（終わりの行を読み直さない。ディスクの有無を 2 回確かめて、結果が食い違わないため）。終わりの行を書かない終わり方（`not-started`・`not-stopped`）では、終わりの行に試しの結果が残らないが、その回の sandbox の組の結果（`pass` でない）が `runs.jsonl` に残るので、次の実行は省かない（上の「試しのセッションを省く判定」の (2)）。

| 判定の元 | 集め方 | 渡す形 |
| --- | --- | --- |
| 試しのスクリプトの出力 | `stream-json` の Bash の呼び出し（`tool_use`）のうち、決めたコマンド（試しのスクリプトのパスと、値を確かめる試しの期待する値（`$TMPDIR` に期待する `<短い一時フォルダ>/claude-<uid>`、store が入るはずのセッションの `tmp/`、`NODE_USE_ENV_PROXY` に期待する `1`）を引数に置いたもの。進行 Bot が組み立てる）と全体が一致するものの結果（`tool_result`）の文 | 1 行に 1 つの JSON（`{"probe":"<試しの名前>","ok":true}` の形）。`ok` は、試しの名前が述べること（読めた・書けた・一覧を出せた・値が引数の期待する値と同じだった）が成り立ったか。形の違う行は数えない |
| Read と Write の道具 | `stream-json` の Read と Write の呼び出しと結果、`result` の `permission_denials` | 呼び出しごとのパスと、結果がエラーか、拒否に載ったか |
| 道具の一覧 | `init` のイベントの道具の一覧と MCP のサーバーの一覧 | 名前の並び |
| 自動のメモリ | `assistant` のメッセージと `result` の文 | 文 |
| ディスクの有無 | 書けないはずのパスにファイルができたかを、進行 Bot が試しの後に確かめる | パスごとの有無 |
| 終わり方 | ターン・時間・費用の上限に当たったか、出力を読めたか | 記号 |

- 試しのスクリプトは、試しの名前ごとに、読めたか・書けたか・一覧を出せたか・値が引数の期待する値と同じだったかだけを出力し、読めたファイルの中身と読んだ値を出力しない。期待する結果との照らしは `logic/check/trial-judge.ts` だけが行う（「[導入と点検][b04]」の「試しのセッション」）。試しのスクリプトはほかのファイルを import できないので、試しの名前の並びを自分で持つ。`logic/check/trial-judge.ts` の並びと同じことを、単体テストで確かめる
- 決めたコマンドの Bash が 1 回も無い、決めたコマンドと違う Bash がある、試しの名前が出力に 1 つでも欠けている、出力を読めないときは、該当する項目を `fail` にする。確かめられなかったものを pass と読まないため
- 項目の ID は、基本設計の「確かめる項目」の表の行ごとに 1 つ持つ（例：`sandbox.bash-read-denied`、`sandbox.read-tool`、`sandbox.tools-list`）
- 試しのセッションの終わり方（「[AI のセッション][d07]」の終わり方の記号）ごとに、sandbox の組の結果を次のとおりに決める（`logic/check/trial-judge.ts`）

  | 終わり方 | sandbox の組の結果 |
  | --- | --- |
  | `not-started`（起動の前の確かめの順 1 の合図。理由は `stop-signal` か `signal-unreadable`） | 項目を `warn`（`unverified` が `stop-signal`） |
  | `not-started`（起動の前の確かめの順 1 の全体の停止の Issue。扱いは `deferred`） | 項目を `warn`（`unverified` が `halt-issue`） |
  | `not-started`（ほかの順。費用の上限、短い一時フォルダの根の異常など。記録の目印のファイルを作った日を含む。目印の日は、`check.ts` が試しを起こす前に見て `setup-day` の warn にする（上の「組の順と前提」）ので、ふつうはここに来ない）、`prepare-failed` | 項目を `fail`（`not-started`）。`not-started` なら、`details` に外れた起動の前の確かめの順の番号を入れる（「[導入と点検][b04]」の「組と回数」の表の下の、回すべきときに起動できないときは fail） |
  | `settings-tampered` | 項目を `fail`（`settings-tampered`）。安全設定の守りが効いていない疑いのため |
  | `not-stopped` | 項目を `fail`（`unchecked`。関数を呼ばず、残りが動いているので、判定の元を確かめ切れない）にし、ほかに、マシンの組の止めなかったプロセスの項目を `fail` に直す。終わりの行を書かず、残ったプロセスの PID とフォルダを `runs.jsonl` に書く（作業の単位を持たないセッションの扱い。人が残りを止めた後の実行が、前の実行が残したセッションとして探し直す） |
  | ほかの記号（`done`、上限に当たった、`error` など） | 項目は判定の元から決める（`flow/session/run.ts` が返した関数の値。上の箇条のとおり、上限に当たったときと出力を読めないときは `fail`） |

- `not-started` は、セッションの終わり方の記号の `not-started` と同じ意味（起動の前の確かめに外れた）で使う

## 共有する比べる規則

### ruleset の比べ方

`logic/check/rulesets.ts` は、設定（`baseBranch`、`checks.required`、`labels.branchTypes`、`labels.defaultBranchType`、`push.rulesetBypassApps` の ID）から 3 つの ruleset の期待する形（「[導入と点検][b04]」の「ruleset の形と確かめ方」の表）を作り、読んだ ruleset と比べて違いの一覧を返す。`setup` の読み戻しと点検が、同じ関数を使う。

- 違いごとに、守りが弱い向きか（PR 必須でない、force push を許す、必須チェックが足りないか strict でない、`active` でない、base ブランチが対象に無い、作業ブランチの形より広い除外、bypass に許した者のほかがある）か、守りが弱い向きでない違い（設定に無い型の除外など）かを付ける。点検は、守りが弱い向きの違いを `fail`、守りが弱い向きでない違いを `warn` にする
- 読んだ ruleset に `bypass_actors` が無い（進行 Bot の App のトークンで読んだ。FACT-88・91）ときは、bypass を比べず、「bypass を比べていない」と結果に付ける。点検は、ruleset の控え（`DEV_AUTOPILOT_RULESETS`）の ID と `updated_at` と、`current_user_can_bypass` で確かめる（「[導入と点検][b04]」の「ruleset の形と確かめ方」の確かめ方）。`setup` は、`bypass_actors` が返る認証で読み、bypass も比べる
- 控えの形（`{"<ruleset の ID>": "<updated_at>"}`）を読む関数と、`setup` が控えを書くときの組み立ても、同じファイルに持つ

### App の権限の比べ方

`logic/check/app-permissions.ts` に、進行 Bot の App の権限の表（「[導入と点検][b04]」の「GitHub App の権限」の表）を定数で持つ。インストールのトークンへの引き換えの本文の `permissions`（「[外との境][d01]」の「JWT で呼ぶ 3 つの API」）も、同じ定数から作る。表を 2 か所に書かないため。

- インストールの情報の `permissions` と表を比べ、表に無い権限（`extra`）、表より強い権限（`stronger`。表で読み取りとした権限が書き込み）、表にあって無いか弱い権限（`missing`）を返す。点検は、3 つとも `fail` にする。基本設計は前の 2 つを fail とし、`missing` は書いていないが、足りない権限では進行 Bot の書き込みが途中で断られ、作業の単位が半端な状態で止まるので、作業に入る前に止める
- `repository_selection` が `selected` でないこと、インストールが読めるリポに当てる先のリポのほかがあることも、同じ関数で返す。インストールが読めるリポは、`io/github-token.ts` の `readInstallationRepositories` で読んだリポの名前の一覧で比べる（リポを絞らずに作ったトークンで読む。当てる先のリポに絞ったトークンでは、ほかのリポに入っていても 1 件だけが返る。[FACT-124][facts]、「[導入と点検][b04]」の「GitHub App の権限」）。一覧を読めなければ、ほかの読めない項目と同じく `fail`（`unchecked`）にする

### Environment の規則の照らし

`logic/check/fnmatch.ts` は、Environment の使えるブランチの規則（`deployment-branch-policies` の `name`）が、ブランチの名前に当たるかを決める。GitHub の当たり方は、[FACT-101][facts] の 6 つの規則（`main`・`*`・`**`・`feat/issue-*`・`refs/pull/*/merge`・`**/*`）と 2 つの名前の組で、Ruby の `File.fnmatch` に `File::FNM_PATHNAME` を付けたときと同じだった。同じ当たり方を TypeScript で書き、GitHub の振る舞いを確かめていない書き方は、当たる側に倒す（下の箇条）。

| 書き方 | 当たり方 |
| --- | --- |
| `*` | `/` のほかの 0 文字以上 |
| `?` | `/` のほかの 1 文字 |
| `[…]` | 括弧の中の 1 文字（`a-z` の範囲、先頭の `!` か `^` で否定）。`/` には当たらない |
| `**/` | 0 個以上のフォルダ（`**/*` は `/` を含む名前にも当たる） |
| `\` | 次の 1 文字を、記号でなく文字として当てる |

- `FNM_DOTMATCH` と `FNM_EXTGLOB` を付けない当たり方にする。`/` の後と名前の先頭の `.` には、`*` と `?` と `[…]` が当たらない。`{` を含む規則は、GitHub が括弧を広げるか（`FNM_EXTGLOB`）を確かめていないので、照らさずに、作業ブランチと PR に当たるものとして扱う（点検は fail）
- 点検は、規則のどれかが、作業ブランチの形（`labels.branchTypes` と `labels.defaultBranchType` の型ごとの `<型>/issue-<番号>`）か、PR の名前の形（`refs/pull/<番号>/<名前>`。名前は `/` を含まない 1 文字以上。[ADR-20261028-001][adr-ci-secrets] の決定 2 の `refs/pull/*`。`pull_request` の CI は `refs/pull/<番号>/merge` と照らした。FACT-99）の、どれか 1 つの名前にでも当たりうれば fail にする（番号は 1 以上の整数。[ADR-20261028-001][adr-ci-secrets] の決定 2）。当たりうるかは、見本の名前で照らさず、規則と名前の形の両方に当たる名前が 1 つでもあるかを、規則と名前の形を先頭から 1 文字ずつ並べてたどって決める（たとえば `feat/issue-2*` と `refs/pull/[2-9]*/merge` は当たりうる。「[導入と点検][b04]」の「GitHub の準備」の表の下）
- 当たり方が Ruby と同じことは、手元の Ruby の `File.fnmatch` で作った前提データ（`fixtures/fnmatch/`。規則・名前・当たるかの組）で確かめる。[FACT-101][facts] の 6 つの規則と 2 つの名前の組を含める。パスの照らしで、本物の git で作った前提データを使うのと同じ考え方（「[設定と記録][d02]」の「パスの照らし」）

## 人が呼ぶ check

`flow/skill/check.ts` は、「[導入と点検][b04]」の「点検だけで動かす仕組み」の順 1〜5 のうち、人の側（順 1・2・5）を受け持つ。点検の処理は持たず、`check.ts` と `flow/check/` を import しない（[README][readme] の「入口ごとの import の範囲」）。

- 依頼を置くコマンドと、結果を消すコマンドは、Skill が人の許可を得て sandbox の外で動かす。`entry/check.ts` は、書く先のパスと書く中身（依頼の ID・置いた時刻・待つ時間）を、人が読めるコマンドの文の形で返す。コマンドは、`node` の 1 行で、書く先のパスと中身を引数に置く（秘密を含まないので、引数に置いてよい）
- 人の Skill が共有する読み取り（`flow/skill/context.ts`。受け持ちとテストは「[設定と記録][d02]」の「ファイルの一覧」と「テスト」）で、マシンの設定と `run.lock` と `status.json` と依頼に書く待つ時間を読む
- 依頼に書く待つ時間は、`status.json` のリポの設定の値の欄（進行 Bot が base ブランチの先端のリポの設定から最後に読んだ `run.checkWaitMinutes`。「[設定と記録][d02]」の「status.json」）から読む。`status.json` が無い（`setup` の順 9 の点検など、進行 Bot がまだ 1 回も動いていない）か、欄が無いか、設定の表の型と範囲に合わなければ、設定の表の初期値（`logic/settings/` の表）を使う。人の Skill は、作業コピーの `.claude/dev-autopilot.json` を読まない（別のブランチか古い版でありうるため）
- 依頼の ID は、「[設定と記録][d02]」の「実行 ID と依頼の ID」の形で作る
- 結果を待つのは、`entry/check.ts` の引数 `wait`（sandbox の中で動く）の 1 回の呼び出しで最大 60 秒（「[setup][d05]」の `next` と同じ。Bash の道具の 1 回の時間の上限に収めるため）。5 秒ごとに結果のファイルを読み、60 秒の内に来なければ、待ち続けるかを返して終わる。Skill は、依頼を置いた時刻から依頼に書いた待つ時間を過ぎるまで、`wait` を繰り返し呼ぶ（intake の「下書き」と同じ形。[ADR-20261022-004][adr-intake-req] の決定 1）。読む・待つは sandbox の中で行う（「[導入と点検][b04]」の「点検だけで動かす仕組み」の表の下）
- 依頼に書いた待つ時間を過ぎても結果が来なければ、待つのをやめ、`run.lock` を読む。中身を読めれば、実行の最中か、前の実行が落ちて lock が残っているかのどちらかであることと、lock の起動の時刻を示す（`/dev-autopilot` と intake の「下書き」と同じ決まった文。`logic/text/comments.ts` に置く。「[文の検査と受け入れ][d06]」の「コメントの組み立て」）。中身を読めなければ、壊れた lock であることと戻し方（「[設定と記録][d02]」の「lock」）を示す。lock が無ければ、ジョブが起きなかったかを、定期の実行の登録と `launchd.err.log` で確かめるように示す（「[導入と点検][b04]」の「点検だけで動かす仕組み」の順 5）
- 表示は、全体の結果、`fail` の項目、`warn` の項目の順にし、`pass` の項目は数だけを出す。項目は ID と `logic/check/items.ts` の決まった文と `details` で出す
- 結果のファイルの形が違えば、結果が無いものとして扱い、形が違うことを示す（「[設定と記録][d02]」の「依頼と結果のファイル」）

| ファイル | 単体テストで確かめること |
| --- | --- |
| `check.ts` | 組の順と前提。前提が欠けた組の項目が `unchecked` の `fail` になること。順 1〜5 に `fail` があれば試しのセッションを起こさず、sandbox の組が `unchecked` の `fail` になること。合図が `run` でない間（`stop`、ほかの値、変数が無い、読めない）と記録の目印のファイルを作った日に、未確認の warn になること。試しの直前に読み直した合図が `run` でなければ、書き込みの権限の試しを投げず、試しのセッションを起こさないこと。全体の停止の Issue がある間（読めなかったときを含む）は、試しのセッションを起こさずに `halt-issue` の warn になり、書き込みの権限の試しは行うこと。見つかりの記録が読めないときも、マシンの組に fail が出ず、sandbox の組が `unchecked` の fail でなく `halt-issue` の warn になること。2 つ以上に当たるときに `stop-signal`・`halt-issue`・`setup-day` の順で 1 つを書くこと。組の処理が思わない失敗で止まっても、次の組へ進むこと。結果の無い項目を `unchecked` の `fail` で埋める関数を、外から呼べること |
| `logic/check/result.ts` | 全体の結果の決め方。`details` に秘密の値の型（`logic/secret.ts`）を入れると型の検査で落ちること。種類の一覧に無い値と、秘密の置き場の下のパスを入れると落ちること |
| `logic/check/items.ts` | 項目の ID が重ならず、どの組にも 1 つ以上あること。ID ごとに、`fail` と `warn` の `reason` のすべてに文があること。`check.ts` の組が返しうる ID がすべて一覧にあること |
| `logic/check/rulesets.ts` | 期待する形のとおりの ruleset で違いが無いこと。守りが弱い向きの違いの種類ごとの判定。`bypass_actors` が無いときに bypass を比べないこと。控えの読み書き。控えが無い、控えた ID の ruleset が無い、`updated_at` が控えと違う、`current_user_can_bypass` が `never` でない、のそれぞれで fail を返すこと（[ADR-20261028-004][adr-bypass-baseline]） |
| `logic/check/app-permissions.ts` | `extra`・`stronger`・`missing`、`repository_selection`、ほかのリポ。引き換えの本文の `permissions` が表と同じこと |
| `logic/check/fnmatch.ts` | `fixtures/fnmatch/` の組のすべてで、Ruby と同じ当たり方になること。`{` を含む規則が当たるものになること。見本の番号に当たらないが形には当たる規則（`feat/issue-2*`、`refs/pull/[2-9]*/merge`、`refs/pull/*/head`、`*/issue-1?`）を当たりうると判定し、形に当たらない規則（`main`、`release/*`）を当たらないと判定すること。`labels.defaultBranchType` の型も照らすこと |
| `logic/check/trial-skip.ts` | 5 つの条件の 1 つずつが外れると省かないこと。キーの順を変えても条件のハッシュが変わらないこと。ハッシュの組み立てが乱数と時刻を使わず、同じ設定から同じハッシュになること。`runs.jsonl` の最新の sandbox の組の結果が `pass` でなければ、`sessions.jsonl` の最新の終わりの行が `pass` で 4 つの値が同じでも省かないこと。`runs.jsonl` の 1 行に順 5 の `pass` と順 10 の `fail` があれば省かないこと。順 10 の点検し直しで、同じ実行の順 5 の結果が `fail` なら省かず、`pass` なら前の行が未確認の `warn` でも省くこと |
| `logic/check/trial-judge.ts` | 基本設計の「確かめる項目」の表の行ごとの判定。決めたコマンドと違う Bash、欠けた試しの名前、読めない出力、上限に当たったときに `fail` になること。試しのセッションの終わり方ごとの結果（上の「試しのセッションの判定」の表の行ごと） |
| `entry/check-probe.ts` | 外に触れる関数を偽物にして渡し、試しの名前ごとに 1 行を出すこと、偽物が返したファイルの中身を出力に出さないこと、引数の期待する値と違う値で `ok` が `false` になること。import しただけでは試しを行わないこと。試しの名前の並びが `logic/check/trial-judge.ts` と同じこと（子プロセスと本物の git・pnpm は使わない） |
| `flow/check/settings.ts` | 設定を確かめた問題を項目の結果に写すこと。`io/secrets.ts` が返した `notify-webhook-url` の無いことと形の問題を、fail の項目の結果にし、`details` に URL を入れないこと |
| `flow/check/machine.ts` | OS に依る項目を `io/os.ts` で読むこと。定期の実行に渡る環境（登録の中身と `launchctl getenv`）に `HTTP_PROXY`・`HTTPS_PROXY`（小文字の名前も）・`NODE_USE_ENV_PROXY`・`NODE_EXTRA_CA_CERTS`・`NODE_OPTIONS` のどれかがあれば fail になること（[ADR-20261107-001][adr-github]）。短い一時フォルダの根を作った後に長さを数えること。止めなかったプロセスが、人に渡したセッションのフォルダの中なら `warn`、ほかのものと、止められなかった作業の単位を持たないセッション（受け入れの依頼の実行の受付 AI（`verify-intake-issue-`）と点検の試し（`check-`））の残りなら `fail` になること。止められなかった作業の単位のセッションを、止めなかったプロセスの項目の `warn` にし、`fail` にしないこと。定期の実行の下書きと書き直しの受付 AI（`intake-issue-`）の止められなかったセッションを、作業の単位を持たないセッションとして `fail` にしないこと。順 10 で渡された、今の実行で止められなかった作業の単位を持たないセッションを `fail` にすること。`machine.security-pending` が、`flow/run/records.ts` の読む関数の結果から、無ければ `pass`、あれば `warn`（`pending`。`details` にすべての記録の Issue の番号と時刻）、`runs.jsonl` の行か今の実行の書き直した結果に書き直せずに残した記録があれば `warn`（`rewrite-failed`。すべての記録の番号と時刻に、書き直せなかった記録の回数と最後の時刻と理由の種類を足す）、読めなければ `warn`（`unreadable`）になり、どれも `fail` にならないこと。2 つ以上に当たるときに `unreadable`・`rewrite-failed`・`pending` の順で 1 つを選ぶこと。一時のファイル（`<名前>.new-<PID>`）と名前の違うファイルとフォルダを読めないときに `unreadable` になり、名前から読めた作業の単位の Issue の番号を `details` に入れること（番号を読めない名前はパスだけ、フォルダを読めないときはフォルダのパス）。見つかった文を出さないこと（[ADR-20261111-001][adr-halt-records] の決定 3） |
| `flow/check/app.ts` | 前提が欠けたら組の項目が `unchecked` の fail になること。リポの一覧を `readInstallationRepositories` で読み、読めなければ `unchecked` の fail になること。読み直した合図が `run` でない間は、書き込みの権限の試しを投げないこと |
| `flow/check/github.ts` | リポの秘密がある、組織の秘密が届く、Environment の使えるブランチが無制限か保護ブランチだけ、作業ブランチの形に当たる規則がある、のそれぞれで fail になること（[ADR-20261028-001][adr-ci-secrets]・[ADR-20261028-002][adr-app-secrets]） |
| `flow/check/probes.ts` | モデルを使わない試しの外れ方ごとの項目の結果 |
| `flow/check/trial.ts` | 省く条件に当たれば起こさないこと。結果を `logic/check/trial-judge.ts` に渡すこと。試しの結果と省く条件の値を返す関数を `flow/session/run.ts` に渡すこと。前の記録を `sessions.jsonl` と `runs.jsonl` の 2 つから読むこと（`runs.jsonl` は後に行った点検の結果を、順 10 では同じ実行の順 5 の結果を読むこと）。`flow/session/run.ts` が返した関数の値を項目の結果にすること。`not-stopped` で項目を `unchecked` の `fail` にすること |
| `flow/skill/check.ts` | 依頼を置くコマンドの文に、書く先のパスと中身が見えること。`status.json` の待つ時間を依頼に書き、`status.json` が無いか形が違えば初期値を書くこと。`wait` の 1 回の呼び出しが 60 秒を超えないこと。依頼に書いた待つ時間を過ぎたら、待ち続けないと返すこと。待つ時間を過ぎたときに、読めた lock・読めない lock・lock が無い、のそれぞれで示す文が変わること。形の違う結果のファイルを結果と読まないこと。項目を `logic/check/items.ts` の決まった文で出すこと |

- 結合テストは、人の `check` が依頼を置いて偽の `launchctl` で進行 Bot を起こし、結果のファイルを読んで消す流れと、点検だけの実行で作業に入らないことを確かめる（「[テスト][b05]」の「偽物」）。人の `check` の処理は、`node --permission` で秘密の置き場を読ませずに起こす
