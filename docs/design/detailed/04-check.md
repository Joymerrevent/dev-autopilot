# 点検

点検の組ごとの処理の分け方、結果の形、組の順と前提、試しのセッションを省く判定と結果の決め方、`setup` の読み戻しと共有する比べる規則、人が呼ぶ `check` の処理を決める。
点検の項目の正本は要件の [SETUP-2][setup] で、項目の組と、いつ・どう確かめるかは基本設計の「[導入と点検][b04]」の「点検」にある。本書は、項目を並べ直さず、組の処理の作りを決める。

## ファイルの一覧

| ファイル | 層 | 受け持つこと | 基本設計 |
| --- | --- | --- | --- |
| `check.ts` | 流れ | 点検の正本。組の一覧（順・回数・前提）と項目の ID の一覧を持ち、組の処理を順に呼んで結果をまとめる | 「[導入と点検][b04]」の「組と回数」 |
| `flow/check/settings.ts` | 流れ | 設定の組。設定を確かめた問題（「[設定と記録][d02]」の「設定の表を 1 か所に持つ」）を項目の結果にする | 「[設定][b01]」の「`check` が設定について確かめること」 |
| `flow/check/machine.ts` | 流れ | マシンの組。OS に依る項目は外との境の OS ごとの部分（「[外との境][d01]」の「OS ごとの部分」）で読む | 「[導入と点検][b04]」の「組と回数」のマシンの行 |
| `flow/check/app.ts` | 流れ | アプリの権限の組（読み取り、書き込みの権限の試し、権限とインストールの範囲） | 「[導入と点検][b04]」の「GitHub App の権限」 |
| `flow/check/github.ts` | 流れ | GitHub の組（ラベル、Project、ruleset、必須チェック、止める合図、base ブランチ、印の鍵の warn、基線、通知の warn） | 「[導入と点検][b04]」の「組と回数」の GitHub の行 |
| `flow/check/probes.ts` | 流れ | 子プロセスと clone の組（モデルを使わない試し） | 「[導入と点検][b04]」の「モデルを使わない試し」 |
| `flow/check/trial.ts` | 流れ | sandbox と AI のセッションの組（試しのセッションを起こし、判定の元を集める） | 「[導入と点検][b04]」の「試しのセッション」 |
| `logic/check/result.ts` | 判断 | 項目の結果の形と、全体の結果の決め方 | 「[導入と点検][b04]」の「点検」 |
| `logic/check/rulesets.ts` | 判断 | 3 つの ruleset の期待する形と、読んだ ruleset との比べ方（`setup` の読み戻しと共有） | 「[導入と点検][b04]」の「ruleset の形と確かめ方」 |
| `logic/check/app-permissions.ts` | 判断 | 進行 Bot の App の権限の表と、インストールの情報との比べ方（トークンの引き換えの要求と共有） | 「[導入と点検][b04]」の「GitHub App の権限」 |
| `logic/check/fnmatch.ts` | 判断 | Environment の使えるブランチの規則の照らし（[FACT-101][facts]） | 「[導入と点検][b04]」の「GitHub の準備」の表の下 |
| `logic/check/trial-skip.ts` | 判断 | 試しのセッションを省くかの判定と、省く条件のハッシュ | 「[導入と点検][b04]」の「組と回数」の表の下 |
| `logic/check/trial-judge.ts` | 判断 | 試しのセッションの記録（`stream-json`）と、試しのスクリプトの出力と、進行 Bot がディスクで確かめた有無から、項目の結果を決める | 「[導入と点検][b04]」の「試しのセッション」 |
| `flow/skill/check.ts` | 流れ | 人が呼ぶ `check` の処理（依頼を置く、ジョブを起こす、結果を待って表示する、結果を消す）。点検の処理は持たない | 「[導入と点検][b04]」の「点検だけで動かす仕組み」 |

| `entry/check-probe.ts` | 入口 | 試しのスクリプト。試しのセッションの中で、AI に 1 回だけ実行させる | 「[導入と点検][b04]」の「試しのセッション」 |

- 試しのスクリプト `entry/check-probe.ts` は、ファイルとプロセスに触れるので入口の層に置く。セッションのフォルダに写して `node` で動かすので、`node:` で始まるモジュールのほかを import しない（写した先に `plugin/src/` も `node_modules` も無いため。[README][readme] の「入口ごとの import の範囲」）
- 組の処理は、外との境を型だけで受け取り、入口が組み立てた実体を引数で受ける（[README][readme] の「層と依存の向き」）

## 結果の形

`logic/check/result.ts` に、項目の結果の形を持つ。点検の結果のファイル（`check-result-<依頼の ID>.json`。「[設定と記録][d02]」の「依頼と結果のファイル」）、`status.json` の点検の欄、実行の記録は、どれも同じ形で項目を書く。

| 欄 | 中身 |
| --- | --- |
| `id` | 項目の ID。`<組>.<項目>` の形（例：`github.rulesets`、`machine.os`）。組は `settings`・`machine`・`app`・`github`・`probes`・`sandbox`。項目は英小文字と数字を `-` でつないだもの |
| `level` | `pass`・`warn`・`fail` |
| `unverified` | 確かめなかった warn のときだけ、理由の記号（`stop-signal`：全体の止める合図が `stop` の間。`setup-day`：記録の目印のファイルを作った日） |
| `reason` | fail と warn の理由の記号。項目ごとに決める。確かめようとして確かめられなかった fail は `unchecked`（前の組が fail で前提が欠けた、応答が読めない、時間の上限を過ぎた） |
| `details` | 人が直すための値の並び。数（Issue と PR の番号、鍵の行の番号）・名前（ラベル、必須チェック、ruleset、Environment）・リポの中のパス・版だけ |

- 項目の ID の一覧は `check.ts` に持ち、ID ごとに、確かめる基本設計の項目（「組と回数」の表の項目）を書き添える。点検の項目の正本は要件と基本設計なので、本書には一覧を写さない
- 人に見せる文は、ID と `level` と `reason` ごとに `check.ts` が持つ決まった文にする。外から読んだ文（GitHub の応答の `message`、ファイルの中身）を、書き換えずに文に入れない
- `details` に、秘密（鍵の値、トークン、JWT、Webhook の URL、秘密の置き場のファイルの中身）と、秘密の置き場の実体のパスを入れない。鍵は行の番号で示す（「[状態遷移と判定][b02]」の「印の署名」）。結果のファイルは記録の置き場にあり、人の Claude Code の文脈にも入るため
- 全体の結果は、fail が 1 つでもあれば `fail`、無くて warn があれば `warn`、どちらも無ければ `pass`。確かめなかった warn も warn に数える（[SETUP-2][setup] の「fail が 1 つでもあれば作業に入らない」は、`fail` だけを見る）
- 確かめられなかったものを pass にしない。組の処理が思わない失敗で止まったら、止まった組でまだ結果の無い項目をすべて `fail`（`unchecked`）にして、次の組へ進む

## 組の順と前提

![組の順と前提][fig-groups]

`check.ts` は、組を次の順に呼ぶ。前の組の結果が、後の組の前提になるため。

| 順 | 組 | 前提（欠けたら、組の項目を `fail` の `unchecked` にする） | 毎回の実行の最初 | `setup`・人の `check` |
| --- | --- | --- | --- | --- |
| 1 | 設定 | 無し（マシンの設定を読めないときは、記録の置き場も分からず結果を書けない。「[導入と点検][b04]」の「点検だけで動かす仕組み」） | 行う | 行う |
| 2 | マシン | マシンの設定を読めた | 行う | 行う |
| 3 | アプリの権限 | マシンの設定の `githubApp.*` と秘密鍵がある | 行う | 読み取りは行う。書き込みの権限の試しは、合図が `run` のときだけ |
| 4 | GitHub | インストールのトークンを作れた（順 3 の読み取りが通った）。リポの設定を読む項目は、リポの設定を読めた | 行う | 行う |
| 5 | 子プロセスと clone | リポの設定を読めた（AI のセッションの環境変数を組み立てるため） | 行う | 行う |
| 6 | sandbox と AI のセッション | 順 1〜5 に `fail` が無い | 省く条件（下の「試しのセッションを省く判定」）に当たらないときだけ | 合図が `run` のときだけ |

- 順 6 は、前の組に `fail` が 1 つでもあれば、試しのセッションを起こさずに `fail`（`reason` は `not-started`）にする。壊れた環境で AI のセッションを起こさないため。基本設計の「GitHub の組の、base ブランチの先端に local の設定と指示が無いことの確かめが fail なら、試しのセッションを起こさない」を、前の組の `fail` のすべてに広げた形
- 全体の止める合図が `stop` の間は、書き込みの権限の試し（順 3）と試しのセッション（順 6）を行わず、`warn`（`unverified` が `stop-signal`）にする。記録の目印のファイルを作った日は、試しのセッションを行わず、`warn`（`unverified` が `setup-day`）にする（「[導入と点検][b04]」の「組と回数」の表の下）
- 人が呼ぶ `check` で入れた Plugin と写しの版が違うことの warn は、人の Skill だけが確かめる（定期の実行は入れた Plugin の場所を知らない）。`flow/skill/check.ts` が結果を表示するときに足す
- 1 つの組の中の項目は、互いに前提を持たない限り、すべて確かめる。最初の `fail` で組を止めない。人が 1 回の点検で直すものをまとめて知るため

## 試しのセッションを省く判定

`logic/check/trial-skip.ts` は、前の試しのセッションの記録と今の値を受け取り、省くかを返す（「[導入と点検][b04]」の「組と回数」の表の下の 5 つの条件）。前の記録は、手元の記録の `sessions.jsonl` の試しのセッションの終わりの行から読む（残す欄の正本は「[状態遷移と判定][b02]」の「手元の記録」）。

- 省く条件の値は、`claude --version` の出力、条件のハッシュ、写しの版、OS の版（macOS は `sw_vers -productVersion`）の 4 つと、前の結果が `pass` であること
- 条件のハッシュは、試しのセッションに渡す安全設定と、環境変数の名前の並びと、マシンの設定の `sessionTmp.*` を、1 つの JSON にして取る SHA-256（16 進）。安全設定は、セッションの名前を決まった名前（`check-hash`）にして組み立てる。セッションごとに変わるパス（セッションのフォルダ、短い一時フォルダ）を、毎回同じにするため
- JSON は、印の署名と同じく、キーを文字の符号の順に並べて空白を入れない（「[印][d03]」の「署名」の順 2）。キーの順で同じ値のハッシュが変わらないため
- 前の記録が無い、読めない、`pass` でない（`fail`・未確認・起動できなかった）ときは、省かない

## 試しのセッションの判定

`flow/check/trial.ts` は、「[導入と点検][b04]」の「試しのセッション」の手順で試しのセッションを起こし、判定の元を集める。`logic/check/trial-judge.ts` は、集めた元から項目の結果を決める。判定の決まりは基本設計の「試しのセッション」のとおりで、本節は判定の元の受け渡しを決める。

| 判定の元 | 集め方 | 渡す形 |
| --- | --- | --- |
| 試しのスクリプトの出力 | `stream-json` の Bash の呼び出し（`tool_use`）のうち、決めたコマンドと全体が一致するものの結果（`tool_result`）の文 | 1 行に 1 つの JSON（`{"probe":"<試しの名前>","ok":true}` の形）。形の違う行は数えない |
| Read と Write の道具 | `stream-json` の Read と Write の呼び出しと結果、`result` の `permission_denials` | 呼び出しごとのパスと、結果がエラーか、拒否に載ったか |
| 道具の一覧 | `init` のイベントの道具の一覧と MCP のサーバーの一覧 | 名前の並び |
| 自動のメモリ | `assistant` のメッセージと `result` の文 | 文 |
| ディスクの有無 | 書けないはずのパスにファイルができたかを、進行 Bot が試しの後に確かめる | パスごとの有無 |
| 終わり方 | ターン・時間・費用の上限に当たったか、出力を読めたか | 記号 |

- 試しのスクリプトは、試しの名前ごとに、読めたか・書けたか・一覧を出せたかだけを出力し、読めたファイルの中身を出力しない（「[導入と点検][b04]」の「試しのセッション」）。試しのスクリプトはほかのファイルを import できないので、試しの名前の並びを自分で持つ。`logic/check/trial-judge.ts` の並びと同じことを、単体テストで確かめる
- 決めたコマンドの Bash が 1 回も無い、決めたコマンドと違う Bash がある、試しの名前が出力に 1 つでも欠けている、出力を読めないときは、該当する項目を `fail` にする。確かめられなかったものを pass と読まないため
- 項目の ID は、基本設計の「確かめる項目」の表の行ごとに 1 つ持つ（例：`sandbox.bash-read-denied`、`sandbox.read-tool`、`sandbox.tools-list`）

## 共有する比べる規則

### ruleset の比べ方

`logic/check/rulesets.ts` は、設定（`baseBranch`、`checks.required`、`labels.branchTypes`、`labels.defaultBranchType`、`push.rulesetBypassApps` の ID）から 3 つの ruleset の期待する形（「[導入と点検][b04]」の「ruleset の形と確かめ方」の表）を作り、読んだ ruleset と比べて違いの一覧を返す。`setup` の読み戻しと点検が、同じ関数を使う。

- 違いごとに、守りが弱い向きか（PR 必須でない、force push を許す、必須チェックが足りないか strict でない、`active` でない、base ブランチが対象に無い、作業ブランチの形より広い除外、bypass に許した者のほかがある）か、守りが弱い向きでない違い（設定に無い型の除外など）かを付ける。点検は、守りが弱い向きの違いを `fail`、守りが弱い向きでない違いを `warn` にする
- 読んだ ruleset に `bypass_actors` が無い（進行 Bot の App のトークンで読んだ。FACT-88・91）ときは、bypass を比べず、「bypass を比べていない」と結果に付ける。点検は、ruleset の控え（`DEV_AUTOPILOT_RULESETS`）の ID と `updated_at` と、`current_user_can_bypass` で確かめる（「[導入と点検][b04]」の「ruleset の形と確かめ方」の確かめ方）。`setup` は、`bypass_actors` が返る認証で読み、bypass も比べる
- 控えの形（`{"<ruleset の ID>": "<updated_at>"}`）を読む関数と、`setup` が控えを書くときの組み立ても、同じファイルに持つ

### App の権限の比べ方

`logic/check/app-permissions.ts` に、進行 Bot の App の権限の表（「[導入と点検][b04]」の「GitHub App の権限」の表）を定数で持つ。インストールのトークンへの引き換えの本文の `permissions`（「[外との境][d01]」の「JWT で呼ぶ 2 つの API」）も、同じ定数から作る。表を 2 か所に書かないため。

- インストールの情報の `permissions` と表を比べ、表に無い権限（`extra`）、表より強い権限（`stronger`。表で読み取りとした権限が書き込み）、表にあって無いか弱い権限（`missing`）を返す。点検は、3 つとも `fail` にする。基本設計は前の 2 つを fail とし、`missing` は書いていないが、足りない権限では進行 Bot の書き込みが途中で断られ、作業の単位が半端な状態で止まるので、作業に入る前に止める
- `repository_selection` が `selected` でないこと、インストールが読めるリポに当てる先のリポのほかがあることも、同じ関数で返す

### Environment の規則の照らし

`logic/check/fnmatch.ts` は、Environment の使えるブランチの規則（`deployment-branch-policies` の `name`）が、ブランチの名前に当たるかを決める。GitHub の当たり方は、Ruby の `File.fnmatch` に `File::FNM_PATHNAME` を付けたときと同じだった（[FACT-101][facts]）ので、同じ当たり方を TypeScript で書く。

| 書き方 | 当たり方 |
| --- | --- |
| `*` | `/` のほかの 0 文字以上 |
| `?` | `/` のほかの 1 文字 |
| `[…]` | 括弧の中の 1 文字（`a-z` の範囲、先頭の `!` か `^` で否定）。`/` には当たらない |
| `**/` | 0 個以上のフォルダ（`**/*` は `/` を含む名前にも当たる） |
| `\` | 次の 1 文字を、記号でなく文字として当てる |

- `FNM_DOTMATCH` と `FNM_EXTGLOB` を付けない当たり方にする。`/` の後と名前の先頭の `.` には、`*` と `?` と `[…]` が当たらない。`{…}` は、括弧の文字のまま当てる
- 点検は、`labels.branchTypes` の型ごとの `<型>/issue-1` と、`refs/pull/1/merge` を、規則のどれにも当たらないかで照らす（「[導入と点検][b04]」の「GitHub の準備」の表の下）
- 当たり方が Ruby と同じことは、手元の Ruby の `File.fnmatch` で作った前提データ（`fixtures/fnmatch/`。規則・名前・当たるかの組）で確かめる。[FACT-101][facts] の 6 つの規則と 2 つの名前の組を含める。パスの照らしで、本物の git で作った前提データを使うのと同じ考え方（「[設定と記録][d02]」の「パスの照らし」）

## 人が呼ぶ check

`flow/skill/check.ts` は、「[導入と点検][b04]」の「点検だけで動かす仕組み」の順 1〜5 のうち、人の側（順 1・2・5）を受け持つ。点検の処理は持たず、`check.ts` と `flow/check/` を import しない（[README][readme] の「入口ごとの import の範囲」）。

- 依頼を置くコマンドと、結果を消すコマンドは、Skill が人の許可を得て sandbox の外で動かす。`entry/check.ts` は、書く先のパスと書く中身（依頼の ID・置いた時刻・待つ時間）を、人が読めるコマンドの文の形で返す。コマンドは、`node` の 1 行で、書く先のパスと中身を引数に置く（秘密を含まないので、引数に置いてよい）
- 依頼の ID は、「[設定と記録][d02]」の「実行 ID と依頼の ID」の形で作る
- 結果を待つ間は、5 秒ごとに結果のファイルを読み、`run.checkWaitMinutes` を過ぎたら待つのをやめる。読む・待つは sandbox の中で行う（「[導入と点検][b04]」の「点検だけで動かす仕組み」の表の下）
- 表示は、全体の結果、`fail` の項目、`warn` の項目の順にし、`pass` の項目は数だけを出す。項目は ID と決まった文と `details` で出す
- 結果のファイルの形が違えば、結果が無いものとして扱い、形が違うことを示す（「[設定と記録][d02]」の「依頼と結果のファイル」）

| ファイル | 単体テストで確かめること |
| --- | --- |
| `check.ts` | 組の順と前提。前提が欠けた組の項目が `unchecked` の `fail` になること。順 1〜5 に `fail` があれば試しのセッションを起こさないこと。合図が `stop` の間と記録の目印のファイルを作った日に、確かめなかった warn になること。組の処理が思わない失敗で止まっても、次の組へ進むこと。項目の ID が重ならず、どの組にも 1 つ以上あること |
| `logic/check/result.ts` | 全体の結果の決め方。`details` に秘密の値の型を入れると型の検査で落ちること |
| `logic/check/rulesets.ts` | 期待する形のとおりの ruleset で違いが無いこと。守りが弱い向きの違いの種類ごとの判定。`bypass_actors` が無いときに bypass を比べないこと。控えの読み書き |
| `logic/check/app-permissions.ts` | `extra`・`stronger`・`missing`、`repository_selection`、ほかのリポ。引き換えの本文の `permissions` が表と同じこと |
| `logic/check/fnmatch.ts` | `fixtures/fnmatch/` の組のすべてで、Ruby と同じ当たり方になること |
| `logic/check/trial-skip.ts` | 5 つの条件の 1 つずつが外れると省かないこと。キーの順を変えても条件のハッシュが変わらないこと |
| `logic/check/trial-judge.ts` | 基本設計の「確かめる項目」の表の行ごとの判定。決めたコマンドと違う Bash、欠けた試しの名前、読めない出力、上限に当たったときに `fail` になること |
| `entry/check-probe.ts` | テストの一時フォルダに試しの場所を作り、子プロセスで動かして、試しの名前ごとに 1 行を出し、読めたファイルの中身を出さないこと。試しの名前の並びが `logic/check/trial-judge.ts` と同じこと |
| `flow/skill/check.ts` | 依頼を置くコマンドの文に、書く先のパスと中身が見えること。待つ時間を過ぎたら待つのをやめること。形の違う結果のファイルを結果と読まないこと |

- 結合テストは、人の `check` が依頼を置いて偽の `launchctl` で進行 Bot を起こし、結果のファイルを読んで消す流れと、点検だけの実行で作業に入らないことを確かめる（「[テスト][b05]」の「偽物」）。人の `check` の処理は、`node --permission` で秘密の置き場を読ませずに起こす
