# dev-autopilot 基本設計

dev-autopilot の進行 Bot と、進行 Bot が起動する AI のセッションを、どう作るかを書く構造仕様（基本設計）。
[要件][req]が「何をするか」を、[ADR][adr] が「どちらを選んだか」を決め、基本設計は「どの部品が、どの値で、どう動くか」を決める。

## ファイル

| ファイル | 話題 |
| --- | --- |
| [01-settings.md][d01] | 設定（リポの設定とマシンの設定の項目ごとの置き場・初期値・根拠） |
| 02-flow-and-judgment.md（まだ無い） | 状態遷移と判定（Issue の状態の遷移、収束とマージの判定の表、印の種類） |
| 03-ai-sessions.md（まだ無い） | AI のセッション（起動の形、セッションごとの安全設定、止め方、モデルと effort） |
| 04-modules-and-tests.md（まだ無い） | モジュールとテスト（`plugin/src/` の分け方、単体テストと結合テスト、前提データの置き場、定期の実行の登録） |

## 読み方

- 根拠は、要件の番号（FLOW-1 など）と ADR の番号（ADR-20261015-005 など）で示す。用語は[要件の読み方][req-read]と同じ（進行 Bot、AI の 5 役、工程、段階、印、渡す文）
- 基本設計は、要件と ADR に従う。食い違っていたら要件と ADR が正しく、基本設計を直す
- 設定の項目の初期値と根拠は [01-settings.md][d01] の表が正本で、今の値の正本は設定ファイル（STRUCT-2）

## 基本設計を変えるとき

- 要件の形を変えない細かい選択（[決めていないこと][undecided]の「基本設計の中で決めてよいもの」）は、基本設計の PR で決める。
  決めた項目は、同じ PR で要件の番号を欠番にし、どの文書で決めたかを添える（例：`- UNDECIDED-19 **欠番**（基本設計の「設定」で決めた）：~~元の文~~`。書き方は[要件を変えるとき][req-change]と同じ）
- 要件の形を変える判断と、安全の境界を緩める変更（AI の道具・読み書きの範囲・通信先を広げる、MERGE-4 の許可一覧にパスを足す、IMPL-15 の一覧からパスを外す、上限を外す）は、基本設計の中で決めない。ADR を `proposed` で起票し、メンテナが `accepted` にしてから基本設計を直す（STRUCT-2、ADR-20261015-005）
- 基本設計を書く中で、要件の誤りや足りない点に気づいたら、要件を直す PR を別に出す。基本設計に要件の文を写さず、番号で指す
