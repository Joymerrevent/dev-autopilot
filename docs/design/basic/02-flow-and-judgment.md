# 状態遷移と判定

進行 Bot が、毎回の実行で GitHub の状態を読み、作業の単位（Issue 1 件と、結びつく PR）ごとに状態を組み立て、「次の工程」を決めて進める仕組みを決める。
主な流れの状態と線、重ねる 3 本の軸、線の番号（T・S・D・Q）は[要件の Issue の状態の遷移][flow]が正本で、基本設計は、GitHub の何をどの順に読んで状態を決め、状態ごとにどの工程に進むかを表にする（[ADR-20261024-001][adr-model-states]）。

## 工程ごとの PDCA

![工程ごとの PDCA][fig-pdca]

AI が受け持つ工程を、段取り（P）・作業（D）・検証（C）・直す（A）で見ると、次のとおり。AI で回すループのエージェント定義は、ループごとのフォルダに置く（[STRUCT-9][struct]）。

| 工程 | P（段取り） | D（作業） | C（検証） | A（直す） | AI で回すループ |
| --- | --- | --- | --- | --- | --- |
| 依頼 | 進行 Bot（入口の検疫） | 受付 AI（マスターの下書き） | 人がマスターを読む | 人が直す（`## 作業指示`）か、差し戻して受付 AI に書き直させる（`## 差し戻し`）。直した全文は進行 Bot がマスターに写し、書き直した下書きは投稿して、人がもう一度読む | 置かない。人が必ず読んで決めるので、AI の検証を足しても人の手間は減らない（定義は `brief/`） |
| 計画 | 人が決めたマスター | 計画 AI | 計画を確かめる AI（レビュー AI） | 計画 AI が計画し直す（上限は `limits.planRevisions`） | ある。同じ回の実行の中で回す（定義は `plan/`。[ADR-20261019-003][adr-replan]） |
| 変更と直し | 計画 | 作業 AI | 機械の検査（必須チェック）と、検査が通った後のレビュー AI（4 つの軸）と批評 AI | 作業 AI が直す（検査の失敗・指摘・衝突）。直した後は検査からやり直す | ある。往復は `limits.roundTrips` の回数まで（定義は `change/`。[ADR-20261024-003][adr-check-first]） |
| マージの判定 | レビュー合格の PR と、判定の条件（[MERGE-2][merge]） | 進行 Bot | 人がマージする | 判定の条件を ADR で直す | 置かない。進行 Bot の判定は決まった処理で、同じ入力なら同じ結果になる |

- 前の工程の検証を通った結果が、次の工程の段取りになる（人が決めたマスターが計画の段取りに、確かめを通った計画が変更の段取りに、レビュー合格の PR がマージの判定の段取りになる）
- AI の検証（計画の確かめ、見落としの軸、批評）は、最初から流れを止める判定に使う。記録だけに残して人の判断と比べる試しは持たない（[ADR-20261024-002][adr-no-stages]）

## 1 回の実行の流れ

![1 回の実行の流れ][fig-run-flow]

| 順 | すること | うまくいかないとき |
| --- | --- | --- |
| 1 | 定期の実行の定義が渡したパスから、マシンの設定を読む（[ADR-20261015-005][adr-settings]） | 作業に入らず止まる（[SAFE-4][safety]）。記録の置き場が分からないので、点検の依頼があっても結果を書けない（人の `check` は待つ時間を過ぎたら止まる。「[導入と点検][design-setup]」の「点検だけで動かす仕組み」） |
| 2 | 記録の置き場の lock（`run.lock`）を取る。lock には PID・起動の時刻（lock を取ったプロセスの起動の時刻。時刻帯に依らないエポック秒）・ホスト名を書く。PID が生きていないか、PID のプロセスの起動の時刻が lock の起動の時刻と違えば、古い lock として奪う。再起動の後に使い回された PID で、実行を見送り続けないため（[運用の規則][flow]）。PID が生きていて起動の時刻が同じなら、持ち主が動いているので、ホスト名を問わず奪わない。ホスト名は人が読むためだけに書き、奪うかの判定に使わない（macOS では、つないだネットワークでホスト名が変わりうるため。動かすマシンを替えるときは lock を写さない。下の「手元の記録」の「記録の置き場のほかのファイル」の表の下）。起動の時刻の取り方と、2 つのプロセスが同時に古い lock と読んでも片方だけが lock を取る手順は、表の下の「lock の取り方」。取ったら、手動の 1 回実行・点検・受け入れの依頼のファイルを見て、起こされ方（定期・手動・点検の依頼・受け入れの依頼）を決める。置いた時刻から、依頼のファイルに書いた待つ時間を過ぎた点検と受け入れの依頼は、人が待つのをやめた後に残ったものとして扱う（「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」）。続けて、前の実行が残した AI のセッションを止め、費用を数える（「[AI のセッション][design-ai]」の「前の実行が残したセッション」）。止める猶予と費用は、リポの設定をまだ読んでいないので、見つけたセッションの始まりの行に書いた値（止める猶予と、`--max-budget-usd` に渡した値。下の「手元の記録」）で決める。止められなかったセッションの作業の単位は控えておき、停止中にすること（`session-not-stopped`。実装の都合の記号）は、順 4 でリポの設定（表示の欄の ID など）を読み、順 7 で状態を組み立てた後に、次の工程の表より先に行う。受け入れの依頼の実行は順 6〜9 に進まないので、停止中にせず、次の実行に任せる。止められなかったセッションは、停止中にする（`stop` の印を書く）まで終わりの行を書かず、動いているセッションとして費用の上限で数える。順 3〜7 で実行が止まっても、次の実行が、終わりの行の無いセッションとしてもう一度見つけるため | 実行を見送り、見送ったことを記録に残す（[運用の規則][flow]）。点検の依頼は、動いている実行が終わりに行う（順 10） |
| 3 | 全体の止める合図（リポの変数 `DEV_AUTOPILOT_RUN`）を読む（[運用の規則][flow]）。読む先と認証は、マシンの設定の `repository.*` と `githubApp.*` で決める（[設定][design-settings]。進行 Bot は GitHub App だけを使い、`githubApp.*` が無ければ読めずに止まる）。あわせて、全体の停止の Issue（下の「全体の停止の Issue」）があるかを読む | 合図の値が `run` でないか読めなければ、作業に入らず止まる（[ADR-20261017-007][adr-stop]）。点検の依頼のファイルがあれば、順 4 の設定の読み込みと順 5 の点検だけを行ってから止まる。試しのセッションと書き込みの権限の試しは行わず、未確認の warn にする（「[導入と点検][design-setup]」の「点検だけで動かす仕組み」）。全体の停止の Issue があれば、作業には入るが、この実行では AI のセッションを起こさない（[SAFE-19][safety]）。全体の停止の Issue を読めなければ、あるものとして扱う |
| 4 | 進行 Bot の clone で fetch し、base ブランチの先端からリポの設定を読む。1 回の実行は、この版の設定で動く（[ADR-20261017-007][adr-stop] の決定 4） | 読めないか形が違えば、作業に入らず止まる。点検の依頼のファイルがあれば、読めないことを fail として結果に書く |
| 5 | 点検を回す。作業場所の残骸の見分け（下の「作業場所の残骸」）を含む。試しのセッションが要るとき（「[導入と点検][design-setup]」の「組と回数」）は、ここで回す（[SETUP-2][setup]）。全体の停止の Issue があるときは、試しのセッションを起こさず、未確認の warn にする | fail が 1 つでもあれば、作業に入らず止まる（[SETUP-2][setup]）。待つ時間の内の点検の依頼のファイルがあれば、結果を書いて、作業に入らずに止まる。待つ時間を過ぎた点検の依頼は、結果を書いて依頼のファイルを消してから、定期の実行として作業を続ける（「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」。[ADR-20261022-004][adr-intake-req] の決定 5） |
| 6 | 基線（base ブランチの先端の必須チェック）を読む（[IMPL-9][impl]） | 緑でなければ、新しい着手（計画の輪）・最初の変更の作成・載せ直しだけを止め、ほかは続ける（[ADR-20261015-006][adr-flow] の決定 2） |
| 7 | Project の Issue と、結びつく PR と、人の操作と、印と、必須チェックの結果を読み、作業の単位ごとに状態を組み立てる（下の「状態の組み立て」） | API が失敗したら、作業を増やさずに記録して止まる（[SAFE-4][safety]） |
| 8 | 作業の単位ごとに、「次の工程」の表で工程を決めて進める。作業の単位を進める順は下の「作業の単位を進める順」。進めた後に、Project の表示の欄（主な流れの枠・状態・止め方・先の依頼・安全）と、表示のラベル `security-suspected`（安全の軸に値がある間だけ付け、値が外れたら外す）を書く。どちらも判定には読まない（[FLOW-39][flow]、[SAFE-19][safety]） | — |
| 9 | 作業の単位を 1 つ進めるごとに、所要時間の上限（`run.maxMinutes`）を見る。上限の内なら順 8 に戻って次の作業の単位を進め、超えたら、残りの作業の単位は次の実行に回す（[FLOW-4][flow]） | — |
| 10 | 点検の依頼のファイルがあれば（実行の途中で人が `check` を呼んだ）、順 3 の合図を読み直し、順 5 の点検だけを行って結果を書く。記録と、状態の表示のファイル（`status.json`。「[導入と点検][design-setup]」の「状態の表示」）を書き、lock を外す（[FLOW-5][flow]） | — |

- 受け入れの依頼の実行（人が `/verify-issue` から呼んだ intake の Skill の依頼で起こされた実行）は、順 1〜5 をほかの実行と同じに行い、順 6〜9 に進まずに、受付 AI のセッションを 1 つ起こしてから順 10 を行う。GitHub には何も書かない。順 3〜5 で止まるときと、全体の停止の Issue があるときは、受付 AI を起こさない理由を、受け入れの依頼の結果のファイルに書く（「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」、[ADR-20261022-004][adr-intake-req] の決定 2）
- lock の取り方（順 2。[運用の規則][flow]）
  - 起動の時刻は、lock を書く側と比べる側で同じ関数で取り、時刻帯に依らないエポック秒（整数）にする。macOS は `TZ=UTC LANG=C ps -o lstart= -p <PID>` の文字を UTC の時刻として読む（`ps` の時刻の書き方は `TZ` と `LANG` で変わるため）。Linux は、`/proc/<PID>/stat` のプロセスの起動の時刻（マシンの起動からの時間）に、マシンの起動の時刻（`/proc/stat` の `btime`）を足す。`sessions.jsonl` のプロセスの行の `claude` の起動の時刻も、同じ関数で取る（下の「手元の記録」）
  - lock は、排他の作成で作る。中身を書き終えた一時のファイル（`run.lock.new-<自分の PID>`）に、`link` で `run.lock` の名前を付ける（同じ名前のファイルがあれば失敗する）。作れれば、lock を取れた。一時のファイルは、作れても作れなくても消す。中身を書く前の空の lock を、ほかのプロセスが読まないため
  - 作れなければ（lock がある）、lock を読み、順 2 の条件で古い lock かを見分ける。持ち主が動いていれば、見送る。中身を読めない lock（壊れたもの）は、古いかを見分けられないので奪わずに見送る（止める側）
  - 古い lock なら、lock を取ろうとするプロセスごとに違う名前（`run.lock.stale-<自分の PID>`）に rename で退け、退けたファイルを読み直す。読み直した中身が、古いと見分けた中身と同じなら、新しい lock を排他の作成でもう 1 回だけ作り、退けたファイルを消す。作れなければ、見送る
  - rename が失敗したとき（ほかのプロセスが先に退けた）は、見送る。読み直した中身が違うとき（ほかのプロセスが奪った後に作った新しい lock を退けた）は、退けたファイルを `run.lock` に rename で戻してから、見送る
  - 2 つのプロセスが同時に古い lock と読んでも、排他の作成で片方だけが lock を取る。退けたファイルを読み直すのは、先に奪ったプロセスの新しい lock を、後のプロセスが古い lock と取り違えて退けたときに、持ち主に返すため
- 全体の止める合図と全体の停止の Issue は、順 3 のほかに、AI のセッションを起動する前にも読む。全体の止める合図は、GitHub に書き込む前にも読み、AI のセッションが動いている間は `run.stopSignalPollSeconds` ごとに読む（[運用の規則][flow]、[SAFE-19][safety]）
- 書かずに試す合図（`run.dryRun`）は持たない。最初の実行から GitHub に書く（[ADR-20261024-002][adr-no-stages] の決定 2）
- 進行 Bot が起こす子プロセス（`gh`・`git`・`lsof` など。AI のセッションを除く）は、1 つずつ `run.commandMinutes` を過ぎたら止める。止めた後の扱いは、子プロセスの種類（GitHub を読む処理、GitHub への書き込み、push と取り込み、止める手順の残りの探し方）ごとに、[設定][design-settings]の「子プロセスが時間の上限を過ぎたとき」の表で決める（[SAFE-4][safety]）。順 2〜4 の子プロセス（前の実行が残したセッションを探す `lsof`、合図を読む `gh api`、リポの設定を読むための `git fetch`）は、リポの設定を読む前に動くので、`run.commandMinutes` でなく、プログラムに固定した 10 分（`run.commandMinutes` の初期値と同じ）を過ぎたら止める。止めるときの `SIGTERM` から `SIGKILL` までの猶予も、`limits.stopGraceSeconds` でなく、プログラムに固定した 10 秒（`limits.stopGraceSeconds` の初期値と同じ）にする

### 全体の停止の Issue

AI が書いた文の検疫で見つかったとき（Q2 のうち、`security` の印の `where` が `text` のとき）に、進行 Bot が全体を止めるために開く Issue（[SAFE-19][safety]、[ADR-20261024-005][adr-security] の決定 3）。

- 見分け方：当てる先のリポの Issue のうち、`safety.botAccounts`（[設定][design-settings]）のアカウントが起票し、コメントに有効な `halt` の印がある Issue。進行 Bot は、毎回の実行で、`safety.botAccounts` のアカウントごとに、起票した Issue を開閉を問わず REST の `creator` で一覧にし、コメントの印を読む。起票した人は書き換えられないので、人が題名やラベルを変えても見失わない
- 止める間：開いている全体の停止の Issue が 1 つでもあるか、閉じた全体の停止の Issue のうち、最新の `halt` の印より後に maintain 以上の人が書いた `## 安全の確認` が無いものが 1 つでもあれば、全体を止める。確かめずに閉じたときも止めたままにする（止める側に倒す）。全体の停止は、すべての全体の停止の Issue が、最新の `halt` の印より後の `## 安全の確認` を持って閉じたときに解ける
- 止めている間は、どの作業の単位でも AI のセッションを起こさない。AI を使わない工程（検疫、マスターの写し、決定の印、表示の欄、載せ直しのうち衝突しないもの、マージの判定、催促、片付け）は続ける
- 開き方：開いている全体の停止の Issue があれば、新しく開かずに、開いている Issue に `halt` の印のコメントを足す。無ければ Issue を開き、すぐに `halt` の印（`issue` に見つけた作業の単位の Issue の番号）のコメントを書く。本文とコメントには、見つけた作業の単位の Issue の番号と、人がすること（ほかの作業も確かめ、`## 安全の確認` を書いて閉じる）を書き、見つかった文は写さない（[ADR-20261024-005][adr-security] の決定 4）
- 開いた実行で動いている AI のセッションは、全体の止める合図と同じ手順（プロセスグループごと）で止める（「[AI のセッション][design-ai]」の「止める手順」）
- 全体の停止の Issue は、作業の単位にしない（入口の検疫・下書き・表示の欄の対象にしない）。進行 Bot のアカウントが起票した Issue は、`follow-up` の印があるときだけ作業の単位にし、`halt` の印も `follow-up` の印も無いもの（Issue を開いた後、印を書く前に実行が切れたもの）は、作業の単位にせず、点検の warn に出す。人が読んで閉じるまで、AI に渡さないため
- 見つけた作業の単位の安全の軸（攻撃の疑い（AI の文））は、全体の停止を解いても残り、作業の単位の Issue の `## 安全の確認` で外れる（Q4）

## 作業の単位を進める順

1 回の実行の中で、作業の単位を次の順に進める。同じ組の中は、Issue の番号の小さい順にする。ただし、新しい着手（組 4）はマイルストーンの版の小さい順に並べ、同じ版の中を Issue の番号の小さい順にする（[FLOW-1][flow]）。マージの判定は、組 2 の中では行わず、組 2 を進めた後に、PR の番号の小さい順で別に回す（[MERGE-5][merge]）。

![作業の単位を進める順][fig-issue-order]

| 順 | 組 | 理由 |
| --- | --- | --- |
| 1 | 片付け（マージ済み・閉鎖済み） | 進行中の作業の単位の数の上限（`limits.wip`）を先に空ける。片付けは、軸の値と全体の停止を問わず行う（[FLOW-42][flow]、[MERGE-7][merge]） |
| 2 | 進行中（計画済みと、変更の枠の状態） | 始めた作業を先に進める。新しい着手は進行中の作業の単位の数の上限で止まるので、進行中の作業が先に動かないと流れが詰まる（[FLOW-3][flow]） |
| 3 | 依頼（起票済み・検疫済み・差し戻し済み・直し済み・下書き済み） | 人が読むマスターを早く渡す。受付 AI を起こす下書きと書き直しの件数は、1 回の実行の上限（`limits.intakePerRun`）で抑える（[TEXT-12][text]） |
| 4 | 新しい着手（決定済み） | 決定の印を書き、上の組を進めた後に空いた分だけ、計画の輪に進める（[FLOW-1][flow]） |

- 組を進めるたびに状態を GitHub から読み直さず、その実行で書いた印と GitHub の変化を、組み立てた状態に足す（下の「次の工程」の見直し）

順は暫定。運用の記録（[FLOW-5][flow]）で、所要時間の上限に当たって次の実行に回された組を見て見直す。

## 作業の単位の状態遷移

![作業の単位の状態遷移][fig-states]

図は、要件の図と同じファイル（[要件の Issue の状態の遷移][flow]の写し）。主な流れは 17 の状態を 4 つの枠（依頼・計画・変更・終了）に分け、止め方・先の依頼・安全の 3 本の軸を主な流れに重ねる。
基本設計は、下の「状態の組み立て」で状態を GitHub の何から決めるかを、「次の工程」で状態ごとに進行 Bot が何をするかを決める。

### 状態の組み立て

![状態の組み立て][fig-state-assembly]

進行 Bot は、毎回の実行で次のものを読み、作業の単位ごとの状態を組み立て直す。判定には、GitHub にある人の操作・進行 Bot の印・PR・必須チェックの結果だけを使う。Project の表示の欄と、表示のラベル（`security-suspected`）は、進行 Bot が書く表示で、判定に読まない。手元の記録は、上限の数え上げにだけ使う（[ADR-20261015-006][adr-flow] の決定 4、[ADR-20261024-001][adr-model-states] の決定 4）。

- 読むのは、設定した Project（[SETUP-1][setup]）の項目のうち、当てる先のリポ（マシンの設定の `repository.*`）の Issue だけ。ほかのリポの Issue と、Project に入った PR の項目は読まない（PR は、結びつきから作業の単位ごとに読む）。ただし、別のリポに移された Issue を見つけるため、当てる先のリポの開いている PR のうち、作業ブランチ（`<型>/issue-<番号>`）から開き、PR に進行 Bot の `link` の印（`issue` に番号）があるものも読む。印の Issue を REST で引いて、返った Issue の `repository_url` が当てる先のリポでないか、GraphQL で引いて `NOT_FOUND` なら、別のリポに移されたとみなす。REST は移した先の Issue へ `301` を返し、`gh api` は `301` をたどって移した先の Issue を返すので、引けたことを当てる先のリポにあると読まない（FACT-66）
- 閉じた Issue も読む。閉鎖済み・中止・完了の見分けと、片付けと、作業場所の残骸の見分けに使う
- 進行 Bot のアカウントが起票した Issue は、`follow-up` の印があるときだけ作業の単位にする（上の「全体の停止の Issue」）

| 読むもの | 読む先 | 使い方 |
| --- | --- | --- |
| 人の操作のラベル（`agent-ready`・`agent-paused`・`agent-manual`）と、付けた人と外した人と時刻 | Issue の timeline（`LabeledEvent`・`UnlabeledEvent`） | 決める・一時止める・引き取る（[FLOW-38][flow]）。権限は読む直前に 1 人ずつ引き、要る権限の無い人の操作は無いものとして読む（[TEXT-10][text]） |
| 人の見出しのコメント（`## 作業指示`・`## 差し戻し`・`## 再開 <戻す先>`・`## 安全の確認`・`## 仕組みの変更の承認`）と、書いた人・最後に編集した人・時刻 | Issue のコメントと、編集の記録（`userContentEdits`） | 依頼の中の状態、戻した後の読み方、軸の値、変えてよいパス。要る権限は [FLOW-38][flow] の表で、満たさない人の見出しは無いものとして読む。進行 Bot の印を持つコメントは、人の見出しに数えない（[FLOW-14][flow]） |
| PR の人の見出しのコメント（`## 却下 R<n>`・`## 判定と違う判断`） | PR のコメント | 指標と、マージの判定の一致の記録にだけ使う（[FLOW-14][flow]、[MERGE-3][merge]） |
| 進行 Bot の印（21 種類） | Issue と PR のコメント | どこまで進んだか。投稿者・未編集・署名の 3 つを満たす印だけを読む（[IMPL-20][impl]、[印と固定の見出しの一覧][markers]） |
| Issue の開閉と閉じた人、Project にあるか、マイルストーン、依存（blocked by） | Issue、Issue の timeline（`ClosedEvent` の `actor` と時刻）、Project（GraphQL） | 閉鎖済みに入るか、片付けをやり直さないか（[FLOW-42][flow]）、着手の条件（[FLOW-1][flow]）、先の依頼の軸（[FLOW-43][flow]） |
| 結びつく PR | PR の一覧。結びつきは、ブランチ名・同じリポ・`link` の印の 3 つで決める（[IMPL-6][impl]） | 開いているか、マージされたか（マージの時刻も。片付けをやり直さないか。[FLOW-42][flow]）、マージされずに閉じたか、head の SHA、draft か |
| 必須チェックの結果 | PR の head の SHA と、base ブランチの先端のチェック | 検査合格・検査不合格・待つ（[IMPL-27][impl]）、基線が緑か（[IMPL-9][impl]） |
| 依存の相手 | 相手の Issue の開閉と閉じた人、相手の結びつく PR | 先の作業が終わったか（[FLOW-43][flow]） |
| 手元の記録 | 記録の置き場 | 実行の失敗と片付けの失敗が続いた回数、受付 AI の拒否、累計と 1 日の利用枠。上限の数え上げにだけ使う |

進行 Bot は、作業の単位ごとに、次の順に読んで状態を組み立てる（[ADR-20261024-001][adr-model-states] の決定 6）。

1. 戻した後の読み方（下の「戻した後の読み方」）と、数えない無効な印（下の「数えない無効な印」）で、数えない印と PR を外す
2. 主な流れの状態を、下の「主な流れの状態の決め方」の表で決める
3. 主な流れが依頼の中の状態なら、下の「依頼の中の状態の決め方」の表で決める
4. 重ねる 3 本の軸の値を、下の「重ねる軸の決め方」で決める

#### 主な流れの状態の決め方

表を上から見て、最初に当てはまった行の状態にする。事実が重なったときは、進んだほうを先に見る（終了 → 変更 → 計画 → 決定 → 依頼）。変更の枠の中だけは、検査不合格をレビュー合格より先に見る（[FLOW-41][flow]）。「結びつく PR」と「印」は、1 で外したものを除いて読む。

| 順 | 状態 | 条件 | 次に動く担い手 |
| --- | --- | --- | --- |
| 1 | 完了 | 結びつく PR がマージされ、`cleanup` の印がある | —（終わり） |
| 2 | マージ済み | 結びつく PR がマージされ、`cleanup` の印が無い | 進行 Bot（片付け） |
| 3 | 中止 | push 以上の人が Issue を閉じ、結びつく PR がマージされておらず、`cleanup` の印がある | —（終わり） |
| 4 | 閉鎖済み | push 以上の人が Issue を閉じ、結びつく PR がマージされておらず、`cleanup` の印が無い | 進行 Bot（片付け） |
| 5 | 衝突あり | 開いた結びつく PR があり、PR の head を `head` に持つ `conflict` の印がある | AI（衝突の直し） |
| 6 | 検査不合格 | 開いた結びつく PR があり、head の必須チェックに `failure` か `timed_out` がある | AI（直し） |
| 7 | レビュー不合格 | 開いた結びつく PR があり、PR の head を `head` に持つ最新の `review` の印の `result` が `fix` | AI（直し） |
| 8 | レビュー合格 | 開いた結びつく PR があり、PR の head を `head` に持つ最新の `review` の印の `result` が `pass` で、必須チェックがすべて `success` | 人（マージ） |
| 9 | 検査合格 | 開いた結びつく PR があり、必須チェックがすべて `success` で、PR の head を `head` に持つ `review` の印が無い | AI（変更の確かめ） |
| 10 | 変更済み | 開いた結びつく PR があり、順 5〜9 に当たらない（必須チェックがまだ無いか、動いている途中、ほかの結果） | CI |
| 11 | 計画済み | 開いた結びつく PR が無く、`plan` の印がある | AI（変更の作成） |
| 12 | 決定済み | 依頼の中の状態の決め方で下書き済みになり、有効な `agent-ready` がある | AI（計画の輪。着手の条件を満たしてから） |
| 13 | 依頼の中の状態 | 順 1〜12 に当たらない。下の「依頼の中の状態の決め方」で決める | 下の表 |

- Issue を閉じた人は、Issue の timeline の最新の `ClosedEvent` の `actor` で確かめる。push 未満の人が閉じたときは、順 3・4 に当てず、順 5 から見る（閉じる前の状態のまま読む）。止め方は、下の「次の工程」で停止中（`unauthorized-close`）にする（[FLOW-42][flow]、FACT-73）。結びつく PR がマージされていれば、誰が閉じても順 1・2 で読む
- 結びつく PR がマージされずに閉じたとき（1 で外した PR を除く）は、開いた結びつく PR が無いので、順 11 か順 12 で読み、下の「次の工程」で停止中（`pr-closed`）にする
- 順 6 を順 7・8 より先に見るので、レビュー合格の後に必須チェックが赤に変わったとき（状態遷移に入れない出来事）は、検査不合格と読む
- 必須チェックの結果の読み方（すべて `success` が緑、`failure` と `timed_out` が赤、ほかは待つか止める）は [IMPL-27][impl] の表のとおり。必須チェックは、チェックの名前・チェックを出した app・base 側のワークフローのパスの 3 つがすべて一致するものだけを数え、同じ名前が複数あれば最新の 1 件を採る。一致するチェックが無ければ、まだ無いものとして読む（[ADR-20261016-001][adr-pr]）
- 有効な `agent-ready`（決めるラベルの条件）：push 以上の人が付け、付けた時刻（timeline の最新の `agent-ready` の `LabeledEvent`）が、最新のマスターを投稿した時刻より後。差し戻して AI が書き直したマスターと、人の直しを写したマスターは、前に付けたラベルより新しいので、人は読み直して付け直す（[FLOW-36][flow]、[ADR-20261024-004][adr-master] の決定 5）
- 決定済みの間（計画の前）に push 以上の人が `## 作業指示` を書くと、依頼の中の状態の決め方で直し済みになり、決定済みでなくなる。人の直しを写した新しいマスターは、前に付けた `agent-ready` より新しいので、人は読み直して付け直す。`## 作業指示` も Issue の本文も読まないのは、決定済みより後（計画済みから）の状態（[FLOW-36][flow]、[TEXT-4][text]）
- 数える `decision` の印は、最新のマスターより後に書いたものだけ。決め直したときに、前の決定の印を最新のマスターと照らさないため
- 決定済みより後の状態では、`agent-ready` を読まない（外されても止めない。[TEXT-8][text]）

#### 依頼の中の状態の決め方

主な流れの順 13 に当たったときに、表を上から見る。「人の操作」は、push 以上の人が書いた `## 作業指示`（投稿か最後の編集の時刻）と `## 差し戻し`（投稿の時刻）。「マスター」は、最新のマスターの下書き（有効な `draft` の印のあるコメント。[FLOW-36][flow]）。

| 順 | 状態 | 条件 | 次に動く担い手 |
| --- | --- | --- | --- |
| 1 | 起票済み | Issue が Project にあり、`quarantine` の印（`target` が `issue`）が無い | 進行 Bot（入口の検疫） |
| 2 | 検疫済み | マスターがまだ無い | AI（下書き） |
| 3 | 差し戻し済み | 最新の人の操作が `## 差し戻し` で、マスターより新しい | AI（書き直し） |
| 4 | 直し済み | 最新の人の操作が `## 作業指示` で、マスターより新しい | 進行 Bot（人の直しの検疫） |
| 5 | 下書き済み | マスターが、最新の人の操作より新しい | 人（直す・差し戻す・決める） |

- AI に渡す依頼の文は、いつも人が決めたマスター（`decision` の印が指すもの。[TEXT-1][text]）
- 人の `## 作業指示` は、マスターを写して直した全文で書く。作業指示が 2 つ以上あっても止めず、最新の 1 つを読む（[FLOW-36][flow]）
- 依頼の中の状態の間は、先の依頼の軸を見ない（[FLOW-43][flow]）

#### 戻した後の読み方

push 以上の人が書いた最新の `## 再開 <戻す先>` を R とする（[FLOW-40][flow]、[ADR-20261024-001][adr-model-states] の決定 7）。

| 戻す先 | 数えないもの | 続ける状態 |
| --- | --- | --- |
| 続きから | 無い | 同じ状態。結びつく PR がマージされずに閉じていれば、また停止中（`pr-closed`）になる |
| 計画から | R より前の `plan`・`review`・`fix`・`merge`・`conflict` の印と、R より前に作った PR | 決定済み（AI が計画し直す） |
| 下書きから | 計画からの数えないものに加えて、R より前に付けた `agent-ready` と、R より前の `decision` の印 | 依頼の中の状態（ふつうは下書き済み。マスターより新しい `## 作業指示` があれば直し済み） |

- 計画からと下書きからでは、R より前に作った開いている PR を、進行 Bot が閉じ、作業ブランチを消す（下の「次の工程」の「先に見る」の表の順 9）。新しい PR を、同じ名前の作業ブランチ（`<型>/issue-<番号>`）で作るため。前の PR の番号の名前のセッションのフォルダも、片付けと同じに消す（下の「作業場所の残骸」）
- 一時停止中と引き取り中は、ラベルを外したときに、ラベルを付けた後に書かれた R の戻す先で続ける。ラベルを付けた後の R が無ければ、続きから
- R の戻す先は、`## 再開` の見出しの行の語（`続きから`・`下書きから`・`計画から`）で読む。ほかの語の `## 再開` は、無いものとして読む

#### 重ねる軸の決め方

1 本の軸に当てはまる値が 2 つ以上あるときは、表の上の値にする。人が外すのに手間がかかるほうが上で、下の値は消えずに残り、上の値が外れると次の値が出る（[FLOW-38][flow]）。

| 軸 | 値 | 条件 |
| --- | --- | --- |
| 止め方 | 停止中 | 最新の `stop` の印が、R より新しい |
| 止め方 | 引き取り中 | push 以上の人が付けた `agent-manual` がある |
| 止め方 | 一時停止中 | push 以上の人が付けた `agent-paused` がある |
| 先の依頼 | 未完了 | 主な流れが決定済みか、決定済みより後で、依存の相手のどれかが、マージ済み（相手の結びつく PR がマージされた）でも閉鎖済み（push 以上の人が相手の Issue を閉じ、相手の PR がマージされていない）でもない |
| 先の依頼 | 中止あり | 主な流れが計画済みか、計画済みより後で、依存の相手のどれかが閉鎖済みで、相手の番号を `dependency` に持つ `dependency-review` の印が無い。主な流れが決定済み（計画の前）なら、見直さずに（なし）と読む |
| 安全 | 攻撃の疑い（AI の文） | 最新の `security` の印（`where` が `text`・`code`・`leak` のどれか）が、maintain 以上の人が書いた最新の `## 安全の確認` より新しい |
| 安全 | 攻撃の疑い（入口） | 最新の `security` の印（`where` が `entry`）が、maintain 以上の人が書いた最新の `## 安全の確認` より新しい |

- どの軸も、当てはまらなければ（なし）
- 先の依頼の軸の「マージ済み」と「閉鎖済み」は、相手の作業の単位の状態でなく、相手の Issue と PR の事実で見る。相手が push 未満の人に閉じられて止まっている間は、未完了のまま（[ADR-20261024-006][adr-cleanup] の決定 3）
- 止め方の停止中は、印を書き換えられても外れないよう、R と `stop` の印の新しさだけで決める。R が無ければ、`stop` の印が 1 つでもあれば停止中

#### 数えない無効な印

人が `marker-invalid` で止めた作業の単位を戻したとき（[止まった状態から戻す手順][flow]）、進行 Bot は、次をすべて満たす無効な印を、止める契機に数えない（[IMPL-20][impl]、[ADR-20261021-004][adr-marker-keys] の決定 4）。

- 印の置き場の Issue で（置き場が PR なら、結びつく Issue で）、push 以上の人が R を書いた。PR の結びつく Issue は、作業ブランチの名前（`<型>/issue-<番号>`）の番号と、同じリポの 2 つで決める。PR の `link` の印が無効になったときと、数えない印になったとき（前の鍵を外した後など）も、結びつく Issue を決められるようにするため
- R より前に書いた有効な `stop` の印（`reason` が `marker-invalid`）のどれかの `comments` に、無効な印のコメントの ID がある。読む `stop` の印は、Issue と、結びつく PR のもの（`link` の印が無効な PR は、作業ブランチの名前で引いた PR）
- 無効な印のコメントが、R より後に編集されていない（`lastEditedAt` が無いか、R より前）。R の後に編集されたら、新しく無効になった印として数える

数えない印と、条件に当たらない無効な印は、次のように扱う。

- 数えない印は、無いものとして読み、中身（判定・件数・ハッシュなど）を判定に使わない。無いものとして読んだ結果、ほかの判定（`review` の印の `round` の欠け、マスターが無いので検疫済みに戻るなど）に当たれば、当たった判定に従う
- `stop` の印に挙がっていない無効な印は、1 つでもあれば止める。R の後に新しく無効になった印と、鍵を一覧から外して確かめられなくなった印も、まず止めて知らせ、人が R を書いた後に、数えない対象になる
- `review` の印の `round` の欠けは、数えない対象にしない。欠けは印のコメントが無いことで、挙げるコメントが無いため。途中のラウンドの `review` の印を数えないと `round` が欠けるので、人は `## 再開 計画から` で計画からやり直す（[止まった状態から戻す手順][flow]）
- `stop` の印は、有効なものだけを読む。`comments` は署名の対象に入るので、`stop` の印を別の Issue に写しても、直しても、数えない印は増えない

#### 進行中の作業の単位の数え方

進行中の作業の単位の数の上限（`limits.wip`）で数えるのは、計画済みから、マージ済み・閉鎖済みの前までの作業の単位（[FLOW-3][flow]、[ADR-20261024-001][adr-model-states] の決定 10）。

- 重ねる軸に値がある作業の単位も数える。人の対処を待つ作業があるうちに、新しい作業を積み増さないため
- 決定済み（計画の前）と依頼の中の状態は数えない。人が見る作業がまだ無いため
- 記録を失ったときの扱い（「[運用の規則][flow]」の、`records-missing`。実装の都合の記号）も、同じ作業の単位に掛ける

#### 状態遷移に入れない出来事

| 出来事 | 見つけ方 | 扱い |
| --- | --- | --- |
| 決めた後に依頼が変わる | 決定済みより後の状態で、最新の `decision` の印より後に `## 作業指示` が書かれたか、Issue の本文が変わった | 読まない（AI には決めたときのマスターだけを渡す）。作業指示は、読まなかったことを `ignored-instruction` の印で 1 回だけ知らせる。本文の変更は知らせない。数える `decision` の印の `textHash` が、最新のマスターの文のハッシュと違えば、印の書き換えとして停止中（`marker-invalid`）にする（[TEXT-4][text]） |
| レビュー合格の後に検査が落ちる | head の必須チェックが赤 | 主な流れの状態の決め方の順 6 で、検査不合格と読む（止めない） |
| 触ってはいけない所を変える | 計画が変える見込みのパスか、変更が触れたパスが、変えてはいけないパスの一覧に当たる | 計画の後なら計画済みのまま停止中（`protected-path`）、push の前なら push せずに停止中（`protected-path`）。push で効くものは、認めていても停止中（`manual-push`）にして、人が push する。認めた `.claude/**` と `.mcp.json` は、作業 AI を起こす前に停止中（`manual-change`）にして、人が変える（[IMPL-15][impl]、[ADR-20261027-003][adr-claude-dir]、下の「状態ごとの工程」の計画済み、「計画の工程の中の順番」と「push の手順」） |

### 次の工程

作業の単位ごとに、上の「状態の組み立て」の後、「先に見る」の表を上から見て、当てはまった行の扱いにする。どの行にも当たらなければ、「状態ごとの工程」の表で、主な流れの状態の行の工程に進む。

- 「重い」は AI のセッションを起動する工程で、作業の単位ごとに 1 回の実行で 1 つまで。「軽い」は起動しない工程で、重い工程の前後に同じ実行で続けてよい（[FLOW-4][flow]、[ADR-20261015-006][adr-flow] の決定 1）
- 工程を 1 つ進めたら、その工程で書いた印と GitHub の変化（PR の作成、ラベルの付け外し）を組み立てた状態に足して、同じ作業の単位の表を上から見直し、次に当てはまった行に進む。見直しは、push をしたとき、同じ実行で 2 つ目になる重い工程に当たったとき、待つか何もしない行に当たったときに止める
- push した実行（変更の作成・直し・載せ直し）では、push した作業の単位をそれ以上進めない。CI の結果が要る工程（レビュー、マージの判定）は、CI の結果が出ている実行でだけ進める（[FLOW-4][flow]）
- 重い工程は、全体の止める合図が `run` で、全体の停止の Issue が無いときだけ起こす。起こす前に「[AI のセッション][design-ai]」の「起動の前の確かめ」を行う。全体の停止の Issue がある間は、重い工程に当たったら何もしない（[SAFE-19][safety]）
- 基線が緑でない間は、決定済みの計画の輪、計画済みの変更の作成、レビュー合格の載せ直しだけを止め、ほかは続ける（[IMPL-9][impl]）
- 状態を決められない（読んだ事実の組み合わせが、どの表のどの行にも当たらない）ときは、作業を増やさずに停止中（`unrecoverable`。実装の都合の記号）にする（[SAFE-4][safety]）

| マージ済み | 片付け：Issue を閉じ、作業ブランチ（残っていれば）と作業場所（セッションのフォルダ）を消し、`cleanup` の印を書く（[FLOW-42][flow]、[MERGE-7][merge]） | 軽い | T27 |
| 閉鎖済み | 片付け：開いた結びつく PR を閉じ、作業ブランチと作業場所を消し、`cleanup` の印を書く（[FLOW-42][flow]） | 軽い | T28 |

- マスターを投稿したとき（T2・T3・T30）に `agent-ready` が付いていれば、投稿の後に外し、`approval-reset` の印（マスターの前に付けたものは `early`、前の版のマスターの後に付けたものは `stale`）を書く。前のマスターを読んで付けたラベルで、新しいマスターを決めたことにしないため。外すのは見た目を合わせるためだけで、外し損ねても、有効な `agent-ready` の条件で無効と読む（[FLOW-36][flow]）
- 片付けは、`cleanup` の印を最後に書く。途中で切れても印が無いので、次の実行が同じ行に当たって続きを行う（消したものは消し直さない）。片付けが `limits.retry.count` 回続けて失敗したら、片付けの前の状態のまま停止中（`cleanup-failed`）にし、止めた理由のコメントに消せなかったものを書く。回数は実行の失敗と同じく手元の記録で数える（[ADR-20261024-006][adr-cleanup] の決定 1）
- 作業場所を消す前に、作ったときと同じかを確かめ（[ADR-20261013-001][adr-workspace]）、違えば消さずに、片付けの前の状態のまま停止中にする（`workspace-tampered`。実装の都合の記号。下の「作業場所の残骸」）。片付けの失敗の続いた回数には数えない。止めたのはマージ済みか閉鎖済みに入った後なので、人が `## 再開 続きから` を書くまで、片付けもやり直さない（上の「先に見る」の順 2。[ADR-20261025-001][adr-tampered] の決定 1）
- 作業場所を消す前に、残りのプロセスを探す（作り直す前と同じ探し方。「[AI のセッション][design-ai]」の「止める手順」の表の下）。見つかるか、探し方が時間の上限（`run.commandMinutes`）を超えるか失敗したら、消さずに、片付けの前の状態のまま停止中にする（`session-not-stopped`）。進行 Bot は、見つけたプロセスを止めない。片付けの失敗の続いた回数には数えない。止めたのはマージ済みか閉鎖済みに入った後なので、人が `## 再開 続きから` を書くまで、片付けもやり直さない（上の「先に見る」の順 2。[ADR-20261027-001][adr-leftover]）
- 決定済みより後の状態で、最新の `decision` の印より後に push 以上の人の `## 作業指示` があれば、`ignored-instruction` の印（`comment` に作業指示のコメントの ID）を、同じコメントの有効な印が無いときだけ 1 回書く（軽い。[TEXT-4][text]）
- 作業 AI の commit を取り込んだとき（変更の作成と直し）に、PR の変更ファイルの一覧を、ほかの進行中の PR の変更ファイルと比べ、重なりがあれば `overlap` の印を、同じ PR の組の有効な印が無いときだけ 1 回書く（待たせない。[FLOW-8][flow]）
- レビュー合格の (1) と (2) は、レビューで `pass` を書いた実行でも続けて行う（軽い工程）。🟢 の Issue を作ってから ready にするのは、先にマージされると、Issue にし損ねた指摘が消えるため（[IMPL-26][impl]）
- 変更済みに入った PR（直しの push、人の push、載せ直しで差分が変わった）は、必須チェックを待ってから、検査合格でレビューする。修正の後と人の push の後の再レビューも、検査合格の行に当たる（[ADR-20261024-003][adr-check-first]）

### 計画の工程の中の順番

![計画の工程の中の順番][fig-plan-step]

決定済みの計画の輪（重い）は、1 回の実行の中で、次の順に AI のセッションを起動する。工程は 1 つのまま（[FLOW-4][flow]）。
セッションを起動する前には、毎回、「[AI のセッション][design-ai]」の「起動の前の確かめ」を行う。全体の止める合図、全体の停止の Issue、1 日の上限、1 回の実行の上限のどれかで起動できなければ、計画を投稿せずに終わり、次の実行で計画の工程を 1 から始め直す（[ADR-20261018-002][adr-redo]、[ADR-20261019-003][adr-replan]）。1 Issue の累計の上限に当たったら、停止中（`cost-limit`）にする。

| 順 | すること | 次に進む先 |
| --- | --- | --- |
| 1 | 計画 AI が計画を返す（`models.plan`。作業ごとに変えず、受付 AI の判定と人のラベル `plan:*` は使わない。[ADR-20261024-004][adr-master] の決定 8、[ADR-20261031-002][adr-same-model]） | `opus` が自己申告したら 2。しなければ 3 |
| 2 | 計画 AI が `fable` で計画し直す（1 回だけ。`models.planHard`。[ADR-20261018-002][adr-redo]） | 3 |
| 3 | 計画を確かめる AI（レビュー AI）が計画を確かめ、`ok` か `fix` と指摘の一覧を返す（`models.planReview`） | `ok` なら 5。`fix` で、指摘で計画し直した回数が上限（`limits.planRevisions`）に達していなければ 4、達していれば 6 |
| 4 | 計画 AI が、マスター・直す前の計画・指摘の一覧を受け取って計画し直す（直す前の計画と同じモデル。自己申告は無視して記録に残す） | 3 |
| 5 | 最後の計画の文の欄を、検疫（[TEXT-11][text]）と漏えいの検査に通してから、`plan` の印付きで投稿する（計画済み。T7）。続けて、計画が変える見込みのパス（`plan.paths`）を、変えてはいけないパスの一覧（[IMPL-15][impl]）と照らす | 投稿した実行では、変更の作成に入らない。認めていないパスに 1 つでも当たれば、計画済みのまま停止中（`protected-path`）にし、止めた理由のコメントに、当たったパスと、maintain 以上の人が `## 仕組みの変更の承認` で認めれば変えられることを書く（[ADR-20261024-004][adr-master] の決定 9）。検疫で見つかれば投稿せず、攻撃の疑い（AI の文）にして全体の停止の Issue を開く。漏えいの検査に引っかかれば投稿せず、攻撃の疑い（AI の文。`security` の印の `where` が `leak`）にする（全体は止めない。[ADR-20261027-002][adr-leak]） |
| 6 | 上限まで計画し直しても `fix` だった | 計画を投稿せずに停止中（`plan-limit`）。止めた理由のコメントに最後の指摘を書く（指摘は AI の文なので、検疫と漏えいの検査を通す。[ADR-20261024-002][adr-no-stages] の決定 3） |

- 認めたパスは、その作業の単位の Issue に、maintain 以上の人が書いた `## 仕組みの変更の承認` のどれかに挙がったパス。push で効くもの（[IMPL-15][impl]）は、認めていても計画では止めず、push の前に停止中（`manual-push`）にして人に渡す（下の「push の手順」）
- 計画が変える見込みのパスを照らすのは、計画を投稿した後で、照らす前に実行が切れたら、次の実行は計画済みから変更の作成に進む。照らし損ねたパスは、push の前の検査（下の「push の手順」）が止める（[IMPL-10][impl]）
- 順 5 で投稿する計画コメントに、計画の確かめの結果も、指摘で計画し直したことも書かない（確かめを通った計画だけを投稿する）。直す前の計画、確かめの結果と指摘、やり直した計画は、手元の記録に残す。人が計画を読むことは決まりにしない（[IMPL-10][impl]、[ADR-20261024-002][adr-no-stages] の決定 3）
- 順 2 で計画し直したことは、計画コメントに固定の文で書き添える（[ADR-20261018-002][adr-redo]）
- 計画 AI と計画の確かめのどのセッションも、失敗したとき（出力契約が解析できない、時間かターンか費用の上限など）は、実行の失敗として計画を投稿せずに終わり、次の実行で計画の工程を 1 から始め直す（[IMPL-14][impl]）。確かめが失敗した計画をそのまま投稿しない
- 上限が初期値（1 回）のとき、計画の工程は最大 5 つのセッション（計画 AI が 3 つ、計画の確かめが 2 つ）を起動し、1 セッションの上限 45 分なら最大 225 分かかる。1 回の実行の所要時間の上限（`run.maxMinutes` の初期値 180 分）を超えたら、ほかの作業の単位を次の実行に回す

## push の手順

![push の手順][fig-push]

作業 AI の commit を GitHub に届ける手順（[IMPL-15][impl]、[ADR-20261013-001][adr-workspace] の「取り込み」）。変更の作成・直し（検査の失敗と指摘）・衝突の直しのセッションの後と、進行 Bot だけで行う載せ直しの後に行う。AI が書いた commit は、進行 Bot が検査してから、進行 Bot の clone から送る。

照らす範囲は、PR が base ブランチに足す commit のうち、まだ GitHub に無いもの（進行 Bot の clone で fetch した base ブランチの先端の SHA を `<base>`、origin の作業ブランチの先端の SHA を `<origin>`（作業ブランチがまだ無ければ `<base>`）として、`git rev-list <控えた SHA> ^<base> ^<origin>`）にする。載せ直しと衝突の直しで取り込んだ base の commit は、範囲に入らない。人が base ブランチに入れた変更を、AI の変更として止めないため。GitHub にもうある commit（進行 Bot が照らしてから push したものと、人が作業ブランチに push したもの）も、範囲に入らない。人が push した変更（`manual-push` と `manual-change` の後の push、人の直しの push）で、作業 AI の後の push を止め直さないため。マージの判定の漏えいの検査の掛け直しは、今のまま最終の head の差分の全体に掛ける

| 順 | すること | うまくいかないとき |
| --- | --- | --- |
| 1 | 作業 AI の出力契約を取り出す（「[AI のセッション][design-ai]」の「役ごとの出力契約」）。進行 Bot だけで行う載せ直しでは、とばす | 取り出せなければ、実行の失敗として次の実行に持ち越す。取り出せて、止まった理由（`stopReason`）を返していれば、push せず、止まった理由で停止中にする |
| 2 | 進行 Bot の clone で、AI の作業場所から作業ブランチを取り込み（`git fetch <置き場>/sessions/<セッションの名前>/worktree <ブランチ>`）、取り込んだ先端の SHA を控える。AI の作業場所の clone では git を実行しない（[ADR-20261013-001][adr-workspace]）。控えた SHA が、作業場所を作ったときの SHA と同じ（新しい commit が無い）なら、push しない | 取り込みが objects の検査で失敗したら、停止中にする（`workspace-tampered`）。AI が objects を書き換えたおそれがあるため（FACT-18、FACT-57）。作業 AI が `done` を返したのに新しい commit が無ければ、停止中にする（`no-new-commit`。全部 `unable` の直しと、直せなかった検査の失敗を含む）。新しい commit が無いまま次の実行に回すと、同じ直しを毎回やり直すため |
| 3 | 範囲の commit ごとに、差分が触れるパスを、変えてはいけないパス（進行 Bot のプログラムに固定した名指しのパス（[ADR-20261021-005][adr-blocked]）と、リポの設定の足す分を合わせた一覧。push で効くものとマージまで効かないものの 2 つの組。[IMPL-15][impl]、[ADR-20261024-004][adr-master] の決定 9）と照らす。merge の commit は、どの親とも違う部分（`git show --cc`）を照らす。あわせて、PR の全体の差分（`git diff <base>...<控えた SHA>`）のうち、範囲の commit が触れたパスも照らす | push で効くものに当たれば、認めていても push せず、差分を検査してから Issue に載せて（`manual-push` の印。`head` に控えた SHA、`paths` に当たったパス）、停止中にする（`manual-push`。表の下）。マージまで効かないもののうち、認めていないパスに当たれば、push せずに停止中にする（`protected-path`）。`.claude/**` と `.mcp.json` は、認めていても当たりにする（作業 AI には変えさせない。[ADR-20261027-003][adr-claude-dir]）。途中の commit で触れて後の commit で戻しても、途中の commit が GitHub に届くので止める |
| 4 | GitHub に書く文を組み立てる。初回は PR の題名と本文、直しと衝突の直しは対応コメント（直しは出力契約の `responses`、衝突の直しは固定の文と出力契約の `checks`。形は「[AI のセッション][design-ai]」の「コメントの形」）。題名は、作業 AI の案（出力契約の `pr.title`）を規約（`conventions.*`。Conventional Commits の形と言語）に照らしてから使い、外れていれば、Issue の文を使わない固定の形で作る（`conventions.language` が `ja` なら `<作業ブランチの型>: issue #<Issue の番号> の対応`。言語ごとの固定の文は進行 Bot のプログラムに持つ。[TEXT-6][text]、[IMPL-6][impl]）。本文は、「AI が生成した」の 1 行、`Closes #<Issue の番号>`、作業 AI が確かめた検査の結果（出力契約の `checks`）、本文の案（`pr.body`）の順に並べる。続けて、漏えいの検査を、範囲の commit ごとの差分（merge の commit は `git show --cc`）、commit ごとのメッセージと作者、組み立てた文（最後に使う題名を含む）に掛け、組み立てた文のうち AI の文の欄に検疫（[TEXT-11][text]）を掛ける。検査は `plugin/src/` の中のものを使い、worktree の中の検査は使わない（[IMPL-15][impl]） | 漏えいの検査に引っかかれば push せず、攻撃の疑い（AI の文。`security` の印の `where` が `leak`）にする（全体は止めない。[ADR-20261027-002][adr-leak]）。途中の commit で足して後の commit で消した秘密も、途中の commit が GitHub に届くので止める。検疫で見つかれば push せず、攻撃の疑い（AI の文）にして、全体の停止の Issue を開く（上の「全体の停止の Issue」、[SAFE-19][safety]）。push の後に見つけて、push だけ済んだ状態で止めないため |
| 5 | 進行 Bot の clone から `git ls-remote` で、作業ブランチの今の先端を読み、控えた SHA の祖先であることを確かめる（fast-forward で届くこと）。作業ブランチがまだ無ければ、作業場所を作ったときに控えた base の SHA で確かめる（[IMPL-15][impl]、[SAFE-13][safety]） | 祖先でなければ push せず、停止中にする（`not-fast-forward`）。AI が履歴を書き換えたか、ほかの誰かが push したため |
| 6 | 全体の止める合図と、全体の停止の Issue を読み直す（[運用の規則][flow]、[SAFE-19][safety]） | 合図が `run` でないか、全体の停止の Issue があれば、push せずに止まる。実行の失敗には数えない。AI が操られた疑いがある間は、AI の変更を GitHub に届けないため。止まった作業は、合図が `run` に戻り、全体の停止が解けた後に、同じ状態からやり直す |
| 7 | 直しと衝突の直しでは、順 4 で組み立てて検査した対応コメントを、`fix` の印（`round` は最新の `review` の印の `round`、`head` は控えた SHA、`cause` は直したもの、`model` は作業 AI を起こしたモデル）付きで PR に書いてから送る。push の後に実行が切れても、直しを往復に数え、次のラウンドで同じ指摘の再発を判定し、対応コメントも PR に出るため（[ADR-20261022-003][adr-rounds] の決定 4）。進行 Bot の clone から、deploy key で `git push origin <控えた SHA>:refs/heads/<型>/issue-<番号>` を送る。ブランチ名でなく SHA を送り、force push はしない（[IMPL-15][impl]） | 対応コメントを書けなければ、push せずに、実行の失敗として次の実行に持ち越す。push が断られたら（ruleset など）、実行の失敗として次の実行に持ち越す。書いた `fix` の印は PR に届かないので、直しは次の実行で同じ状態（検査不合格かレビュー不合格）からやり直す。衝突の直しは、PR の head が変わらず `conflict` の印が残るので、次の実行で衝突ありからやり直す（往復の上限の確かめを含む）。届かなかった `fix` の印も往復に数える（止まる側） |
| 8 | `git ls-remote` で、作業ブランチの先端が送った SHA になったことを読み戻す。初回は、順 4 で組み立てて検査した題名と本文で PR を draft で作り、すぐに `link` の印（Issue には `pr`、PR には `issue`）を Issue と PR に書く（[IMPL-11][impl]、[IMPL-6][impl]）。表示の欄は、作業の単位の状態を書く（[IMPL-7][impl]、[FLOW-39][flow]） | 読み戻した SHA が違えば、停止中にする（`unrecoverable`）。PR を作れなければ、実行の失敗にする。作業ブランチだけが残るので、次の実行は計画済みの行で停止中にする（`branch-without-pr`） |

- push で効くもの（順 3）に当たったときは、順 4 の漏えいの検査のうち、範囲の commit ごとの差分と、commit ごとのメッセージと作者に掛ける検査を同じく行い、PR の全体の差分（`git diff <base>...<控えた SHA>`）に検疫（[TEXT-11][text]）を掛けてから、差分を `manual-push` の印のコメントで Issue に載せる。漏えいの検査に当たれば攻撃の疑い（AI の文。`security` の印の `where` が `leak`）、検疫で見つかれば攻撃の疑い（AI の文。`security` の印の `where` が `code`）にし、差分を載せない。差分を載せたコメントがコメントの上限（60,000 文字。「[AI のセッション][design-ai]」の「共通の決まり」）を超えるときは、差分を載せず、当たったパスと、変わったファイルの一覧だけを載せる
- 人は、載った差分を確かめ、自分で作業ブランチ（`<型>/issue-<番号>`）に push してから、`## 再開 続きから` を書く（[止まった状態から戻す手順][flow]）。PR があるとき（直しと衝突の直し）は、人の push（T16）として、変更済みから進む（往復に数えない）。PR が無いとき（変更の作成）は、次の実行で、進行 Bot が人の push した作業ブランチから PR を作る（上の「状態ごとの工程」の計画済み）。差分を載せられなかったときと、人が push しないときは、`## 再開 計画から` か `## 再開 下書きから` で戻す
- 変えてはいけないパスを「認めた」と読むのは、maintain 以上の人が書いた `## 仕組みの変更の承認` に挙げたパスだけ。最新の `decision` の印より後に書かれ、書いた人と最後に編集した人のどちらも maintain 以上のものを読む（[TEXT-10][text]）。`## 再開 下書きから` で戻して決め直したら、前の依頼のための承認は読まない（新しい依頼で人が認め直す）
- 載せ直し（[MERGE-6][merge]、[FLOW-44][flow]）は、レビュー合格の PR だけに行う。AI のセッションを起こさずに、進行 Bot の clone で base ブランチを作業ブランチに取り込み（`git merge`）、順 3〜8 を同じく行う。衝突したら取り込みをやめ、`conflict` の印（`head` に PR の head）を書いて、衝突ありにする（T19）。次の実行で、作業 AI の衝突の直しのセッションで解き、順 1〜8 を直しと同じく行う（対応コメントと `fix` の印（`cause` は `conflict`）を順 7 で書く）。作業 AI を起こす前に、往復の回数が上限に達していないかを確かめる（上の「状態ごとの工程」の衝突あり）。差分の patch-id を比べて、印を付け直すか再レビューに回すかは、上の「状態ごとの工程」のレビュー合格の (3)
- 衝突の直しで、作業 AI が merge の commit の後に commit を足しても、merge の commit を作らずに衝突を解いても、`fix` の印 1 つで往復 1 回に数える。head が merge の commit 1 つだけかは確かめない（[ADR-20261022-003][adr-rounds] の決定 2）
- 進行 Bot の clone は作業ツリーを持ち、取り込み（`git merge`）に使う。取り込む前に毎回、進行 Bot の clone で動いている git のプロセスが無いことを確かめ（lock を持つ実行の中なので、あれば前の実行の残り）、残った `index.lock` を消し、取り込みの途中の状態（`MERGE_HEAD`）があれば取り込みをやめ（`git merge --abort`）、作業ツリーと index を先端にそろえる（`git reset --hard` と `git clean -ffdx`）。前の実行が取り込みの途中で落ちても、後の実行の git が失敗し続けないため。git のプロセスが残っていれば、取り込まずに実行の失敗にする
- 進行 Bot の clone の git は、ホームの個人設定とシステムの設定を読まず（`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`）、`core.hooksPath` を空のフォルダにし、署名しない（`commit.gpgsign=false`）で動かす（[SAFE-16][safety]）。載せ直しの merge の commit の作者は、投稿に使うアカウントの名前と、GitHub の noreply のアドレスにする（作業 AI の commit と同じ。「[AI のセッション][design-ai]」の「環境変数」）。手元の Mac で、人の鍵で署名した commit を送らないため
- push した実行では、push した作業の単位を次の実行まで進めない（[FLOW-4][flow]）
- 順 2 で控えた SHA を、順 3〜8 のすべてで使う。途中で作業ブランチを読み直さないので、検査した commit と送る commit が同じになる

## 判定

上の「状態ごとの工程」の、検査合格・検査不合格・レビュー不合格・衝突あり・レビュー合格の行で使う判定を決める。判定には、GitHub にある署名付きの印と、PR と必須チェックの状態だけを使う（[ADR-20261015-006][adr-flow] の決定 4、[ADR-20261024-002][adr-no-stages] の決定 5）。

### ラウンドと往復の数え方

![ラウンドと往復の数え方][fig-rounds]

- ラウンドは、PR のレビューの 1 回。`review` の印の `round` は 1 から始め、レビューするたびに 1 増やす。欠けていたら停止中にする（`marker-invalid`。[IMPL-18][impl]）
- 直しか衝突の直しの後の再レビュー、進行 Bot だけの載せ直しで差分（patch-id）が変わったときの再レビュー、人の push の後の再レビューは、新しいラウンドにする。載せ直しで差分が同じときは、ラウンドを増やさず、同じ内容の印を新しい head に付け直す（[MERGE-6][merge]）。どのレビューも、必須チェックが通ってから行う（[IMPL-27][impl]）
- `fix` の印の `round` は、最新の `review` の印の `round`（直しでは、直した対象のラウンド）と同じにする。最初のレビューの前の検査の失敗の直しは、`round` を 0 にする。`cause` には、直したもの（`check`・`review`・`conflict`）を書く（[IMPL-27][impl]、[MERGE-6][merge]、[ADR-20261024-001][adr-model-states] の決定 9）。`model` には、その直しで作業 AI を起こしたモデル（`--model` に渡した値。`models.work` か `models.workRaised` の `model`）を書く。`models.workRaised` で起こしたとき（最初の実装が `sonnet`）は、`fix` の印のコメントに、最初の実装のモデルから上げたことを決まった文で書き、Issue には別のコメントを書かない（[IMPL-25][impl]、[ADR-20261101-001][adr-raise-in-fix]）
- 往復の回数は、PR の有効な `fix` の印の数（作業 AI が変更を push した回数）。`fix` の印は、作業 AI の変更を push するたびに 1 つ書き、レビューの指摘を直したとき（[IMPL-23][impl]）、検査の失敗を直したとき（[IMPL-27][impl]）、載せ直しの衝突を解いたとき（[MERGE-6][merge]）のどれも 1 回に数える。1 つのラウンドに、指摘の直しと検査の失敗の直しの `fix` の印が 2 つ以上つくこともある（[ADR-20261024-003][adr-check-first] の決定 4）。`fix` の印は push の前に書くので、push が GitHub に届かなかった回の印も数える（上の「push の手順」の順 7）。届かなかった回の数えすぎは、止まる側に倒れる（[IMPL-24][impl]、[ADR-20261022-003][adr-rounds] の決定 1、決定 4）
- 進行 Bot だけで行う載せ直し（AI のセッションを起こさない）で差分が変わった再レビューと、人の push の後の再レビュー（人が GitHub の画面で base ブランチを取り込んだ後を含む）は、新しいラウンドにするが、往復に数えない。base ブランチが進んで差分が変わるたびに起こすレビューは、往復の上限でなく、1 Issue の累計の費用の上限（`limits.issueCostUsd`）で止まる
- 数える元は GitHub の `fix` の印だけで、commit の親の形も手元の記録も使わない。1 つのラウンドを、`fix` の印と載せ直しのラウンドの 2 回に数える形は無い。衝突の直しで作業 AI が merge の commit の後に commit を足しても、`fix` の印 1 つで 1 回に数える（上の「push の手順」）
- 検査不合格・レビュー不合格・衝突ありで、往復の回数がすでに上限（`limits.roundTrips`）に達していれば、作業 AI を起こさずに停止中にする（`round-limit`。[IMPL-24][impl]、[FLOW-40][flow]）
- 往復の回数は PR の初めから数え、人が `## 再開 続きから` で戻しても数え直さない（1 Issue の累計の費用と同じ。[止まった状態から戻す手順][flow]）。`## 再開 計画から` か `下書きから` で戻したときは、前の PR の `fix` の印を数えない（上の「戻した後の読み方」）
- 運用の記録の「AI が直した回数」（[FLOW-13][flow] の往復の回数）は、この往復の回数と同じ数にし、2 つの数に分けない。検査の失敗の直しや衝突の直しの回数を分けて見たいときは、`fix` の印の `cause` で分ける（[ADR-20261022-003][adr-rounds] の決定 1、[ADR-20261024-001][adr-model-states] の決定 9）

| ラウンド | 起きたこと | 往復の回数 |
| --- | --- | --- |
| 1 | 最初のレビューが `fix` を返し、作業 AI が指摘を直す | 0 回 |
| 2 | 直した後に必須チェックが落ち、作業 AI がレビューの前に検査の失敗を直す。通った後の再レビューが `pass` を返す。base ブランチが進み、進行 Bot だけの載せ直しで差分が変わる | 2 回。指摘の直しと検査の失敗の直しを 1 回ずつ数える |
| 3 | 載せ直しの後の再レビューが `fix` を返す。作業 AI が直す前に、人が push する | 2 回。進行 Bot だけの載せ直しは数えない |
| 4 | 人の push の後の再レビューが `pass` を返す。base ブランチが進み、載せ直しが衝突して、作業 AI が衝突を解く | 2 回。人の push は数えない |
| 5 | 衝突の直しの後の再レビューが `fix` を返す | 3 回。衝突の直しを 1 回に数える。上限（3 回）に達しているので、直さずに停止中にする（`round-limit`） |

表の往復の回数は、そのラウンドのレビューの時点の `fix` の印の数。

### レビュー合格の判定

![レビュー合格の判定][fig-convergence]

PR がレビュー合格か（上の「主な流れの状態の決め方」の順 6〜9）を、次の順に確かめる（[IMPL-27][impl]、[FLOW-41][flow]）。必須チェックを先に見るので、レビュー合格の後に必須チェックが赤に変わったら、検査不合格と読む。

| 順 | 確かめること | 当てはまらないとき |
| --- | --- | --- |
| 1 | 必須チェック（`checks.required`）のすべてが、PR の head に対して `success` | 結果ごとの扱いは IMPL-27 の表のとおり。`failure` と `timed_out` は検査不合格（レビューせずに作業 AI が直す）、まだ無いか動いている途中なら待つ（変更済み）、`action_required` は停止中（`ci-action-required`）、`cancelled` などは待って `limits.ciStaleHours` を過ぎたら停止中（`ci-stale`）（[IMPL-27][impl]） |
| 2 | 最新の `review` の印の `head` が、PR の head と同じ | その head はまだレビューしていない（検査合格。レビューに進む） |
| 3 | 最新の `review` の印の `result` が `pass` | レビュー不合格（作業 AI が直す） |

- 必須チェックは、チェックの名前・チェックを出した app・base 側のワークフローのパスの 3 つがすべて一致するものだけを数え、同じ名前が複数あれば最新の 1 件を採る。一致するチェックが無ければ、まだ無いものとして待つ（[IMPL-27][impl]、[ADR-20261016-001][adr-pr]）
- 3 つとも満たせばレビュー合格（T11）。最初のレビューから `pass` なら、1 回でレビュー合格になる（[IMPL-27][impl]）

### マージの判定

![マージの判定][fig-merge]

レビュー合格の PR を、マージしてよいかで判定する（[MERGE-2、MERGE-3][merge]）。判定は、レビュー合格の間に、PR の head を `head` に持つ `merge` の印が無いときに行う（上の「状態ごとの工程」のレビュー合格の (4)）。判定の時点で CI が緑でないか、base ブランチが PR の head より先に進んでいれば、判定を次の実行に回し、印を書かない（`human` の判定にもしない。[MERGE-3][merge]）。
CI が緑なら、次の条件をすべて確かめ、満たさない条件の記号を `merge` の印の `reasons` に書く。

| 記号（`reasons`） | 満たさない条件 | 確かめ方 |
| --- | --- | --- |
| `not-bot-pr` | dev-autopilot が作った PR でない | PR に、進行 Bot の署名付きの `link` の印が無い（[MERGE-2][merge]、[IMPL-6][impl]） |
| `base` | 向き先が base ブランチでない（`release/*` ブランチと `main` 向けの PR を含む） | PR の向き先の名前を、マシンの設定の `baseBranch` と比べる（[MERGE-2、MERGE-4][merge]） |
| `not-converged` | レビュー合格でない | 上の「レビュー合格の判定」を、判定の時点でもう一度確かめる（[MERGE-2][merge]） |
| `leak` | 漏えいの検査に引っかかった | 判定の時点で、最終の head の diff 全体に検査を掛け直す（[IMPL-15][impl]）。見つかれば、作業の単位の安全の軸にも攻撃の疑い（AI の文。`security` の印の `where` が `leak`）を入れる（[ADR-20261027-002][adr-leak]） |
| `dropped-high` | 批評 AI が 🔴 を再現できなかったラウンドがある | 最新の `review` の印の `droppedHigh`（PR ごとの累計）が 1 以上。数え方は「[AI のセッション][design-ai]」の「批評 AI」の統合の規則（[IMPL-22][impl]） |
| `path` | 許可一覧（`merge.allowPaths`）に無いパスを触った | 進行 Bot の clone で取った `git diff --raw <base>...<head>` の一覧と比べる（[MERGE-2、MERGE-4][merge]） |
| `diff-kind` | 状態が追加（A）か変更（M）でないもの（削除・改名・コピー・種類の変更など）がある。または、mode が `100644` でない | 同じ `git diff --raw` の状態と mode を見る。状態は、許す 2 つ（A と M）で照らし、並べていない状態も通さない（[MERGE-2、MERGE-4][merge]） |
| `policy` | 方針に係るパス（`merge.policyPaths`）を触った | 同じ `git diff --raw` の一覧と比べる（[MERGE-2][merge]） |

- 当てはまった記号をすべて `,` でつないで `reasons` に書く。1 つも無ければ `result` を `ready`、1 つでもあれば `human` にする（[MERGE-3][merge]）
- `ready` の判定にするのは、1 回の実行で 1 件まで。2 件目以降の、`ready` の判定になるはずの PR は、判定を次の実行に回し、印を書かない。次の実行でも、1 件目が開いていてマージされていなければ、2 件目以降の `ready` の判定は書かない。`human` の判定は 1 件の上限に数えず、書く。1 件目が閉じられたら、待つのをやめる（[MERGE-5][merge]、[ADR-20261016-001][adr-pr] の決定 2）
- 変えてはいけないパスのうち、マージまで効かないもので人が認めたパス（上の「push の手順」）は、許可一覧に無いので、`path` で `human` の判定になる（[ADR-20261024-004][adr-master] の決定 9）

### 同じ指摘の再発の判定

![同じ指摘の再発の判定][fig-repeat]

AI の変更の後のラウンド（作業 AI が直すか衝突を解いた後のラウンド）で、前のラウンドと同じ指摘がもう一度出たかを、`review` の印の `findings` で見分ける（[ADR-20261019-001][adr-repeat]、[ADR-20261022-003][adr-rounds] の決定 3、[ADR-20261024-003][adr-check-first] の決定 4、[IMPL-24][impl]）。

- 進行 Bot は、`review` の印を書く前に、批評 AI の統合の後に残った 🔴 🟡 の指摘ごとに ID を計算し、`findings` に書く。ID は「軸」「正規化した見出し」「ファイルのパス」を改行でつないだ文字列の SHA-256 の先頭 8 文字（16 進）。正規化は、Unicode の NFKC にそろえ、先頭の重要度の記号と空白を除き、英字を小文字にする（[ADR-20261019-001][adr-repeat] の決定 1）
- AI の変更の後のラウンドの `findings` の ID が、前のどれかのラウンド（判定しないラウンドを含む）の `findings` にもあれば、同じ指摘の再発とする。間が空いていても数える。同じラウンドの中の重複は数えない（[ADR-20261019-001][adr-repeat] の決定 2）
- AI の変更の後のラウンドは、1 つ前のラウンドに有効な `fix` の印があり、ラウンドの `review` の印の `head` が、次のどちらかに当たるラウンド。1 つのラウンドに `fix` の印が 2 つ以上あるときは、最新の 1 つで見る（[ADR-20261024-003][adr-check-first] の決定 4）
  - 1 つ前のラウンドの最新の有効な `fix` の印の `head` と同じ
  - その `head` を 1 つ目の親に、base ブランチの commit を 2 つ目の親に持つ merge の commit。merge の commit の作者は問わず、人が base ブランチを取り込んだ merge の commit も、形が同じなら判定する。base ブランチを取り込んだだけの merge の commit では、レビューする変更が作業 AI の変更のままのため
- 次のラウンドでは判定しない
  - PR の最初のラウンド。最初のレビューの前の検査の失敗の直し（`round` が 0 の `fix` の印）があっても、比べる相手の `findings` が無いので判定しない
  - 進行 Bot だけの載せ直しで差分が変わったラウンド（1 つ前のラウンドに `fix` の印が無い）
  - 人の push の後のラウンド（head が上の 2 つの形に当たらない）。人が直した後では、同じ指摘の再発でも止めない（[IMPL-24][impl]）
- 判定しないラウンドの `review` の印にも、`findings` を書く。後のラウンドの比べる相手になるため
- head の形の見分けは、同じ指摘の再発を判定するかにだけ使い、往復の回数（上の「ラウンドと往復の数え方」）には使わない。形を見誤っても、往復の上限は `fix` の印で効く
- 同じ指摘の再発なら、往復の上限と同じく、作業 AI を起こさずに停止中にし（`repeated-finding`）、再び出た指摘の見出しと、出たラウンドを、止めた理由のコメントに書く（[IMPL-24][impl]、[FLOW-40][flow]）

| ラウンド | `findings`（例） | 判定 |
| --- | --- | --- |
| 1 | A、B | 前のラウンドが無い。直しに進む |
| 2 | C | A も B も出ていない。直しに進む |
| 3 | A | A はラウンド 1 にも出ている。同じ指摘の再発として停止中にする |

表の例は、ラウンド 2 と 3 がどちらも AI の変更の後のラウンドのとき。ラウンド 3 が進行 Bot だけの載せ直しか人の push の後のラウンドなら、判定しない（ラウンド 3 の `findings` は、後のラウンドの比べる相手になる）。

## 印の種類

印は、HTML のコメントの中に JSON を 1 行で書く 21 種類（[ADR-20261024-001][adr-model-states] の決定 9）。印の形と欄の正本は[印と固定の見出しの一覧][markers]で、基本設計は、署名の作り方と、どのときにどの印を書くかと、止めた理由の記号の一覧を決める。進行 Bot が投稿するコメントは、すべて署名付きの印を 1 つ持つ（[印と固定の見出しの一覧][markers]）。

### 印の署名

印の `sig`（[IMPL-20][impl] の (c)）は、HMAC-SHA256 で作る。署名を確かめる鍵は一覧で持ち、進行中の Issue と着手の前の Issue があっても替えられる（[ADR-20261021-004][adr-marker-keys]）。

- 鍵の一覧：秘密の置き場の `marker-signing-keys`（1 行に 1 つ、32 バイトの乱数を base64 で書いたもの。[設定][design-settings]の「秘密の置き場のファイル」）。人が作り（初めて導入するときは、`setup` が作り方のコマンドを示す。例：`openssl rand -base64 32`）、進行 Bot だけが読む。AI のセッションには渡さない。HMAC は書く鍵と確かめる鍵が同じで、確かめにだけ使う鍵でも印を作れるので、どの行の鍵も同じに秘密として扱う。動かすマシンを替えるときは、作り直さずに前のマシンから一覧を写す
- 書く鍵と確かめる鍵：印を書くときは、一覧の先頭の行の鍵で署名する。印を確かめるときは、一覧の鍵を先頭の行から順に試し、どれかで通れば、署名の条件を満たすとする。一覧に無い鍵で書いた印は、署名の条件を満たさない。印に、どの鍵で書いたかを示す欄は持たない（署名の対象は変えない。[ADR-20261015-004][adr-markers] の決定 1）
- 鍵の読み方：行ごとに末尾の空白と改行を除き、空の行は読まない。各行の base64 を解いた 32 バイトを HMAC の鍵にする。解けない行か、解いた値が 32 バイトでない行が 1 つでもあれば、点検を fail にする。鍵の行が 1 つも無いとき（空のファイル）も、点検を fail にする。人がエディタで保存し直して改行が変わっても鍵が変わらず、短い文字列の弱い鍵で署名しないため
- 署名する文字列：印の `sig` を除いた欄に、印の置き場（リポ（`owner/repo`）と、Issue か PR の番号）を加えた JSON を、決まった並べ方にそろえたもの。並べ方は詳細設計で決める（[ADR-20261024-001][adr-model-states] の決定 9）。置き場は印の欄として書かず、署名にだけ入れる。別の Issue や PR に写した印は、署名が通らない（[ADR-20261015-004][adr-markers] の決定 1）
- `sig` の値：HMAC-SHA256 の結果の 16 進の 64 文字
- 点検は、投稿に使うアカウントが書いた最新の未編集の印の署名を一覧の鍵で確かめ、どの鍵でも通らなければ warn にする。マシンを替えたときの鍵の取り違えを、人に知らせるため。fail にしないのは、下の「鍵を替えるとき」の、鍵が漏れたときの順 3 の実行で、外した鍵の印のある Issue と PR を止めるため。一覧に 2 つ以上の鍵があるときは、先頭でない鍵でだけ確かめられた印が残る開いた Issue と PR を warn に出す（[設定][design-settings]の「`check` が設定について確かめること」、「[導入と点検][design-setup]」の「組と回数」）

#### 鍵を替えるとき

鍵は、進行中の Issue の有無を問わず、いつでも替えてよい（[ADR-20261021-004][adr-marker-keys] の決定 2）。鍵が漏れていないときは、次の順に替える。

| 順 | する人 | すること |
| --- | --- | --- |
| 1 | 人 | 新しい鍵を作り、一覧の先頭の行に足す。前の鍵は、2 行目より後に残す |
| 2 | 進行 Bot | 次の実行から、新しい鍵で書き、一覧のどれかの鍵で確かめる（進行 Bot は、起動したときに秘密を読む。[ADR-20261015-001][adr-read] の決定 2） |
| 3 | 進行 Bot | 点検の warn に、先頭でない鍵でだけ確かめられた印が残る開いた Issue と PR の番号を出す。残りが無くなったら、前の鍵を外してよいことを warn に出す（出し方は「[導入と点検][design-setup]」の「組と回数」） |
| 4 | 人 | 前の鍵でだけ確かめられる印が残る開いた Issue と PR が無くなったら、前の鍵を一覧から外す。外し忘れて、印を作れる鍵が多いまま残らないため |

- 動かすマシンを替えて、新しいマシンで鍵を作るときも、鍵を替えたものとして同じ順に従う（前の鍵を一覧に残す。「[導入と点検][design-setup]」の「動かすマシンを替えるとき」）
- 人が決める番の作業の単位が長く開いていて急ぐときは、残りがあっても前の鍵を外してよい。前の鍵の印のある開いた Issue と PR は `marker-invalid` で止まる（`link` の印が前の鍵の PR も、上の「先に見る」の順 11 の `unlinked-pr` でなく、順 5 で止まる）。人が中身を確かめて `## 再開` で戻すと、挙げた印は無いものとして読まれ、読んだ結果の状態から続ける（例：マスターの下書きの印が無いものになれば、検疫済みに戻って受付 AI が書き直す。[FLOW-40][flow]、上の「数えない無効な印」）

鍵が漏れたとき（漏れたかもしれないときを含む）は、漏れた鍵を確かめにも使わない。人が次の順に行う（[ADR-20261021-004][adr-marker-keys] の決定 3）。

| 順 | すること |
| --- | --- |
| 1 | 全体の止める合図（[ADR-20261017-007][adr-stop]）を `stop` にする。鍵の一覧はマシンの中にあり、替え終わるまでに時間がかかりうるので、替え終わるまでの間に、漏れた鍵で作られた印を読まないため |
| 2 | 新しい鍵を作って一覧の先頭の行に足し、ほかの鍵をすべて一覧から外す（新しい鍵だけを残す）。鍵の一覧は 1 つのファイルにあるので、漏れた鍵のほかの鍵も、漏れたかもしれない鍵として扱う（[ADR-20261021-004][adr-marker-keys] の決定 3 の「漏れたかもしれないとき」）。漏れた鍵は、確かめにも残さない（漏れた鍵を持つ人は、確かめの通る印を作れるため）。開いた Issue と PR の進行 Bot の印がすべて無効になり、人が再開した後は数えない印になるので、どの作業の単位も、印を無いものとして読んだ状態からやり直せる |
| 3 | 全体の止める合図を `run` に戻す。外した鍵で署名した印が残る開いた Issue と PR は、次の実行で `marker-invalid` で止まる（上の「先に見る」の順 5。`link` の印が外した鍵の PR も、順 11 の `unlinked-pr` でなく、順 5 で止まる） |
| 4 | 止まった作業の単位ごとに、印のあるコメントと GitHub の状態（PR の差分、作業ブランチ）を確かめ、`## 再開` で戻す。漏れた鍵の印は誰が作ったかが分からないので、PR を作り直すなら `## 再開 計画から`、依頼から決め直すなら `## 再開 下書きから` で戻す（「[止まった状態から戻す手順][flow]」の `marker-invalid`） |

- 秘密の置き場のほかの秘密（アプリの秘密鍵、deploy key）を替えるかは、漏れた経路を見て人が決める

### 印が付く順

![印が付く順][fig-markers]

主な流れの順で、Issue と PR のコメントに付く印。

| 順 | 印 | 置き場 | 書くとき |
| --- | --- | --- | --- |
| 1 | `quarantine`（`target` が `issue`） | Issue | 入口の検疫を通ったとき（起票済み。T29） |
| 2 | `draft`（`source` が `ai`） | Issue | マスターの下書きを投稿するとき（検疫済みと差し戻し済み。T2・T3） |
| 3 | `quarantine`（`target` が `instruction`）と `draft`（`source` が `instruction`） | Issue | 人の直しが検疫を通り、全文をマスターに写すとき（直し済み。T30） |
| 4 | `decision` | Issue | 有効な `agent-ready` を見つけ、依存とマイルストーンを付けた後（決定済み。T6） |
| 5 | `plan` | Issue | 確かめを通った計画を投稿するとき（T7） |
| 6 | `link` | Issue と PR | PR を作った直後に、両方に書く（T8。[IMPL-6][impl]） |
| 7 | `fix`（`cause` が `check`） | PR | 検査の失敗の直しを push する前（検査不合格。T13。最初のレビューの前は `round` が 0） |
| 8 | `review` | PR | ラウンドごとに、確かめの結果を投稿するとき（検査合格。T11・T12） |
| 9 | `fix`（`cause` が `review`） | PR | 指摘の直しを push する前（レビュー不合格。T14） |
| 10 | `follow-up` | 🟢 を記録した Issue（新しい Issue か、同じ見出しの開いた Issue） | レビュー合格に入るときに、🟢 を新しい Issue にするか、同じ見出しの開いた Issue に足すとき（T11。[IMPL-26][impl]） |
| 11 | `conflict`、`fix`（`cause` が `conflict`） | PR | 載せ直しが衝突したとき（T19）と、衝突の直しを push する前（T20） |
| 12 | `merge` | PR | レビュー合格の間に、マージの判定をするとき（上の「マージの判定」） |
| 13 | `remind` | PR | `ready` の判定のまま、マージも `## 判定と違う判断` も無く `limits.remindDays` 日を過ぎたとき（[MERGE-3][merge]） |
| 14 | `cleanup` | Issue | 片付けの最後（マージ済みと閉鎖済み。T27・T28） |

順 7 の `fix` は、必須チェックが落ちたときだけ付く。順 11 は、base ブランチが進んで載せ直しが衝突したときだけ付く。

### ほかの印

主な流れの順のほかに、場面に応じて書く印。

| 印 | 書くとき | 置き場 | 1 回だけ書く判定 |
| --- | --- | --- | --- |
| `wait` | 先の依頼で待つとき（D1。[FLOW-10][flow]、[FLOW-43][flow]） | Issue | 同じ `blockedBy` の有効な印があれば書かない |
| `overlap` | 作業 AI の commit を取り込んだとき（上の「push の手順」の順 2）に、変更ファイルの一覧が、ほかの進行中の PR の変更ファイルと重なったとき（[FLOW-8][flow]） | Issue | 同じ `prs` の有効な印があれば書かない |
| `stop` | 停止中にするとき（S5。下の「止めた理由の記号」） | Issue（PR が契機なら PR にも） | 1 回だけにしない。止めるたびに、止めた先ごとに書く |
| `dependency-review` | 先の依頼が中止になり、計画を見直したとき（D4・D5。[FLOW-43][flow]） | Issue | 同じ `dependency` の有効な印があれば書かない（先の Issue ごとに 1 回） |
| `security` | 検疫か漏えいの検査で攻撃の疑いを見つけたとき（Q1・Q2。[SAFE-19][safety]） | Issue（PR が契機なら PR にも） | 1 回だけにしない。見つけるたびに書く |
| `halt` | AI が書いた文で攻撃の疑いを見つけ、全体を止めるとき（上の「全体の停止の Issue」） | 全体の停止の Issue | 1 回だけにしない。見つけた作業の単位ごとに書く |
| `approval-reset` | 無効な `agent-ready` を外したとき（[FLOW-36][flow]） | Issue | 1 回だけにしない。外すたびに書く |
| `ignored-instruction` | 決めた後の `## 作業指示` を読まなかったとき（[TEXT-4][text]） | Issue | 同じ `comment` の有効な印があれば書かない |
| `manual-push` | push で効くものの差分を人に渡すとき（上の「push の手順」の順 3。[IMPL-15][impl]） | Issue | 同じ `head` の有効な印があれば書かない |

- `stop` を 1 回だけにしないのは、人が再開した後に同じ理由で再び止まったとき、前の印を見て書かないと、今回止まったことが人に伝わらないため。止めている間は、進行 Bot は止める契機を確かめない（上の「先に見る」の順 3）ので、同じ理由で重ねて書くことは無い
- `security` も同じく、値がある間は AI に文を渡さず、検疫を掛け直さないので、重ねて書くことは無い。人が `## 安全の確認` で外した後に、また見つかったら書く
- 組み直す前の `note kind=duplicate`（🟢 の重複の Issue に PR の番号を足した）は、`follow-up` にした（[IMPL-26][impl]、[ADR-20261031-001][adr-follow-up-dup]）。`note kind=raise`（作業 AI のモデルを上げた）は、`fix` の印の `model` の欄と、上げた修正の `fix` の印のコメントの決まった文にした（[IMPL-25][impl]、[ADR-20261101-001][adr-raise-in-fix]）。どちらも `stop` と `link` に寄せていない。`stop` に寄せると止まったと読まれ、`link` に寄せると PR と Issue の結びつきを誤るため

### 止めた理由の記号

停止中にするとき（S5）に書く `stop` の印の `reason` の一覧。組み直した形で止まる場面から決めた 14 個（[FLOW-40][flow]、[ADR-20261024-001][adr-model-states] の決定 7）と、実装の都合の記号に分ける。止めた理由のコメントには、止まった理由と、人がすること（[止まった状態から戻す手順][flow]）を書く。

| `reason` | 止めた契機 |
| --- | --- |
| `retry-limit` | 同じ作業の単位で実行の失敗が続き、回数の上限（`limits.retry.count`）に達した（[IMPL-14][impl]） |
| `round-limit` | 往復の回数が上限に達した。検査不合格・レビュー不合格・衝突ありの作業 AI を起こす前に確かめる（[IMPL-24][impl]、[ADR-20261022-003][adr-rounds]）。止めた理由のコメントに、往復の回数は PR の初めから数え、`## 再開 続きから` でも数え直さないことを書く |
| `repeated-finding` | 同じ指摘の再発（上の「同じ指摘の再発の判定」）。止めた理由のコメントに、再び出た指摘の見出しと出たラウンドを書く |
| `plan-limit` | 上限まで計画し直しても、直す点が残った（上の「計画の工程の中の順番」。[IMPL-10][impl]）。止めた理由のコメントに、最後の確かめの指摘を書く（検疫と漏えいの検査を通す） |
| `cost-limit` | 1 Issue の累計の費用に、次のセッションの費用の上限を足すと、上限（`limits.issueCostUsd`）を超える（[IMPL-14][impl]、「[AI のセッション][design-ai]」の「止め方と利用枠の数え方」）。止めた理由のコメントに、累計は Issue の初めから数え、再開しても数え直さないことを書く |
| `pr-closed` | 結びつく PR が、マージされずに閉じられた（[IMPL-6][impl]）。止めた理由のコメントに、選べる戻す先と、戻した後に進行 Bot が消すフォルダ（閉じた PR の番号の名前のセッションのフォルダ）を書く（下の「作業場所の残骸」） |
| `cleanup-failed` | 片付けが `limits.retry.count` 回続けて失敗した（[FLOW-42][flow]）。止めた理由のコメントに、消せなかったものを書く |
| `plan-change` | 先の依頼が中止になり、計画を確かめる AI が、計画を変える必要があると判断した（D5。[FLOW-43][flow]）。止めた理由のコメントに、AI の判断と理由を書く |
| `unauthorized-close` | push 未満の人が Issue を閉じた（[FLOW-42][flow]） |
| `protected-path` | 計画が変える見込みのパスか、push の前の差分が、認めていない変えてはいけないパスに当たった（[IMPL-10][impl]、[IMPL-15][impl]）。push の前の差分の `.claude/**` と `.mcp.json` は、認めていても当たる（[ADR-20261027-003][adr-claude-dir]）。止めた理由のコメントに、当たったパスと、認め方（`## 仕組みの変更の承認`）を書く |
| `manual-push` | push で効くものの差分を、人に渡した（`manual-push` の印。[IMPL-15][impl]）。止めた理由のコメントに、人が作業ブランチに push してから `## 再開 続きから` を書くこと、PR が無ければ進行 Bot が作ること、差分を載せられなかったときは `## 再開 計画から` か `## 再開 下書きから` で戻すことを書く（上の「push の手順」の表の下） |
| `manual-change` | 計画が変える見込みのパスに、`## 仕組みの変更の承認` で認めた `.claude/**` か `.mcp.json` がある（作業 AI には変えさせない。Claude Code 自身も書かせない。FACT-77、[IMPL-15][impl]、[ADR-20261027-003][adr-claude-dir]）。止めた理由のコメントに、人が変えるパスと、人が作業ブランチ（`<型>/issue-<番号>`。base ブランチから作る）にそのパスの変更を push してから `## 再開 続きから` を書くことを書く。人が push した後は、作業ブランチの先端から作業 AI が計画の残りの変更を作る（上の「状態ごとの工程」の計画済み） |
| `marker-invalid` | 進行 Bot の印の署名が合わないか、印が編集された（[IMPL-20][impl]）。`review` の印の `round` が欠けている（[IMPL-18][impl]）。数える `decision` の印の `textHash` が、最新のマスターの文のハッシュと違う（[TEXT-4][text]）。`stop` の印の `comments` に、書く先の書き換えられた印のコメントの ID を挙げる（`round` の欠けだけのときと、挙げるコメントが無いときは持たない）。人が再開した後は、挙げた印を数えない（上の「数えない無効な印」、[ADR-20261021-004][adr-marker-keys] の決定 4） |
| `ci-action-required` | CI のワークフローの実行に、人の承認が要る（[IMPL-27][impl]） |
| `ci-stale` | CI の結果が、取り消しなどのまま `limits.ciStaleHours` を過ぎても変わらない（[IMPL-27][impl]） |

実装の都合の記号は、組み直す前の名前をそのまま使う（名前を変えるなら、詳細設計で決める）。

| `reason` | 止めた契機 |
| --- | --- |
| `review-too-long` | レビューのコメントが、🟢 の失敗シナリオと推奨をすべて省いても 60,000 文字を超える（[IMPL-17][impl]、「[AI のセッション][design-ai]」の「レビューのコメントの形」） |
| `adr-required` | 作業 AI が、ADR の起票か、人が認めていない規約の正典の変更が要ると返した（[IMPL-8][impl]） |
| `session-not-stopped` | AI のセッションを止めた後、コマンドの残りが止まったと確かめられない（[IMPL-14][impl]）。または、片付けか順 9 で作業場所を消す前に、残りのプロセスが見つかったか、探し切れなかった（[ADR-20261027-001][adr-leftover]）。止めた理由のコメントに、見つかったプロセスの PID とコマンドの名前と、消すフォルダの組と消す順を書く。人は、プロセスを止めてから `## 再開 続きから` を書く |
| `brief-sensitive` | 渡す文（人が決めたマスター）に、事業データか認証情報の形が混じっている（[TEXT-7][text]） |
| `not-fast-forward` | push する SHA が、GitHub の作業ブランチの今の先端（まだ無ければ、作業場所を作ったときに控えた base の SHA）の子孫でない（[IMPL-15][impl]、[SAFE-13][safety]、上の「push の手順」） |
| `no-new-commit` | 作業 AI が作業を終えた（`done`）と返したのに、新しい commit が無い（変更の作成・直し・衝突の直し。上の「push の手順」の順 2） |
| `issue-changed` | Issue が別のリポに移された（[TEXT-8][text]）。結びつく PR に書く（上の「先に見る」の順 8） |
| `unlinked-pr` | ブランチ名が一致するのに、`link` の印が無い PR がある。PR を作った直後、`link` の印を書く前に切れたときも当たる（作者を問わない。[IMPL-6][impl]、[ADR-20261016-001][adr-pr] の決定 3）。無効な `link` の印を持つ PR は、`marker-invalid` で止める。人は PR の中身を確かめてから、`## 再開 計画から` で戻す（前の PR は、進行 Bot が閉じる） |

| `local-settings` | AI のセッションの作業場所の worktree に、`.claude/settings.local.json` か、どのフォルダかに `CLAUDE.local.md` がある（FACT-56、FACT-60、[SAFE-2][safety] の (a)、「[AI のセッション][design-ai]」の「起動の前の確かめ」）。作業フォルダの上のフォルダの `CLAUDE.local.md` は、作業の単位に書かずに実行を終える |
| `draft-format` | 人の直し（`## 作業指示`）の見出しの下が空で、マスターに写せない（上の「状態ごとの工程」の直し済み）。または、決定の印を書くときに、マスターの依存とマイルストーンの候補の行を、決まった形で読めない |
| `settings-tampered` | セッションの安全設定のファイルが、作ったときのハッシュと違う（起動の直前か、セッションの後。[SAFE-2][safety] の (e)、「[AI のセッション][design-ai]」の「セッションごとの安全設定」） |
| `records-missing` | 着手した作業の単位の手元の記録が無い（[運用の規則][flow]。見分け方は「[AI のセッション][design-ai]」の「起動の前の確かめ」） |
| `unrecoverable` | 状態を決められない（読んだ事実の組み合わせが、どの表のどの行にも当たらない。上の「状態の組み立て」、[SAFE-4][safety]）。または、push した後に読み戻した作業ブランチの先端が違う |

## 作業場所の残骸

UNDECIDED-27（作業場所の残骸の決め方）を決める。セッションのフォルダ（`<置き場>/sessions/<セッションの名前>/`）は、同じ名前で作り直すか片付けるまで残るので、終わっていない作業の単位のフォルダがあるのは普通の状態（[ADR-20261013-001][adr-workspace]）。
セッションの名前は、役と、Issue か PR の番号を略さずに書く（例：`work-issue-<番号>`、`review-pr-<番号>-round-<ラウンド>-<軸>`。役ごとの名前の一覧は「[AI のセッション][design-ai]」の「セッションの名前」）。進行 Bot は、名前から役と番号を読み、次の表で見分ける。表の「作業の単位」は、名前から引いた作業の単位（PR の名前のフォルダは、PR の `link` の印から引いた Issue の作業の単位）。

![作業場所の残骸の見分け方][fig-residue]

| フォルダ | 扱い | 扱う所 |
| --- | --- | --- |
| 作業の単位が終了の枠の前（完了・中止・マージ済み・閉鎖済みのどれでもない）で、Issue の名前のフォルダか、結びつく PR の名前のフォルダ | 普通の状態。作り直すか片付けるまで残す。止め方か安全の軸に値がある間（停止中の `pr-closed` と `unauthorized-close` を含む）も残す。人が戻した後に同じ状態から続けるか、人が Issue を閉じた後の片付けで消すため（[ADR-20261013-001][adr-workspace]） | — |
| 作業の単位がマージ済みか閉鎖済み | 片付け（T27・T28）で消す。片付けは、名前から作業の単位を引けるフォルダ（R より前に作った PR の番号のものを含む）をすべて消す。途中で切れて残ったものも、`cleanup` の印がまだ無いので、次の実行の片付けで消す（[FLOW-42][flow]、[MERGE-7][merge]） | 次の工程（上の「先に見る」の順 2） |
| 名前の PR が、戻す先が計画からか下書きからの R より前に作った PR | 片付けと同じに消す。人が R を書いたことを、消してよい印として扱う（`pr-closed` の止めた理由のコメントに、戻した後に消すフォルダを書いてある）。人が専用のマシンに入ってフォルダを消さずに済むため | 次の工程（順 9） |
| 名前の番号の Issue が別のリポに移された（REST で引いた Issue の `repository_url` が当てる先のリポでないか、GraphQL で `NOT_FOUND`。上の「状態の組み立て」。FACT-66） | 消さずに、結びつく PR を停止中にする（`issue-changed`）。止めた理由のコメントに、消すフォルダの組と消す順を書く。開いた結びつく PR が無ければ、下の「引けない」の行と同じ | 次の工程（順 8） |
| 作業の単位が終了の枠の前で、上の行のどれにも当たらない（名前の PR が、結びつく PR でも、R より前に作った PR でもないなど） | 作業の単位に紐づく残骸。消さずに、作業の単位を停止中にする（`workspace-residue`） | 次の工程（順 12） |
| 名前から引けた Issue が、当てる先のリポの Issue で、設定した Project に無い（人が Project から外した） | 消さずに、引けた Issue に `stop` の印（`workspace-residue`）を書く。止めた理由のコメントに、Issue を Project に戻すか、フォルダの組を消すかを書く。Project に無いので、表示の欄は書かない（[SETUP-1][setup]） | 点検 |
| 作業の単位が完了か中止（`cleanup` の印がある） | 片付けの後に残った残骸。片付けはフォルダを消してから `cleanup` の印を書くので、片付けの後に作られたか、止められなかったセッションのもの。消さずに点検を fail にし、実行は作業に入らずに止まる。人が中身を確かめて消す（[SAFE-4][safety]） | 点検 |
| 短い一時フォルダの根（`sessionTmp.root`）の下にあり、ID が、どのセッションのフォルダの ID のファイル（`short-tmp-id.txt`）にも無い（記録を失っても、ID のファイルで組を引く） | 作業の単位に紐づかない残骸。点検を fail にし、実行は作業に入らずに止まる。人が中身を確かめて消す（[ADR-20261017-006][adr-tmp]、「[AI のセッション][design-ai]」の「短い一時フォルダ」） | 点検 |
| 名前から Issue か PR を引けない | 作業の単位に紐づかない残骸。点検を fail にし、実行は作業に入らずに止まる。人が中身を確かめて消す（[運用の規則][flow]、[SETUP-2][setup]、[SAFE-4][safety]） | 点検 |

- 扱う所が「点検」の行は、点検（上の「1 回の実行の流れ」の順 5）の残骸の見分けで扱う。Project に無い Issue と、完了か中止の作業の単位は、次の工程に進まない（Project の外の Issue は作業の単位にならず、完了と中止は「先に見る」の順 1 で何もしない）ため。扱う所が「次の工程」の行は、点検では何もせず、作業の単位ごとに次の工程で扱う
- 片付けと順 9 で消す前に、`commondir` と `gitdir` が、作ったときの値（作業場所のパスから決まる値）と同じかを確かめる。違えば消さずに、作業の単位を停止中にし（`workspace-tampered`）、点検で warn に出す（[ADR-20261013-001][adr-workspace]、[SAFE-12][safety]）
- 片付けと順 9 で消す前に、残りのプロセスも探す（作業フォルダがフォルダの中にあるか、フォルダの中のファイルを開いているプロセス。`lsof` と `lsof +D`）。見つかるか探し切れなければ、消さずに、作業の単位を停止中にする（`session-not-stopped`。[ADR-20261027-001][adr-leftover]）
- 消さずに止めるとき（`issue-changed`・`workspace-residue`・`workspace-tampered`、片付けか順 9 で残りのプロセスが見つかって `session-not-stopped` にしたとき、片付けがフォルダを消せずに `cleanup-failed` にしたとき）は、止めた理由のコメントと点検の結果に、消すフォルダの組（セッションの名前と、セッションのフォルダの ID のファイルにある短い一時フォルダの ID。絶対パスは GitHub に書かない）と、消す順（短い一時フォルダ、セッションのフォルダの順。「[AI のセッション][design-ai]」の「短い一時フォルダ」の順 5 と同じ）を書く。人がセッションのフォルダだけを消すと、組の短い一時フォルダが、どのセッションのフォルダの ID のファイルにも無い残骸になり、点検が fail になって全体が止まるため。人は、挙がった組を書いた順に消してから、`## 再開 続きから` を書く
- Project に無い Issue の `stop` の印は、R より新しい `stop` の印が Issue に無いときだけ書く（止め方の停止中と同じ読み方）。人が消すまでの毎回の実行で、同じコメントが増えないため。人が Issue を Project に戻すと停止中として読まれ、人が R を書くと、フォルダは普通の状態に戻る

進行 Bot が、名前から引けない残骸を消さないのは、何のフォルダか分からないものを消すと、人が調べる材料を失うため。作業に入らないのは、判定できない状態で作業を増やさないため（[SAFE-4][safety]）。

## 手元の記録

![手元の記録][fig-records]

進行 Bot は、記録の置き場（`paths.records`。[設定][design-settings]の「マシンの中のフォルダ」）に、実行と AI のセッションの記録を残す（[FLOW-5][flow]）。記録は、判定に使わず、上限の数え上げ（実行の失敗と片付けの失敗が続いた回数、受付 AI の拒否、累計と 1 日の利用枠）と、運用の記録の数え上げ（下の「運用の記録の数え方」）と、人が読むためにだけ使う（[ADR-20261015-006][adr-flow] の決定 4）。判定に手元の記録を使う例外は持たない（[ADR-20261024-002][adr-no-stages] の決定 5）。AI は sandbox の中から読めず、書けない。

### 置くもの

| ファイル | 1 件 | 欄 |
| --- | --- | --- |
| `runs.jsonl` | 1 回の実行（lock で見送った実行も） | 実行 ID、起こされ方（定期・手動・点検の依頼・受け入れの依頼）、起動と終わりの時刻、終わり方（作業した・点検だけ・受け入れの依頼だけ・合図で止めた・設定を読めずに止めた・点検の fail で止めた・GitHub を読めずに止めた・lock で見送った。設定を読めずに止めたのは順 4、GitHub を読めずに止めたのは順 7）、リポの設定を読んだ base ブランチの SHA、点検の fail と warn、基線の結果（緑でない必須チェックの名前）、起動しなかった定期の実行の時刻、待つ時間を過ぎて消した依頼と、ほかの依頼と重なって見送った受け入れの依頼（種類と依頼の ID）、受け入れの依頼の実行の結果（Issue の番号と、受付 AI を起こしたか、起こさなかった理由。[ADR-20261022-004][adr-intake-req]）、前の実行が残したセッションの片付け（止めたセッションと、探して止めなかったプロセスの PID・コマンドの名前・フォルダ）、作業の単位ごとの結果（進めた工程、待たせた理由か止めた理由（`stop` の印の理由の記号）、外れた着手の条件（上の「状態ごとの工程」の決定済み）、マージの判定と理由の記号、検疫で見つかった種類（URL は、GitHub の添付の URL（FACT-69）かを分けて））、使った時間 |

| `outputs/<実行 ID>/<セッションの名前>.json` | AI のセッションの出力契約 1 つ | 取り出した出力契約をそのまま残す。受付 AI の下書き、直す前の計画と、計画の確かめの結果と指摘（[ADR-20261024-002][adr-no-stages] の決定 3）、計画 AI の自己申告、レビュー AI（4 つの軸）と批評 AI の結果も、ここから読む |
| `streams/<実行 ID>/<セッションの名前>.jsonl` | AI のセッション 1 回の `stream-json` | 受け取った行をそのまま残す。人のホームに会話の記録を残さないので、会話の流れを読むときはここを読む（「[AI のセッション][design-ai]」の「起動の形」の `--no-session-persistence`） |
| `writes/<実行 ID>.jsonl` | GitHub に書いた 1 件 | 書く先（Issue か PR の番号）、種類（コメント・ラベル・Project の欄・PR・push）、本文か値、実際に書いたか |

- `.jsonl` のファイルは 1 行に 1 件の JSON（JSON Lines）で、後ろに足すだけにし、書き直さない。書くたびに、ファイルを閉じる前にディスクへ書き出す（電源が切れても、前の行を失わないため）。`outputs/` の `.json` は 1 つの出力契約を 1 つのファイルに書き、書き直さない
- `.jsonl` の最後の行が途中で切れていたら（書いている途中で電源が切れた）、切れた行を読まずに点検で warn に出す。途中の行が読めなければ点検を fail にする。数え上げが少なく出て、上限が効かなくなる側に倒さないため（[運用の規則][flow]）

| --- | --- | --- |
| `run.lock` | 実行の lock。JSON で、PID・起動の時刻（lock を取ったプロセスの起動の時刻。時刻帯に依らないエポック秒）・ホスト名（人が読むためだけに書き、奪うかの判定に使わない）。古い lock かの見分け方と取り方は、上の「1 回の実行の流れ」の順 2 と、表の下の「lock の取り方」 | 進行 Bot と、`setup`（プログラムの写しを作り直すときと、引数 `uninstall` のとき。「[導入と点検][design-setup]」の「プログラムの写し」と「動かすマシンを替えるとき」）だけ（人が呼ぶ intake の Skill は lock を取らない。[ADR-20261022-004][adr-intake-req] の決定 5）。lock を外すときに消す。古い lock を奪うときに退けたファイル（`run.lock.stale-<PID>`）は、奪ったプロセスが新しい lock を作った後に消す |
| `records-created.json` | 記録の目印のファイル。JSON で、作った時刻と `setup` の版 | `setup`。消さない（無ければ点検が fail にする。[運用の規則][flow]） |
| `check-request.json` | 点検の依頼。JSON で、依頼の ID、置いた時刻、待つ時間（人の `check` が読んだ `run.checkWaitMinutes` の値。進行 Bot は、リポの設定を読む前の「1 回の実行の流れ」の順 2 で、待つ時間を過ぎた依頼かを見分ける） | 人の `check` が置き、進行 Bot が結果を書いた後に消す |
| `check-result-<依頼の ID>.json` | 点検の結果。JSON で、項目ごとの fail・warn・pass | 進行 Bot。人の `check` が表示した後に消す。残ったものは、7 日を過ぎたら進行 Bot が消す |
| `run-request.json` | 手動の 1 回実行の依頼。JSON で、依頼の ID と時刻 | 人の `/dev-autopilot` が置き、進行 Bot が lock を取った後に読んで消す |
| `intake-request.json` | 受け入れの依頼。JSON で、Issue の番号、依頼の ID、置いた時刻、待つ時間（人が呼ぶ intake の Skill が読んだ `run.intakeWaitMinutes` の値） | 人が `/verify-issue` などから呼ぶ intake の Skill が置き（待つ時間の内の依頼があれば置かない）、進行 Bot が結果を書いた後に消す（読んだ依頼と ID が同じときだけ）。待つ時間を過ぎた依頼は、進行 Bot が受付 AI を起こさずに消す（「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」） |
| `intake-result-<依頼の ID>.json` | 受け入れの依頼の結果。JSON で、検疫と漏えいの検査を通った受付 AI の文の欄（マスターの下書きの欄と `policyReason`。`planReason` は持たない。[ADR-20261024-004][adr-master] の決定 8）と受付 AI のセッションの費用か、受付 AI を起こさなかった理由（検疫か漏えいの検査で見つかった種類と場所、止められなかったプロセスの PID とフォルダを含む） | 進行 Bot。intake の Skill が示した後に消す。残ったものは、7 日を過ぎたら進行 Bot が消す |
| `status.json` | 状態の表示（「[導入と点検][design-setup]」の「状態の表示」） | 進行 Bot が実行の終わりに書き直す |
| `launchd.out.log`、`launchd.err.log` | 定期の実行の出力（macOS） | launchd。大きくなりすぎたら人が消す |

- 動かすマシンを替えるときは、`run.lock` と依頼のファイル（`run-request.json`・`check-request.json`・`check-result-<依頼の ID>.json`・`intake-request.json`・`intake-result-<依頼の ID>.json`）を新しいマシンへ写さない（「[導入と点検][design-setup]」の「動かすマシンを替えるとき」の順 2）。前のマシンの lock と依頼を、新しいマシンの実行が読まないため
- 実行 ID と依頼の ID は、UTC の時刻と乱数の組（`YYYYMMDDTHHMMSSZ-<16 進の 4 文字>`。例：`20261020T150000Z-3fa9`）。パスに入れても困らない文字だけにする。試しのセッションの名前の `<日時>` も同じ形（`check-20261020T150000Z-3fa9`）

### 運用の記録の数え方

測る指標（[FLOW-13][flow]）と、マージの判定と人の判断の一致（[MERGE-3][merge]）と、並列化（段階 9）に入る条件（[FLOW-12][flow]）は、上の記録と GitHub から、数えるときに数える。数えるための欄を別に持たない。段階 4〜8 の出口の数え上げは持たない（[ADR-20261024-002][adr-no-stages] の決定 6）。

| 数えるもの | 数え方 | 数える元 |
| --- | --- | --- |
| マージ率（[FLOW-13][flow]） | 着手した作業の単位（決定済みから計画の輪に進んだもの）のうち、結びつく PR がマージされたものの割合 | `runs.jsonl` の作業の単位ごとの結果（進めた工程）、PR |
| 往復の回数（[FLOW-13][flow]） | PR ごとの有効な `fix` の印の数（上の「ラウンドと往復の数え方」）。`cause`（`check`・`review`・`conflict`）ごとに分けて見る。`round-limit` と `repeated-finding` で止めた件数も数える | `fix` の印、`stop` の印 |
| 誤検知率（[FLOW-13][flow]） | 人が `## 却下 R<n>` で挙げた指摘の、同じラウンドのレビューのコメントの指摘に対する割合。push 以上の人が書き、進行 Bot の印を持たない見出しだけを数える（[FLOW-14][flow]） | PR の `## 却下 R<n>` のコメント、`review` の印 |
| revert 率（[FLOW-13][flow]） | マージした PR のうち、マージから 14 日以内に、base ブランチにその squash の commit を revert する commit か、本文でその PR の番号を「戻す」と言及する fix の PR がマージされたものの割合 | base ブランチの commit の履歴（進行 Bot の clone）、マージされた PR の本文 |
| 1 Issue あたりの利用枠（[FLOW-13][flow]） | 作業の単位ごとの、AI のセッションの費用の累計 | `sessions.jsonl` の終わりの行（費用） |
| マージの判定と人の判断の一致（[MERGE-3][merge]） | PR ごとに 1 件。人がマージしたか `## 判定と違う判断` を書いた時点の、最新の `merge` の印と比べる。`human` の PR を人がマージしたら不一致。`ready` の PR は、`## 判定と違う判断` があれば不一致、マージされたら一致。どちらも無い PR は、催促（`remind` の印）の後も、人が動くまで数えない | `merge` と `remind` の印、PR のマージ、`## 判定と違う判断` のコメント |
| URL で止まった回数（[ADR-20261022-001][adr-url]） | 検疫が URL で見つけた回数。GitHub の添付の URL（FACT-69）で止まった回数を分けて数える。公式文書の URL を通す ADR を起票するかの材料にする | `runs.jsonl` の作業の単位ごとの結果（検疫で見つかった種類）、`security` の印の `finding` |
| 並列化（段階 9）に入る条件（[FLOW-12][flow]） | 連続 7 回の実行で、停止中か攻撃の疑いになった作業の単位が 0 件で、利用枠の消費が上限の内か。lock で見送った実行、起動しなかった定期の実行、受け入れの依頼の実行は、7 回に数えない（[運用の規則][flow]） | `runs.jsonl`（止めた理由、検疫で見つかった種類）、`sessions.jsonl`（費用） |

- 記録を消す時期は決めない。運用の記録の数え上げと見直しに使うため。古い実行の分だけを移すことはしない。移した実行の費用と失敗の回数が、着手した作業の単位の累計から黙って減り、上限が効かなくなるため。大きくなりすぎて移すときは、記録の置き場の全体を移し、`setup` で記録のフォルダと記録の目印のファイルを作り直す。目印のファイルが新しくなるので、着手した作業の単位は停止中（`records-missing`）になり、人が失ったことを認めて戻す（「[AI のセッション][design-ai]」の「起動の前の確かめ」）
