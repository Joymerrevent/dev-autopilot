# 状態遷移と判定

進行 Bot が、毎回の実行で GitHub の状態を読み、Issue ごとに「次の工程」を決めて進める仕組みを決める。
遷移そのもの（正常な順と止まる遷移）は[要件の Issue の状態の遷移][flow]が正本で、基本設計は、何をどの順に読み、どの条件でどの工程に進むかを表にする。

## 工程ごとの PDCA

![工程ごとの PDCA][fig-pdca]

AI が受け持つ工程を、段取り（P）・作業（D）・検証（C）・直す（A）で見ると、次のとおり。AI で回すループのエージェント定義は、ループごとのフォルダに置く（[STRUCT-9][struct]）。

| 工程 | P（段取り） | D（作業） | C（検証） | A（直す） | AI で回すループ |
| --- | --- | --- | --- | --- | --- |
| 受け入れ | 進行 Bot（検疫と、受け入れる Issue を選ぶ処理） | 受付 AI（作業指示の下書き） | 人が下書きを読む | 人が下書きを直すか、`## 作業指示` のコメントを書く | 置かない。人が必ず読むので、AI の検証を足しても人の手間は減らない（定義は `brief/`） |
| 計画 | 作業指示 | 計画 AI | レビュー AI と、人（マージ判定工程（段階 8）の前は、人がすべての計画を読む） | 計画 AI が計画し直す（上限は `limits.planRevisions`） | ある。同じ回の実行の中で回す（定義は `plan/`。[ADR-20261019-003][adr-replan]） |
| 実装と修正 | 計画 | 作業 AI | 機械の検査、レビュー AI（3 つの軸。見落としの軸は記録だけ）、批評 AI | 作業 AI が修正し、次のラウンドでレビューする | ある。往復は `limits.roundTrips` の回数まで（定義は `change/`） |
| マージの判定 | 判定の条件 | 進行 Bot | 人がマージする | 判定の条件を ADR で直す | 置かない。進行 Bot の判定は決まった処理で、同じ入力なら同じ結果になる |

- 前の工程の作業の結果が、次の工程の段取りになる（受け入れの作業指示が計画の段取りに、計画が実装の段取りになる）
- 新しい AI の検証は、記録だけに残して人の判断と比べてから、流れを止める判定に使う（計画のレビュー、見落としの軸、マージの判定）。この進め方も、段階の表で回す PDCA になっている（[段階の表][setup]）

## 1 回の実行の流れ

![1 回の実行の流れ][fig-run-flow]

| 順 | すること | うまくいかないとき |
| --- | --- | --- |
| 1 | 定期の実行の定義が渡したパスから、マシンの設定を読む（[ADR-20261015-005][adr-settings]） | 作業に入らず止まる（[SAFE-4][safety]）。記録の置き場が分からないので、点検の依頼があっても結果を書けない（人の `check` は待つ時間を過ぎたら止まる。「[導入と点検][design-setup]」の「点検だけで動かす仕組み」） |
| 2 | 記録の置き場の lock（`run.lock`）を取る。lock には PID・起動の時刻（lock を取ったプロセスの起動の時刻。時刻帯に依らないエポック秒）・ホスト名を書く。PID が生きていないか、PID のプロセスの起動の時刻が lock の起動の時刻と違えば、古い lock として奪う。再起動の後に使い回された PID で、実行を見送り続けないため（[運用の規則][flow]）。PID が生きていて起動の時刻が同じなら、持ち主が動いているので、ホスト名を問わず奪わない。ホスト名は人が読むためだけに書き、奪うかの判定に使わない（macOS では、つないだネットワークでホスト名が変わりうるため。動かすマシンを替えるときは lock を写さない。下の「手元の記録」の「記録の置き場のほかのファイル」の表の下）。起動の時刻の取り方と、2 つのプロセスが同時に古い lock と読んでも片方だけが lock を取る手順は、表の下の「lock の取り方」。取ったら、手動の 1 回実行・点検・受け入れの依頼のファイルを見て、起こされ方（定期・手動・点検の依頼・受け入れの依頼）を決める。置いた時刻から、依頼のファイルに書いた待つ時間を過ぎた点検と受け入れの依頼は、人が待つのをやめた後に残ったものとして扱う（「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」）。続けて、前の実行が残した AI のセッションを止め、費用を数える（「[AI のセッション][design-ai]」の「前の実行が残したセッション」）。止める猶予と費用は、リポの設定をまだ読んでいないので、見つけたセッションの始まりの行に書いた値（止める猶予と、`--max-budget-usd` に渡した値。下の「手元の記録」）で決める。止められなかったセッションの Issue（と PR）は控えておき、`needs-human`（`session-not-stopped`）は、順 4 でリポの設定（ラベルの名前、Status の選択肢の ID、`run.dryRun`）を読み、順 7 で状態を組み立てた後に、次の工程の表より先に付ける。受け入れの依頼の実行は順 6〜9 に進まないので、付けずに、次の実行に任せる。止められなかったセッションは、`needs-human` を付けるまで終わりの行を書かず、動いているセッションとして費用の上限で数える。順 3〜7 で実行が止まっても、次の実行が、終わりの行の無いセッションとしてもう一度見つけるため | 実行を見送り、見送ったことを記録に残す（[運用の規則][flow]）。点検の依頼は、動いている実行が終わりに行う（順 10） |
| 3 | 全体の止める合図（リポの変数 `DEV_AUTOPILOT_RUN`）を読む（[運用の規則][flow]）。読む先と認証は、マシンの設定の `repository.*` と `githubApp.*`（`null` なら PAT）で決める（[設定][design-settings]） | 値が `run` でないか読めなければ、作業に入らず止まる（[ADR-20261017-007][adr-stop]）。点検の依頼のファイルがあれば、順 4 の設定の読み込みと順 5 の点検だけを行ってから止まる。試しのセッションと書き込みの権限の試しは行わず、未確認の warn にする（「[導入と点検][design-setup]」の「点検だけで動かす仕組み」） |
| 4 | 進行 Bot の clone で fetch し、base ブランチの先端からリポの設定を読む。1 回の実行は、この版の設定で動く（[ADR-20261017-007][adr-stop] の決定 4） | 読めないか形が違えば、作業に入らず止まる。点検の依頼のファイルがあれば、読めないことを fail として結果に書く |
| 5 | 点検を回す。作業場所の残骸の見分け（下の「作業場所の残骸」）を含む。試しのセッションが要るとき（「[導入と点検][design-setup]」の「組と回数」）は、ここで回す（[SETUP-2][setup]） | fail が 1 つでもあれば、作業に入らず止まる（[SETUP-2][setup]）。待つ時間の内の点検の依頼のファイルがあれば、結果を書いて、作業に入らずに止まる。待つ時間を過ぎた点検の依頼は、結果を書いて依頼のファイルを消してから、定期の実行として作業を続ける（「[導入と点検][design-setup]」の「見送った実行と、起動しなかった定期の実行」。[ADR-20261022-004][adr-intake-req] の決定 5） |
| 6 | 基線（base ブランチの先端の必須チェック）を読む（[IMPL-9][impl]） | 緑でなければ、新しい着手・最初の実装・載せ直しだけを止め、ほかは続ける（[ADR-20261015-006][adr-flow] の決定 2） |
| 7 | Project の Issue と、結びついた PR と、印と、必須チェックの結果を読み、Issue ごとに状態を組み立てる（下の「状態の組み立て」） | API が失敗したら、作業を増やさずに記録して止まる（[SAFE-4][safety]） |
| 8 | Issue ごとに、「次の工程」の表で工程を決めて進める。Issue を進める順は下の「Issue を進める順」 | — |
| 9 | Issue を 1 つ進めるごとに、所要時間の上限（`run.maxMinutes`）を見る。上限の内なら順 8 に戻って次の Issue を進め、超えたら、残りの Issue は次の実行に回す（[FLOW-4][flow]） | — |
| 10 | 点検の依頼のファイルがあれば（実行の途中で人が `check` を呼んだ）、順 3 の合図を読み直し、順 5 の点検だけを行って結果を書く。記録と、状態の表示のファイル（`status.json`。「[導入と点検][design-setup]」の「状態の表示」）を書き、lock を外す（[FLOW-5][flow]） | — |

- 受け入れの依頼の実行（人が `/verify-issue` から呼んだ intake の Skill の依頼で起こされた実行）は、順 1〜5 をほかの実行と同じに行い、順 6〜9 に進まずに、受付 AI のセッションを 1 つ起こしてから順 10 を行う。GitHub には何も書かない。順 3〜5 で止まるときは、受付 AI を起こさない理由を、受け入れの依頼の結果のファイルに書く（「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」、[ADR-20261022-004][adr-intake-req] の決定 2）
- lock の取り方（順 2。[運用の規則][flow]）
  - 起動の時刻は、lock を書く側と比べる側で同じ関数で取り、時刻帯に依らないエポック秒（整数）にする。macOS は `TZ=UTC LANG=C ps -o lstart= -p <PID>` の文字を UTC の時刻として読む（`ps` の時刻の書き方は `TZ` と `LANG` で変わるため）。Linux は、`/proc/<PID>/stat` のプロセスの起動の時刻（マシンの起動からの時間）に、マシンの起動の時刻（`/proc/stat` の `btime`）を足す。`sessions.jsonl` のプロセスの行の `claude` の起動の時刻も、同じ関数で取る（下の「手元の記録」）
  - lock は、排他の作成で作る。中身を書き終えた一時のファイル（`run.lock.new-<自分の PID>`）に、`link` で `run.lock` の名前を付ける（同じ名前のファイルがあれば失敗する）。作れれば、lock を取れた。一時のファイルは、作れても作れなくても消す。中身を書く前の空の lock を、ほかのプロセスが読まないため
  - 作れなければ（lock がある）、lock を読み、順 2 の条件で古い lock かを見分ける。持ち主が動いていれば、見送る。中身を読めない lock（壊れたもの）は、古いかを見分けられないので奪わずに見送る（止める側）
  - 古い lock なら、lock を取ろうとするプロセスごとに違う名前（`run.lock.stale-<自分の PID>`）に rename で退け、退けたファイルを読み直す。読み直した中身が、古いと見分けた中身と同じなら、新しい lock を排他の作成でもう 1 回だけ作り、退けたファイルを消す。作れなければ、見送る
  - rename が失敗したとき（ほかのプロセスが先に退けた）は、見送る。読み直した中身が違うとき（ほかのプロセスが奪った後に作った新しい lock を退けた）は、退けたファイルを `run.lock` に rename で戻してから、見送る
  - 2 つのプロセスが同時に古い lock と読んでも、排他の作成で片方だけが lock を取る。退けたファイルを読み直すのは、先に奪ったプロセスの新しい lock を、後のプロセスが古い lock と取り違えて退けたときに、持ち主に返すため
- 全体の止める合図は、順 3 のほかに、AI のセッションを起動する前と、GitHub に書き込む前にも読む。AI のセッションが動いている間は `run.stopSignalPollSeconds` ごとに読む（[運用の規則][flow]）
- 書かずに試す合図（`run.dryRun`）が `true` の間は、GitHub に書く代わりに、書くつもりだった内容を手元の記録に残す。読むことと AI のセッションは行う（[運用の規則][flow]）。点検の書き込みの権限の試し（書けないことを確かめる試し）は例外で、`true` の間も行う（「[導入と点検][design-setup]」の「PAT の権限」）
- 進行 Bot が起こす子プロセス（`gh`・`git`・`lsof` など。AI のセッションを除く）は、1 つずつ `run.commandMinutes` を過ぎたら止める。止めた後の扱いは、子プロセスの種類（GitHub を読む処理、GitHub への書き込み、push と取り込み、止める手順の残りの探し方）ごとに、[設定][design-settings]の「子プロセスが時間の上限を過ぎたとき」の表で決める（[SAFE-4][safety]）。順 2〜4 の子プロセス（前の実行が残したセッションを探す `lsof`、合図を読む `gh api`、リポの設定を読むための `git fetch`）は、リポの設定を読む前に動くので、`run.commandMinutes` でなく、プログラムに固定した 10 分（`run.commandMinutes` の初期値と同じ）を過ぎたら止める。止めるときの `SIGTERM` から `SIGKILL` までの猶予も、`limits.stopGraceSeconds` でなく、プログラムに固定した 10 秒（`limits.stopGraceSeconds` の初期値と同じ）にする
- 書かずに試すのは、受け入れ工程（段階 4）の最初だけ（[ADR-20261021-002][adr-dry]）。書かずに試す間は印を書かないので、手元の記録の「書くつもりだった受け入れの下書き」を、同じ Issue で受け入れに使う文（題名・本文・コメント）のハッシュが同じ間は、書いたものとして扱う（[ADR-20261015-006][adr-flow] の決定 4 の例外。ハッシュの取り方は「[AI のセッション][design-ai]」の「ハッシュの取り方」）。扱うのは、受け入れの相手を選ぶとき（次の工程の表の順 9）と、選定の結果を作るときだけ
  - 書くつもりだった `needs-human`（`quarantine` と `retry-limit`）も、同じハッシュの間は書いたものとして扱い、受け入れ直さない。受付 AI が拒否した Issue は、次の実行で `sonnet` で受け入れ直す（[IMPL-29][impl]）
  - 受け入れの相手は、書いたものとして扱う Issue を除いて、Issue の番号の小さい順に `limits.intakePerRun` 件まで。実行を重ねると、番号の大きい Issue にも下書きが出る。記録が無ければ受け入れ直す（受け入れを黙って飛ばさない）
  - 選定の結果は、下の「Issue を進める順」の組 5（新しい着手）の位置で、書いたものとして扱う下書きがある `Todo` の Issue について、候補の条件（[FLOW-1][flow]）から人の承認にかかわる条件（`agent-ready` があること、付けた人の権限、受け入れの下書きがあり人が `agent-ready` を付けていること）を除いて確かめる。まだ確定していない依存とマイルストーンは、人が先に Issue に付けた値を優先し、無ければ書いたものとして扱う下書きの候補を確定した値として確かめる（書き始めた後の承認の確定で入る値と同じにするため）。満たすか、どの条件で外れたか、着手する順を、手元の記録にだけ残す
  - `run.dryRun` が `false` の実行は、書くつもりだった内容を読まない。書き始めた最初の実行から、GitHub に受け入れの印が無い Issue を改めて受け入れる（書かずに試した下書きは投稿しない）
  - 人は、記録の置き場の `dry-run-drafts.md`（進行 Bot が実行の終わりに書き直す。「[導入と点検][design-setup]」の「状態の表示」）をエディタで開いて、書いたものとして扱う下書きと選定の結果を読み、書き始めるまで `agent-ready` を付けない。異議は、記録の置き場の `dry-run-objections.md` に、`## 異議` の見出しで書き足す（受け入れ工程（段階 4）の出口で、GitHub の異議と合わせて数える。[段階の表][setup]）

## Issue を進める順

1 回の実行の中で、Issue を次の順に進める。同じ組の中は、Issue の番号の小さい順にする。ただし、新しい着手（組 5）はマイルストーンの版の小さい順に並べ、同じ版の中を Issue の番号の小さい順にする（[FLOW-1][flow]）。マージの判定（次の工程の順 19）は、組 2 の中では行わず、組 2 を進めた後に、PR の番号の小さい順で別に回す（[MERGE-5][merge]）。

![Issue を進める順][fig-issue-order]

| 順 | 組 | 理由 |
| --- | --- | --- |
| 1 | 片付け（結びついた PR がマージされた Issue） | 進行中の Issue の数の上限（`limits.wip`）を先に空け、依存していた PR の載せ直しにつなぐ（[MERGE-7][merge]） |
| 2 | 進行中の Issue（Status が `In Progress` から `Ready to Merge`） | 始めた作業を先に進める。新しい着手は進行中の Issue の数の上限で止まるので、進行中の Issue が先に動かないと流れが詰まる（[FLOW-3][flow]） |
| 3 | 承認の確定（人が `agent-ready` を付けた Issue） | 軽い工程で、着手の前に要る（[FLOW-18][flow]） |
| 4 | 受け入れ（受け入れの印が無い Issue） | 人が読む下書きを早く渡す。数は 1 回の実行の件数の上限（`limits.intakePerRun`）で抑える（[TEXT-12][text]） |
| 5 | 新しい着手（候補の Issue） | 上の組を進めた後に、空いた分だけ着手する。候補の順は、マイルストーンの版の小さい順（[FLOW-1][flow]）。書かずに試す間は、組 5 の位置で選定の結果を作る（上の「1 回の実行の流れ」） |

- 承認の確定（組 3）で `intake-final` の印を書いた Issue は、同じ実行の新しい着手（組 5）の候補に入れる。組を進めるたびに状態を GitHub から読み直さず、その実行で書いた値（印・Status・Agent 欄・ラベル）を、組み立てた状態に足す（下の「次の工程」の見直し）

順は暫定。マージ判定工程（段階 8）までの記録（[FLOW-5][flow]）で、所要時間の上限に当たって次の実行に回された組を見て見直す。

## 状態の組み立て

進行 Bot は、毎回の実行で次のものを読み、Issue ごとの状態を組み立て直す。判定には GitHub の状態と印だけを使い、手元の記録は上限の数え上げにだけ使う（[ADR-20261015-006][adr-flow] の決定 4）。例外は、下の表の手元の記録の行の 2 つ（書かずに試す間の受け入れと、比べるためのレビューを起こすか）。

- 読むのは、設定した Project（[FLOW-1][flow]）の項目のうち、当てる先のリポ（マシンの設定の `repository.*`）の Issue だけ。ほかのリポの Issue と、Project に入った PR の項目は読まない（PR は、結びつきの印から Issue ごとに読む）。ただし、別のリポに移された Issue を見つけるため、当てる先のリポの開いている PR のうち、作業ブランチ（`<型>/issue-<番号>`）から開き、PR に進行 Bot の結びつきの印（`note kind=link issue=<番号>`）があるものも読む。印の Issue を REST で引いて、返った Issue の `repository_url` が当てる先のリポでないか、GraphQL で引いて `NOT_FOUND` なら、別のリポに移されたとみなす（次の工程の順 3）。REST は移した先の Issue へ `301` を返し、`gh api` は `301` をたどって移した先の Issue を返すので、引けたことを当てる先のリポにあると読まない（FACT-66）
- 閉じた Issue は、片付け（次の工程の順 1）と、着手した後に閉じられた Issue（順 3）と、作業場所の残骸の見分けのためにだけ読む。受け入れ・承認の確定・着手の対象にしない
- Status が空の項目は `Todo` とみなす

![状態の組み立て][fig-state-assembly]

| 読むもの | 読む先 | 判定での使い方 |
| --- | --- | --- |
| Status と Agent 欄 | Project（GraphQL） | 今の工程と、人の意思表示（`human`・`paused`） |

## 次の工程

Issue ごとに、表を上から順に見て、最初に当てはまった行の工程に進む。
進行 Bot の印も `agent-ready` も無い Issue（人が Project で自分の作業に使っている Issue など）は、受け入れ（順 9）のほかの行には進めない（何もしない。順 2 の付け直しも行わない。[TEXT-2][text]、[FLOW-1][flow]）。受け入れに進むのも、Status が `Todo` で、Agent 欄が `human` でも `paused` でもなく、`needs-human` が無いときだけ（順 2 と同じ）。人が自分で使う Issue に書き込まず、計画も起こさないため。
工程を 1 つ進めたら、その工程で書いた値（印・Status・Agent 欄・ラベル）を組み立てた状態に足して、同じ Issue の表を上から見直し、次に当てはまった行に進む。見直しは、push をしたとき、同じ実行で 2 つ目になる重い工程に当たったとき、待つか何もしない行に当たったときに止める（重い工程の後の収束のような軽い工程は、同じ実行で続ける。[ADR-20261015-006][adr-flow] の決定 1 の正常な流れの目安）。承認の確定（上の「Issue を進める順」の組 3）の後の見直しは、着手（順 11）の前で止める。着手は組 5 の並びで行う。新しい着手をマイルストーンの版の順に並べるため（[FLOW-1][flow]）。マージの判定（順 19）は見直しの中では行わず、上の「Issue を進める順」のとおり組 2 の後に回す。レビュー工程（段階 6）の比べるためのレビュー（順 22）は、軽い工程を先に進めてから起こす（下の「比べるためのレビューに進む順番」）。
「重い」は AI のセッションを起動する工程で、Issue ごとに 1 回の実行で 1 つまで。「軽い」は起動しない工程で、重い工程の前後に同じ実行で続けてよい（[FLOW-4][flow]、[ADR-20261015-006][adr-flow] の決定 1）。
push した実行（実装・修正・載せ直し）では、push した Issue をそれ以上進めない。CI の結果が要る工程（収束・マージの判定）は、CI の結果が出ている実行でだけ進める（[FLOW-4][flow]）。
渡す文を AI に渡す工程（計画・実装・レビュー・修正・衝突の解消）は、起動の前に、渡す文のハッシュが最新の `intake-final` の印と同じかを確かめ、違えば `needs-human` にする（`brief-changed`。[TEXT-4][text] の「着手時と対応ループの各回」）。着手した後に、照らす相手の `intake-final` の印が無いとき（数えない印を無いものとして読んだときを含む。下の「数えない無効な印」）も、`brief-changed` にする。渡す文は、承認の確定と同じ規則で選び、push 以上の人の作業指示コメントが 2 つ以上なら `needs-human` にする（`multiple-instructions`。[ADR-20261021-003][adr-reapprove]）。

| 順 | 条件 | 次の工程 |

| 1 | 結びついた PR がマージされた | 片付け（軽い）：Issue を閉じ、作業場所を消す。Agent 欄とラベルは書き換えない。順 2（触らない）の除外より先に見る（[FLOW-27][flow]、[MERGE-7][merge]、[ADR-20261015-006][adr-flow] の決定 3）。依存していた PR の載せ直しは、片付けの中で行わず、依存していた PR の Issue で、下の「作業中」の表を見る前の確かめで行う（基線の条件と、順 2 の除外を通すため） |
| 2 | Agent 欄が `human` か `paused`。または `needs-human` がある。または、`needs-human` が無く、最後に `needs-human` を外した人（timeline の最新の `UnlabeledEvent` の `actor`）が push 未満 | Agent 欄が `human` か `paused` か、`needs-human` があれば、触らない（[Issue の状態の遷移][flow]の決まり、[FLOW-1][flow]）。push 未満の人が `needs-human` を外したなら、Status を問わず `needs-human` を付け直す（`unauthorized-resume`。[TEXT-10][text]、[ADR-20261015-004][adr-markers] の決定 2） |
| 3 | 着手した後に、Issue が閉じられた・別のリポに移された・`agent-ready` かマイルストーンが外された。着手した後かは、下の「進行中の Issue の数え方」と同じ見方（計画の印か結びつく PR があるか、Status が `In Progress`・`In Review`・`Ready to Merge`。計画の印は、下の「戻した Issue のやり直し」の読み方で読む）で見る。閉じた Issue は Project が Status を `Done` にするので、計画の印か結びつく PR で見る。外されたかは、外した記録でなく今の値で見る（付け直せば止めない） | `needs-human` にし（`issue-changed`）、作業ブランチと PR は残す（[TEXT-8][text]）。別のリポに移された Issue は、上の「状態の組み立て」で結びつく PR から見つけ、結びつく PR に `needs-human` を付けて、stop のコメントに移った先の Issue を書く（当てる先のリポの Issue ではなくなったので、Issue には書かない）。PR に `needs-human` があれば、何もしない |
| 4 | 結びつく PR がマージされずに閉じられた。または、ブランチ名が一致するのに結びつきの印が無い PR がある（無効な結びつきの印を持つ PR は除き、順 5 で止める） | 閉じた PR なら `needs-human` にする（`pr-closed`）。印の無い PR は、作者を問わず `needs-human` にする（`unlinked-pr`）。PR を作った直後、結びつきの印を書く前に切れたときも当たる（まれなので、人が確かめる。[IMPL-6][impl]、[ADR-20261016-001][adr-pr] の決定 3）。無効な結びつきの印（`safety.botAccounts`（[設定][design-settings]）のアカウントが書いた `note kind=link` の形のコメントで、署名か未編集の条件を満たさないもの）を持ち、無効な結びつきの印が下の「数えない無効な印」に当たらない PR は、印の無い PR に数えず、順 5 で止める（`marker-invalid`）。止める先の Issue は、作業ブランチの名前（`<型>/issue-<番号>`）の番号と同じリポで決める（下の「数えない無効な印」の 1 つ目の箇条と同じ決め方）。前の鍵を外した後と鍵が漏れたときの PR と、人が誤って結びつきのコメントを編集した PR で、Issue と PR の無効な印を止めた理由の印に挙げ、人が `marker-invalid` の戻し方（[止まった状態から戻す手順][flow]、[ADR-20261021-004][adr-marker-keys] の決定 4）で 1 回で戻せるようにするため。無効な結びつきの印が数えない印になった後（人が `needs-human` を外した後）は、印の無い PR として扱う。人は、`marker-invalid` の戻し方のとおり、挙がった印に結びつきの印があれば PR を閉じてから戻す。ただし、閉じた PR（印の無い PR を含む）が、人が戻した時刻（下の「戻した Issue のやり直し」）より前に閉じられていれば、Status を問わず、止めずに、閉じた PR を結びつきから外す（ほかに結びつく PR が無ければ、計画からやり直す）。人が戻した時刻は着手した後も GitHub から同じ値に決まるので、着手した後の見直しと次の実行でも、同じ閉じた PR を外し続ける。人が戻した時刻より後に閉じた PR は、止める（閉じた PR は `pr-closed`、印の無い PR は `unlinked-pr`。人が戻した後に、戻す手順を経ずに閉じられた PR で、人が閉じた意図を確かめるため。[IMPL-6][impl]、[ADR-20261022-005][adr-unlink] の決定 1） |
| 5 | 進行 Bot の印のうち、未編集（`intake` の印には掛けない）か署名の条件を満たさないものがある（下の「数えない無効な印」に当たる印を除く）。または、`review` の印の `round` が欠けている | `needs-human` にし、`note kind=stop reason=marker-invalid` を書く（[IMPL-20][impl]、[IMPL-18][impl]）。止めた理由の印は、`needs-human` を付けた先（Issue と PR）ごとに書き（表の下の箇条）、`comments=` に、書く先の無効な印のコメントの ID を挙げ（書く先に無効な印が無ければ持たない）、人向けの本文に、挙げたコメントへのリンクを書く（[印と固定の見出しの一覧][markers]、[ADR-20261021-004][adr-marker-keys] の決定 4）。印の置き場が PR のときは、PR と、結びつく Issue の両方に `needs-human` を付ける。順 4 から回した、無効な結びつきの印を持つ PR では、作業ブランチの名前で決めた Issue を結びつく Issue とし、Issue と PR の両方の止めた理由の印の `comments=` に、書く先の無効な印を挙げる。進行 Bot が `needs-human` を読むのは Issue だけで、PR だけに付けても止まらないため |
| 6 | Issue に紐づく作業場所の残骸がある（下の「作業場所の残骸」） | `needs-human` にする（`workspace-residue`。[FLOW-29][flow]） |
| 7 | 依存（blocked by）の相手に、閉じていない Issue がある。かつ、`intake-final` の印があるか、Status が `In Progress` 以降 | 待つ（欄は変えない）。待つことを、`note kind=wait` の印付きのコメントで 1 回だけ書く（[FLOW-10][flow]）。作業中なら、レビューと修正も止める（[FLOW-33、FLOW-34][flow]）。`intake-final` の印の前（受け入れと承認の確定）は、依存で止めない（[TEXT-12][text] の受け入れの対象は依存を問わない） |
| 8 | Status が、印と PR から許す値（下の「印と PR から許す Status」）に無い | 人が戻す手順に当たれば、Status に従う。当たるのは、push 以上の人が、結びつく開いた PR が無ければ `Todo` に、あれば `In Review` に戻して `needs-human` を外し、最後に外した時刻が進行 Bot の最後の印より後のときと、承認のやり直し（下の「承認のやり直し」）に当たる `Todo` のとき（[止まった状態から戻す手順][flow]）。結びつく開いた PR が無いのに `In Review` に戻したときは、当たらない。push 未満の人が外したときは、順 2 で付け直す（[TEXT-10][text]）。ほかは想定外の Status として `needs-human` にする（`unexpected-status`。[Issue の状態の遷移][flow]の決まり、[SAFE-4][safety]） |

- `needs-human` にするときは、どの契機でも Status を `Blocked` にする（[Issue の状態の遷移][flow]の決まり）。`needs-human` は、いつも Issue に付ける。印の置き場が PR の契機（順 5、`session-not-stopped` など）では、PR にも付ける。別のリポに移された Issue（順 3）だけは、PR にだけ付ける。進行 Bot が `needs-human` を読むのは Issue だけで、PR だけに付けても止まらないため
- 止めた理由の印（`note kind=stop`）は、`needs-human` を付けた先（Issue と PR）ごとに書く。`marker-invalid` の `comments=` は、書く先にある無効な印だけを挙げ、書く先に無効な印が無ければ持たない。Issue の stop の人向けの本文には、PR の stop のコメントへのリンクを書く。人が Project で見る Issue に、止めた理由を残すため（下の「note の種類」）
- 進行 Bot の印も `agent-ready` も無い Issue（人が Project で自分の作業に使っている Issue など）は、順 2 の付け直しを含め、受け入れ（順 9）のほかの行に進めず（上の「次の工程」）、進行中の Issue の数え方の対象にもしない

#### 印と PR から許す Status

| 印と PR | 許す Status | 進行 Bot が書く Agent 欄 | 違うときの扱い |
| --- | --- | --- | --- |
| 計画の印も PR も無い | `Todo`。着手した後（Agent 欄が `worker`）は `In Progress` も | 着手の前は書かない。着手した後は `worker` | 順 8 |
| 計画の印があり、PR が無い | `In Progress` | `worker` | 順 8 |
| draft の PR がある | `In Review`。PR を作った直後に切れた `In Progress` も | 計画・実装工程（段階 5）は空。レビュー工程（段階 6）以降は `reviewer`（修正の間は `worker`、人の番は空） | `In Progress` なら、次の工程の前に、Agent 欄を書いてから `In Review` に書き直す（軽い） |
| ready の PR がある | `Ready to Merge`。ready にした直後に切れた `In Review` と、載せ直しやレビューで戻した `In Review` も | `Ready to Merge` は空。`In Review` に戻したときは `reviewer` | 順 8 |
| `needs-human` がある | `Blocked` | 変えない | 順 2 で触らない |
| `needs-human` が無く、`Blocked` | 人が戻す手順の途中とみなし、何もしない（状態の表示に出す） | 変えない | — |

- 表の「計画の印」は、下の「戻した Issue のやり直し」の読み方で読む。結びつく PR が無く、最新の計画の印が人が戻した時刻（最新の `intake-final` の印の時刻を含む）より前なら、計画の印が無いものとして読み、`Todo` を許す。承認のやり直し（下の「承認のやり直し」）に当たる間だけでなく、新しい `intake-final` の印を書いた後と、人が戻した後に進行 Bot が待ちの印を書いた後も、同じに読む。止まっていなかった Issue で承認をやり直したとき（手順の最初に `needs-human` を付け、最後に外す。[ADR-20261022-005][adr-unlink] の決定 2）も、着手するまで `unexpected-status` で止めないため（[ADR-20261021-003][adr-reapprove] の決定 1、決定 2）
- 進行 Bot が Status を書く途中で切れた組（draft の PR があって `In Progress`）は、[運用の規則][flow]の「GitHub の状態から復旧する」として、次の工程の前に書き直す。人が戻す手順（`Todo` か `In Review`）のほかの値を人が書いたときは、順 8 で止める
- Agent 欄は、表の値を、工程ごとに書く（次の工程の表の順 11・13・14・15・17・18 と、下の「作業中」の表の前の確かめと、下の「push の手順」の順 8。[FLOW-19][flow]〜[FLOW-25][flow]、[ADR-20261015-006][adr-flow] の決定 3）。Status を変える工程では、Agent 欄を先に書き、Status を最後に書く。途中で切れても Status が前の値のままなので、次の実行が同じ行に当たって続きを書く（書いてある値は書き直さない）。Status を変えない工程（修正の後の `reviewer`）で切れたときは、次に当たる工程（レビュー）が、工程の前に要る値を書く

#### 戻した Issue のやり直し

人が戻す手順（Status を `Todo` に戻して `needs-human` を外す。[止まった状態から戻す手順][flow]）か、承認のやり直し（下の「承認のやり直し」）で戻した Issue を、次のように扱う。
人が戻した時刻は、push 以上の人が最後に `needs-human` を外した時刻（timeline の `UnlabeledEvent`）、最新の `intake-final` の印の時刻、承認のやり直しに当たる `agent-ready` を付けた時刻（timeline の最新の `LabeledEvent`。新しい `intake-final` の印を書くまでの間）の、最も遅いもの。どれも着手した後も GitHub から同じ値に決まるので、着手した後の見直しと次の実行で、読み方が変わらない（[ADR-20261022-005][adr-unlink] の決定 1）。

- 結びつく PR が無い Issue で、最新の計画の印が人が戻した時刻より前なら、計画の印が無いものとして読み、着手の後に計画し直す（順 12）。計画の印を無いものとして読むことは、Status を問わず、次の工程の表の全体（上の「印と PR から許す Status」、下の「進行中の Issue の数え方」、順 3 の「着手した後」、順 12）に掛ける。止まった理由（`adr-required`、`plan-blocked-path` など）が計画にあることが多く、人が直したものを計画に入れるため。読むのは、最新の計画の印だけ。PR のある Issue を `In Review` に戻したときは、計画し直さず、PR の状態から続ける（[止まった状態から戻す手順][flow]）
- マージされずに閉じた PR（結びつきの印の無い PR を含む）が、人が戻した時刻より前に閉じられていれば、Status を問わず、その PR を結びつきから外す（順 4）。外した PR は、Issue 1 件に結びつく PR の数に入れない。外したことは、GitHub にも手元の記録にも書かず、実行のたびに、閉じた時刻と人が戻した時刻から決め直す。閉じた PR の番号の名前のセッションのフォルダは、片付けと同じに消す（下の「作業場所の残骸」。[ADR-20261022-005][adr-unlink] の決定 1）
- 作業ブランチは、人が消してから戻す。残っていれば、結びつく PR の無い作業ブランチとして、順 13 で `needs-human` になる（`branch-without-pr`）

#### 承認のやり直し

承認した後に渡す文を直したいとき、人は、`needs-human` が無ければ付け（Status は変えなくてよい）、文を直し、PR があれば閉じて作業ブランチを消し、Status を `Todo` に戻し、`agent-ready` を外して付け直してから、最後に `needs-human` を外す（[止まった状態から戻す手順][flow]、[ADR-20261021-003][adr-reapprove]、[ADR-20261022-005][adr-unlink] の決定 2）。`needs-human` がある間は、進行 Bot は Issue に触らない（順 2）ので、手順の途中に実行が入っても止まり直さない。進行 Bot は、次のように扱う。

- 次をすべて満たす Issue を、承認のやり直しとして、承認の確定（順 10）に回す
  - `intake-final` の印がある
  - push 以上の人が `agent-ready` を付けた最新の時刻（timeline の `LabeledEvent`）が、最新の `intake-final` の印の投稿より後
  - Status が `Todo` で、`needs-human` が無く、開いている結びつく PR が無い
- 承認のやり直しに当たる Issue は、順 4 と順 8 で止めない。人が戻した時刻より前に閉じた PR は結びつきから外し（順 4）、計画の印は無いものとして読んで `Todo` を許す（順 8）。手順どおりに戻した Issue では、手順の中で閉じた PR は、最後に `needs-human` を外した時刻と `agent-ready` を付け直した時刻より前に閉じているので、人が戻した時刻より前に閉じた PR に当たる。承認のやり直しより先に `pr-closed` か `unexpected-status` で止めないため
- 承認の確定と同じこと（下の「受け入れと承認の確定で確かめること」）を確かめ、満たせば新しい `intake-final` の印を新しいコメントで書く。時刻の確かめ（`brief-edited-after-approval`）は、最新の `agent-ready` を付けた時刻で見る
- 進行 Bot は、最新の `intake-final` の印だけを読む。渡す文のハッシュの照らし（`brief-changed`）も、最新の印で行う
- 計画の印が、最新の `intake-final` の印より前なら、計画の印が無いものとして読み、着手の後に計画し直す（順 12）。最新の `intake-final` の印の時刻は人が戻した時刻に入るので、上の「戻した Issue のやり直し」の読み方と同じで、新しい `intake-final` の印を書いた後も、着手して計画し直すまで変わらない
- 着手した後（Status が `Todo` でない）に付け直した `agent-ready` は、やり直しとして扱わない。渡す文が変わっていれば、ハッシュの照らしで止まる（`brief-changed`）。人は、戻す手順で `Todo` に戻してから付け直す

#### 数えない無効な印

人が `marker-invalid` で止めた Issue を戻したとき（[止まった状態から戻す手順][flow]）、進行 Bot は、次をすべて満たす無効な印を、順 5 で止める契機に数えない（[IMPL-20][impl]、[ADR-20261021-004][adr-marker-keys] の決定 4）。

- 印の置き場の Issue で（置き場が PR なら、結びつく Issue で）、push 以上の人が `needs-human` を外した。外したかを確かめるときと、無効な結びつきの印を持つ PR を順 5 で止めるとき（次の工程の順 4）だけ、PR の結びつく Issue を、作業ブランチの名前（`<型>/issue-<番号>`）の番号と、同じリポの 2 つで決める。PR の結びつきの印が無効になったときと、数えない印になったとき（前の鍵を外した後など）も、結びつく Issue を決められるようにするため。外した人は、timeline の最新の `UnlabeledEvent` の `actor` で確かめる（[TEXT-10][text]）。push 未満の人が外したときは、順 2 で付け直す（`unauthorized-resume`）
- 最後に `needs-human` を外した時刻より前に書いた、有効な `note kind=stop reason=marker-invalid` の印のどれかの `comments=` に、無効な印のコメントの ID がある。読む止めた理由の印は、Issue と、結びつく PR のもの（結びつきの印が無効な PR は、作業ブランチの名前で引いた PR。次の工程の順 4）
- 無効な印のコメントが、最後に `needs-human` を外した時刻より後に編集されていない（`lastEditedAt` が無いか、外した時刻より前）。外した後に編集されたら、新しく無効になった印として数える

数えない印と、条件に当たらない無効な印は、次のように扱う。

- 数えない印は、無いものとして読み、中身（判定・件数・ハッシュなど）を判定に使わない。無いものとして読んだ結果、ほかの判定（`review` の印の `round` の欠け、受け入れの下書きの前の `agent-ready`、承認の確定など）に当たれば、当たった判定に従う
- 止めた理由の印に挙がっていない無効な印は、1 つでもあれば止める。外した後に新しく無効になった印と、鍵を一覧から外して確かめられなくなった印も、まず止めて知らせ、人が `needs-human` を外した後に、数えない対象になる
- `review` の印の `round` の欠けは、数えない対象にしない。欠けは印のコメントが無いことで、挙げるコメントが無いため。途中のラウンドの `review` の印を数えないと `round` が欠けるので、人は PR を閉じて計画からやり直す（[止まった状態から戻す手順][flow]）
- 止めた理由の印は、有効なものだけを読む。`comments=` は署名の対象に入るので、止めた理由の印を別の Issue に写しても、直しても、数えない印は増えない

#### 進行中の Issue の数え方

進行中の Issue の数の上限（`limits.wip`）で数える Issue は、着手した後で、閉じていない Issue。

- 着手したかは、計画の印か結びつく PR があるか、Status が `In Progress`・`In Review`・`Ready to Merge` かで見る。計画の印は、上の「戻した Issue のやり直し」の読み方で読む（結びつく PR が無く、人が戻した時刻より前の計画の印は無いものとして読む）
- `Blocked` の Issue も、計画の印か結びつく PR があれば数える。人の対処を待つ作業があるうちに、新しい作業を積み増さないため
- 受け入れで止まった Issue と、着手した直後に計画の前で止まった Issue（計画の印も PR も無い）は数えない。人が見る作業がまだ無いため
- 要件の FLOW-3 は、上の数え方を指す
- 記録を失ったときの扱い（「[運用の規則][flow]」の `records-missing`）は、進行中の数え方と違い、着手した Issue（Status が `In Progress`・`In Review`・`Ready to Merge` か、計画の印か結びつく PR がある Issue）に掛ける（[ADR-20261015-006][adr-flow] の決定 4 の「進行中の Issue」）。着手の直後で計画の前の Issue も、失敗の回数と累計を数え直さないため

### 作業中（Status が `In Progress` から `Ready to Merge`）

![次の工程：作業中][fig-in-progress]

作業中の Issue では、表を見る前に、次の 4 つを順に見る。

- PR の head の必須チェックの結果を、IMPL-27 の表の上の行から順に当てる。`action_required` があれば `needs-human` にし（`ci-action-required`）、`cancelled` `skipped` `neutral` `stale` のまま完了から `limits.ciStaleHours` を過ぎていれば `needs-human` にして（`ci-stale`）、表には進まない。ほかの結果（赤、まだ無い、動いている途中）は、表の順 15（修正）と順 16（CI を待つ）で扱う（[IMPL-27][impl]、[ADR-20261016-001][adr-pr]）
- 依存の相手の Issue に結びつく PR がマージされ、依存の相手の PR のマージの commit が、PR の head にまだ含まれていなければ、表を見る前に載せ直す（順 18 と同じ手順。基線が緑のときだけ。[FLOW-9][flow]、[FLOW-34][flow]、[MERGE-7][merge]）。待ちの印（順 7 の `note kind=wait`）の有無は問わない。待ちの印を書く前に切れた Issue と、待つ前に先行が閉じた Issue も、先行の変更を取り込むため。基線が緑でない間は、取り込まずにレビューと修正を続ける（[IMPL-9][impl]、[ADR-20261015-006][adr-flow] の決定 2）。依存の相手に閉じていない Issue があれば、ここに来る前に順 7 で待つ。ただし、作業 AI が直す番（修正工程（段階 7）以降で、最新の `review` の印が `fix` か CI が赤で、そのラウンドの、PR に届いた `fix` の印（順 15）がまだ無い間）は、表を見る前に載せ直さず、修正（順 15）を先に行う。載せ直しは、修正の push の後の実行で、再レビュー（順 14）の前にここで行い、再レビューは載せ直した head で行う（[ADR-20261022-003][adr-rounds] の決定 5）。修正の前の載せ直しが衝突すると、衝突の解消の `fix` の印がまだ直していないラウンドに付き、順 15 が直したラウンドと読んで修正に進まず、次のラウンドで直していない指摘を同じ指摘の再発と読むため。修正の前の載せ直しで差分が変われば、まだ直していない変更をもう一度レビューする分の利用枠も使う。作業 AI が直す番でない PR（レビュー工程（段階 6）で人が直す番の PR を含む）は、今のとおり表を見る前に載せ直す
- PR の head が、最新の `review` の印の `head` を 1 つ目の親に、base ブランチの commit（進行 Bot の clone で fetch した base ブランチの先端の祖先）を 2 つ目の親に持つ merge の commit（載せ直しで進行 Bot が作る形）で、head に `review` の印が無ければ、差分の patch-id を最新の `review` の印の `head` と比べ直す。同じなら印を付け直し（順 18 と同じ。軽い）、違えば下の確かめと順 14 で再レビューに回す。載せ直しの push の後、印を付け直す前に切れても、差分が同じ PR を再レビューせず、往復にも数えないため（[MERGE-6][merge]）
- Status が `Ready to Merge` で、PR の head が最新の `review` の印の `head` と違う（人の push か、修正か衝突の解消。載せ直しで差分が同じときは、印を付け直すので当たらない）なら、Agent 欄を `reviewer` にしてから、Status を `In Review` に戻す（軽い）。新しい head をレビューし、収束（順 17）で 🟢 を Issue にしてから `Ready to Merge` に戻すため（[MERGE-6][merge]、[IMPL-26][impl]）

| 12 | 結びつく PR が無く、計画の印（`plan`）が無いか、最新の計画の印が人が戻した時刻（最新の `intake-final` の印の時刻を含む。上の「戻した Issue のやり直し」と「承認のやり直し」）より前。結びつく PR のある Issue は、計画の印が無くても（数えない印を無いものとして読んだときを含む）計画せず、PR の状態から続ける | 計画（重い。中の順番は下の「計画の工程の中の順番」）。基線が緑のときだけ（計画は新しい着手に含む。[IMPL-9][impl]、[ADR-20261015-006][adr-flow] の決定 2）。計画を投稿した実行では、実装に入らない（[FLOW-20][flow]、[IMPL-10][impl]） |
| 13 | 計画の印があり、結びつく PR が無い | 実装と PR の作成（重い）。基線が緑のときだけ（[FLOW-21][flow]、[IMPL-9][impl]）。PR を作った後に、Agent 欄（計画・実装工程（段階 5）は空、レビュー工程（段階 6）以降は `reviewer`）を書いてから、Status を `In Review` にする（下の「push の手順」の順 8）。作業ブランチ（`<型>/issue-<番号>`。型を問わず、番号が同じもの）が origin にすでにあれば、実装せずに `needs-human` にする（`branch-without-pr`）。push の後、PR を作る前に切れた場面と、閉じた PR の作業ブランチが残った場面を GitHub の状態から見分けられず、古い渡す文と計画で作った commit を PR にしないため。人は作業ブランチの中身を確かめて消してから戻す |
| 14 | PR の head に、まだ `review` の印が無い | 計画・実装工程（段階 5）なら何もしない（人がレビューする番）。レビュー工程（段階 6）以降なら、Agent 欄を `reviewer` にしてから（すでに `reviewer` なら書かない）、レビュー（重い）。修正の後と人の push の後の再レビューも、ここに当たる（[FLOW-21、FLOW-22][flow]、[ADR-20261015-006][adr-flow] の決定 3） |
| 22 | レビュー工程（段階 6）で、最新の `review` の印の `head` が PR の head と同じ（順 14 に当たらない）。かつ、最新の `review` の印のラウンドの比べるためのレビューが済んでいない（下の「比べるためのレビューが済んだかの見分け方」） | 比べるためのレビュー（重い）：3 つの軸を `models.reviewComparison` のモデルで起こし、印を書かず、結果を手元の記録にだけ残す（起こし方は「[AI のセッション][design-ai]」の「セッションの名前」。[IMPL-19][impl]）。順 15〜18 の軽い工程にも当たるときは、軽い工程を先に進める（下の「比べるためのレビューに進む順番」）。基線が緑でなくても起こす（PR の head の上の作業で、base ブランチを取り込まないため。[ADR-20261015-006][adr-flow] の決定 2）。修正工程（段階 7）以降では起こさない（[ADR-20261021-007][adr-compare] の決定 1） |
| 15 | 最新の `review` の印が `fix` か、CI が赤で、そのラウンドの `fix` の印のうち、PR に届いたもの（`head` が PR の head か、PR の head の祖先の印）がまだ無い | 修正工程（段階 7）以降なら、修正（重い）。修正のセッションを起こす前に Agent 欄を `worker` にし、`fix` の印を書いて push した後に `reviewer` にする（[FLOW-22][flow]、下の「push の手順」の順 7・8）。push が断られたか、`fix` の印を書いた後、push の前に実行が切れたときは、`fix` の印が PR に届かないので、次の実行でここに当たり、修正をやり直す。届かなかった `fix` の印も往復に数える（[ADR-20261022-003][adr-rounds] の決定 4）。往復の回数がすでに上限（`limits.roundTrips`）に達しているか（`round-limit`）、同じ指摘の再発（直したはずの指摘が再び出た。`repeated-finding`）なら、修正せずに `needs-human` にする（[FLOW-22][flow]、[FLOW-28][flow]、[IMPL-23、IMPL-24][impl]。往復の数え方は下の「ラウンドと往復の数え方」）。レビュー工程（段階 6）では、AI は直さず、人の番にする（Agent 欄を空にする。[Issue の状態の遷移][flow]の「段階による違い」）。往復の上限と同じ指摘の再発は、AI の変更の往復に掛けるので、AI が直さないレビュー工程（段階 6）では当てはまらない（段階 6 には `fix` の印が無く、段階 6 から持ち越した PR は往復を 0 回から数える。[IMPL-24][impl]） |
| 16 | 最新の `review` の印が `pass` で、CI の結果がまだ出ていない | 待つ。次の実行で読み直す（[IMPL-27][impl]） |
| 17 | 最新の `review` の印が `pass` で、CI が緑。Status が `In Review` | 収束（軽い）：🟢 を Issue にしてから、PR を ready にし、Agent 欄を空にしてから、Status を `Ready to Merge` にする（[FLOW-23][flow]、[IMPL-26、IMPL-27][impl]）。レビュー工程（段階 6）から行う |
| 18 | Status が `Ready to Merge` で、base ブランチが PR の head より先に進んでいる | 載せ直し（軽い）。基線が緑のときだけ。差分の patch-id（行番号を除いた差分から git が作る、変更の中身の指紋）が同じなら印を付け直し、変わったら Agent 欄を `reviewer` にしてから、Status を `In Review` に戻して再レビューに回す。衝突したら、修正工程（段階 7）以降は作業 AI の衝突の解消のセッション（重い）で解き、修正と同じく対応コメントと `fix` の印を書く（下の「push の手順」の順 7）。衝突の解消の作業 AI を起こす前に往復の回数を確かめ、すでに上限（`limits.roundTrips`）に達していれば、衝突を解かずに `needs-human` にする（`round-limit`。[ADR-20261022-003][adr-rounds] の決定 2）。レビュー工程（段階 6）では人の番にする（Agent 欄を空にし、衝突したことを `note kind=conflict` の印付きのコメントで Issue に書く。PR の head ごとに 1 回だけ。`fix` の印は書かない）（[FLOW-25][flow]、[MERGE-6][merge]） |
| 19 | Status が `Ready to Merge` で、head に `merge` の印が無く、CI が緑で、base ブランチが PR の head より先に進んでいない | 修正工程（段階 7）以降なら、マージの判定（軽い）。修正工程（段階 7）は判定を記録にだけ残し、印を書かない。マージ判定工程（段階 8）以降は印を書く。`merge=ready` にするのは 1 回の実行で 1 件まで。`merge=ready` の印があってマージされていない、開いている PR がほかにあれば、`merge=ready` になる判定を次の実行に回す（1 件目がマージされるまで待つ）。`merge=human` の判定は 1 件の上限に数えず、書く（[FLOW-24][flow]、[MERGE-2、MERGE-3、MERGE-5][merge]、[ADR-20261016-001][adr-pr] の決定 2） |
| 20 | `merge=ready` の PR が、マージも「判定と違う判断」のコメントも無いまま `limits.remindDays` 日を過ぎ、催促の印（`note kind=remind`）がまだ無い | 催促（軽い）（[MERGE-3][merge]） |
| 21 | どれにも当てはまらない | 次の待ちに当たれば、何もしない：基線が緑でない（新しい着手・最初の実装・載せ直しを止めている）、人のレビューか修正の番（段階 5・6）、CI の結果、人のマージ（`merge` の印のある PR と、段階 6・7 の `Ready to Merge` の PR）。どれにも当たらなければ、GitHub の状態から次の工程を決められない組み合わせとして `needs-human` にする（`unrecoverable`。[運用の規則][flow]） |

- 順 14（レビュー）と順 15（修正）の「そのラウンド」は、PR の head に対して最後に書いた `review` か `fix` の印の `round` で決める。ラウンドの数え方と、収束とマージの判定は、下の「判定」の節で決める
- レビュー工程（段階 6）で AI が直さない扱い（順 15）は、要件の「[段階による違い][flow]」が決めている。順 17 の収束はレビュー工程（段階 6）から行い、順 19 のマージの判定は修正工程（段階 7）から行う（[段階の表][setup]）
- 収束（順 17）で Issue にする 🟢 は、その PR のすべてのラウンドの `review` のコメント（進行 Bot が書き、未編集のもの）の 🟢（批評 AI の統合で 🟡 から下げたものを含む）。指摘の ID ごとに 1 件にまとめる。読み方は「[AI のセッション][design-ai]」の「レビューのコメントの形」（[IMPL-26][impl]）

#### 比べるためのレビューに進む順番

順 22 は、順 14 の後、順 15 の前に置く。レビュー工程（段階 6）では、順 15 より後の行は軽い工程か待ちだけ（AI は直さず、人の番にする）なので、比べに進んでも、本番の重い工程を次の実行に回さない（[ADR-20261021-007][adr-compare] の決定 1）。

- 順 22 に当たったら、起こす前に、順 22 を除いて順 15〜21 を見る。軽い工程（順 15 のレビュー工程（段階 6）の人の番にする、順 17 の収束、順 18 の載せ直し）に当たれば、同じ実行で先に進め、進めた後の状態で順 22 の条件を確かめ直す。軽い工程が無くなり、待つか何もしない行（人の番、順 16 の CI を待つ、順 21 の待ち）に当たったら、比べるためのレビューを起こす（[FLOW-4][flow] の、重い工程の前後に軽い工程を続けてよい決まり）
- 載せ直しで push した実行では、比べるためのレビューを起こさない（push した Issue をそれ以上進めない。上の「次の工程」）
- 本番のラウンドの `review` の印を書いた実行では、比べるためのレビューは同じ実行で 2 つ目の重い工程になるので、起こさない（[FLOW-4][flow]）。次の実行より後で起こす

#### 比べるためのレビューが済んだかの見分け方

進行 Bot は、順 22 の条件を確かめるときだけ、手元の記録の `sessions.jsonl` を読み、最新の `review` の印のラウンドの、3 つの軸の比べのセッション（名前は `review-pr-<PR の番号>-round-<ラウンド>-<軸>-compare`。「[AI のセッション][design-ai]」の「セッションの名前」）に終わりの行があるかを見る。手元の記録を判定に使わない決まり（[ADR-20261015-006][adr-flow] の決定 4）の、2 つ目の例外にあたる（[ADR-20261021-007][adr-compare] の決定 2。下の「手元の記録」）。

- 3 つの軸のすべてに終わりの行があれば、済んだとする。終わりの行は、失敗で終わった回（時間・ターン・費用の上限、利用枠切れ、出力契約が解析できないなど）も含む。失敗した比べは、やり直さない
- 終わりの行が、全体の止める合図で止めた回（終わりの行の欄で見分ける。下の「手元の記録」の `sessions.jsonl`）なら、その軸は済んでいないとする。起動の前の確かめ（止める合図、1 日と 1 回の実行の上限）で起動しなかった軸は、終わりの行が無いので済んでいない。順 22 は、済んでいない軸だけを起こす
- 記録を失ったとき（記録のフォルダを失った、行が読めない、人が記録の置き場を移して作り直した）は、済んでいないとして、条件に当たれば比べを起こし直す。比べの結果は本番の判定に使わないので、本番の流れは変わらない
- 比べるのは、最新の `review` の印のラウンドだけで、ラウンドごとに 1 回。比べる前に人の push で head が変わり、本番が新しいラウンドをレビューしたら、前のラウンドの比べは起こさない。載せ直しで差分が同じで、同じラウンドの印を新しい head に付け直したときは、ラウンドが同じなので起こし直さない
- 比べの結果は、収束、マージの判定、同じ指摘の再発、ラウンドの数え方には使わない。段階の出口の数え上げと、人が読むためにだけ使う（[IMPL-19][impl]）

### 計画の工程の中の順番

![計画の工程の中の順番][fig-plan-step]

順 12 の計画（重い）は、1 回の実行の中で、次の順に AI のセッションを起動する。工程は 1 つのまま（[FLOW-4][flow]）。
セッションを起動する前には、毎回、「[AI のセッション][design-ai]」の「起動の前の確かめ」を行う。全体の止める合図、1 日の上限、1 回の実行の上限のどれかで起動できなければ、計画を投稿せずに終わり、次の実行で計画の工程を 1 から始め直す（[ADR-20261018-002][adr-redo]、[ADR-20261019-003][adr-replan]）。1 Issue の累計の上限に当たったら、`needs-human` を付ける（`usage-limit`）。

| 順 | すること | 次に進む先 |
| --- | --- | --- |
| 1 | 計画 AI が計画を返す（モデルは `intake-final` の印の `plan=`。承認したときのラベル `plan:*` で上書き済みの値で、承認の後に付いたラベルは読まない。`models.plan` か `models.planHard`。[TEXT-10][text]、[ADR-20261018-002][adr-redo]） | `opus` が自己申告したら 2。しなければ 3 |
| 2 | 計画 AI が `fable` で計画し直す（1 回だけ。`models.planHard`） | 3 |
| 3 | 進行 Bot が、計画の `plan.paths` を push しないパスの一覧（IMPL-15 が名指しするパスと `push.blockedPaths` を合わせた一覧。[ADR-20261021-005][adr-blocked]）と照らす | 1 つでも当たれば、計画を投稿せず、`needs-human` を付ける（`plan-blocked-path`。[ADR-20261019-004][adr-policy]）。当たらなければ 4 |
| 4 | レビュー AI が計画をレビューし、`ok` か `fix` と指摘の一覧を返す（`models.planReview`） | `ok` なら 6。`fix` で、レビューの指摘で計画し直した回数が上限（`limits.planRevisions`）に達していなければ 5、達していれば 6 |
| 5 | 計画 AI が、渡す文・直す前の計画・指摘の一覧を受け取って計画し直す（直す前の計画と同じモデル。自己申告は無視して記録に残す） | 3 |
| 6 | 最後の計画の文の欄を、検疫（[TEXT-11][text]）と漏えいの検査に通してから、`plan` の印付きで投稿する | 計画を投稿した実行では、実装に入らない。検疫か漏えいの検査で見つかれば、投稿せずに `needs-human` を付ける（`quarantine` か `leak`）。計画の印が無いので、人が戻せば計画からやり直す |

- マージ判定工程（段階 8）の前は、順 6 で投稿する計画コメントに、レビューの結果も、レビューの指摘で計画し直したことも書かない（人の判断に影響を与えないため）。直す前の計画、レビューの結果と指摘、やり直した計画は、手元の記録に残す（[IMPL-10][impl]）
- 順 2 で計画し直したことは、計画コメントに固定の文で書き添える（[ADR-20261018-002][adr-redo]）
- 計画 AI と計画のレビューのどのセッションも、失敗したとき（出力契約が解析できない、時間かターンか費用の上限など）は、実行の失敗として計画を投稿せずに終わり、次の実行で計画の工程を 1 から始め直す（[IMPL-14][impl]）。計画のレビューは、計画・実装工程（段階 5）から計画し直しに使うので、レビューが失敗した計画をそのまま投稿しない
- 上限が初期値（1 回）のとき、計画の工程は最大 5 つのセッション（計画 AI が 3 つ、計画のレビューが 2 つ）を起動し、1 セッションの上限 45 分なら最大 225 分かかる。1 回の実行の所要時間の上限（`run.maxMinutes` の初期値 180 分）を超えたら、ほかの Issue を次の実行に回す
- マージ判定工程（段階 8）以降に、順 6 で `fix` のまま上限に達した計画を止めるか（`needs-human` にするか）は、マージ判定工程（段階 8）に進む前に別の ADR で決める（[ADR-20261018-004][adr-planrev] の決定 3、[ADR-20261019-003][adr-replan] の決定 3）

## push の手順

![push の手順][fig-push]

作業 AI の commit を GitHub に届ける手順（[IMPL-15][impl]、[ADR-20261013-001][adr-workspace] の「取り込み」）。実装・修正・衝突の解消のセッションの後と、進行 Bot だけで行う載せ直しの後に行う。AI が書いた commit は、進行 Bot が検査してから、進行 Bot の clone から送る。

照らす範囲は、PR が base ブランチに足す commit（進行 Bot の clone で fetch した base ブランチの先端の SHA を `<base>` として、`git rev-list <base>..<控えた SHA>`）にする。載せ直しと衝突の解消で取り込んだ base の commit は、範囲に入らない。人が base ブランチに入れた変更を、AI の変更として止めないため。

| 順 | すること | うまくいかないとき |
| --- | --- | --- |
| 1 | 作業 AI の出力契約を取り出す（「[AI のセッション][design-ai]」の「役ごとの出力契約」）。進行 Bot だけで行う載せ直しでは、とばす | 取り出せなければ、実行の失敗として次の実行に持ち越す。取り出せて、止まった理由（`stopReason`）を返していれば、push せず、止まった理由で `needs-human` を付ける |
| 2 | 進行 Bot の clone で、AI の作業場所から作業ブランチを取り込み（`git fetch <置き場>/sessions/<セッションの名前>/worktree <ブランチ>`）、取り込んだ先端の SHA を控える。AI の作業場所の clone では git を実行しない（[ADR-20261013-001][adr-workspace]）。控えた SHA が、作業場所を作ったときの SHA と同じ（新しい commit が無い）なら、push しない | 取り込みが objects の検査で失敗したら、`needs-human` を付ける（`workspace-tampered`）。AI が objects を書き換えたおそれがあるため（FACT-18、FACT-57）。作業 AI が `done` を返したのに新しい commit が無ければ、`needs-human` を付ける（`no-new-commit`。全部 `unable` の修正と、直せなかった CI の赤を含む）。印を書かずに止めるのは、`fix` の印を同じ head に書くと次の工程の表のどの行にも当たらず、書かないと毎回同じ修正をやり直すため |
| 3 | 範囲の commit ごとに、差分が触れるパスを、push しないパス（進行 Bot のプログラムに固定した、IMPL-15 が名指しするパスと、`push.blockedPaths` を合わせた一覧。[ADR-20261021-005][adr-blocked]）と照らす。merge の commit は、どの親とも違う部分（`git show --cc`）を照らす。あわせて、PR の全体の差分（`git diff <base>...<控えた SHA>`）も照らす | 当たれば push せず、`needs-human` を付ける（`blocked-path`）。途中の commit で触れて後の commit で戻しても、途中の commit が GitHub に届くので止める |
| 4 | GitHub に書く文を組み立てる。初回は PR の題名と本文、修正と衝突の解消は対応コメント（修正は出力契約の `responses`、衝突の解消は固定の文と出力契約の `checks`。形は「[AI のセッション][design-ai]」の「コメントの形」）。題名は、作業 AI の案（出力契約の `pr.title`）を規約（`conventions.*`。Conventional Commits の形と言語）に照らしてから使い、外れていれば、Issue の文を使わない固定の形で作る（`conventions.language` が `ja` なら `<作業ブランチの型>: issue #<Issue の番号> の対応`。言語ごとの固定の文は進行 Bot のプログラムに持つ。[TEXT-6][text]、[IMPL-6][impl]）。本文は、「AI が生成した」の 1 行、`Closes #<Issue の番号>`、作業 AI が確かめた検査の結果（出力契約の `checks`）、本文の案（`pr.body`）の順に並べる。続けて、漏えいの検査を、範囲の commit ごとの差分（merge の commit は `git show --cc`）、commit ごとのメッセージと作者、組み立てた文（最後に使う題名を含む）に掛け、組み立てた文のうち AI の文の欄に検疫（[TEXT-11][text]）を掛ける。検査は `plugin/src/` の中のものを使い、worktree の中の検査は使わない（[IMPL-15][impl]） | 漏えいの検査に引っかかれば push せず、`needs-human` を付ける（`leak`）。途中の commit で足して後の commit で消した秘密も、途中の commit が GitHub に届くので止める。検疫で見つかれば push せず、`needs-human` を付ける（`quarantine`。投稿する AI の文ごとの扱いは「[AI のセッション][design-ai]」の「共通の決まり」の表）。push の後に見つけて、push だけ済んだ状態で止めないため |
| 5 | 進行 Bot の clone から `git ls-remote` で、作業ブランチの今の先端を読み、控えた SHA の祖先であることを確かめる（fast-forward で届くこと）。作業ブランチがまだ無ければ、作業場所を作ったときに控えた base の SHA で確かめる（[IMPL-15][impl]、[SAFE-13][safety]） | 祖先でなければ push せず、`needs-human` を付ける（`not-fast-forward`）。AI が履歴を書き換えたか、ほかの誰かが push したため |
| 6 | 全体の止める合図を読み直し、書かずに試す合図（`run.dryRun`）を見る（[運用の規則][flow]） | 合図が `run` でなければ push せずに止まる。`dryRun` が `true` なら push せず、送るつもりだった SHA を手元の記録に残す |
| 7 | 修正と衝突の解消では、順 4 で組み立てて検査した対応コメントを、`fix` の印（`round` は最新の `review` の印の `round`、`head` は控えた SHA）付きで PR に書いてから送る。push の後に実行が切れても、修正を往復に数え、次のラウンドで同じ指摘の再発を判定し、対応コメントも PR に出るため（[ADR-20261022-003][adr-rounds] の決定 4）。進行 Bot の clone から、deploy key で `git push origin <控えた SHA>:refs/heads/<型>/issue-<番号>` を送る。ブランチ名でなく SHA を送り、force push はしない（[IMPL-15][impl]） | 対応コメントを書けなければ、push せずに、実行の失敗として次の実行に持ち越す。push が断られたら（ruleset など）、実行の失敗として次の実行に持ち越す。書いた `fix` の印は PR に届かないので、修正は次の実行の順 15 でやり直し、衝突の解消は、base ブランチが PR の head より先に進んだままなので、次の実行の載せ直しからやり直す（往復の上限の確かめを含む）。届かなかった `fix` の印も往復に数える（止まる側） |
| 8 | `git ls-remote` で、作業ブランチの先端が送った SHA になったことを読み戻す。初回は、順 4 で組み立てて検査した題名と本文で PR を draft で作り、すぐに結びつきの印（`note kind=link`）を Issue と PR に書き、続けて Agent 欄（計画・実装工程（段階 5）は空、レビュー工程（段階 6）以降は `reviewer`）を書いてから、Status を `In Review` にする（[IMPL-11][impl]、[IMPL-6][impl]、[IMPL-7][impl]、[FLOW-21][flow]）。修正は、Agent 欄を `reviewer` にする（対応コメントと `fix` の印は順 7 で書いた。[FLOW-22][flow]） | 読み戻した SHA が違えば、`needs-human` を付ける（`unrecoverable`）。PR を作れなければ、実行の失敗にする。作業ブランチだけが残るので、次の実行は順 13 で `needs-human` にする（`branch-without-pr`） |

- 載せ直し（[MERGE-6][merge]）は、AI のセッションを起こさずに、進行 Bot の clone で base ブランチを作業ブランチに取り込み（`git merge`）、順 3〜8 を同じく行う。衝突したら取り込みをやめ、作業 AI の衝突の解消のセッションで解き、順 1〜8 を修正と同じく行う（対応コメントと `fix` の印を順 7 で書く）。作業 AI を起こす前に、往復の回数が上限に達していないかを確かめる（上の「作業中」の順 18）。レビュー工程（段階 6）では人の番にし、`note kind=conflict` の印付きのコメントを Issue に書く。差分の patch-id を比べて、印を付け直すか再レビューに回すかは、上の「作業中」の順 18
- 衝突の解消で、作業 AI が merge の commit の後に commit を足しても、merge の commit を作らずに衝突を解いても、`fix` の印 1 つで往復 1 回に数える。head が merge の commit 1 つだけかは確かめない（[ADR-20261022-003][adr-rounds] の決定 2）
- 進行 Bot の clone は作業ツリーを持ち、取り込み（`git merge`）に使う。取り込む前に毎回、進行 Bot の clone で動いている git のプロセスが無いことを確かめ（lock を持つ実行の中なので、あれば前の実行の残り）、残った `index.lock` を消し、取り込みの途中の状態（`MERGE_HEAD`）があれば取り込みをやめ（`git merge --abort`）、作業ツリーと index を先端にそろえる（`git reset --hard` と `git clean -ffdx`）。前の実行が取り込みの途中で落ちても、後の実行の git が失敗し続けないため。git のプロセスが残っていれば、取り込まずに実行の失敗にする
- 進行 Bot の clone の git は、ホームの個人設定とシステムの設定を読まず（`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`）、`core.hooksPath` を空のフォルダにし、署名しない（`commit.gpgsign=false`）で動かす（[SAFE-16][safety]）。載せ直しの merge の commit の作者は、投稿に使うアカウントの名前と、GitHub の noreply のアドレスにする（作業 AI の commit と同じ。「[AI のセッション][design-ai]」の「環境変数」）。手元の Mac で、人の鍵で署名した commit を送らないため
- push した実行では、push した Issue を次の実行まで進めない（上の「次の工程」）
- 順 2 で控えた SHA を、順 3〜8 のすべてで使う。途中で作業ブランチを読み直さないので、検査した commit と送る commit が同じになる

## 判定

次の工程の表の順 14〜20 で使う判定を決める。判定には、GitHub にある署名付きの印と、PR と必須チェックの状態だけを使う（[ADR-20261015-006][adr-flow] の決定 4）。

### ラウンドと往復の数え方

![ラウンドと往復の数え方][fig-rounds]

- ラウンドは、PR のレビューの 1 回。`review` の印の `round` は 1 から始め、レビューするたびに 1 増やす。欠けていたら `needs-human` にする（[IMPL-18][impl]）
- 修正か衝突の解消の後の再レビュー、進行 Bot だけの載せ直しで差分（patch-id）が変わったときの再レビュー、人の push の後の再レビューは、新しいラウンドにする。載せ直しで差分が同じときは、ラウンドを増やさず、同じ内容の印を新しい head に付け直す（[MERGE-6][merge]）
- `fix` の印の `round` は、最新の `review` の印の `round`（修正では、直した対象のラウンド）と同じにする（[IMPL-27][impl]、[MERGE-6][merge]）
- 往復の回数は、PR の有効な `fix` の印の数（作業 AI が変更を push した回数）。`fix` の印は、作業 AI の変更を push するたびに 1 つ書き、レビューの `fix` を直したとき（[IMPL-23][impl]）、CI の赤を直したとき（[IMPL-27][impl]）、載せ直しの衝突を解いたとき（[MERGE-6][merge]）のどれも 1 回に数える。`fix` の印は push の前に書くので、push が GitHub に届かなかった回の印も数える（上の「push の手順」の順 7）。届かなかった回の数えすぎは、止まる側に倒れる（[IMPL-24][impl]、[ADR-20261022-003][adr-rounds] の決定 1、決定 4）
- 進行 Bot だけで行う載せ直し（AI のセッションを起こさない）で差分が変わった再レビューと、人の push の後の再レビュー（人が GitHub の画面で base ブランチを取り込んだ後を含む）は、新しいラウンドにするが、往復に数えない。base ブランチが進んで差分が変わるたびに起こすレビューは、往復の上限でなく、1 Issue の累計の費用の上限（`limits.issueCostUsd`）で止まる
- レビュー工程（段階 6）では作業 AI が直さないので、`fix` の印が無い。段階 6 から修正工程（段階 7）に持ち越した PR は、往復を 0 回から数える
- 数える元は GitHub の `fix` の印だけで、commit の親の形も手元の記録も使わない。1 つのラウンドを、`fix` の印と載せ直しのラウンドの 2 回に数える形は無い。衝突の解消で作業 AI が merge の commit の後に commit を足しても、`fix` の印 1 つで 1 回に数える（上の「push の手順」）
- 最新のラウンドが `fix` か CI が赤で、往復の回数がすでに上限（`limits.roundTrips`）に達していれば、修正せずに `needs-human` にする（`round-limit`。[IMPL-24][impl]、[FLOW-28][flow]）。載せ直しが衝突したときも、往復の回数がすでに上限に達していれば、衝突の解消の作業 AI を起こさずに `needs-human` にする（`round-limit`。上の「作業中」の順 18）
- 往復の回数は PR の初めから数え、人が `needs-human` を外しても数え直さない（1 Issue の累計の費用と同じ。下の「stop の理由の記号」の `round-limit`、[止まった状態から戻す手順][flow]）
- 修正工程（段階 7）の記録の「AI が直した回数（往復の回数）」（[IMPL-25][impl]、[段階の表][setup]）は、この往復の回数と同じ数にし、2 つの数に分けない。衝突の解消の回数を分けて見たいときは、手元の記録のセッションの名前（衝突の解消は `rebase-pr-<PR の番号>`。「[AI のセッション][design-ai]」の「セッションの名前」）で分ける（[ADR-20261022-003][adr-rounds] の決定 1）

| ラウンド | 起きたこと | 往復の回数 |
| --- | --- | --- |
| 1 | 最初のレビューが `fix` を返し、作業 AI が直す | 0 回 |
| 2 | 修正の後の再レビューが `fix` を返し、作業 AI が直す | 1 回 |
| 3 | 修正の後の再レビューが `pass` を返す。base ブランチが進み、進行 Bot だけの載せ直しで差分が変わる | 2 回 |
| 4 | 載せ直しの後の再レビューが `fix` を返す。作業 AI が直す前に、人が push する | 2 回。進行 Bot だけの載せ直しは数えない |
| 5 | 人の push の後の再レビューが `pass` を返す。base ブランチが進み、載せ直しが衝突して、作業 AI が衝突を解く | 2 回。人の push は数えない |
| 6 | 衝突の解消の後の再レビューが `fix` を返す | 3 回。衝突の解消を 1 回に数える。上限（3 回）に達しているので、修正せずに `needs-human` にする |

表の往復の回数は、そのラウンドのレビューの時点の `fix` の印の数。

### 収束の判定

![収束の判定][fig-convergence]

PR が収束した（`Ready to Merge` に進めてよい）かを、次の順に確かめる（[FLOW-23][flow]、[IMPL-27][impl]）。

| 順 | 確かめること | 当てはまらないとき |
| --- | --- | --- |
| 1 | 最新の `review` の印の `head` が、PR の head と同じ | その head はまだレビューしていない。次の工程の表の順 14（レビュー）に進む |
| 2 | 最新の `review` の印の `verdict` が `pass` | 順 15（修正）に進む |
| 3 | 必須チェック（`checks.required`）のすべてが、PR の head に対して `success` | 結果ごとの扱いは IMPL-27 の表のとおり。`action_required` は `needs-human`、`failure` と `timed_out` は修正、まだ無いか動いている途中なら待つ、`cancelled` などは待って `limits.ciStaleHours` を過ぎたら `needs-human`（[IMPL-27][impl]） |

- 必須チェックは、チェックの名前・チェックを出した app・base 側のワークフローのパスの 3 つがすべて一致するものだけを数え、同じ名前が複数あれば最新の 1 件を採る。一致するチェックが無ければ、まだ無いものとして待つ（[IMPL-27][impl]、[ADR-20261016-001][adr-pr]）
- 3 つとも満たせば収束。1 回目のレビューから `pass` なら、1 回で収束する（[IMPL-27][impl]）

### マージの判定

![マージの判定][fig-merge]

Status が `Ready to Merge` の PR を、マージしてよいかで判定する（[MERGE-2、MERGE-3][merge]）。判定の時点で CI が緑でなければ、判定を次の実行に回し、印を書かない（`merge=human` にもしない。[MERGE-3][merge]）。
CI が緑なら、次の条件をすべて確かめ、満たさない条件の記号を `merge` の印の `reasons` に書く。

| 記号（`reasons`） | 満たさない条件 | 確かめ方 |
| --- | --- | --- |
| `not-bot-pr` | dev-autopilot が作った PR でない | PR に、進行 Bot の署名付きの結びつきの印が無い（[MERGE-2][merge]、[IMPL-6][impl]） |
| `base` | 向き先が base ブランチでない（`release/*` ブランチと `main` 向けの PR を含む） | PR の向き先の名前を、マシンの設定の `baseBranch` と比べる（[MERGE-2、MERGE-4][merge]） |
| `not-converged` | 収束していない | 上の「収束の判定」を、判定の時点でもう一度確かめる（[MERGE-2][merge]） |
| `leak` | 漏えいの検査に引っかかった | 判定の時点で、最終の head の diff 全体に検査を掛け直す（[IMPL-15][impl]） |
| `dropped-high` | 批評 AI が 🔴 を再現できなかったラウンドがある | 最新の `review` の印の `dropped_high`（PR ごとの累計）が 1 以上。数え方は「[AI のセッション][design-ai]」の「批評 AI」の統合の規則（[IMPL-22][impl]） |
| `path` | 許可一覧（`merge.allowPaths`）に無いパスを触った | 進行 Bot の clone で取った `git diff --raw <base>...<head>` の一覧と比べる（[MERGE-2、MERGE-4][merge]） |
| `diff-kind` | 状態が追加（A）か変更（M）でないもの（削除・改名・コピー・種類の変更など）がある。または、mode が `100644` でない | 同じ `git diff --raw` の状態と mode を見る。状態は、許す 2 つ（A と M）で照らし、並べていない状態も通さない（[MERGE-2、MERGE-4][merge]） |
| `policy` | 方針に係るパス（`merge.policyPaths`）を触った | 同じ `git diff --raw` の一覧と比べる（[MERGE-2][merge]） |

- 当てはまった記号をすべて `,` でつないで `reasons` に書く。1 つも無ければ `merge=ready`、1 つでもあれば `merge=human` にする（[MERGE-3][merge]）
- `merge=ready` にするのは、1 回の実行で 1 件まで。2 件目以降の、`merge=ready` になるはずの PR は、判定を次の実行に回し、印を書かない。次の実行でも、1 件目が開いていてマージされていなければ、2 件目以降の `merge=ready` は書かない。`merge=human` の判定は 1 件の上限に数えず、書く。1 件目が閉じられたら、待つのをやめる（[MERGE-5][merge]、[ADR-20261016-001][adr-pr] の決定 2）
- 修正工程（段階 7）は、判定を手元の記録にだけ残し、印を書かない。マージ判定工程（段階 8）から印を書く（[FLOW-24][flow]）。計画・実装工程（段階 5）とレビュー工程（段階 6）では判定しない

### 同じ指摘の再発の判定

![同じ指摘の再発の判定][fig-repeat]

AI の変更の後のラウンド（作業 AI が直すか衝突を解いた後のラウンド）で、前のラウンドと同じ指摘がもう一度出たかを、`review` の印の `findings` で見分ける（[ADR-20261019-001][adr-repeat]、[ADR-20261022-003][adr-rounds] の決定 3、[IMPL-24][impl]）。

- 進行 Bot は、`review` の印を書く前に、批評 AI の統合の後に残った 🔴 🟡 の指摘ごとに ID を計算し、`findings` に書く。ID は「軸」「正規化した見出し」「ファイルのパス」を改行でつないだ文字列の SHA-256 の先頭 8 文字（16 進）。正規化は、Unicode の NFKC にそろえ、先頭の重要度の記号と空白を除き、英字を小文字にする（[ADR-20261019-001][adr-repeat] の決定 1）
- AI の変更の後のラウンドの `findings` の ID が、前のどれかのラウンド（判定しないラウンドを含む）の `findings` にもあれば、同じ指摘の再発とする。間が空いていても数える。同じラウンドの中の重複は数えない（[ADR-20261019-001][adr-repeat] の決定 2）
- AI の変更の後のラウンドは、1 つ前のラウンドに有効な `fix` の印があり、ラウンドの `review` の印の `head` が、次のどちらかに当たるラウンド
  - 1 つ前のラウンドの `fix` の印の `head` と同じ
  - 1 つ前のラウンドの `fix` の印の `head` を 1 つ目の親に、base ブランチの commit を 2 つ目の親に持つ merge の commit。修正の後に進行 Bot が依存の載せ直しを行ったラウンド（上の「作業中」の表の前の確かめ）に当たる。merge の commit の作者は問わず、人が base ブランチを取り込んだ merge の commit も、形が同じなら判定する。base ブランチを取り込んだだけの merge の commit では、レビューする変更が作業 AI の変更のままのため
- 次のラウンドでは判定しない
  - PR の最初のラウンド
  - 進行 Bot だけの載せ直しで差分が変わったラウンド（1 つ前のラウンドに `fix` の印が無い）
  - 人の push の後のラウンド（head が上の 2 つの形に当たらない）。人が直す番では、同じ指摘の再発でも止めない（[IMPL-24][impl]）
  - レビュー工程（段階 6）のラウンドと、段階 6 から持ち越した PR の、作業 AI が直す前のラウンド
- 判定しないラウンドの `review` の印にも、`findings` を書く。後のラウンドの比べる相手になるため
- head の形の見分けは、同じ指摘の再発を判定するかにだけ使い、往復の回数（上の「ラウンドと往復の数え方」）には使わない。形を見誤っても、往復の上限は `fix` の印で効く
- 同じ指摘の再発なら、往復の上限と同じく、修正せずに Status を `Blocked` にして `needs-human` を付け（`repeated-finding`）、再び出た指摘の見出しと、出たラウンドを Issue にコメントする（[IMPL-24][impl]、[FLOW-28][flow]）

| ラウンド | `findings`（例） | 判定 |
| --- | --- | --- |
| 1 | A、B | 前のラウンドが無い。修正に進む |
| 2 | C | A も B も出ていない。修正に進む |
| 3 | A | A はラウンド 1 にも出ている。同じ指摘の再発として `needs-human` にする |

表の例は、ラウンド 2 と 3 がどちらも AI の変更の後のラウンドのとき。ラウンド 3 が進行 Bot だけの載せ直しか人の push の後のラウンドなら、判定しない（ラウンド 3 の `findings` は、後のラウンドの比べる相手になる）。

## 印の種類

UNDECIDED-39（進行 Bot のほかのコメントに付ける印の種類）を決め、`stop` の印の理由の記号をそろえる。
印の形と欄の正本は[印と固定の見出しの一覧][markers]で、基本設計は、どのコメントにどの印を付けるかと、記号の一覧を決める。進行 Bot が投稿するコメントは、すべて署名付きの印を 1 つ持つ（[印と固定の見出しの一覧][markers]）。

### 印の署名

印の `sig`（[IMPL-20][impl] の (c)）は、HMAC-SHA256 で作る。署名を確かめる鍵は一覧で持ち、進行中の Issue と着手の前の Issue があっても替えられる（[ADR-20261021-004][adr-marker-keys]）。

- 鍵の一覧：秘密の置き場の `marker-signing-keys`（1 行に 1 つ、32 バイトの乱数を base64 で書いたもの。[設定][design-settings]の「秘密の置き場のファイル」）。人が作り（初めて導入するときは、`setup` が作り方のコマンドを示す。例：`openssl rand -base64 32`）、進行 Bot だけが読む。AI のセッションには渡さない。HMAC は書く鍵と確かめる鍵が同じで、確かめにだけ使う鍵でも印を作れるので、どの行の鍵も同じに秘密として扱う。動かすマシンを替えるときは、作り直さずに前のマシンから一覧を写す
- 書く鍵と確かめる鍵：印を書くときは、一覧の先頭の行の鍵で署名する。印を確かめるときは、一覧の鍵を先頭の行から順に試し、どれかで通れば、署名の条件を満たすとする。一覧に無い鍵で書いた印は、署名の条件を満たさない。印に、どの鍵で書いたかを示す欄は持たない（署名の対象は変えない。[ADR-20261015-004][adr-markers] の決定 1）
- 鍵の読み方：行ごとに末尾の空白と改行を除き、空の行は読まない。各行の base64 を解いた 32 バイトを HMAC の鍵にする。解けない行か、解いた値が 32 バイトでない行が 1 つでもあれば、点検を fail にする。鍵の行が 1 つも無いとき（空のファイル）も、点検を fail にする。人がエディタで保存し直して改行が変わっても鍵が変わらず、短い文字列の弱い鍵で署名しないため
- 署名する文字列：1 行目に印の種類、2 行目にリポ（`owner/repo`）、3 行目に置き場の Issue か PR の番号、4 行目から `sig` 以外の欄を `<欄>=<値>` の形で欄の名前の順（Unicode の符号の順）に 1 行ずつ並べ、改行（LF）でつなぐ（種類・リポ・番号は欄として書かず、署名にだけ入れる。[ADR-20261015-004][adr-markers] の決定 1）
- `sig` の値：HMAC-SHA256 の結果の 16 進の 64 文字
- 点検は、投稿に使うアカウントが書いた最新の未編集の印の署名を一覧の鍵で確かめ、どの鍵でも通らなければ warn にする。マシンを替えたときの鍵の取り違えを、人に知らせるため。fail にしないのは、下の「鍵を替えるとき」の、鍵が漏れたときの順 3 の実行で、外した鍵の印のある Issue と PR を止めるため。一覧に 2 つ以上の鍵があるときは、先頭でない鍵でだけ確かめられた印が残る開いた Issue と PR を warn に出す（[設定][design-settings]の「`check` が設定について確かめること」、「[導入と点検][design-setup]」の「組と回数」）

#### 鍵を替えるとき

鍵は、進行中の Issue の有無を問わず、いつでも替えてよい（[ADR-20261021-004][adr-marker-keys] の決定 2）。鍵が漏れていないときは、次の順に替える。

| 順 | する人 | すること |
| --- | --- | --- |
| 1 | 人 | 新しい鍵を作り、一覧の先頭の行に足す。前の鍵は、2 行目より後に残す |
| 2 | 進行 Bot | 次の実行から、新しい鍵で書き、一覧のどれかの鍵で確かめる（進行 Bot は、起動したときに秘密を読む。[ADR-20261015-001][adr-read] の決定 2） |
| 3 | 進行 Bot | 点検の warn に、先頭でない鍵でだけ確かめられた印が残る開いた Issue と PR の番号を出す。残りが無くなったら、前の鍵を外してよいことを warn に出す（出し方は「[導入と点検][design-setup]」の「組と回数」） |
| 4 | 人 | 前の鍵でだけ確かめられる印が残る開いた Issue と PR が無くなったら、前の鍵を一覧から外す。外し忘れて、印を作れる鍵が多いまま残らないため |

- 動かすマシンを替えて、新しいマシンで鍵を作るときも、鍵を替えたものとして同じ順に従う（前の鍵を一覧に残す。「[導入と点検][design-setup]」の「動かすマシンを替えるとき」）
- 承認を待つ Issue が長く開いていて急ぐときは、残りがあっても前の鍵を外してよい。前の鍵の印のある開いた Issue と PR は `marker-invalid` で止まる（結びつきの印が前の鍵の PR も、次の工程の順 4 の `unlinked-pr` でなく、順 5 で止まる）ので、人が「[止まった状態から戻す手順][flow]」の、鍵が漏れたときの手順で戻す（受け入れからやり直す）。前の鍵の印を数えない印として続けると、無いものとして読んだ印の種類によって、`approved-before-intake`・`brief-changed`・`unlinked-pr` などのほかの止め方に当たるため（上の「数えない無効な印」）

鍵が漏れたとき（漏れたかもしれないときを含む）は、漏れた鍵を確かめにも使わない。人が次の順に行う（[ADR-20261021-004][adr-marker-keys] の決定 3）。

| 順 | すること |
| --- | --- |
| 1 | 全体の止める合図（[ADR-20261017-007][adr-stop]）を `stop` にする。鍵の一覧はマシンの中にあり、替え終わるまでに時間がかかりうるので、替え終わるまでの間に、漏れた鍵で作られた印を読まないため |
| 2 | 新しい鍵を作って一覧の先頭の行に足し、ほかの鍵をすべて一覧から外す（新しい鍵だけを残す）。鍵の一覧は 1 つのファイルにあるので、漏れた鍵のほかの鍵も、漏れたかもしれない鍵として扱う（[ADR-20261021-004][adr-marker-keys] の決定 3 の「漏れたかもしれないとき」）。漏れた鍵は、確かめにも残さない（漏れた鍵を持つ人は、確かめの通る印を作れるため）。開いた Issue と PR の進行 Bot の印がすべて無効になり、人が戻した後は数えない印になるので、どの Issue も、鍵が漏れたときの戻し方で受け入れからやり直せる |
| 3 | 全体の止める合図を `run` に戻す。外した鍵で署名した印が残る開いた Issue と PR は、次の実行で `marker-invalid` で止まる（次の工程の順 5。結びつきの印が外した鍵の PR も、順 4 の `unlinked-pr` でなく、順 5 で止まる） |
| 4 | 止まった Issue ごとに、印のあるコメントと GitHub の状態（PR の差分、作業ブランチ）を確かめ、「[止まった状態から戻す手順][flow]」の、鍵が漏れたときの手順で戻す（受け入れからやり直す） |

- 秘密の置き場のほかの秘密（PAT かアプリの秘密鍵、deploy key）を替えるかは、漏れた経路を見て人が決める

### 印が付く順

![印が付く順][fig-markers]

正常な順で、Issue と PR のコメントに付く印。

| 順 | 印 | 置き場 | 書くとき |
| --- | --- | --- | --- |
| 1 | `intake` | Issue | 受け入れの下書きを投稿するとき（次の工程の順 9） |
| 2 | `intake-final` | Issue | 人が `agent-ready` を付けた後、承認を確定するとき（順 10） |
| 3 | `plan` | Issue | 計画を投稿するとき（順 12） |
| 4 | `note kind=link` | Issue と PR | PR を作った直後に、両方に書く（順 13。[IMPL-6][impl]） |
| 5 | `review` | PR | ラウンドごとに、レビューの結果を投稿するとき（順 14。レビュー工程（段階 6）から） |
| 6 | `fix` | PR | 修正か衝突の解消を push する前（順 15 と順 18。`head` は送る SHA。修正工程（段階 7）から） |
| 7 | `merge` | PR | マージの判定のとき（順 19。マージ判定工程（段階 8）から） |

このほかに、`note` の印を、待つとき・重なりを警告するとき・催促するとき・止めるとき・モデルを上げたとき・🟢 が重複したとき・載せ直しの衝突を人の番にしたときに書く（下の「note の種類」）。

### note の種類

| `kind` | 書くとき | 置き場 | 欄 | 1 回だけ書く判定 |
| --- | --- | --- | --- | --- |
| `wait` | 依存の相手が閉じていないので待つとき（[FLOW-10][flow]） | Issue | — | 同じ `kind` の有効な印があれば書かない |
| `overlap` | 触る範囲が、ほかの進行中の PR と重なったとき。作業 AI の commit を取り込んだとき（「push の手順」の 2）に、変更ファイルの一覧をほかの進行中の PR の変更ファイルと比べる（[FLOW-8][flow]） | Issue | — | 同じ `kind` の有効な印があれば書かない |
| `remind` | `merge=ready` の PR が、マージも「判定と違う判断」のコメントも無いまま日数を過ぎたとき（[MERGE-3][merge]） | PR | — | 同じ `kind` の有効な印があれば書かない |
| `link` | PR を作った直後（[IMPL-6][impl]） | Issue と PR | Issue には `pr=<PR の番号>`、PR には `issue=<Issue の番号>` | 同じ番号の有効な印があれば書かない |
| `stop` | `needs-human` を付けるとき | `needs-human` を付けた Issue と PR | `reason=<記号>`（下の「stop の理由の記号」）。`marker-invalid` は、書く先の無効だった印のコメントの ID を `comments=<ID>,<ID>,...` で持つ（次の工程の順 5） | 1 回だけにしない。`needs-human` を付けた先（Issue と PR）ごとに書く（次の工程の「止める・待つ・触らない」の表の下の箇条）。閉じた Issue の作業場所の残骸（`workspace-residue`）だけは、同じフォルダの組を書いた有効な印があれば書かない（下の箇条） |
| `raise` | 作業 AI のモデルを `sonnet` から `opus` に上げたとき（[IMPL-25][impl]） | Issue | `from=<別名>`、`to=<別名>` | 同じ `kind` の有効な印があれば書かない（1 つの Issue で上げるのは 1 回） |
| `duplicate` | 🟢 を Issue にするときに、同じ見出しの開いている Issue があり、新しく作らずに PR 番号を足すとき（[IMPL-26][impl]） | すでにある 🟢 の Issue | `pr=<PR の番号>` | 同じ番号の有効な印があれば書かない |
| `conflict` | レビュー工程（段階 6）で、載せ直し（次の工程の順 18）が衝突し、人の番にしたとき（[MERGE-6][merge]） | Issue | `head=<PR の head の SHA>` | 同じ `head` の有効な印があれば書かない（base が先に進んでいる間、毎回の実行で載せ直しを試して同じコメントを書かないため） |

- `raise` と `duplicate` は、ほかの種類（`stop` と `link`）に寄せず、別の種類にする（要件の印の一覧の `note` の `kind`。[印と固定の見出しの一覧][markers]）。`raise` を `stop` に寄せると止まったと読まれる。`duplicate` を `link` に寄せると、PR と Issue の結びつき（[IMPL-6][impl] の判定に使う）を誤る
- `stop` だけは、1 回だけにせず、`needs-human` を付けた先ごとに書く。`needs-human` の Issue は進行 Bot が触らないので、同じ理由で重ねて書くことは無い。人が `needs-human` を外した後に、同じ理由で再び止まったとき、前の印を見て書かないと、今回止まったことが人に伝わらないため。例外は、閉じた Issue の作業場所の残骸（`workspace-residue`）で、`needs-human` の有無を問わず、同じフォルダの組を書いた `workspace-residue` の有効な stop の印が Issue に無いときだけ、1 回書く（下の「作業場所の残骸」の表の下の箇条）

### stop の理由の記号

`needs-human` を付けるときに書く `note kind=stop` の `reason` の一覧。止まる遷移（[FLOW-28、FLOW-29][flow]）の契機ごとに 1 つ決める。

| `reason` | 止めた契機 |
| --- | --- |
| `round-limit` | 往復の回数（`fix` の印の数）が上限に達した。修正（次の工程の順 15）と衝突の解消（順 18）の作業 AI を起こす前に確かめる（[IMPL-24][impl]、[ADR-20261022-003][adr-rounds]）。stop のコメントに、往復の回数は PR の初めから数え、`needs-human` を外しても数え直さないので、何もせずに外すと次の実行でまた止まることと、人がすること（人が直して push してから戻す。人の push の後の再レビューは往復に数えないが、再レビューが `fix` を返すと、往復の回数は上限のままなので、また止まる。作業 AI に続けさせるなら、リポの設定の `limits.roundTrips` を上げる PR をマージしてから戻す。[止まった状態から戻す手順][flow]）を書く |
| `repeated-finding` | 同じ指摘の再発（直したはずの指摘が、AI の変更の後のラウンドで再び出た。[IMPL-24][impl]、[ADR-20261019-001][adr-repeat]、[ADR-20261022-003][adr-rounds]）。stop のコメントに、再び出た指摘の見出しと出たラウンド（上の「同じ指摘の再発の判定」）、`needs-human` を外しても同じラウンドの同じ判定で次の実行でまた止まることと、人がすること（人が直して push してから戻す。人の push の後のラウンドでは、同じ指摘の再発を判定しない。`limits.roundTrips` を上げても、同じ指摘の再発の止まり方は変わらない。[止まった状態から戻す手順][flow]）を書く |
| `review-too-long` | レビューのコメントが、🟢 の失敗シナリオと推奨をすべて省いても 60,000 文字を超える（[IMPL-17][impl]、[AI のセッション][design-ai]の「レビューのコメントの形」） |
| `adr-required` | 作業 AI が、ADR の起票か規約の正典の変更が要ると返した（[IMPL-8][impl]） |
| `retry-limit` | 同じ Issue で実行の失敗が続き、回数の上限に達した（[IMPL-14][impl]） |
| `usage-limit` | 1 Issue の累計の費用に、次のセッションの費用の上限を足すと、上限を超える（[IMPL-14][impl]、[AI のセッション][design-ai]の「止め方と利用枠の数え方」）。stop のコメントに、人がすること（続けるなら、リポの設定の `limits.issueCostUsd` を上げる PR をマージしてから、Status を戻し、`needs-human` を外す。上げないなら、Issue を閉じるか、小さい Issue に分けて元の Issue を閉じる。[止まった状態から戻す手順][flow]）と、累計は Issue の初めから数え、`needs-human` を外しても数え直さないので、上限を上げずに外すと次のセッションの前にまた止まることを書く |
| `session-not-stopped` | AI のセッションを止めた後、コマンドの残りが止まったと確かめられない（[IMPL-14][impl]） |
| `leak` | 漏えいの検査に引っかかった（push の前、計画を投稿する前など。[IMPL-15][impl]） |
| `blocked-path` | diff が、push しないパスに触れている（[IMPL-15][impl]） |
| `not-fast-forward` | push する SHA が、GitHub の作業ブランチの今の先端（まだ無ければ、作業場所を作ったときに控えた base の SHA）の子孫でない（[IMPL-15][impl]、[SAFE-13][safety]、上の「push の手順」） |
| `no-new-commit` | 作業 AI が作業を終えた（`done`）と返したのに、新しい commit が無い（実装・修正・衝突の解消。上の「push の手順」の順 2） |
| `plan-blocked-path` | 計画が変える見込みのパスが、push しないパスに当たる（[IMPL-10][impl]、[ADR-20261019-004][adr-policy]） |
| `approved-before-intake` | 受け入れの下書きの前に、`agent-ready` が付いた（[TEXT-12][text]。人が下書きを読む前の承認を通さない） |
| `brief-changed` | 渡す文のハッシュが、承認したときと違う（[TEXT-4][text]） |
| `brief-edited-after-approval` | 渡す文（作業指示コメントか、直した下書き）の投稿か最後の編集が、`agent-ready` を付けた時刻より後（[TEXT-10][text]） |
| `brief-sensitive` | 渡す文に、事業データか認証情報の形が混じっている（承認の確定で確かめる。[TEXT-7][text]） |
| `quarantine` | 受け入れの検疫で見つかった。受付 AI が返した文の欄で見つかった。見つかった Issue に `## 作業指示` のコメントが無いまま `agent-ready` が付いた（[TEXT-12][text]）。承認の確定か、AI に渡す直前か、AI の文を GitHub に書く前（計画、PR の題名と本文、対応コメント、レビューのコメント、🟢 から起票する Issue の本文など）の検疫で見つかった（[TEXT-11][text]、[AI のセッション][design-ai]の「起動の前の確かめ」と「共通の決まり」の表） |
| `issue-changed` | 作業中に、Issue が閉じられた・移された・`agent-ready` かマイルストーンが外された（[TEXT-8][text]）。別のリポに移されたときは、結びつく PR に書く（次の工程の順 3） |
| `permission` | `agent-ready` を付けた人か、下書きのコメントか読む作業指示コメントを編集した人が push 未満（[TEXT-10][text]、[FLOW-29][flow]）。push 未満の人が書いた作業指示コメントは読まないので、止めない |
| `unauthorized-resume` | push 未満の人が `needs-human` を外した（[TEXT-10][text]） |
| `unlinked-pr` | ブランチ名が一致するのに、結びつきの印が無い PR がある。PR を作った直後、結びつきの印を書く前に切れたときも当たる（作者を問わない。[IMPL-6][impl]、[ADR-20261016-001][adr-pr] の決定 3）。無効な結びつきの印を持つ PR は、`marker-invalid` で止める（次の工程の順 4）。stop のコメントに、人がすること（PR の中身を確かめてから、PR を閉じ、作業ブランチを消し、Status を `Todo` に戻してから、最後に `needs-human` を外す。[止まった状態から戻す手順][flow]）を書く。人が戻すと、手順の中で閉じた印の無い PR は人が戻した時刻より前に閉じたので、進行 Bot は止めずに計画からやり直す（次の工程の順 4、[ADR-20261022-005][adr-unlink] の決定 1） |
| `pr-closed` | 結びつく PR が、マージされずに閉じられた（[IMPL-6][impl]）。stop のコメントに、人がすること（作業ブランチの中身を確かめて消し、Status を `Todo` に戻してから、最後に `needs-human` を外す。[止まった状態から戻す手順][flow]）と、人が戻した後に進行 Bot が消すフォルダ（閉じた PR の番号の名前のセッションのフォルダ）を書く（下の「作業場所の残骸」）。人が戻すと、閉じた PR は人が戻した時刻より前に閉じたので、進行 Bot は閉じた PR を結びつきから外し、計画からやり直す（次の工程の順 4、[ADR-20261022-005][adr-unlink] の決定 1） |
| `branch-without-pr` | 計画の印があり、結びつく PR が無いのに、作業ブランチが origin にある（次の工程の順 13）。push の後、PR を作る前に切れたときも当たる。人は作業ブランチの中身を確かめて消してから戻す |
| `marker-invalid` | 進行 Bot の印が、未編集（`intake` の印には掛けない）か署名の条件を満たさない。または `review` の印の `round` が欠けている（[IMPL-20、IMPL-18][impl]）。止めた理由の印の `comments=` に、書く先の無効だった印のコメントの ID を挙げる（`round` の欠けだけのときと、書く先に無効な印が無いときは持たない）。人が `needs-human` を外した後は、挙げた印を数えない（上の「数えない無効な印」。[ADR-20261021-004][adr-marker-keys] の決定 4） |
| `ci-action-required` | CI のワークフローの実行に、人の承認が要る（[IMPL-27][impl]） |
| `ci-stale` | CI の結果が、取り消しなどのまま時間を過ぎても変わらない（[IMPL-27][impl]） |
| `workspace-residue` | Issue に紐づく作業場所の残骸がある。stop のコメントに、消すフォルダの組と消す順を書く（下の「作業場所の残骸」） |
| `workspace-tampered` | 作業場所の `commondir` か `gitdir` が、作ったときの値と違う。または、取り込みの fetch が objects の検査で失敗した（[SAFE-12][safety]、[ADR-20261013-001][adr-workspace]、上の「push の手順」）。作業場所の残骸の見分けで見つけたときは、stop のコメントに、消すフォルダの組と消す順を書く（下の「作業場所の残骸」） |
| `local-settings` | AI のセッションの作業場所の worktree に、`.claude/settings.local.json` か、どのフォルダかに `CLAUDE.local.md` がある（FACT-56、FACT-60、[SAFE-2][safety] の (a)、[AI のセッション][design-ai]の「起動の前の確かめ」の順 9）。作業フォルダの上のフォルダの `CLAUDE.local.md` は、Issue に付けずに実行を終える |
| `draft-format` | 承認の確定で、受け入れの下書きの依存とマイルストーンの候補の 2 行を決まった形で読めないか、確定するマイルストーンが無い（下書きの行が `なし`、`quarantine=found` の Issue で人が Issue にマイルストーンを付けていない）。または、渡す文が空（[AI のセッション][design-ai]の「コメントの形」） |
| `multiple-instructions` | push 以上の人の作業指示コメントが 2 つ以上ある（承認の確定、着手、対応ループの各回。[TEXT-12][text]、[ADR-20261021-003][adr-reapprove]） |
| `settings-tampered` | セッションの安全設定のファイルが、作ったときのハッシュと違う（起動の直前か、セッションの後。[SAFE-2][safety] の (e)、[AI のセッション][design-ai]の「セッションごとの安全設定」） |
| `records-missing` | 着手した Issue の手元の記録が無い（[運用の規則][flow]。見分け方は「[AI のセッション][design-ai]」の「起動の前の確かめ」） |
| `unrecoverable` | GitHub の状態から、次の工程を決められない（次の工程の表の順 21。[運用の規則][flow]）。または、push した後に読み戻した作業ブランチの先端が違う |
| `unexpected-status` | Status が、印と PR から決まる値と違い、人が戻す手順にも当たらない（[SAFE-4][safety]） |

## 作業場所の残骸

UNDECIDED-27（作業場所の残骸の決め方）を決める。セッションのフォルダ（`<置き場>/sessions/<セッションの名前>/`）は、同じ名前で作り直すか片付けるまで残るので、作業中の Issue のフォルダがあるのは普通の状態（[ADR-20261013-001][adr-workspace]）。
セッションの名前は、役と、Issue か PR の番号を略さずに書く（例：`work-issue-<番号>`、`review-pr-<番号>-round-<ラウンド>-<軸>`。役ごとの名前の一覧は「[AI のセッション][design-ai]」の「セッションの名前」）。進行 Bot は、名前から役と番号を読み、次の表で見分ける。

![作業場所の残骸の見分け方][fig-residue]

| フォルダ | 扱い |
| --- | --- |
| 名前から Issue か PR を引け、その Issue が設定した Project にあり、作業中（閉じておらず、結びつく PR がマージも閉じもされていない） | 普通の状態。作り直すか片付けるまで残す（[ADR-20261013-001][adr-workspace]） |
| 名前から引けた PR（Issue の名前のフォルダは、結びつく PR）がマージされた | 片付け（次の工程の順 1）で消す。片付けが途中で止まって残ったものも、次の実行の片付けで消す（[FLOW-27][flow]、[MERGE-7][merge]） |
| 名前から引けた PR が、マージされずに閉じられ、閉じた時刻が、結びついていた Issue を人が戻した時刻（上の「戻した Issue のやり直し」）より前 | 片付けと同じに消す（消す前に `commondir` と `gitdir` を確かめる。違えば下の `workspace-tampered` の行）。人が `pr-closed` の stop のコメント（戻した後に消すフォルダを書いてある）を読んで戻したことを、消してよい印として扱う。人が専用のマシンに入ってフォルダを消さずに済むため |
| 名前から引けた Issue が、PR がマージされないまま閉じられたか、結びつく PR がマージされずに閉じられた（人が戻す前） | Issue に紐づく残骸。消さずに Issue を `needs-human` にし（`workspace-residue`）、人が中身を確かめてから消す（消すフォルダの組と順は、表の下の箇条）。閉じた Issue に `needs-human` がすでにあれば、stop のコメントだけを、フォルダの組ごとに 1 回書く（表の下の箇条）。人が着手した Issue をやめるときは、[止まった状態から戻す手順][flow]の、着手した Issue をやめるときの手順に従う（[FLOW-29][flow]） |
| 名前の番号の Issue が別のリポに移された（REST で引いた Issue の `repository_url` が当てる先のリポでないか、GraphQL で `NOT_FOUND`。上の「状態の組み立て」。FACT-66） | Issue に紐づく残骸として、消さずに、移した Issue の結びつく PR（PR の結びつきの印から引く）に `needs-human` を付ける（次の工程の順 3 の `issue-changed` と同じ。PR に `needs-human` があれば何もしない）。人が中身を確かめてから消す。結びつく PR が無ければ、下の「引けない」の行と同じ |
| 消す前に読んだ `commondir` か `gitdir` が、作ったときの値（作業場所のパスから決まる値）と違う | 消さずに Issue を `needs-human` にし（`workspace-tampered`）、`check` で warn にする。人が中身を確かめてから消す（消すフォルダの組と順は、表の下の箇条。[ADR-20261013-001][adr-workspace]、[SAFE-12][safety]） |
| 短い一時フォルダの根（`sessionTmp.root`）の下にあり、ID が、どのセッションのフォルダの ID のファイル（`short-tmp-id.txt`）にも無い（記録を失っても、ID のファイルで組を引く） | Issue に紐づかない残骸。点検を fail にし、実行は作業に入らずに止まる。人が中身を確かめて消す（[ADR-20261017-006][adr-tmp]、[AI のセッション][design-ai]の「短い一時フォルダ」） |
| 名前から引けた Issue（PR の名前のフォルダは、結びつきの印から引いた Issue）が、当てる先のリポの Issue で、設定した Project に無い（人が Project から外した） | Issue に紐づく残骸として、消さずに、引けた Issue に `needs-human` を付ける（`workspace-residue`。Project に無いので Status は書かない）。stop のコメントに、Issue を Project に戻すか、フォルダの組を消すかを書く（[SETUP-2][setup]、[FLOW-29][flow]） |
| 名前から Issue か PR を引けない | Issue に紐づかない残骸。点検を fail にし、実行は作業に入らずに止まる。人が中身を確かめて消す（[運用の規則][flow]、[SETUP-2][setup]、[SAFE-4][safety]） |

- Issue に紐づく残骸（`workspace-residue`）と、`workspace-tampered` で止めるときは、stop のコメントと点検の結果に、消すフォルダの組（セッションの名前と、セッションのフォルダの ID のファイルにある短い一時フォルダの ID。絶対パスは GitHub に書かない）と、消す順（短い一時フォルダ、セッションのフォルダの順。「[AI のセッション][design-ai]」の「短い一時フォルダ」の順 5 と同じ）を書く。人がセッションのフォルダだけを消すと、組の短い一時フォルダが、どのセッションのフォルダの ID のファイルにも無い残骸になり、点検が fail になって全体が止まるため
- 閉じた Issue に紐づく残骸（上の表の、名前から引けた Issue が閉じられた行）の stop は、`needs-human` の有無を問わず、同じフォルダの組を書いた `workspace-residue` の有効な stop の印が Issue に無いときだけ、1 回書く。`needs-human` がある Issue には stop のコメントだけを書き、ラベルと Status は変えない。`needs-human` が無ければ、`needs-human` も付ける。閉じた Issue は次の工程の表の順 6（作業場所の残骸）まで進まない（順 2 の触らないか、順 3 の `issue-changed` が先に当たる）ので、点検（上の「1 回の実行の流れ」の順 5）の残骸の見分けで書く。人は、着手した Issue をやめるときに `needs-human` を外さずに閉じる（[止まった状態から戻す手順][flow]）ので、閉じた Issue はたいてい `needs-human` を持ち、触らない決まり（次の工程の順 2）のままでは、消すフォルダの組が人に届かないため。組ごとに 1 回なので、人が消すまでの毎回の実行で、同じコメントが増えない

進行 Bot が、名前から引けない残骸を消さないのは、何のフォルダか分からないものを消すと、人が調べる材料を失うため。作業に入らないのは、判定できない状態で作業を増やさないため（[SAFE-4][safety]）。

## 手元の記録

![手元の記録][fig-records]

進行 Bot は、記録の置き場（`paths.records`。[設定][design-settings]の「マシンの中のフォルダ」）に、実行と AI のセッションの記録を残す（[FLOW-5][flow]）。記録は、判定に使わず、上限の数え上げと、段階の出口の数え上げと、人が読むためにだけ使う（[ADR-20261015-006][adr-flow] の決定 4）。例外は 2 つで、書かずに試す間の受け入れ（上の「1 回の実行の流れ」。[ADR-20261021-002][adr-dry]）と、レビュー工程（段階 6）で比べるためのレビューを起こすか（上の「比べるためのレビューが済んだかの見分け方」。[ADR-20261021-007][adr-compare]）。AI は sandbox の中から読めず、書けない。

| `streams/<実行 ID>/<セッションの名前>.jsonl` | AI のセッション 1 回の `stream-json` | 受け取った行をそのまま残す。人のホームに会話の記録を残さないので、会話の流れを読むときはここを読む（「[AI のセッション][design-ai]」の「起動の形」の `--no-session-persistence`） |
| `writes/<実行 ID>.jsonl` | GitHub に書いた 1 件（`run.dryRun` の間は、書くつもりだった 1 件） | 書く先（Issue か PR の番号）、種類（コメント・ラベル・Project の欄・PR・push）、本文か値、実際に書いたか。受け入れの下書きと、受け入れで付ける `needs-human` では、受け入れに使った文（題名・本文・コメント）のハッシュも書く（書かずに試す間に、同じ文の間は書いたものとして扱うため） |
| `dry-run-objections.md` | 人が書く異議 | `## 異議` の見出し（上の「1 回の実行の流れ」） |
| `plan-comparisons.md` | 人が書く、直す前と後の計画の見比べ 1 件（[ADR-20261019-003][adr-replan] の決定 2） | `## 見比べ #<Issue の番号>` の見出し（下の箇条） |

- `.jsonl` のファイルは 1 行に 1 件の JSON（JSON Lines）で、後ろに足すだけにし、書き直さない。書くたびに、ファイルを閉じる前にディスクへ書き出す（電源が切れても、前の行を失わないため）。`outputs/` の `.json` は 1 つの出力契約を 1 つのファイルに書き、書き直さない
- `.jsonl` の最後の行が途中で切れていたら（書いている途中で電源が切れた）、切れた行を読まずに点検で warn に出す。途中の行が読めなければ点検を fail にする。数え上げが少なく出て、上限が効かなくなる側に倒さないため（[運用の規則][flow]）
- `dry-run-objections.md` には、`## 異議` の見出しの次の行に、書いた日（`YYYY-MM-DD`）を書く。受け入れ工程（段階 4）の出口で、数える期間に入るものだけを数えるため
- `plan-comparisons.md` には、`## 見比べ #<Issue の番号>` の見出しの次の行に書いた日（`YYYY-MM-DD`）、日の次の行に `良くなった`・`変わらない`・`悪くなった` のどれかを書く（`dry-run-objections.md` と同じ書き方）。人は、計画し直した Issue で、直す前の計画（手元の記録の `outputs/`）と投稿した計画を見比べて書く。修正工程（段階 7）を終えるときに数える（下の「段階の出口の数え方」）

### 記録の置き場のほかのファイル

| ファイル | 中身 | 書く人と消す時 |
| --- | --- | --- |
| `run.lock` | 実行の lock。JSON で、PID・起動の時刻（lock を取ったプロセスの起動の時刻。時刻帯に依らないエポック秒）・ホスト名（人が読むためだけに書き、奪うかの判定に使わない）。古い lock かの見分け方と取り方は、上の「1 回の実行の流れ」の順 2 と、表の下の「lock の取り方」 | 進行 Bot と、`setup`（プログラムの写しを作り直すときと、引数 `uninstall` のとき。「[導入と点検][design-setup]」の「プログラムの写し」と「動かすマシンを替えるとき」）だけ（人が呼ぶ intake の Skill は lock を取らない。[ADR-20261022-004][adr-intake-req] の決定 5）。lock を外すときに消す。古い lock を奪うときに退けたファイル（`run.lock.stale-<PID>`）は、奪ったプロセスが新しい lock を作った後に消す |
| `records-created.json` | 記録の目印のファイル。JSON で、作った時刻と `setup` の版 | `setup`。消さない（無ければ点検が fail にする。[運用の規則][flow]） |
| `check-request.json` | 点検の依頼。JSON で、依頼の ID、置いた時刻、待つ時間（人の `check` が読んだ `run.checkWaitMinutes` の値。進行 Bot は、リポの設定を読む前の「1 回の実行の流れ」の順 2 で、待つ時間を過ぎた依頼かを見分ける） | 人の `check` が置き、進行 Bot が結果を書いた後に消す |
| `check-result-<依頼の ID>.json` | 点検の結果。JSON で、項目ごとの fail・warn・pass | 進行 Bot。人の `check` が表示した後に消す。残ったものは、7 日を過ぎたら進行 Bot が消す |
| `run-request.json` | 手動の 1 回実行の依頼。JSON で、依頼の ID と時刻 | 人の `/dev-autopilot` が置き、進行 Bot が lock を取った後に読んで消す |
| `intake-request.json` | 受け入れの依頼。JSON で、Issue の番号、依頼の ID、置いた時刻、待つ時間（人が呼ぶ intake の Skill が読んだ `run.intakeWaitMinutes` の値） | 人が `/verify-issue` などから呼ぶ intake の Skill が置き（待つ時間の内の依頼があれば置かない）、進行 Bot が結果を書いた後に消す（読んだ依頼と ID が同じときだけ）。待つ時間を過ぎた依頼は、進行 Bot が受付 AI を起こさずに消す（「[AI のセッション][design-ai]」の「人の Skill から受け入れを呼ぶ形」） |
| `intake-result-<依頼の ID>.json` | 受け入れの依頼の結果。JSON で、検疫と漏えいの検査を通った下書きの文の欄（下書きの 4 つの欄、`planReason`、`policyReason`）と受付 AI のセッションの費用か、受付 AI を起こさなかった理由（検疫か漏えいの検査で見つかった種類と場所、止められなかったプロセスの PID とフォルダを含む） | 進行 Bot。intake の Skill が示した後に消す。残ったものは、7 日を過ぎたら進行 Bot が消す |
| `status.json` | 状態の表示（「[導入と点検][design-setup]」の「状態の表示」） | 進行 Bot が実行の終わりに書き直す |
| `dry-run-drafts.md` | 書かずに試す間の、書いたものとして扱う受け入れの下書きと、最新の実行の選定の結果。Markdown で、人がエディタで読む（上の「1 回の実行の流れ」、「[導入と点検][design-setup]」の「状態の表示」） | 進行 Bot が、`run.dryRun` が `true` の実行の終わりに書き直す。書き始めた後は読まず、書き直さない。消す時期は、ほかの記録と同じく決めない（下の「段階の出口の数え方」） |
| `launchd.out.log`、`launchd.err.log` | 定期の実行の出力（macOS） | launchd。大きくなりすぎたら人が消す |

- 動かすマシンを替えるときは、`run.lock` と依頼のファイル（`run-request.json`・`check-request.json`・`check-result-<依頼の ID>.json`・`intake-request.json`・`intake-result-<依頼の ID>.json`）を新しいマシンへ写さない（「[導入と点検][design-setup]」の「動かすマシンを替えるとき」の順 2）。前のマシンの lock と依頼を、新しいマシンの実行が読まないため
- 実行 ID と依頼の ID は、UTC の時刻と乱数の組（`YYYYMMDDTHHMMSSZ-<16 進の 4 文字>`。例：`20261020T150000Z-3fa9`）。パスに入れても困らない文字だけにする。試しのセッションの名前の `<日時>` も同じ形（`check-20261020T150000Z-3fa9`）

### 段階の出口の数え方

段階の出口と、段階で記録する値（[段階の表][setup]）は、上の記録と GitHub から、数えるときに数える。数えるための欄を別に持たない（[ADR-20261018-003][adr-raise] と同じ考え方）。

| 段階 | 数えるもの | 数える元 |
| --- | --- | --- |
| 受け入れ工程（段階 4） | 実行の回数（起こされ方が定期で、終わり方が「作業した」の実行。lock で見送った実行・起動しなかった定期の実行・点検だけの実行・受け入れの依頼の実行・合図で止めた実行・設定を読めずに止めた実行・GitHub を読めずに止めた実行は数えない）、投稿ありの実行 | `runs.jsonl`、`writes/` |
| 受け入れ工程（段階 4） | 人が `## 異議` の見出しで書いた回数 | Issue のコメントと `dry-run-objections.md` |
| 受け入れ工程（段階 4） | 方針に係る要望の判定と、人が `agent-ready` を付けたか（[ADR-20261019-004][adr-policy]） | `outputs/` の受付 AI、Issue の timeline |
| 受け入れ工程（段階 4） | 受け入れた件数と、マイルストーンの候補を人が直した件数（[ADR-20261015-003][adr-intake] の確認方法）。人が下書きを直した件数を、コラボレータと外の人の Issue に分けて（[ADR-20261016-002][adr-draft] の確認方法） | `writes/` の下書き、Issue のコメントの編集の記録（`userContentEdits`） |
| 受け入れ工程（段階 4）と計画・実装工程（段階 5） | 検疫で URL によって止まった回数。GitHub の添付の URL（FACT-69）で止まった回数を分けて数える（[ADR-20261022-001][adr-url] の確認方法と影響） | `runs.jsonl` の Issue ごとの結果（検疫で見つかった種類）、受け入れの下書きの「検疫の結果」 |
| 計画・実装工程（段階 5） | 人が手直しせずにマージした PR（手直しは、人が PR に commit を足したか、close して作り直したこと） | PR の commit の作者、閉じた PR |
| 計画・実装工程（段階 5） | `plan=` の判定への異議、`fable` にした計画と `opus` の計画の違い、自己申告で捨てた計画 | `outputs/` の受付 AI と計画 AI、Issue のコメント |
| 計画・実装工程（段階 5）から修正工程（段階 7） | 計画のレビューの結果と、計画し直したこと。人が止めた計画（[ADR-20261018-004][adr-planrev] の確認方法。計画を投稿した後で、結びつく PR を作る前に止めたものだけ。上の「置くもの」の `runs.jsonl`。毎回の実行で重なるので、計画の印ごとに 1 件として数える）と、人の見比べの結果（[ADR-20261019-003][adr-replan] の確認方法） | `outputs/` の計画のレビューと、直す前の計画、`runs.jsonl` の Issue ごとの結果（人が止めた計画）、`plan-comparisons.md` |
| 計画・実装工程（段階 5）から修正工程（段階 7） | 作業 AI の最初の実装のモデルと、Issue の種類（作業ブランチの型）ごとの結果 | `sessions.jsonl` の作業 AI、`review` の印、PR |
| レビュー工程（段階 6） | 一致率と却下率、`opus` と `fable` の比べ（比べのセッションの失敗の数と終わり方、`opus` と `fable` の利用枠を含む。[ADR-20261021-007][adr-compare] の決定 3）、見落としの軸の 2 つの数（人の 🔴 🟡 のうち、3 つの軸が見落として見落としの軸が見つけたものの数と、見落としの軸だけが出して人が出さなかった 🔴 🟡 の数。[段階の表][setup]） | `outputs/` のレビュー AI（3 つの軸、比べるための実行、見落としの軸）、`sessions.jsonl` の終わりの行（3 つの軸と比べのセッションの終わり方と費用）、人のレビューの結果、`## 却下` のコメント |
| 修正工程（段階 7） | 往復の回数（上の「ラウンドと往復の数え方」の数え方。衝突の解消の回数は、作業 AI のセッションの名前で分けて見る）、`opus` に上げた件数、上げた後に Ready to Merge まで進んだ件数。`round-limit` と `repeated-finding` で止めた件数と、止めたときの往復の回数とラウンド（作業 AI が直す前に止まった PR が無いかを人が確かめる。[ADR-20261022-003][adr-rounds] の確認方法） | `fix` の印（往復の回数）、`review` の印、`sessions.jsonl` の作業 AI（衝突の解消は `rebase-pr-<PR の番号>`）、`runs.jsonl` の Issue ごとの結果（止めた理由）、Project の Status |
| 修正工程（段階 7）とマージ判定工程（段階 8） | マージの判定と人の操作が合ったか。修正工程（段階 7）は印を書かず毎回の実行で判定が重なるので、PR と head ごとに最後の判定を 1 件として数える | `runs.jsonl` のマージの判定、`merge` の印、PR のマージと「判定と違う判断」のコメント |
| マージ判定工程（段階 8） | revert（マージから 14 日以内に、`develop` にその squash の commit を revert する commit か、本文でその PR の番号を「戻す」と言及する fix の PR がマージされたもの） | base ブランチの commit の履歴（進行 Bot の clone）、マージされた PR の本文 |
| 並列化（段階 9） | 連続 7 回の実行で `needs-human` が 0 件か、利用枠が上限の内か（[FLOW-12][flow]） | `runs.jsonl`（止めた理由）、`sessions.jsonl`（費用） |

- どの行も、受け入れの依頼の実行（`runs.jsonl` の起こされ方が受け入れの依頼のもの）と、受け入れの依頼の実行のセッション（名前が `verify-intake-issue-` で始まるセッション）を除いて数える。除くのは、`outputs/` の受付 AI を数える行（受け入れ工程（段階 4）の方針に係る要望の判定と `agent-ready` の比べ、計画・実装工程（段階 5）の `plan=` の判定への異議など）と、`runs.jsonl` を数える行に当たる。人の確かめの助けとして起こしたセッションで、Issue に書いた下書きと結びつかないため（[ADR-20261022-004][adr-intake-req] の決定 4）。待つ時間を過ぎた依頼を消して作業に入った実行は、起こされ方が定期なので数える（[ADR-20261022-004][adr-intake-req] の決定 5）
- 記録を消す時期は決めない。段階の出口と見直しに使うため。古い実行の分だけを移すことはしない。移した実行の費用と失敗の回数が、開いている Issue の累計から黙って減り、上限が効かなくなるため。大きくなりすぎて移すときは、記録の置き場の全体を移し、`setup` で記録のフォルダと記録の目印のファイルを作り直す。目印のファイルが新しくなるので、着手した Issue は `records-missing` で止まり、人が失ったことを認めて戻す（「[AI のセッション][design-ai]」の「起動の前の確かめ」）
